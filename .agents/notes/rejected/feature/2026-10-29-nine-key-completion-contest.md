# Agent Note: 九宫格停在声母上时让「增强」的键盘模型给首页补全行排第一

Status: rejected — 打字流里主配置有净收益，但冷启动的 prefix 两份集合 top1 掉 0.50–0.58pp，聊天九键主配置的按块区间下界 −0.65pp，按事先写下的门不改

## Problem

九键打字流（`typing_sim`）里三成的块停在末音节声母上，缺口分析把「金标准补全排在别的补全后面」（E1）列为主配置里九键特有的一大类：打 `963` 想要 我都，首位是 我的。首页里的补全行是词典行，回答整个按键（九宫格里补全也吃掉全部数字），所以首行是可信词典命中，runtime 的键盘模型碰不到它。[补全行往后排](../bug-fix/2026-10-29-nine-key-completion-order-in-typing-flow.md) 结尾写了「真正能两头都赢的是停在声母上时按上下文挑补全」，这次用现成的 4.49 MB 模型量这一条。

## Proposal

和 [最近选择裁决](../../implemented/feature/2026-10-29-nine-key-model-contests.md) 同一套机制（引擎标 `candidate_contest`，runtime 只在标记的行之间用模型挑）：首行是没有固定的词典补全行（规范读音的组码比覆盖的数字长）时，首页里所有同样条件、字数与首行相同的补全行都参与，挑战者逐字平均对数概率比首行高出 margin 才提到首位。

事先写下的三臂（研究目录 `RULE.md`）：C1 m=0 无权重门，C2 m=0 且 w/w首 ≥ 0.1，C3 m=1 无权重门。dev 选臂，test 只看一次；门是九键 test 合并为正、12 格按块配对 95% 区间下界 ≥ −0.5pp、`convert_eval` 四份 found 和 top6 不少且 top1 不低于基线 0.5pp 以上、M4 Pro 按键 p95 增量 ≤ 2.5 ms。

## Alternatives considered

- **补全和拼满的读法混在一起比**：九宫格里两者都回答按键，但模型分数按字归一，补全只在同一前缀的补全之间才可比（chinese-ime-lm 文档的第一个陷阱），没有跑。
- **只比 ≤ 2 字的补全**：计划里提过；评测里停在声母上的块多数是一两个字的词，按字数相同限制已经差不多是这个范围，没有另开一臂。

## Acceptance criteria

见上面的门。

## Risks

- 冷启动、没有上文时模型只能凭字频挑，正是 `trusted_leader` 想挡住的情形。

## Evaluation and rejection

dict-v2.0.39，手机出厂配置，学习开，`--model keyboard`，基线 A0 是 develop 52a78a2fc9 只开 runtime 层。dev（九键 4 格合并 7942 字）：C1 +0.29pp，**C2 +0.40pp**，C3 +0.24pp，选 C2。一词一块不简拼的两格没有停在声母上的块，三臂都是 0。

两条门没过：prefix 集合 top1 的降幅超过 0.5pp，聊天九键主配置区间下界 −0.65pp。延迟（三个裁决点合起来量）没有问题。按规则不改。

dev 上的例子：赢 之间（直接 → 之间）、区别（如此 → 区别）、请问（情绪 → 请问）、时候（是个 → 时候）、火锅（混合 → 火锅）、冰箱（并在 → 冰箱）、客厅（课题 → 客厅）；输 觉得累（觉得冷）、教授（减少）、发现（大学）、使用（是在）、我妹妹（我每年）、用户（综合）。赢的多是上文给出了话题，输的是上文不够、模型按字频把更常见的词提上来。

### 以后再碰这里

- 打字流里有上文时它是净赢（主配置 4 格全正），冷启动时是净输，结论取决于上文有多长；换一个更会用上文的模型（计划的第 2 阶段）之后值得重量。
- 门里的 prefix 集合是冷启动、没有上文的；如果以后把门改成看打字流，要先改门再量，不能看了结果再挑口径。
