# Agent Note: 九键补全行在打字流里进一步往后排

Status: rejected — 严口径下 complete2 的收益不存在，首页内的七种加大折算都没让分块打字变好，按事先写下的规则不改

## Problem

九键打字流评测（`typing_sim`，在未合并的 `test/typing-sim-eval` 分支上）的缺口分析里，oracle「complete2」看起来是排序上最大的一项：不打切分时也把多音节补全排到同覆盖的完整读法后面（`rank_key_for_reading` 的 `completion` 改成 `(prefer_exact || canonical.contains('\''))`），主配置 CFA 0.601 → 0.616（Tatoeba）、0.608 → 0.630（聊天）。它是整张表的硬分档，正是 [首页内折算](../../implemented/bug-fix/2026-10-27-nine-key-completion-discount-on-first-page.md) 否掉的第一轮做法：停在声母上的金标准会被挤出 `CANDIDATE_LIMIT`。所以要找一种只在首页里调序、召回不变、又保住这份收益的做法。

后来打字流评测把主口径改成严口径：一块里补完简拼或锁过拼写之后点到的第一位不再算首选。complete2 的数字是按宽口径量的。

## Proposal

在首页内（`discount_completions_on_first_page`）把首页里覆盖全部数字的拼音词典行分三类：E 拼满的完整读法、S 单音节补全、M 多音节补全（都不算锁定的音节）。调序键改成 E: w·Kp·Km，S: w·Km，M: w；Kp 只在首页有拼满的多音节词时生效（即 #10110 的条件和倍数，现状 Kp=6、Km=1），Km 让多音节补全在任何首页里再打一次折。∞ 表示该类整个排在后面。首页由哪些行组成、候选表截到哪里都不变，所以 `found` 和首页 6 行的 top6 从构造上不变。

### 事先写下的选择规则

规则在跑任何一臂之前写在研究产物 `RULE.md` 里（sha256 8419b522…）：

- 臂：A0（6, 1）现状，A1（16, 1），A2（∞, 1），A3（6, 2），A4（6, 4），A5（6, ∞），A6（16, 4），A7（∞, ∞），另跑 complete2 本身（R）作参照、不参与选择。同一个探针二进制，只换环境变量。
- 资格门：`convert_eval` 的 `nine-key-prefix`、`fourteen-key-prefix` 的 found 和 top6 一条不少；`nine-key` 的 top1 不降；一词一块不简拼的 test 严口径 CFA 两份不降；`3` → 的 成立。
- 目标：主配置 dev 部分 Tatoeba 加聊天合并的严口径 CFA 增量最大；相差 0.10pp 以内取更靠近现状的（少改一个开关、倍数小的优先）；最大增量不到 0.10pp 就不改。
- 验证：选中的臂在主配置 test 上两份都要高于 A0，否则不改。

## Alternatives considered

- **complete2 原样（整张表硬分档）。** 宽口径上它确实最好，打全读音的词级 top6 也 +88 条。但它就是被否过的第一轮：`nine-key-prefix` found 少 144 条、top6 少 190 条，`fourteen-key-prefix` found 少 61 条。严口径下它在主配置上是负的（见下）。
- **把补全排序交给模型或上下文（缺口分析里的 E1）。** 停在声母上时该给哪个补全，要看前文，这一项要新数据或让模型参与补全行排序，不在这次范围。
- **调小 #10110 的倍数（K<6）。** 打字流里简拼占三成，按 #10110 的贝叶斯推法倍数应在 2.3 上下，但 K<6 会让词级集 `nine-key` 的 top1 回落（K=1 是 0.5185 对 0.5392），过不了本轮的资格门，没有跑。

complete2 在简拼的块上宽口径 +4.0pp、严口径 −3.5pp：用户在候选栏找不到要的词、把简拼补完之后，整张表里完整读法领先，补完后点到的第一位多了；严口径不算这些字，而停在声母时第一眼就对的字少了。打全的块上各臂只多 0.3–0.5pp。打字流里三成的块停在声母上，首页内无论怎样加大折算，打全那边的收益和简拼那边的损失差不多相抵；一词一块不简拼和打全的词级集上它是净赢，所以这件事取决于用户多常停在声母上，而这个比例没有设备数据。

### 以后再碰这里

- 不要再用宽口径的 complete2 数字当收益依据；任何补全排序的改动都要报严口径，并按块是否简拼拆开。
- 拿到设备上的 `chars_per_commit` 和停在声母上的比例之前，改倍数只是在两种用户之间换。
- 真正能两头都赢的是停在声母上时按上下文挑补全（缺口分析的 E1，当时按宽口径估的上限约 4 个点），那要新数据。
