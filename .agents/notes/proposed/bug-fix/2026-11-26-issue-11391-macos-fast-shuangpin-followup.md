# Agent Note: 跟踪 macOS 快速双拼输入异常

Status: proposed

## Problem

Issue #11391 报告 macOS 26.6、水杉 0.59.4、微软双拼下快速输入时字母被错误分词、被当作英文候选或候选窗口不显示。报告没有给出最小按键串、异常时预编辑文本、编辑器或输入源切换上下文，因此不能确认是双拼方案读取、输入源切换状态还是候选窗口更新造成。

## Proposal

把本 issue 记录为待复现调查，并用当前 `develop` 的代码核对已经落地的相关修复：

- #11333 已让首个会话读取最新双拼方案。
- #11336、#11341 已处理输入源切换时的字母和方案上下文。
- 双拼完整输入判定和候选查询的回归覆盖微软双拼与合成 ASCII 输入，候选窗口路径已有 macOS 专项测试。
- 现有报告来自 0.59.4，而上述修复在之后的版本才进入发布版本。当前没有报告者在 0.60.x、nightly 或 `develop` 上重新复现的证据。

下一步只收集合成复现资料：

1. 在最新 nightly 或 `develop` 构建上使用公开词语或合成按键串，例如 `nihao` 或 `j;gk`，记录完整预编辑文本和异常候选列表。
2. 记录异常是否只发生在刚从 ABC 或其他输入源切回后，以及是否只发生在微信、浏览器、终端或所有编辑器。
3. 开启诊断日志后复现一次，只提供 `[key-latency]`、候选窗显示/隐藏和输入源状态行，删除输入内容、账号和私人路径。

如果较新版本已不再复现，则用报告者复验结果关闭 issue。若仍能以合成输入稳定复现，再为确定的根因写 `Fixes #11391` 修复 PR。

## Alternatives considered

- 直接调整双拼切分或候选窗口刷新。当前缺少异常输入和预编辑状态，无法判断修改哪条规则，容易破坏已有双拼回归，因此不采用。
- 把 0.59.4 的报告直接归因于 #11333、#11336 或 #11341 并关闭 issue。报告者尚未在包含这些修复的版本上复验，不能把版本时间关系当作修复证据，因此不采用。

## Acceptance criteria

- 报告者在包含相关修复的版本上完成一次合成输入复验，或提供可重复的最小按键串。
- 可复现时新增行为回归并定位具体责任层，再另开实现 PR。
- 不可复现时记录复验版本和结果后关闭 issue。

## Risks

在没有最小复现前改动切分、方案或候选窗口逻辑，可能重新引入输入源切换和快速双拼已有回归。
