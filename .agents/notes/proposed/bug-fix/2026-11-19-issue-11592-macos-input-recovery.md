# Agent Note: #11592 macOS 输入法失效调查

Status: proposed

## Problem

#11592 报告 macOS 27.2.1 上输入法不定时失效且无法切换，原始报告只说“最近几个版本都是一样”，没有具体构建号。维护者在 2026-11-18 请求补充构建号、输入源菜单状态、系统输入法对照、受影响 App 和诊断事件后，报告者在 2026-11-20 补充了以下信息：

- 受影响 App：所有 App 都会出现，不限于特定编辑器；在不同 App 的可输入位置之间切换，偶尔能恢复，但很少。
- 恢复方式：有一次从系统设置的输入源列表删除水杉再重新添加后恢复；大多数情况需要重启系统才恢复。
- 输入源菜单状态：报告者不确定菜单图标，只说明失效时仍能输入英文，表现与 issue 截图一致。

仍然缺少：具体构建号、是否能切换到系统自带输入法的明确结论，以及删去输入内容和私人路径的 `focus_in`、`keyboard_loaded`、输入源切换日志。

“所有 App 都受影响、删除再添加输入源或重启系统才恢复”这组特征指向系统级的输入源注册或输入法进程状态，而不是单个宿主的 IMK 会话问题，但在拿到构建号和诊断事件前仍无法确认具体路径。

#11464（macOS 26.7.1、水杉 0.59.4 下输入法变灰、无法切换或重新加入）中，#11592 的报告者在 2026-11-18 留言称是同一个 BUG（使用 86 五笔）。#11464 由独立的跟踪 PR #11704 记录。维护者在 #11464 的调查留言中提到 2026-11-10 合入 develop 的 #11231 进程退出收尾修复（正常退出、`SIGTERM` 和崩溃路径最后都用 `SIGKILL` 收尾，避免 `imklaunchagent` 累计死亡次数后把输入法模式置灰）；按 git 标签，该提交（`5a24389143`）已包含在 `macos-v0.59.3` 及之后的 macOS 发布中，而 #11464 的报告环境正是 0.59.4，因此 #11231 本身不足以解释这类失效，仍需要报告者环境中的状态和日志。两边的恢复表现也不完全一致：#11464 的报告说删掉重新加入也不行，而 #11592 的报告者有一次删除再添加后恢复。两个 issue 的现象是否同源，需要以复测结果和诊断证据为准。

## Proposal

本笔记作为 #11592 的跟踪记录合入 develop。修复在单独的 PR 中进行（正文写 `Fixes #11592`），前提是先拿到以下证据之一：

- 报告者确认的具体构建号，以及在最新 nightly 或预览版上是否仍复现；
- 失效期间输入源的注册与启用状态（`check_input_source.swift` 能区分的未注册、无可选模式启用、部分模式关闭），以及失效前后输入法进程是否重启；
- 删去输入内容和私人路径的 `focus_in`、`keyboard_loaded`、输入源切换日志片段。

拿到证据后，按其指向的输入源注册路径或输入法进程生命周期做最小修复并补回归测试；在此之前不改重启或重注册逻辑。若与 #11464 确认同源，两边共用同一个修复 PR，并同时关联两个 issue。

## Alternatives considered

- 无条件重启输入法或重新注册输入源：可能掩盖输入源状态、`imklaunchagent` 或进程崩溃的真实原因，且会影响所有 macOS 用户。
- 直接把 #11592 当作 #11464 的重复关闭：报告者认为是同一问题，但两边的 macOS 版本不同（27.2.1 与 26.7.1），#11592 的构建号也未知，在复测前合并会丢失这份独立报告。

## Acceptance criteria

- 获得能定位到输入源注册、输入法进程生命周期或特定宿主的证据（构建号加复测结果，或状态与诊断日志）。
- 修复 PR 覆盖该路径，并有 macOS 回归测试及适用构建验收。
- 明确 #11592 与 #11464 是否同源，并在两个 issue 中互相引用结论。

## Risks

未经复现的恢复逻辑可能破坏正在进行的组字、输入源选择或其他 App 的 IMK 会话。报告者说明“删除再添加输入源”能恢复，若据此在产品中自动重注册输入源，可能在系统设置里反复增删用户的输入源配置。
