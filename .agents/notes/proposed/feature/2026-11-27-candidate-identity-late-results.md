# Agent Note: 候选身份与晚到结果规则

Status: proposed

## Problem

Issue #11819 要求统一停顿重解、在线候选、按文字选词和候选身份的规则。当前实现已经让 `Runtime` 为候选快照维护带代次的 `CandidateId`，并在若干宿主中暂停按住期间的异步刷新，但共享层仍有几条相互耦合的现状：

- `settle_deferred_scorer` 的每一片都会推进候选代次，即使候选文字没有变化。macOS 依赖延后重排的 `view`，Android 和 Rust 回归也覆盖了这一行为。
- `dispatch` 会在非打字派发前摘下延后模型，读音行选择可能先按无模型顺序显示，再在下一次停顿恢复模型顺序。
- 云占位行、AI 行和尾部展开会改变座位，宿主要按可见行处理，不能把引擎下标直接当作用户看到的位置。
- 共享接口目前主要按 `(session, generation, index)` 选择，Windows 已有按文字匹配的宿主侧规则，其他宿主仍各自绑定槽位或代次。

## Proposal

把 #11819 作为共享 `input-runtime`、`host-api` 和宿主之间的设计记录，先确定规则再拆实现切片。实现顺序建议如下：

1. 定义候选身份的稳定字段。身份至少要包含当前会话代次、候选文字、来源和必要的编码或出现序号，明确同词不同来源、多次出现和云占位的处理。按文字找回必须由共享层核对当前快照，不能让宿主自行猜测。
2. 区分用户可见候选与引擎内部座位。候选页、展开列表、数字键、方向键和在线占位统一走可见行映射。任何晚到结果都必须说明是追加、替换或重新排序，并保留已显示候选的身份。
3. 明确代次推进条件。候选文字、来源或选择身份发生变化时必须使旧选择失效；只更新不影响用户可见候选的元数据时不应让宿主点击失效。这个决定需要更新 macOS、Android、HarmonyOS 和 Rust 现有回归，而不是只改 `Runtime` 的计数。
4. 让非打字派发保留延后模型的排序上下文，或明确它必须立即完成重解。读音行选择、云/AI 回包和停顿重解要有同一份上屏前规则，尤其是未完成重解时空格是否选择画面上的首选。
5. 逐宿主迁移选择入口。共享 C ABI 先提供“按期望文字和来源选择当前候选”的结果码，宿主再把鼠标、数字键、读音行、硬件键和长按都绑定到画面中的身份。旧的代次/索引接口在迁移期间保留兼容路径。

每个切片都要有合成候选和延迟回包测试，覆盖候选未变、同词不同来源、云占位、AI 尾部、滑动页、读音行、停顿未完成、旧代次选择和按文字找回失败。六端的设备或宿主测试分别验证用户看到的候选与上屏文字一致。完成这些规则后再为共享引擎或各宿主开独立实现 PR，并在对应 issue 中逐项回填。

## Alternatives considered

- 只让每个宿主继续按槽位冻结候选。改动较小，但会保留共享层与宿主身份不一致，在线候选和读音行仍会选错词，因此不采用。
- 只禁止代次递增。候选座位仍可能被替换，旧索引会指向另一条候选；还会破坏现有旧回包失效保护，因此不采用。
- 立即把所有宿主改成按文字选择。没有先定义来源、重复词和云占位规则，宿主会各自实现不同的匹配谓词，因此先保留设计切片。

## Acceptance criteria

- 共享层有明确的候选身份、可见座位、代次推进和晚到结果规则。
- C ABI 与 Host API 能表达按身份选择成功、身份过期、文字不存在和来源不匹配等结果。
- macOS、Android、HarmonyOS、Windows、Linux 和 iOS 的候选显示、数字键、点选、读音行与上屏行为由同一规则覆盖，并有对应回归。

## Risks

代次和身份是跨平台输入协议的一部分。若只修改某一个宿主，旧 ABI、异步回包和其他平台仍可能把同一点击解释成另一条候选，造成静默错选或点击无效。
