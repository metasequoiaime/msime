# Agent Note: Android 键盘内拍照与可选离线 OCR 模块

Status: proposed

## Problem

#9207 要求在键盘区域完成相机预览、拍照、离线识别和选字上屏。报告人的补充明确要求模块不进入基础安装包，由用户从本项目 GitHub 下载后手动导入。外部相机应用、仅导入图片或 Google Play 按需下载不能代替该流程。

## Proposal

先在 API 28 和 35 上验证一个独立 OCR 模块能否通过公开接口、隔离的类加载器及自己的资源和原生库运行，同时保留已经初始化的手写识别器。试验模块使用固定的 `com.google.mlkit:text-recognition-chinese:16.0.1`，以中文与拉丁文字合成图验证真正识别；宿主探针不申请网络权限。探针不是产品验收，不包含相机或编辑器插入，也不代表已经实现本 issue。

候选模块接口只传递 Android `Context`、`Bitmap` 和文本行，不暴露 Google 类型。基础 APK 不依赖 OCR 模型和运行库；普通 Gradle 构建不包含试验模块。正式导入需要核验项目分发的模块身份、接口版本、ABI 和完整性，限制读取大小，先发布完整版本再切换，输入法进程只读。相机仅在用户打开面板并授权后工作，关闭面板或切换编辑器必须停止相机、取消识别并拒绝迟到结果。识别内容只在当前面板中待选，不写日志或自动复制。

宿主沿用手写依赖的自动 Provider 初始化，不能对已经存在的宿主容器重复调用 `MlKit.initialize`；公开初始化只用于尚未初始化的独立模块类加载器。探针识别断言同时要求合成英文单词、数字和中文，不能只认出数字就报告英文识别成功。手写检查只创建客户端，不等于已有手写模型的实际识别已经验收。

ML Kit 的公开初始化仍通过宿主包的 `MlKitComponentDiscoveryService` 元数据发现组件。正式宿主与探针一样声明 `VisionCommonRegistrar`、`TextRegistrar`，仅组件名进入基础清单，OCR 类和模型只在模块内。各类加载器忽略自己不可见的声明，保留原手写组件。产品专项同时检查 OCR 前后的宿主手写客户端创建，不能只凭独立探针的组件声明就推断正式宿主也能初始化。

模块自己的类加载器在进程内复用公开 SDK 容器，只有首次初始化调用 `MlKit.initialize`；关闭后重新创建识别器或模块实例不重置该容器。多字号探针在用例之间关闭并新建模块实例，覆盖连续打开工具的生命周期，而不是只测进程内第一次调用。

参考实现固定为 `LeanBitLab/LeanType@be774536dfb415634da176831852e0b8eed247dc` 及 `LeanBitLab/LeanType-OCR-Plugin@968949a7b54b8f0e3a4a5063ca03812554cf23ef`，仅用于研究，不复制未提交源码。其插件使用 ML Kit 私有初始化和识别文本日志，不沿用这两点。公开初始化接口见 [Google MlKit API](https://developers.google.com/android/reference/com/google/mlkit/common/MlKit)；模型安装方式见 [文本识别 Android 指南](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)。

## 产品接入边界

产品分支接入键盘内相机和主进程导入页，但在真实设备验证及正式模块分发完成前保持提案状态。`resources/ocr-module-android.lock.json` 的 `artifact: null` 明确表示尚未提供配套模块：共享层不列出、不安装、不导入它，设置页不能选择任意 APK 绕过检查。此时没有下载地址，也不能宣称 #9207 已交付。

导入复用 `resource_packs::import` 的固定长度、完整 SHA-256、限长暂存和整体替换。正式锁由源码审查固定本项目 GitHub Release 的已审计产物，完整摘要才是运行时的信任依据；接口版本为 1，仅支持宿主已有的 `arm64-v8a`、`x86_64`。主进程导入后将 APK 封为只读；输入法加载前通过新增的 `resource_pack_verify` 再读全量摘要，并拒绝有写权限的 APK。暂存清单和文件选择器提供的名字均不能决定信任。Play 分发不提供外部可执行模块，Java 安装入口和运行库入口也拒绝该渠道，不能只隐藏按钮。

原生库从只读、未压缩且已对齐的 APK 内部路径映射，不在输入法进程中解压或写文件。这个路径仍需 API 28/35 产品验收，若任一 API 无法加载，不能以扩大动态代码写入权限绕过。隔离类加载器在进程内复用，识别器按任务关闭；不触碰原宿主的手写单例。

共享资源包枚举也由桌面设置编译。桌面的 `offered_by` 明确拒绝 Android OCR 模块，三个桌面平台的既有资源包筛选回归同时覆盖它，避免新增枚举造成桌面编译遗漏或错误提供模块入口。

面板使用专用相机线程，拍照后释放相机，图片仅在内存中按尺寸限制解码并处理 EXIF 方向。识别结果绑定面板代次和输入连接；`onStartInput` 的保留组字早返也先作废 OCR。关闭面板、窗口隐藏、`onFinishInputView`、停止会话和销毁都会释放相机并清空结果。用户可以勾选识别行或长按选取部分文字，确认后才经现有上屏入口插入。

设备验证使用当次构建模块的完整摘要生成临时源码锁，随后构建原生产品；这个测试清单不提交到产品锁文件，不把合成模块伪称为已发布资产，也不在运行时添加任意路径或跳过校验的测试开关。测试清单里的保留域名 `example.test` 仅标识合成夹具，共享层和 Java 层都拒绝 OCR 自动下载，不会访问该地址。模拟器通过官方 `-camera-back imagefile:<path>` 输入固定合成图，实走相机拍照回调，而不以预设的识别文本代替图片推理。专项另经可访问性接口选择识别文本中的固定数字并只上屏所选部分，保留独立截图；预览期间隐藏键盘后重新打开相机，以区分面板关闭释放和拍照完成释放。撤回相机权限会终止目标进程，因此脚本在两次 instrumentation 之间撤权，再检查原生入口显示授权提示且不创建相机预览。这些检查均以设备实际结果为准，源码存在不等于已经通过。

## 产品设备证据

[API 28/35 第六轮产品专项](https://github.com/metasequoiaime/msime/actions/runs/40088444305)已通过固定摘要导入、只读 APK 原生库映射、完整中英文静态合成图识别、重开和错误替换拒绝。两版均完成真实相机拍照、完整 `SYNTHETIC OCR 2468` 识别及整行上屏，再通过可访问性接口只选择 `2468` 四字符并精确上屏；照片、预览、结果和编辑器截图均保留。OCR 前后只验证宿主手写客户端创建，没有手写模型实际推理证据。

设备截图发现的两个产品缺陷已经修正：公用 `s.button` 使用横排零宽权重，OCR 的单项动作必须各自放入横排，不能直接挂到纵向面板；SurfaceView 的独立 Surface 不能依赖父容器裁剪，预览必须保持比例完整容纳在框内。相机同时选择与照片比例匹配的预览尺寸，首帧到达后才启用拍照。第五轮及第六轮截图确认按钮可见、预览留在键盘内。[第五轮](https://github.com/metasequoiaime/msime/actions/runs/40086972668)导出的同类相机 JPEG 已在 OCR 前截断测试图右侧，夹具因此把同一完整字符串放入已确认可见的源图区域，完整期望与精确断言不变；原图和失败照片仍保留，不能将裁剪归为模型精度问题。

第六轮随后停在隐藏后重开：日志显示编辑器 `START` 发生在 HOME 任务真正切换之前，稍后的 HOME 又盖住编辑器，失败截图确实停在桌面。专项现在等待桌面取得焦点且输入法窗口消失后再启动编辑器，分别保留隐藏和重新取相机的截图；切换编辑器时也检查迟到结果不会重建 OCR 面板。这个调整修正测试时序，不放宽相机恢复断言。恢复、切框与撤权检查仍需下一轮设备结果，源码已包含不等于已通过。

[固定干净基点的基础输入对照](https://github.com/metasequoiaime/msime/actions/runs/40082820419)在两版均复现 `phrase composition` 失败；OCR 专项和完整基础冒烟必须分别报告。产品分支同步 `develop` 时，JNI 校验清单同时保留新账号接口与 OCR 校验接口，合并结果需要重新检查，不能沿用旧基点的设备证据。

## Probe invocation

只在专用的 `x86_64` API 28/35 AVD 中运行 `bash platforms/android/tests/device/ocr-runtime-probe.sh <serial>`。脚本用仓库已有的 Gradle wrapper 显式启用 `-PmsimeOcrProbe=true`，分别构建、检查两个试验 APK，导入的模块文件放在标准 `target/android/ocr-probe-assets` 下。该脚本只清理两个试验应用的数据，不安装或修改产品 APK，也没有相机或编辑器验收。

普通捆绑 SDK 对照只进模块的 `debug` 构建。两种方式使用同一份生成夹具；探针产物允许导出它自己生成的固定图片及其合成识别对照，不接受外部文件或用户图片，不在运行库中记录识别文本，也不把任意异常消息写入日志。这样能分别判断模型的识别偏差和动态模块加载问题，而不会把生产输入泄露到测试产物中。

原始 88 px 文字夹具在 API 28/35 均存在模型误识别；普通捆绑与动态模块的结果逐字一致，图片也逐字节一致，因此不能把该偏差归因于类加载器。保留这张原图及其失败结果，并增加内容不变、字号为 44 px 和 22 px 的两个用例。运行库探针要求所有图片、所有识别结果均与普通捆绑方式一致，且至少一张图片同时正确识别完整英文单词、数字与中文；不把几张图的局部成功拼成完整成功，不把运行库等价解释为模型精度通过。产品的识别质量、手写实际推理及真实拍照仍需独立验收。

API 35 的普通捆绑与动态模块均在三个字号输出同词的 `測/测` 字形差异，较小字号的完整英文均匹配；API 28 则在大字号出现 `文/丈` 的实质误识别。内容可用门禁接受「测试」的规范简繁字形组合，仍拒绝 `文/丈`、`O/0` 这类不同字词；逐图另报是否与简体原文完全一致，保留原始合成输出。这只调整探针对同义字形的判断，不转换、改写或纠正运行库返回的文本，也不把简繁混用视为产品精度已经验收。

API 28/35 的[最终隔离探针](https://github.com/metasequoiaime/msime/actions/runs/40074617788)均通过。每个 API 先用固定的旧模块源码复现关闭后重开时的 `IllegalStateException`，再恢复当前源码，断言没有残留源码差异，运行修正后的完整探针。三张合成图片逐字节一致、全部识别结果与普通捆绑 SDK 对照逐字一致，OCR 前后的手写客户端创建也通过。API 28 的 44 px 用例与简体原文完全一致，API 35 的较小字号识别内容匹配但含 `測/测` 字形差异；原始大字号与其他字号的误识别仍保留。首次宿主重复初始化和后续模块重开失败都是已复现并修正的探针问题，不是产品验收。

## Alternatives considered

- **用同发行者 APK 签名放行多个模块版本**：可避免宿主每次固定模块摘要，也能复用系统验包；但还需确认最低 API 的验包语义、签名轮换和接口兼容。本次选择共享层已有的固定完整摘要机制，信任边界随宿主源码审查，尚未提供产物时明确拒绝。
- **在基础包内捆绑 OCR**：使用官方默认初始化，接入和设备兼容验证最简单；但违反报告人明确的可选模块与基础包体积要求。
- **原样加载参考插件**：已经包含多语言模型和 APK 加载流程；但接口示例与实现不一致，且会操作私有 ML Kit 状态、记录识别文本，不能直接采用。
- **ONNX 开源 OCR 模型与现有可选运行库**：模型许可和推理链更可控，并能避免 Google SDK 的诊断收集；现有语音 API 不能直接执行 OCR，还需要检测、裁剪、矫正与识别管线。保留为真实备选，公开 API 探针或隐私、许可边界不能满足要求时重访，尚未否定。
- **安装另一个 OCR 应用并绑定服务**：SDK 初始化和权限可按应用隔离；但增加系统安装流程，与用户要求的手动导入资源模块有差异，尚未作为实现方案。

## Acceptance criteria

- 不装模块时基础输入法可用，基础 APK 不包含 OCR 模型、OCR 原生库和识别依赖；不自动下载模块。
- 用户手动导入项目配套模块后，在键盘内授权相机、拍照并离线识别中文和英文，选择部分文字或全部上屏，保留当前编辑器焦点。
- API 28/35 真实设备验证导入、损坏/错误 ABI 拒绝、撤权、相机释放、会话切换、迟到结果以及手写识别共存；完整门禁和产品入口验收仍必须补齐。
- 分发前记录实际引擎、模型和全部依赖的固定来源、许可、通知与分发限制；不把示例代码许可证当作 Google SDK 或模型许可证。

## Risks

动态模块在 Android 14 起要求代码文件只读。隔离探针已在 API 28/35 完成模块资源、原生库和公开初始化的加载；正式模块导入与原生输入法进程中的运行仍需设备验证。官方说明识别输入和输出留在设备，但 SDK 仍可能收集诊断数据；无网络探针通过不能证明有网络权限的正式输入法进程绝不发诊断请求，正式方案必须处理并披露这一边界。原生相机生命周期和焦点代次已经接入，但尚未通过产品设备验收；已有模型的误识别与简繁混用需要单独评估。
