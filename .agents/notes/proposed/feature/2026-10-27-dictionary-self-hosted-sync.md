# Agent Note: 自建存储个人词库同步方案

Status: proposed

## Problem

#9880 要求在多个平台之间通过自选存储同步个人词库，明确同步对象、冲突合并、删除传播和凭据保管。现有账号云词库绑定水杉账号，而且合并模式只加词、不传播删除；[WebDAV 云剪贴板](../../implemented/feature/2026-10-26-cloud-clipboard-webdav.md)和自建中继处理加密剪贴板，没有离线合并语义，不能当作词库同步已经实现。#9989 也提到常用词库，剪贴板那部分见 [自建存储云剪贴板同步方案](2026-10-27-clipboard-self-hosted-sync.md)。

难点在于网盘没有服务端逻辑，设备会长期离线、随时崩溃，Engine 的个人词库又有十几条写入路径（设置页、导入、MCP、候选栏删除、集合、账号云词库合并、打字自动造词），而且不区分用户显式加的词和打字自动造的词。坚果云免费账号每 30 分钟 600 个请求、与所有第三方应用共用，`If-None-Match` 被忽略，`GET`/`HEAD` 没有 ETag，根目录下的文件夹删不掉。

## Proposal

维护者已定：只同步「我的词条」；端到端加密并复用云剪贴板的设备批准；六个平台都要能驱动同一个核心；自动加手动触发；首版只做 WebDAV（坚果云、Nextcloud）。契约（存储布局、记录、合并规则、上限、请求量）写在 [`docs/dictionary-webdav-sync.md`](../../../../docs/dictionary-webdav-sync.md)，这里记各项怎么定的、为什么。

本篇拆成两个 PR 落地，所以仍是 proposed：第一个 PR 交付协议、不碰网络和 Engine 的状态机（`client-core::cloud::dictionary_sync`）、文档和多设备模拟测试；第二个 PR 交付 WebDAV 传输、词库密钥串、偏好、Engine 一侧的本机词库和 C 接口，届时转 implemented。各平台的界面和触发接线在之后按平台各开 PR。

### 同步对象

同步的是「我的词条」列表里看到的那些：Engine 日志里 `user_inserted` 的词条，以及它们的删除。打字自动造的词也在里面——Engine 对它们和用户显式加的词写的是同一种行，列表里也不区分，要排除就得先改 Engine 的写入格式，首版不做；被同步的仍只是词本身，打字学到的权重、候选顺序、固定位置、选择次数一律不同步，符合「不同步打字学到的频率、权重和顺序」。身份是（词库类别、编码、词），类别就是 Engine 的五个词库（`pinyin`、`wubi`、`wubi98`、`quick`、`english`），这也是「词条所属的词库类别」的含义；用户命名的词条集合是 client-services 自己的元数据，首版不同步集合本身，集合里的词照样作为词条同步。对主词库词条的删除和改权重属于主词库，不同步。

### 时钟与冲突

每条操作带混合逻辑时钟时间戳：高位 Unix 毫秒、低 10 位计数，整个值不超过 2^53 - 1。本机生成取「比见过的都大、不早于本机时间」；收到操作就把本机时钟推到它之后；时钟随同步状态原子写盘，重启和系统时间回调都不会倒退；不在合法范围的时间戳整条跳过；快于本机一天以上只提示、不改合并。重装是一个新的设备编号，第一次加入前先读完日志或检查点、推进时钟（从检查点开始时取检查点里最晚的时间戳），再记录本机的词。

每个词条是最后写入者胜的寄存器，删除也是写入（墓碑），按（时间戳、设备编号、是否存在）比较；平局时设备编号大的胜，同一设备同一时间戳「存在」胜过「删除」。合并与到达顺序无关、重复合并不改变结果。改编码就是删旧加新。合成示例（文档里有完整的表）：B 10:00 改编码、A 10:05 删旧词条，结果旧词条删除、新编码保留；同一词条一删一加，晚者胜，与谁先上传无关。

### 发布、恢复与版本

一个事件一个不可变文件 `e-<12 位序号>.json`，独占创建下一个序号（`PUT` 临时名加 `MOVE` 带 `Overwrite: F`，与云剪贴板同一条代码路径），没抢到就重读再试。事件用哈希串成链；本机读过的最后一个事件消失、列表跳过一个直接 `GET` 也不存在的序号、检查点的位置或代数变小，都是 `dictionary_sync_rollback`——链头只挡得住改写，挡不住截掉尾部，后两条是为此加的。重复操作靠（设备、时间戳）认出：本机写成的事件在下一次读到时从待发送里去掉，所以发出之后、写盘之前崩溃不会重发。`format.json` 版本不认识就不读不写；已经在运行的客户端靠带 `upgrade` 的封口事件得知格式升级。

本机的应用顺序是：记录本机改动并写盘 → 拉取并与位置一起写盘 → 分批写进本机词库、写好才计入 → 发送 → 封口和清理。远端改动在写进 Engine 之前只存在于共享状态里，本机确认的位置只在 Engine 写好之后推进。每一步之间崩溃，下一次重新比较就接上；模拟测试在每一次写盘处注入崩溃验证不丢也不重。上限：一个事件 1000 条操作、明文 256 KiB、文件 512 KiB；检查点 32 MiB、30 万个词条、64 台设备；列目录 2 MiB；共享词库 10 万个词条以内收新词；待发送 2 万个词条；一次写进 Engine 128 项。

### 捕获本机改动：三方核对而不是在写入点挂钩

本机记着「认为本机词库里有哪些词」（`applied`）。本机词库相对它的变化是本机改动，记成操作；共享状态叠上待发送操作相对它的变化，是要写进本机词库的远端改动。宿主在用户改词后马上调用一次只做核对、不联网的入口，时间戳因此接近改动发生的时刻；每次同步开始前也核对一次，漏掉的通知不会丢改动。核对要求本机词库给出同一时刻的一致视图（Engine 的 `stream_dictionary_state` 已经在一个读事务里读全部记录）。一次核对里少了 50 个以上、且至少一半的词时先挡下删除，由用户选择同步删除或从网盘恢复：词库被重置或损坏时不能把其他设备上的词也删掉。

### Engine 集成

状态机只经 `LocalDictionary` 接口写词库，一次一批，从不跨网络请求持有维护权。第二个 PR 里桌面端每批经 `QuiescedHosts` 取维护权（遇忙请求宿主释放输入会话，50 毫秒间隔、2500 毫秒预算，租约 30 秒），移动端经 `try_maintenance` 不请求会话退出；拿不到就返回「忙」，这一轮不写，5 秒、30 秒、2 分钟、10 分钟后再试，拉取和发送照常。写入用 Engine 的批量编辑接口和由操作派生的请求编号，重试是幂等的；删除前按 Engine 的要求取当前行的权重。整个调用由宿主放在工作线程上，输入线程从不等网络。

### 加密、设备与压缩

词库有自己的密钥串：云剪贴板端到端加密协议的另一个实例（同一个驱动、同一个日志核心、同一个虚拟中继），放在 `msime-dictionary/keyring/`，与剪贴板的空间分开；事件和检查点的子密钥由 HKDF 从它的密钥派生。不与剪贴板共用同一份批准，理由见下面的备选方案。设备身份是这份密钥串里的设备编号：一个安装一份密钥串，所有进程在同一把锁下读不到才生成，登记按编号进行、重复登记只更新名称，批准方看到的每台设备只有一条；日志的设备表同样按编号记（模拟测试覆盖「两个进程共用一份状态、写多少次都只有一条」）。

移除设备时密钥串换钥并在日志里宣布移除，持有新旧两把密钥的设备封口当前 epoch、用新密钥写下一个 epoch 的检查点；被移除的设备读到封口为止。持有旧密钥的设备都不在了时，用户可以「以本机为准重新开始」：新的共享词库编号，其他设备按第一次加入合并，不删词。

一个 epoch 攒到 64 个事件或 8 MiB 封口，下一个 epoch 从加密的检查点开始，旧 epoch 10 分钟后删除。墓碑在封口时回收：参与确认的是没被移除、在日志里最晚一次写入之前 90 天内出现过的设备，它们确认位置的最小值以内的墓碑删掉。确认游标的因果范围是「这台设备的本机词库已经持久地写到了这个序号」。长期离线的设备从最新检查点重新开始，按 `applied` 与检查点比较得出别处的删除；离线超过 90 天的设备对同一词条做过的、早于那次删除的修改会让词条复活，这是接受的限制。

### 触发与请求量

每台设备每 30 分钟自动同步最多 40 个请求，加上手动最多 60 个，三台设备用满只占坚果云配额的三成。改词后防抖一分钟（一直改时最多十分钟）、两次自动发送至少隔五分钟；打开设置时拉一次（一分钟内不重复），宿主活着时每 30 分钟拉一次；「立即同步」不受防抖限制。连不上按 1、2、5、10、30、60 分钟退避，限流等 30 分钟，需要用户处理的错误自动同步停一小时。宿主每次调用都拿到下一次该什么时候再调用，不用自己算。

### 宿主接口（第二个 PR）

C 接口沿用云剪贴板的形状：一个 JSON 请求入口，动作是 `run`（带触发原因：改词、打开、定时、手动）、`status`、设备的 `approve`、`reject`、`remove`、`reset`、`restart`、被挡下删除的 `confirm_deletions` 和 `restore_deletions`，以及保存前的 `probe`；偏好是 `dictionary_sync_webdav {url, username, password}`，规则照 `cloud_clipboard_webdav`：应用密码进凭据清单，整组进 `LOCAL_SECTIONS`，不进账号设置同步和 MCP，诊断里换成 `<redacted>`。

## Alternatives considered

- **与云剪贴板共用一份密钥串和批准** — 最强的理由是用户只批准一次，两个功能看到同一份设备列表。不用：剪贴板的生命周期会直接伤到词库——关闭云剪贴板会删掉全部密钥、封装和设备登记，「重置云剪贴板」会换钥并清空；它的空间绑定的是 `cloud_clipboard_webdav` 的地址和账号，词库就得强制要求同一个网盘账号；Android 的剪贴板密钥串由 Java 用 AndroidKeyStore 保存，iOS 和 HarmonyOS 的宿主还没接中继，共用就要先把这些宿主的剪贴板密钥串接进词库同步。复用代码、分开实例，换来两个功能互不牵连，代价是用两个功能的设备要批准两次。
- **在每个写入点挂钩产生操作** — 最强的理由是时间戳精确等于改动时刻，也不用比较整个词库。不用：写入路径有十几条，跨 host-api、MCP、会话里的候选删除、集合和账号云词库合并，漏一条就静默丢同步；挂钩写在 Engine 提交之外就有「提交了但没记下操作」的崩溃窗口；日志表只记每个词条的当前状态和秒级 `updated_at`，没有可以接着读的序号。三方核对只依赖「本机现在有哪些词」，任何路径的改动都覆盖到，崩溃后重新比较就能接上。
- **每台设备各写自己的目录** — 最强的理由是写入不会争抢序号，也不需要独占创建。不用：读一次就要对每台设备的目录各发一个 `PROPFIND`，设备一多就吃掉坚果云的配额；单一日志一个 `PROPFIND` 就看到全部新事件，哈希链和压缩也只有一条。
- **按到达日志的先后决定胜负，不要时钟** — 最强的理由是简单，日志本身就是全序。不用：离线设备回来时，它几天前的旧修改会盖掉别人今天的修改；用时间戳比较，结果与谁先上传无关。
- **向量时钟识别真正的并发** — 最强的理由是能区分「先后」和「并发」，并发时可以选择保留词条。不用：每条记录的大小随设备数增长，而墓碑回收和设备淘汰会让向量越来越难维护；既然冲突规则本来就是最后写入者胜，混合逻辑时钟已经足够，并发的平局也有确定的结果。
- **身份只用（类别、词），编码作为值** — 最强的理由是两台设备同时改编码只会留下一个。不用：同一个词有多个编码是常态（多音字词、简拼和全拼），用户会显式加好几个；把编码当成值就只能留一个。
- **墓碑永不回收** — 最强的理由是任何离线多久的设备回来都能正确判断删除。不用：删除只增不减，检查点会一直变大；回收加上「长期离线设备从检查点按本机记录比较」已经能正确传播删除，只在超过 90 天离线又改过同一词条时复活。
- **直接同步数据库或 Rime `sync` 目录** — 可复用现成文件同步工具，但数据库版本、并发使用和删除传播无法因此获得一致契约，不作为首版路径。
- **复用水杉账号云词库 API** — 已有认证和分页代码，但不能满足用户自选存储，也不能把个人词库自动改发到账号服务。
- **首版同时支持 WebDAV、S3、OneDrive** — 覆盖面更大，但会同时扩散认证、发布、重试和错误语义；日志格式与传输无关，以后加 S3 只需另一个独占创建的实现。

## Acceptance criteria

- 第一个 PR：协议核心与文档合入；`cargo test -p msime-client-core --lib dictionary_sync` 的模拟覆盖三台设备增词、改编码、删词后收敛，随机离线交错加崩溃和重放收敛且没有重复发送，并发修改与删除两种上传顺序结果相同，时钟在重启和系统时间回调后不倒退，重装设备重新加入，同一设备只登记一次，移除设备后换钥并把它挡在外面，压缩并删除旧 epoch 后长期离线设备重新加入，Engine 忙时不提前确认、墓碑等它，每一次写盘处崩溃都不丢不重，回退、截尾、删除整个文件夹被识别，大批删除被挡下，Engine 不收的词不反复重试，坏事件被所有设备跳过，列表滞后与争抢序号，断网后进度保留，超大响应和凭据错误，格式升级，以本机为准重新开始不删别人的词，网盘文件和调试输出里没有词、编码和密钥，调度在额度之内。
- 第二个 PR：WebDAV 传输对着本机 `dav-server` 跑认证失败、超大响应、发布争抢、远端回退、断网恢复；凭据不出现在导出、诊断、日志和远端记录；密钥串登记幂等（同一安装的几个进程首次并发使用也只登记一台设备）；Engine 一侧的本机词库在维护权的预算内批量写入，遇忙返回「忙」；C 接口写进 `msime_client.h`。本篇随之转 implemented。
- 各平台 PR：界面（设置、待批准设备与核对码、立即同步、被挡下删除的选择）和触发（改词后、打开设置、定时）接线，并在真实设备上验收。

## Risks

- 打字自动造的词会被同步。用户若不希望，需要 Engine 先区分来源，届时再改捕获规则。
- 两个功能分别批准增加了一次操作；共用批准要等剪贴板密钥串的生命周期与词库解耦后再评估。
- 离线超过 90 天、又改过已在别处删除的词条，会让它复活。
- 核对要读整个「我的词条」，开销随词条数线性增长；只在工作线程上做，触发有防抖。第二个 PR 要在真实词库规模上量一次。
- 本机同步状态里有词条明文和派生出的子密钥，与 Engine 词库同等对待：只放在本机私有目录，不导出、不进诊断。
- 已知应用密码又持有密钥的人仍能往后追加事件；移除设备后要换应用密码，文档写明。
