# Agent Note: 共享崩溃记录与持续授权基础

Status: proposed

## Problem

各平台的崩溃入口需要共同的落盘、队列和授权代次语义，但现有 Host API 只有布尔开关和分散的记录路径。平台各自补实现会让撤回后旧进程晚写、队列发送竞态、原件清理和构建身份字段出现不同规则，也无法让 Windows WER、Android 致命信号和 Apple 延迟诊断使用同一套脱敏边界。

## Proposal

先把跨平台基础收敛到 `client-services::telemetry`、`host-api` 和 `platforms/common`：持续授权在偏好锁内产生本机代次；遥测状态、崩溃原件和发送快照都绑定代次；撤回或换代时条件清理旧队列，逐条发送前再次核对授权；只有队列和收据持久化成功后才确认删除原件。原生 `CrashRecorder` 只在正常路径准备路径和固定头，故障处理器不读偏好、不联网、不等待可能被故障线程持有的锁，并保留模块相对偏移与构建身份。

Host API 继续使用有界 JSON ABI，兼容旧调用方的显式布尔参数，但提供 `preferences_directory` 和 `consent_epoch` 的严格绑定接口。共享 C++ 包装器只负责本进程生命周期和调用 ABI，不把网络或偏好锁带进故障现场。平台入口、系统诊断和符号归档在后续独立平台 PR 中接入；本切片不改变任何平台出厂默认值。

## Related notes

本切片只记录共享层的授权、队列和记录器决定；平台入口与最终验收范围由后续各平台 PR 另行记录。本切片不把其他工作区中的设备或后台证据带入共享层 PR。

## Alternatives considered

- **每个平台各自保存授权和队列状态**：实现初期较快，但会复制撤回、重试和脱敏规则，无法防止跨进程旧记录混入新授权，因此不采用。
- **只新增一个布尔开关，不引入代次**：改动较小，但撤回后立即重开无法区分旧进程和新授权，不能满足延迟崩溃诊断的归属要求。
- **在故障处理器里读取偏好并发送网络请求**：能直接得到当前开关，但会触碰文件锁、分配和网络，在堆损坏或 loader lock 场景下不安全，因此不采用。

## Acceptance criteria

- 共享 Rust 单测、Host API 遥测测试和 C++ `CrashRecorder`/telemetry 测试覆盖代次换代、撤回清理、旧原件拒收、队列写失败保留原件、重复送达和有界字段。
- `cargo fmt --all -- --check`、相关 crate 的测试/严格 Clippy、共享 C++ 严格编译和 `pnpm run verify-notes` 通过。
- 新 ABI 在缺失或错误授权目录、未知字段、越界头部和错误代次时拒绝；正式构建不获得测试后台目标。
- 共享层不声称任何平台的真实编辑器、设备、系统 WER、MetricKit、HiAppEvent 或后台收件已完成；这些由后续独立平台 PR 验收。

## Risks

代次绑定会让旧版本或未迁移的宿主停止补报，平台接入必须在后续 PR 中完成并保留兼容边界。记录器在信号或异常现场只能尽力展开栈，不能承诺完整调用链。共享 ABI 和状态格式一旦发布，后续平台必须保持字段有界、旧记录可拒收而不误删的语义。
