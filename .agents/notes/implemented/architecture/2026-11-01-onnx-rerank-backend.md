# Agent Note: 按键重排的 ONNX Runtime 后端：精简构建、uint8 权重、按自测速度分档

Status: implemented

## Problem

整句联想「增强」的逐键重排用随包的 chinese-ime-lm `model-v1`（4.25M），推理是 chinese-ime-lm 的纯 Rust 参考实现：单线程、int8 权重逐元素转 f32，文档记的吞吐约 12.5 GMAC/s，已接近单核上限。2026-11-01 在真实运行时（`rerank_latency`，sentences-v2 与 typing-chat-v1 共 643 条、约 8100 次按键）里量，它在 Pixel 3 XL 上让 20% 的按键超过一帧（16 ms），整键 p95 38–40 ms；iPhone XR 上整键 p95 11–12 ms。更准的模型更大：chinese-ime-lm `rerank-v1` 的 8x448 在 ctx-v1 上有上下文 91.9%、无上下文 82.7%（`model-v1` 的 4.25M 同口径 79.5% / 76.1%：同一个候选池，挑按字平均对数概率最高的那个，上文按 `rerank_context` 截，每条用例从空缓存开始），用同一个参考实现一次决策 71 ms，上不了按键路径。

## Decision

按键重排在宿主编译时打开 `onnx-rerank` 特性、资源里又有 ORT 格式的重排模型时，跑在 ONNX Runtime 上（`crates/onnx-rerank` 的 `OnnxScorer`，经 [CandidateScorer](2026-11-01-candidate-scorer-boundary.md) 挂上），不开特性或没有模型时照旧用随包模型。

落地到哪一步：后端 crate、host-api 的挂载与分档、`rerank_latency` 的 `--onnx-model`、精简构建的脚本（`tools/onnxruntime-minimal`）、Linux x86_64 上开着特性的 CI（`onnx-rerank.yml`），以及静态库的分发（Release `onnxruntime-minimal-1.24.4-r2`、锁文件和下载脚本，见下面「静态链接」一条）已经在仓库里。接入从 iOS 开始：`platforms/ios/build-native.sh` 按锁下载 `aarch64-apple-ios` / `aarch64-apple-ios-sim` 的库、开着 `onnx-rerank` 编 host 库，`stage-resources.sh` 用 `scripts/fetch_rerank_model.py` 按 `resources/rerank-model.lock.json` 取两档模型、放在 `EngineResources` 旁边，键盘扩展把 `rerank-model/`、`rerank-model-small/` 作为文件夹打包（见下面「模型放在资源目录旁边」一条）。Linux 跟着接上：发布页的 deb、rpm 和 tar.gz 由 `platforms/linux/package-container.sh` 按锁下载容器架构（x86_64 或 aarch64）的库、开着 `onnx-rerank` 编 `libmsime_host_api.so`，用同一个下载脚本取两档模型，CMake 按模型锁核对后装在 `share/msime-client/rerank-model{,-small}`，只装给带键盘模型的版本（full 与 pinyin），IBus 宿主和 Fcitx5 插件读同一个库，不用改 C++。legacy 包（glibc 2.28）和发行版仓库的源码构建不开这个特性。macOS 接着接上：`package-release.sh` 按锁下载两种架构的库、开着 `msime-host-api/onnx-rerank` 编 universal 的 host 库（`msime-mcp` 经 feature 合并一起带上），CI（`ci-macos.yml`）按 runner 架构取库、开着特性编；两档模型由 CMake 放进输入法 bundle 的 `Contents/rerank-model`、`Contents/rerank-model-small`（见下面「macOS 的模型跟着输入法」一条）。Windows 接在 Server 上，见下面「Windows 只在 Server 的会话里挂」一条。Android 接着接入：`platforms/android/build-native.sh` 按锁下载 `aarch64-linux-android` / `x86_64-linux-android` 的库、开着 `onnx-rerank` 编宿主库，模型不进 APK，6x256 作为资源包 `rerank-model-small` 在用户选「增强」时下载（见下面「Android 的模型是资源包」一条）。别的平台还没有接，照旧用随包模型。

- **单图、跨按键缓存。** 模型是 chinese-ime-lm 的 `lm_step`：上屏时把上文编码进缓存，之后每次按键只算缓存里还没有的候选前缀。候选共享的前缀算一次，候选的最后一个字不用算，上一次按键算过的前缀直接复用。缓存簿记（`prefix.rs`）不依赖原生库，单测覆盖。
- **ONNX Runtime 精简构建、静态链接。** 只编进两个模型用到的 27 个算子和类型（`tools/onnxruntime-minimal/required_operators_and_types.config`），只读 ORT 格式，链进程序约 1.5 MB；官方安卓库 34 MB。每个平台一个静态库（MSVC 目标是 `onnxruntime.lib`），gzip 压缩后作为 GitHub Release `onnxruntime-minimal-1.24.4-r<序号>` 的附件发布；`resources/onnxruntime-minimal.lock.json` 按 Rust 目标三元组锁住地址、SHA-256 和大小，`scripts/fetch_onnxruntime.py` 下载核对后打印 `ORT_LIB_LOCATION` 要指的目录。r1 有苹果四个目标（macOS 两种架构、iOS 真机与 arm64 模拟器）、安卓 arm64 与 x86_64、Linux aarch64、Windows x64 与 arm64；r2 原样带上 r1 的全部附件，补上 Linux x86_64。没有 32 位（32 位设备不跑 ONNX 重排）。Linux x86_64 的库由 CI 的 `onnx-rerank.yml` 在 x86_64 runner 上、用发 Linux 版的同一个 bookworm 镜像编出并作为附件上传，同一次运行里跑过 golden 和挂载测试；Apple Silicon 上 Docker 的 `linux/amd64` 是模拟的，Mac Studio 上这样编过一次没有编成，所以不在 Mac 上编。锁里记着算子清单的 SHA-256，改清单不重新发布时检查失败。Windows arm64 的库用静态 CRT，因为 arm64 的 host-api 是 `+crt-static` 编的，用动态 CRT 的库链接不上；Windows 两种架构都关掉调试信息，`/Zi` 的 `.debug$S` 让 x64 的库从 111 MB 涨到 374 MB 而没有 PDB 可用。Rust 绑定是 `ort` 2.0.0-rc.15（`api-24`，不带默认特性），对齐 ONNX Runtime 1.24.4。
- **uint8 权重。** ONNX Runtime 按 CPU 特性选 int8 内核：int8 权重时 M4 Pro（有 I8MM）与 M1 Max（没有）在 ctx-v1 的 6317 例里有 42 例选得不同（90.7% 对 90.5%），uint8 权重两边分数逐位相同、准确率不变。
- **模型来源。** 两档模型是 chinese-ime-lm 的 `rerank-v1`：GitHub Release [`metasequoiaime/chinese-ime-lm` 的 `rerank-v1`](https://github.com/metasequoiaime/chinese-ime-lm/releases/tag/rerank-v1)（文件名带尺寸前缀，如 `rerank-8x448.ort`），同一批文件也在 Hugging Face：[`msime/pinyin-ime-keystroke-reranker-25M`](https://huggingface.co/msime/pinyin-ime-keystroke-reranker-25M)（8x448）和 [`msime/pinyin-ime-keystroke-reranker-8M`](https://huggingface.co/msime/pinyin-ime-keystroke-reranker-8M)（6x256），那里是原名（`lm_step.ort`、`model.json`、`vocab.json`）并附 `LICENSE` 与 `NOTICE`。Apache-2.0，语料署名写在图的元数据和 `model.json` 里，见 `docs/third-party.md`。
- **大小两档，按自测速度选。** 资源目录旁边有 `rerank-model`（8x448）和 `rerank-model-small`（6x256，训练时自归一化，读候选字只算一次点积）时，先加载大的，用 `OnnxScorer::calibrate` 量它打一页重负载（32 字上文、9 个 6 字候选、37 个新前缀），超过 10 ms 换小的。真机自测值：iPhone 17 大模型 3.8–4.8 ms、Mac 4–7 ms，iPhone XR 21.9–23.4 ms、Pixel 3 XL 30.4 ms，与各机在真实运行时里量出的最优选择一致。iOS 上可用内存（`os_proc_available_memory`）不到 120 MiB 时不加载大的，直接用小的，见 [iOS 键盘的内存](../../implemented/bug-fix/2026-11-02-ios-keyboard-reranker-memory.md)。
- **进程里只加载一份。** `ffi::OnnxRerankers` 是进程级缓存：同一时刻只加载一个模型，各会话经 `Arc<Mutex<OnnxScorer>>` 共用，档位在第一次挂上时定下、之后沿用；大模型的自测结果按模型文件的长度和修改时间记下，进程里只测一次。「增强」关掉时放开，文件换了重新加载。
- **模型放在资源目录旁边，不放进去。** 资源目录要与词库锁逐项相符：`ResourceStore::verify` 只放过 `helpcodes/`，iOS 键盘每次启动都按它校验 `EngineResources`，多一个 `rerank-model/` 整套词库就校验失败、键盘起不来。所以两档模型和 `settled-model/`、`language-dictionaries/` 一样是资源目录的兄弟（`ffi::rerank_models_root`），锁也单独一份（`resources/rerank-model.lock.json`，由 `scripts/fetch_rerank_model.py` 下载核对并改回 `lm_step.ort`、`model.json`、`vocab.json` 三个原名），不进各平台共用的词库锁。装了在线词库更新、`resources` 换成下载的代次目录时，按 `EngineOptions::helpcode_fallback_resources` 记的随包资源目录去找，模型仍是安装包里的那份。Linux 的安装包根本不带词库，`msime-linux-setup` 把它下载到用户自己的 `$XDG_DATA_HOME/msime-client/resources`，资源目录的上一级是用户目录；那里没有模型时，Host API 再看会话的内置音效包目录（两个 Linux 宿主按自己的安装位置写成 `sound_packs`，官方插件包也是据它找的）的上一级，也就是 `/usr/share/msime-client`。Windows 不这样找，那里的音效包目录普通用户可写。最早的 Linux 接入只放了模型、没有这一步，在 VM 上装好后「增强」挂的是随包的句子模型（`keyboard reranker bundled model`），这一步之后才是 ONNX。
- **macOS 的模型跟着输入法。** macOS 输入法建会话时把自己 bundle 的 `Contents/Resources` 作为 `helpcode_fallback_resources` 交给 host-api（`InputController.mm` 的 `MSIMESessionOptions`，运行时选项文件没写这个键时都是如此），所以「随包资源目录的上一级」是 `水杉输入法.app/Contents`，模型放在 `Contents/rerank-model{,-small}`。没有放进设置应用 `MSIME.app/Contents/Resources` 的 `EngineResources` 旁边：那里 host-api 根本不找，而且 Sparkle 分别更新输入法和设置应用，模型放在设置应用里就可能与输入法里链进去的 ONNX Runtime（算子清单）不是同一次构建。`codesign` 把 `Contents` 下的这两个目录当资源封进签名。不提供「增强」的版本（版本表 `features.neural_keyboard` 为 false：五笔、日文、越南文、藏文版）打包时去掉它们。
- **Android 的模型是资源包，只给 6x256。** Android 发布用的瘦包（full、拼音版）有 135,000,000 字节的上限，2026-11-01 的 nightly 里 full 已是 129,984,724 字节；两档模型合计约 39 MB，只带 6x256 也要 8.3 MB，都放不下，而链进宿主库的 ONNX Runtime 本身只多 约 2.0 MB（剥离符号后的 arm64 `libmsime_host_api.so` 多 1,966,888 字节，APK 里不压缩存放）。所以模型走已有的按需资源包：`ResourcePack::RerankModelSmall`（id `rerank-model-small`，文件取自 `resources/rerank-model.lock.json` 的 6x256，装好后是 `lm_step.ort`、`model.json`、`vocab.json`，锁里补了 `source_commit`）。「增强」开着而本机没有它时自动下载：「增强」多半是缺省或从别的设备同步来的，只靠用户在设置里选「增强」时下载，多数人永远拿不到模型。输入法进程（读到偏好时）和设置应用（回到前台时）经 `RerankModelDownload` 排一个 JobScheduler 任务（`home.RerankModelJobService`，主进程），只在不按流量计费的网络上、电量和存储不低时跑，不进前台、不发通知，连不上或服务器出错按 JobScheduler 的退避重试，每个进程只排一次；按流量计费的网络上不在后台下，设置应用回到前台时问一次（问过就记下）。设置里选成「增强」时直接下载（按流量计费先确认），增强开着而没装好时那里多一行下载状态；切回「标准」或「关闭」时撤掉任务、卸掉模型，不让不用它的人留着 8.3 MB。资源包目录名就是 id，与 host-api 找的 `rerank-model-small` 相同，`rerank_models_root` 在随包资源目录旁边两档都没有时，退到 `<state_root>/resource-packs/`（只认与锁一致、完整发布的资源包）。输入法进程从不联网，会话在聚焦时比较模型来源（`onnx_rerank_source`），资源包刚装好或被移除就重新挂，不等会话重建；没装好时照旧用随包的 `sentence-model.safetensors`。8x448 不在 Android 上提供：Pixel 3 XL 上它自测一页 30.4 ms，远超 10 ms 的换档线，还没有量过哪台安卓手机能在线内跑完它；只装小的时也省掉加载大模型和自测。只有带拼音的版本（full、拼音版，`neural_keyboard` 为真的那两个）下载它，Java 侧按版本有没有全拼判断。32 位不在发布里（`build-native.sh` 只编 arm64-v8a 和 x86_64），精简库也没有 32 位产物。模型的 Apache-2.0、上游 NOTICE 与语料署名（`resources/licenses/rerank-model-Apache-2.0.txt`）随原生库的声明进 APK，关于页列出它。
- **挂的是哪一档写进诊断。** 「增强」开着时会话建立和开关打开各写一行：`keyboard reranker onnx large` / `onnx small` / `onnx small (low memory)`（细节带模型目录、自测毫秒数、可用内存，与之前的会话共用时标 `(shared)`）、`bundled model`（没有 ONNX 模型，退回随包的句子模型）或 `missing`。类别本身就说明了档位，只留类别的宿主（macOS、iOS 的诊断日志）也看得出来。Android 原先没有登记诊断出口，这些行写进没人读的 stderr；现在 `client_jni.cpp` 在 `JNI_OnLoad` 里登记，把类别写进 logcat（标签 `MSIMEHost`，`host_api: <类别>`）。
- **线程数。** 安卓 4 线程（Pixel 3 XL 上整键 p95 两线程 10.8 ms、三线程 10.0 ms、四线程 9.3 ms），其余 2 线程（苹果 A 系列只有两个大核，四线程在 iPhone XR 和 iPhone 17 上都更慢）。
- **Windows 只在 Server 的会话里挂，只编 x64。** Windows 有两处 host-api 会话：TIP 在每个打字的应用进程里各有一个（跟着 Server 选词的镜像会话），Server 进程里每个连上来的 TIP 客户端各有一个（`src/input/InputQueue.cpp` 为每个连接建一个 `FocusedSession`）。候选窗是 Server 画的、顺序是 Server 的会话排的，TIP 按文字选中同一个词（`tsf/HostServerSelection.h`，两边顺序不同时到完整候选列表里找），重排只是把前几条里的一条提到首位、不增删候选，TIP 自己再排一遍用户看不到；挂上却要在每个打字的进程里各加载、自测一份模型（大模型权重 31 MB），32 位应用加载的 x86 TIP 也没有库可链。所以 TIP 的会话选项写 `keyboard_reranker: false`（`tsf/HostConfiguration.cpp`），「增强」打开也不挂，原来每个进程各加载一份的随包句子模型也一起省掉；Server 的会话照常挂，靠进程级的 `OnnxRerankers` 共用一份：Server 启动时所有已经装着 TIP 的进程同时连上来，每个连接建一个会话，各自加载、自测一份时，2026-11-02 在验收虚拟机上 Server 的私有内存随打开的应用一份份涨（打开一次记事本多两个会话，112 → 190 MB），会话建立被加载和自测拖慢到两三百毫秒，同时 explorer 里的 TIP 每秒发十几次复位请求，Server 每秒重新加载三四次，两个 CPU 被占满（「增强」关着启动时没有这个循环）；共用之后只有第一个会话加载和自测。Server 在内存里把自己所在的目录写成 `rerank_models`（`src/system/RerankModelRoot.h`）：安装器把两档模型装在 Program Files 的 `server\` 下、`resources\` 旁边，但 Windows 会话选项里的随包资源目录回退（`helpcode_fallback_resources`）是放辅助码表的 DataDir，装了在线词库更新后 `resources` 又换成 DataDir 下的代次，按资源目录推都找不到安装包里的模型。Server 是 x64 程序（Windows on Arm 上也是 x64 转译），所以只有 x64 宿主开 `onnx-rerank`（`Build-RustOutputs.ps1` 按锁下载 `x86_64-pc-windows-msvc` 的 /MD 库）；x86 与 arm64 宿主只给 TIP 加载，不开，锁里 arm64 的 /MT 库暂时没有构建用。安装包只给带键盘神经模型的版本（full、pinyin）装两档模型，轻量包不带。
- **Win7 不接，照旧用随包的句子模型。** Win7 的宿主是 Tier 3 目标 `x86_64-win7-windows-msvc` / `i686-win7-windows-msvc`，用 build-std 和静态 CRT 编（`Build-Windows7Core.ps1`），锁里没有对应的库：发布的 x64 库是动态 CRT（/MD），要另编、另发静态 CRT 的 x64 与 x86 两份。更根本的是 Windows 7 加载不了：2026-11-02 用 dumpbin 比较开着与不开 `onnx-rerank` 的 x64 宿主 DLL，精简构建的 ONNX Runtime 多导入了 kernel32 的 `CreateFile2`、`api-ms-win-core-path-l1-1-0.dll` 的 `PathCchRemoveBackslash` 与 `PathCchRemoveFileSpec`、advapi32 的 `EventSetInformation`，都是 Windows 8 才有的接口，Win7 的宿主若链接它，宿主 DLL 在 Win7 上就加载不起来，TIP 和 Server 一起失效。要接得先在 ONNX Runtime 里绕开这些接口，不值得。

结果（真实运行时，整键 p95）：Mac 约 4 ms（8x448），iPhone 17 3.8–4.1 ms（8x448），iPhone XR 4.4–4.9 ms（6x256），Pixel 3 XL 9.3 ms（6x256）。

## Alternatives considered

- **官方预编译的 ONNX Runtime（动态库或 xcframework）** — 不用自己维护构建，CI 也省事；安卓已经因为离线语音和 OCR 带着它的两份。但那两份都不在键盘本体里（离线语音是用户打开时才下载的资源包，OCR 是单独的模块），iOS 那份静态链接在 sherpa-onnx 的 xcframework 里、不保证导出 C 接口；为重排单独带一份完整库每个平台多二三十 MB，安卓 34 MB。精简构建只有 1.5 MB，代价是每个平台自己编、每换一次模型算子清单就要核对一次。
- **把 chinese-ime-lm 的纯 Rust 实现做快（SIMD、多线程）** — 不加原生依赖，网页引擎也能用。但它约 12.5 GMAC/s 已接近单核标量上限，ONNX Runtime 在 ARM 上用 SDOT/I8MM 等整数点积指令，同一个模型在 M4 Pro 上快一个数量级以上；在 `#![forbid(unsafe_code)]`、低工具链门槛的参考实现里手写这些内核，等于另造一个推理引擎。
- **XNNPACK 执行提供者或 fp32 权重** — 在 Pixel 3 XL 上都试过：XNNPACK 跑 fp32 比默认的 int8 慢约 3.7 倍，跑 int8 慢约 1.7 倍；不量化的 fp32 权重比 int8 慢约 2 倍。
- **int8 权重配 `reduce_range` 或逐通道量化** — 都想减小不同 CPU 之间的差异：7 位权重时 M4 与 M1 有 30 例选得不同，逐通道 48 例；只有 uint8 权重两边逐位相同。
- **按机型名单选模型** — 名单要人维护，新机型出来总是落后；自测在每台机器上量的就是要决定的那件事，十毫秒以内的一页负载在加载时只多花几十毫秒。
- **Android 的 APK 带上模型（两档，或只带 6x256）** — 理由最强的一条：和 iOS 一样装好就能用，没有「选了增强、模型还在下载」的中间状态，也不用联网。但 full 的瘦包加上运行库已到 131 MB 上下（Studio 上不带背单词词书的构建 131,114,566 字节，词书约 1 MB），离 132 MB 的预警线不到 0.1 MB，再带 8.3 MB 的小模型就越过 135 MB 的上限；为它抬高上限，等于让上限不再挡「整组按需资源悄悄回到包里」。日文词典、五笔码表、语音运行库都是这样改成资源包的，重排模型照同一条路走。
- **Android 也提供 8x448 资源包，两个都装、照常自测** — 新的旗舰手机也许能在 10 ms 内跑完大模型，有上下文时多 1.5 个点。但还没有一台安卓手机量过能做到，Pixel 3 XL 自测 30.4 ms；每台手机为它多下 31 MB，每个输入法进程多一次大模型加载和自测，而多数手机自测完就丢掉它。等量到一台过线的机器，再加一个 `rerank-model` 资源包、只在设置里给它一行，不改这里的查找规则（两个目录都在资源包根下）。

## Consequences

- **收益**：同一台设备上，新模型比 `model-v1` 既更准又更快：Pixel 3 XL 上重排开销 p95 从 36 ms 降到 6.9 ms，超过一帧的按键从 20% 降到 0.1%；iPhone XR 整键 p95 从约 11.5 ms 降到约 4.6 ms。
- **代价**：多一个 C++ 依赖要按平台自己编（苹果与安卓在 macOS 上编，Linux 在 msime 发 Linux 版的同一个镜像里编，Windows 要 MSVC），换模型若算子清单变了要重编全部平台、发一个新的 `-r<序号>` 并更新锁。`ort-sys` 会把静态库复制进自己的输出目录，换库后要 `cargo clean -p ort-sys`。权重是动态量化的，同一个前缀与不同的节点一起算时分数会差在第三位小数（约 0.005），测试按这个量级放宽。
- **还没做的**：iOS、macOS、Linux、Windows 与 Android 以外的平台构建打开 `onnx-rerank`、用下载脚本取库并在资源目录旁边带上两档模型（照 iOS 的 `stage-resources.sh`、Linux 的 `package-container.sh`）。Android 只有 6x256，大模型没有下载入口（见上面的取舍）。Linux 的 legacy 包（Debian 10 / UOS 20，glibc 2.28）不开：bookworm 上编的静态库引用 glibc 2.30 与 2.32 才有的 `pthread_cond_clockwait`、`__libc_single_threaded`（`nm -u` 看得到），在 buster 上链接不了，要另在 buster 镜像里编一份；发行版仓库的源码构建（COPR、OBS、PPA、AUR、Gentoo、nix）在没有网络的构建农场里，也不该链接仓库外编出的静态库，照旧用随包模型。iOS 键盘扩展的内存余量见 [iOS 键盘的内存](../../implemented/bug-fix/2026-11-02-ios-keyboard-reranker-memory.md)，改动后的余量还要在真机上用诊断日志的 `mem=` / `avail=` 核对。
- **已知上限**：iPhone 17 上 8x448 整键 p95 在 4 ms 上下，手机档 6x256 在 ctx-v1 有上下文只高出 90% 的线 0.4 个点（90.4%；宿主连着打分、沿用上一条的缓存时是 90.2%）；HarmonyOS 没有 ONNX Runtime 产物（不在官方支持的平台里），照旧用随包模型；Windows 2026-11-02 在验收虚拟机（i5-14600KF 上的 4 核 Windows 11 虚拟机）上量：自测一页大模型 5.2–6.2 ms、小模型 1.3–1.6 ms，挂大模型；真实运行时（`rerank_latency`，sentences-v2 与 typing-chat-v1 共 643 条、8104 键）大模型整键 p95 6.3 ms、p99 8.6 ms、最慢 16.5 ms（3 键超过 16 ms），小模型 p95 2.9 ms、p99 4.1 ms。大模型的 p99 没到桌面 4 ms 的目标；在这台机器上同时有很多会话加载、自测时（上面「Windows 只在 Server 的会话里挂」那一条里的重连）自测值在 10 ms 上下跳，档位在大小之间来回换。Windows on Arm 上 Server 是 x64 转译，没有量过。量化或模型换代后，要重跑 `rerank_latency` 与 `calibrate` 并更新 `LARGE_RERANK_MODEL_BUDGET_MS` 旁的数字。

## Verification

- `crates/onnx-rerank/tests/golden.rs`：随机小模型（`tests/fixtures`，算子与正式模型相同）逐键打分与 ONNX Runtime Python 包相差 1e-3 以内，复用缓存与从头算只差在量化误差以内，自测后不留缓存。
- `crates/host-api/src/tests.rs` 的 `keyboard_reranker_prefers_the_onnx_model_when_one_is_installed`：模型放在资源目录旁边，资源目录里的同名目录不算，下载的词库代次按随包资源目录找；大小两档放的 `model.json` 上文字数不同，按 `context_length` 认出挂的是哪一个；只装大的时用大的，两个都装时自测预算够用大的、不够换小的（预算和可用内存经 `OnnxRerankers::attach` 注入），可用内存不够时用小的且不自测，同一个模型再挂一次是同一份、放开后重新加载、自测只做一次，大的坏了用小的，都坏了退回随包的句子模型，连句子模型也没有就不挂。
- macOS：`bundle_contents.py`（ctest `bundle-contents`）核对构建出的输入法 bundle 在 `Contents/rerank-model{,-small}` 下有三个文件、`Contents/Resources` 下没有；`package-release.sh` 的 `check_app` 按版本核对在或不在；`scripts/test-macos-package-resources.py` 核对打包脚本按目标取库、开特性，CMake 取模型。2026-11-02 在 Mac Studio 上编出 universal 的输入法（两种架构的 host 库各链一份精简库，`bundle-contents` 与 `backend-library-load` 通过），装到 M4 Pro 上：`codesign --verify --deep --strict` 通过，签名的 `CodeResources` 封着两个目录的六个文件；打开「增强」后诊断日志写 `host_api: keyboard reranker onnx large`。剥离后的输入法可执行文件 arm64 多 1.5 MB、x86_64 多 1.8 MB，两档模型 39.2 MB（gzip 后约 26.7 MB）。同一台 M4 Pro 上 `rerank_latency`（643 例、8104 次按键，随包模型臂用当时装着的词库代次）：8x448 整键 p95 2.47 ms、p99 3.24 ms（重排本身 p95 2.21 ms），6x256 整键 p95 1.11 ms、p99 1.45 ms，原来的 `model-v1` 整键 p95 4.25 ms、p99 7.10 ms。
