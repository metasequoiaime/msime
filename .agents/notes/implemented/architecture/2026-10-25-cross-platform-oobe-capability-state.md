# Agent Note: 全平台 OOBE 与系统能力状态分离

Status: implemented

## Problem

六个平台都有首次使用流程，但它们处理的对象不同：macOS 的安装页负责注册输入源和运行配置，Windows 安装器与 Server 分别保存安装偏好和运行时选项，Linux 在缺少配置或词库过期时进入准备页，Android 用原生引导和原子词库准备，iOS 用 SwiftUI 引导，鸿蒙按系统输入法实时状态推进状态机，Web engine 则把首次使用交给宿主。各平台没有统一的 OOBE 状态契约，最容易产生的误判是把“用户看过引导”当成“输入法已在系统启用”。

## Decision

- 各平台继续由原生宿主持有 OOBE 流程；共享 Rust `oobe` 模块和 TypeScript `OobeState` 统一事实语义、完成条件和未知状态策略，不抽走平台特有的系统设置动作。Web engine 没有系统 OOBE，由宿主负责。
- 统一检查和设计讨论使用四类状态：资源是否准备好、系统输入法是否已启用或为当前输入法、应用偏好是否已保存、用户是否离开过 OOBE。权限和账号是能力前置条件，不能由 OOBE 离开标记推导。
- iOS 没有公开 API 判断键盘是否添加到系统列表或是否获得完全访问；私有的 AppleKeyboards 读取和键盘写入标记都不作为状态来源。因此 `hasSeenOnboarding` 只记录“已看过/已离开首次引导”，并兼容迁移旧的 `hasCompletedOnboarding` 偏好。设置首页的 `KeyboardStatusCard` 长期保留两步操作，并明确告知用户 iOS 无法自动确认状态，不显示伪造的成功或失败图标。
- iOS 的“稍后再说”、跳过和 iPad 卡片关闭仍然可以离开首次流程；离开后用户可从设置页重新打开引导，系统能力由用户在系统设置中确认。

六个平台的现状核对如下；各原生宿主按自身能力报告事实，不把开发壳当成移动端产品：

| 平台 | OOBE 入口 | 离开后仍需确认的系统能力 |
| --- | --- | --- |
| macOS | 独立安装页；`desktop_oobe_status` 校验运行资源、读取偏好并查询输入源启用状态 | 输入源注册、词库运行配置，以及部分系统版本需要用户在系统设置或重新登录后生效的输入模式 |
| Windows | 安装器询问数据目录和云候选；Server 首次启动写 `runtime-options.json`，首次准备成功后自动打开原生设置首页 | 设置页状态卡检查输入法是否已添加、是否为默认；失败时打开 Windows「语言和区域」 |
| Linux | 缺配置或词库过期时进入设置页；`desktop_oobe_status` 校验资源、读取偏好，`msime-linux-setup --status --json` 只读查询 Fcitx5/IBus | 服务启用和当前输入法由桌面环境决定 |
| Android | Splash 后的原生四步引导，`Bootstrap.prepare` 原子准备词库；原生首页在返回前台后重查系统状态，失败的引导选择保留到写入成功 | 系统输入法启用与当前输入法选择 |
| iOS | SwiftUI 四步引导和长期状态卡；调用共享宿主准备资源，独立持久队列保留未保存选择；系统状态未知 | 键盘列表、完全访问和当前输入法均需用户在系统界面确认 |
| HarmonyOS | ArkTS 原生桥报告实际资源暂存结果和系统状态，独立保存离开标记，失败可重试 | 麦克风和剪贴板权限仍在功能触发时处理 |

### 保存与重试边界

Android 和 iOS 将引导中未写成的方案、译文选择保留在主应用的待保存队列中；只有共享偏好确认成功才清除对应字段，离开引导不清空队列。首页继续提供重试入口。HarmonyOS 的离开标记独立于系统输入法启用状态，跳过不伪造完成；保存失败时保留流程中的选择并显示重试提示，不能吞掉错误后离开。Android 的系统服务不可用、默认输入法标识不可读时也保留未知，以中性标记提示重新确认。

桌面状态查询失败或原生桥返回空快照会清除旧的成功结果，返回前台重新查询。资源准备与系统设置是两个动作：macOS 重新从安装资源生成运行配置；Linux 资源修复显式复用已有目录的更新事务，系统设置则打开当前 Fcitx5 或 IBus 的配置工具。Windows 首次准备失败显示可重试的原生提示，WinUI 与 Win7 共用系统查询和添加、设为默认操作。

## Alternatives considered

- **用私有系统设置读取在 iOS 画出 ✓ / !**：可以让界面看起来像 Android，但有审核风险，且读取结果不稳定；不采用。
- **把“允许完全访问”写入 App Group 后当成长期真值**：实现简单，但用户撤销权限后旧标记仍在；不采用。
- **马上抽象成所有平台共用的 OOBE 状态机**：会掩盖 macOS、Linux 和移动系统不同的权限及系统设置边界；因此只抽象状态契约和纯策略，不强行共用流程状态机。

## Consequences

iOS 老用户的旧完成标记会迁移到 `hasSeenOnboarding`，不会再次被强制拉回引导；UI 测试使用的旧启动参数仍兼容。用户离开引导后，首页会继续显示两项系统设置动作和无法自动确认的说明，避免把“看过引导”误解为“键盘已经可用”。Windows 首次准备成功后会通过现有 Shell 路由打开原生设置首页，设置页顶部的输入法状态卡负责添加和设为默认，已有状态的启动不会重复弹出。代价是 iOS 不能在首页给出自动化的完成勾选，系统能力验收仍需真实系统设置或输入框验证；桌面平台的系统能力仍由各自原生宿主报告，共享契约不把未知状态替换成布尔值。

## Verification

- 共享 Rust OOBE 纯逻辑测试 5 项通过；它们验证状态语义，不代表六个平台设备验收。
- `msime-host-api` 的只读资源状态测试通过，覆盖正确资源、损坏资源、相对路径和未知版本拒绝，以及查询不创建状态目录。
- 桌面与鸿蒙 TypeScript 类型检查通过；6 个 vitest 文件共 119 项通过，包括空快照、前台刷新、资源动作分离、Linux 修复与鸿蒙保存失败重试。
- Linux 配置脚本测试通过，覆盖 Fcitx5/IBus 只读状态查询、部分查询失败和注册流程；鸿蒙桥调用一致性检查通过。
- Android Java/API/manifest 检查通过；原生 APK 构建、API 28/35 安装和系统输入冒烟通过。两个 API 的 client-base、client-core、client-providers、client-services 设备单测均通过。`smoke.sh <serial> --oobe` 是引导专项入口，使用实际安装产品与沙箱权限失败验证待保存选择、离开标记、系统状态刷新和恢复写入；它不代表完整键盘套件验收。
- iOS 原生 App 与键盘扩展构建通过，模拟器待保存队列单测 3 项通过；iOS 27 专用模拟器的首次引导与首页 UI 用例 2 项通过。
- macOS 原生输入法 CMake 构建、设置应用 Rust 全目标检查通过；HarmonyOS 的 Rust/NAPI、共享设置页和完整 ArkTS/HAP 构建通过。
- Win7 完整窗口通过 Clang/MinGW 交叉语法检查。Linux 原生宿主与设置应用、Windows GNU 及 WinUI 构建另由 PR CI 检查；编译不代表实际系统入口验收，未执行 Windows、Linux 和 HarmonyOS 的实机 OOBE。
