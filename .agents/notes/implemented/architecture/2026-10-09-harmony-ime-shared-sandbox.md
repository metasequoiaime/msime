# Agent Note: 鸿蒙设置应用与键盘扩展经共享沙箱镜像交换数据

Status: implemented

## Problem

鸿蒙宿主是按「设置应用（UIAbility）和键盘（InputMethodExtensionAbility）两个进程共用 `files/state`」设计的：偏好、登录会话、按键反馈、自定义皮肤、打字统计、遥测队列都放在那里，各自加锁读写。

从 API 12（OpenHarmony 5.0.0.38）起，输入法扩展进程改用独立沙箱。OpenHarmony 的变更说明把这标为不兼容变更：「输入法 Extension 进程使用独立沙箱……新增输入法 Extension 与应用的主入口的共享沙箱」。2026-10-09 在 HarmonyOS 6.0.2(22) 模拟器上实测，两个进程的 `files/state` 内容完全不同，设置应用写的文件键盘一个也看不到。

可见的后果：
- 设置页改的输入方案、按键反馈、自定义皮肤传不到键盘；
- 键盘看不到登录会话，账号相关功能按未登录处理；
- 打字统计永远是 0：统计默认关闭，设置页开启的只是它自己那份文件。

## Decision

用华为提供的「共享沙箱」，但两个进程不直接共用一个状态目录，而是各自保留私有的 `files/state`，只经共享目录镜像对方要看到的那部分。

1. AppGallery Connect 为包名 `app.msime.hmos` 签发了「输入法应用内数据共享」的 data-group-id `group.1516753898738609107`（工单 D645548）。键盘扩展在 `module.json5` 的 `dataGroupIds` 里声明它，代码里同一个值在 `keyboard/SharedStateMirror.ets` 的 `DATA_GROUP_ID`。签名 Profile 必须在 AGC 网页端手动新建（DevEco 自动签名走标准模板，带能力开关但不写授权值），生成时间要晚于能力「已通过」的时间，`bundle-info` 里要有 `"data-group-ids": ["group.1516753898738609107"]`；Profile 里的值与邮件不一致时以 Profile 为准，两处代码一起改。
2. 两个进程都用 `context.getGroupDir(DATA_GROUP_ID)` 拿共享目录（`SharedStateMirror.resolve`）。拿不到（签名不带 ID、模拟器不做这项授权校验、调用失败）时两边照旧各用各的 `files/state`，记一条日志，设置页不对用户提示：这是签名和开发上的状态，用户对它无能为力。
3. 发布方把条目复制到 `<共享目录>/msime/<settings|keyboard>/`，最后写清单 `manifest.json`（每条的内容指纹和变化时刻）；导入方读清单，把指纹与上次导入不同的条目复制回自己的私有目录，导入到哪一版记在私有的 `state/shared-import-<发布方>.json`。规则在 `keyboard/SharedStateMirrorPolicy.ts`，文件操作在 `keyboard/SharedStateMirror.ets`，两侧的时机在 `keyboard/SharedStateSync.ets`。
   - 设置应用发布：偏好、按键反馈、应用主题、打字统计开关（`typing-statistics-switch.json`：开关、保留期、清空次数）、候选窗皮肤 `skins/`、插件 `plugins/`（含 `mentions.json`）、社区回复库 `CommunityLibrary.json`、账号会话和匿名账号，以及云剪贴板的设备身份与网盘日志缓存。时机：每次改设置后合并 300 ms 发布一次（同步桥接方法开头、异步请求经 `deliverReply` 交回时），以及窗口退到后台时立即发布。
   - 键盘导入：扩展 `onCreate` 在会话第一次读状态之前导入一次，之后每次获得焦点（`KeyboardSession.attach`）在偏好修订号比较之前导入。偏好经 `savePreferences` 写入（走存储的锁和修订号），随后的修订号比较发现变化并重建会话；按键反馈和应用主题在 attach 里本来就会重新读；插件和皮肤由原生会话在获得焦点时重新盖戳；正在用的皮肤包被同名替换时修订号不变，`attach` 随后比较选中包的文件身份，变了就重新应用外观（见[皮肤包同名替换](../bug-fix/2026-10-20-macos-replaced-skin-package-refresh.md)）。统计开关经 `typingStatistics` 的 `set_enabled` / `set_retention` / `reset` 用到键盘自己的统计文件上；第一次导入时不清空，免得共享沙箱启用前记下的计数被早先的清空带走。
   - 键盘只在完整体验模式下发布（`getSecurityMode() === FULL`）：键盘里改的偏好和按键反馈、刷新过的账号会话、打字统计、长按菜单「加入生词本」写进的那本生词本和它的清走记录（`keyboard-vocabulary/`，设置应用只并进上次以后新加的词，并在自己清单的 `applied` 里写明并到了哪一版，键盘据此清走交过的词，见[移动键盘的「加入生词本」](../feature/2026-11-01-mobile-candidate-personal-wordbook.md)），并附上它从设置应用导入到了哪一版。时机：每次获得焦点导入之前、失去焦点时。设置应用在窗口回到前台时先发布自己的、再导入键盘的；键盘的统计文件只在键盘已经导入了设置应用当前的统计开关时才采用，否则会把刚改的开关或刚清空的计数改回去；采用时不整体覆盖，计数取键盘的，设置应用自己记的试过的皮肤（`skinsTried`）和徽章（`achievements`）取并集，并持有统计存储的同一把 flock 写回，免得与工作线程上的 `summary` 互相覆盖。
4. 指纹只看内容：偏好按 `preferences` 本身（不含修订号、键排好序），小文件按全文，目录按每个文件的路径、大小和修改时间（锁文件和暂存文件不算）。导入写回的内容与对方相同，指纹也相同，所以不会被发布回去，两边不会来回打转。本地普通文件和偏好的指纹按路径缓存（`FingerprintCache`），文件的 inode、大小和纳秒修改时间都没变时直接用上次的指纹、不重读，缓存只省读取、不改指纹的含义（见[鸿蒙键盘收起后不再空转](../bug-fix/2026-10-27-harmony-keyboard-idle-and-hot-path-costs.md)）。两边都改过同一条时，以变化时刻较晚的一方为准；基础访问模式下键盘不发布，设置应用的改动总会覆盖键盘里的同一条。
5. 账号会话（`account-session.json`、`anonymous-account.json`、`anonymous-session.json`）只在完整体验模式下交换。服务端会轮换刷新令牌，同一个刷新令牌用第二次会被拒绝；基础访问模式下键盘刷新后写不回共享目录，设置应用手里的令牌就作废了。所以基础访问模式下键盘不导入会话，继续用自己的匿名账号，与改动前相同。两份会话（`account-session.json`、`anonymous-session.json`）导入时不再整份复制，改由 Rust 的 `session_adopt` 在导入方的锁里决定，匿名账号的身份文件随匿名会话一起由它采用、不再复制，见 [鸿蒙账号与云端业务整体切到 Rust 目录模式](2026-10-17-harmony-account-rust-directory-mode.md)。
6. 只属于各自进程的数据不交换：键盘的 `user/`（个人词库、学习记录、工作词典代次）、`cache/`、常用语、表情记录、剪贴板历史、遥测队列，设置应用的通知、背单词进度、词库导出暂存。两份个人词库里的「我的词条」另经共享目录里的发布文件交换、收敛成同一组，不复制 `user/`，见 [鸿蒙设置应用与键盘的「我的词条」经共享沙箱收敛成一份](../feature/2026-10-27-harmony-unified-user-words.md)。

## Alternatives considered

- **两个进程直接把状态目录换成共享目录（原计划）。** 最强的理由是只有一份数据，没有复制、没有指纹、没有冲突规则，任何一边写下的东西另一边立刻看到。没采用，是因为落地前的盘点发现它在默认的基础访问模式下根本跑不起来：client-core 的存储连读都要在目录里以读写方式创建锁文件再加独占锁（`storage.rs`、`file_lock.rs`，`PreferencesStore::load` 先加锁），键盘对共享目录只读，连偏好都读不到；`prepare_host` 每次启动和每次重建会话都要往状态目录里写（资源校验标记、第一份偏好文档、`user/`、`cache/`、日志回放到代次目录），而 `user/`、`cache/` 是从同一个 `state_root` 推出来的；剪贴板历史、本地语音模型、社区回复库还是按状态目录的上一级推出的，会被一起搬进共享目录；设置应用的词库维护会和键盘的会话抢 `user/` 的访问锁。要让它成立，得给原生层加只读加锁的读路径、把 `user/`/`cache/` 与偏好目录拆成两个参数，并在 ArkTS 里把十几处路径各自改对，改动面和风险都远大于镜像。
- **设置应用通过进程间通信把数据推给键盘。** 理由是不需要 AGC 申请，不签名的开发包也能用。不用它，是因为文档明确说基础访问模式下键盘的公共事件、进程间通信、共享内存都被限制；而且输入法框架没有给自家设置页传数据的接口，`privateCommand` 只对键盘当前绑定的编辑器有效。
- **用带 `dataGroupId` 的 `@ohos.data.preferences` 或关系型数据库。** 文档说它们支持「同一应用的不同进程间共享，只支持三方应用中输入法和输入法的扩展场景使用」，并提供 `multiProcessChange` 通知。不用，是因为偏好文档、统计、皮肤库都是 client-core 管理的文件，带着锁和原子替换，换成 preferences 等于把这些存储在 ArkTS 里重写一遍。
- **什么都不改，只在文档里说明。** 不行：设置页对键盘基本不起作用，打字统计永远为零，这是功能失效。

## Consequences

- 签名 Profile 带上 data-group-id 之后，设置页改的方案、按键反馈、主题、皮肤、插件在键盘下次获得焦点时生效；完整体验模式下，键盘里的登录会话、打字统计也和设置应用一致。没有共享目录时行为与改动前完全相同。
- 基础访问模式下是单向的：键盘工具栏里改的简繁、标点等会在设置应用下次改动偏好并发布时被覆盖；统计计数留在键盘里，设置应用的统计页看不到；键盘里的云剪贴板等账号功能仍按匿名账号。统计页还没有提示「需要完整体验模式」，这一条留作后续。
- 同一份数据在两个沙箱和共享目录里各有一份，皮肤和插件目录会占两到三倍空间；目录指纹按秒级修改时间和大小算，同一秒内大小不变的改动察觉不到，下一次变化会一起带过去。
- 本地语音模型（`files/voice-models`，体积大）不在镜像范围内，复制代价太大；设置应用下载的本地语音模型键盘仍然用不到，留作后续。云剪贴板的端到端密钥串（账号路径与自建中继、WebDAV 各一份）和网盘日志缓存由设置应用发布、键盘导入，键盘只用设置应用生成的身份，一台手机只登记一台设备，见 [鸿蒙接入自建中继与 WebDAV](../feature/2026-10-27-harmony-cloud-clipboard-relay-webdav.md)。
- 两边对同一条的冲突按变化时刻裁决，依赖同一台设备的系统时钟；用户在两个进程里几乎同时改同一项时，后发布的一方赢。

## Verification

- `bash platforms/harmony/tests/run.sh` 全部通过，其中 `shared-state-mirror-policy.test.ts` 覆盖指纹（偏好不受修订号和键顺序影响、目录不受列举顺序影响）、只复制变化的条目、删除的条目通知对方、只导入变化的条目、账号会话只在完整体验模式交换、两边都改时较晚的一方为准、导入后不会发布回去、统计开关未同步时不采用键盘的统计；`shared-sandbox-policy.test.ts` 覆盖拿不到共享目录时的退回。
- `hvigorw assembleHap --no-daemon` 编译 ArkTS 并打出未签名的 HAP。
- 没有在真机上验证：华为工单答复模拟器不做这项授权校验，运行会报 15501002，验收要等 AGC 网页端新建的 Profile 签名后在真机上做。验收项：设置页改输入方案，键盘下次弹出时生效；完整体验模式下设置页登录后，键盘里的云剪贴板可用；开启统计后打字，回到设置应用统计页计数增加；基础访问模式下键盘不写共享目录，没有异常日志。
