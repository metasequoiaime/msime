# Agent Note: 会话中的连续多语言候选与学习边界

Status: implemented

## Problem

#8921 的[词库适配器](2026-10-24-multilingual-dictionary-adapter.md)能返回完整混合路径，但还没有会话候选与选择语义。直接将新行塞进列表会影响固定槽位、快捷短语组的位置与调频，分段信息也不能靠候选下标跨重排传递。完整产品仍归[统一输入提案](../../proposed/feature/2026-10-24-unified-language-composition.md)。

## Decision

`SessionOptions::multilingual_languages` 默认空集合关闭。会话持有独立适配器，仅在普通全拼、混输总开关打开、没有专用英文、本地模式、光标前缀、辅助码或单字限制时查询全串。中文边基于全拼，不将双拼原始编码解释成全拼。

候选来源追加为 `Multilingual = 18`，不改变已有数值。适配器证明存在完整中文路径时，混合行放在完整中文候选之后；否则可以领先。固定槽位和联系人组优先保留，新行插在最后一条保留行之后，避免挤动用户指定的候选位置。已有同文行保留原来源。

选择来源 18 时整段消费，不调词频、不写跨语言整句或个人上下文，也不参加候选管理。快捷短语计位谓词同样排除此来源：选中混合行不能触发越组调频，选择短语组时也不能将混合行算成普通槽位。领先混合行之后的默认中文候选继续按默认选择处理。

当前最多一条最佳混合路径，`SessionSnapshot::multilingual_conversion` 只在实际存在来源 18 的可见行时导出单个转换。[运行时逐段输出](2026-10-24-multilingual-runtime-output.md)按来源、编码及完整词面匹配使用，不将它当成与候选索引平行的数组。取消组字清当前转换，词库修订清适配器缓存；下一次组字不能复用旧分段。

会话使用已解析的 `japanese_dictionary` 路径，空路径才回退到资源目录；准备时沿现有日文提供者后台预热。预热与立即按键仍可能竞争首次加载锁，本切片不声称消除了冷启动等待。

## Alternatives considered

- 给每条候选增加一份平行分段数组，能直接按索引取信息，但每个固定位置、个人上下文和在线行重排都必须同步另一组状态；当前仅一个最佳混合结果，因此使用单个可选转换与来源、编码、词面核对。
- 最后无条件插到列表首位，能让混合结果容易被看到，但会挤动固定槽位，也违反完整中文优先，因此按中文覆盖证据和已有保留位置插入。
- 沿用普通候选的快捷短语计位和学习，能复用全部调频路径，但会把跨语言转换当成普通词库行，选择混合结果也可能改变短语组槽位，因此显式排除来源 18。

## Verification

真实合成词库与会话覆盖完整混合候选、两次语言切换、中文优先、关闭及语言子集、显式日文资源路径、光标前缀、取消与分段元数据失效、固定位置、快捷短语计位及学习边界。独立审查发现混合行挤动固定候选后，先以一项真实固定操作复现失败；修复后该项通过。随后两项快捷短语回归得到 28 通过、2 失败，均为实际槽位 1、预期 0；排除来源 18 后 30 项通过，独立复审关闭阻断。

同源 Windows 最终验证为连续多语言专项 30 项、快捷短语相关套件 18 项全部通过，引擎全部 target 的严格 clippy、workspace 格式、Host API 构建、正规 CMake 配置和完整 quick 均通过，前后 18 份源码与笔记散列一致。quick 实际构建 TSF、Server 及原生目标，131 项可移植检查通过、2 项按宿主差异排除、116 项交原生构建，pipe-only 通过。缺前端依赖、移动 SDK、Apple 宿主和 Docker 的阶段如实跳过，既有链接器诊断没有压制。

同一源码使用正规 `target/android-cargo` 构建 `aarch64-linux-android` 测试程序，在专用 API 35 `emulator-5590` 执行 30 项专项全部通过，耗时 1.78 秒，部署前后程序 SHA-256 与源码散列一致。这是 `adb shell` UID 的引擎测试，未安装 APK，不代表应用沙箱、设置或 IME 入口已经验收。

## Consequences

会话层可以在关闭产品入口的情况下验证完整消费、中文优先及学习边界。代价是启用时额外持有词库连接；首次日文模型准备仍需后续处理。此切片没有共享偏好、Host API 选项、逐段简繁或四套设置入口，不能作为 #8921 已完成的证据，部分 PR 仍使用 `Refs #8921`。
