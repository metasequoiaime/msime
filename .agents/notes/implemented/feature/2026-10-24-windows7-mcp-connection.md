# Agent Note: Windows 7 的 AI 助手连接与双架构 MCP

Status: implemented

## Problem

兼容设置已有 AI 服务配置，却没有现代设置里的 MCP 连接操作；只把 `settings:mcp` 路由落到 AI 服务表单不能算能力可达。专用核心脚本也只收集 x64 MCP，32 位 Windows 无法执行它。

## Decision

为 MCP 提供独立原生页面，复用 `McpConnect.h` 的权限、命令与 JSON 配置生成规则，经同一 Host API 读取状态和写入助手配置。页面提供 Claude Code、Codex、命令行、可自动写入的助手和其他 JSON 配置；已经连接的助手读取实际权限，修改保留为该助手的草稿。仅写入时确认当前权限；已有不同条目由共享接口拒绝，另一次明确确认后才允许替换。其他配置键和用户偏好默认值保持不变。

服务位置、运行时选项和助手配置在串行工作线程读写。仅保存两个权限开关的本机选择到现代设置相同的 edition 注册表值；不放进云端偏好。测试通过传输边界注入合成状态与临时助手配置，不能扫描或改写开发机真实助手配置。复制只写用户明确选中的命令或配置。

Win7 核心脚本为 x64 和 x86 同样构建、审计、收集 MCP，继续在 MCP 重链 host-api 之前保存兼容核心。原生入口只连接同架构产物，Win7 loader 与实际协议另验。

Win7 SP1 x64 的交互桌面实际启动 x64 与 x86 `msime-mcp tools`，使用各自的独立合成配置与状态目录完成客户端／服务端握手，退出码均为 0，各返回 8 个工具。PowerShell 2 验收先持有进程句柄再等待退出，避免已退出进程的 `ExitCode` 为空被误判；成功结果还核对实际工具清单。

## Alternatives considered

- **只展示一段固定 MCP 配置。** 不需要配置写入，但无法反映实际安装路径、运行时选项、已连接权限和配置冲突，因而沿用现有共享状态与安装服务。
- **让 x86 包继续携带 x64 MCP。** 可复用已有构建，但 32 位 Windows 根本无法执行，所以两个架构都构建同一源码。

## Testing

在 Windows 11 构建机上，x64 与 x86 设置窗口各 13 套回归通过。新增实际 HWND 回归覆盖已连接助手的真实权限、分助手草稿、复制命令与配置、授权取消、冲突取消及明确替换、撤销权限后的实际重读、无效 JSON、字段类型错误、尚未初始化与关闭等待线程。根设置窗口另验 `settings:mcp` 的延迟导航、懒创建与偏好修订不变；后台读取期间不假定导航已同步完成。测试传输与注册表边界注入合成内容，不读写真实助手配置。

设置程序的已知阻断导入检查 x64 覆盖 362 项、x86 覆盖 356 项。`Build-Windows7Core.ps1 -Architecture x86` 完成核心、四套兼容测试与 MCP 构建；收集后的 x86 MCP 有 265 项导入并通过检查，`--version` 返回源码平台版本 `0.3.0`。两个架构的最终收集程序经 `tests/tools/windows7_mcp.py` 验证 CLI、MCP initialize、工具列表、权限差异、读取偏好及合成快捷短语。Win7 SP1 x64 交互桌面的 x64／x86 MCP 原生窗口回归均通过，包含后台状态、权限草稿、两阶段确认、错误响应及关闭等待；这项窗口回归不启动真实 AI 助手。完整偏好由共享写入服务在临时目录生成，不在 Python 另抄默认值；SQLite 连接显式关闭后清理目录。

## Consequences

Windows 7 的 AI 助手连接有独立 `settings:mcp` 页面，命令、权限与写入规则继续由既有共享层持有。独立子页面保持后台文件访问与根设置偏好保存分离，但要维护一组 Win32 控件、工作线程收尾和对共享状态格式的读取校验。无效或过时的响应不能保持写入按钮可用；每次成功写入后重新读取实际状态，不用草稿伪造已连接结果。

Win7 上第三方 AI 助手能否运行归各自产品，页面生成的连接配置与本机 MCP 功能仍需可用。配置文件可能被其他程序并发修改，共享安装服务继续保留原子写入边界。双架构 MCP 的 Win7 loader 和客户端／服务端协议已实测，产品已进入完整安装布局；真实第三方 AI 助手未启动，现代完整安装包未重新实装。
