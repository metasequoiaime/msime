# Agent Note: 鸿蒙手机长按候选打开释义卡片

Status: implemented

## Problem

#10915 要求三端手机键盘长按候选时打开一张「释义」卡片：盖住按键区，列出候选的全部译文和来源，能「上屏译文」和「复制译文」，原来长按菜单里的操作并进卡片。维护者 2026-11-05 已经定了设计，本篇只记鸿蒙这一端怎么落地、issue 没写死的地方怎么取舍。

鸿蒙改动前：手机上长按候选栏的候选，在按键上方弹出一条横向滚动的「候选词管理」条，里面是上屏释义、优先显示、五个固定位、取消固定、删除词条、朗读和加入生词本；长按展开面板里的候选，只在它带着译文时弹出一条只有上屏释义的「释义」条。候选栏上的译文是一整串（多种语言、多个来源用「 / 」连着），不带来源；手机候选栏还只显示第一目标语言（`TranslationPolicy.keepPrimaryOnly`），第二目标语言根本没查。

## Decision

手机和平板（`!KeyboardFormFactor.isDesktop()`）上，长按候选栏或展开面板里的候选打开释义卡片；2in1 的候选窗不变，触屏长按仍是释义加最后一组、右键仍是整份管理菜单。上屏后的联想候选照旧长按什么也不做（`candidateManagementAllowed`）。

**画面**（`keyboard/candidate/CandidateGlossCard.ets`）：标题「释义」和「收起」，候选原文大字，每种目标语言一段：义项逐条列出（多于一条时编号），下面一行「目标语言名 · 来源名」；没有任何一段时写「暂无译文」，没有可用的在线服务时再补一句「可以在设置里开启翻译服务」，在线请求还没回来时写「正在查询译文…」。下面是原来长按菜单里的操作（横向滚动的一行），最底下是「上屏译文」「复制译文」两个按钮。卡片画在 `keyboardStack` 里按键区的位置，候选栏那一段是一层透明的点按区。

**译文从哪来**（`CandidateGlossCardPolicy`、`KeyboardSession.glossCardLookup` / `glossCardFetch`）：只走现有的候选翻译通路。

- 查询文档取共享层此刻的 `translationQuery`，`cardQuery` 把候选换成长按的这一个（Engine 原文和来源，繁体输出时显示的字不是查词的字），不经过 `keepPrimaryOnly`，所以有第二目标语言时两种都查。「仅当前高亮」时共享层把整页的离线释义放在 `gloss_query` 里，`cardQuery` 把它的目标语言、离线词典和英文释义开关并回主查询，服务配置取主查询的。来源本来就不配释义的候选（`sourceGetsNoGloss`）不查。共享层不给查询（候选翻译和离线释义都关着）时卡片直接是空状态。
- 打开时同步查本机：随包英文释义（`appendOfflineGloss`）、各语言的离线释义词典（`offlineTargetGlosses`），以及候选栏此前问在线服务得到、还在 `translationCache` 里的译文。缓存里没有、也不在失败冷却期里（`translationNegativeCache`）的语言记成 `wanted`。
- 有 `wanted` 的语言时，`glossCardFetch` 对每一种调候选栏同一个 `fetchTargetTranslations`，只带这一个候选：同一份翻译计划、同样先问隐私政策授权（`translationHttp` 里的 `HarmonyPrivacyConsent.networkAllowed`）、答到的写进缓存、失败进冷却，所以一个候选每种语言最多请求一次，候选栏之后直接用缓存。请求挂在候选栏当前的翻译代次上，候选栏换页或换会话时作废，卡片按本机已有的画。
- 「仅当前高亮」时长按一个不是高亮的候选，也为它问一次服务：长按是用户对这一个候选的明确请求，发送的仍是 PRIVACY.md 已写的「待翻译的候选词」。高亮不在这一页时共享层只给不带服务的离线文档，卡片只有离线释义。
- 每种语言只列一个来源，先后与候选栏相同：英语的随包英文释义最先（有它时候选栏也不问服务），然后是用户自己的在线服务，离线释义词典补服务没答的。来源名是 `离线释义`、`腾讯翻译`、`小牛翻译`、`自定义服务`、`AI 辅助`；`水杉账号` 也在表里，但鸿蒙没有账号译文这条路径（PRIVACY.md 写明），实际不会出现；`AI 辅助` 由 `AiGenerationGate` 关着，鸿蒙上目前也不会出现。

**两个按钮**交出同一段文字：第一目标语言那一段的第一条义项。第一目标语言没有译文、只有第二目标语言有时，两个按钮都不可用，读屏补一句「第一目标语言还没有译文」，不拿第二目标语言顶上。「上屏译文」先上屏再 `cancel` 结束组字，与上屏释义同一个顺序，诊断行写「已输入 …」，卡片关掉，从展开面板打开的还收起面板。「复制译文」用 `pasteboard` 写纯文本，卡片留着，诊断行写「已复制译文」或剪贴板拒绝的原因（忙、系统禁止，码与 `MascotStickerPolicy` 认的相同）；鸿蒙写剪贴板不需要权限，没有 iOS 完全访问那种前置条件。

**原来的菜单**：从候选栏打开的卡片，次要操作就是改动前手机长按的整份菜单（`managementActionsFor(index, false)`），点下去照旧走 `manageCandidate`，执行完关掉卡片；「删除词条…」第一次只是待确认，卡片留着。从展开面板打开的只有上屏释义，与改动前相同（管理操作按候选栏这一页的序号，展开列表没有对得上的序号），点下去走原来的 `insertExpandedGloss`。候选栏重画时卡片换上那一格此刻的菜单（释义晚到时会多出上屏释义），那一格换了候选就关掉卡片。

**关闭**：点「收起」，点候选栏那一段（这一下被透明层吃掉，不落到候选上），键盘收起（`onPanelHidden`；鸿蒙的返回手势收起输入法，走的就是这条），换输入框（`onEditorAttached`），以及卡片对应的那一格换了候选（上屏、继续打字、展开列表重取）。

**无障碍**：标题、候选（「候选，…」）、每一段（「英语：…；…。来源：…」，整段一个焦点）、收起（「收起释义」）和两个按钮各有读屏文字，按钮是 `Button`，不可用时读屏知道。卡片开着时工具条和按键整块不进读屏（`keysAccessibilityLevel`，与键盘调整时相同），读屏不会落到被盖住的键上。

`tests/run.sh` 里钉着键盘调整时按键不进读屏的那条源码 grep 已删掉，规则改成 `candidate-gloss-card.test.ts` 的行为测试；按 AGENTS.md，改到旧守卫对应的代码时就这样换。

## Alternatives considered

- **直接用候选栏上已有的那串译文**：最省事，不用再查一遍，也绝不多发请求。不用：那一串不带来源，几种语言、几条释义用「 / 」连在一起分不开，手机候选栏又只查第一目标语言，issue 要的「目标语言名 · 来源名」和第二目标语言两段都给不出来。
- **在候选栏的翻译流程里给每条译文记上来源，卡片只读记录**：卡片不必自己查本机词典。不用：要改 `applyTranslations` 交给共享层的条目格式，或在宿主另存一份按候选、语言、来源的表，跟着候选栏的代次一起失效；第二目标语言照样要另查。卡片自己按同一套规则查一次，本机部分是几次本地词典查询，在线部分复用候选栏的缓存，结果一样，没有新的状态要维护。
- **第一目标语言没有译文时，按钮改交第二目标语言的**：只要卡片上有译文按钮就能用。不用：issue 写的是「上屏的是第一目标语言的译文」，Android、iOS 按同一句话做，鸿蒙不能单独放宽；这种情况下第二目标语言的译文仍然列在卡片上。
- **「上屏译文」交整段释义，和上屏释义一样**：少一种规则。不用：离线释义把义项用分号连着，整段上屏会把「my; mine」连分号一起打进去，Android 修过同样的问题（[Android 长按候选按义项上屏释义](../bug-fix/2026-10-11-android-gloss-insertion-senses.md)）；要整段的还可以点次要操作里的上屏释义。
- **「暂无译文」后面总是补「可以在设置里开启翻译服务」**：issue 原话没有限定。不用：用户开着服务、只是这个词没答上来时，这句话是错的，AGENTS.md 也要求每段文字有存在的必要；只在确实没有可用服务时补。
- **用 `bindSheet` 或 `bindContextMenu` 弹出卡片**：系统组件，自带动画。不用：这类弹层在输入法面板里不显示（`KeyboardView` 里展开面板长按处已经记过），所以和原来的长按条一样画在键盘窗口自己的区域里。

## Consequences

- 收益：手机上长按任一候选都能看到它在两种目标语言下的译文和来源，原来那条横向滚动的管理条里的操作一项不少，按钮和读屏都能用；在线翻译只为长按的这一个候选、每种语言最多请求一次，答到的候选栏也能直接用。
- 代价：长按会同步查一次本机词典，在线服务开着而缓存里没有时会多一次请求（「仅当前高亮」时还包括非高亮的候选）；候选栏同时在为同一个词发请求时，两边可能各发一次。手机上第二目标语言只在卡片里出现，候选栏照旧只显示第一种。
- 长按条 `overlayStrip` 在手机上不再出现候选词管理和展开面板的释义两种内容，只剩常用标点和括弧；2in1 照旧用它。
- PRIVACY.md 不改：发送内容（待翻译的候选词）、目的地（用户自己选的服务）和条件（候选翻译开着、选了服务、有凭据、已同意隐私政策）都在它已写的范围里。第二目标语言在 2in1 上本来就各请求一次，手机卡片也是。
- 卡片的视图、会话接线和手势都是 ArkTS，node 下的测试只覆盖 `CandidateGlossCardPolicy`；ArkTS 由 `hvigorw assembleHap` 编译。
- 与[移动键盘的「加入生词本」](2026-11-01-mobile-candidate-personal-wordbook.md)和[系统语音朗读](2026-11-01-system-tts-read-aloud.md)部分重叠：鸿蒙手机长按的整份菜单现在是卡片的次要操作，那两篇说的菜单项和核对规则不变。

## Verification

`platforms/harmony/tests/run.sh` 全部通过，新增的 `candidate-gloss-card.test.ts` 15 组 83 项：查询收窄到一个候选并保留第二目标语言、「仅当前高亮」的离线释义并回来、不配释义的来源不查、什么时候问服务、每种语言的来源先后、多条离线释义逐条列出和编号、六个来源名和七种语言名、两个按钮只交第一目标语言的第一条、空状态和设置提示、在线答案换上、卡片过期、原菜单的全部操作按原顺序进卡片、卡片开着时按键不进读屏、两个按钮之后的提示。`scripts/test-harmony-*.py` 58 个全部通过。

ArkTS：本机 DevEco 命令行工具 `ohpm install && hvigorw assembleHap --no-daemon` 通过，带 arm64 原生库（`build-native.sh arm64-v8a`）、引擎资源和语音运行库，改动的文件没有 ArkTS 警告。

模拟器（HarmonyOS 6.0.2 手机镜像，debug 签名覆盖安装，浏览器搜索框，全拼 26 键打 `pingguo`）：长按候选栏的「苹果」打开卡片，盖住按键区、候选栏和读音行留着；没有译文时显示「暂无译文」和设置提示，两个按钮不可用；次要操作行是原来的优先显示、五个固定位等，「平过」这种不能改词库的候选这些项置灰；点「优先显示」执行后卡片关掉；点候选栏的「平过」只关掉卡片、组字还在；点「收起」关掉；展开面板里长按「苹果电脑」打开卡片，关掉后回到展开面板；返回手势收起键盘，重新弹出时没有卡片。第一版卡片在按键区里放不下空状态的第二行，压缩了字号和间距后两行都看得见。

没有验证的：模拟器的键盘读不到隐私政策授权（没有共享沙箱），在线翻译不会发请求，键盘的偏好也改不到随包英文释义，所以有译文时的卡片（多段、多条义项、来源行、两个按钮的上屏和复制、「正在查询译文」）只有策略测试，没有在设备上看过；读屏也没有在设备上走过。
