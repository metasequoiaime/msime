# Agent Note: 鸿蒙设置应用与键盘的「我的词条」经共享沙箱收敛成一份

Status: implemented

## Problem

API 12 起鸿蒙的输入法扩展用独立沙箱，设置应用和键盘各有一份 Engine 日志（各自的 `files/state/user/msime_user.db`），各有一份「我的词条」。[共享沙箱镜像](../architecture/2026-10-09-harmony-ime-shared-sandbox.md)只交换偏好、皮肤、插件这类文件，明确把键盘的 `user/` 排除在外。可见的后果：

- 键盘打字学到的词、候选栏里删掉的词只在键盘那份里，设置页的「我的词条」列表里看不到；
- 设置页改的词、按 Engine 路线导入的词只在设置应用那份里，键盘用不上；
- 走个人词库队列的词（导入个人词库文件、云词库下载、命名词库的增删）写进的是设置应用沙箱里的队列，键盘排空的是它自己沙箱里那个，这些词哪一份词库都没进；
- 「我的词条」的 WebDAV 网盘同步（#10050）只在设置应用里跑、只同步设置应用那份：键盘的词上不了网盘，网盘来的词也进不了键盘。键盘不能自己调同步——那个 C 入口没有「只用已有身份」的开关，键盘一调就是这台手机的第二个设备身份。

## Decision

两个进程照旧各管一份日志，「我的词条」经共享沙箱里的发布文件交换，收敛成同一组；规则在 Rust 的新 C 入口 `msime_client_user_words_mirror`（`crates/host-api/src/user_words_mirror.rs`），鸿蒙宿主只决定时机（`keyboard/UserWordsMirrorPolicy.ts`）。

1. 交换的对象与 WebDAV 同步相同：日志里 `user_inserted` 而且没删的词条，身份是（词库类别、编码、词），读写都经 `dictionary_webdav` 的 `EngineDictionary`（一致的只读事务读、每批 128 项的批量写、每批之前取维护权）。权重、学习记录、固定位置不交换：设置应用不打字，那些只属于键盘。
2. 每一边在自己私有的 `files/state/user-words/` 里给每个词条记一个「最后写入者胜」的寄存器（混合逻辑时钟的时间戳、在不在）和本机词库里实际有没有它（`applied`），并把寄存器表原子发布到 `<共享目录>/msime/<settings|keyboard>/user-words/words.json`。这个文件不进镜像的清单和指纹，由两边的 Rust 直接写、直接读，不在共享目录里建锁文件。
3. 一次 `sync` 依次：把本机词库相对 `applied` 的变化记成带新时间戳的寄存器；合并对方的发布（时间戳大的胜，相同时「在」胜过「不在」），本机词库与胜出的值不一致时写进去；回收对方已经确认见过的墓碑；存盘，再发布。`publish` 只做第一步、存盘和发布，不写词库、不要维护权。
4. 时机：
   - 设置应用在窗口回到前台和每次改完设置之后（与镜像发布同一时机）在工作线程上 `sync`，之前先排空它自己的个人词库队列（每轮 4 条、最多 64 轮，命名词库每轮 `flush` 一批）。本方日志、两个队列文件和键盘的发布都没变时不做。
   - 键盘在建会话之前 `sync`（与个人词库队列的排空同一个边界，一次最多 128 项，剩下的在空闲时的会话重建里接着写）；获得焦点时发现设置应用的发布变了，排一次空闲时的会话重建。失去焦点时，完整体验模式下在工作线程上 `publish`（日志变了、距上次至少 30 秒）。基础访问模式下键盘不发布，只收设置应用的。
5. 迁移与冲突的规则：
   - 第一次运行两边都没有寄存器，各自的词都记成新加的，结果是并集，从不删词；状态文件读不懂时同样从头开始。
   - 之后按察觉到改动的时刻比较，晚的胜。删除是墓碑，对方在它的发布里报出「完整合并过本方哪一版」（`merged`），不小于墓碑时间戳时两边各自回收；墓碑另有两万个的上限。
   - 键盘一次少了 50 个以上、并且至少是原有一半的词时不记成删除，只标成本机没有：输入法里没有这种操作，多半是日志坏了被换成空的，不能让它清空设置应用和网盘上的词。设置应用一侧不挡：那边的大批删除是用户在设置页的操作，或者来自已经挡过一次的 WebDAV 同步。
   - Engine 不收的词照实记下、不再重试，免得下一次核对把它当成本机的删除或新词传回去。
6. 与 WebDAV 同步：同步照旧只在设置应用里跑（键盘仍不调 `msime_client_dictionary_sync`，没有第二个设备身份），同步的就是设置应用那份词库，所以键盘的词一旦经交换写进设置应用的词库，同步任何一次运行开头的核对都会把它们记成本机改动。为了不等下一次运行，设置应用的 `sync` 写进了键盘的改动或者记下了本方新的改动时，向设置页派发 `msime-user-words-changed`；同步由设置页排队调用：`use-dictionary-sync` 在宿主提供了词库同步、配置了网盘时听这个事件（`HOST_USER_WORDS_CHANGED_EVENT`），收到就和经设置改了词一样以 `local_change` 记一次，连续几次只排一次；宿主不在页面的队列之外另调同步。鸿蒙没有隐私政策的授权时页面拿不到词库同步，也就不听，`local_change` 可能联网，这道闸不能绕过。网盘来的词写进设置应用的词库后，下一次发布就带给键盘。

## 两种方案的比较

| | 选中：各管一份、经发布文件交换 | 两个进程直接打开共享目录里同一份日志 |
| --- | --- | --- |
| 完整体验模式 | 两个方向都通 | 能读写，但两个沙箱的 SQLite 锁要跨进程可靠 |
| 基础访问模式 | 设置应用到键盘通，键盘的词留在键盘 | 键盘对共享目录只读，SQLite 连读都要建 `-wal`/`-shm` 或锁文件，键盘打不开词库，学习和组词全坏 |
| 模拟器（没有共享目录） | 与改动前相同，两份各管各的 | 没有共享目录就没有词库 |
| 崩溃 | 状态在写词库之后存盘；没存上时，下一次核对把已写的改动当成本方的新改动再发一次，结果相同；请求编号让同一次写入重试不变 | SQLite 自己保证，但日志在别人也会写的目录里 |
| 并发编辑 | 各自的日志各自加锁，交换按寄存器的全序合并，与谁先运行无关 | 两个进程抢同一把维护锁：设置页改一个词要等键盘让出会话 |
| 键盘内存 | 一次核对在内存里放「我的词条」和寄存器表，上限十万个寄存器、文件 32 MiB | 不多占 |
| 隐私 | 不联网；词条明文在两个沙箱和共享目录里（共享目录只有这个应用的两个进程能读） | 同样在共享目录里 |
| 迁移 | 并集，不删词 | 要先把两份日志合成一份，合并规则一样要定，而且只能做一次 |

## Alternatives considered

- **两个进程打开共享目录里同一份日志。** 最强的理由是只有一份数据：没有寄存器、没有发布文件，学到的词设置页立刻看得到，也不会出现「一边学到、另一边还没收到」的窗口。不用：#10050 已经发现基础访问模式下键盘建不出锁文件，SQLite 的 WAL 也要在日志旁边建 `-shm`；默认的基础访问模式下键盘就会连词库都打不开，那是「没有键盘」。`prepare_host` 每次准备都从 `user_data` 推出工作词典代次并往里写，`user/` 整个都得搬进共享目录，[共享沙箱的决定](../architecture/2026-10-09-harmony-ime-shared-sandbox.md)当时就因为同样的原因放弃了直接共用状态目录。模拟器上没有共享目录，这条路在开发机上也没法跑。
- **设置应用持有唯一权威的词表，键盘只经一个发件箱把自己的改动交给设置应用。** 理由是规则简单：设置应用是唯一的写者，键盘发件箱里的每条操作按顺序应用一次。不用：基础访问模式下键盘写不了共享目录，发件箱根本发不出去，而键盘仍要按设置应用的词表改自己的词库——要么把键盘学到、还没交出去的词按权威词表删掉，要么键盘自己也得记「这是我加的、还没交出去」，那就又回到了每边一份状态。发件箱还要确认和截断，设置应用要记着处理到了哪一条；对称的寄存器表把这两件事并成一件，两个方向用同一套规则和同一份测试。
- **复用 WebDAV 同步的协议核心，把共享目录当成一个本地「网盘」。** 理由是合并、墓碑、时钟都已经写好并且测过。不用：那个协议带着密钥串、设备批准、加密、epoch 封口和请求额度，这些在同一台设备的两个进程之间都没有意义，键盘还会因此多一个设备身份——正是要避免的事。这里只借用了它的词条身份（`WordKey`）、时钟（`Clock`）和本机词库的读写（`EngineDictionary`）。
- **键盘也在会话开着的时候 `sync`。** 理由是设置页的改动立刻生效。不用：写词库要 Engine 的独占维护权，会话开着时拿不到；为它中途重建会话会打断组字。现在的做法是获得焦点时发现有新发布就排一次空闲时的重建，和个人词库队列一样。

## Consequences

- 有共享沙箱、完整体验模式下，设置页改的词、导入的词、网盘来的词在键盘下一次空闲重建会话之后可用；键盘学到、删掉的词在它失去焦点之后（最多每 30 秒一次）发布，设置应用下次回到前台时写进来，再交给 WebDAV 同步。基础访问模式下只有设置应用到键盘这一个方向。
- 迁移按并集：以前只在一边删过、另一边还在的词会回到两边。冲突按察觉到改动的时刻裁决，不是改动本身的时刻：键盘里删的词要等它下一次核对才有时间戳，这期间设置应用里对同一个词的改动更早就算更早。
- 设置应用自己排空个人词库队列，导入的个人词库文件、云词库下载和命名词库的词第一次真正写进词库；命名词库的名字、开关和来源仍只在设置应用里。
- 键盘的日志坏了被换成空的时，设置应用和网盘上的词保留，键盘这边不自动写回；设置页的大批删除（停用命名词库、清除学习数据）会删掉键盘里同样的词，学习权重和候选顺序不受影响。所以鸿蒙暂不提供「清除学习记录」，见 [移动端「清除学习记录」](2026-10-29-mobile-clear-learning.md)。
- 寄存器超过十万个或者文件超过 32 MiB 时交换停下（`user_words_too_large`），两份词库各自不变。键盘一直在基础访问模式下时，设置应用的墓碑得不到确认，最多留两万个。
- 同一组词条在两个沙箱和共享目录里各有一份寄存器；词条明文出现在共享目录里，与镜像的其他条目一样只有这个应用的两个进程读得到。共享目录会不会进系统备份没有核对过。

## Verification

- `rbuild cargo test -p msime-host-api --lib user_words_mirror`：内存词库上的规则（第一次合并取并集、一边删一边加两者都保留、同一个词条晚的胜而且与合并顺序无关、并发的相反改动收敛不来回翻、基础访问模式只收不发、忙和上限留到下一次且写好才确认、Engine 不收和删不掉的词不传回去、键盘的大批删除挡下而设置应用的不挡、墓碑在对方确认后回收和上限）、发布与状态的编解码，以及两份真实的 Engine 词库经 C 入口收敛、输入会话开着时 `sync` 留到下一次而 `publish` 照常、请求校验和同一目录的并发调用。
- `apps/desktop` 的 `vitest run tests/settings/dictionary-sync.test.tsx`：宿主派发的事件只排一次 `local_change`，停用网盘或卸载以后不再听，宿主不提供词库同步时不发请求。
- `bash platforms/harmony/tests/run.sh`：`user-words-mirror-policy.test.ts` 覆盖请求的形状（基础访问模式不带发布路径、`publish` 不带对方和上限）、回复的解析、哪些错误重试、键盘建会话之前和失去焦点时什么时候做、设置应用的标记、队列排空的判断。
- `scripts/test-harmony-user-words-mirror.py` 钉住 ArkTS 里编不进 node 测试的调用点：键盘在 `client.create` 之前 `sync`、只在完整体验模式下给发布路径、失去焦点时在工作线程上 `publish`，设置应用先排空队列再在工作线程上 `sync`，键盘不调词库同步。`scripts/run-checks.sh` 全部通过或按规则跳过。
- `apps/harmony` 的 `pnpm run build` 通过；`hvigorw assembleHap --no-daemon` 编译 ArkTS 并打出 HAP（没有先跑 `build-native.sh`，包里不带原生库）。
- 没有在真机或模拟器上跑：模拟器不做共享沙箱的授权校验、拿不到共享目录，这条路只能在带 data-group-id 的签名包装到真机后验收。验收项：完整体验模式下键盘里学一个词，回到设置应用「我的词条」里看得到，配置了网盘时另一台设备收到；设置页加一个词，键盘下一次弹出后能打出来；基础访问模式下设置页的词照样到键盘、hilog 里没有写共享目录的错误。
