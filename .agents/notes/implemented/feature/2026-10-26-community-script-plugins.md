# Agent Note: 脚本插件可以发布到社区，先审后发

Status: implemented

## Problem

维护者 2026-10-26 定下的目标是让用户按自己的需要做插件、把插件生态做起来，而脚本插件是唯一能写出「行为」的类型。之前脚本插件只能本地导入：`PUBLISHABLE_KINDS` 里没有 `script`（见 [脚本插件进入插件包体系](../architecture/2026-10-12-script-plugin-kind-and-grants.md)），社区后端只收 `schema_version = 1` 且拒绝非空 `permissions`。一个人写好的插件只能靠别处传文件分享，别人拿到的包也没有任何人看过。

数据类插件的社区是先发后审：发布即公开，`pending` 当作已通过，审核员事后下架。这套做法放到脚本插件上不够：脚本包带着在输入法进程里运行的代码，它申请的 `rewrite_commit` 能改掉用户输入到应用里的文字，第二批提案里的 `persist_data` 能把读到的文字长期留在本机。先公开再下架，中间那段时间里已经有人装了。

## Decision

社区接受第三方脚本插件，**先审后发**：脚本包审核通过之前，只有作者和管理后台看得到。数据类插件不变，仍然先发后审。

客户端（本仓库）：

- `crates/client-services/src/plugins/community.rs` 的 `PUBLISHABLE_KINDS` 在桌面（macOS、Windows、非 ohos 的 Linux）多一项 `PluginKind::Script`，`KINDS_DECLARATION` 同时声明 `script`；鸿蒙和移动端两者都不变，所以它们既发不出也收不到脚本包。打包（`pack`）和安装（`install`）走的是本地导入同一份校验器，模块按 ABI v1 校验，安装不授予任何能力。
- 社区条目多一个可选的 `permissions`（清单申请的能力名）。只有 `script` 条目能带它，形状不对（非小写字母和 `_`、重复、过长、超过 16 个）整页拒绝；本客户端还不认识的能力名照样收下，页面原样列出并提示「安装会失败，请先更新输入法」，因为服务端会先于客户端认识第二批能力。
- 发布脚本包时服务端以「请求不合法」拒绝（旧服务端对未知 kind 回 400 `invalid_kind`），客户端说成 `plugin_community_script_unsupported`：「服务器暂时还不接受脚本插件，可能尚未更新」。打包时已经用完整的校验器检查过包，元数据也在本机查过，正常情况下 400 只可能是服务端不认识 `script`。
- 共享设置页：社区插件页在宿主声明 `script_plugins` 且接了授权命令时多一个「脚本插件」筛选；发布对话框列出自己导入的脚本包（官方 `uuid` 不列），选中脚本包时提示要经审核、按钮改成「提交审核」；作者自己 `pending` 的脚本条目显示「审核中」（只对脚本，数据类插件的 `pending` 照旧不显示）；脚本条目的卡片列出申请的能力，详情用授权页的同一套白话（`plugin-script-model.ts` 的 `capabilityLabels`）逐项列出，`rewrite_commit` 和 `persist_data` 标「注意」，并写明「安装后不会运行，要在脚本插件页授权」；装好脚本包后切回「我的插件」并直接打开它的授权页（`PluginOpenRequest` 从设置外壳传到 `PluginsSection`）。
- Windows 原生设置（WinUI 与 Win7）的社区插件页做同样的事，能力说法复用 `PluginPageModel.h` 的 `capability_label`。
- 鸿蒙 2in1 的设置页接上社区插件图库（`apps/harmony/src/main.tsx` 的 `communityPluginClient`，经 ArkTS 的 `community_plugin` 通道转给 `msime_client_community` 的 plugin_* 操作，打包预检、发布和安装带上状态目录），只有数据类插件。
- `mcp-server` 的 `publish_plugin` 仍然拒绝脚本包：发布可执行代码要经设置页的发布对话框，用户在那里看到审核提示。

服务端（msime-cloud，另一个 PR）：

- `pluginKinds` 加入 `script`，清单校验镜像 `script_pack.rs`：`schema_version = 2`、能力白名单与依赖互斥规则、`[script]` 的键与取值、指令规则、模块以 wasm 文件头开头且不超过 256 KiB。第二批能力提案（[脚本插件第二批能力](https://github.com/metasequoiaime/msime/blob/feat/script-capabilities-v2/.agents/notes/implemented/architecture/2026-10-26-script-plugin-capabilities-v2.md)）里的 `insert_candidates`、`persist_data`、`[[script.settings]]`、`[script].data` 和 `[[script.commands]].arguments` 提前接受，客户端实现它们时不用再等一次服务端发版。
- 先审后发落在可见性条件上：作者以外的人在列表、搜索、详情、下载、评分、收藏和举报里都把 `pending` 的脚本包当作不存在。审核列表带类型、申请的能力和要重点看的能力。

### 服务端与客户端的分工

服务端不能运行 wasm 校验器，模块的导入表、导出和「申请的能力与模块用到的一一对应」只有客户端能判断。所以服务端只做「不执行代码就能检查」的那部分，而且**只会比客户端宽，不会比它严**：服务端拒绝一个客户端能装的包，用户就没有办法发布它；放进来一个客户端装不了的包，代价只是安装时失败，客户端在发布前和每次安装时都会用同一份校验器重新检查。插件文本里客户端禁止的那批格式和不可见字符，服务端只检查控制字符，就是按这条取舍的。

### 新版本

服务端的发布不能原地替换包，新版本以新的发布 UUID 发布成新的一行。于是新版本待审期间，旧的已通过版本照常可见、可下载，不需要额外的表结构；审核通过后由作者自己删旧版本。

## Alternatives considered

- **脚本插件也先发后审，靠举报和事后下架。** 最强的理由是一套审核流程、零额外代码，社区反应更快。不用：脚本包是代码，`rewrite_commit` 能改上屏、`persist_data` 能留下输入记录，事后下架挡不住下架前装上的人；授权页的逐项授权是第二道防线，不能当第一道。
- **只让官方维护的脚本包进社区（白名单作者）。** 最强的理由是风险最小，审核员只需要信任少数人。不用：维护者要的是用户自己做插件的生态，白名单等于不开放。
- **服务端解析并校验 wasm（用 Go 的 wasm 库重写一份 ABI 校验）。** 最强的理由是服务端能在发布时就拒掉导入表不对的模块，审核员看到的都是能装的包。不用：ABI 校验的权威实现在 `msime_script_runtime`，第二份实现会和它漂移，而漂移的方向一旦是「服务端更严」，用户就发不出合法的包；客户端在发布前和安装时都会检查，服务端再查一遍收益很小。
- **新版本覆盖旧行、回到待审，旧版本在审核期间隐藏。** 最强的理由是每个插件在社区里只有一行，评分和下载数延续。不用：服务端的发布本来就不允许原地替换（重试幂等靠发布 UUID 和请求摘要），新版本作为新行最省事，还顺带让已通过的旧版本在审核期间照常可用；要合并评分是另一件事。
- **把能力的中文说法下沉到 Rust，经命令交给共享页和 Windows 原生页。** 最强的理由是说法只有一份。不用：授权页的两份说法（`plugin-script-model.ts` 和 `PluginPageModel.h`）已经存在且注释要求一字不差，这次社区页复用它们，不新增第三份；下沉是另一次重构。

## Consequences

- 收益：用户写的脚本插件可以分享，每个进社区的脚本包都有人看过；作者在「我的作品」里看得到「审核中」，别人看不到没审过的包。安装和本地导入一样不授予能力，用户装好后被直接带到授权页。
- 代价：审核员要读脚本包的能力和说明，审核不及时会让作者等。服务端放行的包可能在本机装不上（服务端规则更宽），用户会看到安装失败的原因。
- 归档上限没有改：数据文件合计 8 MiB 加上模块会超过 8 MiB 的归档上限，带满数据文件的脚本包要等提高上限后才能发布；现在没有客户端写数据文件。
- 上线顺序：先部署服务端，再发布客户端。新客户端碰到旧服务端时发布脚本包会看到「服务器暂时还不接受脚本插件」；列表照旧，因为旧服务端忽略不认识的 `kinds` 名字。滚动更新期间旧版本副本的下载不认识先审后发，知道发布 UUID 的人能经旧副本下载待审的包，全部副本升级后关闭。
- 验证缺口：共享页、鸿蒙页和 Windows 原生页没有在真机上走过「发布 → 审核 → 安装 → 授权」全程；WinUI 的 `main.cpp` 只由 PR 的 Windows CI 编译。
