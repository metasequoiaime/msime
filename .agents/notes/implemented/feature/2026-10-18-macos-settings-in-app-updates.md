# Agent Note: macOS 设置应用在应用内更新完整安装包

Status: implemented

## Problem

[输入法本体的 Sparkle 更新](../../implemented/feature/2026-10-15-macos-sparkle-input-method-updates.md)只更新 `~/Library/Input Methods` 中的输入法。设置应用的关于页继续询问 GitHub 并打开下载页，用户要下载 DMG、替换应用再启动，设置界面的修复也无法自动到达。用户要求点击更新后直接完成升级。

## Decision

设置应用复用包内 Sparkle 2.9.6 的标准更新界面，用独立的 `appcast-settings-<edition>.xml` 和包含完整设置应用的签名归档更新 `/Applications` 中的应用。更新后 Sparkle 重启设置应用，既有启动安装流程把内嵌的新输入法安装到用户输入法目录；输入法原有独立 feed 保留。

宿主只在本应用包含 feed、公钥与 Sparkle 框架时向共享页面提供原生检查更新能力；关于页优先调用它，由 Sparkle 完成检查、下载、验签、安装和重启。不带 feed 的开发构建保留官网入口。框架在运行时从应用的 `Contents/Frameworks` 加载，Rust 开发编译不新增 Sparkle SDK 路径依赖，也不把更新能力扩散到 Windows、Linux 或移动端。

设置应用的 `CFBundleVersion` 与内嵌输入法一致，保证跨版本构建号单调递增。打包工具从已暂存的输入法读取 feed、公钥和构建号；两份 appcast 和两份归档都由现有私钥签名，正式发布时同时核对和上传。设置应用只在用户主动检查时启动更新器，避免多个共享面板进程各自检查更新；输入法保留原来的后台检查策略。此改动不触发发布，不生成新产品密钥。

## Alternatives considered

- **只从设置页唤起输入法的 Sparkle**：复用全部既有更新产物，接线最少。但设置应用及其界面仍然落后，用户依然要手动替换 DMG，不能满足整个应用直接升级。
- **引入 Tauri updater 插件**：能够更新外层应用，也能把进度留在共享页面。但需要另一套更新格式、密钥与发布元数据；现有原生宿主已经随包分发 Sparkle，复用它可以保留相同的签名与安装机制。

## Consequences

- 发布包关于页的检查更新走原生更新器；无 feed 构建诚实保留官网下载页，失败可重试。
- 配置、归档、版本隔离与 UI 入口有回归验证；本机完成设置组件编译、打包和签名验证。
- 标准原生更新器已在合成应用中启动并发现签名更新；后台合成应用通过同一 Sparkle 核心完成签名 feed 下载、归档下载、安装与重启，落盘构建号和重启标记均为 `2`，新包严格验签通过。正式版本间升级依赖新通道发布后再验收。

## Limits

- 已发布的旧设置应用没有新更新器，首次接入需要安装一次带更新器的版本。
- 更新设置应用需要重启该应用；输入法进程仍由既有版本比较与安装逻辑更新。

## Verification

- 完整应用更新入口优先于发布列表与外链、失败可重试的两项 React 回归通过。
- 六个发行版本的独立 feed、单调构建号、框架符号链接，以及拒绝错误版本和不验签配置的合成包测试通过。
- 前端类型检查和生产构建、Objective-C++ 编译检查通过；打包资源和既有六版本契约检查通过。
