# Agent Note: 云剪贴板端到端加密，设备批准代替口令

Status: implemented

## Problem

#6787：云剪贴板的文字以明文存在 `api.msime.app` 的账号下，服务端能读、能搜，数据库泄露就是全部内容。issue 想要自建中继；在那之前，先让服务端根本读不到内容。约束有三条：六个平台（五套独立的 HTTP 实现：Rust `client-core`、Swift `BackendClipboardClient`、Android 两套 Java、HarmonyOS ArkTS）都要能读写同一份剪贴板；用户不该为此记一个额外的口令；服务端被攻破时也不能悄悄加一台设备来读。

## Decision

协议、接口和宿主职责写在 [`docs/cloud-clipboard-e2e.md`](../../../../docs/cloud-clipboard-e2e.md)，那是服务端、驱动和各平台共同的契约；这里记为什么这样定。

- **设备批准，不用口令**：每台设备（每个应用安装）首次使用时生成 X25519 密钥对，私钥只在本机。账号的剪贴板密钥 `K` 由第一台开启的设备随机生成，服务端只存用各设备公钥封装过的 `K`（临时 X25519 + HKDF + XChaCha20-Poly1305）。新设备登录后是「待批准」，在已有设备上点「允许」才封装一份给它。两台设备显示同一组由新设备公钥算出的 16 位核对码；服务端想混进一台自己的设备，得在用户核对前碰出同一组核对码。
- **换钥只封装给本机**：移除设备、重置都生成新的 `K`，服务端删掉全部条目和旧封装（最多 50 条、本来就是临时内容，不做重新加密）。新密钥不封装给设备列表里标着「已批准」的其他设备，因为这个标志来自服务端，服务端可以把自己的设备也标成已批准；其他设备要重新点一次「允许」。
- **唯一模式**：不保留明文路径。服务端上线时删掉全部明文条目，此后拒收 `text`；旧客户端的云剪贴板显示加载失败或上传失败，直到升级。
- **去重和搜索**：去重用 `HMAC(由 K 派生的去重密钥, 明文)`，服务端只比较标签；搜索移到客户端，在解密后的最多 50 条上做。明文长度上限仍是 4000 个 UTF-16 单元，密文字段上限 16384 个字符。
- **流程只写一份，sans-IO**：`crates/client-core/src/cloud/clipboard_e2e.rs` 既有原语，也有驱动：驱动决定下一步发哪个请求（取密钥状态、登记本机、建钥、解封装、列出并解密、上传、批准、换钥），宿主只负责带凭据发请求、把状态码和正文交回、保存驱动交回的密钥串。C ABI 是 `msime_client_cloud_clipboard_e2e`，Android 经 JNI、HarmonyOS 经 NAPI、Apple 平台由宿主把它注入 `shared/backend`（那个 SPM 包不链接 Rust 库）、桌面端在 Rust 里用 `run` 直接驱动。各宿主原有的列表解析几乎不用改：驱动交回的列表与旧接口的明文形状相同，只多了 `e2e` 状态。
- **一台设备一份密钥串**：存在与账号会话相同的安全存储里（位置见协议文档的表），输入法进程、设置进程和 Tauri 设置页共用；否则同一台设备会登记成几台、要批准几次。Tauri 移动端经平台插件的 `loadCloudClipboardKeystore` / `saveCloudClipboardKeystore` 读写原生那一份。退出登录时与会话一起删除。
- **Swift 密钥读写绑定登录**：每次操作把驱动绑定到发起时的 `userID` / `sessionID`。读写密钥串时取得账号已有的跨进程刷新锁，重读持久化会话并在 actor 同一同步段里校验、读写；网络请求不持锁。驱动每步及下一次发送前再核对会话，令牌刷新保持绑定，退出或同账号重新登录后旧操作取消。iOS App、键盘扩展、macOS 原生回退页与共享面板 provider 都传入这份绑定。

## 威胁模型与残余风险

防的是数据库泄露、运维读库，以及服务端主动登记设备。服务端仍看得到条目数量、时间、置顶、写入设备名、哪些条目内容相同，以及设备的名称、公钥和登记时间，这些写在 PRIVACY.md。没有防的：服务端可以给一台刚登录、还没被批准的设备发一把它自己生成的密钥，这台设备随后上传的内容服务端能读到；其他设备解不开这些条目（密钥编号不同），表现为「这台设备传的东西别的设备看不到」。要防住它，新设备也得核对批准者的身份，v1 不做。

## Alternatives considered

- **同步口令（Argon2id 派生密钥）** — issue 里最初的设想，实现最直接：任何一台设备输入同一个口令就能派生出同一把密钥，不需要已有设备在线，也不需要批准流程。用户否决：为一个剪贴板再记一个口令，忘了就只能清空，体验上不可接受。设备批准把这份负担换成了「新设备第一次要在旧设备上点一下」。
- **换钥时封装给所有已批准的设备** — 移除一台设备后其余设备不用重新批准，体验更好。不用的原因见上：「已批准」来自服务端，信它就等于让服务端决定谁拿到新密钥。
- **同账号的设备自动批准** — 完全无感。只防得住数据库泄露，防不住主动作恶的服务端或被盗的账号令牌：登记一台假设备就能拿到密钥。用户选择了弹窗批准。
- **各平台原生实现加密（CryptoKit、javax.crypto、cryptoFramework、Rust 各一份）** — 不加 Rust 依赖，各平台用系统库。不用的原因是五份实现、互通只靠测试向量兜底，流程（建钥竞争、换钥后的重试、解封装失败）也要写五遍；每个平台都已经链接了 Rust 库，写一份就够。
- **服务端托管密钥、静态加密**（Telegram 普通云聊天的做法） — 换设备零成本、能服务端搜索。但服务端仍能解密，不是 issue 要的东西。
- **保留明文模式作为可选项** — 旧客户端不受影响。用户选择唯一模式：两条路径要在五套客户端里长期维护，而且「可选」意味着多数人仍是明文。
- **只在保存前异步调用 `requireSession`** — 能复用现有 API、改动最少，但检查返回后 actor 可重入，别的进程也能在写入前登出；校验必须和实际读写在同一共享锁和同步段中。
- **锁住整个加密操作** — 最容易串行化所有步骤，但网络等待会挡住登出与令牌刷新，iOS 扩展挂起还会长期占锁；只锁本地读写。

## Consequences

- **收益**：服务端和数据库里只有密文；用户不用记任何东西；新设备必须在旧设备上被允许；以后做自建中继时，中继只需实现同一组接口，不需要碰密钥。
- **代价**：新设备第一次要在已有设备上批准，只剩一台设备时丢了它就只能重置；移除设备或重置后其余设备都要重新批准；服务端搜索没了，客户端每次列出要先取一次密钥状态（列表多一次请求）；旧版本客户端在服务端上线后不能用云剪贴板，服务端和各平台新版本要一起排期上线。新增依赖 `chacha20poly1305 0.11`、`x25519-dalek 3`、`hkdf 0.13`、`getrandom 0.4`（后三者的底层 crate 已在锁文件里）。
- **已知缺口**：同一台设备上两个进程同时第一次使用时，iOS、macOS、HarmonyOS 和桌面端可能各生成一个设备身份，服务端多出一台永远待批准的设备（可以拒绝掉）；Android 的密钥串存储拒绝写入与已存身份不同的私钥，后到的进程改用已存的身份重来，所以只会登记一台。HarmonyOS API 12 起键盘与设置应用沙箱分开，键盘读不到会话（见 [共享沙箱提案](../../implemented/architecture/2026-10-09-harmony-ime-shared-sandbox.md)），云剪贴板在键盘里按未登录处理，这次没有改变。macOS 上首次使用约 6 个串行请求，IPC 会话 35 秒、Rust 客户端 40 秒超时，网络很慢时首次使用可能超时，重试即可。Linux 上用户自建的 socket provider 不在本仓库，要自己按协议实现加密和新动作。
- **与旧笔记的关系**：[Android 剪贴板搜索](2026-10-09-android-clipboard-search.md) 的备选里提到云端分段可以用 `?q=` 做服务端搜索，这条路已不存在。自建中继沿用这里的协议和设备批准，见 [云剪贴板自建中继](2026-10-12-cloud-clipboard-relay.md)。

## Verification

协议层：`crates/client-core/src/cloud/clipboard_e2e_tests.rs` 用按协议文档实现的内存服务端跑两到三台设备的完整流程（首台建钥、待批准、批准后读到旧条目、去重、搜索、移除后换钥并锁住被移除设备、待批准设备重置接管、拒绝、两台新设备并发建钥只留一把、上传途中换钥后重传、关闭时不建任何东西、服务端伪造公钥拿不到封装、给错封装仍是待批准、解不开的条目只计数），另有一组已知答案向量：由独立实现（libsodium 的 X25519 与 XChaCha20-Poly1305、pyca/cryptography 的 HKDF）按文档算出，与 Rust 输出逐字节一致，锁住线上格式。`crates/host-api/src/tests.rs` 覆盖 C ABI 入口。

服务端（msime-cloud 的配套改动）：全部新接口和错误码、比较并交换的建钥冲突、撤销、设备淘汰、关闭与删除数据时的清理、拒收明文、迁移删除明文行，都在 `postgres:17-alpine` 上以 `go test -race` 跑过（不是跳过）。

各平台：Android 经 JNI 在 API 28 与 API 35 模拟器上跑真实驱动对假服务端的设备冒烟（`CloudClipboardDriverDeviceSmoke`）和密钥串的跨进程冒烟，`run-core-test.sh` 两边各 1267 项通过，`check-host.sh` 的 JVM 冒烟通过。iOS 模拟器上 `MSIMEClientTests` 855 项通过，其中一项经 C 绑定驱动真实 Rust 驱动、一项读写真实钥匙串条目；macOS 全量 `ctest` 149 项通过，`shared/backend` 的 `swift test` 168 项通过。HarmonyOS `tests/run.sh` 通过（新增的驱动循环测试用按脚本应答的假驱动），原生交叉编译后确认 `.so` 导出新符号，`hvigorw assembleHap` 打包成功。桌面端 `client-core` 账号层 115 项（两台设备流程、401 刷新、密钥串保存顺序与文件权限）、`host-api`、`host-macos`、Tauri 的云剪贴板测试和 iOS、Android 目标的 `cargo check` 通过；共享面板 vitest 新增 10 项，合并后 `apps/desktop` 与 `apps/harmony` 的类型检查通过。

Windows 原生设置窗口的剪贴板页（`platforms/windows/settings/main.cpp`）照共享页认得「本机待批准」和「已关闭」，这处 C++ 改动只由 PR 上的 MinGW 交叉构建检查，本机没有编译。

没有验证的：真实服务端（还没部署）、各平台装机后的真实输入法会话与设置页界面、macOS 上 Tauri 面板经 IPC 与原生 provider 的联调、Android 的 Tauri 合包 APK。服务端上线前要在一台 macOS 和一台 Android 上用测试账号走一遍：开启、在另一台上批准、互传、移除、重置。

Swift 登录绑定回归：合成请求暂停后退出登录、同账号重新登录、跨 actor 退出与重登均验证旧请求不再保存密钥或发送后续请求；锁等待期间身份被替换时不执行存储操作，同一登录的令牌刷新仍可执行，锁失败时不写入。`swift test --package-path shared/backend` 198 项通过；独立 iOS 27 模拟器的 `KeyboardCloudClipboardTests` 18 项通过，原生 service 的列表、上传及按需上传三个入口均覆盖；macOS 原生账号模型和 desktop cloud provider 测试通过，iOS 原生 App 与键盘扩展的 Release 模拟器构建通过。页面生命周期契约同步双参数操作闭包，原有两项生命周期检查通过。测试均使用合成数据，未使用真实账号或剪贴板内容。
