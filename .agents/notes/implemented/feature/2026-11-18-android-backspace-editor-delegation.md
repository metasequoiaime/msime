# Agent Note: Android 用户退格默认交给编辑器

Status: implemented

## Problem

普通退格直接调用 `deleteSurroundingText*` 删除光标前的文字，绕过了应用自己的退格处理。应用的内联对象（微信 `[微笑]`、QQ 小黄脸表情和 @、引用）的样式不跨进程返回，输入法看到的只是文字，于是要按多次逐字删掉：0.8.3 在 QQ 里删一个 21 字的 @ 要按 22 次，QQ 一直画着完整的 @，直到最后一次才消失；删一个小黄脸表情按 2 次，第一次看不出变化；微信里删一个 11 字的 @ 按 12 次。

此前靠字符特例补救：空框转交按键、拒写回退、以 `]`／U+FFFC 结尾时转交按键。QQ 的表情不以这两个字符结尾，QQ 的 @ 以普通空格、微信的 @ 以 U+2005 结尾，特例都覆盖不到，继续按应用的格式加字符规则不可持续。Gboard、fcitx5-android、Trime 在这些应用里一次删掉整个对象，它们的退格都由应用处理。

## Decision

用户的退格（各布局删除键、日文九键删假名、表情与符号面板、手写、语音锁定面板）在没有组字和选区时发送 `KEYCODE_DEL`，删几个单元由编辑器决定；输入法不再按字符猜测应用对象。组字仍归引擎，选区仍以空串替换。

只有三处仍由输入法直接按字素删除（`EditorBackspaceBoundary` 的 ICU 字素和内联范围）：

- 光标前以拉丁类组合附加符号（U+0300–U+036F、U+1AB0–U+1AFF、U+1DC0–U+1DFF）结尾。系统 `EditText` 的按键退格只删附加符号，分解形式的 é 要按两次；应用对象从不以附加符号结尾。印地文、泰文等的元音和声调符号、表情键帽和变体选择符仍交给编辑器。
- 编辑器不处理退格按键：按键超时（100 ms）后再等 400 ms，光标前文字与发出前完全相同，本次输入会话改为直接删除，并补上这一次。换输入框时复位。
- 输入法自己替换刚写下的内容（日文九键连点换假名），紧接着就要写入替换文字。

智能标点、英文纠正与候选替换、邮箱后缀、横滑和快速删除走 `deleteBeforeCursor(int)` 等各自的直接删除，不受影响：它们之后紧跟写入，必须和写入在同一通道上保持先后。

## 代码位置

交给编辑器这一路的状态和时序都在 `core/ImeEditorDelete.java`（何时改为直接删除、等待与确认、超时、横滑与快速删除的推迟、读回核对、不处理按键的判断）；`MSIMEInputService` 只在删除入口、`onUpdateSelection`、`onStartInput`／`onFinishInput`、横滑与快速删除入口各留一行接线（遵照 AGENTS.md 不往巨型文件加功能），直接按字素删除仍是它原来的 `deleteGraphemeBefore`。纯 Java 的规则分在 `BackspaceSettle`、`TouchHoldQueue`、`EditorDeleteCheck`，根容器是 `TouchHoldLayout`。

## 按键与写入的先后

按键事件和 `InputConnection` 的写入在应用侧不保证先后。模拟器探针上，普通 `EditText` 里同一批调用先发按键再 `commitText`，200 次有 12–54 次退格落在新文字之后；先上屏、再退格、再上屏 200 次全部错位。真机 QQ 9.3.85 上，退格后约 40 ms 内开始组字，10 次有 8 次新组字被退格删掉（约 80 ms 未出现）；选区回报在 QQ 晚 17–51 ms、微信 3–22 ms。所以每次交给编辑器的退格都经过 `BackspaceSettle`：

- 输入法自己的写入还有回声没到时，退格先等，回声到达或 100 ms 后再发。
- 发出后到编辑器回报选区或 100 ms 超时之前，输入法窗口根容器 `TouchHoldLayout` 按住新开始的触摸（以整次触摸为单位，规则在 `TouchHoldQueue`），确认后按原顺序放出；放出的触摸又发出退格时停在下一次触摸前面。已经开始的触摸（按着的退格自己的左右滑）照常分发。
- 连删的下一次、按住期间到来的横滑目标和松手时的快速删除、撤回，都等确认后再做；同一时刻只有一次退格在路上。
- `SelectionEchoTracker.deleteBeforeOpaque` 为这次退格记一条范围预期（光标左移 1 到读到的长度个单元、没有组字区），不再整体作废；迟到的回报不会把确认前后开始的组字当外部移动取消。超时后作废预期，和以前发按键后一样。空框（光标前读到空）不记预期：编辑器不会回报。
- 换输入框（`onStartInput`、`onFinishInput`）放弃在路上的退格，按住的触摸照常放出。

## 横滑恢复

确认后再读一次光标前文字，与发出前比较（`EditorDeleteCheck.onePlainCodePointRemoved`）：恰好少了最后一个普通码位（不是 U+FFFC）才并进这次按压的恢复记录，和直接删除时一样；应用删掉了自己的对象、删多了或读不到，一律作废恢复，不会把应用对象当文字写回。超时没有确认时同样作废。

## Alternatives considered

- **继续加字符特例**（U+2005 结尾的 @、QQ 表情的编码）：改动小，但每个应用、每个版本格式不同，QQ 的 @ 以普通空格结尾，无法从文字可靠识别；拒绝。
- **把 `[文字]` 当表情直接删除**（原私有内联表情笔记的否决项）：不依赖编辑器按键，但会误删用户的普通括号文字；拒绝。
- **横滑和快速删除也改发按键**：一致，但大段删除要发成百上千个按键，慢且无法核实，按压内恢复也无从谈起；保持直接删除并读回核实。
- **在写入处逐个等待确认，而不是按住触摸**：更精确，但写入分散在组字、候选、工具栏、手写等许多路径，而且确认在同一主线程上到达，无法同步等待；按住根容器的触摸是一个汇合点（用户选定）。
- **完全交给编辑器，不留附加符号例外**（fcitx5-android、Trime 的做法）：没有任何字符规则，但分解形式的 é 在系统 `EditText` 里要按两次，倒退 #11444 要求的行为；HeliBoard 同样只对 U+0300–U+035B 按整字删除。保留这一个由 Unicode 定义、不涉及应用格式的例外（用户选定）。

## Consequences

收益：微信、QQ 的表情和 @ 一次删掉（真机 QQ 9.3.85、微信 8.0.80），以后应用换了对象格式也不用跟着改；按键退格后紧接着的输入不再被删掉，迟到的回报也不再取消组字。

代价与边界：

- 每次按键退格后，下一次按键最多晚到编辑器确认为止（QQ 约 20–50 ms，微信 10 ms 以内）；编辑器不回报时（空框、光标在开头）晚 100 ms，按键音和振动随之推迟。真机按住连删的速度与 0.8.3 相当。
- 无障碍点击（TalkBack 双击）直接调用按键，不经触摸分发，按住对它不起作用；实体键盘的退格本来就交给应用。
- 处理按键超过约 0.5 s 才生效的应用会被误判为不处理按键，多删一次；未见这样的应用。
- 微信删掉 @ 后会重启输入会话，按住的连删在那里停止，需要松手再按；跨重启续删留作后续。
- 微信的引用不响应退格（Gboard 同样），只能点 ✕ 移除。
- 每次按键退格确认后多一次光标前文字读取（只在有横滑恢复记录时）。
