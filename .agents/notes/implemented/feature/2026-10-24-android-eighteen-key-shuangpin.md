# Agent Note: Android 18 键双拼

Status: implemented

## Problem

#9124 希望在 Android 上使用更大的双拼按键，正文接受 17 键或 18 键。附件实际包含三排共 18 个字母键：`Q WE RT Y U IO P / A SD FG H JK L / Z XC V BN M`，26 个字母各出现一次。开始处理时 Android 只有 26 键双拼，14 键双拼仍在 #9404 中验收；该依赖已于 2026-10-24 合入。直接扩大 26 键的视觉宽度无法减少一排的按键数量，宿主先猜一个字母又会丢掉同组其他合法读音。

## Decision

横滑精确字母的后续契约见[十八键双拼横滑限定字母](2026-10-24-eighteen-key-exact-swipe.md)；点按布局与默认值沿用本篇。

采用附件的 18 组，作为双拼布局的额外选择；沿用 `touch_shuangpin_layout`，默认继续为 `twenty_six_key`，已有 `fourteen_key` 保留。新值为 `eighteen_key`，由共享 Rust 负责解析、默认值和持久化，Android 负责键面与设置入口。使用当前内置或合法自定义的 26 键双拼方案，微软或自定义表中的分号与 `L` 共键，键面与读屏明确说明分号入口。物理字母仍使用原 26 键双拼，触摸按键使用组码入口；英文、密码、URL、本地模式和数字层往返沿用现有输入边界。

解码在 Engine 中派生两键音节表，复用既有九宫格会话的多义读音、候选、锁定、整句、学习及撤销，不在 Java 复制拼音表。14 键与 18 键共用派生过程，但缓存身份包含布局与原方案，不能让同一方案的两种分组共用一张表。网格快照明确返回 `eighteen_key`，Android 根据实际网格选择键面；其他平台保留该偏好，但本轮不自动打开尚无对应键面的布局。C ABI 的显式网格选择追加编号 `5`；已合入的十八键全拼继续使用 `4`，拒绝不匹配的方案时保留布局、组合与候选代次。两种布局共用字母分组，分号只在双拼派生时映射到 `L`。iOS 继续支持原有 26／14 键双拼，保留十八键偏好而不启用尚无键面的网格。

Android 三排字母键按 7、6、5 排列，第三排两侧保留分词和退格，第二排居中；底行继续使用本产品的符号、数字、空格、中英文和回车操作。按键高度、间距、皮肤、浮动、单手、候选展开与拼音侧栏沿用现有机制，并在窄屏上检查实际触控范围。字母组的长按直接输入与统计标识必须与 26 键和 14 键区分。键面值复用 `FourteenKeyLayout.Key` 的一到二字母表示和可访问标签，18 键独立提供 7＋6＋5 数据和统计前缀，三排绘制复用已有路径；无需再维护一套长按、皮肤与拼音侧栏。各端统计白名单同时追加 18 个 `Eighteen*` 标识，当前没有该布局的宿主也能保留共享统计。

设备验收复用 `FourteenKeyDeviceSmoke -e eighteen_shuangpin true`，全拼保留原有的 `-e eighteen_key true`；不新增清单入口：现有清单已经有 100 个 instrumentation，新增第 101 项会被 Android 35 拒绝安装，Java 编译无法发现这个限制。18 键专项调用共用双拼行为断言，并在专用模拟器里检查窄屏、横屏、浮动和左右单手模式的全部 18 个实际触控范围、等宽、排布、第二排居中及截图；结束后恢复显示配置和本地设置。成功说明也分别标明全拼或双拼，不能用两次相同的全拼结果证明双拼覆盖。

第二行的两侧半键占位保留自己的半个键距外边距；行级半间距会与占位边距重复扣除一个键距，因此几何刷新不再给第二行额外设置水平内边距，三行由相同的七份权重分配宽度。热更新键距时仍通过占位边距同步调整。设备首轮在 API 28 竖屏及 API 35 横屏发现跨行宽度不等，修正重复间距后保留等宽断言，不放宽容差。窄屏截图还发现 `WE`、`XC`、`BN` 折行，18 键标签改用已有的单行自适应字号策略，范围为 12–22 sp。完整冒烟同时发现日语箭头的旧测试定位漏了生产 `iconKey` 统一添加的「按键 」前缀，测试改为匹配实际无障碍描述。

双拼键面可能先于方案配置完成而创建；如果只在创建时判断 `fourteenShuangpin()`，首次渲染会漏掉横滑监听，之后方案变为小鹤也只能点按。十八键的双字母键现在始终绑定监听，触摸时再读取当前方案；全拼仍返回未消费事件以保留普通点按，双拼则按当前字母横滑。

## Alternatives considered

- 自行定义 17 键：能严格对应标题中的键数，且可能进一步增大触控范围。但正文允许 18 键，附件给出了完整的 18 组规格，没有提供 17 键的分组；采用附件可以避免替报告者发明另一张表。
- 只实现小鹤方案：最贴近标题，也能减少首轮测试范围。但分组与双拼声韵母定义独立，现有内置和合法自定义方案都能从同一种字母表派生，因此复用共享派生过程并验证全部方案。
- 在 Android 里将同组字母选成一个确定字母：能保留原单路径双拼的代码，但会丢掉其他合法读音，并把输入算法复制到宿主，因此不采用。
- 从 `develop` 另做一套 18 键多义解码：能避免等待 #9404，但会重复其网格投影、快照与撤销契约；采用依赖 PR 的固定提交，新增内容保持为独立 issue 的差异。

## 回归范围

- 先通过现有 JSON 偏好与 Host API 写出失败回归，证明当前实现不能选择或启用 `eighteen_key`；补齐后验证默认不变、保存回读、换方案和其他平台门控。
- 对每个内置与合法自定义双拼方案，逐一投影可接受的两键编码，核对零声母、分号、别名和两种布局的缓存隔离；覆盖多义拼音锁定、退格、分词、选词后的撤销以及实际正文提交。
- Android 的纯键面回归核对 7＋6＋5 排列、26 字母完整且无重复、分号读屏和每个按键的组码；运行时读取相同的 `eighteen_key` 快照。
- 在 API 28、35 原生产品中通过设置选择 18 键，验证小鹤、微软及自定义表、消歧、实际提交、数字和英文往返、重启、密码及 URL 回落，并检查窄屏、横屏、浮动和单手截图。
- 原有 26 键双拼、14 键全拼／双拼和九键双拼回归继续通过；相关 Rust 测试、Clippy、Android 宿主检查、完整 quick、笔记和差异检查通过后再提交可审查的实现 PR。

## Consequences

- 合入依赖并迁到新 `develop` 后需重新验证组合，迁移前的结果只证明原草稿；不得把 #9404 的既有测试结果记为 18 键通过。
- 更少的字母组仍会产生多义读音，不能承诺合成示例永远位于首选；设备验收必须选择期望读音并核对真实正文。
- 新偏好枚举值不保证旧客户端能够降级读取；缓存身份、网格快照、布局路由和统计键位任一处漏改都会造成跨模块漂移。
- 字母组宽度在窄屏、单手和浮动模式中受到可用宽度限制，需检查真实按键范围，不能仅凭 JVM 的排列断言宣称减少误触。
