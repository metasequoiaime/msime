# Agent Note: 鸿蒙确认键原样上屏编码

Status: implemented

## Problem

鸿蒙触屏键盘的回车键在普通编码组字时按候选数量分派：有候选就选中首行，没有候选才结束组字。这样「确认」键不能像 Android 与 iOS 一样把用户输入的拼音、双拼或五笔编码作为英文原样上屏，直接输入编码的场景会得到第一个候选字。

## Decision

鸿蒙 `ReturnKeyAction` 对普通编码组字统一返回 `COMMIT_RAW`，由 `KeyboardSession.commitRaw()` 发送 `MSIME_COMMIT_RAW`。空格和候选点选继续负责提交高亮候选；上屏后联想仍优先交给编辑器。日文、韩文、越南语、藏文以及打开的韩文候选列表保留各自的提交规则。为避免藏文的书写组字被误当作编码串，回车分派显式接收 `tibetan` 标志，藏文继续只提交藏文、不执行编辑器动作。

## Alternatives considered

- 只把“有候选”的普通中文回车改成 `COMMIT_RAW`：改动较小，但候选为空时仍会走另一条结束路径，无法保证确认键始终上屏用户输入的编码；因此统一普通编码组字的回车语义。
- 让 `KeyboardView` 直接调用 `commitRaw()`，绕过 `ReturnKeyAction`：能够改变触屏路径，但会让回车显示、预测和其他方案的分派规则分散在视图里，硬件与触屏的行为契约也更难测试；因此把规则保留在纯策略类。
- 把所有组字方案都改成 `COMMIT_RAW`：最简单，但会破坏日文、韩文、越南语和藏文已经验证的书写文本与编辑器动作顺序；因此保留显式的方案分支。

## Consequences

确认键在普通中文编码组字中原样上屏编码，候选首选仍由空格、数字或点选提交；普通候选、联想、日文、韩文、越南语和藏文的既有边界继续由策略测试覆盖。`ReturnKeyAction.dispatch` 增加了藏文参数，调用方和联想测试需要同步维护。鸿蒙逻辑测试覆盖了有候选、无候选、预测和藏文回车路径。

验证：`bash platforms/harmony/tests/run.sh`，4737 项键盘逻辑断言及其余鸿蒙策略测试通过；`git diff --check` 通过。HAP 编译和真实鸿蒙设备验收待本机 DevEco 工具链与可接受签名设备具备后执行。
