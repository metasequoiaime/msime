# Agent Note: 鸿蒙确认键原样上屏编码

Status: implemented

## Problem

鸿蒙触屏键盘的回车键在组字时按候选数量分派：有候选就上屏高亮行，没有候选才结束组字。这样「确认」键不能像 Android 与 iOS 一样把用户键入的拼音、双拼或五笔编码作为英文原样上屏，直接输入编码的场景会得到第一个候选字（#11120）。

第一版把 `ReturnKeyAction.dispatch` 的兜底分支整个改成了 `COMMIT_RAW`。真机验收（华为 JUY-AL50，对照 develop 基线包）查出它同时改掉了三处不该动的行为：日语 26 键敲 `nihon` 回车上屏罗马字 `nihon`（基线是 にほん）；全拼 9 键按 64426 回车上屏数字串 `64426`（基线是首选「你好」）；注音候选列表打开时回车把整段转换结果直接上屏并结束组字（基线是选中高亮行、组字保留）。原因是兜底分支接住的不只是「普通中文编码」：视图的 `japanese` 标志只在假名九宫格时为真，日语 26 键、九键、14/18 键、注音、英文和本地工具模式都落在它上面，而引擎对这些组字的原样上屏给出的是罗马字、数字串或整段转换结果。

## Decision

原样上屏只给「编码本身就是用户想写的拉丁字母」的组字：全拼、双拼、五笔、粤拼的 26 键。判断放在纯策略 `ReturnKeyAction.commitsSpelling(rulesScheme, nineKeyFace, letterGridFace)` 里，视图按键盘自己选的方案（`SchemeCompositionPolicy.selectedRulesScheme`，英文和本地工具模式是 -1）、九键网格和 14/18 键网格是否画着来算，结果作为 `spelling` 参数交给 `dispatch`；组字且 `spelling` 为真时返回 `COMMIT_RAW`，由 `KeyboardSession.commitRaw()` 发送 `MSIME_COMMIT_RAW`。笔画仍走自己的分支上屏字母。

其余组字回到改动前的共享规则，与 develop 逐项相同：有候选上屏高亮行（`COMMIT_HIGHLIGHTED`），没有候选结束组字（`FINISH_COMPOSITION`）。范围按 issue 的原话「编码作为英文上屏」划定：

- 九键和九键双拼的原文是按下的数字，不是英文，回车照旧上屏首选。iOS 的 `CompositionBoundaryPolicy` 也把九键排除在原样上屏之外。
- 14 键和 18 键的原文是每组的代表字母，不是用户打的码；引擎自己也把它们的原样上屏改成取首选，这里不依赖那一层，直接走原规则。
- 日语 26 键的罗马字不是用户想写的字，Android、iOS、macOS 的回车都不上屏罗马字。
- 注音的回车仍按候选列表是否打开区分：列表打开（才有候选）时选中高亮行、组字保留，否则上屏转换结果。
- 英文和本地工具模式不归方案的规则管，回车照旧。

空格和候选点选继续负责提交高亮候选；上屏后联想仍优先交给编辑器；日文假名九宫格、韩文、越南语、藏文保留各自的分支。藏文显式的 `tibetan` 分支保留：它原先靠兜底分支得到 `FINISH_COMPOSITION`，现在结果不变，但写明了不随兜底规则变化。

## Alternatives considered

- 兜底分支统一 `COMMIT_RAW`，再逐个排除不该原样上屏的方案（第一版的方向）：每多一种组字就要记得加一条排除，漏掉的后果是把数字串或罗马字写进用户的文字里，真机验收查出的三处正是这样漏的；因此改成只列出该原样上屏的方案，其余保持原规则。
- 日语 26 键回车改成上屏假名读音（`COMMIT_READING`，与 Android、iOS、macOS 一致）：方向是对的，但那是另一处行为改动，鸿蒙的日语 26 键空格也不进入转换状态，要连同空格一起设计；本 PR 只做 #11120，日语保持基线。
- 让 `KeyboardView` 直接调用 `commitRaw()`，绕过 `ReturnKeyAction`：能够改变触屏路径，但会让回车显示、联想和其他方案的分派规则分散在视图里，也没法在 node 下测；因此把规则保留在纯策略类。
- 按引擎回报的方案号（`engineScheme`）而不是键盘自己选的方案判断：引擎回报的方案分不出 26 键和九键、14/18 键，那几种键面由键盘决定；因此和 `strokeFace`、`tibetanFace` 一样读键盘自己的方案和键面。

## Consequences

确认键在全拼、双拼、五笔、粤拼 26 键组字时原样上屏键入的字母，有没有候选都一样；九键、14/18 键、日语、注音、英文和本地工具模式的回车与 develop 相同。`ReturnKeyAction.dispatch` 增加了 `tibetan` 和 `spelling` 两个参数，`spelling` 缺省为假，所以漏传的调用方得到的是改动前的行为而不是原样上屏。以后新增方案默认不原样上屏，要原样上屏须把它加进 `commitsSpelling`。

各端在这几点上仍不一致，本 PR 没有去动：Android 的 `enter()` 对九键也发原样上屏（上屏数字串）；Android、iOS、macOS 的日语回车上屏假名读音，鸿蒙日语 26 键上屏高亮候选；iOS 的注音回车不论列表是否打开都上屏整段转换结果，Android 和鸿蒙在列表打开时选高亮行。

验证：`bash platforms/harmony/tests/run.sh` 通过，新增的「回车只在编码就是用户键入的拉丁字母时原样上屏编码」一组覆盖全拼、双拼、五笔、粤拼 26 键以及日语 26 键、九键、九键双拼、14/18 键、注音、英文和本地模式；这组测试在只加参数、不改行为的桩上运行时失败。`hvigorw assembleHap` 在 Mac Studio 上编译通过（原生库、引擎资源和设置页沿用另一个检出已暂存的产物，只用来确认 ArkTS 能编译）。修复后的真机复验待做。
