# Agent Note: 粤语每键读全部条目，单字按所在的词带出下限

Status: implemented

## Problem

#10448 报告粤语双拼打 `YV`（jyu）出不来「逾」。之前的回复说它大约排在第 200 位，实际上它根本出不来：`dict-v2.0.48` 的 `msime-cantonese.db` 里 `jyu` 有 342 条，「逾」权重 177，排第 204；而 `crates/engine/src/cantonese/scheme.rs` 每个完整音节段只读 `SPAN_LIMIT = 200` 行（`LanguageDictionary::lookup_into` 的 `ORDER BY weight DESC, text ASC LIMIT ?2`），第 200 名以后的条目永远不会成为候选。超过 200 条的键有 10 个（zi 386、ji 361、jyu 342、jyun 282、ci 278、jau 254、wai 254、fu 250、si 218、jin 214），共 839 条打全音节也出不来，其中有寓、御、譽、愚、漁、愉、議、慈这类常用字。构建器从来不检查一个键的条目数会不会超过引擎的上限，[#10420 的香港字形](2026-10-31-cantonese-hong-kong-forms.md)也是撞上同一个上限才发现的。

上限只是让这些字看不到，它们排得低是另一个原因：`crates/dict-builder/src/cantonese.rs` 的 `build` 给单字的权重直接取 essay 的单字分数，而 essay 对多数字只数它单独出现的次数。主要出现在词里的字因此分数很低（逾、寓、御、譽、慈都是 177，愚、漁、愉、議是 88），排在郗（621）、螭（617）、魑（615）这类罕用字后面；「逾期」1196、「逾越」833 这些词的分数完全没有用到。

## Decision

- `SPAN_LIMIT` 从 200 提到 512，覆盖现有最大的键（zi 386）且有余量。完整音节的精确查询、双拼末尾单键的区间查询都用这个常量，两处一起变。
- `cantonese::verify` 增加一道检查：库里条目最多的键超过 `msime_engine::cantonese::scheme::SPAN_LIMIT` 时构建失败，错误写明是哪个键、多少条。以后词库长到超限，会在发布前停下来，由人决定提高上限还是删减条目，而不是再悄悄截掉一段。dict-builder 本来就依赖 msime-engine，直接引用同一个常量，不另写一个数。
- 单字加「词带字」下限（`build` 末尾，所有来源的词都写入之后）：对每个词库里的多字词，若它的字数等于音节数、且 essay 列了它，就把它的 essay 分数按位置记到「这个音节上的这个字」；每个单音节字的下限是这些分数之和 `s` 换算成 `s × C / (s + C)`，`C = WORD_FLOOR_CEILING = 2000`，字的权重取下限与原权重中较大的那个。按位置和读音计，所以「銀行」只抬 hong 的「行」，不抬 haang 的「行」。
- `EXPECTED` 改成三元组（键、字、前几名），加入 (jyu, 逾, 50) 与 (ci, 慈, 30)。没有这个下限时二者分别在第 204、171 位，构建会失败。
- `languages` 的构建摘要写出抬高了多少个单字条目。

## 为什么是饱和换算、为什么是 2000

最先试的是直接取 `max(原权重, 词频之和 × 系数)`。按源数据粗算（脚本没做香港字形替换），系数为 1 时 730 个键里有 213 个换了首选，系数降到 1/8 也还有 74 个，而且换掉的多是粤语里单独常用的字：baa 的「把」让给「爸」，faa 的「花」让给「化」，gaan 的「揀」让给「間」，dung 的「凍」让给「動」。词里出现得多，不代表单打这个音时更想要它，用户要「間」会直接打「時間」。

饱和换算把下限压在 `C` 以下：词频再高也排不过 essay 单独计到 `C` 分及以上的字，各键常用字的相对顺序不变；`C` 以下按 `max(原分, 换算后的词频)` 重排，词频越高越靠前，并且换算单调，不会把一批字压成同一个值后按码位排。essay 所列 20,549 个单字里只有约 1,850 个在 2000 分以上，2000 以下的单字分数大多是零散计数（ci 下「嗤」1156、「茨」1154 排在「持」978 前面，「慈」177 排在「郗」「螭」「魑」后面），用词频重排它们是改善。

用 `dict-v2.0.48` 的源数据（加上「雙拼」一行）构建后对比：703 个单音节键里 37 个换了首选，全是罕用字让位给常用字（畟→測、趿→輯、闃→隙、郝→確、适→括、鞟→擴、埒→劣、颯→圾 等），有争议的是 kyut 的「缺」→「決」、ou 的「澳」→「奧」，两者原分都低于 2000。jyu 下「逾」从第 204 到第 39，寓 38、御 34、譽 21、愚 27、漁 22、愉 33；ci 下「慈」从 171 到 22，「持」从 22 到 15；ji 下「議」从 200 到 26。前三名不变的例子：jyu 仍是 於、魚、瑜，「瑜」不会因为「瑜伽」上升（它本来就是 38264 分），wai 仍是 為、爲 紧挨着。共有 3,033 个单字条目被抬高。

## 延迟

按键延迟用新加的 `crates/engine/examples/cantonese_latency.rs` 在 Mac Studio 上量（`CANTONESE_ROUNDS=100`，同一个新库，只改 `SPAN_LIMIT`，各跑三次）：粤拼入口 p95 200 时 1.30–1.43 ms，512 时 1.28–1.44 ms；双拼入口 p95 200 时 1.56–1.97 ms，512 时 1.94–2.12 ms，p99 2.1–3.8 ms。zi、ji、jyu 每次按键多读一百多行，双拼入口约多 0.4 ms，远低于 p95 ≤ 10 ms。Studio 同时跑着 CI，最大值有十几毫秒的离群点，两种上限下都有。手机上的实际耗时没有量。

## Alternatives considered

- **不改上限，只让构建器把每个键截到 200 条**：查询代价不变。但截掉的就是本来就打不出的那 839 条，问题原样留着，只是从「看不到」变成「库里没有」。
- **上限设成「无限」（不加 LIMIT）**：最简单，也永远不会再截。但一个键的条目数完全由数据决定，以后某次上游更新让一个键涨到上千条时，每次按键的代价会悄悄翻倍；保留常量加构建检查，超限时由人决定。
- **只把精确查询的上限提高，双拼末尾单键的区间查询保留 200**：末尾单键那一路的读行数不变。但那一路的整音节段（如单按 `o` 时的 `m`）同样是精确键，分开两个常量会让同一个键在两条路径上可见的条数不同；实测合用一个常量的延迟可以接受。
- **另建一份人工审校的单字权重表放在 msime-dictionary 的 `custom/`**：可以逐字把关。但要人工排好几百个键、上万个字，工作量和审校门槛都远大于这个规则，而且长尾的问题正是没人看得过来。
- **直接用词频之和，或乘一个固定系数**：见上一节，会大面积换掉常用字的首选。
- **按每个键的第 N 名封顶，保住首页**：封顶处会有大批字同分，只能按码位排，长尾的顺序反而失去信息；同一个字在不同键上的封顶值也不一致。
- **参考普通话拼音或普通话词库的排序**（报告人的建议）：粤语和普通话的用字频率不同，[粤语整词与整句评估](../../proposed/feature/2026-10-30-cantonese-word-sentence-evaluation.md)量过逐字转粤拼有 8.1137% 的词面与明确注音不一致，普通话词频也不能当粤语字频，没有采用。

## Consequences

- 收益：每个键的每个条目都能翻到；主要出现在词里的字排进前几页（逾 39、慈 22、議 26）；以后条目数超限会在构建时失败。
- 代价：整份粤语单字的长尾顺序变了，属于默认排序的变化；部分 2000 分以下的首选会换（37 个键，见上）。zi、ji、jyu 这类键每次按键多读一百多行，桌面实测约多 0.4 ms，手机上没有量。
- 这个改动只在下一次 `dict-v*` 发布（用合入后的 develop 构建器）之后进入词库，应用自带的库还要等 `resources/language-dictionaries.lock.json` 换到那次发布；引擎的上限随下一个客户端版本生效。`tools/cantonese-evaluation/report.json` 的基线是锁文件固定的已发布库，不受构建器改动影响，换锁时再重新评估。
- 验证：`cargo test -p msime-dict-builder`（下限的取值、按位置计、饱和不超过上限、verify 的条目数检查）；`cargo test -p msime-engine --lib cantonese` 的 `every_row_of_a_key_up_to_the_span_limit_is_offered`（粤拼与双拼入口都能翻到上限内的最后一行）；用真实 msime-dictionary checkout 跑 `msime-dict-build languages` 并对比名次与首选变化；上面的延迟测量。没有在模拟器或真机上验收。
