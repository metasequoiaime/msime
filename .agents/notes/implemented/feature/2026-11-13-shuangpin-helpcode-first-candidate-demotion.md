# Agent Note: 辅助码命中时原首选退避

Status: implemented

## Problem

用户已经看到双拼候选的首选后再输入辅助码，通常是在排除这个首选。现有单辅助码重排会把命中行分组，但当原首选也命中辅助码时仍可能留在第一位；双辅助码筛选也只保留命中行而不改变它们的相对首位。用户因此还要按数字键选择真正想要的候选。行为需要同时覆盖双拼的缓存生成路径和模糊候选路径，并保持未命中行的稳定顺序。

## Decision

单辅助码先按现有的首码、末码优先级稳定重排；如果输入前的第一个候选命中辅助码且还有其他命中候选，就把它放到命中组的末尾，未命中候选仍排在命中组之后。只有一个命中候选时保留原位置。

双辅助码继续只保留完整命中的候选；如果输入前的第一个候选命中且筛选后还有其他命中候选，就把它旋转到筛选结果末尾。单、双辅助码都在共享 Engine 层执行，双拼词典缓存生成复用共享双码筛选函数，避免不同查询入口产生不同顺序。

实现使用现有候选缓冲和排列索引：短单辅助码路径仍使用栈上索引，通用单辅助码路径通过移出并插回首项完成退避，不复制候选文本；双辅助码在原缓冲上 `retain` 和旋转。

句中间接辅助码也遵守这一规则。它先解析成 `syllable_helpcodes`，不经过上述末尾筛选；`dictionary/syllable_helpcode_order.rs` 因此在逐音节约束筛选时，保留原首选是否命中的事实，再把仍命中的原首选移到最后一条受约束的命中行之后。只有一个命中行、首选被筛除、首选是非拼音行或约束落在短前缀之外时不退避；未被约束的短前缀不算其他命中行。筛选与移动都在原缓冲上执行，不复制词面。

这覆盖 #11573 的句中大写入口：小鹤码表下 `heR`、`heRK` 让“何”排在“合”之前，`uiO` 让“时”排在“是”之前。末尾直接模式继续把 `rK` 读为顺序双码、首码大写读为倒序；句中大写段的 `RK` 按键入顺序匹配。修复不改变这两套既有输入协议或任何默认值。句中段与缓存签名的归属仍见[三组辅助码触发方式](2026-10-22-shuangpin-helpcode-trigger-modes.md)。

## Alternatives considered

- **只调整单辅助码的首码、末码优先级**：改动最小，但无法表达“用户已经排除原首选”的意图；当原首选属于最高优先级匹配组时仍会留在第一位，因此不采用。
- **只在宿主或候选栏层面交换显示顺序**：可以绕开 Engine，但缓存、模糊音、双拼和全拼入口会各自出现不同规则，宿主也无法可靠判断哪些行属于同一组命中，因此不采用。
- **把原首选从候选中删除**：能避免误上屏，但用户仍可能需要它，且会破坏现有辅助码候选的完整性；本次只移动到命中组末尾。

## Consequences

辅助码输入后的第一候选更符合“排除当前首选”的用户意图，单辅助码、双辅助码、缓存命中和模糊候选的顺序规则一致。未命中辅助码的行、唯一命中行及没有辅助码的普通查询保持原有顺序。新增的回归测试固定了单码和双码的原首选退避，以及短批次单码重排仍不申请排列索引堆内存。

原修复仅覆盖底层末尾排序，不能证明句中入口生效。#11573 的完整会话回归在修复前复现 `heR` 首选仍为“合”，默认末尾直接入口则通过；回归还检查双码、删除辅助码后恢复原首选、缓存重查以及实际选词上屏。独立约束筛选测试覆盖唯一命中、原首选未命中和不受约束的短前缀。构建和测试通过远端构建机运行，不依赖设备安装或真实编辑器验收。

2026-11-18 验证：辅助码专项 124 项通过；`ulimit -n 4096` 后完整 `cargo test --locked -p msime-engine` 的单测为 3192 通过、59 忽略，另外 37 项集成测试全部通过；`cargo clippy --locked -p msime-engine --all-targets -- -D warnings` 通过。直接在 SSH 默认的 256 文件句柄限制下跑全套会导致夹具打不开 SQLite 文件；采用仓库 `verify-local.sh` 已有的 4096 上限，不修改测试输入或测试开关。
