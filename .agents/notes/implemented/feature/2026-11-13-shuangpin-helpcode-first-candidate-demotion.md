# Agent Note: 辅助码命中时原首选退避

Status: implemented

## Problem

用户已经看到双拼候选的首选后再输入辅助码，通常是在排除这个首选。现有单辅助码重排会把命中行分组，但当原首选也命中辅助码时仍可能留在第一位；双辅助码筛选也只保留命中行而不改变它们的相对首位。用户因此还要按数字键选择真正想要的候选。行为需要同时覆盖双拼的缓存生成路径和模糊候选路径，并保持未命中行的稳定顺序。

## Decision

单辅助码先按现有的首码、末码优先级稳定重排；如果输入前的第一个候选命中辅助码且还有其他命中候选，就把它放到命中组的末尾，未命中候选仍排在命中组之后。只有一个命中候选时保留原位置。

双辅助码继续只保留完整命中的候选；如果输入前的第一个候选命中且筛选后还有其他命中候选，就把它旋转到筛选结果末尾。单、双辅助码都在共享 Engine 层执行，双拼词典缓存生成复用共享双码筛选函数，避免不同查询入口产生不同顺序。

实现使用现有候选缓冲和排列索引：短单辅助码路径仍使用栈上索引，通用单辅助码路径通过移出并插回首项完成退避，不复制候选文本；双辅助码在原缓冲上 `retain` 和旋转。

## Alternatives considered

- **只调整单辅助码的首码、末码优先级**：改动最小，但无法表达“用户已经排除原首选”的意图；当原首选属于最高优先级匹配组时仍会留在第一位，因此不采用。
- **只在宿主或候选栏层面交换显示顺序**：可以绕开 Engine，但缓存、模糊音、双拼和全拼入口会各自出现不同规则，宿主也无法可靠判断哪些行属于同一组命中，因此不采用。
- **把原首选从候选中删除**：能避免误上屏，但用户仍可能需要它，且会破坏现有辅助码候选的完整性；本次只移动到命中组末尾。

## Consequences

辅助码输入后的第一候选更符合“排除当前首选”的用户意图，单辅助码、双辅助码、缓存命中和模糊候选的顺序规则一致。未命中辅助码的行、唯一命中行及没有辅助码的普通查询保持原有顺序。新增的回归测试固定了单码和双码的原首选退避，以及短批次单码重排仍不申请排列索引堆内存。

验证受本机磁盘剩余空间约 13 GiB 限制，未启动新的完整 Rust 构建或测试；已运行 `cargo fmt --all -- --check` 和 `git diff --check`，完整 Engine 测试交由 PR CI 执行。
