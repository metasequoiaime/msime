# Agent Note: Android 14 键双拼

Status: implemented

## Problem

#8770 要在 Android 的 14 键键面使用双拼。目前 `KeyGrid::FourteenKey` 把全拼字母归到相邻两字母的组，`Session::grid_key` 和宿主布局网格只允许全拼；直接打开双拼的 14 键外观会把两键音节按全拼解释。26 键双拼每个编码只有一种读法，合并按键以后则可能对应多个音节，不能直接沿用单路径的双拼切分。

## Decision

沿用现有 `QW ER TY UI OP / AS DF GH JK L / ZX CV BN M` 键面，把当前双拼方案每个声母键、韵母键和零声母两键编码映射到这 14 组；音节仍占两键，多种读法交给现有九宫格会话的路径、锁定、候选、整句和学习处理。复用九键双拼的两键编码表及拼写表构造，不在 Android 再保存一份音节表。原来的九键用户表继续只允许数字，14 键的表只从已经解析的 26 键双拼方案派生，不增加第二种用户码表格式。微软或自定义方案使用的分号归到 L 键，使用时键面与读屏明确显示该入口。

双拼布局作为共享 Rust 偏好 `touch_shuangpin_layout` 的独立选择（`twenty_six_key` / `fourteen_key`），默认 26 键且默认值不写进配置文档；Android 在双拼设置中选择 26 键或 14 键，沿用当前内置或自定义双拼方案。切换方案、英文、符号页、输入框及重启时保留该选择。输入算法仍在 Engine，偏好校验和默认值仍在 client-core，Android 只负责键面、设置和输入来源。物理字母继续走原来的 26 键双拼路径，14 键触摸输入走 `grid_key`。`View.key_grid` 沿用 `fourteen_key` 表示外形，但组字快照必须报告双拼方案；不沿用九键原来的固定全拼快照，否则 Android 会在组字中丢掉双拼身份。退格恢复选词时也要按原网格重放组码。只有编译到 Android 的宿主自动读取该字段，其他平台保留但忽略，避免偏好同步后改变尚未支持该布局的宿主。其他平台本轮不增加该布局的设置入口；iOS 的 #9190 单独处理。

## Alternatives considered

- 让 Android 先猜每组中的一个字母，再交给 26 键双拼：可以少改引擎并沿用当前双拼词典查询。但相同按键组可能对应多个合法音节，先猜会永久丢掉其他读法，还把输入规则复制到宿主，因此不采用。
- 为 14 键单独扩展 26 键双拼的多路径切分：双拼辅助码和原有切分都在那里，表面上更接近原方案。但九宫格已经处理同一类两键多义编码、锁定与整句，重复实现会产生两份算法，因此复用已有网格解码。
- 只提供小鹤 14 键：能缩小首轮验证范围。但需求是已有 14 键支持双拼，现有内置和自定义方案都能从同一种字母表派生，不以方便测试为由限制为一个方案。

## Consequences

- 现有内置方案和合法自定义方案都能派生 14 键，不新增用户码表格式；微软的分号入口有键面和读屏标记，别名编码继续有效。
- 双拼组码沿用九键双拼的音节规则，不按全拼 14 键的字母归组规则混入英文；英文模式仍使用 26 键。
- 14 组会压缩双拼的信息量，同一组码可能对应多个读法；沿用拼音侧栏锁定与候选选择，不承诺某个示例永远首选。
- 独立偏好默认不序列化，已有 26 键配置保持原义。开启 14 键后，旧版客户端不认识新增偏好字段，不能保证降级读取；其他当前宿主只保留该字段，不自动启用网格。
- 验证达到 Android API 28、35 模拟器运行层，未做 Android 真机验收；iOS 的 #9190 保持独立。
