# Agent Note: 鸿蒙 26 键竖向滑动输入辅助码

Status: implemented

## Problem

鸿蒙手机的 26 键全拼和双拼在已有组字时，辅助码大写只能先点左下角 `Shift` 再点字母。触屏键盘的按键空间有限，这条路径需要额外一次点按；现有字母键竖向滑动只用于角标符号，不能直接表达辅助码。

## Decision

鸿蒙手机 26 键字母层在全拼或双拼已经有组字、且没有英文或本地模式接管时，按下字母后上滑或下滑超过 14vp，并且竖直位移大于横向位移，就把这次触摸作为辅助码大写。字符沿 `tapLetter` 已有的 `ChineseHelpcodePolicy.letterInput` 与 `KeyboardSession.press(..., true)` 路径送入引擎，因此引擎看到的契约与 `Shift+字母` 完全相同。

手势在按下时锁定是否可用，避免组字状态变化改写一根已经按下的手指。触发后吞掉 ArkUI 可能随后到达的点击；没有越过门槛时照常点按。长按计时先成立时保留原来的角标提示，横向位移占优时让位给现有滑行输入。角标提示的方向设置只影响非辅助码场景；组字中的这两种竖向滑动都代表辅助码，不新增设置项或落盘字段。

本次只改鸿蒙宿主。Android 与 iOS 已有各自的触屏手势和设置契约，用户请求的目标平台是鸿蒙，不把三个宿主强行改成不同的共享偏好。

## Alternatives considered

- **继续要求先按 `Shift`**：实现成本最低，但保留了用户希望减少的一次点按，不能解决手机上输入辅助码的主要痛点。
- **复用角标滑动的单一方向**：可以少写一个手势判定，但会让上滑或下滑取决于「滑动输入符号」设置，用户难以记忆；组字中的两种方向都可用更符合“滑一下就是辅助码”的目标。
- **增加一个专门的辅助码开关或键位**：能让行为显式可配置，但会增加设置和按键负担；该手势只在辅助码有意义的组字上下文中生效，不需要新的持久化状态。

## Consequences

用户在鸿蒙手机 26 键组字时可直接竖向滑动输入大写辅助码，点按、长按角标、九键、14/18 键和滑行输入保持原行为。代价是组字中的字母竖向滑动不再按角标符号上屏；角标仍可长按取得，非组字场景的角标滑动方向和设置不变。该手势没有可见的独立键面标识，触发时复用按键预览显示大写字母。
