# Agent Note: 九宫格把最近选择、拼满读法的前两名这类窄决策点交给「增强」的键盘模型裁决

Status: implemented

## Problem

runtime 的逐键重排器（「增强」，#10197 之后只挂这一层）只在首行不是可信词典命中、并且至少两条候选回答整个按键时才改首选（`ordering::rerank_needs_model` 里的 `trusted_leader`，chinese-ime-lm 的 `best_where` 同一条规则）。九键一词一块打字时首行几乎总是词典行，所以模型在这种打法下一个字也改不了：`typing_sim` 一词一块不简拼，只开 runtime 层和不挂模型的 test 严口径首选率逐字相同（Tatoeba 0.7873 / 聊天 0.8237）。缺口分析里这种打法下最大的一类是「最近选择来回翻转」（G：固定在第 1 位的最近选择在 他/她、那/哪、的/得 之间跟着上一次选择翻），其次是同一串数字的另一个词（B、B′），都在这道门外面。

拆掉 `trusted_leader` 的宽版本已经否决过：让模型越过词典首选，在没有上文的 2052 例词级集上任何 margin 都掉分（0.719 对最好 0.690，见 chinese-ime-lm `CandidateFacts::trusted_dictionary_hit` 的说明）。

## Decision

- **引擎只在几种窄决策点上标记候选行，runtime 只在标记过的行之间让模型挑。** 九宫格会话（`NineKeySession::refresh` 末尾的 `mark_contests`）给候选行标裁决种类（`ordering::CONTEST_*`），经 `SessionSnapshot::candidate_contest`、`EngineSnapshot::candidate_contest` 交给 runtime；一行都没标时向量为空。runtime 的所有排列（`promote_row`、`apply_candidate_order`、插件插入和撤下）同步搬动它，逐键重排（`Runtime::rerank(true)`）经 `ParallelOrderRows::with_contests` 把它交给排序决策；长度不对时当作没有标记。
- **`rerank_pick` 的裁决路径**：首行带标记、这种裁决点有 margin、同种标记并且回答按键的行至少两条（最多 9 条）时，只把这几行交给 `Reranker::log_probabilities`，挑战者的逐字平均自然对数概率比首行高出 margin 才提到首位，否则不动。首行是可信词典命中也一样。没有标记时 `trusted_leader` 和原来的比较集合原样不变。
- **只交给逐键模型，停顿重排不裁决。** 落定模型（桌面 `neural_desktop` 打开时停顿后跑的那一层，`rerank_settled`、`begin_settled_rerank` / `score_settled_rerank`）读的候选行不带标记，`rerank_needs_model` 照旧按 `trusted_leader` 判断，可信的词典首选不会因为标记在停顿后被换掉。margin 是在随包的键盘模型上调出来的，落定模型没有量过；Linux fcitx5 和 Windows win7 面板的九键模式再加上用户打开 `neural_desktop` 才走得到那里。评审时发现第一版两条停顿路径都会读标记，已改；`tests/model_contests.rs` 的 `only_the_keystroke_model_settles_a_contest` 覆盖。
- **只有挂了 runtime 重排器才起作用。** 标记本身不改任何顺序；「增强」关着（移动端缺省）时没有模型，行为逐字节不变（`typing_sim --model off` 四个变体都与基线的报告和 dump 相同）。全键盘不走 `NineKeySession`，四格逐字节不变。
- **最近选择（`CONTEST_RECENCY`）**：首行是固定在第 1 位（不是手动置顶，见下）、覆盖全部数字、不是简拼行、拼满读法（规范读音的组码不比数字长）的词典行，对手是首页里其后第一条没有固定、同样条件、文字不同的词典行，也就是没有置顶时会领先的那一行；那一行是补全或字数和首行不同时不裁决。只比这两行。margin `RECENCY_MARGIN` = 1.0 nat/字。置顶记录的写入（#8492、#9066）一点不改：模型只决定这一次谁坐首位；用户点了被提上来的那一行，`NineKeySession::select` 照旧把它当作非首位的选择记成新的最近选择。
- **拼满读法的前两名（`CONTEST_RUNNER_UP`）**：首行是没有固定、拼满读法（规范读音的组码不比数字长，不是补全）、覆盖全部数字、不是简拼行、权重为正的词典行；对手是首页里其后第一条同样条件、字数相同的词典行，读音可以不同（监狱/教育、乘客/成了）也可以相同（他/她、件/间），权重不低于首行的 `RUNNER_UP_WEIGHT_RATIO` = 0.1。只比这两行，margin `RUNNER_UP_MARGIN` = 1.0 nat/字。首行固定在第 1 位时走上面的最近选择，不走这一条。
- **用户手动置顶的词不裁决。** 首行是用户在这个上下文里手动置顶的词时两种都不标（`mark_contests` 的 `manually_pinned`）：手动置顶是用户明说的首选，模型只裁决自动记下的最近选择和词频排出来的首选。固定位置表分不清手动和自动写进第 1 槽的行，所以九键的 `pin` 和固定到第 1 位（`set_position(…, 1)`）另外往 `pinned_candidates` 记一条 `(nine-key:<digits>:<locked>, 词)`，和 26 键置顶记的是同一张表、同一个「每个上下文一条，后一次手动置顶替换它」的规则（26 键用它不让个人上下文重排挪走置顶的词），上下文前缀 `nine-key:` 不会和 26 键的拼音上下文撞。自动记下的最近选择既不写也不清这一条：用户置顶过的词以后被别的选择挤下第 1 槽、又因为再选它回到第 1 位时，仍按手动置顶对待；挤上来的别的词照旧裁决。用户显式取消固定（`set_position(…, 0)`）或把它挪到第 2–5 位时，这个上下文里这个词的记录随之删掉（`positions::clear_pinned_candidate`），以后它再被自动记成最近选择时照旧裁决。两种裁决查的范围不同（`manually_pinned`）：最近选择的首行坐的是这个上下文的固定第 1 槽，只认同一个上下文的记录；前两名的首行没有固定，是靠置顶写进的全局权重领先的，而权重不分锁定读法，所以同一串数字下任何锁定读法（`nine-key:<digits>:` 开头）里置顶过它都算，不锁定时置顶、锁定读法后再看（或者反过来）仍然不裁决。置顶已经坐在第 1 槽的行（多半是自动记下的最近选择）时，先放开这一槽、同别的置顶一样把权重抬到最高，再固定回第 1 位并记这一条：原来这一步会因为它是固定行而调频失败、报 `NINE_KEY_FREQUENCY_NOT_PERSISTED`；只记不调频的话，它以后被别的选择挤下第 1 槽时会掉回词典原位，而别的置顶路径抬过权重、排在第 2，同一个「置顶」按钮结果不一样。查这一条只在真要标的时候做，没有裁决点的按键不碰日志。

### 最近选择

第一版（A2）的对手只要求覆盖全部数字的词典行，补全行和字数不同的词也拿来和置顶行比逐字平均分。逐字平均分天然偏向第二个字好猜的多字补全，dev 上 A2 的输块里这一类占 Tatoeba 一词一块 20/38、聊天一词一块 6/19（您 → 你们、让 → 然后、买 → 那个、只 → 一个、下 → 一般），这是计划里写的「补全不能和完整读法混着比」那个陷阱。评审后补了两臂，都要求置顶行和对手拼满读法、字数相同，margin 不重调：A4 只比没有置顶时会领先的那一行（它不合格就不裁决），A5 往后找第一条合格的行。

### 手动置顶不裁决

这一条在评审之后加，不改任何数字：`typing_sim` 和 `convert_eval` 都不手动置顶，`pinned_candidates` 里没有九键上下文的行，`manually_pinned` 永远是假。实测核对过：c570588eee 和加上这一条的二进制，九键、14 键各 4 格（`--model keyboard`，学习开）的报告和 dump 逐字节相同，报告也与上面最终状态的 test 数字逐字节相同（九键 Tatoeba 主配置 0.524、一词一块 0.834，聊天 0.531 / 0.861）；`convert_eval` 的 nine-key、nine-key-prefix、nine-key-sentences 报告逐字节相同，nine-key 的 dump 只差行内日期时间行的秒数（`convert_eval` 用真实时钟），把时刻抹掉后也相同。按键路径上多出的只有要标裁决时的一次 `pinned_candidates` 查询，没有另测延迟。报告和 dump 的哈希在 `/Users/e-hu/worktrees/_scratch/nine-key-manual-pin/`。

评审第二轮的三处修正（取消固定清记录、前两名按同一串数字的前缀查、置顶第 1 槽的最近选择也抬权重）同样碰不到评测：两个工具里没有任何置顶、固定或取消固定的调用，`pinned_candidates` 里始终没有九键上下文的行，前缀查询和精确查询一样是假，所以没有重跑。

### 延迟

M4 Pro 本机，`typing_sim --latency`，最终状态的二进制对 A0，按「A0、终态、终态、A0」交替，本机负载 3.5–6.8：

| 打法 | 按键 p95（两轮中位数） | p50 | 超 16 ms 的按键 |
|---|---|---|---|
| 九键聊天主配置 | 9.78 对 9.76 ms | 2.1 对 1.8 ms | 0.65% 对 0.20% |
| 九键聊天一词一块（裁决最常触发） | 4.63 对 3.98 ms | 1.74 对 1.50 ms | 0% 对 0% |

p95 增量 +0.02 ms 和 +0.65 ms，在 2.5 ms 的代理门槛之内。事先写下的「超 16 ms 的按键 ≤ 0.5%」这一条原文没过（0.65%）：两轮里 0.40% 和 0.90%，后一轮的峰值 212 ms、本机负载在这一轮里升到 6.8；再跑一轮时前半（负载 3.6）终态 0.30% 对 A0 0.20%，后半本机负载升到 33、两边都到 3% 以上而作废。第一版量过的另一组里 A0 自己是 0.60–0.75%，所以这条在本机上分不清是改动还是噪声，按补记以 p95 增量判定。每个被裁决的按键多一次两行的模型评分，按 p50 推算本机约 +0.2–0.3 ms；Pixel 3 XL 这类慢机上会大几倍，没有复测。相对不挂模型的「标准」，九键 p95 仍是 runtime 层原有的约 +4.5 ms（见 [「增强」只挂 runtime](2026-10-29-enhanced-runtime-reranker-only.md)），真机上「增强」能不能默认打开仍取决于那一层。

## 和已有决定的关系

- [最近选中的候选优先](2026-10-17-nine-key-recent-candidate-priority.md)、[锁定读法后的最近选择](../bug-fix/2026-10-21-nine-key-locked-selection-recent.md)：部分重叠。最近选择的存储、写入、清除和手动槽位的规则都不变；九键的手动置顶和固定到第 1 位另外在 `pinned_candidates` 里记一条，只给裁决用。「增强」打开时，自动记下的最近选择在上文明显指向没有它时的首选时让出这一次的首位，手动置顶的不让。单字和多字词一样适用。两篇加了互链。
- [最近选择只给多字词](../../rejected/feature/2026-10-29-nine-key-recent-pin-words-only.md)：同一类错误（G）的另一种修法，它收回单字契约而这里不收；那篇的「不要让一部分选择写、另一部分不写」这里遵守，写入规则没有任何分支。
- [补全行在打字流里进一步往后排](../../rejected/bug-fix/2026-10-29-nine-key-completion-order-in-typing-flow.md) 结尾提到的「停在声母上时按上下文挑补全」这次也试了，没过门，见 [停在声母上的补全裁决](../../rejected/feature/2026-10-29-nine-key-completion-contest.md)。
- [独立句子排序保留静态证据](../bug-fix/2026-10-14-rerank-static-evidence.md)：不重叠。裁决路径只比被标出的词典行，它们没有静态证据，不和词网格分混合。
- [「增强」只挂 runtime 逐键重排器](2026-10-29-enhanced-runtime-reranker-only.md)：本篇只改那一层能碰到哪些决定，不改挂载和缺省值。

## Alternatives considered

- **拆掉 `trusted_leader`，让模型在所有回答按键的行之间比**：最简单，也能碰到 G 和 B。但这正是历史上量过、任何 margin 都掉分的宽版本，这次不跑。
- **前两名只裁决读音不同的（b）**：B′（他/她、件/间）是键盘无关的错误，原以为放进来会多输；dev 上同音也裁决的一臂反而多 0.11pp，按事先写下的规则取它。
- **前两名不设权重门，或门设到 0.3**：0.3 的两臂在 dev 上少 0.05–0.11pp；不设门没有跑，历史上没有门的宽版本已经否决。
- **margin 取 0 或 2**：dev 上 m=0 在聊天一词一块上输得多（−2.44pp），m=2 收益少（合并 +1.47pp）；按事先写下的规则取 m=1。
- **模型分数和词频（或置顶本身）加权混合**：置顶行没有和模型同单位的分；给最近选择一个可调的先验，等价于 margin，只多一个参数。
- **手动置顶也交给模型裁决**：第一版这样做，理由是固定位置表分不清手动和自动（[只给多字词](../../rejected/feature/2026-10-29-nine-key-recent-pin-words-only.md) 里也提到）。用户明说要某个词坐首位，「增强」却按上文把它换下去，这是在替用户改他刚做的决定；评审时定为手动置顶不裁决。
- **给 `fixed_candidate_positions` 加一列标手动 / 自动**：最直接，但要改落盘格式、迁移，同步设计（`docs/learning-sync.md` 的 `position` 记录）和备份恢复也得跟着带这一列。`pinned_candidates` 已经是「这个上下文用户手动置顶了哪个词」，本地备份（输入习惯）、下载云端快照时的保留、删词和重置都已经带着它，输入习惯同步协议也已经规定了它的 `pin` 记录，复用它不改任何格式。
- **自动记下最近选择时清掉这个上下文的手动置顶记录**：能让「手动」只跟着当前第 1 槽的主人走，被挤下去又回来的词改按自动对待。但用户没有做任何解除置顶的操作，自动的选择不该替他撤销；用户置顶过的词又回到首位时继续保护它，本身也说得通。
- **显式取消固定时也不清记录**：第一版这样做。结果是用户固定到第 1 位又取消之后，这个词以后自动回到首位时仍被当成手动置顶；单字删不掉（九键的 `remove` 对单字不处理），只剩重置学习一条路。评审后改成取消固定和挪到别的槽位时删掉这个词在这个上下文里的记录。代价是 `pin` 多了一条删除路径，而 `docs/learning-sync.md` 的 `pin` 规则原先写的是取消置顶只发生在删词时：已在那里补上，九键取消固定删 `pin` 和取消固定删 `position` 一样只删本机、不留删除记录，远端副本以后仍可能把它带回来。那份协议还没实现，现在没有远端副本。
- **前两名也只按置顶时的上下文查**：第一版这样做。不锁定时置顶的词靠调高的全局权重领先，锁定读法后上下文变成 `nine-key:<digits>:<locked>`，查不到记录，前两名照样拿它去比，模型可能把它换下去。26 键的同类保护另外用 `has_matching_user_weight` 兜底，九键没有；改成按同一串数字的前缀查。也考虑过置顶时把不锁定的上下文再记一条，但锁定读法时置顶、不锁定再看仍然查不到。
- **把裁决放进引擎（引擎内键盘模型那一层）**：引擎层 #10197 之后固定关，开它要多一份模型和约 40 MB 内存、九键 p95 多 6–7 ms；runtime 已经挂着同一个模型，标记交过去就够了。

## Consequences

- 收益：「增强」第一次在一词一块打字里起作用，两条一起九键 test 合并 +2.72pp（Tatoeba 一词一块 0.787 → 0.834、聊天 0.824 → 0.861），14 键同向；主配置也涨。「标准」不受影响，桌面的停顿重排也不受影响。
- 代价：每次首行是固定在第 1 位的词典行、或者前两名权重相近时多一次两行的模型评分（要标的时候还多一次 `pinned_candidates` 查询），本机按键 p50 约多 0.2–0.3 ms，一词一块 p95 多 0.65 ms。冷启动的 `nine-key` 词级集 top1 −0.25pp。
- 没量的：标记由 `NineKeySession` 的所有网格共用，十八键、九键双拼、14 键双拼、十八键双拼都会标，`typing_sim` 只量了九键和 14 键；`convert_eval` 学习关，量不到最近选择；Android README 原先写的「下次直接输入同一数字串也会优先显示这次选择」在「增强」打开时不再无条件成立，已在那段补上例外；真机（Pixel 3 XL）没有复测，桌面 25M 模型的上限臂没有跑（资源里没有那份模型）。
- 手动置顶：九键里置顶、固定到第 1 位的词不再被「增强」换下去；`pinned_candidates` 从此也有九键上下文的行，本地备份和下载云端快照时保留，删词和重置时清掉，输入习惯同步实现后按 `pin` 记录走（云同步上传时 `include_learning` 为假，云端快照里本来就没有它）。一个上下文里手动置顶的那个词一直受保护，直到用户在这个上下文里手动置顶别的词、取消它的固定或把它挪到别的槽位、删掉它，或者重置学习；它被自动记下的最近选择挤下去时，挤上来的词照旧裁决。靠调频置顶、没有固定的单字只能靠前两种或重置解除（九键删不掉单字），这和它被抬高的权重一样一直留着。置顶已经坐在第 1 槽的自动最近选择不再报调频失败，而且和别的置顶一样抬了权重。
- 升级前留下的手动第 1 槽：旧版本里 `set_position(…, 1)` 或置顶接管最近选择写下的第 1 槽没有对应的 `pinned_candidates` 行，分不出是手动的，仍当成自动的最近选择去裁决，直到用户再置顶或固定一次。「增强」默认关，这套裁决还没发布，没有做语义迁移。
- 重访信号：真机上「增强」默认打开时，再看裁决点的 margin 和对手规则。
