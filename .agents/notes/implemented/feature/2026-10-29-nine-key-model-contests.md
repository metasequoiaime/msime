# Agent Note: 九宫格把最近选择、拼满读法的前两名这类窄决策点交给「增强」的键盘模型裁决

Status: implemented

## Problem

runtime 的逐键重排器（「增强」，#10197 之后只挂这一层）只在首行不是可信词典命中、并且至少两条候选回答整个按键时才改首选（`ordering::rerank_needs_model` 里的 `trusted_leader`，chinese-ime-lm 的 `best_where` 同一条规则）。九键一词一块打字时首行几乎总是词典行，所以模型在这种打法下一个字也改不了：`typing_sim` 一词一块不简拼，只开 runtime 层和不挂模型的 test 严口径首选率逐字相同（Tatoeba 0.7873 / 聊天 0.8237）。缺口分析里这种打法下最大的一类是「最近选择来回翻转」（G：固定在第 1 位的最近选择在 他/她、那/哪、的/得 之间跟着上一次选择翻），其次是同一串数字的另一个词（B、B′），都在这道门外面。

拆掉 `trusted_leader` 的宽版本已经否决过：让模型越过词典首选，在没有上文的 2052 例词级集上任何 margin 都掉分（0.719 对最好 0.690，见 chinese-ime-lm `CandidateFacts::trusted_dictionary_hit` 的说明）。

## Decision

- **引擎只在几种窄决策点上标记候选行，runtime 只在标记过的行之间让模型挑。** 九宫格会话（`NineKeySession::refresh` 末尾的 `mark_contests`）给候选行标裁决种类（`ordering::CONTEST_*`），经 `SessionSnapshot::candidate_contest`、`EngineSnapshot::candidate_contest` 交给 runtime；一行都没标时向量为空。runtime 的所有排列（`promote_row`、`apply_candidate_order`、插件插入和撤下、停顿重排的副本）同步搬动它，`ParallelOrderRows::with_contests` 把它交给排序决策；长度不对时当作没有标记。
- **`rerank_pick` 的裁决路径**：首行带标记、这种裁决点有 margin、同种标记并且回答按键的行至少两条（最多 9 条）时，只把这几行交给 `Reranker::log_probabilities`，挑战者的逐字平均自然对数概率比首行高出 margin 才提到首位，否则不动。首行是可信词典命中也一样。没有标记时 `trusted_leader` 和原来的比较集合原样不变；`rerank_needs_model` 对带标记的首行返回真，停顿重排沿用同一判断。
- **只有挂了 runtime 重排器才起作用。** 标记本身不改任何顺序；「增强」关着（移动端缺省）时没有模型，行为逐字节不变（`typing_sim --model off` 四个变体都与基线的报告和 dump 相同）。全键盘不走 `NineKeySession`，四格逐字节不变。
- **最近选择（`CONTEST_RECENCY`）**：首行是固定在第 1 位、覆盖全部数字、不是简拼行的词典行，对手是首页里其后第一条没有固定、同样条件、文字不同的词典行，也就是没有置顶时会领先的那一行。只比这两行，字数可以不同。margin `RECENCY_MARGIN` = 1.0 nat/字。置顶记录的写入（#8492、#9066）一点不改：模型只决定这一次谁坐首位；用户点了被提上来的那一行，`NineKeySession::select` 照旧把它当作非首位的选择记成新的最近选择。
- **拼满读法的前两名（`CONTEST_RUNNER_UP`）**：首行是没有固定、拼满读法（规范读音的组码不比数字长，不是补全）、覆盖全部数字、不是简拼行、权重为正的词典行；对手是首页里其后第一条同样条件、字数相同的词典行，读音可以不同（监狱/教育、乘客/成了）也可以相同（他/她、件/间），权重不低于首行的 `RUNNER_UP_WEIGHT_RATIO` = 0.1。只比这两行，margin `RUNNER_UP_MARGIN` = 1.0 nat/字。首行固定在第 1 位时走上面的最近选择，不走这一条。

## Alternatives considered

- **拆掉 `trusted_leader`，让模型在所有回答按键的行之间比**：最简单，也能碰到 G 和 B。但这正是历史上量过、任何 margin 都掉分的宽版本，这次不跑。
- **前两名只裁决读音不同的（b）**：B′（他/她、件/间）是键盘无关的错误，原以为放进来会多输；dev 上同音也裁决的一臂反而多 0.11pp，按事先写下的规则取它。
- **前两名不设权重门，或门设到 0.3**：0.3 的两臂在 dev 上少 0.05–0.11pp；不设门没有跑，历史上没有门的宽版本已经否决。
- **margin 取 0 或 2**：dev 上 m=0 在聊天一词一块上输得多（−2.44pp），m=2 收益少（合并 +1.47pp）；按事先写下的规则取 m=1。
- **模型分数和词频（或置顶本身）加权混合**：置顶行没有和模型同单位的分；给最近选择一个可调的先验，等价于 margin，只多一个参数。
- **用存储区分手动置顶和自动记下的最近选择，只裁决后者**：固定位置表分不清两者（[只给多字词](../../rejected/feature/2026-10-29-nine-key-recent-pin-words-only.md) 里也提到），要改落盘格式、同步和清除路径；这次不改存储，手动固定在第 1 位的行同样参与裁决，代价见下。
- **把裁决放进引擎（引擎内键盘模型那一层）**：引擎层 #10197 之后固定关，开它要多一份模型和约 40 MB 内存、九键 p95 多 6–7 ms；runtime 已经挂着同一个模型，标记交过去就够了。

## Consequences

- 收益：「增强」第一次在一词一块打字里起作用，两条一起九键 test 合并 +2.56pp（Tatoeba 一词一块 0.787 → 0.829、聊天 0.824 → 0.853），14 键同向；主配置也涨。「标准」不受影响。
- 代价：用户在九键里手动固定在第 1 位的词（`set_position` 固定第 1 位，或置顶时写进第 1 槽）同样会在上文明显不对时让出首位，存储里分不出它和自动记下的最近选择；只在「增强」打开时发生。每次首行是置顶词典行、或者前两名权重相近时多一次两行的模型评分，按键 p50 约多 0.3–0.5 ms，p95 没有变高。冷启动的 `nine-key` 词级集 top1 −0.25pp。
- 没量的：标记由 `NineKeySession` 的所有网格共用，十八键、九键双拼、14 键双拼、十八键双拼都会标，`typing_sim` 只量了九键和 14 键；`convert_eval` 学习关，量不到最近选择；真机（Pixel 3 XL）没有复测，桌面 25M 模型的上限臂没有跑（资源里没有那份模型）。
- 重访信号：真机上「增强」默认打开时，或者固定位置表能分清手动和自动之后，再看要不要只裁决自动记下的那一种。
