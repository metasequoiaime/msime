# Agent Note: 九键双拼

Status: implemented

## Problem

#6572 的主要诉求是在九宫格上打双拼：每个音节固定两个数字，第一个数字表示声母所在的组，第二个表示韵母所在的组，方案点名了米旮旯 2、米旮旯 3、辜氏 2 和辜氏 2 低重码，并希望能自定义这种数字键位。原来的九宫格（`NineKeySession`）只会全拼 T9：每个字母按电话键盘换成数字（`KEYPAD`），一个音节有几个字母就占几个数字；26 键双拼（`ShuangpinEngine`）则假定一个两键编码只解出一个音节（`cvt_single_sp_to_pinyin` 的前提，自定义表的校验也守着这一点）。九键双拼两条都不满足：编码定长两位，但八到十个数字键装 23 个声母、33 个韵母，一个两位编码必然对应好几个音节。

[自定义双拼方案](2026-10-10-custom-shuangpin-profile.md) 先把用户自定义 26 键表这一层做了；本篇记录九键双拼怎么接到九宫格上、内置哪几个方案、用户表的形状和校验，以及各宿主怎么画它；[iOS 宿主](2026-10-16-ios-nine-key-shuangpin.md)补齐原生入口与键面，鸿蒙随后复用同一套网格和 NAPI 接口接入，桌面共享屏幕键盘也通过同一个无状态接口取键面。

## Decision

### 方案数据

内置三个方案：米旮旯 2（`migala2`）、米旮旯 3（`migala3`，默认）、辜氏 2 低重码（`gushi2_low`）。表在 `crates/engine/src/nine_key_shuangpin.rs`，是按下面的公开描述独立整理的数字，没有复制任何键位图、配置文件或软件实现：

- **米旮旯 2、3**：百度百科「米旮旯」词条（`https://wapbaike.baidu.com/item/米旮旯`）的「方案规则」整理了两个版本各键上的韵母和特殊声母（2 版：ch 在 5，sh、zh 在 8，零声母在 6；3 版：ch 在 3，r 在 4，sh、zh 在 8，零声母在 2），以及「单韵母保持原始键位」的约定。米旮旯 3 用点讯输入法的那一版：u、ü、ei 在 0 键。用 `AlexShyXie/myTRIME-migala3-Layout`（提交 `a24edf47684d62e716b150165e7d82d4ae985be9`）的 `migala3.schema.yaml` 拼写运算和 #6572 里贴的搜狗键位截图交叉核对，三处一致。那份 Rime 方案的 `[oi]ng$` 写在 `iong$` 之前，iong 实际被编成三位，是它自己的笔误，百科和截图都把 iong 放在 6 键。米旮旯 2 用截图交叉核对，一致。
- **辜氏 2 低重码**：雷子的小站 2023-01-31 的文章（`https://www.lernen.top/index.php/archives/12/`，CC BY-SA 4.0，作者按百度输入法实打整理）给出了每个键上的声母和韵母（in、ing、eng 在 0 键，1 键放 ou、ong、iong，零声母在 2）和七个零声母音节的编码（爱 22、熬 27、诶 23、耳 23、嗯 23、安 25、昂 25）。用 #6572 的搜狗截图交叉核对，一致。
- **两处推断**，两个来源都没有逐字写出：没有列出的单韵母留在电话键盘上自己字母所在的键（a 2、e 3、i 4、o 6，u 和 ü 在米旮旯 2、辜氏 2 低重码里是 8），这是百科写明的「单韵母保持原始键位」；零声母音节的编码是「零声母键 + 它的韵母键」，`er` 取描述里列出 er 的那个键（三个方案都是 3），辜氏 2 低重码的七个例子与这条规则一致。

不收录的：

- **辜氏 2（普通版）**：唯一的完整描述是 #6572 里一张搜狗键盘的截图，没有作者发布的规则，也没有第二个来源可以核对；照截图抄进来就是按别人的软件界面定表。维护者的要求是拿不到完整、一致的公开描述就不收，用户可以照自己的输入法用自定义表打出它。
- **米旮旯 3 的百度早期版**（ei 挪到 8、u 和 ü 留在 8）：百科说那是百度当年不支持 0 键时的变通；现在的百度辜氏 2 低重码已经用 0 键，搜狗的米旮旯 3 也用 0 键，收两份同名方案只会让人选错。需要的人同样可以用自定义表。

### 表的形状与校验

用户表与 26 键自定义表同形（`{initials, finals, zero_initials}`，各是单位到键的对象），键换成数字：`initials` 给全部 23 个声母（九键上每个声母都要放到某个数字上），`finals` 给 33 个韵母，`zero_initials` 给 12 个零声母音节各两位数字；数字是 `0`–`9`，1 和 0 方案用得到就能用。每个音节按拼写拆成声母加韵母（`ju` 是 j 加 `u`，`lve` 是 l 加 `ve`），或者是零声母音节，所以每张合法的表给每个音节恰好一个编码；一个编码可以对应好几个音节。能打的音节是九宫格的完整音节表去掉 `jv`、`lue` 这类别名（词库只存 `ju`、`lve`），再加零声母表里的 `eng`。

Engine 判定合法性，错误是带位置的 `NineKeyShuangpinError`（`UnknownUnit`、`DuplicateUnit`、`MissingUnit`、`InvalidKey`，都带 part 和单位），与 `CustomProfileError` 同样摊成宿主的 `ShuangpinCustomProblem`。没有「编码冲突」这一类：九键上一个两位编码本来就对应五六个音节，零声母音节和声母加韵母的音节共用编码（米旮旯 3 的「安」an 和「班」ban 都是 25）是三个公开方案共同的设计，照字面禁止零声母编码与声母加韵母的编码相同，三个方案一个都收不进来。26 键那条规则防的是「零声母表先查，占掉的那个音节就打不出来」，九键双拼的解码同时保留一个编码的全部读法，不存在被占掉的音节。合法的表按内容只留一份（`nine_key_shuangpin`，与 26 键自定义表相同），连同它的拼写表；编辑中的表用不留存的 `check_table` 和 `table_key_hints`。

### 解码：九宫格的又一种网格

`KeyGrid` 加一个变体 `NineKeyShuangpin(&'static NineKeyShuangpin)`，仍是 `Copy`，相等按表的引用比较。九宫格的路径搜索、锁定、切分、整句种子、简拼、学习和候选排序照旧，只经由网格取码：

- **拼写表**：完整音节的码是方案给的两位数字，只打了一位的片段是声母（`zh`、`b`）和零声母音节的首字母（`a`、`e`、`o`）。`a` 既是两位的完整音节，又是一位的零声母片段，所以 `SpellingTable::by_code` 给每个片段记「在这个码下是不是完整音节」，`split_paths` 按它判断片段能不能在中间结束、路径的末段完不完整；全拼九宫格的这个标志就是原来的 `intact.contains`，行为不变。
- **一个音节占几个码**：锁定的拼写、左列的音节和整句种子都是完整音节，九键双拼总是两位（`KeyGrid::syllable_code_len`），全拼按字母数；`rank_key` 判断补全也按网格算码长。读音行把只覆盖了一位的音节显示成它的声母（`8146` 打到 `814` 时首选 中国 读作 `zhong'g`）。
- **按声母位找词**：一个两位编码五六个音节，三个音节以上时每个位置按音节频度留 48 条的切分常常没有词的那一条（`22942288` 有一千多种读法，百依百顺 排不进去）。九键双拼另按每个音节的声母那一位查简拼，只留编码正好以这串数字开头、音节数也对得上的词（`shuangpin_word_codes`、`shuangpin_word_spells`）。全拼九宫格一个音节的码长不定，没有这一步。
- **简拼行核对声母所在的键**：简拼按首字母查词库，`z` 同时查出 z 和 zh 开头的词，九键双拼里它们常在不同的键上（米旮旯 3 的 zh 在 8、z 在 9），所以先多取一些行，再逐行核对声母所在的键。
- **英文九键关闭**：数字不是字母的分组，没有英文行，专用英文里数字照常是数字，`Session` 不把它交给九宫格。日期时间的关键词按音节编码比（`riqi`）或按声母的键比（`rq`）；emoji、颜文字的读法边界按每条读法换算成字母位置。
- **数字路由**：`Session::character` 把方案用到的数字（可以有 1 和 0）交给九宫格；`'` 照旧切分。runtime 里网格用数字时（九键、九键双拼）数字都不当选词键，方案没用到的数字也一样，否则米旮旯 2 下按到 0 会选走一个候选。`View.key_grid` 是 `"nine_key_shuangpin"`，`View.nine_key` 为假（它没有英文九键，也不开注音九键）。
- **Android 实体键盘的数字边界**：`onKeyDown` 先处理注音键、本地模式拼写和数字选词，只在 `local_mode` 为 `none` 时把九键、九键双拼下未被认领的数字按字面上屏；仍有组合时先执行自动确认命令，避免替换组字区。表情、快捷短语等本地模式保持引擎自己的数字回退规则：不接数字时可以先上屏原文，不能被宿主的自动确认改为选择首个候选。普通组字的数字不能送回 `character`：这个入口同时承载触屏九键组码，数字 2 会开启 ABC 的候选，数字 3 会开启 DEF 的候选。触屏继续直接调用 `character`，不用为实体数字切换全局网格，因而不会丢失触屏组合或改写布局偏好。

### 偏好、宿主接口与 MCP

- **共享偏好**：`TouchKeyboardLayout::NineKeyShuangpin`（`nine_key_shuangpin`）和 `TouchKeyboardScheme::NineKeyShuangpin` 追加在末尾，默认不启用，引擎方案是全拼；`nine_key_shuangpin_profile`（默认 `migala3`）和 `nine_key_shuangpin_custom_profile`（与 `shuangpin_custom_profile` 同一个类型和大小限制，非法时报 `InvalidNineKeyShuangpinCustomProfile`）。两项等于默认值、表为空时都不写进文件，没用过九键双拼的文档以前的版本照样读得懂。Android 账号同步照 `fourteen_key` 上传布局 `nine_key_shuangpin`，表是本机设置，不上传。
- **host-api**：偏好的布局是九键双拼、方案是全拼时，建会话和重建会话都按表开网格；`custom` 的表不能用时按米旮旯 3 运行，偏好变更的响应带诊断 `Nine-key shuangpin table unusable because <原因>; using migala3.`，与 26 键自定义双拼按小鹤运行相同。换了表也算换了布局，宿主设下的网格覆盖随之作废。`msime_client_set_key_grid` 的 3 是九键双拼（表按已应用的偏好）。`msime_client_nine_key_shuangpin_layout` 是给宿主的唯一入口：给方案名和（`custom` 时的）表，回答实际用的方案和它的表、用户表带位置的问题、按 1 到 9、0 排好的每个键的声母和韵母；键面和设置页的编辑器都从这里取，宿主不另存键位。Rust 侧对应 `nine_key_shuangpin_layout`、`validate_nine_key_shuangpin_custom_profile`、`nine_key_shuangpin_custom_profile_problem` 和 `builtin_nine_key_shuangpin_custom_profile`。
- **MCP**：`get_preferences` 显示 `nine_key_shuangpin_profile` 和保存着的表，`update_preferences` 可以换方案、整张替换表；给了表或要选 `custom` 时先用 host-api 的同一个校验，不能用就拒绝并说明哪一项。它不切换键盘布局。

### 桌面共享屏幕键盘

桌面设置页已经能保存九键双拼偏好，但共享的 Tauri 屏幕键盘此前只认识普通九键和 26 键，导致九键双拼偏好在桌面面板上仍显示成没有键面提示的普通数字键。桌面宿主注册 `nine_key_shuangpin_layout` 命令，把当前方案和自定义表交给 host-api 的无状态接口；`DesktopKeyboard` 随偏好快照读取返回的 1 到 9、0 键面，`KeyboardPanel` 用它绘制提示。键帽始终发送对应的数字虚拟键，不能把提示中的声母或韵母当作字母发送。面板的手动切换仍在九键双拼和 26 键之间切换，切回九键双拼时恢复宿主当前方案的键面。

### Android 宿主

- **方案**：`KeyboardScheme.NINE_KEY_SHUANGPIN`（`nine_key_shuangpin`，引擎方案全拼，卡片字形「双」、角标「9」）追加在末尾，`optIn`；`fromPreferences` 有显式分支，通用循环同时排除它。打字统计记作「9 键」（`nineKey`）：统计按键盘的形态分，它没有自己的一档。
- **键面**：九键双拼画在九键的键面上，`touchLayout` 看到 `View.key_grid` 为 `nine_key_shuangpin`（没有本地模式）就给 `QUANPIN_NINE_KEY_LAYOUT`，读音行、左列拼音、三栏面板、123 数字层、组字不写进编辑器都与拼音九键相同。数字键面是四行：1–9 以数字作主标签，下一行完整提示声母项，只有韵母时显示「韵母」；触摸键面的完整映射展示由[收简键面提示](2026-10-13-android-shuangpin-compact-keyfaces.md)取代，完整映射仍在读屏和设置表中提供，点按经 `character()` 送数字；最后一行是「@#」/「分词」键、0 和逗号，「@#」/「分词」从 1 键挪下来，因为三个内置方案都把韵母放在 1 上；表用到 0 时 0 是组码键，否则原样上屏；右列 ⌫ 占两格。键面经 `NativeClient.nineKeyShuangpinLayout` 取，宿主不存键位（`NineKeyShuangpinKeypad` 只管怎么印、怎么读）。拼音九键和九键双拼同一个布局编号，`apply` 不会因为换了方案或换了表重建键行，所以 `ImeLayoutRows.shuangpinStale` 记着建行时的键面，变了就重建。没有英文九键，键上没有长按字母和滑动数字（它们给的是电话键盘上的字母）。
- **设置**：「输入 › 普通话」的「九键双拼」子菜单选表，选中即切换到这个键盘；「九键双拼」页（`NineKeyShuangpinPage`）选表、列出当前表每个键上的声母和韵母，编辑自定义表（从内置方案开始、逐格改数字），经系统文件选择器导入导出 `{initials, finals, zero_initials}` 的 JSON。编辑中的表每改一格就经同一个接口校验，问题带着出错的单位显示在那一格和保存行上，能用时才能「保存并使用」（写表并选 `custom`）。

### 评测与延迟

评测工具 `convert_eval`、`rerank_latency` 加了 `--grid shuangpin-<方案>`：用例是不带分隔的全拼，九键双拼要先切成音节，切法不唯一（xian 和 xi'an）的用例不计入（`convert_eval/grid_keys.rs`）；`--unique-segmentation` 让全拼九宫格只量同一批用例。锁定资源 dict-v2.0.14 加 `sentence-model.safetensors`，同一台机器、同一次构建：

| 集合（只留切法唯一的用例） | 九键 top-1 / top-5 / found | 米旮旯 3 | 辜氏 2 低重码 | 米旮旯 2 |
|---|---|---|---|---|
| `quanpin-words-v1` `--limit 3000`（2741 条） | 0.580 / 0.857 / 0.976 | 0.389 / 0.670 / 0.951 | 0.389 / 0.655 / 0.955 | 0.337 / 0.558 / 0.914 |
| `sentences-nine-key-v1`（75 条） | 0.520 / 0.533 / 0.640 | 0.213 / 0.213 / 0.213 | 0.200 / 0.213 / 0.240 | 0.093 / 0.093 / 0.107 |

按声母位找词之前，米旮旯 3 的词级是 0.290 / 0.562 / 0.842，四个音节的词 found 只有 0.395。全拼九宫格在这个分支上的两份评测与 develop 的结果逐字节相同，与提交的 `baseline-nine-key.json` 也相同。

`rerank_latency` 在 `sentences-nine-key-v1` 上，develop 的全拼九键、本分支的全拼九键和三个九键双拼方案交替各跑三轮（毫秒每键，按键数不同：全拼 1791 键，九键双拼 1296 键）：

| | 只有引擎 mean / p50 / p95 | 挂键盘模型 mean / p50 / p95 |
|---|---|---|
| develop 九键 | 4.65–4.71 / 4.86–4.91 / 9.20–9.28 | 9.15–9.22 / 6.82–6.98 / 22.68–22.80 |
| 本分支九键 | 4.48–4.58 / 4.73–4.77 / 8.81–9.03 | 9.00–9.09 / 6.83–6.96 / 22.53–22.70 |
| 米旮旯 3 | 4.26–4.39 / 3.19–3.25 / 8.92–9.34 | 7.90–8.06 / 3.23–3.38 / 24.69–24.91 |
| 辜氏 2 低重码 | 4.23–4.28 / 3.28–3.33 / 8.83–8.89 | 7.89–7.93 / 3.35–3.39 / 24.21–24.51 |
| 米旮旯 2 | 4.69–4.73 / 3.52–3.55 / 9.93–10.09 | 8.36–8.41 / 3.56–3.66 / 25.01–25.12 |

只有引擎时九键双拼每键的均值和中位数不高于全拼九键，p95 相当（米旮旯 2 高约 0.8 ms）；挂上键盘模型时均值和中位数更低，p95 高约 2 ms：九键双拼每一键带进的音节信息比全拼多，同样长的句子每键要重排的整句更长。

## Alternatives considered

- **Android 检测到实体键盘就关闭引擎网格**：实体数字自然不再进入触屏组码。但切换时可能还有触屏组合，而且用户仍能同时点屏幕九键；临时改会话网格会让两种来源互相影响。保留网格，在硬件事件边界处理未被认领的数字。
- **在 26 键双拼的 `ShuangpinEngine` 上扩展多义编码**：双拼的切分、辅助码、整句都在那里。但它的切分是「两键能组成音节就两键，否则一键」的贪心（`pinyin_segmentation`），转换结果是一条全拼切分；多义编码要求同时保留多条音节路径，这正是九宫格已经实现、而双拼引擎没有的东西。在双拼引擎里再写一套多路径搜索就是两份实现。
- **把九键双拼映射成「每个数字代表键上的几个字母」再走全拼 T9**：零改动引擎。但九键双拼的数字分组不是电话键盘的字母分组，一个音节固定两位、与字母数无关，套用全拼 T9 的编码会给出完全不同的切分。
- **照字面禁止零声母编码与声母加韵母的编码相同**：这是提案里写下、维护者拍板时沿用的规则，最强的理由是与 26 键自定义表的校验一致，用户表里也查得出「安」和「班」挤在一个编码上。但三个公开方案都把零声母当成某个声母键上的一员（米旮旯 3 在 2 键，与 b、c 同键），照字面执行一个内置方案也收不进来，而这条规则在九键上防的事情（某个音节打不出来）并不存在。没有照做，而是在 PR 里请维护者确认这一解释。
- **种子多接几条余下数字的切分（九键双拼的 `SEED_TAIL_LIMIT` 从 3 加到 8 或 16）**：整句集 top-1 从 0.213 升到 0.28、0.32，是这次试过的最有效的整句改动。但只有引擎的 p95 从 9 ms 涨到 15.7 ms（8）和 27 ms（16），挂模型的 p95 到 30.6 ms 和 41.8 ms，违背「逐键延迟不能明显回退」的要求，没有采用。九键双拼整句的根本问题是每个位置按音节频度留 48 条切分，这是 [九键整句改由数字层统一词网格解码](../../proposed/feature/2026-10-09-nine-key-digit-lattice.md) 要解决的，那份方案落地后九键双拼一并受益。
- **辜氏 2 普通版照 #6572 的截图收录**：报告人提供了截图，键位完整。但那是一家商业输入法界面的截图，没有作者发布的规则，也没有第二个来源核对，见上文「不收录的」。
- **键面提示走会话句柄（`msime_client_*(handle)` 回答当前会话的网格）**：最准确，键面永远与正在跑的表一致。但设置页预览编辑中的表时没有会话，桌面宿主也没有九宫格会话；无状态的 `msime_client_nine_key_shuangpin_layout` 用与建会话相同的回退规则，键面与会话一致，编辑器和键盘共用一个入口。
- **另起一个 client-core 表类型**：类型名更准确。但 JSON 形状和大小限制与 `ShuangpinCustomProfile` 完全相同，另起一个类型就要在 TS 类型、对等检查和 MCP 里各多维护一份；共用类型，含义靠字段名和文档区分。
- **Android 的 0 放在空格键上**：百度、搜狗的九键双拼都这么做（lernen.top 的文章说辜氏 2 低重码「包括 1 和空格」），从那边换过来的用户最顺手。但组字中空格就不再能确认首选，而空格键属于各方案共用的底栏，要按方案和组字状态改它的行为和键面；单独一格 0 放在 8 的正下方，空格的意思不变，与注音 9 键的最后一行同一个排法。
- **Android 给九键双拼一个新的触屏布局编号**：判断更直白，不靠 `key_grid` 补一层。但宿主里按 `QUANPIN_NINE_KEY_LAYOUT` 判断的地方有十几处（读音行、左列、三栏面板、数字层、Shift、快捷标点……），14 键的笔记已经记着这种非穷举判断漏一处就静默变成 26 键的行为；九键双拼除了键面以外都该与拼音九键相同，共用编号让这些地方一处不改就对。

## Consequences

`HardwareTranslationDeviceSmoke` 先运行隔离原生服务的 `HardwareDigitChecks`，覆盖九键、九键双拼、26 键、数字选词开关、组合后输入数字、触屏组码、U 模式数字和表情模式的原文回退与数字选词；`-e digits-only true` 只执行这部分合成按键回归，不要求系统接着实体键盘。完整套件仍要求实体键盘并验证翻译快捷键。合成事件不能代替 Android 16 平板蓝牙键盘的真机验收。

- **收益**：
  - 九宫格上能打三个公开的九键双拼方案和任意一张合法的用户表，与全拼九宫格共用路径搜索、锁定、切分、整句、学习和候选排序，以后九宫格的改进九键双拼自动得到。
  - 表不合法时有带位置的原因，宿主按米旮旯 3 运行而不是打不了字；默认行为不变：没有人选九键双拼时，偏好文件、会话和全拼九宫格的评测都与原来相同。
- **代价与已知上限**：
  - 重码比全拼九键高得多（72 到 80 个两位编码装四百多个音节），词级 top-1 约 0.39，长句 top-1 只有 0.2 左右；整句的提升要等数字层统一词网格。
  - 按声母位找词每次按键多一次简拼查询（三个音节以上），延迟已经计入上表。
  - 进程为用过的每一张不同的合法表常驻一份表和拼写表（几十 KB），不能回收。
  - `View.nine_key` 在九键双拼下为假，宿主判断「数字是组码」要看 `View.key_grid`。
  - 降级：选了九键双拼后装回旧版，偏好严格解析整份读不出来（`touch_keyboard_layout` 和 `touch_keyboard_schemes` 有新值）。与 14 键相同，照现有的严格解析接受这个代价。
  - 鸿蒙由[共享设置页](2026-10-17-harmony-nine-key-shuangpin-editor.md)提供内置选表和自定义表编辑，iOS 由[原生宿主设置页](2026-10-16-ios-nine-key-shuangpin.md)提供；桌面宿主没有单独的九键双拼设置入口，但共享屏幕键盘会读取已有偏好并显示同一张键面。
  - Android 的四行网格挤在三行九键的高度里，键比拼音九键扁，数字主标签为 22sp，单行简短提示为 11sp；触摸键面不再铺完整韵母表，初学者需要查看设置中的映射。
  - HarmonyOS 复用已有九键外框和底行，数字键直接把 1–9、0 交给 `character()`，不提供电话字母长按；设置页的选表与自定义表编辑见[鸿蒙设置页](2026-10-17-harmony-nine-key-shuangpin-editor.md)，仍通过同一无状态接口取表与校验。
