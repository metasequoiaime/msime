# Agent Note: 上屏后联想与组字状态分离

Status: implemented

## Problem

#9433 要求选中「吃」后仍能在候选栏选择「饭」「东西」等后续内容。现有整句候选只重排正在输入的拼音，空闲会话没有下一词生产者；运行时又把非空候选视为组字，直接填入候选会造成空格误选、失焦误提交和数字键被截走。

## Decision

新增独立的 `next_word_prediction` 偏好，默认关闭，Android 在「表达 → 智能」提供「上屏后联想」。共享引擎拥有联想状态与候选，运行时保留正常的带代次候选选择，并明确区分联想与组字。只有显式选择能提交联想；新输入、标点、空格、回车、删除、取消、失焦、外部光标移动、切换布局或模式清除建议。（2026-11-02 起空格和数字键也能选联想，见下文「统一选法」。）

数据源是现有拼音词库的同字同音前缀续词，以及学习已启用时的个人相邻词记录。拼音查询在 `key` 前缀索引范围内筛选汉字前缀，再截取未上屏部分，最多返回八行；不开新模型、不联网、不全库反查。个人查询合并已落盘和待刷新的同一批转移，遵守 `writer → pending → model` 锁顺序，读取不创建 journal。密码或私密输入继续使用宿主已有的隐私门禁，停用学习时不读取个人词序。

Android 全拼、双拼及触屏组码布局接入这一能力。底层能力共享，但其他宿主没有完成交互验收前不启用该选项。哪些宿主启用由 `HostPlatform::shows_next_word_prediction`（`HostCapabilities.next_word_prediction`）决定，取代原先 host-api 里的 `cfg!(target_os = "android")`：鸿蒙的 Rust 目标是 `*-linux-ohos`，按 `target_os` 判断会把它和桌面 Linux 混在一起；各宿主在接好「没有预编辑时显示候选、能点选和用键盘选中」的那次改动里把自己加进去，共享设置页（桌面在输入页「候选与联想」组，鸿蒙手机在表达页「智能」组）随这一项列出开关。六个平台用同一条规则，见下文「统一选法」。（最初的取舍是：普通空格仍插入空格，回车仍执行编辑器动作，数字仍输入或开始九键组字，失焦不会提交建议。）

## Existing decisions

- [整句候选文案](../../implemented/bug-fix/2026-10-23-android-sentence-candidate-wording.md)：部分重叠，保留原设置的含义，本篇新增独立能力并互链。
- [九键个人排序](../../implemented/feature/2026-10-09-nine-key-initials-personal-ranking.md)：只约束组字候选的排序，不承担空闲建议；继续复用同一份个人 journal。
- 备份习惯相关笔记说明既有表的恢复方式，与本次只读查询无决策冲突；不改变存储格式。

## Alternatives considered

- **独立可枚举预测模型**：可以提供更广的跨词语义覆盖，但现有内置二元、三元模型只有哈希与分数，无法枚举词面；引入新模型还需要来源、许可证、资源分发与内存预算。现有词库续词和个人词序能提供真实建议，先复用这些已部署的数据。
- **把建议放进普通组字**：能复用所有候选交互，但会让空格、回车和失焦把用户没有输入的建议当成待提交文字，必须独立标记状态。
- **只修改设置文案**：最小且不改变输入行为，已由前篇完成，但无法满足 #9433 的实际需求。

## Consequences

词库续词的冷启动范围取决于现有短语覆盖；它不提供通用语义预测，不虚构词库中不存在的命中。开关默认关闭，避免未经选择的建议接管空格、回车或数字。新增查询不改变个人词序的表结构或落盘格式，隐私输入不读取或显示个人联想。

自己的延迟上屏回声保留建议；外部选区变化通过重新聚焦同一原生会话切断旧的词序上下文。普通取消命令保留已上屏的词序，不能代替这个边界。隐私设置接口返回布尔值，Java 校验响应信封后另取最新视图；不能把布尔值按对象解析，否则会误走停止会话的失败分支。

设备夹具使用每次独立的合成目录，防止上次测试学习出的「吃 → 吃」影响下一次的候选顺序；不修改用户偏好或真实词序。

macOS 把联想画在普通候选窗里。空格和候选窗上画着那一行的 1–9 照常走组字时的选词路径，按候选身份上屏；其余的键不逐个改写既有分支，而是在 `handleKeyEvent:` 最前面先把联想收掉，再照没有联想时的路径处理：回车、退格和越过这一页的数字照常交给应用，`, . - = [ ]` 走中文标点而不是翻页，方向键交给应用移动光标。逐个分支加例外会漏掉以后新加的候选快捷键（Option/Control+数字取释义列、Tab 进展开网格这些都按「候选窗可见」接管按键），收在入口只有一处要维护。光标已被挪走时空格和数字也不选，免得把旧位置的联想选进新位置。收掉的方式分两种：方向键、Home/End、翻页和 Command/Control 组合键会挪动光标或改动文档，按 Android 外部选区变化的做法重新聚焦（`setFocused:YES`）切断词序上下文；其余打字的键送 Cancel，保留刚上屏的词序。Esc 只关闭联想不交给应用，Vim 模式名单里的应用例外，Esc 照常到达应用并切英文。IMK 在没有预编辑时不报告光标移动，所以联想出现时记下客户端选区，下一次按键前或全局鼠标监视器看到其他应用里的点击之后再比一次，对不上就重新聚焦；点自己的候选窗是本进程事件，不经过全局监视器，照常按候选身份上屏。判断「有没有组字」的地方（智能标点、小键盘标点、成对引号、Vim Esc、Tab、菜单、中日英循环）改用排除联想的同一个判断，与 runtime 的 `has_composition` 一致。

联想时候选栏右端放展开键还是关闭键由用户在三种样式里选，关闭键送 Cancel、不插入空格，见[上屏后联想的候选栏按键样式](2026-10-29-post-commit-prediction-buttons.md)。

## 统一选法（2026-11-02）

用户在 macOS 上试用时，联想出来以后按空格、按数字都选不中，期望和普通候选一样能用键盘选。六个平台改用同一条规则：点选、数字键选本页对应的一条、空格选高亮的一条；回车、标点、退格照常交给编辑器，Esc 或关闭键关掉联想。运行时在把按键交给引擎之前接管空格和数字（引擎收到任何按键都会先清掉联想），九键、字母网格和拿数字拼写的方案里数字仍是输入，越过本页的数字照常输入。这推翻了上文「普通空格仍插入空格、数字仍输入」的取舍：联想默认关闭，打开它的用户要的是能快速选中；Android 触屏上空格从此在联想时选首条，不再插入空格。中间曾按「手机和电脑不一样」改成只有电脑能用空格和数字选，用户随后明确：手机和电脑都能用空格、数字和点选选中联想，所以这条规则对六个平台都成立；手机和电脑不同的是界面（触屏候选栏有 × 和 ∨，电脑候选窗没有）。
