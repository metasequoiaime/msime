# Agent Note: dict-builder 生成新世纪五笔表 wubixsj

Status: implemented

## Problem

新世纪五笔的单字码表已经登记为 `wubi06-rime`（来源与许可见[新世纪五笔单字码表取自 byujiang/wubi06_rime](2026-11-02-wubixsj-table-source.md)），上游码表的词组和权重都不能直接用：词组疑似从搜狗细胞词库导入；权重是个人手调值。新世纪表本身因此只有单字，词组要自己生成，排序也要自己定，而且不能动已经发出去的 `wubi86`、`wubi98`。

## Decision

- `Stage::WubiXsj`（`--only wubixsj`，排在 `Wubi98` 之后，`STAGES` 15→16）在工作库里建 `wubixsj` 表，结构和两个索引与 86、98 相同；`product::split_wubi_database` 把它拆进 `msime-wubi.db`，`verify` 要求至少 50000 行。
- 发布开关是 msime-dictionary checkout 里的新世纪词组快照 `sources/wubi/wubixsj-supplement.txt`（`main.rs` 的 `wubixsj_published`）：没有它时这个阶段跳过，`verify` 要求 `msime-wubi.db` 里没有 `wubixsj`；有它时要求这张表至少 50000 行。构建器不读快照的内容，词组照样每次重新派生。这样第一个带新表的 `dict-v` 由收快照的那个 msime-dictionary PR 发出，它同时补上 NOTICE 的生成表一行和发布说明的措辞，维护者在合入它之前查专利和商标；本 PR 和收上游码表的 PR 合入的先后不再要紧，那之前的日常词条合入照常发布、`msime-wubi.db` 不变，`upstream.lock.json` 还没记录上游码表的旧提交（例如 `dict-v2.0.41`）也照常能重建。做法与粤语 `custom/cantonese.txt` 相同：checkout 没有这个文件就照旧构建。
- 单字只收 CJK 统一汉字基本区（U+4E00–U+9FFF）、编码是 1 到 4 个 a–y 字母的行：部首、私用区、扩展区、兼容区汉字、`·`、`〇` 共 6668 行不收，剩 24130 个单字行。
- 同码单字的名次按上游权重从高到低（同权重保持文件先后），写进表的权重按名次给 10 的倍数（`msime::rank_weights`，98 表也改用它）。这与计划第 3 节「按行序」不同，需要维护者确认；从上游表里取的因此是单字全码和同码先后两样，不只是单字码。上游文件里同码单字的先后没有意义：25 个一级简码里 15 个的文件第一项不是权重最高的那个（`g` 下「王」在「一」之前），三码、四码同样大多不一致（`hgd` 下「丄」在「上」之前）；上游权重是唯一带着一级简码 200000、二级简码 10000、三码 9000 这一层次的信息。
- 词组全部由 `wubixsj-supplement`（`src/wubixsj_supplement.rs`）生成，候选与 86、98 补全相同，编码用同一套词组规则（`msime_engine::wubi_phrase_code`）和新世纪单字全码；这套规则在上游自己的 61702 个四码词组上全部还原。
- 权重两层：86 极点表里有的词（第一层）沿用它在极点表里的最大权重；其余的词（第二层）走共用的 `wubi_supplement::rank`，把单字和第一层一起当作「原有行」，上限取 9 与同码最低权重减 1 中较小者、最低为 0。所以第二层低于所有单字（最低 10）；对第一层，只要同码第一层最低权重大于 0 就严格更低，等于 0 时两者同为 0。生成表在单字之后并入，同一编码内第一层在第二层前面，引擎同权重按 rowid 排，所以第二层在候选里永远排在同码单字和第一层之后。实测快照里第一层最低的权重是 5（`个位数 wwov`），没有出现并列。
- `wubi_supplement::upstreams` 改为接收要列出的 reference；86、98 的表头仍只列原来四个上游，快照除生成器提交外逐字节不变。
- `web` 子命令接受带 `wubixsj` 的 `msime-wubi.db`，两个输出里都清空它；输入里没有这张表（`dict-v2.0.41` 及以前）时照常裁。和 split 放在同一个 PR，否则第一个带新表的 `dict-v` 一被钉住，`release-web-engine.yml` 就会失败。
- 只加表，不改 `format_version`：现有引擎的 `merge_split_wubi` 只搬 `SPLIT_WUBI_TABLES` 里的 86、98，`wubixsj` 留在 `msime-wubi.db` 里不用，直到引擎支持新世纪方案。

## 实测（Mac Studio，msime-dictionary 收文件的分支对 main ed18a95 的基线）

- `wubixsj` 726606 行：24130 个单字，702476 个词组（第一层 63111，第二层 639365），232867 个编码。1919 个编码的第一个候选从单字变成了第一层词组；9545 个原本只有一个单字的四码因为有了词组不再自动上屏。
- `msime-wubi.db` 由 94994432 字节涨到 142368768 字节，多 47374336 字节。
- `wubi86`（729733 行）、`wubi98`（731263 行）按 rowid 逐行比较与基线完全相同，表和索引的 SQL 也相同。

## Alternatives considered

- **照计划按文件行序给单字定名次（与 98 表相同）。** 最强的理由是完全不碰上游的手调权重。不用：这份文件的行序没有意义，按行序排会把 15 个一级简码和大多数同码字排错，例如打 `g` 先出「王」；行序也来自同一份上游文件，换成它并不缩短许可链。
- **不加开关，把查专利和商标挪到本 PR 合入之前。** 代码最少。不用：本 PR 与收上游码表的 PR 都合入后，下一次改到 `sources/` 或 `custom/` 的日常合入（10 月以来有 65 次）就会发出带新表的 `dict-v`，那时 NOTICE 还没有生成表那一行、发布说明也还写着只有 86、98；而且本 PR 先合的话，每次发布都会因为 checkout 里没有上游码表而失败。
- **以 `upstream.lock.json` 是否记录上游码表为开关。** 也能让旧提交照常重建。不用：发布时刻就成了收上游码表的 PR 与本 PR 中后合的那个，仍然早于 NOTICE 和发布说明。
- **按本项目拼音字频给同码单字排序。** 不依赖上游的任何数值。不用：字频不知道简码层次，`aa` 这类二级简码位上会按常用程度而不是按简码排；上游权重恰好编码了这一层。
- **所有词组都压在 9 以下（与 86、98 补充表一样）。** 实现最简单，单字永远在前。不用：新世纪表没有自己的词组，这样常用词会全部排在同码生僻单字之后（`学生`、`社会` 会排在「浶」「祔」之后）。
- **第一层的权重封顶在同码单字之下。** 能保证单字永远在前。不用：效果与上一条相同；极点表的 10、20、30 档本来就和单字按名次给的 10 倍数同一尺度，在 86 里常用词组排在同码生僻单字之前是正常的。

## Consequences

- **收益**：新世纪表有了与 86 相当的词组覆盖和排序，`力 ent`、`为 ytny`、`上 hgd`、`段 wdwc`、`男 ler` 都在对应编码的第一位；`我们`、`中国`、`工作`、`问题`、`可以` 等常用词的候选顺序与 86 同码基本一致。86、98 两张表不变。
- **代价**：`msime-wubi.db` 约增 47 MB，每个平台的安装包和代次工作副本跟着变大；单字的先后依赖上游个人手调的权重，`aa` 下「工」在「式」之前这类取舍原样继承。上游错码要等拿到 CNMan 的许可后对照修正。
