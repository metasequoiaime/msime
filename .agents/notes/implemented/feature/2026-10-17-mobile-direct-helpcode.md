# Agent Note: 移动端支持双拼直接辅助码

Status: implemented

## Problem

#8328 的移动端键盘只能在完整拼音或双拼组合的末尾识别辅助码。用户连续输入时，`uibjm` 这类「双拼音节 + 一位辅助码 + 下一个音节」会被按普通双拼重新切分，`tartantab` 这类多个音节各带一位辅助码的句子也无法缩小候选。

## Decision

在双拼查询入口增加直接辅助码路径：枚举每个两键音节后接一位辅助码、或接一位小写加一位大写辅助码的完整切分；用当前辅助码表把切分中的约束应用到候选词，再按约束数量选择最具体的非空结果。没有直接辅助码匹配时继续使用原有的末尾单辅助码和双辅助码逻辑；三键单字仍直接使用原有路径。

解析只使用共享 Engine 已有的双拼 profile、词典候选和辅助码表，不在 Android、iOS、HarmonyOS 各自复制一套规则；三个移动端宿主已有的 Shift 路由继续把按键交给 Engine。

后续修正：`raw_input_with_cases` 会保留 Shift 造成的大小写，但双拼音节本身的两键编码仍按不区分大小写处理。解析每个音节时先将这两键折叠为小写，只把音节后的辅助码大小写用于区分单辅助码和双辅助码；因此首个音节以大写键开头时不会错误回退到普通双拼查询。

第一位辅助码必须为小写，第二位必须为大写。大写单辅助码继续走原有的末字优先路径，不能把普通句尾 Shift 辅助码重新解释为句中约束。搜索最多访问 512 个节点、返回 64 条路径，限制包含无解分支在内的逐键开销。

直接辅助码候选的 `pinyin` 保存原始输入前缀，包含其音节内的辅助码；`canonical_pinyin` 保留词典中的全拼读音。会话按这个原始前缀消耗输入，完整选词不残留辅助码，前缀选词保留后续输入的大小写。

普通候选没有符合约束的整句时，共享词网格先按音节位置过滤词边，再执行每段上限和束搜索。查词阶段读取完整同音页，避免低频匹配字在过滤前被普通 32 条上限截掉。这样词库只有单字时也能组合出「他她它」，并继续使用已有的 n 元和个人模型评分；关闭词网格时不额外合成句子。

## Alternatives considered

- **只在三个移动端宿主拼接反引号**：可以复用现有输入转发接口、避免改动共享查询入口；但宿主不知道词典中哪些字支持某个辅助码，也无法在多段编码存在歧义时决定切分，同一逻辑会在三平台分叉。
- **把所有输入预先改写成固定两键分组**：解析线性且易于复用现有分词；但直接辅助码允许一位或两位辅助码，固定分组会把 `uibjm` 和 `tartantab` 的合法路径提前丢掉。
- **替换现有末尾辅助码查询**：可以统一查询实现；但会改变单字末尾辅助码的候选顺序和缓存语义，保留原路径并只在解析到直接约束时提前返回，影响面更小。
- **只过滤现有整句结果**：完全复用现有候选和缓存，改动更小；但未入库的同音字组合可能从未进入普通束搜索结果，即使辅助码唯一也找不到目标句，因此需要约束后的整句搜索。

## Verification

引擎合成词库回归覆盖 `uib`、`uibT`、`uibjm`、`uibTjm`、`Uibjm`、`tartantab` 和 `tartantabA`，验证单辅助码、双辅助码、辅助码后继续输入、多音节直接辅助码、大小写音节键、缓存命中、原始输入范围与禁用回退。另以只有单字、并有 40 个更高权重同音字的词库验证低频约束句子合成。会话回归从按键输入到候选选择，检查完整提交、前缀选词保留尾段及无残留输入。解析器回归覆盖手工分隔符、非 ASCII 和长歧义输入。

## Consequences

移动端连续输入可以直接使用逐音节辅助码，候选约束由共享 Engine 完成。存在歧义时需要查询多条候选路径，达到搜索预算后可能回到原有查询；遇到无匹配路径同样回退。约束整句搜索需要临时保留完整同音词边，增加内存和查询开销；该回退搜索使用 n 元和个人模型评分，尚未对约束后的路径额外执行神经重排。本轮验证覆盖共享 Engine 和会话层，不包含三平台装机验收。
