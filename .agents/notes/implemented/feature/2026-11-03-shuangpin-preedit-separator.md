# Agent Note: 双拼预编辑保留原始按键并显示音节分隔

Status: implemented

## Problem

双拼预编辑原来只有两种显示：保留连续的原始按键，或显示展开后的全拼分词。展开后的全拼能看见音节边界，却把用户实际按下的韵母键换成了另一串字母；连续原始按键又看不出边界。引擎请求已经维护按音节切开的 `raw_segmentation`，但预编辑显示没有消费它。macOS 的原生设置窗口和共享设置页也只有两档。

## Decision

新增 `shuangpin_preedit_shows_separator` 布尔偏好，默认值为 `false`，与既有 `shuangpin_preedit_uses_raw` 组合表示三档：`false + false` 是展开后的拼音分词，`true + false` 是连续原始按键，`true + true` 是原始按键加音节撇号。设置控件切换档位时总是同时写两个字段；从第三档切回旧档位会清掉分隔字段，旧配置只含 `shuangpin_preedit_uses_raw` 时仍保持原来的行为。

引擎在分隔档位开启原始双拼分段，让既有的 `raw_segmentation` 和辅助码装饰路径生成 `wo'mf` 这样的预编辑；展示层只在选择分隔档位时画撇号，提交、编辑文字和候选查询仍使用原始按键。参考快照和宿主展示快照继续沿用原有双拼预编辑边界，新增档位只改变 `preedit` 的显示文本。

共享 UI、Host API、C API 选项和 macOS 原生设置都接入该字段。macOS 的本机 defaults、共享偏好合并、云快照、恢复默认值和设置同步均登记新键；旧云文档缺少新字段时按默认关闭处理。其他平台通过共享偏好和 Host API 获得引擎能力；本次 issue 只要求 macOS 的原生备用设置入口，因此没有把 Linux/Windows 原生的旧两档控件改成第三档。

## Alternatives considered

- **直接改变 `shuangpin_preedit_uses_raw` 的语义，让它在某种情况下自动插入撇号。** 这样无需新增字段，但无法同时表达连续原始按键与原始按键分隔，旧配置也会出现无法区分的状态，因此保留旧字段并增加组合字段。
- **在设置页只保存字符串枚举。** 枚举能直观表达三档，但会破坏现有跨平台布尔配置和旧宿主的读取路径；两个布尔字段可以让旧客户端继续读取第一、第二档，并让新客户端无损表示第三档。
- **从展开后的 `normalized_segmentation` 重新拼出原始分段。** 这会把双拼韵母换回全拼，不能满足核对实际按键的需求；直接复用请求中的 `raw_segmentation` 能保留原始键和已有大小写、辅助码处理。

## Consequences

新增字段默认关闭，不改变既有用户的预编辑手感和已发布配置；选择第三档后可以同时核对实际按键与音节边界。配置格式多一个可选布尔字段，macOS 云端快照字段数随之增加，旧云文档在下载时由本机快照补齐。原生 macOS 备用设置可以选择三档，主共享设置页和引擎显示保持一致。Linux/Windows 原生旧控件仍只能改动原有两档，但它们读取共享偏好时可消费第三档。

验证覆盖 Rust 引擎的三档输出、Host API 映射、共享 UI 状态和切换、macOS defaults/共享合并/云快照字段。尚未在 macOS 真机输入法进程中做交互验收，需在后续 macOS 宿主验证中确认原生窗口选择第三档后候选窗显示 `wo'mf`。
