# Agent Note: 插件列表直接控制启用状态并保存展示顺序

Status: implemented

## Problem

「我的插件」列表只有进入详情后才能启用或停用指令表、短语表，用户需要逐个打开详情才能处理常用插件。列表也没有保存用户自己的排列顺序，Windows 原生设置和共享桌面设置页无法保持同一顺序。

## Decision

插件卡片在列表中直接提供可用类型的启用开关；指令表和短语表继续使用现有的 `command_tables`、`phrase_tables` 上限、去重和优先级规则，脚本插件继续通过既有授权对话框处理，不在卡片上绕过能力授权。列表排列单独保存为 `plugins.plugin_order`，条目使用 `kind/id` 键，只用于设置页展示，不改变指令表、短语表或脚本插件的运行顺序。未知、重复和已删除的键在读取展示时忽略，新的插件按原有类型分组顺序追加；拖动后的顺序由共享偏好保存，因此 Windows 与使用共享设置页的桌面宿主可以同步。

共享 Rust 偏好持有并校验该字段，TypeScript 设置页和 Windows 原生设置页各自只负责控件与调用既有偏好写入路径。列表排序不改变任何宿主加载或执行契约。

macOS 的 `preference-coverage` 将 `plugins.plugin_order` 记为有明确理由的宿主豁免：共享设置页直接读取和写回它，输入法宿主不应把仅用于设置页展示的顺序误当成插件加载或运行顺序。

## Alternatives considered

- **把列表顺序复用为指令表或脚本执行顺序**：可以少一个字段，但会让视觉整理意外改变输入行为；没有采用，因为报告者明确要求拖动只影响插件列表。
- **只在详情页增加快捷入口**：改动较小，但仍不能在列表中快速处理多个插件，也没有解决跨平台展示顺序；没有采用。
- **让脚本插件卡片开关直接写授权**：操作看似统一，但会绕过能力确认、内容哈希检查和既有错误恢复；没有采用，脚本插件仍打开授权流程。

## Consequences

列表新增一个可同步的偏好字段，旧配置缺字段时保持原有类型顺序和行为；删除或导入插件不会留下影响运行时的状态。共享页和现代 Windows 页需要维护同一套展示排序规则，Win7 偏好读写也保留该字段以免旧设置窗口覆盖它。列表控件增加了键盘和读屏路径，拖动只作为顺序编辑手段，启用状态和运行时优先级仍由原有业务规则决定。
