# Agent Note: 九键整句在按键之间沿用好切分，跨切分比较时每个词组多扣一份奖励

Status: implemented

## Problem

#6059：九键长句的整句首选经常不对。[九键长句回归集](../../proposed/feature/2026-10-09-nine-key-digit-lattice.md) 的 81 条在锁定资源上九键 top-1 0.457、found 0.556（挂重排模型），不挂模型（产品默认，「键盘神经联想」默认关）0.346 / 0.556；同一批句子在全键盘上 0.691 / 0.716。

逐条分类（不挂模型，引擎直接打每串数字，再对照同一串拼音在全键盘上的结果）：

- 全键盘对、九键错的 17 条是九键自己的问题，其中 10 条是**正确切分根本没被查**：`split_paths` 每个位置只留 48 条，按「音节少、末音节完整、单字频度」排，长串里正确的切分排不进去（`zhe'ge'di'fang'wo'yi'qian'lai'guo'yi'ci` 29 个数字，正确切分不在 48 条里，首选是「这非当我已善睐国债」）。把上限放到 96、192 条也只把 81 条里留住正确切分的从 56 条提到 62、64 条，改成只按频度排是 57 条：单字频度看不懂词，加多少条都一样。
- 另外 7 条是**正确切分查了，但跨切分比较输了**：`comparable_weight` 每个音节扣一份 `PHRASE_LENGTH_BONUS` 之后，词组边只剩它的 `ln(词频)`（正数），单字边是 `ln(w / 1e6)` 再扣一份奖励，一个单字比一个词组低二三十个单位，于是把读法切成更多词组反而得分：「匿名天佑龙马」的分是「你明天有空吗」的两倍多。
- 还有 11 条正确切分自己解出来的整句就不对（「我倒加了」「回到加了」），全键盘同样错，是整句解码和词库的问题，不是九键。

## Decision

- **按键之间做一次束搜索（`NineKeySession::sentence_seeds`、`seeded_paths`、`next_seeds`，`crates/engine/src/nine_key.rs`）。** 每次刷新后，从排好的候选里取覆盖全部数字、不是模糊音的前 `SENTENCE_SEED_LIMIT`（4）条全拼当种子，去掉最后一个音节后相同的只留一条；上一次的种子只要去掉最后一个音节后仍拼得出数字开头，就一起留着，合计最多 `SEED_RETAIN_LIMIT`（8）条。下一次刷新时，每条种子去掉最后一个音节（它可能被新数字续长，或者本来只拼了一半），取仍拼得出数字开头的那几个音节，接上余下数字按频度排的前 `SEED_TAIL_LIMIT`（3）条切分，补进要查的切分里。词网格看得懂词，前几次排在前面的整句的切分多半就是这一次的前半截，所以每次按键只需把束里的切分往后接一两个音节。
- **种子只在用户没锁定拼写、没打切分、没选首字母时用。** 那些情况下切分已经被用户限定。末尾只按了下一个音节的头一两个数字、没有覆盖全部数字的行时，种子原样留着，否则每隔一键就丢一次。组字结束时清空。两个种子缓冲建会话时留好容量、刷新时轮换，按键时不分配。
- **有种子、数字至少 `SEEDED_TRUNCATE_DIGITS`（12）个时，按频度留的切分截到 `SEEDED_PATH_LIMIT`（24）条。** 长串的好切分主要靠种子补，频度切分截短省下的查询抵掉种子的开销；短串（词级输入）照旧留满 `PATH_LIMIT` 条。
- **`comparable_weight` 对每个多字词再扣一份奖励：`weight - PHRASE_LENGTH_BONUS * 1000 * (音节数 + 多字词数)`。** 多字词按 `sentence_words` 里两个字以上的词数。等于给每个词一份插入代价，切得越碎越吃亏；单字本来就按 `unigram_z` 扣过，不再加扣。没有 `sentence_words` 的行和原来一样只按音节扣。同一条切分内的整句也按这个分排先后，整句备选的顺序因此可能变。

## Alternatives considered

- **只做种子，不改打分。** 理由是改动只在切分集合上、不碰任何分数。实测 81 条 top-1 从 0.457 掉到 0.185（挂模型）：种子是按旧分数排在前面的整句取的，旧分数偏爱切碎的词组读法，种子把这些读法一路带下去，正确的前半截反而被挤掉。打分不改，种子是放大器。
- **少扣单字的分（每个单字少扣 5～20）。** 想法是单字被扣得太狠。不挂模型从 0.346 起，实测 5 时不变，10 降 1 条，20（等于只扣词组实际拿到的奖励，旧笔记里试过的那条）降到 0.185：单字一便宜，满是单字的碎读法就冒上来。缺的是「每个词都要付代价」，不是「单字少付」。
- **按音节多扣或少扣。** 不挂模型时每音节多扣 3 到 30、少扣 3，结果完全不动，少扣 30 降 3 条：输掉的那几条里，错的读法本来就比正确读法音节少（`zhei'fei'dang` 三个音节顶 `zhe'ge'di'fang` 四个），按音节调哪个方向都帮不上。
- **把 `PATH_LIMIT` 放大到 96 或 192。** 改动最小，但如上所述留住正确切分的只多 6～8 条，耗时按切分数线性增长。
- **种子留 16 条、每条接 4 条尾巴、频度切分不截。** 81 条挂模型 0.543、不挂 0.407、found 0.667，三项都比现在高一两条，但本机九键只有引擎时每键耗时均值从 5.7 ms 涨到 11 ms，p95 从 11 ms 涨到 25 ms 左右，违背「延迟不能明显退化」。现在的参数在 24/8/3 和 48/16/4 之间按准确率与耗时取了一个不慢于原来的点。
- **覆盖全部数字的整句里每条切分先出一句，同切分的其余几句排后面。** 想让重排模型的九行窗口里多看几条切分。实测 top-5、found 反而下降：种子也从这个顺序里取，前几条切分越分散，束里留下的好前半截越少。
- **数字层统一词网格（[九键整句改由数字层统一词网格解码](../../proposed/feature/2026-10-09-nine-key-digit-lattice.md)）。** 一劳永逸地去掉切分截断，但要新写一套按数字位置的取词与解码，并且仍需上面这条每个词的代价，否则统一网格照样偏爱切碎的词组。这次先在现有结构上把两处缺口补上并量出收益，统一网格留待单独排期。

## Consequences

锁定资源（dict-v2.0.14 加 `sentence-model.safetensors`），MacBook 本机，`convert_eval --nine-key`；「不挂模型」把 `sentence-model.safetensors` 从资源目录拿掉：

| 九键集 | 原来 top-1 / top-5 / found | 现在 |
|---|---|---|
| `sentences-nine-key-v1` 81 条，挂模型 | 0.457 / 0.481 / 0.556 | 0.506 / 0.519 / 0.617 |
| 同上，不挂模型 | 0.346 / 0.457 / 0.556 | 0.395 / 0.506 / 0.617 |
| `sentences-v1` 60 条，挂模型 | 0.383 / 0.450 / 0.500 | 0.400 / 0.467 / 0.550 |
| 同上，不挂模型 | 0.233 / 0.400 / 0.500 | 0.250 / 0.450 / 0.550 |
| `quanpin-words-v1` 3000 条，挂模型 | 0.573 / 0.850 / 0.967 | 0.575 / 0.851 / 0.968 |

- 长句收益最大：81 条里 10 到 12 个字的三档 top-1 从 0.000 / 0.222 / 0.111 到 0.111 / 0.444 / 0.222。词级集没有任何音节档回退。代价是少数中短句的名次后移：5 个字一档少对 1 条，`nk-014`（下午三点见）从第 8 位落到第 17 位，`nk-024`（会议改到明天）从第 5 位落到第 42 位。
- 按键耗时（`rerank_latency --nine-key`，同一台机器上原来与现在交替各跑三次，取中位）：只有引擎每键均值 5.6 → 5.0 ms、p95 11.1 → 9.8 ms；挂模型 10.7 → 9.6 ms、p95 28.0 → 23.5 ms，超过 16 ms 一帧的按键从 28.8% 到 24.7%。长串截短的频度切分抵掉了种子的查询。
- 九键和全键盘还差一截：81 条 found 0.617 对 0.716，top-1 0.506 对 0.691。剩下的主要是三类：仍查不到正确切分的长串（种子束只有 8 条宽，前面几个音节一旦选错就接不回来）；正确切分解出来的整句本身就错、全键盘同样错的 11 条（整句解码和词库）；以及只有语言模型分得清的同码异词（晚饭 / 遭到、早点 / 要点），默认不挂模型时引擎分不出来。
- `baseline-nine-key-sentences.json`、`baseline-nine-key.json` 随本次更新。
