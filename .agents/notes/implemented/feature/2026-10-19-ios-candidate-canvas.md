# Agent Note: iOS 候选条与展开面板绘制 canvas 皮肤

Status: implemented

## Problem

[共享皮肤清单](2026-10-19-windows-skin-schema-parity.md)已接受 Windows 的 canvas 包，但 iOS 只有安全回退配色，没有九宫格与挂件。普通候选条和展开网格需要同一个资源快照，否则展开或切换明暗会丢掉皮肤。键盘扩展不能在每次按键时读盘或解码，也不能因桌面皮肤的大留白把固定高度的候选条挤成零高。

## Decision

`CandidateCanvasAssets.swift` 在共享 Rust 资源 ABI 校验后，在串行后台队列解码 ImageIO 的静态图、APNG、GIF 与 WebP。面板预裁成九张独立图片，切片优先使用 `stretchDip`，一、二、四值按 CSS 展开，源切片用像素、绘制边宽用 DIP。Core Animation 播放离散帧，10ms 及以下归一到 100ms；有限循环保留末帧，无循环扩展的 GIF 播放一轮。

`CandidateCanvasHostView` 为普通候选条和展开面板提供面板下、面板、文字、面板上的层级。挂件按 z 与书写顺序稳定排列，支持九锚点与 contain，图片不接收触摸。资源成功解码后才请求 `canvas_panel_drawn`，失败则保留共享层的可读回退色；贴图配色仍由共享解析器叠加取色器。选中、释义、预编辑和竖条使用共享细分色。候选主题实际明暗决定资源，并遵循 iOS「候选栏使用主题配色」开关。

桌面几何在空间足够时按 DIP 生效；固定高度的候选条统一缩放皮肤几何，优先保留至少 28pt 的候选文字区，放大字号与多行释义增加的高度不让给皮肤，独立读音行与行距另计。展开网格与九键三栏从同一个内容布局指南取得内外留白。最小内容宽高是承载视图的显式参数，小尺寸预览与产品条分别指定；测试不因布局压缩而误把零尺寸挂件当成层级正确。宿主高度不随开始组字变化。

解码只发生在主题、模式、清单或键盘重新出现时，按键复用快照。代次校验阻止旧异步结果覆盖新选择。隐藏、切后台与减少动态效果时撤下帧动画；内存警告丢弃快照和待回调结果，回到可读配色，下一次主题刷新再加载。

## 资源经 base64 读取

`CandidateCanvasAssets` 向 `msime_client_skin_resource` 请求时带 `encoding: "base64"`，读回 `bytesBase64` 再 `Data(base64Encoded:)`。默认的 `bytes` 数组每个字节在共享层是一个 `serde_json::Value`，在 Swift 侧又是 `JSONSerialization` 里的一个数字对象：用 `crates/host-api/examples/skin_resource_memory.rs` 的计数分配器测 1 MiB 的图，共享层建响应时峰值 64 MiB（8 MiB 的图是 512 MiB），base64 是 5.3 MiB；macOS 上用同一份响应测 Swift 侧解析，数组多占约 40 MiB，base64 约 3 MiB。键盘扩展从冷启动到画出第一帧一共才三四十 MiB（见[内存读数](../bug-fix/2026-10-10-ios-keyboard-memory-telemetry.md)），而这次读取在后台队列上、每次键盘出现都会做一遍（`viewWillAppear` 清掉请求键后由 `applyKeyboardSkin` 重新加载）。键盘先画出来、随后系统按内存上限结束扩展、退回系统键盘，正是 #9008 那类现象；这条路径只影响打开「候选栏使用主题配色」并选了带图片皮肤的用户，#9008 的报告者是否属于这一类没有确认。

随后其余调用方也都改成请求 base64：Android 键盘、HarmonyOS 键盘（装饰图、贴图面板、工具栏图）、HarmonyOS 设置页的图片与字体、Windows 设置和 Win7 设置。它们没有键盘扩展那样低的上限，但共享层那份开销与平台无关：单个资源上限 8 MiB，按数组返回时共享层峰值约 512 MiB；Android 的 1 MiB 上限和 HarmonyOS 的 16 MiB 预算都要等整份数组解析完才检查，挡不住这个峰值。HarmonyOS 键盘最终要的本来就是 base64，以前是数组转 `Uint8Array` 再重新编码，现在直接使用；宽高比只解码文件头的前几 KiB。HarmonyOS 设置页面的 `SkinImage` 契约仍是 `bytes` 数组，由 `apps/harmony` 的桥接把 base64 解回数组，页面不变。Windows 候选窗、macOS、Linux 自己读文件，不经这个接口。数组仍是默认值，只为旧调用方保留；未知的 `encoding` 报错，不悄悄退回数组。

## Alternatives considered

- 只显示首帧最省资源，也能让九宫格看起来正常。但上游两款官方皮肤明确使用动态挂件，永久忽略动画不满足兼容目标。
- 每次绘制时从大图裁切最少代码，但会重复分配切片，并可能在相邻色块间采样；资源加载时预裁一次，视图只排列位图。
- 共享层直接把响应写成字符串、跳过 `Value` 树，线上格式不变，所有平台一起受益：共享层的 64 倍能降到约 5 倍。但 Swift 侧解析数字数组的那 40 MiB 一点没少，键盘扩展照样超限；要省掉后者就必须换掉数组。
- 新增一个把原始字节交给回调的 C 函数（像 `msime_client_skin_animation_decode` 那样）：没有编码开销。但它是一个新符号，Swift 要写回调桥，换来的只是 base64 那 1.33 倍；社区接口已经用 base64 传预览图，沿用同一种做法。
- Swift 自己按清单里的相对路径读文件：最省内存。但包的再校验（清单合法、路径不出包、类型与请求一致）就绕过了共享层，`msime_client_skin_resource` 存在的意义正是这道校验。
- 完整保留桌面留白能得到最直接的几何映射，但桌面的外留白加内边距可能超过整个手机候选条高度；统一缩放装饰与边框，把可读文字区作为下限，比提高键盘高度更符合固定高度的输入法约束。

## 未签名测试宿主

`CODE_SIGNING_ALLOWED=NO` 的 CI 测试宿主没有 App Group 容器，真实控制器测试不能把 `ExternalCandidateSkin.defaultRoot` 当作必定存在。控制器接受创建视图前注入的 `candidateSkinsRoot`，主题解析与资源加载一律使用同一个目录，资源请求键也携带目录身份；默认仍使用 App Group。合成皮肤的控制器回归在自己的临时目录安装和删除资源，因此未签名 CI 仍执行它；只在本机暂存上游图片的人工验收用例缺少容器时按前置条件跳过。不能为了跑测试把发布宿主改成使用不共享的私有资源目录。未签名模拟器验证：`CandidateCanvasTests` 与 `CandidatePaletteTests` 共 31 项、0 失败，只有要求本机暂存上游图片的 1 项按前置条件跳过；合成皮肤的真实控制器测试实际执行通过。该修复同时通过原生静态库构建、`verify-local.sh --quick`、笔记校验与差异检查。

## Consequences

普通条、普通展开网格和九键三栏现在绘制同一皮肤，关闭跟随开关、明暗切换和资源失败不会沿用上一份画布。未使用 canvas 的「首选高亮」取色器仍保持既有 `hover` 语义。

代价是单份动画快照仍占用扩展内存，限制为 120 帧、2048 边长和累计八百万解码像素，并复用同路径资源。读取本身经 base64，每张图在共享层和 Swift 侧的临时开销各是图片大小的几倍，不再是几十倍；解码后的帧仍按八百万像素的预算计，最多约 32 MiB，这一项没有变。固定高度的移动候选条会缩小桌面装饰，不能宣称桌面几何逐像素一致。App 的外部皮肤选择器经[原生画布预览](2026-10-20-ios-canvas-settings-preview.md)显示 canvas；通用六词 SwiftUI 主题预览卡仍使用安全配色，未绘制 canvas。本改动也不改变社区后端的资源上传能力。

验证覆盖：UIKit 像素断言检查九宫格方向与边缘采样、二值切片、`stretchDip` 优先、中心不填充、九锚点、contain、前后层、点击穿透与窄尺寸布局。合成 APNG/GIF/WebP 验证帧数、时长、有限循环、帧归一化、像素预算及隐藏／后台／减少动态效果。真实控制器验证逐键复用、展开面板共用和关闭开关清除画布。新增 11 项 canvas 测试已通过。

固定上游 `dd018f79858314ed542a47c528608752b13bd261` 的 `green_leaf`、`sakura-night` 在专用 iOS 27 模拟器验收，明暗 × 全键盘／九键 × 普通／展开共 16 张生产控制器栅格图完成目测。皮肤资源只暂存到模拟器，不复制进仓库；未暂存时该条上游专项明确跳过。原生 `MSIMEApp` 与内嵌键盘扩展 Release 构建通过，本地 quick 已通过；完整 `MSIMEClientTests` 1024 项、7 跳过、0 失败（键盘 835、共享 95、服务 94），跳过项依赖未暂存的注音／笔画或释义数据。最终布局修正后的皮肤、字号、十四键专项 85 项通过；原生包 ad-hoc 签名、安装并在专用模拟器启动，首页截图正常。验证到原生模拟器与生产控制器层，未声称真机或系统编辑器验收完成。
