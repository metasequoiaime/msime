# Agent Note: HarmonyOS 14/18 键宽窄字母键布局

Status: implemented

## Problem

Issue #11051 已在 Android 和 iOS 提供 14/18 键的「等宽 / 宽窄」选择，HarmonyOS 仍按旧的每排铺满布局绘制，也没有读取 `touch_fourteen_key_letter_widths`。同一账号在鸿蒙上因此无法使用已选择的几何，第二排的宽窄空白也会成为不可点击的死区。

## Decision

HarmonyOS 读取共享偏好 `touch_fourteen_key_letter_widths`，缺字段和未知值按既有的 `equal`。新增 `FourteenKeyLetterWidths.ts` 作为键盘侧几何策略：`equal` 保持现有份额，`varied` 使用单字母键 0.75 份、双字母键 1 份，三排共用首排单位宽度。较短的第一、二排两端加入透明占位格，占位格分别把触摸转发给同排最外侧字母键；第三排让分词和删除键分掉两端剩余宽度。双字母键绘制使用 0.15em 字距，双拼 `L;` 使用 0.08em。

账号同步把该共享偏好加入 `TouchHostKeys`，Android 与鸿蒙分别使用 `platform.android.fourteen_key_letter_widths` 和 `platform.harmony.fourteen_key_letter_widths`，避免两台设备互相覆盖；设置预览与键盘按已有偏好使用同一份宽度规则。设置应用顶部的「键盘布局」打开独立 ArkUI 原生面板，提供「等宽 / 宽窄」选择及标题旁的「?」，不在共享设置页增加控件。Android、iOS 已有原生控件的范围不变。

原生面板通过既有共享偏好桥读写，每次选择都重新读当前快照，只修改宽度字段并用修订号比较保存；读取、保存失败和并发冲突均保留权威值并显示重试入口。返回前台重新回读，退出面板时通知已有共享页面刷新，键盘继续沿用原有共享镜像发布及重排链路。`LetterWidthSettings` 的行为测试覆盖缺字段不主动落盘、单字段更新、重开回读、不覆盖其他端更新、保存失败和并发冲突。

原生面板的按钮返回和系统返回都先关闭宽度面板，再强制把当前偏好快照交还已有共享页，不让隐藏页面的历史接管返回。退出与回读复用九键 flick 面板的既有桥接方法，整合 develop 时保留两个原生入口及词库分组的隐私门控。

ArkUI `Text.letterSpacing` 的数字参数单位是 fp，并非 em（[OpenHarmony 官方接口说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/arkui-ts/ts-basic-components-text.md#letterspacing)）。实际按键 options 先把 0.15/0.08 的 em 比例乘以 `TOUCH_LETTER_FONT_SIZE`，再交给组件；直接传 0.15/0.08 fp 无法呈现规定的字距。`letter-width-panel-adapter.test.cjs` 执行真实控件、返回和按键 options 方法，旧实现分别在系统返回与字距换算处失败，修复后通过；既有几何测试继续保留比例断言。

原行容器把占位格也算进 `Row.space`，即使三排份额总数相同，额外的键距仍会压缩短排的单位宽度。独立 `LetterWidthRow` 在宽窄模式按完整键距分配份额，再从实际键帽两侧各扣半份键距；整排多给一份键距并向左移半份，保证首末键帽仍与字母区边缘齐平。占位格不扣键距，继续转发给原外侧键；等宽模式保留原 `Row.space` 及份额。真实行 Builder 回归覆盖 180/320/600 vp、0/3/6 vp 键距、14/18 键及两种模式，旧实现首先在 180 vp、3 vp 键距的 14 键第二排失败；修复后共同单位宽度通过。

`@Builder` 中只保留组件调用，按键份额作为参数交给普通的 `fourteenKeyOptions` / `eighteenKeyOptions` 方法构造。ArkTS 的真实 HAP 编译拒绝在 Builder 分支内声明 `KeyOptions` 变量和赋值；Node 几何测试与 TypeScript 子集检查不能替代这项编译。方法的默认份额仍为 1，长按键外层的份额规则不变。

设置预览按键面中的字母数计算份额，双拼的 `L;` 仍只有一个字母，取 0.75 份；兼带的分号不把它变成双字母键。预览与原生宽度策略的逐排行为对照同时覆盖全拼、双拼的 14/18 键及两种宽度模式，防止预览与实际几何分叉。

宽窄字母排给预览格附带 `letterPitch` 标记，「按键布局」的 HTML 预览和尺寸、皮肤、社区卡片的 SVG 预览都按含键距的份额分配，再从真实键帽扣一道间距；占位格只推进份额坐标，不再额外增加间距。数字行、底行、等宽及其他键盘保留原绘制规则。SVG 行为测试读取真实路径边界和文字中心，在全拼、双拼 14/18 键及非零键距下检查三排共同单位和相邻键帽间距。

## Alternatives considered

- **只在 `KeyboardView.ets` 中为第二排加固定空白。** 这样可快速改变视觉，但无法复用到设置预览，也无法给第一、三排计算同一单位宽度，容易重新产生死区，因此采用独立几何策略并让占位格拥有按键动作。
- **把偏好放进 Android 命名空间让鸿蒙直接读取。** 这样会让鸿蒙读取另一台设备的宿主设置，违反触屏宿主按平台隔离命名空间的同步约定，因此增加鸿蒙自己的同步键。

## Consequences

键盘和设置预览的三排宽度会随偏好即时重排，组字状态不被打断；双字母键面更容易辨认，第二排空白仍可输入。共享偏好字段、几何策略和原生面板增加了跨文件维护面。设备连接及签名状态以实际检查为准；新增面板的完整 HAP 编译、触摸转发、字距、原生设置页及前后截图按层级分别验收，实际构建与真实宿主证据列在 PR 验证段。按维护者当前授权不保留 Draft，满足门禁后正常合并。

2026-11-18 在 HarmonyOS 6.0.2/API 22 手机模拟器安装同源 HAP，原生面板的问号说明、宽窄保存、按钮返回、系统返回、前台回读、冷启动回读及恢复等宽已通过，入口改前/改后与面板截图保留。模拟器不提供设置应用与输入法扩展的共享沙箱，设置应用选择 14/18 键后，扩展仍使用自己的 26 键配置；这与既有[共享沙箱约束](../architecture/2026-10-09-harmony-ime-shared-sandbox.md)一致。本轮未修改扩展私有偏好、未注入文本，不把 26 键截图当作网格验收；14/18 键实际重排、透明占位触摸与跨沙箱联动仍未验证。
