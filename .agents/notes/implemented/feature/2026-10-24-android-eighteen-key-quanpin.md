# Agent Note: Android 十八键全拼入口

Status: implemented

## Problem

#8892 希望 Android 全拼提供比二十六键更宽的按键，并能选择布局。现有十四键已提供完整组码与消歧入口，共享引擎也已支持十八键全拼，但 Android 原生键盘尚无十八键全拼的偏好、方案卡片与键面接线。

## Decision

在全拼既有二十六键、十四键、九键选择中追加十八键，并提供独立、默认不启用的 `eighteen_key` 触屏入口。复用 `KeyGrid::EighteenKey` 和编号 4 的 C ABI，字母组固定为 `Q WE RT Y U IO P / A SD FG H JK L / Z XC V BN M`。点按发送多义组码，实体键盘仍发送确定字母，组词、读音锁定和候选归共享引擎。

原生键面复用十四键的符号与拼音侧栏、三栏候选、分词、长按、底行和数字层。三排采用七份宽度，第二排居中，第三排加上分词和删除后同宽；窄屏文字保持单行。布局可在设置中切换和恢复，英文、密码和本地模式沿用确定字母的回退路径。

只在 Android 自动启用十八键全拼。其他宿主原样保留新增偏好，暂不画出未接线的键面。保留现有出厂默认值与启用列表，不增加十七键或任意可编程布局；这些需要额外的明确分组与行为契约。

## Behavior coverage

原生设置可在二十六、十八、十四、九键之间选择；重启后保留选择。十八个键覆盖全部字母，触屏多义组码与实体确定字母分路；可以选择读音、撤销锁定并提交候选。英文、密码和 URL 回落可用，数字层返回十八键。API 28／35 的真实键面和窄屏、横屏、浮动、单手几何均已通过专项验收；默认列表不增加入口。

## Historical audit

- [共享十八键全拼](../../implemented/feature/2026-10-24-eighteen-key-quanpin-engine.md)：部分重叠，直接复用已合并的算法与编号；Windows 的原生接线仍由 #8936 单独跟踪。
- [十四键全拼](../../implemented/feature/2026-10-10-fourteen-key.md)：部分重叠，沿用组码、确定字母和候选身份边界，不翻转已有布局决定。
- [Android 拼音侧栏](../../implemented/bug-fix/2026-10-13-android-fourteen-key-left-spellings.md)：部分重叠，复用已有纵向拼音选择，不重新引入增加键盘高度的独立拼音行。
- #9124 的 PR #9530 实现十八键双拼；#8930 另请求双拼与精确滑动字母。它们不属于本 issue，本分支不复制双拼算法、不自动关闭其他 issue。

## Alternatives considered

**只把两个字母印在键上并发送首字母**：可直接复用普通字母按键，但另一个字母无法参与候选，所以使用共享组码入口。

**在 Android 保存音节表和组词状态**：可以独立调整触屏行为，但会复制引擎算法、学习与候选身份，跨越架构边界；Android 只负责键面和输入来源。

## Consequences

新增入口由用户选择，出厂布局与启用列表不变。复用十四键的组码展示和共享引擎消歧，避免宿主保存另一份拼音状态；代价是统计来源和键位白名单跨端追加，同时维护旧来源的顺序与读取兼容。十八键双拼的并行 PR 会改到相同的网格展示代码，整合时需要保留两个 issue 各自的方案入口与验收记录。

## Risks

加权键行在两级设备按实际边距和宽度检查，保留 2 像素误差上限，单看权重不足以证明第二排与其他行同宽。统计白名单在四端独立声明，由离线键表契约防止新增键被丢弃。十八键双拼与全拼共用分组，但设置和路由分别归各自 issue。

## Verification

先记录缺少原生入口和偏好识别的失败，再实现设置、宿主与布局。验证包含共享偏好与平台门控、Java 键表和入口、API 28/35 实际设置与组字、消歧、提交、布局切换及几何。复用已完成任务的标准远端构建缓存，不新建本地 Rust 或原生构建树；完整门禁与设备结果按实际执行范围更新。

已记录入口、共享偏好、宿主门控、统计来源与键面标签的初始失败；新增 Rust 专项及账号布局往返通过，离线键表／四端统计契约通过。Android 266 项 JVM 冒烟、234 份设备源码编译及 Java/JNI、清单、资源检查通过。client-core 534 项、host-api 945 项通过（另 5 项忽略），相关前端 35 项、类型检查和 HarmonyOS 键盘逻辑检查通过；远端 quick 门禁通过，Apple 原生和真实 ArkTS 构建因环境未就位而跳过。

API 28 在原 APK 的真实设置中确认缺少十八键选项。新 APK 已通过设置保存、组码提交、读音锁定与撤销、分词、展开候选、英文／数字／实体字母和密码／URL 回退；初次几何验收在左手模式发现中排宽 95 像素、首排宽 92 像素。中排只有六个字母键，普通半权重占位未计入第七个键的横向边距；在每次应用几何时由两端占位各保留半个键的边距预算，保证键距就地变化时也更新。修正后 API 28／35 的完整十八键专项均通过；竖屏、720×1280 窄屏、左手、右手、浮动和横屏六种几何全部满足原来的 2 像素误差上限，两级共十二张键面截图已逐一检查。

专项复用 `FourteenKeyDeviceSmoke -e eighteen_key true`，不增加 instrumentation 清单项，并接入 `smoke.sh` 的 API 28 核心和 API 35 完整路径。长按 WE 选择确定字母、L 无多字母长按菜单、本地 Unicode 模式退出、设置重启和布局回退也在同一专项通过。API 28 整套冒烟随后在既有拼写放大编辑的中间插入断言失败：输入框实际为 `nhi'hao`，测试仍要求原始拼写 `nhihao`；放大条实际保留完整 `nhihao`。同一 APK 的单独放大编辑专项复现相同结果。按既有 `CandidatePreeditStylePolicy.inlineSpelling` 和 JVM 契约更新设备夹具的显示预期，仍核对完整字符串、退格撤销和长拼写两端，不删除断言。修正后的 API 28／35 完整放大编辑专项均通过，覆盖中间插删、九键、偏移手柄和长拼写双端；API 35 首轮停在合成编辑器 ANR 弹窗，尚未执行新断言，关闭该测试应用并重新观察恢复原生设置后，单独复验取得通过标记。

API 35 整套冒烟在十八键专项末尾的原生布局恢复步骤报告 `native quanpin layout select 26 键` 未找到控件，尚未完成整套验收。此前独立专项的成功不替代整套结果，保留失败日志继续定位。后续单独重跑在浮动几何阶段未找到合成控件；截图显示编辑器已出现但没有输入法窗口，设备 crash buffer 没有崩溃记录，尚不足以归因于产品或测试启动时序。

API 28 上四个共享 crate 的完整 Android 单测通过：base 36 项（另 2 项忽略、3 项硬链接过滤），core 533 项（另 1 项忽略），providers 254 项（另 2 项忽略），services 主进程 1250 项（另 10 项忽略、4 项子进程用例过滤，子进程分别通过）。API 35 的 base、providers、services 同样通过；core 最初两次在 `resources::tests::a_recorded_verification_only_matches_the_files_it_recorded` 失败，532 项通过、1 项忽略，改写文件前后记录的时间戳相同。夹具原来依赖固定等待 20 毫秒，现在同长度改写后用既有 `FileTimes` 模式显式推进修改时间 2 秒，产品校验逻辑和拒绝断言保持原样，不增加失败豁免。远端宿主原测试通过，重新交叉编译的完整 core 程序在 API 28／35 分别通过 533 项、忽略 1 项。本机 iOS 统计文件仅完成 Swift 语法解析。PR #9564 的 CI 已构建共享 Apple 桥与 iOS 测试宿主；唯一报告断言失败的用例是 `TypingStatisticsTests.testKeyIDsAreTheSharedWhitelist`：实现已追加十八个键位，但三处测试仍要求 141 个，实际为 159 个。在 `1974adac95` 同步这三处预期，保留逐键可记录和未知键整批拒绝断言；该提交的 iOS 原生 CI 和 macOS arm64 CI 均通过。后续 Android 夹具提交仍等待各自新 HEAD 的 CI，不把修正前的运行或旧 HEAD 的结果记为新提交通过；x86_64 与 sanitizer 仍按分支范围跳过。

完整 services 套件暴露的账号会话采用断言，在未修改的基线 `d364cf00af28d9f9019c9fd581fbd453fa00be53` 也会失败，不作为本功能已通过的验证。HTTP 重定向用例受远端代理影响，测试进程清除代理后通过。基线与功能的对照复用同一个标准 Cargo 目录；切回功能源码后刷新源文件时间，避免解包保留旧时间而错误复用基线编译产物。

API 35 按仓库流程预先启动原生设置，再以 `--no-restart` 附着产品进程；失败时截图确认原生键盘设置已打开，但被 `Quickstep isn't responding` 弹窗遮挡，未到十八键选择步骤。以当时的可访问性树定位并点击「等待」后弹窗仍在；刷新观察后点击「关闭应用」，再截图确认原生设置恢复正常，随后同一 APK 的完整十八键专项通过。保留失败截图作为环境状态证据，不将等待按钮点击本身记为恢复成功。

本轮更新夹具后的远端 `verify-local.sh --quick` 通过，包含 Rust、Android、Wasm、Java/JNI、共享前端和 Linux 宿主门禁。Windows 原生、Apple 原生及真实 ArkTS 构建仍按实际环境跳过。两级设备安装的产品和测试包 SHA-256 均与本任务的本地产物一致，避免将其他会话换包后的结果混入。
