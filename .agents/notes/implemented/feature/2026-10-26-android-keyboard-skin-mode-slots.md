# Agent Note: Android 键盘皮肤按明暗分别选择

Status: implemented

## Problem

Android 皮肤页只列出当前明暗可用的内置主题，但卡片没有说明适配范围。`global_theme` 及 `custom_theme.keyboard` 各只有一份，浅色时选一款键盘皮肤会覆盖深色时的选择。已有的 `candidate_skin` 和 `candidate_skin_dark` 是候选窗皮肤包标识，不能存键盘主题或设计。

## Decision

在共享偏好里增加 Android 键盘专用的浅色、深色选择，每槽保存内置主题标识或本机设计库 id。选择设计前先确保设计已保存入库，避免一份偏好文档里复制两张照片。缺槽时读取现有的 `global_theme` 和 `custom_theme.keyboard`，保留旧偏好、旧版本以及现有明暗不匹配时回退 `system` 的规则；引用的设计从库中消失时也回退。Android 皮肤页分别编辑两个槽位，并清楚标注内置主题的适配范围；社区及本机设计在两种模式都能选择，但同一份设计的配色不会自动转明暗，界面标示为固定外观。键盘及其皮肤选择器按键盘实际明暗读取槽位，候选窗、表情、手写继续按现有全局主题读取，两个候选皮肤包槽位不变。候选按钮原先在没有外部候选包时从键盘 `skin` 取选中色，设备测试证明单独换键盘皮肤会连候选 chip 一起改色；现在统一从 `candidateAppearance` 取色，使候选窗沿用自己的全局主题。Android 云同步为新选择分配独立字段；服务端字段表尚不认识时，本地选择仍可用，老账号设置兼容。设计库现有云同步导出不包含照片，所以别的设备缺少照片时按已有的无照片设计呈现。

沿用[固定明暗主题的显示与回退决定](2026-10-11-skins-follow-dark-mode.md)：当前模式只列可用的内置主题，社区与本机设计两边都列，跨模式或缺失引用时不清除用户原有的选择。

## Alternatives considered

- **直接复用 `candidate_skin` 两槽。** 这两个值是候选窗包的目录标识，键盘设计是完整 JSON。复用会同时破坏候选窗和键盘两端的解析。
- **切换模式时覆盖 `global_theme`。** 不用增加字段，但会丢失另一种模式的选择，也无法在系统切换后自动恢复。

## Consequences

- 收益：皮肤页标注适配范围，并可独立查看、选择浅色和深色键盘皮肤；两种明暗来回切换时各自恢复，无新槽位的旧文档保持原行为。候选窗皮肤包选择和其它平台行为不变。
- 代价：键盘选择不再同时改变候选窗皮肤；与键盘皮肤有关的 Android 入口都要写模式槽位。设计库引用失效时回到旧全局主题，照片不能通过现有设计库云同步传到另一设备。
- 首帧皮肤提示只保存短引用；键盘进程冷启动时，设计库在偏好工作线程读完之前可能短暂显示旧全局主题，随后原地重绘。内置主题引用无需读库。
- 验证：`platforms/android/check-host.sh` 的 279 项 JVM smoke 和设备测试源码编译通过；四个核心包的整套 Rust 单测已在 API 28 模拟器运行，`ThemeModeDeviceSmoke` 在安装的原生 APK 上通过浅深浅切换、皮肤筛选、候选配色和表情独立明暗检查；`bash scripts/verify-local.sh --quick`、`pnpm run verify-notes` 通过。API 28 的完整 `smoke.sh --core` 因本地 APK 未暂存粤拼、注音和笔画词库而没有跑完；基础 `DeviceSmoke` 已通过，皮肤专项另行通过。API 35 和报告者设备尚未验收。

偏好文档只有 1 MiB 上限，而一份设计里的合法照片可达 512,000 字节；两个槽位只存短引用。设计库删除、导入和账号同步后引用可能失效，解析时无副作用地回退。
