# Agent Note: 自建存储个人词库同步方案

Status: implemented

## Problem

#9880 要求在多个平台之间通过自选存储同步个人词库，明确同步对象、冲突合并、删除传播和凭据保管。现有账号云词库绑定水杉账号，而且合并模式只加词、不传播删除；[WebDAV 云剪贴板](2026-10-26-cloud-clipboard-webdav.md)和自建中继处理加密剪贴板，没有离线合并语义，不能当作词库同步已经实现。#9989 也提到常用词库，剪贴板那部分见 [自建存储云剪贴板同步方案](../../proposed/feature/2026-10-27-clipboard-self-hosted-sync.md)。

难点在于网盘没有服务端逻辑，设备会长期离线、随时崩溃，Engine 的个人词库又有十几条写入路径（设置页、导入、MCP、候选栏删除、集合、账号云词库合并、打字自动造词），而且不区分用户显式加的词和打字自动造的词。坚果云免费账号每 30 分钟 600 个请求、与所有第三方应用共用，`If-None-Match` 被忽略，`GET`/`HEAD` 没有 ETag，根目录下的文件夹删不掉。

## Decision

维护者已定：只同步「我的词条」；端到端加密并复用云剪贴板的设备批准；六个平台都能驱动同一个核心；自动加手动触发；首版只做 WebDAV（坚果云、Nextcloud）。契约（存储布局、记录、合并规则、上限、请求量、宿主接入）写在 [`docs/dictionary-webdav-sync.md`](../../../../docs/dictionary-webdav-sync.md)，这里记各项怎么定的、为什么。

协议和共享核心已经落地：不碰网络和 Engine 的状态机在 `client-core::cloud::dictionary_sync`，WebDAV 传输和词库密钥串在 `client-services::dictionary_webdav`，Engine 一侧的本机词库和 C 入口 `msime_client_dictionary_sync` 在 `host-api`。各平台的界面和触发接线按平台各开 PR。

### 同步对象

同步的是「我的词条」列表里看到的那些：Engine 日志里 `user_inserted` 的词条，以及它们的删除。打字自动造的词也在里面——Engine 对它们和用户显式加的词写的是同一种行，列表里也不区分，要排除就得先改 Engine 的写入格式，首版不做；被同步的只是词本身，打字学到的权重、候选顺序、固定位置、选择次数一律不同步，符合「不同步打字学到的频率、权重和顺序」。身份是（词库类别、编码、词），类别就是 Engine 的五个词库（`pinyin`、`wubi`、`wubi98`、`quick`、`english`），这也是「词条所属的词库类别」的含义；用户命名的词条集合是 client-services 自己的元数据，首版不同步集合本身，集合里的词照样作为词条同步。对主词库词条的删除和改权重属于主词库，不同步。

### 时钟与冲突

每条操作带混合逻辑时钟时间戳：高位 Unix 毫秒、低 10 位计数，整个值不超过 2^53 - 1。本机生成取「比见过的都大、不早于本机时间」；收到操作就把本机时钟推到它之后，从检查点开始时推到检查点里最晚的时间戳之后；时钟随同步状态原子写盘，重启和系统时间回调都不会倒退；不在合法范围的时间戳整条跳过；快于本机一天以上只提示、不改合并。重装是一个新的设备编号，第一次加入前先读完日志或检查点再记录本机的词。

每个词条是最后写入者胜的寄存器，删除也是写入（墓碑），按（时间戳、设备编号、是否存在）比较；平局时设备编号大的胜，同一设备同一时间戳「存在」胜过「删除」。合并与到达顺序无关、重复合并不改变结果。改编码就是删旧加新。合成示例（文档里有完整的表）：B 10:00 改编码、A 10:05 删旧词条，结果旧词条删除、新编码保留；同一词条一删一加，晚者胜，与谁先上传无关。

### 发布、恢复与版本

一个事件一个不可变文件 `e-<12 位序号>.json`，独占创建下一个序号（`PUT` 临时名加 `MOVE` 带 `Overwrite: F`，与云剪贴板同一条代码路径），没抢到就重读再试。事件用哈希串成链；本机读过的最后一个事件消失、列表跳过一个直接 `GET` 也不存在的序号、检查点的位置或代数变小，都是 `dictionary_sync_rollback`——链头只挡得住改写，挡不住截掉尾部，后两条是为此加的。重复操作靠（设备、时间戳）认出：本机写成的事件在下一次读到时从待发送里去掉，所以发出之后、写盘之前崩溃不会重发。`format.json` 版本不认识就不读不写；已经在运行的客户端靠带 `upgrade` 的封口事件得知格式升级。

本机的应用顺序是：记录本机改动并写盘 → 拉取并与位置一起写盘 → 分批写进本机词库、写好才计入 → 发送 → 封口和清理。远端改动在写进 Engine 之前只存在于共享状态里，本机确认的位置只在 Engine 写好之后推进。每项写入带一个由操作唯一决定的请求编号，Engine 的回执让重试幂等；Engine 删不掉的词照实留着、不再重试，免得下一次核对把它当成本机新加的词发出去、在所有设备上复活。上限：一个事件 1000 条操作、明文 256 KiB、文件 512 KiB；检查点 32 MiB、30 万个词条、64 台设备；列目录 2 MiB；共享词库 10 万个词条以内收新词；待发送 2 万个词条；一次写进 Engine 128 项。

### 捕获本机改动：三方核对而不是在写入点挂钩

本机记着「认为本机词库里有哪些词」（`applied`）。本机词库相对它的变化是本机改动，记成操作；共享状态叠上待发送操作相对它的变化，是要写进本机词库的远端改动。宿主在用户改词后马上以 `local_change` 调一次，只做核对、不联网，时间戳因此接近改动发生的时刻；每次同步开始前也核对一次，漏掉的通知不会丢改动。核对读的是 Engine `stream_dictionary_state` 在一个读事务里给出的一致视图。一次核对里少了 50 个以上、且至少一半的词时先挡下删除，由用户选择同步删除或从网盘恢复：词库被重置或损坏时不能把其他设备上的词也删掉。

### Engine 集成

状态机只经 `LocalDictionary` 接口写词库，一次一批，每批之前取独占维护权、写完就放，从不跨网络请求持有；跨批保留的输入法让出租约在这一轮写完、联网之前由 `release` 撤掉。拿不到维护权时，Linux、macOS、Windows 在用户手动同步、打开设置和设备操作时经 `QuiescedHosts` 请输入法让出词库（50 毫秒间隔、2500 毫秒预算、租约 30 秒）；自动同步和移动端不打扰输入会话，直接答「忙」，这一轮不写，5 秒、30 秒、2 分钟、10 分钟后再试（不联网），拉取和发送照常。加入用默认权重并且总是写成用户词（主词库里有同样的词也写一行，否则它不会出现在这台设备的列表里，下一次核对会当成本机删掉了），删除带上刚读到的权重，权重被打字学习改了就重读一次再试。整个调用由宿主放在工作线程上，输入线程从不等网络。

### 加密、设备与压缩

词库有自己的密钥串：云剪贴板端到端加密协议的另一个实例（同一个驱动、同一个日志核心、同一个虚拟中继），放在 `msime-dictionary/keyring/`。实现上它就是一个给每个请求路径加上这个前缀的传输，云剪贴板的代码不知道自己被放进了别的目录；全部用法收在 `KeyRingAccess` 一处，云剪贴板的驱动改了（例如 #10032 的重复登记修复）只影响那一处。密钥串只交出 `HKDF(K, "msime-dictionary-v1-key")`，不交出 `K` 本身；事件和检查点的子密钥再由它派生。不与剪贴板共用同一份批准，理由见下面的备选方案。

设备身份是这份密钥串里的设备编号：一个安装一份密钥串，所有进程给同一个目录、整次同步持有同一把锁，读不到才生成，登记按编号进行、重复登记只更新名称，批准方看到的每台设备只有一条；日志的设备表同样按编号记。模拟测试覆盖「两个进程共用一份状态、写多少次都只有一条」，传输测试覆盖「同一个安装的两个进程同时第一次使用、反复同步，批准方只看到一条等待中的设备」。

移除设备时密钥串换钥并在日志里宣布移除，持有新旧两把密钥的设备封口当前 epoch、用新密钥写下一个 epoch 的检查点；被移除的设备读到封口为止。持有旧密钥的设备都不在了时，用户可以「以本机为准重新开始」：新的共享词库编号，其他设备按第一次加入合并，不删词。

一个 epoch 攒到 64 个事件或 8 MiB 封口，下一个 epoch 从加密的检查点开始，旧 epoch 10 分钟后删除。墓碑在封口时回收：参与确认的是没被移除、在日志里最晚一次写入之前 90 天内出现过的设备，它们确认位置的最小值以内的墓碑删掉。确认游标的因果范围是「这台设备的本机词库已经持久地写到了这个序号」。长期离线的设备从最新检查点重新开始，按 `applied` 与检查点比较得出别处的删除。

### 本机状态与响应字节预算

本机状态读取和写入都受 64 MiB 预算约束，序列化后先检查再原子替换，超限答 `dictionary_sync_too_large` 并保留上次可读文件。词条数量合法不代表字节数够小：1 万条各 4096 字节的快捷短语同时出现在 `applied` 和 `outbox` 时就超过预算，不能先写出无法再读取的状态。用户删减本机新增内容后可以继续同步。预算不扩大，避免把读取与内存开销转嫁给移动宿主。

成功 HTTP 正文读取失败必须作为失败交回；只有有界读取报告 `InvalidData`（超过字节上限）时才标记为 `TooLarge`，其他传输错误仍为 `Unavailable`。这覆盖 chunked 和没有 `Content-Length` 的响应，防止把坏文件当空文件跳过并持久化错误日志位置；非成功 HTTP 状态保持原有鉴权和退避语义。

检查点的 32 MiB 同时约束生成和读取。合法的 4096 字节快捷短语约 6500 条就会超过它，不能仅靠 10 万词的条数上限。普通压缩在封口前生成下一 epoch 的检查点预检，超限则保留当前日志继续写，后续删除和确认使状态缩小后再压缩；每轮先发送本机改动，再做普通压缩。换钥仍先压缩，超限返回 `dictionary_sync_too_large`，不继续用旧钥发送；用户须用仍持旧钥的设备删减词库并同步后再换钥，或用较小的本机词库重新开始。重新开始也在写封口前生成、检查完整检查点；超过上限时不留下封口或新目录。补写别人已封口的检查点同样检查大小，防止发布其他设备读不了的文件。

### 触发与请求量

每台设备每 30 分钟自动同步最多 40 个请求（密钥串的请求也算在里面），加上手动最多 60 个，三台设备用满只占坚果云配额的三成。改词后防抖一分钟（一直改时最多十分钟）、两次自动发送至少隔五分钟；打开设置时拉一次（一分钟内不重复），宿主活着时每 30 分钟拉一次；「立即同步」不受防抖限制。连不上按 1、2、5、10、30、60 分钟退避，限流等 30 分钟，需要用户处理的错误自动同步停一小时。宿主每次调用都拿到下一次该什么时候再调用，不用自己算。

### 偏好与凭据

偏好是 `dictionary_sync_webdav {url, username, password}`，规则照 `cloud_clipboard_webdav`，两者各配各的：应用密码进凭据清单，账号在诊断里换成 `<redacted>`，整组进 `LOCAL_SECTIONS`，不进账号设置同步和 MCP。本机同步状态只记网盘地址和账号的摘要，不记凭据；测试证明网盘文件不含凭据和词条明文；本机状态含词条明文但不含凭据，调试输出也不打印凭据。

### Windows 宿主（含 Win7）

Win7 词库同步面板关闭时只撤销窗口投递、丢弃尚未开始的任务并唤醒工作线程，不在 `WM_DESTROY` 等待网盘请求。线程以共享状态保留正在使用的服务、偏好快照和同步请求，当前调用返回后自行退出，不再触碰已销毁的窗口。否则离线或网盘缓慢时关闭窗口会把界面线程卡到全部请求超时。

触发分在两类进程里。自动的两种在 Server：它一直活着、持有输入会话，候选菜单的「删除」和维护快捷键删词之后以 `local_change` 记一次（只记录、不联网，连着几次只记一次），启动两分钟后第一次 `periodic`，之后照回答里的 `next_check_ms`（夹在 1 秒到 30 分钟之间，与共享设置页相同；调用本身失败时半小时后再试）。这些都在 `DictionarySyncWorker` 自己的工作线程上，不在输入线程、管道线程或消息循环上；偏好里没配网盘时线程只等着，偏好发布时配上就十秒后开始、清掉就停。只有受管理的 Server 做，预览实例不替用户联网；Win7 的 Server 是同一份代码。用户在等着看的两种由设置窗口调：进入 WinUI 词库页「云端词库」标签（或打开 Win7 词库同步面板）时 `opened`，「立即同步」是 `manual`；设置窗口经 `msime_client_settings_dictionary` 改了词之后也自己记一次 `local_change`，与共享页的 `withDictionaryChangeNotices` 相同。Win7 设置窗口的导航不收云端同步的页面，所以 Win7 的配置与设备管理放在独立面板 `--route=dictionary-sync`，与云剪贴板一样，由设置窗口词库页的按钮打开。

一个安装只有一份设备身份：同步目录是本用户的 `%LOCALAPPDATA%\<本版本的用户目录>\dictionary-sync`，Server、WinUI 设置、Win7 设置和 Win7 面板都调 `common/DictionarySyncDirectory.h` 的同一个函数。两个进程第一次使用时同时生成身份由 Rust 的文件锁和「不覆盖另一个身份」挡住；仍然报 `clipboard_keystore_conflict`（#10032 的约定：已经发出请求之后才发现存储里是另一个身份）时，宿主用同一个请求再调，最多三次（`common/DictionarySyncRetry.h`），第二次就会用存着的那份身份。

### iOS 宿主

- **入口和触发**：设置 App「词库 → 词库同步」（`DictionarySyncView.swift`），表单的做法照 iOS 云剪贴板的网盘填写页：应用密码遮罩、不回显、留空沿用，「测试连接」只测不存，「保存」先测、通过才写 `dictionary_sync_webdav`，不通过时填写页和草稿都留着。`DictionarySyncCenter` 在 App 回到前台时以 `opened` 调、在前台时按 `next_check_ms` 以 `periodic` 再调，进后台就停；iOS 不让 App 在后台常驻，App 关着的那段时间里别处的词等下次打开 App 时写进来。每个调用都在专用线程上，期间用 `beginBackgroundTask` 保持后台执行，挂起时不会还拿着 App Group 里的文件锁（0xdead10cc）。
- **键盘扩展只记录、有条件地记录**：应用了 App 排队的编辑、或者候选栏「删除词条」之后，`KeyboardDictionarySync` 在 `performExpiringActivity` 里以 `local_change` 调一次，连续的改动合并成一次，从不在输入线程上等。只在有完全访问、目录里已经有 App 留下的同步状态和密钥串、状态文件不超过 2 MiB 时才调：`run` 把整份状态和「我的词条」读进内存，键盘扩展的内存上限远低于 App，而 2 MiB 的状态大约对应几万个词；没有密钥串时不调，于是键盘从不生成设备身份、也不替 App 第一次登记。其余情况留给 App 下次打开时的那一次同步来记（时间戳是那时的）。拉取和写入远端改动不在键盘里做：键盘自己的会话占着词库，移动端遇到「忙」本来就留到下一次。待发的改动放了十分钟以上时 Rust 会让这一次 `local_change` 顺带发出，所以键盘里偶尔会有几个请求；它们同样在后台执行时间之内。
- **目录和密钥串**：App Group 容器里的 `dictionary-sync/`，App 和键盘给同一个目录。目录建成 0700、文件保护设为「首次解锁后」（Rust 之后建的文件继承它）、排除在设备备份之外，与云剪贴板网盘缓存的 `cloud-clipboard-relay/` 相同。词库密钥串按核心的存储契约是 Rust 在这个目录里写的 `cloud-clipboard-relay-keystore` 文件（只有本应用可读），不进钥匙串，理由见下面的备选方案。
- **一个安装一个身份**：App 和键盘用同一个目录，Rust 整次同步持有 `dictionary-sync.lock`、在锁里「读不到密钥串才生成」，两个进程第一次同时用也只有一个身份；键盘又只在密钥串已经存在时才调。设备列表按设备编号再去一次重，每台一条。

## Alternatives considered

- **与云剪贴板共用一份密钥串和批准** — 最强的理由是用户只批准一次，两个功能看到同一份设备列表。不用：剪贴板的生命周期会直接伤到词库——关闭云剪贴板会删掉全部密钥、封装和设备登记，「重置云剪贴板」会换钥并清空；它的空间绑定的是 `cloud_clipboard_webdav` 的地址和账号，词库就得强制要求同一个网盘账号；Android 的剪贴板密钥串由 Java 用 AndroidKeyStore 保存，iOS 和 HarmonyOS 的宿主还没接中继，共用就要先把这些宿主的剪贴板密钥串接进词库同步。复用代码、分开实例，换来两个功能互不牵连，代价是用两个功能的设备要批准两次。
- **在每个写入点挂钩产生操作** — 最强的理由是时间戳精确等于改动时刻，也不用比较整个词库。不用：写入路径有十几条，跨 host-api、MCP、会话里的候选删除、集合和账号云词库合并，漏一条就静默丢同步；挂钩写在 Engine 提交之外就有「提交了但没记下操作」的崩溃窗口；日志表只记每个词条的当前状态和秒级 `updated_at`，没有可以接着读的序号。三方核对只依赖「本机现在有哪些词」，任何路径的改动都覆盖到，崩溃后重新比较就能接上。
- **每台设备各写自己的目录** — 最强的理由是写入不会争抢序号，也不需要独占创建。不用：读一次就要对每台设备的目录各发一个 `PROPFIND`，设备一多就吃掉坚果云的配额；单一日志一个 `PROPFIND` 就看到全部新事件，哈希链和压缩也只有一条。
- **按到达日志的先后决定胜负，不要时钟** — 最强的理由是简单，日志本身就是全序。不用：离线设备回来时，它几天前的旧修改会盖掉别人今天的修改；用时间戳比较，结果与谁先上传无关。
- **向量时钟识别真正的并发** — 最强的理由是能区分「先后」和「并发」，并发时可以选择保留词条。不用：每条记录的大小随设备数增长，而墓碑回收和设备淘汰会让向量越来越难维护；既然冲突规则本来就是最后写入者胜，混合逻辑时钟已经足够，并发的平局也有确定的结果。
- **身份只用（类别、词），编码作为值** — 最强的理由是两台设备同时改编码只会留下一个。不用：同一个词有多个编码是常态（多音字词、简拼和全拼），用户会显式加好几个；把编码当成值就只能留一个。
- **只提高检查点读取上限** — 能立即容纳当前复现的词库，但合法词条大小与数量的组合仍会超过新的固定值，读取端的内存预算也随之提高；保留既有上限，在不可逆的封口前检查，并允许用户先同步删减。
- **墓碑永不回收** — 最强的理由是任何离线多久的设备回来都能正确判断删除。不用：删除只增不减，检查点会一直变大；回收加上「长期离线设备从检查点按本机记录比较」已经能正确传播删除，只在超过 90 天离线又改过同一词条时复活。
- **iOS 把词库密钥串放进钥匙串，与云剪贴板的中继密钥串同等保护** — 最强的理由是 iOS 云剪贴板评审时定下的标准：密钥串不弱于账号那份，拿到容器文件不该就拿到设备私钥。没有采用：词库的密钥串整个由 Rust 在 `KeyRingAccess` 里驱动（云剪贴板的中继在 iOS 上是 Swift 跑驱动循环、Rust 只发请求，所以能把密钥串放在 Swift 的钥匙串里），要改放钥匙串就得先在 host-api 加一个由宿主注入的密钥串存储，六个平台的 C 入口一起变，而 Android 的词库密钥串同样是 `noBackupFilesDir` 里的文件。这一版在宿主一侧做到能做的：0700 目录、只有本应用可读的文件、首次解锁后的文件保护、不进备份（于是不随备份到别的设备）。要与钥匙串同等，需要先改共享层。
- **自动同步也请输入法让出词库** — 最强的理由是桌面端别处的改动能及时写进来，不用等打开设置。不用：每 30 分钟和每次改词后都让所有输入会话让出一次词库，会打扰正在打字的用户，而远端的词晚一点出现并不丢；只在用户等着看结果的时候（手动同步、打开设置、设备操作）才这样做。
- **直接同步数据库或 Rime `sync` 目录** — 可复用现成文件同步工具，但数据库版本、并发使用和删除传播无法因此获得一致契约，不作为首版路径。
- **复用水杉账号云词库 API** — 已有认证和分页代码，但不能满足用户自选存储，也不能把个人词库自动改发到账号服务。
- **首版同时支持 WebDAV、S3、OneDrive** — 覆盖面更大，但会同时扩散认证、发布、重试和错误语义；日志格式与传输无关，以后加 S3 只需另一个独占创建的实现。

- **Windows 的同步目录直接用账号目录 `account`（云剪贴板中继密钥串所在的目录）** — 最强的理由是任务要求「照云剪贴板中继的选择」，所有进程都已经知道这个目录。不用：词库密钥串的文件名同样是 `cloud-clipboard-relay-keystore`，放在一起两个功能会读写同一份身份和封装，正是上面「分开密钥串」要避免的；所以照中继的选择取同一个父目录（本用户的 `%LOCALAPPDATA%\<本版本的用户目录>`），另建 `dictionary-sync`。
- **Windows 的同步目录放状态根** — 最强的理由是 Server 和设置窗口本来就共用状态根，偏好也在那里。不用：安装后的状态根是安装器的 DataDir，整台机器一个目录、每个用户都能改，里面不能放词条明文和设备私钥，几个 Windows 用户也会共用一个设备身份。
- **Windows 的 periodic 也放在设置窗口里（像共享页那样开着设置时定时）** — 最强的理由是设置窗口开着时状态能自己刷新。不用：Server 已经在定时，两边都定时只会多花额度；设置窗口在进入页面、点「立即同步」和设备操作后都会重读状态。

## Consequences

- **收益**：有 WebDAV 网盘的用户不用水杉账号就能在设备之间同步「我的词条」，包括删除，离线交错、崩溃和重放后收敛到同一个结果；网盘只见到密文；协议和规则只在 Rust 里一份，六个宿主都经同一个 C 入口驱动。
- **代价**：每台设备都要维护一份共享词库的本机副本（10 万个词约 10 MB）；每次核对读整个「我的词条」，开销随词条数线性增长；用两个功能的设备要分别批准两次；打字自动造的词也会被同步，用户若不希望，需要 Engine 先区分来源；桌面端的远端改动通常在打开设置或者输入会话不占着词库时才写进来。
- **已知限制**：离线超过 90 天、又改过已在别处删除的词条，会让它复活；知道应用密码又持有密钥的人仍能往后追加事件，移除设备后要换应用密码；没有本机状态的新安装没有防回退可言；删掉的密文可能留在网盘回收站。
- **还没做的**：Windows、iOS 以外四个平台的设置界面、待批准设备的提示和触发接线（各平台 PR）；真实的坚果云、Nextcloud 上的端到端验收；真实词库规模下核对和首次上传的耗时测量；Android、HarmonyOS 上 `directory` 的具体位置和跨进程共用的验证；iOS 键盘扩展在真机上调 `local_change` 的内存占用。

## Verification

- 检查点边界：6500 条、每条 4096 字节的合成快捷短语不会发布超限检查点，日志不封口，确认删除后仍可收敛；超限重建不会增加远端事件，原设备可继续写入。

- `cargo test -p msime-client-core --lib dictionary_sync`：66 项，含多设备模拟——三台设备增词、改编码、删词后收敛；40 个种子的随机离线交错加崩溃和重放收敛且没有重复发送；并发修改与删除两种上传顺序结果相同；时钟在重启和系统时间回调后不倒退；重装设备重新加入；同一设备只登记一次；移除设备后换钥并把它挡在外面；压缩并删除旧 epoch 后长期离线设备重新加入；Engine 忙时不提前确认、墓碑等它；每一次写盘处崩溃都不丢不重；回退、截尾、删除整个文件夹被识别；大批删除被挡下；Engine 不收或删不掉的词不反复重试、也不复活；删了又加回来用新的请求编号；从检查点加入时不会因为墓碑删掉本机的词（先在去掉修复时确认会失败）；调度在额度之内。
- `cargo test -p msime-clipboard-relay --test dictionary_webdav_flow`：9 项，对着 `dav-server`：两台设备经密钥串配对（两边的核对码相同）、批准、互传、改编码和删词；同一安装两个进程同时第一次使用只登记一台；错误的应用密码在同步和测试连接里都是 `dictionary_sync_unauthorized`，连不上的地址是 `dictionary_sync_unavailable`；超大事件是 `dictionary_sync_too_large`；两台设备同时同步抢同一个序号，词都进去了；截掉日志尾部是 `dictionary_sync_rollback`，重新测试连接后恢复、本机的词都在；服务端暂时不可用时改动留在本机，恢复后发出；凭据和词条不出现在网盘文件里，凭据不出现在本机状态文件里。
- `cargo test -p msime-host-api --lib dictionary_webdav`：4 项，对着真实的 Engine 词库：读「我的词条」（含多行快捷短语和英文显示形）、加入、删除、删除本来就没有的词、同一个请求编号重试；输入会话占着词库时答「忙」、读照常；Engine 不收的词单独报告、同批其他词照常写进去；请求在联网之前就被校验。
- `cargo test -p msime-client-core --lib`、`cargo test -p msime-client-services`、`cargo test -p msime-clipboard-relay`：全部通过；`cargo test -p msime-host-api --lib` 只有两项与本改动无关的失败（按需资源包列表与 develop 上新增的 `pronunciations` 不符，一项按分钟取本地时间的脚本插件测试）。`cargo clippy` 对四个 crate 加 `--all-targets` 只剩 develop 上已有的两处 `field_reassign_with_default`。
