# Agent Note: 自建存储个人词库同步方案

Status: implemented

## Problem

#9880 要求在多个平台之间通过自选存储同步个人词库，明确同步对象、冲突合并、删除传播和凭据保管。现有账号云词库绑定水杉账号，而且合并模式只加词、不传播删除；[WebDAV 云剪贴板](2026-10-26-cloud-clipboard-webdav.md)和自建中继处理加密剪贴板，没有离线合并语义，不能当作词库同步已经实现。#9989 也提到常用词库，剪贴板那部分见 [自建存储云剪贴板同步方案](../../proposed/feature/2026-10-27-clipboard-self-hosted-sync.md)。

难点在于网盘没有服务端逻辑，设备会长期离线、随时崩溃，Engine 的个人词库又有十几条写入路径（设置页、导入、MCP、候选栏删除、集合、账号云词库合并、打字自动造词），而且不区分用户显式加的词和打字自动造的词。坚果云免费账号每 30 分钟 600 个请求、与所有第三方应用共用，`If-None-Match` 被忽略，`GET`/`HEAD` 没有 ETag，根目录下的文件夹删不掉。

## Decision

维护者已定：只同步「我的词条」；端到端加密并复用云剪贴板的设备批准；六个平台都能驱动同一个核心；自动加手动触发；首版只做 WebDAV（坚果云、Nextcloud）。契约（存储布局、记录、合并规则、上限、请求量、宿主接入）写在 [`docs/dictionary-webdav-sync.md`](../../../../docs/dictionary-webdav-sync.md)，这里记各项怎么定的、为什么。

协议和共享核心已经落地：不碰网络和 Engine 的状态机在 `client-core::cloud::dictionary_sync`，WebDAV 传输和词库密钥串在 `client-services::dictionary_webdav`，Engine 一侧的本机词库和 C 入口 `msime_client_dictionary_sync` 在 `host-api`。各平台的界面和触发接线按平台各开 PR。

### 同步对象

同步的是「我的词条」列表里看到的那些：Engine 日志里 `user_inserted` 的词条，以及它们的删除。打字自动造的词也在里面——Engine 对它们和用户显式加的词写的是同一种行，列表里也不区分，要排除就得先改 Engine 的写入格式，首版不做；被同步的只是词本身，打字学到的权重、候选顺序、固定位置、选择次数一律不同步，符合「不同步打字学到的频率、权重和顺序」。身份是（词库类别、编码、词），类别就是 Engine 的五个词库（`pinyin`、`wubi`、`wubi98`、`quick`、`english`），这也是「词条所属的词库类别」的含义；用户命名的词条集合是 client-services 自己的元数据，首版不同步集合本身，集合里的词照样作为词条同步。对主词库词条的删除和改权重属于主词库，不同步。

### 时钟与冲突

每条操作带混合逻辑时钟时间戳：高位 Unix 毫秒、低 10 位计数，整个值不超过 2^53 - 1。本机生成取「比见过的都大、不早于本机时间」；收到操作就把本机时钟推到它之后，从检查点开始时推到检查点里最晚的时间戳之后；时钟随同步状态原子写盘，重启和系统时间回调都不会倒退；不在合法范围的时间戳整条跳过；快于本机一天以上只提示、不改合并。重装是一个新的设备编号，第一次加入前先读完日志或检查点再记录本机的词。

每个词条是最后写入者胜的寄存器，删除也是写入（墓碑），按（时间戳、设备编号、是否存在）比较；平局时设备编号大的胜，同一设备同一时间戳「存在」胜过「删除」。合并与到达顺序无关、重复合并不改变结果。改编码就是删旧加新。合成示例（文档里有完整的表）：B 10:00 改编码、A 10:05 删旧词条，结果旧词条删除、新编码保留；同一词条一删一加，晚者胜，与谁先上传无关。

### 发布、恢复与版本

一个事件一个不可变文件 `e-<12 位序号>.json`，独占创建下一个序号（`PUT` 临时名加 `MOVE` 带 `Overwrite: F`，与云剪贴板同一条代码路径），没抢到就重读再试。事件用哈希串成链；本机读过的最后一个事件消失、列表跳过一个直接 `GET` 也不存在的序号、检查点的位置或代数变小，都是 `dictionary_sync_rollback`——链头只挡得住改写，挡不住截掉尾部，后两条是为此加的。重复操作靠（设备、时间戳）认出：本机写成的事件在下一次读到时从待发送里去掉，所以发出之后、写盘之前崩溃不会重发。`format.json` 版本不认识就不读不写；已经在运行的客户端靠带 `upgrade` 的封口事件得知格式升级。

本机的应用顺序是：记录本机改动并写盘 → 拉取并与位置一起写盘 → 分批写进本机词库、写好才计入 → 发送 → 封口和清理。远端改动在写进 Engine 之前只存在于共享状态里，本机确认的位置只在 Engine 写好之后推进。每项写入带一个由操作唯一决定的请求编号，Engine 的回执让重试幂等；Engine 删不掉的词照实留着、不再重试，免得下一次核对把它当成本机新加的词发出去、在所有设备上复活。上限：一个事件 1000 条操作、明文 256 KiB、文件 512 KiB；检查点 32 MiB、30 万个词条、64 台设备；列目录 2 MiB；共享词库 10 万个词条以内收新词；待发送 2 万个词条；一次写进 Engine 128 项。

### 捕获本机改动：三方核对而不是在写入点挂钩

本机记着「认为本机词库里有哪些词」（`applied`）。本机词库相对它的变化是本机改动，记成操作；共享状态叠上待发送操作相对它的变化，是要写进本机词库的远端改动。宿主在用户改词后马上以 `local_change` 调一次，通常只做核对、不联网（本机改动没发出去已满十分钟、离上次发送已满五分钟时这一次就发送，见「触发与请求量」），时间戳因此接近改动发生的时刻；每次同步开始前也核对一次，漏掉的通知不会丢改动。核对读的是 Engine `stream_dictionary_state` 在一个读事务里给出的一致视图。一次核对里少了 50 个以上、且至少一半的词时先挡下删除，由用户选择同步删除或从网盘恢复：词库被重置或损坏时不能把其他设备上的词也删掉。

### Engine 集成

状态机只经 `LocalDictionary` 接口写词库，一次一批，每批之前取独占维护权、写完就放，从不跨网络请求持有；跨批保留的输入法让出租约在这一轮写完、联网之前由 `release` 撤掉。拿不到维护权时，Linux、macOS、Windows 在用户手动同步、打开设置和设备操作时经 `QuiescedHosts` 请输入法让出词库（50 毫秒间隔、2500 毫秒预算、租约 30 秒）；自动同步和移动端不打扰输入会话，直接答「忙」，这一轮不写，5 秒、30 秒、2 分钟、10 分钟后再试（不联网），拉取和发送照常。加入用默认权重并且总是写成用户词（主词库里有同样的词也写一行，否则它不会出现在这台设备的列表里，下一次核对会当成本机删掉了），删除带上刚读到的权重，权重被打字学习改了就重读一次再试。整个调用由宿主放在工作线程上，输入线程从不等网络。

### 加密、设备与压缩

词库有自己的密钥串：云剪贴板端到端加密协议的另一个实例（同一个驱动、同一个日志核心、同一个虚拟中继），放在 `msime-dictionary/keyring/`。实现上它就是一个给每个请求路径加上这个前缀的传输，云剪贴板的代码不知道自己被放进了别的目录；全部用法收在 `KeyRingAccess` 一处，云剪贴板的驱动改了（例如 #10032 的重复登记修复）只影响那一处。密钥串只交出 `HKDF(K, "msime-dictionary-v1-key")`，不交出 `K` 本身；事件和检查点的子密钥再由它派生。不与剪贴板共用同一份批准，理由见下面的备选方案。

设备身份是这份密钥串里的设备编号：一个安装一份密钥串，所有进程给同一个目录、整次同步持有同一把锁，读不到才生成，登记按编号进行、重复登记只更新名称，批准方看到的每台设备只有一条；日志的设备表同样按编号记。模拟测试覆盖「两个进程共用一份状态、写多少次都只有一条」，传输测试覆盖「同一个安装的两个进程同时第一次使用、反复同步，批准方只看到一条等待中的设备」。

移除设备时密钥串换钥并在日志里宣布移除，持有新旧两把密钥的设备封口当前 epoch、用新密钥写下一个 epoch 的检查点；被移除的设备读到封口为止。持有旧密钥的设备都不在了时，用户可以「以本机为准重新开始」：新的共享词库编号，其他设备按第一次加入合并，不删词。

一个 epoch 攒到 64 个事件或 8 MiB 封口，下一个 epoch 从加密的检查点开始，旧 epoch 10 分钟后删除。墓碑在封口时回收：参与确认的是没被移除、在日志里最晚一次写入之前 90 天内出现过的设备，它们确认位置的最小值以内的墓碑删掉。确认游标的因果范围是「这台设备的本机词库已经持久地写到了这个序号」。长期离线的设备从最新检查点重新开始，按 `applied` 与检查点比较得出别处的删除。

### 本机状态与响应字节预算

本机状态读取和写入都受 64 MiB 预算约束，序列化后先检查再原子替换，超限答 `dictionary_sync_too_large` 并保留上次可读文件。词条数量合法不代表字节数够小：1 万条各 4096 字节的快捷短语同时出现在 `applied` 和 `outbox` 时就超过预算，不能先写出无法再读取的状态。用户删减本机新增内容后可以继续同步。预算不扩大，避免把读取与内存开销转嫁给移动宿主。

成功 HTTP 正文读取失败必须作为失败交回；只有有界读取报告 `InvalidData`（超过字节上限）时才标记为 `TooLarge`，其他传输错误仍为 `Unavailable`。这覆盖 chunked 和没有 `Content-Length` 的响应，防止把坏文件当空文件跳过并持久化错误日志位置；非成功 HTTP 状态保持原有鉴权和退避语义。

检查点的 32 MiB 同时约束生成和读取。合法的 4096 字节快捷短语约 6500 条就会超过它，不能仅靠 10 万词的条数上限。普通压缩在封口前生成下一 epoch 的检查点预检，超限则保留当前日志继续写，后续删除和确认使状态缩小后再压缩；每轮先发送本机改动，再做普通压缩。换钥仍先压缩，超限返回 `dictionary_sync_too_large`，不继续用旧钥发送；用户须用仍持旧钥的设备删减词库并同步后再换钥，或用较小的本机词库重新开始。重新开始也在写封口前生成、检查完整检查点；超过上限时不留下封口或新目录。补写别人已封口的检查点同样检查大小，防止发布其他设备读不了的文件。

共享设置页的请求队列按宿主和已保存网盘配置的代次隔离。配置切换或停止时立即清除旧代次的忙碌标志；尚未开始的设备批准、移除、重置与后续状态请求逐次检查代次，失效后不再调用宿主。已经开始的请求允许返回，但不能更新新配置的界面或定时器。

### 触发与请求量

每台设备每 30 分钟自动同步最多 40 个请求（密钥串的请求也算在里面），加上手动最多 60 个，三台设备用满只占坚果云配额的三成。改词后防抖一分钟（一直改时最多十分钟）、两次自动发送至少隔五分钟；`local_change` 本身把这次改词记成最后一次，所以只有十分钟的上限会在它身上到期，到期（并且离上次发送满五分钟）时这一次就联网发送，宿主要把它当作联网的调用；打开设置时拉一次（一分钟内不重复），宿主活着时每 30 分钟拉一次；「立即同步」不受防抖限制。连不上按 1、2、5、10、30、60 分钟退避，限流等 30 分钟，需要用户处理的错误自动同步停一小时。宿主每次调用都拿到下一次该什么时候再调用，不用自己算。

自动额度不足一轮所需的三个请求时，下一次联网检查等到滚动窗口内足够多的请求过期；按时间排序计算恢复点，包含手动同步已占用的额度，不假设请求记录已排序。防抖、发送间隔与错误退避仍取各自约束，Engine 忙时的本机重试仍可更早执行，手动同步仍使用自己的剩余额度。只挡联网却返回已经到期的发送时间，会退化为每秒核对整个本机词库并写同步状态；调度时间必须与能否开始自动同步的判定一致。

WebDAV 的额度在实际 HTTP 发送前扣除：同一轮密钥串、词库、临时目录创建、失败后的重试和临时文件清理共用剩余额度。协议核心对能报告实际请求数的存储按本轮增量记账；没有传输计数的模拟存储沿用逻辑操作估算。压缩后的临时文件清理在最终计费和保存调度状态之前执行，不能在返回之后留下未记账请求。密钥串驱动先保存本机身份，再由首次传输准备根目录；即使第一个建目录请求被拒绝，失败请求与退避也能按真实本机身份保存。身份丢失后重新加入保留同一安装的调度窗口，不能借新设备编号重新领额度；对外身份只在当前配置匹配的密钥串缓存日志包含本机登记后公开；仅有内部私钥或空日志缓存都不算登记，首次失败后的状态查询与离线调用也不能放开键盘同步入口。自动 40、含手动 60 的滚动窗口与默认值保持；测试连接、设备管理和重新开始沿用原有独立操作语义。

请求窗口在协议核心运行期间始终留在 `SyncState` 中，结束时只追加本轮请求。核心在捕获本机词条、确认远端进度等步骤会通过 `StateSink` 保存整份状态；原先用 [`std::mem::take`](https://doc.rust-lang.org/std/mem/fn.take.html) 暂时取出历史记录，会让这些保存点把空窗口写盘，进程随后退出或最终调度保存失败时重领额度。直接追加保留已有保存点契约，不增加历史副本、不改状态格式。本轮新增请求仍沿用结束时合并的计费时机，不新增逐请求写盘。

### 宿主接线：共享设置页、macOS、Linux 与 HarmonyOS

用共享 React 设置页的三个宿主共用一份界面和一份触发。界面在「词库」页「我的词条」导入导出之后（`packages/ui/src/settings/dictionary-sync-section.tsx`）：网盘地址、账号、遮罩的应用密码（不回显、留空沿用），「测试连接」只探测不保存，「保存」先探测、通过才写进偏好、失败留着草稿，「停止同步」清掉这组偏好；状态（上次同步、待发送和待写入、错误码对应的中文说明）、「立即同步」、本机等待批准时的核对码、被挡下的大批删除的「同步删除」和「从网盘恢复」；设备一组按设备编号每台只列一条，等待允许的带核对码和「允许」「拒绝」，已允许的本机以外可以「移除」（本机还没获准、手里没有密钥时只列设备，不给这三个按钮），最后是「重置密钥」和「从这台设备重新开始」，危险操作都先确认。宿主没有 `dictionarySync` 时两组都不画。

触发放在共享页的模型里（`use-dictionary-sync.ts`），宿主只提供 `dictionarySync.request(action)`：设置打开且已保存的偏好配置了网盘时 `opened`，按 `next_check_ms` 排 `periodic`（限在 1 秒到 30 分钟），经设置改了词成功之后 `local_change`（模型给词库客户端的写方法包一层成功后的通知，只在宿主提供词库同步时包，其他宿主拿到的还是同一个客户端），按钮是 `manual`；请求排成一队依次发出。

目录：macOS 与 Linux 是账号目录下的 `dictionary-sync/`，账号目录本来就是设置应用和输入法共用的那一个（macOS 的 Application Support 里设置应用 bundle id 那一层，Linux 的状态目录）；鸿蒙是设置应用沙箱的 `files/state/dictionary-sync`。三处都不直接用账号目录或 `files/state`：云剪贴板中继的 `cloud-clipboard-relay-keystore`、`cloud-clipboard-webdav-state` 在那里，词库密钥串的文件名与它们相同。Tauri 设置应用经新公开的 `msime_host_api::dictionary_webdav::request_json` 直接调用（C 入口的同一个实现），鸿蒙经 NAPI `dictionarySync` 在工作线程上调 C 入口；鸿蒙的 `dictionary_sync` 请求除 `status` 外都在隐私政策授权之后，`local_change` 也算，因为发送到了十分钟上限时它会在这一次就发送。macOS 设置应用经 `request_json_announcing` 把 `msime_host_macos::quiesce_input_sessions` 交给让出租约，租约一挂上就经分布式通知叫醒 IMK，与设置页改词（`dictionary_request`）相同；C 入口和 Linux 只靠租约文件和输入法的定时器。

输入法进程：macOS 的 IMK、Linux 的 IBus 和 Fcitx5 由后来的 Rust 后台调度自己触发，见下文「输入法进程的后台同步」。鸿蒙的键盘扩展不触发：它读写的是自己沙箱里的另一份个人词库，沙箱里也没有设置应用生成的词库密钥串（C 入口后来有了 `create_identity: false`，带上它键盘只会答 `clipboard_identity_missing`，不带就是同一台手机的第二个设备身份，#10029、#10032 修的那一类），`scripts/test-harmony-dictionary-sync.py` 守着调用点只在设置应用。

### 偏好与凭据

偏好是 `dictionary_sync_webdav {url, username, password}`，规则照 `cloud_clipboard_webdav`，两者各配各的：应用密码进凭据清单，账号在诊断里换成 `<redacted>`，整组进 `LOCAL_SECTIONS`，不进账号设置同步和 MCP。本机同步状态只记网盘地址和账号的摘要，不记凭据；测试证明网盘文件不含凭据和词条明文；本机状态含词条明文但不含凭据，调试输出也不打印凭据。

### 输入法进程的后台同步（macOS、Linux）

打字时 Engine 自动造的词、候选栏删的词和输入法自带词库窗口里改的词由输入法进程自己触发同步，不等设置应用打开。macOS 的 IMK 进程、Linux 的 IBus 和 Fcitx5 宿主起来时调一次 `msime_client_dictionary_sync_start {options_path, directory}`，退出时 `msime_client_dictionary_sync_stop`；调度是 `client-services::dictionary_webdav_scheduler` 的一个后台线程，宿主一侧是 `host-api` 的 `ImeHost`。目录与设置应用相同：macOS 是 Application Support 里设置应用 bundle id 那一层下的 `dictionary-sync`，Linux 是共享状态目录（runtime options 的 `preferences_directory`）下的 `dictionary-sync`。Windows Server、Android `:ime` 各自的 PR 在本平台的输入法一侧触发，行为与这里一致：只用已有身份、不请输入法让出词库、按 `next_check_ms` 排 `periodic`、词变了才 `local_change`；iOS 的键盘扩展同样只在密钥串已经存在时才调，见下文「iOS 宿主」。

- **改词的信号是个人词库文件的戳加「我的词条」的指纹**。每 5 秒看一次日志库和 `-wal` 的大小与修改时间，变了之后等它安静一轮（一直在变时最多一分钟）再读一遍「我的词条」算指纹，指纹变了才调 `local_change`。日志库被打字学习（权重、选择次数、固定位置）频繁改写，不经指纹直接调 `local_change` 会让核心每次都把「最后一次改词」往后推、防抖一直到不了头，还每次重写一遍本机状态；指纹把这些挡在外面。所有写入路径改的是同一个文件，所以不必挂钩。比较的基线是每次同步开头核对本机改动时读到的那一份（`Watched` 记下的指纹，文件戳在同步之前取），所以核对之后、同步跑完之前才造的词照样触发；同步自己写进本机词库的词也会让指纹对不上，那一次 `local_change` 核对不出改动，不发操作。基线若在同步跑完之后再读，这段时间里造的词会被算进基线，要等下一次 `periodic` 才记下，真实网盘上的调度测试最早就是这样失败的。
- **一个安装一个设备身份**：后台同步固定用 `DictionarySync::existing_identity_only`。本机还没有设置应用生成的词库密钥串时，`run` 在取锁之前就答 `clipboard_identity_missing`（不建目录、不记录本机改动、不联网），有文件时在锁里按内容再判断一次；设备管理和重新开始在建网盘目录之前、驱动在中继锁里各查一次。C 入口 `msime_client_dictionary_sync` 也收同名的 `create_identity: false`，形状与云剪贴板的相同。Windows Server 的自动同步（`DictionarySyncSchedule.h` 的 `dictionary_sync_request`）带上它，WinUI 和 Win7 设置窗口不带、仍由它们在第一次配置时生成身份；Android 的 `:ime` 在本机还没有设备编号时不跑（`DictionarySyncPolicy.imeMayRun`），iOS 键盘扩展只在密钥串已经存在时才调，两者已经守着同一条规则。
- **不配置就不做事**：每一轮重读配置文件和偏好，没配置网盘、配置读不出来或没有身份时不看文件、不读词库，每 5 分钟再问一次。
- **不打扰输入**：不请输入法让出词库，输入会话占着词库时远端改动按核心的忙重试间隔再试，通常在打开设置时才写进来。
- **与设置应用并发**：两个进程经同一把 `dictionary-sync.lock` 串行，额度、防抖和退避都在共享的同步状态里；后台这一侧只等锁 5 秒（`lock_wait`），等不到 30 秒后再来，免得陪着设置应用的一次长同步挂住宿主退出。
- **停下**：不再开始新的一步，在跑的那一次跑完为止。macOS 和 IBus 等两秒（进程随后退出，每一步都写盘），Fcitx5 插件一直等到线程退出：它是 Fcitx5 加载的共享库，卸载之后插件的代码不能再运行，与它等 `fcitx_detached_jobs` 的规则相同。Fcitx5 加载时还没做首次配置的，第一个会话读到配置时再起。

### Windows 宿主（含 Win7）

Windows WinUI 与 Win7 都提供独立的「确认网盘现状并恢复同步」确认，说明会遗忘待发改动、未上传删除可能重新出现，并使用已保存的连接恢复。WinUI 在确认前捕获配置代次，确认期间换代就取消；Win7 在执行前重新读取偏好并核对地址、账号、密码三字段，变化时终止，不访问新连接。恢复成功后提示用户点「立即同步」。

Win7 词库同步面板关闭时只撤销窗口投递、丢弃尚未开始的任务并唤醒工作线程，不在 `WM_DESTROY` 等待网盘请求。线程以共享状态保留正在使用的服务、偏好快照和同步请求，当前调用返回后自行退出，不再触碰已销毁的窗口。否则离线或网盘缓慢时关闭窗口会把界面线程卡到全部请求超时。

触发分在两类进程里。自动的两种在 Server：它一直活着、持有输入会话，候选菜单的「删除」和维护快捷键删词之后以 `local_change` 记一次（通常只记录，持续改动达到共享层发送上限时也会联网；连着几次合并记录），启动两分钟后第一次 `periodic`，之后照回答里的 `next_check_ms`（夹在 1 秒到 30 分钟之间，与共享设置页相同；调用本身失败时半小时后再试）。这些都在 `DictionarySyncWorker` 自己的工作线程上，不在输入线程、管道线程或消息循环上；偏好里没配网盘时线程只等着，偏好发布时配上就十秒后开始、清掉就停。只有受管理的 Server 做，预览实例不替用户联网；Win7 的 Server 是同一份代码。用户在等着看的两种由设置窗口调：进入 WinUI 词库页「云端词库」标签（或打开 Win7 词库同步面板）时 `opened`，「立即同步」是 `manual`；设置窗口经 `msime_client_settings_dictionary` 改了词之后也自己记一次 `local_change`，与共享页的 `withDictionaryChangeNotices` 相同。Win7 设置窗口的导航不收云端同步的页面，所以 Win7 的配置与设备管理放在独立面板 `--route=dictionary-sync`，与云剪贴板一样，由设置窗口词库页的按钮打开。

一个安装只有一份设备身份：同步目录是本用户的 `%LOCALAPPDATA%\<本版本的用户目录>\dictionary-sync`，Server、WinUI 设置、Win7 设置和 Win7 面板都调 `common/DictionarySyncDirectory.h` 的同一个函数。两个进程第一次使用时同时生成身份由 Rust 的文件锁和「不覆盖另一个身份」挡住；仍然报 `clipboard_keystore_conflict`（#10032 的约定：已经发出请求之后才发现存储里是另一个身份）时，宿主用同一个请求再调，最多三次（`common/DictionarySyncRetry.h`），第二次就会用存着的那份身份。

Server 停机时，偏好和候选删词的生产线程可能还在送最后一条通知。`DictionarySyncWorker` 的共享状态指针在对象存活期间保持不变：`stop` 只在状态锁内设置停止标志，不清空指针；后到的 `configure`、`note_local_change` 读到停止标志就返回，`start` 也不能重新启动。这样不用让退出路径无限等待网盘；两秒后仍在途的工作线程继续持有自己的共享状态，通知线程也不会与 `shared_ptr::reset` 并发读写同一个指针。调用方仍须在销毁 worker 对象前结束所有通知来源。

### iOS 宿主

- **入口和触发**：设置 App「词库 → 词库同步」（`DictionarySyncView.swift`），表单的做法照 iOS 云剪贴板的网盘填写页：应用密码遮罩、不回显、留空沿用，「测试连接」只测不存，「保存」先测、通过才写 `dictionary_sync_webdav`，不通过时填写页和草稿都留着。`DictionarySyncCenter` 在 App 回到前台时以 `opened` 调、在前台时按 `next_check_ms` 以 `periodic` 再调，进后台就停；iOS 不让 App 在后台常驻，App 关着的那段时间里别处的词等下次打开 App 时写进来。每个调用都在专用线程上，期间用 `beginBackgroundTask` 保持后台执行，挂起时不会还拿着 App Group 里的文件锁（0xdead10cc）。
- **键盘扩展只记录、有条件地记录**：应用了 App 排队的编辑、或者候选栏「删除词条」之后，`KeyboardDictionarySync` 在 `performExpiringActivity` 里以 `local_change` 调一次，连续的改动合并成一次，从不在输入线程上等。只在有完全访问、目录里已经有 App 留下的同步状态和密钥串、状态文件不超过 2 MiB 时才调：`run` 把整份状态和「我的词条」读进内存，键盘扩展的内存上限远低于 App，而 2 MiB 的状态大约对应几万个词；没有密钥串时不调，于是键盘从不生成设备身份、也不替 App 第一次登记。其余情况留给 App 下次打开时的那一次同步来记（时间戳是那时的）。拉取和写入远端改动不在键盘里做：键盘自己的会话占着词库，移动端遇到「忙」本来就留到下一次。待发的改动放了十分钟以上时 Rust 会让这一次 `local_change` 顺带发出，所以键盘里偶尔会有几个请求；它们同样在后台执行时间之内。
- **目录和密钥串**：App Group 容器里的 `dictionary-sync/`，App 和键盘给同一个目录。目录建成 0700、文件保护设为「首次解锁后」（Rust 之后建的文件继承它）、排除在设备备份之外，与云剪贴板网盘缓存的 `cloud-clipboard-relay/` 相同。词库密钥串按核心的存储契约是 Rust 在这个目录里写的 `cloud-clipboard-relay-keystore` 文件（只有本应用可读），不进钥匙串，理由见下面的备选方案。
- **一个安装一个身份**：App 和键盘用同一个目录，Rust 整次同步持有 `dictionary-sync.lock`、在锁里「读不到密钥串才生成」，两个进程第一次同时用也只有一个身份；键盘又只在密钥串已经存在时才调。设备列表按设备编号再去一次重，每台一条。

普通 `probe` 只测连接，不清同步位置、待发改动或防回退记录。设置保存前预检也遵守这个边界，否则一次无副作用外观的测试会抹掉待上传删除，使远端词重新出现。只有单独确认恢复时才传 `trust_remote:true`，确认文案说明待发改动会遗忘、未上传删除可能重新合并回来。宿主用已保存连接恢复，不能把未保存草稿的探测当作恢复。

### Android 接入

设置 App 的「我的 → 词库同步」（词库页也有入口）是原生 Java 页 `home/DictionarySyncPage`，填写、测试连接和保存的行为与云剪贴板的 WebDAV 页相同；打开时 `opened`，「立即同步」`manual`，状态、被挡下的删除、核对码、设备批准、重置和重新开始都在这一页。键盘进程 `:ime` 由 `core/ImeDictionarySync` 在候选栏删除和设置页排队的改词写进词库之后调 `local_change`，按 `next_check_ms` 定时 `periodic`，输入会话结束时有没写进本机的远端改动就再来一次；调用在它自己的工作线程上，定时用主线程 Handler，与键盘已有的个人词库维护同一种机制。两个进程的目录都是 `noBackupFilesDir/dictionary-sync`，身份靠 Rust 在共用目录的锁里「读不到才生成」；键盘进程另外只在本机已有设备编号时才跑，第一次登记只由设置页做。错误码的中文说法在 `policy/DictionarySyncPolicy`，`scripts/test-android-dictionary-sync-contract.py` 核对它与 Rust 的错误码一致。

Android 的个人队列同步返回 `applied_count`，计 Engine 确认已应用的 `Written` 请求数（含幂等重试），`AlreadyPresent` 或失败项不算；集合有界同步把个人写入数和 `sent` 跨批累计，停止判定仍使用本批进展。每批只申请一份维护租约，覆盖个人队列和集合后释放；后批被新输入会话抢占时返回前批成功的累计确认数和真实待处理数，让宿主立即通知并安排重试，存储错误仍直接报告。键盘按 `Written` 确认或集合发送触发 `local_change`，不比较两轮完成后的队列长度：队列从空到入队再在一批内清空时，两轮事后长度都为零。键盘收起时，已有定时或最近有待应用项就按原重试间隔在独立工作线程重读共享 `pending_apply`；设置进程拉到的改动即使 IME 缓存为零也能被发现。有待应用项才以 `periodic` 交回共享层，无待应用项或只读检查失败时保留原周期，不额外调用同步。检查只合并排队中的同类工作，不覆盖真正的本机改动触发。代价是空闲时增加一次有界的共享状态读取，输入线程不读盘。

Android 设置页的请求代次同时约束工作线程和界面回调。保存或停止网盘配置时，在写偏好之前先使旧代次失效；网络线程在执行用户操作、补读状态和读取设备之前分别检查代次，旧请求已开始的调用可以返回，但不能继续后续请求，尤其不能由 `devices` 对新网盘登记本机。代次由主线程写、工作线程读，用 `volatile` 保证可见。保存失败时也重新读取页面，旧任务的回调既然已失效，就不能再依赖它清理忙碌状态。

Android 的 `dictionary_sync_rollback` 提供独立「重新信任网盘现状」入口，普通测试连接及保存预检不传 `trust_remote:true`。弹窗出现前在工作线程读取已保存的地址、账号和应用密码，弹窗只显示前两项，并明确待发改动会遗忘、未上传删除可能回来、本机词保留。确认归属于弹窗前的代次；点击确认时代次已失效或正在执行其他操作就取消，工作线程执行前再比最新已存三字段，停用或任一字段变化都中止。中止使用内部异常结束整项任务，不补读状态或设备，避免取消后仍对新网盘登记；恢复在途后换代也不继续手动同步。代价是恢复前后多一次偏好读取，不把密码留在页面字段或日志里。

## Alternatives considered

- **集合循环继续调用独立取得租约的个人同步入口** — 最强的理由是复用现成的参数校验与维护权管理，不增加持租约的内核。不用：个人队列写完、释放租约后，集合再次抢锁可能被新输入会话抢先占用，错误返回就会吞掉已确认数量。整批用同一份租约，两步之间没有抢占窗口，批间仍让输入会话进入；后批忙返回前批进展，存储错误继续报告。
- **与云剪贴板共用一份密钥串和批准** — 最强的理由是用户只批准一次，两个功能看到同一份设备列表。不用：剪贴板的生命周期会直接伤到词库——关闭云剪贴板会删掉全部密钥、封装和设备登记，「重置云剪贴板」会换钥并清空；它的空间绑定的是 `cloud_clipboard_webdav` 的地址和账号，词库就得强制要求同一个网盘账号；Android 的剪贴板密钥串由 Java 用 AndroidKeyStore 保存，iOS 和 HarmonyOS 的宿主还没接中继，共用就要先把这些宿主的剪贴板密钥串接进词库同步。复用代码、分开实例，换来两个功能互不牵连，代价是用两个功能的设备要批准两次。
- **在每个写入点挂钩产生操作** — 最强的理由是时间戳精确等于改动时刻，也不用比较整个词库。不用：写入路径有十几条，跨 host-api、MCP、会话里的候选删除、集合和账号云词库合并，漏一条就静默丢同步；挂钩写在 Engine 提交之外就有「提交了但没记下操作」的崩溃窗口；日志表只记每个词条的当前状态和秒级 `updated_at`，没有可以接着读的序号。三方核对只依赖「本机现在有哪些词」，任何路径的改动都覆盖到，崩溃后重新比较就能接上。
- **每台设备各写自己的目录** — 最强的理由是写入不会争抢序号，也不需要独占创建。不用：读一次就要对每台设备的目录各发一个 `PROPFIND`，设备一多就吃掉坚果云的配额；单一日志一个 `PROPFIND` 就看到全部新事件，哈希链和压缩也只有一条。
- **按到达日志的先后决定胜负，不要时钟** — 最强的理由是简单，日志本身就是全序。不用：离线设备回来时，它几天前的旧修改会盖掉别人今天的修改；用时间戳比较，结果与谁先上传无关。
- **向量时钟识别真正的并发** — 最强的理由是能区分「先后」和「并发」，并发时可以选择保留词条。不用：每条记录的大小随设备数增长，而墓碑回收和设备淘汰会让向量越来越难维护；既然冲突规则本来就是最后写入者胜，混合逻辑时钟已经足够，并发的平局也有确定的结果。
- **身份只用（类别、词），编码作为值** — 最强的理由是两台设备同时改编码只会留下一个。不用：同一个词有多个编码是常态（多音字词、简拼和全拼），用户会显式加好几个；把编码当成值就只能留一个。
- **只提高检查点读取上限** — 能立即容纳当前复现的词库，但合法词条大小与数量的组合仍会超过新的固定值，读取端的内存预算也随之提高；保留既有上限，在不可逆的封口前检查，并允许用户先同步删减。
- **墓碑永不回收** — 最强的理由是任何离线多久的设备回来都能正确判断删除。不用：删除只增不减，检查点会一直变大；回收加上「长期离线设备从检查点按本机记录比较」已经能正确传播删除，只在超过 90 天离线又改过同一词条时复活。
- **iOS 把词库密钥串放进钥匙串，与云剪贴板的中继密钥串同等保护** — 最强的理由是 iOS 云剪贴板评审时定下的标准：密钥串不弱于账号那份，拿到容器文件不该就拿到设备私钥。没有采用：词库的密钥串整个由 Rust 在 `KeyRingAccess` 里驱动（云剪贴板的中继在 iOS 上是 Swift 跑驱动循环、Rust 只发请求，所以能把密钥串放在 Swift 的钥匙串里），要改放钥匙串就得先在 host-api 加一个由宿主注入的密钥串存储，六个平台的 C 入口一起变，而 Android 的词库密钥串同样是 `noBackupFilesDir` 里的文件。这一版在宿主一侧做到能做的：0700 目录、只有本应用可读的文件、首次解锁后的文件保护、不进备份（于是不随备份到别的设备）。要与钥匙串同等，需要先改共享层。
- **自动同步也请输入法让出词库** — 最强的理由是桌面端别处的改动能及时写进来，不用等打开设置。不用：每 30 分钟和每次改词后都让所有输入会话让出一次词库，会打扰正在打字的用户，而远端的词晚一点出现并不丢；只在用户等着看结果的时候（手动同步、打开设置、设备操作）才这样做。
- **Android 的词库密钥串也像云剪贴板中继那样用 AndroidKeyStore 加密** — 最强的理由是文件被拷走也解不开。不用：`msime_client_dictionary_sync` 在一次调用里自己读写密钥串，没有让宿主保管它的接口，要做就得先改共享入口，超出 Android 接线的范围；它放在 noBackupFilesDir 下、只有本应用能进，不进云备份和设备间迁移。
- **Android 键盘进程也去做第一次登记** — 最强的理由是用户没打开设置页也能开始同步。不用：Rust 的锁已经保证只生成一个身份，但让设置页独占「第一次登记」多一道保险，也符合 #10032 之后「一个安装一个身份、键盘不另登记」的做法（鸿蒙键盘的 `existing_identity_only` 同理）；用户保存网盘设置时就在设置页里，那一页随即登记。
- **Android 用 WorkManager 或 JobScheduler 定时** — 最强的理由是进程被回收后也能按时同步。不用：应用自己的代码没有用 WorkManager 排过任务（它只作为 ML Kit 的传递依赖、在手写的初始化里出现），拿它做调度是另一项决定；输入法服务被系统绑定时进程一直活着，被回收时下一次键盘起来再接上，远端的词晚一点出现并不丢，与键盘已有的个人词库维护用同一种 Handler 定时。
- **触发放在 Tauri 宿主的后台线程里** — 最强的理由是不依赖网页：设置窗口停在别的页、网页定时器被节流时也照样按 `next_check_ms` 跑，改词也能在 `dictionary_request` 命令里统一挂钩。不用：鸿蒙不经 Tauri，同样的调度要在 ArkTS 里再写一份；页面本来就知道哪些写操作成功了、要显示同步的结果，放在共享页里三个宿主只要提供一个 `request`。代价是只在设置应用开着时同步。
- **只在设置应用里触发，输入法进程不同步（#10050 起初的做法）** — 最强的理由是不必在 IMK、IBus、Fcitx5 里新加线程和原生绑定（它们现有的后台工作只有遥测上传，macOS 的 IMK 经 dlopen 的函数表到 Rust），漏记的改动在下一次同步开头的核对里都能补上、不会丢。不再这样：打字时造的词和候选栏里删的词要等打开设置才发出去，而用户可能几周不开设置；调度写在 Rust 里一份之后，三个宿主只剩起、停两个调用，见上文「输入法进程的后台同步」。
- **鸿蒙的状态放在共享沙箱目录里，键盘也同步** — 最强的理由是键盘那份个人词库才是打字用的那份，网盘来的词直接进键盘。不用：基础访问模式下键盘对共享目录只读，Rust 的锁文件建不出来，模拟器上也没有这个目录；键盘自己的沙箱里没有设置应用生成的词库密钥串，带 `create_identity: false` 调只会答 `clipboard_identity_missing`，不带就是第二个设备身份；两个进程各持一份同步状态、共用一个设备编号也不行，时钟、待发送和确认位置都是按「一台设备一份状态」设计的。要让键盘那份词库参与同步，得先让两份个人词库接上，或者给 Rust 加一个由设置应用代键盘读写词库的办法；后来走的是前一条，见 [鸿蒙设置应用与键盘的「我的词条」经共享沙箱收敛成一份](2026-10-27-harmony-unified-user-words.md)。
- **直接同步数据库或 Rime `sync` 目录** — 可复用现成文件同步工具，但数据库版本、并发使用和删除传播无法因此获得一致契约，不作为首版路径。
- **复用水杉账号云词库 API** — 已有认证和分页代码，但不能满足用户自选存储，也不能把个人词库自动改发到账号服务。
- **首版同时支持 WebDAV、S3、OneDrive** — 覆盖面更大，但会同时扩散认证、发布、重试和错误语义；日志格式与传输无关，以后加 S3 只需另一个独占创建的实现。
- **输入法进程在写入点发「我的词改了」的通知** — 最强的理由是不用轮询文件，改词的那一刻就知道。不用：输入法进程里改词的路径有好几条（Engine 在上屏时自动造词、候选栏删词、AppKit 和 Linux 的词库窗口、经 host-api 的词库请求），自动造词发生在 Engine 的会话里，宿主看不到；漏一条就要等下一次 `periodic`（最长 30 分钟）。文件的戳每 5 秒一次 `stat`，覆盖所有路径和所有进程。
- **日志库每变一次就调 `local_change`** — 最强的理由是最简单，核对本来就会认出没有改动。不用：打字学习几乎每次上屏都写日志库，`local_change` 每次都推迟发送的防抖（最多推到十分钟）、重写一遍本机状态（十万个词约 10 MB），还占着同步锁；读一遍「我的词条」算指纹只是一次只读事务。
- **各宿主自己用原生定时器调 `msime_client_dictionary_sync`** — 最强的理由是与遥测上传一样，宿主完全掌握线程和生命周期。不用：同样的调度（看文件、算指纹、按 `next_check_ms` 排下一次、没配置时只是定时再问）要在 Objective-C++、IBus 和 Fcitx5 的 C++ 里各写一份；放在 Rust 里一份，测试直接喂时间，三个宿主只剩起、停两个调用。

- **Windows 的同步目录直接用账号目录 `account`（云剪贴板中继密钥串所在的目录）** — 最强的理由是任务要求「照云剪贴板中继的选择」，所有进程都已经知道这个目录。不用：词库密钥串的文件名同样是 `cloud-clipboard-relay-keystore`，放在一起两个功能会读写同一份身份和封装，正是上面「分开密钥串」要避免的；所以照中继的选择取同一个父目录（本用户的 `%LOCALAPPDATA%\<本版本的用户目录>`），另建 `dictionary-sync`。
- **Windows 的同步目录放状态根** — 最强的理由是 Server 和设置窗口本来就共用状态根，偏好也在那里。不用：安装后的状态根是安装器的 DataDir，整台机器一个目录、每个用户都能改，里面不能放词条明文和设备私钥，几个 Windows 用户也会共用一个设备身份。
- **Windows 的 periodic 也放在设置窗口里（像共享页那样开着设置时定时）** — 最强的理由是设置窗口开着时状态能自己刷新。不用：Server 已经在定时，两边都定时只会多花额度；设置窗口在进入页面、点「立即同步」和设备操作后都会重读状态。

- **额度不足就固定再等三十分钟** — 计算简单、能避免频繁唤醒，但滚动窗口中的较早请求可能很快过期，固定等待会无谓推迟用户已排队的改动；使用已有请求时间计算最早可启动点，不改变额度或网络协议。

- **只按 `RemoteStore` 逻辑调用计费** — 无需传输层参与，模拟存储也能直接验证预算；但一次创建还可能先建临时目录，HTTP 限流重试和失败清理也会增加请求，逻辑调用数不能约束真实网盘额度。实际 WebDAV 在发送前拦截并报告真实增量，逻辑估算仅作为其他存储的回退。

- **取出历史窗口前先克隆一份留在状态里** — 最强的理由是保留原先的局部累加结构，同时让中途保存带上旧记录。不采用：核心不需要临时取走历史，结束时直接追加即可，避免维护两份窗口。

## Consequences

- **收益**：有 WebDAV 网盘的用户不用水杉账号就能在设备之间同步「我的词条」，包括删除，离线交错、崩溃和重放后收敛到同一个结果；网盘只见到密文；协议和规则只在 Rust 里一份，六个宿主都经同一个 C 入口驱动。
- **代价**：每台设备都要维护一份共享词库的本机副本（10 万个词约 10 MB）；每次核对读整个「我的词条」，开销随词条数线性增长；用两个功能的设备要分别批准两次；打字自动造的词也会被同步，用户若不希望，需要 Engine 先区分来源；桌面端的远端改动通常在打开设置或者输入会话不占着词库时才写进来。
- **已知限制**：离线超过 90 天、又改过已在别处删除的词条，会让它复活；知道应用密码又持有密钥的人仍能往后追加事件，移除设备后要换应用密码；没有本机状态的新安装没有防回退可言；删掉的密文可能留在网盘回收站。
- **宿主接线的已知缺口**：鸿蒙只在设置应用开着时同步，同步的是设置应用那份「我的词条」，键盘那份经共享沙箱的交换与它收敛（基础访问模式下只收不发），见 [鸿蒙设置应用与键盘的「我的词条」经共享沙箱收敛成一份](2026-10-27-harmony-unified-user-words.md)；macOS 与 Linux 的输入法进程自己触发（见上文「输入法进程的后台同步」），但远端改动仍要等输入会话不占着词库（通常是打开设置时）才写进本机。
- **还没做的**：真实的坚果云、Nextcloud 上的端到端验收；真实词库规模下核对和首次上传的耗时测量；HarmonyOS 上 `directory` 的跨进程共用与键盘个人词库接线；iOS 键盘扩展在真机上调 `local_change` 的内存占用；Android 在真实网盘上两个进程同时同步的验证及键盘内待批准设备提示；Windows 真实 Server 删词触发和首次并发登记的验收。各宿主接线分别由 #10046（Windows）、#10050（共享设置页）和 #10060（Android）落地。
