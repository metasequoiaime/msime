# Agent Note: 云剪贴板存到用户的 WebDAV 网盘，客户端在本机扮演中继

Status: implemented

## Problem

云剪贴板有两条路：水杉账号（`api.msime.app`）和 [自建中继](2026-10-12-cloud-clipboard-relay.md)。不想依赖官方服务的用户只能自己部署一台带公网证书的中继，大多数人做不到。很多用户手里已经有坚果云、Nextcloud 这类 WebDAV 网盘，维护者同意把它作为第三种同步方式。

网盘只会存取文件，没有能执行的服务端逻辑：中继在一个事务里做的那些判断——换钥时比较 `previous_key_id`、20 台设备上限和淘汰、去重时保留原编号、50 条上限——没有地方跑。坚果云又有自己的脾气：`PUT If-None-Match: *` 被忽略、`GET`/`HEAD` 没有 ETag、免费账号每 30 分钟 600 个请求与其他第三方应用共用、根目录下的文件夹删不掉。

## Decision

存储布局、事件格式、读写算法和限制写在 [`docs/cloud-clipboard-webdav.md`](../../../../docs/cloud-clipboard-webdav.md)，那是契约；这里记为什么这样定。

- **客户端里的虚拟中继，协议一字不改**：端到端加密驱动照旧发中继的 12 个接口，`clipboard_webdav::VirtualRelay::send` 读写网盘上的日志来回答，状态码和正文与参考中继相同。加密、密钥串、设备批准、核对码和驱动对服务端的不信任（核对 `device_id == SHA-256(公钥)`、重算 `key_id`、不认服务端的「已批准」）全部沿用。`RelayTransport` 装两种后端，`RelayClipboard` 其余部分不分后端，宿主的中继选路和 C ABI 因此只需要多认一种配置。
- **语义只有一份，日志核心不碰网络**：`client-core` 的 `cloud::clipboard_log` 按序号重放事件，规则逐条对照参考中继的 `RelayStore::handle`，中继的五个单元测试一一移植过来。请求的解析和不依赖状态的校验（路由、正文形状、公钥与编号一致、封装和密文格式）从 `store.rs` 挪进这里，参考中继直接调用，两边答出的错误码不会漂移；中继因此把 `msime-client-core` 从测试依赖改为正常依赖。
- **只追加的事件日志，序号是唯一的文件名，抢到下一个序号的写入才算数**：这相当于把中继的「一个请求一个事务」换成「一个请求抢一个序号」。并发换钥只有一个抢到，输的一方重读后比较 `previous_key_id` 失败，驱动收到 409 `clipboard_key_conflict` 后按原有逻辑重取状态。被拒绝或者不改变状态的请求不写事件，只在这一次刚读过网盘时才直接回答，免得拿落后的缓存答错。
- **独占创建是 `PUT` 到唯一的临时名再 `MOVE` 并带 `Overwrite: F`**：坚果云实测（见 Verification）只有这一种做法每轮恰好一个成功。409 和 412 都算没抢到；409 同时也是「目标目录已经被删」，同样重读，不需要区分。所有网盘走同一条代码路径，Nextcloud（sabre/dav）也支持。
- **事件用哈希串成链，本机记着链头和密钥代数，防回退**：知道应用密码的人（包括被移除的设备）能删掉一次换钥让旧密钥复活。每个事件带上一个事件文件的 SHA-256，本机下一个读到的事件接不上记得的链头、或者从快照重新开始时位置和代数变小，就报 `webdav_rollback` 不接受。同一条链也让「网盘的独占创建其实不可靠、两台设备都以为写成了同一个序号」在后续读写里暴露出来，而不是悄悄分叉。设计评估里只要求记住最大的 (epoch, 序号, 代数)；链头不多花一个请求，却能挡住「删掉一段、再写一段更长的」这种改写，所以加上。
- **坏事件占序号但不改状态**：解析不了或在当时的状态上会被拒绝的事件，所有设备都同样跳过它、照样接上链。写入的设备在写之前已经在同一个状态上试过，正常不会写出这种事件；这条规则只防一个坏文件卡住所有设备。
- **封口与确定的快照**：攒了 64 个以上的事件、有条目过了保留期、或者刚清空、换钥、关闭开关时，一个 `seal` 事件抢下一个序号关闭当前 epoch，下一个 epoch 的 `snapshot.json` 是封口那一刻的状态，字节由日志唯一决定，谁写成都一样，封口的设备中断时下一台补上。旧 epoch 在 120 秒宽限期后删除，删除失败不再试。删掉的密文可能还在网盘的回收站里，文档写明。
- **不轮询，两秒内的缓存直接用**：面板本来就在打开和刷新时拉取，读取就是一个 `PROPFIND` 加上新事件的 `GET`；驱动一个操作连着的几个读请求共用一次同步。坚果云的配额（600 次每 30 分钟，与其他应用共用）是硬约束，后台轮询会很快耗光它。429、503 按 `Retry-After` 退避（缺省 1、2、4 秒，最多三次），要等超过 8 秒就直接报 `webdav_rate_limited`，不让输入法挂着。
- **保存前「测试连接」**：建探测子目录、独占创建两次（第二次必须失败）、刚写的马上列得出、四路并发抢同一个名字恰好一个成功，然后删掉探测目录。探测目录建在 `msime-clipboard/` 下面而不是直接在基地址下，因为用户把基地址选在坚果云根目录时，根目录下的文件夹删不掉。它只证明语义，证明不了任何负载下都原子。
- **测试用真的 WebDAV 服务端**：`tests/webdav_flow.rs` 用 `dav-server`（维护者同意的测试依赖）的内存文件系统跑与 `flow.rs` 相同的完整流程。它放在参考中继的 crate 里，因为那里已经有 axum 和 tokio 能把 `dav-server` 跑起来；放进 `client-services` 就要给它另加 HTTP 服务端依赖，维护者只批了 `dav-server` 一个。`dav-server` 的 MOVE 先查目标再改名，并发时不保证只有一个成功，测试外层用一把锁让请求逐个处理；不可靠网盘的行为由 `clipboard_webdav_tests.rs` 里可注入故障的假网盘覆盖。

## Alternatives considered

- **Cloudflare Worker 之类的托管中继** — 最强的理由是协议、实现都现成：参考中继的逻辑搬到 Worker + D1 上，用户点几下就有一台带证书的中继，事务、去重、上限都在服务端，客户端什么都不用改。不用：用户要注册另一家云服务、管理一份部署，出了问题要会看它的日志，这正是自建中继已经覆盖、而大多数用户做不到的那部分；而网盘是用户已经有、已经信任、已经在多台设备上登录过的东西。
- **S3 兼容的对象存储** — 有真正的条件写入（`If-None-Match: *` 在 AWS S3、R2 上都可靠），不用临时文件加 MOVE，列表也是强一致的。不用：普通用户手里很少有 S3 桶和访问密钥，国内常见的网盘基本只给 WebDAV；签名（SigV4）还要再引入一套客户端实现。日志格式与传输无关，以后要加 S3 只需要另一个独占创建的实现。
- **本机的同步文件夹（让网盘客户端去同步）** — 最省事，不用网络代码，任何同步盘（iCloud Drive、Dropbox、坚果云客户端）都能用，也没有请求配额。不用：移动端的输入法进程读不到别的应用的同步文件夹；同步客户端遇到同时修改会生成「冲突副本」而不是拒绝其中一个，独占创建无从谈起，日志会悄悄分叉；何时同步也不受控制。
- **`PUT` 带 `If-None-Match: *` 做独占创建** — 这是 HTTP 标准里本来的写法，一个请求就够，sabre/dav 也实现了。不用：坚果云实测完全忽略这个头，五到八个并发写入全部答 204、互相覆盖，而坚果云是国内 WebDAV 用户最多的网盘。改用 PUT 临时名加 MOVE 只多一个请求。
- **一个可变的状态文件，用 ETag 做比较后交换** — 一个文件、一次 GET 就是全部状态，不用重放。不用：坚果云的 `GET`/`HEAD` 不返回 ETag（只有 PROPFIND 里有 `getetag`），比较和写入之间就有空档；`If-Match` 写错的 ETag 坚果云会答 412，但拿不到可靠的当前 ETag 就没法安全地用它。只追加的日志不需要原地修改任何文件。

## Consequences

- **收益**：有 WebDAV 网盘的用户不用登录水杉账号、不用部署服务就能跨设备用云剪贴板，网盘只见到密文；参考中继和 WebDAV 后端共用同一份请求校验，日志核心逐条对照中继的单元测试。
- **代价**：每个设备都要重放日志、维护一份本机缓存；一次上传至少三个请求（中继是一个），坚果云免费账号的配额要和其他应用分；没有实时推送。网盘看得到每次写入的时间和次数，比中继多一点元数据；删掉的密文可能留在回收站。知道应用密码的人仍能往后追加事件（与中继令牌泄露同级），只能靠文档提醒移除设备后换应用密码。新安装没有本机缓存，第一次读时没有防回退可言。
- **已知缺口**：这一步只有 Rust 客户端：偏好 `cloud_clipboard_webdav`、宿主选路和 C ABI、Android 的 exchange、各平台设置页在后续改动里接入。iOS 和 HarmonyOS 的原生宿主还没接中继，同样也不会有 WebDAV。

## Verification

- 坚果云（2026-10-26 用维护者的坚果云账号做过一次性的手工探测，四轮、每轮五到八个并发写入）：`PUT If-None-Match: *` 被忽略，并发的 PUT 全部答 204、互相覆盖；PUT 到唯一的临时名再 `MOVE` 带 `Overwrite: F`，每轮恰好一个 201、其余全部 409，目标内容来自唯一的赢家；PROPFIND Depth 0/1 可用，新写的文件马上列得出；`getetag` 只在 PROPFIND 里，`GET`/`HEAD` 不带 ETag；`If-Match` 写错的 ETag 答 412；子目录能删（204），根目录下的文件夹删除答 403；免费账号每 30 分钟 600 个请求、与所有第三方应用共用，一次 PROPFIND 最多 750 项，必须用应用密码。这些凭据只用于那一次手工探测，没有进入代码、测试、日志或 CI。
- `cargo test -p msime-client-core --lib cloud::clipboard_log`：16 项，含从 `store.rs` 移植的五项、重放得出同一状态、并发建钥只留一个、坏事件占序号不改状态、接不上链头被拒、封口后快照逐字节相同、快照逐字段校验、保留期过滤与封口删除、不改变状态的写入不写事件、压缩条件、关闭开关推进密钥代数。
- `cargo test -p msime-client-services --lib clipboard_webdav`：20 项，在可注入故障的假网盘上跑完整流程，并证明：缓存落后的设备 MOVE 被 412 拒绝后接在后面写；三台设备并发上传各 4 条全部落地且不重复（连跑六次稳定）；MOVE 先查后写的网盘让两台设备都「写成」同一序号，下一次读写报 `webdav_rollback`；新文件晚几次才列得出时只多几次重试，一直列不出来时有限次后放弃（`relay_unavailable`），不写坏日志；改写历史、删掉整个文件夹、换上代数更小的快照都报 `webdav_rollback`，删掉本机缓存后恢复；限流按 1、1 秒和 1、2、4 秒退避，`Retry-After: 3600` 直接报 `webdav_rate_limited`；401 是 `relay_unauthorized`；不合规的请求不碰网盘；缓存过期前不重读，一次写入只有 PUT 和 MOVE；缓存仅本人可读写、绑定地址和账号，换应用密码不换空间；测试连接放过好网盘且不留文件，拦下不理会 `Overwrite: F`、MOVE 不原子、文件夹不存在的网盘；多状态响应按本地名解析坚果云和 sabre/dav 两种写法；请求路径跑不出用户选的文件夹。
- `cargo test -p msime-clipboard-relay`：中继原有的单元测试和 `flow.rs` 在改用共享校验后照常通过；`tests/webdav_flow.rs` 对着 `dav-server` 跑完整流程、测试连接通过、错误的应用密码被拒、只借 `RelayTransport::with_directory` 的宿主（Android 的做法）与 `RelayClipboard` 设备互相批准和互传。
- 没有验证的：真实的坚果云和 Nextcloud 上的端到端流程（要在设置页接入之后手工走一遍，步骤写在合并说明里）；高并发下网盘 MOVE 的原子性（测试连接证明不了）。
