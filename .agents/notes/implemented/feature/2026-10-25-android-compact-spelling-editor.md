# Agent Note: Android 放大拼写条压成一行，去掉斜指针与下方手柄

Status: implemented

## Problem

[拼写放大编辑](2026-10-21-android-composition-magnifier.md)按 #9016 与 #8633 做出的编辑条在键盘上方占了三层：一行贴边、没有内边距的提示「拖动右侧手柄移动光标」和「完成」，一行 26sp 的放大拼写，再往下留 32dp 空白放一个 56dp 的圆手柄，手柄与光标之间用 Canvas 画一根 45° 的斜杆和箭头。整块约 180dp 高，打开时把候选栏和键盘一起往上顶，输入框被挤到屏幕中间。维护者在 Pixel 3 XL 上看过后认为这块界面不可接受，尤其是那根长箭头和它占掉的高度。

## Decision

编辑条只占一行（约 52dp）：左边是放大的拼写条（22sp，闪动光标），右边是「完成」，没有提示行、下方手柄和斜指针。

- 点拼写条把光标放到点中的字母前，与原来相同。
- 在拼写条上左右拖动，超过系统触摸阈值后按手指的位移移动光标（起点是按下时光标的位置，不是手指落点），手指不必压在光标上；拖到条两端 28dp 内停留时按 90ms 一格持续移动并滚动长拼写，沿用原来的边缘逻辑。没超过阈值就松手算一次点按。
- 拖动时光标常亮不闪，便于看清。
- 无障碍节点仍是「放大拼写」，支持设置选区，提示文字「左右拖动移动光标」放在 `hintText` 里；面板描述仍是「拼写编辑面板」，「完成拼写编辑」不变。
- 编辑入口（点输入框里的拼写、点键盘标题「编辑拼写」）、引擎光标命令和关闭时机都不变。

2026-10-28 的 API 28 核心冒烟在长拼写边缘拖动上出现间歇性失败。临时夹具采样发现，`awaitEdge` 把目标选区条件交给 `DeviceSmoke.find`：目标尚未到端点时，查找还会继续逐个刷新其余无障碍节点。一次遍历实际占用 9.9–11.3 秒，整个 20 秒预算里只能观察到极少数选区快照，甚至可能过了截止时间才返回成功。现在每次拖动前查找拼写节点并读取当前坐标，按住和松手后的轮询都只对这个节点调用 [`AccessibilityNodeInfo.refresh()`](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#refresh())；节点消失立即失败。总预算、双端到达断言和 `finally` 松手保持，产品的边缘移动逻辑不改。临时采样只记录合成用例的坐标、选区下标与耗时，诊断代码不提交。

## Alternatives considered

- 保留手柄，只把它挪进同一行的右端：仍满足 #9016「与光标拉开距离的右侧手柄」的字面要求，高度也能压到一行。但手柄固定在条的右端时，正好落在右侧边缘持续移动区里，一按就开始往右跑；要避开就得另做一套不依赖边缘的长拼写滚动。拖动整条拼写同样做到手指不挡光标，少一个控件。
- 保留斜指针，只缩小尺寸：#8633 的报告者点名要 45° 斜指针。但指针要从光标下缘斜着连到手柄，手柄就只能在拼写下面，高度至少两行；维护者明确不要这种占高的样子。
- 去掉放大条，只在输入框里点按定位：最省地方。但点小字号的拼写本来就不准，这正是 #9016 要放大条的原因。
- 继续从窗口根节点搜索选区条件：能够自动找到重建后的控件，不需要保留节点。但边缘拖动依赖同一触摸目标持续存在，控件消失应当失败；逐个刷新其余节点也占掉了大部分等待预算，因此选择直接刷新目标，不放宽时间或减少断言。

## Consequences

键盘打开编辑条时只比平时高一行，输入框基本不再被顶走。代价是 #8633 要的斜指针和 #9016 字面上的「右侧手柄」都没有了，改由整条相对拖动满足「手指不盖住光标」；如果报告者坚持要手柄形态，需要在一行之内重新设计，且要处理与边缘滚动区的冲突。拼写字号从 26sp 降到 22sp，长拼写一屏能多显示几个字母。
