# Agent Note: 上屏后联想的词库续写按逐键打分器排序

Status: implemented

## Problem

[上屏后联想](2026-10-24-post-commit-prediction.md)（#9433）的行有两种来源：个人习惯（`PersonalNgramStore::next_words`）在前，词库续写（`PinyinDatabase::query_next_words`，与刚上屏的词同字同音开头的长词，取后半截）在后。词库续写按词频取前 8 条，不看上文：上屏「吃」之后，不论前面写的是「今天想」还是「这个人很」，给的都是同一串。逐键重排已经有一个读上文的字级语言模型（[CandidateScorer](../architecture/2026-11-01-candidate-scorer-boundary.md)，随包的 `model-v1` 或 [ONNX Runtime 后端](../architecture/2026-11-01-onnx-rerank-backend.md)的 8x448 / 6x256），联想却没有用它。

## Decision

宿主挂了逐键打分器时，词库续写多取一池，按模型给的「这一行接在上文后面」的总对数概率重排，再截到 8 条：

- **候选池在引擎里，默认关。** `Session::set_prediction_pool(true)` 之后，`Prediction::show` 向词库要 32 条续写（与 `query_next_words` 每张表的上限相同），显示的仍是按词频的前 8 条，多出来的留在 `spare` 里。关着时查询、去重、粗俗词过滤与之前逐行相同，没挂打分器的宿主看不出任何变化。runtime 在 `set_candidate_scorer` / `set_reranker` 和换引擎（`replace_engine`）时按有没有逐键打分器下发这个开关，宿主不用改。
- **排序规则在引擎的 `ordering` 里。** `prediction_order(scorer, context, rows)`：上文按 `rerank_context` 截到模型读得下，逐字平均分乘字数得到总分，从高到低排，同分保持词频顺序，NaN 排最后；少于两行或分数条数不对时不动。只排词库续写；个人习惯行是用户自己的数据，原样留在前面、顺序不变，模型也看不到它们；去重仍是个人行优先。
- **每次上屏只打一次分，在快照之前。** 引擎在 `show` 时记下这次上屏的文字（连续选联想时是选中的那一行，不是种子），`Session::order_prediction(scorer, before)` 用掉它后就不再排。runtime 在 `refresh` 取引擎快照之前调它，`before` 是 `ai_context` 接上暂存的词段（这次上屏的文字要到 `transition` 才进 `ai_context`）。排好的是引擎自己的行，所以座位就是引擎下标，`engine_order` 不参与，选中哪一行上屏的就是哪一行，代次核对、插件变换都照旧。
- **跟着逐键重排的开关走。** 打分器只在「整句联想增强」这类打开逐键模型的偏好下挂上（host-api 的 `keyboard_reranker_enabled`），联想排序没有单独的开关；隐私门禁（`set_prediction_allowed`）和学习开关对联想的约束不变，被隐私门禁关掉时连分都不打。
- **在会话线程上同步打分。** 一次上屏只打一页（最多 32 条、每条一到六个字），延迟见下面的评测；不像停顿重排那样搬到后台线程。上屏时模型为新的上文编码前缀，下一次按键读的是同一段上文，ONNX 后端和随包模型都按前缀缓存，这一份编码下一键不用再付。

## Alternatives considered

- **保持词频顺序** — 最强的理由是零成本、完全可预期，而且联想默认关、只在安卓上开着。但它不看上文：同一个词之后永远是同一串建议，评测里首位命中只有 TODAY_H1，而模型排序在同一批句子上是 MODEL_H1；模型已经随包、按键时已经在跑，多花的只是上屏时的一次打分。
- **个人习惯行也交给模型排** — 好处是模型能把与上文不搭的旧习惯往后放。没有采用：个人行是用户自己打出来的、按次数排的，比模型更懂这个用户；模型的语料里没有用户自己的说法，按它排会把用户最常用的接续挤到后面。个人行最多 8 条、来自用户本人，留在前面也最容易解释。
- **只重排显示的 8 条，不多取** — 不多查词库、打分量少四倍。可行性评测里同样按总分，从 32 条里挑比只排前 8 条首位命中更高（单字上屏 16.9% 对 18.8%，两字以内 8.7% 对 9.3%），前 8 条的召回也更高（25.5% 对 32.2%、13.4% 对 15.6%）；一次上屏多打 24 条的代价见上面的延迟。
- **用逐字平均分排序** — 与逐键重排同一个口径。联想要猜的是接下来真会写的那一段，平均分不让长续写为多出的字付概率；可行性评测里同样从 32 条里挑，平均分的首位命中低于总分（16.7% 对 18.8%、8.6% 对 9.3%）。
- **让模型自己生成词库之外的续写** — 覆盖面最大：词库续写只有与上屏的词同字开头的长词，答案在 32 条池里的只有一部分。没有在这一步做：要逐字生成并限制在合法词里，需要解码策略、粗俗词与隐私过滤、更长的延迟预算，属于下一步。
- **放到后台线程打分，像停顿重排那样** — 不占会话线程。但联想在上屏的同一次派发里就要显示，后台算完再换顺序会让用户先看到一串再看到另一串，选中的行也要跨代次核对；量下来一次打分在会话线程上的代价见上表，先不搬。

## Consequences

- **收益**：挂了打分器的宿主，上屏后联想按上文排序，首位和前三的命中明显提高（见评测）；排序规则只有一份，在引擎里，网页引擎或第三方宿主挂一个 `CandidateScorer` 就能用同一套规则。
- **代价**：每次产生联想的上屏多一次模型打分和一次多取 32 条的词库查询；联想行在有没有模型的宿主之间不再相同。
- **已知上限**：只能在词库续写的范围里挑，答案不在 32 条池里时排序帮不上；词库续写按刚上屏的那一个词查，暂存词段只进模型的上文、不进查询。延迟在低端手机上会是 Mac 的数倍，手机档（6x256）或随包模型在真机上的上屏延迟还没量；量出来超过一帧时，要么把打分搬到后台，要么在手机上缩小候选池。

## Verification

- `crates/engine/src/session/tests/prediction_pool.rs`：没开池时与之前逐行相同、给了打分器也不打分；开池后在排序前显示的仍是词频前 8 条；整池按总分排（平均分高、总分低的两字行排在单字行后面）、只显示 8 条、上文是之前的文字接上这次上屏的词；每次上屏只打一次分；分数条数不对时不动；重排后选第 0 行上屏的就是它，下一轮按它的种子查、上文接的是这次上屏的那一行；只有一条续写时不打分；个人行在前且顺序不变、不送去打分；关池丢掉待排的那一次。`ordering.rs` 的 `prediction_order_*` 守住总分、同分保序、NaN 排最后和上文截取。
- `crates/input-runtime/src/tests/prediction_rerank.rs`：真实引擎加桩打分器，覆盖没挂打分器时保持词频、挂上时按上屏后的上文排序且后续刷新不再打分、每个座位选中上屏的都是它显示的那一行、旧代次的身份作废、拿掉打分器和换引擎、隐私门禁、暂存词段进上文。
- `next_word_eval`：上面的表；`cargo run --release -p msime-input-runtime --example next_word_eval -- --resources <锁定资源> --corpus cmn_sentences_detailed.tsv --longest 2`，加 `--features onnx-rerank`（`ORT_LIB_LOCATION` 见 `tools/onnxruntime-minimal/README.md`）和 `--onnx-model <目录>` 量 ONNX 后端。
