# Agent Note: 上屏后联想的词库续写按逐键打分器排序

Status: implemented

## Problem

[上屏后联想](2026-10-24-post-commit-prediction.md)（#9433）的行有两种来源：个人习惯（`PersonalNgramStore::next_words`）在前，词库续写（`PinyinDatabase::query_next_words`，与刚上屏的词同字同音开头的长词，取后半截）在后。词库续写按词频取前 8 条，不看上文：上屏「吃」之后，不论前面写的是「今天想」还是「这个人很」，给的都是同一串。逐键重排已经有一个读上文的字级语言模型（[CandidateScorer](../architecture/2026-11-01-candidate-scorer-boundary.md)，随包的 `model-v1` 或 [ONNX Runtime 后端](../architecture/2026-11-01-onnx-rerank-backend.md)的 8x448 / 6x256），联想却没有用它。

## Decision

宿主挂了够快的逐键打分器（现在只有 ONNX Runtime 后端）时，词库续写多取一池，按模型给的「这一行接在上文后面」的总对数概率重排，再截到 8 条；挂的是随包 `model-v1` 时不排，联想与没挂打分器时逐行相同：

- **候选池在引擎里，默认关。** `Session::set_prediction_pool(true)` 之后，`Prediction::show` 向词库要 32 条续写（与 `query_next_words` 每张表的上限相同），显示的仍是按词频的前 8 条，多出来的留在 `spare` 里。关着时查询、去重、粗俗词过滤与之前逐行相同，没挂打分器的宿主看不出任何变化。runtime 在 `set_candidate_scorer` / `set_reranker` 和换引擎（`replace_engine`）时按挂着的打分器够不够快（下一条）下发这个开关，宿主不用改。
- **只交给报自己够快的打分器。** `CandidateScorer::scores_prediction_pool_within_a_frame`：在上屏的那一次派发里同步给一整池（最多 32 条）打分，是否仍在一帧之内。默认 `false`，`OnnxScorer` 报 `true`，随包的 `Reranker` 不覆盖。runtime 只认这个能力，不认打分器的类型：宿主怎么选后端、以后换什么后端，都不用改这里。不报的打分器挂着时，引擎不开候选池，`order_prediction` 不调，联想走的就是没挂打分器的那条路，逐行相同（`prediction_rerank.rs` 逐行比较）。逐键重排不受影响，随包模型照旧给按键排序。
- **排序规则在引擎的 `ordering` 里。** `prediction_order(scorer, context, rows)`：上文按 `rerank_context` 截到模型读得下，逐字平均分乘字数得到总分，从高到低排，同分保持词频顺序，NaN 排最后；少于两行或分数条数不对时不动。只排词库续写；个人习惯行是用户自己的数据，原样留在前面、顺序不变，模型也看不到它们；去重仍是个人行优先。
- **每次上屏只打一次分，在快照之前。** 引擎在 `show` 时记下这次上屏的文字（连续选联想时是选中的那一行，不是种子），`Session::order_prediction(scorer, before)` 用掉它后就不再排。runtime 在 `refresh` 取引擎快照之前调它，`before` 是 `ai_context` 接上暂存的词段（这次上屏的文字要到 `transition` 才进 `ai_context`）。排好的是引擎自己的行，所以座位就是引擎下标，`engine_order` 不参与，选中哪一行上屏的就是哪一行，代次核对、插件变换都照旧。
- **跟着逐键重排的开关走。** 打分器只在「整句联想增强」这类打开逐键模型的偏好下挂上（host-api 的 `keyboard_reranker_enabled`），联想排序没有单独的开关；挂上的是 ONNX 后端才排，退回随包模型时不排；隐私门禁（`set_prediction_allowed`）和学习开关对联想的约束不变，被隐私门禁关掉时连分都不打。
- **在会话线程上同步打分。** 一次上屏只打一页（最多 32 条、每条一到六个字），延迟见下面的评测；不像停顿重排那样搬到后台线程。这正是只交给够快的打分器的原因：随包模型同步打这一池在 Pixel 3 XL 上要一百多毫秒。上屏时模型为新的上文编码前缀，下一次按键读的是同一段上文，ONNX 后端和随包模型都按前缀缓存，这一份编码下一键不用再付。

## 评测

`crates/input-runtime/examples/next_word_eval.rs` 在真实运行时里量：Tatoeba 中文句子（CC-BY 2.0 FR，不在 chinese-ime-lm 的训练语料里，语料不进仓库）取开头的汉字串，按词库正向最长匹配切词，随机挑一个不在句末的词。每一臂清空上文、放进这条的上文、打这个词的拼音、选中它上屏，读上屏后的联想行；联想的一行是句子剩下部分的前缀就算命中，分母是所有走到上屏的用例。规则（总分、32 条池、个人行在前）在跑评测之前定下，没有按评测数字调过。资源是 `desktop-dictionary.lock.json` 锁定的 dict-v2.0.41，种子 7，各 3000 句，不学习（没有个人行）。

两组用例：「单字」只切单字词（上屏的都是一个字），「两字以内」最长切两字词。hit@k 是前 k 行里有一行命中，chars@1 是首行命中时的字数按用例平均；括号里是 McNemar 检验（连续性校正）的 p 值，以及只有这一臂命中 / 只有今天命中的用例数。

| 单字上屏（3000 例，今天有联想 85.0%） | hit@1 | hit@3 | hit@8 | chars@1 |
|---|---|---|---|---|
| 今天（词频） | 11.5% | 19.0% | 26.6% | 0.118 |
| model-v1（随包 4.25M） | 16.3%（p 2e-17，+209/−67） | 23.4%（p 7e-14） | 30.5%（p 5e-15） | 0.165 |
| 6x256 | 18.0%（p 5e-26，+262/−69） | 25.5%（p 1e-28） | 31.7%（p 2e-23） | 0.185 |
| 8x448 | 18.4%（p 4e-28，+279/−72） | 26.4%（p 1e-35） | 31.8%（p 4e-24） | 0.188 |

| 两字以内上屏（3000 例，今天有联想 79.7%） | hit@1 | hit@3 | hit@8 | chars@1 |
|---|---|---|---|---|
| 今天（词频） | 7.2% | 11.3% | 14.9% | 0.084 |
| model-v1 | 7.9%（p 0.076，+74/−53） | 12.1%（p 0.051） | 14.8%（p 0.91，+41/−43） | 0.086 |
| 6x256 | 9.3%（p 1e-8，+95/−30） | 13.2%（p 8e-8） | 15.9%（p 1e-3） | 0.107 |
| 8x448 | 9.3%（p 6e-8，+97/−34） | 13.6%（p 2e-9） | 16.2%（p 2e-5） | 0.105 |

两个 ONNX 模型在两组上都显著好于词频顺序，彼此相差不到半个点。随包的 `model-v1` 在单字上屏上显著更好（首位命中 +4.8 个点），在两字以内上首位与前三只高不到一个点、不显著，前八与今天持平（+41/−43）。最初据此让随包模型的宿主也开着这项排序；真机延迟（下面）推翻了这一点，随包模型不排，表里它那一行是 `next_word_eval` 强制排出来的效果（每一臂都套 `Pooled`）。"今天"一臂的首位命中（7.2% / 11.5%）比 Python 可行性评测（6.8% / 9.6%）高，那边用的是旧一版词库（`7c6724…`）、按另一套随机数抽句，数字不能逐格对照。

延迟（上屏那一次 `dispatch`：引擎选词、查续写、打分、取快照；各臂每句轮流先跑，配对差 = 这一臂减「今天」）：

| 臂 | 上屏 p50 | 上屏 p95 | 配对差 p50 | 配对差 p95 |
|---|---|---|---|---|
| 今天（两字以内 / 单字） | 0.31 / 0.90 | 2.21 / 3.94 | — | — |
| model-v1 | 5.65 / 6.37 | 11.51 / 11.24 | 4.87 / 5.12 | 10.98 / 9.41 |
| 6x256（2 线程） | 1.44 / 2.05 | 3.48 / 5.20 | 1.03 / 1.09 | 1.67 / 1.69 |
| 8x448（2 线程） | 3.48 / 4.16 | 6.52 / 7.82 | 2.90 / 3.00 | 5.17 / 5.06 |

单位毫秒，Apple M4 Pro（Mac16,8），每组 2980 次上屏（去掉前 20 次预热）。同一台机器在别的会话满负荷编译时（load average 100–300）第一次跑两字以内那一组，各臂 p95 都涨到 50–135 ms，数字不可用，表里是负载降下来后重跑的（命中率两次逐格相同）。配对差里包括为新的上文编码前缀，这一份下一次按键原本也要付。

真机（Pixel 3 XL，安卓 12，2026-11-02）上随包 `model-v1` 远超一帧。两种量法：

| 量法 | 臂 | 上屏 p50 | 上屏 p95 | 超过 16 ms |
|---|---|---|---|---|
| `next_word_eval` 交叉编译到 aarch64，两字以内 3000 例 | 今天 / model-v1 | 1.75 / 45.74 | 10.50 / 96.16 | — |
| 同上，单字 1000 例 | 今天 / model-v1 | 4.23 / 48.95 | 18.65 / 82.52 | — |
| 装好的 APK 里经 JNI 计 `NativeClient.select`，40 个词连打成一段话、8 轮（去掉第一轮），「增强」开 | 不排序（#10611 的包）/ 排序（本分支合进 #10611 的包） | 2.43 / 133.4 | 18.3 / 156.0 | 21/280 / 280/280 |

`next_word_eval` 的配对差 p50 41–42 ms、p95 75–94 ms，命中率与 Mac 上逐格相同。APK 里的数字更大，没有逐项拆开量过，最可能的差别是上文长度：连着打字时上文一直是满的（模型读得下的那么长），评测的上文是 Tatoeba 句子的开头，平均短得多。同一次量里排序之后下一次按键的 p95 从 23.4 ms 降到 9.7–10.0 ms（上屏时已经为新上文编码过前缀），但省下的远抵不上上屏多出的 130 ms。

## Alternatives considered

- **保持词频顺序** — 最强的理由是零成本、完全可预期，而且联想默认关，现在只有安卓的设置页能打开。但它不看上文：同一个词之后永远是同一串建议。评测里单字上屏的首位命中词频顺序是 11.5%，8x448 排序后 18.4%，随包模型 16.3%；模型已经挂着、按键时已经在跑，多花的只是上屏时的一次打分。
- **个人习惯行也交给模型排** — 好处是模型能把与上文不搭的旧习惯往后放。没有采用：个人行是用户自己打出来的、按次数排的，比模型更懂这个用户；模型的语料里没有用户自己的说法，按它排会把用户最常用的接续挤到后面。个人行最多 8 条、来自用户本人，留在前面也最容易解释。
- **只重排显示的 8 条，不多取** — 不多查词库、打分量少四倍。可行性评测里同样按总分，从 32 条里挑比只排前 8 条首位命中更高（单字上屏 16.9% 对 18.8%，两字以内 8.7% 对 9.3%），前 8 条的召回也更高（25.5% 对 32.2%、13.4% 对 15.6%）；一次上屏多打 24 条的代价见上面的延迟。
- **用逐字平均分排序** — 与逐键重排同一个口径。联想要猜的是接下来真会写的那一段，平均分不让长续写为多出的字付概率；可行性评测里同样从 32 条里挑，平均分的首位命中低于总分（16.7% 对 18.8%、8.6% 对 9.3%）。
- **让模型自己生成词库之外的续写** — 覆盖面最大：词库续写只有与上屏的词同字开头的长词，答案在 32 条池里的只有一部分。没有在这一步做：要逐字生成并限制在合法词里，需要解码策略、粗俗词与隐私过滤、更长的延迟预算，属于下一步。
- **放到后台线程打分，像停顿重排那样** — 不占会话线程，随包模型也能用上。但联想在上屏的同一次派发里就要显示，后台算完再换顺序会让用户先看到一串、一百多毫秒后（Pixel 3 XL 上随包模型的耗时）再看到另一串，这段时间里点下去的那一行和换序后的座位要跨代次核对，还要处理用户已经开始打下一个字时作废这次打分；ONNX 后端同步打分已在一帧以内，不需要它。现在不做：要做时是为随包模型的宿主（Windows、鸿蒙、还没带上 ONNX 产物的各平台）单独加一条异步路径，收益是单字上屏首位命中约 +5 个点、两字以内不显著，值不值得等 ONNX 产物铺开之后再看。
- **随包模型照旧排，但缩小候选池（比如只排显示的 8 条）** — 打分的行少四倍。没有采用：上屏时要为新上文从头编码前缀，这一份不随行数变小；只排 8 条又丢掉了池的大半收益（见上一条「只重排显示的 8 条」），而随包模型在两字以内上屏上本来就不显著。没在真机上量过 8 条的耗时，按行数线性估也在两帧上下，仍然超出预算。
- **等 chinese-ime-lm 0.2.1** — 0.2.1 把决策批量算，约快三倍、结果逐位相同（#10623 把 develop 的锁升到它）。三倍之后 Pixel 3 XL 上每次上屏仍约 45 ms，接近三帧；升级不改变这里的结论，等它合进来后照样不排，只是逐键重排变快。

## Consequences

- **收益**：挂了打分器的宿主，上屏后联想按上文排序，首位和前三的命中明显提高（见评测）；排序规则只有一份，在引擎里，网页引擎或第三方宿主挂一个 `CandidateScorer` 就能用同一套规则。
- **代价**：每次产生联想的上屏多一次模型打分和一次多取 32 条的词库查询；联想行在有没有模型的宿主之间不再相同。
- **已知上限**：只能在词库续写的范围里挑，答案不在 32 条池里时排序帮不上；词库续写按刚上屏的那一个词查，暂存词段只进模型的上文、不进查询。
- **现在没有一个发布的宿主会排**：排序只交给 ONNX 后端，而 ONNX 后端（host-api 的 `onnx-rerank` 特性）还没进任何平台的发布构建；安卓是现在唯一能打开联想的平台，用的是随包模型，所以安卓上的联想与合并前逐行相同。ONNX 后端随哪个平台发布，那个平台的联想就跟着按上文排，不用另改代码；发布前要在那个平台的真机上按上面的方式量一次上屏延迟。

## Verification

- `crates/engine/src/session/tests/prediction_pool.rs`：没开池时与之前逐行相同、给了打分器也不打分；开池后在排序前显示的仍是词频前 8 条；整池按总分排（平均分高、总分低的两字行排在单字行后面）、只显示 8 条、上文是之前的文字接上这次上屏的词；每次上屏只打一次分；分数条数不对时不动；重排后选第 0 行上屏的就是它，下一轮按它的种子查、上文接的是这次上屏的那一行；只有一条续写时不打分；个人行在前且顺序不变、不送去打分；关池丢掉待排的那一次。`ordering.rs` 的 `prediction_order_*` 守住总分、同分保序、NaN 排最后和上文截取。
- `crates/input-runtime/src/tests/prediction_rerank.rs`：真实引擎加桩打分器，覆盖没挂打分器时保持词频、挂上时按上屏后的上文排序且后续刷新不再打分、每个座位选中上屏的都是它显示的那一行、旧代次的身份作废、拿掉打分器和换引擎、隐私门禁、暂存词段进上文。
- `next_word_eval`：上面的表；`cargo run --release -p msime-input-runtime --example next_word_eval -- --resources <锁定资源> --corpus cmn_sentences_detailed.tsv --longest 2`，加 `--features onnx-rerank`（`ORT_LIB_LOCATION` 见 `tools/onnxruntime-minimal/README.md`）和 `--onnx-model <目录>` 量 ONNX 后端。
