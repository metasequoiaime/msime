# Agent Note: Android 中文数字九宫格临时随机排列

Status: implemented

## Problem

#10254 希望按需打乱中文数字九宫格，点击数字后再次打乱。工具栏设置只控制入口是否可见，不能等同于开启随机功能；离开数字页仍保留开关状态，但不应在拼音页继续计算随机排列。英文数字页保持原有布局。

## Decision

Android 本地设置增加默认关闭的「随机数字」工具栏入口，沿既有排序、预览与尺寸规则显示「随」。运行时开关只属于输入法服务，点击仅切换高亮，不自动切页。中文数字九宫格启用时对 0–9 做 Fisher–Yates 排列，数字按其当前键面、沿标准顺序同一条上屏路径（`commitNumberPadText`：U、V 模式和越南语等 Engine 把数字列为拼写时交给会话，其余按字面）提交后重新排列；符号、退格、空格与回车的位置和动作保持。离开九宫格保留开关与上次排列，不取新随机数；关闭时恢复标准键序，英文页不显示该入口且不应用排列。

## Related notes audit

检索活跃笔记中的「随机数字」「打乱数字」没有已有决定。[工具栏按钮排列](../../implemented/feature/2026-10-15-android-toolbar-order.md)的稳定身份和缺项补尾规则继续沿用；[中文默认数字九宫格](../../implemented/feature/2026-10-15-mobile-default-number-pad.md)的数字上屏、底行 0 与统计身份继续沿用；侧边数字键盘与语音启动不改变。

## Alternatives considered

- 把随机开关保存到共享偏好：可以跨服务重启保留，但本需求的设置项只是入口可见性，自动恢复开启会改变普通数字输入，先限定为用户本次服务内主动选择。
- 每次 render 都打乱：实现简单，但换肤、候选刷新与按压重画也会搬动键位，离开数字页仍有额外计算，不采用。render 里只核对随机资格是否与键面一致，资格变了才按已有排列重画键面，不取新随机数。
- 在临时模式进出的代码路径里单独刷新数字键面：只覆盖临时模式，切中/英、藏工具栏等同样改变资格的路径还要各补一处，容易漏，不采用。

## Verification

`check-host.sh` 的宿主与设备源码编译、JVM 冒烟通过；排列策略另外用固定随机源完成 1000 轮完整性、离页零计算、返回沿用及恒等随机排列仍换序验证。原生 JNI 从本分支重编，Gradle 完整开发 APK 编译并开发签名；Rust、共享代码与资源锁和固定 `587b0f9304` 无差异，复用其已验证的 Rust 库和完整资源，不重编未改动部分或复制未提交源码。

API 28 专用 AVD 的 `NumberPadDeviceSmoke -e random-digits true` 通过：全拼 26 键和拼音九键分别验证入口默认关闭、实际原生设置开关只显示入口、真实点击随不跳页、0–9 依次按键面上屏且每次换序、无障碍描述一致、其他符号与退格坐标不变、离页返回沿用、关闭恢复、英文横排不显示入口、不受随机状态影响。测试末尾恢复合成偏好。普通数字页的全拼、小鹤、十四键、九键、笔画、注音九键与全角回归也通过，包含数字字面提交、符号往返和统计身份。远端 `bash scripts/verify-local.sh --quick` 退出 0。API 35 专项与普通数字回归也已通过，包含同样的两种中文键面、英文隔离和普通数字页全部方案。

覆盖安装后的复验暴露了夹具前提：首次安装说明可能挡住原生页，设置窗口与编辑器的两个焦点会话也不能靠上一焦点推断当前中英文。夹具只确认标题明确的已知安装说明，先等「编辑工具栏」页面、按原生 `Switch` 类型定位，再实际保存；回到编辑器后明确选择中文再验证中文入口，英文隔离仍单独断言。修正后远端 quick（`20261030-233055`）和 API 28 随机专项通过，新一轮 API 28／35 随机专项和普通数字回归均通过，运行 `20261030-233055` 退出 0，四份日志为 `target/android/random-notice-final28.log`、`random-notice-number28.log`、`random-notice-final35.log`、`random-notice-number35.log`。

审查发现首版把数字键直接接到字面上屏，绕开了 `NumberPadPunctuation.typesThroughSession`，所有用户在 U、V 模式和越南语组字里点数字九宫格的数字都会被字面上屏，与标准顺序的行为不一致。改为先按键面取数字、走 `commitNumberPadText`、再计数后换序；随机专项在全拼 26 键里补了 U 模式下点数字页的 4 必须进组字（输入框显示 `U4`）的断言。这一轮只做了源码阅读核对，修正后的专项还没在模拟器上跑过。

第二轮审查指出两处与临时模式的交互。一是随机资格本来就要求 `local_mode` 为 `none`，U 模式里数字页是标准顺序、点数字也不换序，上一轮补的「U 模式照常换序」断言必然失败；改为断言 U 模式里是标准顺序、点 4 组字为 `U4` 且不换序。二是在数字页上进出临时模式（以及切中/英、藏起工具栏）时键区不重建，只有绑定、开关和点数字时才刷新键面，资格翻转后键面停在旧排列，键面写着 4、点下去上屏的却是另一个数字。`render` 在重建判断之后调用 `syncNumberDigitFaces`：随机没开或不在数字页时直接返回，否则只在资格与上次画键面时不同才刷新，不取新的随机数，退出临时模式后回到进入前的排列。专项在退格退出 U 模式后断言数字页当场恢复进入前的随机排列。这一轮同样只经源码阅读和编译核对。

`35c168de88` 的 PR 设备检查（API 35，run 41212308772）在「U 模式里数字页保持标准顺序」超时，输入法停在 U 模式的数字页。logcat 里每次点击都有按键音，0–9 十次都在，之后「返回原键盘」再没有按键音、只多画了两帧，15 秒后测试收尾，时间对得上进 U 模式前后那两步等待，不是点 4 之后的组字等待：「返回」的点击没有触发，键盘留在数字页，Shift+U 在数字页上进了 U 模式（左列换成半角写法），字母页的 123 找不到。只把阶段拆细、超时时报出输入框文字和全部窗口与节点的同一份代码（`4c33563a06`，run 41228345096）在 API 35 上整套通过，U 模式进组字、不换序和退出后恢复随机排列都成立，所以产品逻辑和断言本身没有问题，问题在夹具：触摸和 `sendKeySync` 是两条互不等待的注入路径，点完「返回」不等它生效就发硬件键。专项改为点「返回」后先等字母页的 123 出现再发 Shift+U；点击真丢了也会停在这一步，报错不再落到后面无关的等待上。

随后合入 develop 的 nightly 在 API 28 的同一专项暴露了第二个夹具边界：`Instrumentation.sendKeySync` 在 Android 9 直接抛 `SecurityException`，而 API 35 仍能注入。设备测试现在把需要 Shift 元状态的按下、松开事件统一交给 `UiAutomation.injectInputEvent`，并显式标记 `SOURCE_KEYBOARD`；普通触摸和真实键盘 `uinput` 路径不变。共享的 `DeviceSmoke.injectKeyboardEvent` 同时供随机数字和两个辅助码回归使用，避免同一平台版本再次走受限的注入接口。

## Consequences

重排在点击当前数字完成后只更新标签、无障碍描述与统计身份，不重建键区；离页不取随机数。工具入口默认不显示，不改其他工具的默认值，已有排序缺少新稳定 ID 时补尾。关闭入口或把整条工具栏设为隐藏都清除运行时开启状态，避免够不到的开关继续影响输入；取消隐藏后随保持未开启。服务重启后随机状态关闭，入口设置仍保留。

排列用于主动选择的输入体验，不承诺抵御录屏等攻击。新 head CI 仍须单独收结果，不能把模拟器专项和 quick 当作全部 PR 检查通过；真机及更多编辑器仍未验收。
