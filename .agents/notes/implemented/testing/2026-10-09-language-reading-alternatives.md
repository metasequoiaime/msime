# Agent Note: 多读音查询直接写入结果缓冲

Status: implemented

## Problem

`LanguageDictionary::lookup_readings` 在单个位置拥有多个读音时，先为每个读音调用 `lookup` 创建临时 `Vec<LanguageEntry>`，再把这些行转换成带读音键的结果并追加到最终向量。九宫格的候选刷新会反复走这条路径；临时结果向量及其扩容增加了查询分配。

## Decision

多读音且只有一个位置的分支直接复用一条预编译查询语句，把每个 SQL 行构造成 `(读音键, LanguageEntry)` 后写入最终结果向量。查询的 `LIMIT`、权重与文字排序保持与 `lookup` 相同；每个结果仍拥有独立的读音键字符串，公开返回类型不变。合成 SQLite 回归测试覆盖两个读音各有两行结果，预热语句缓存后把查询分配上限从旧实现的 13 次收紧到 10 次，并校验完整结果相等。

## Alternatives considered

- **继续调用 `lookup`，只调整键的克隆顺序**：仍会为每个读音创建临时结果向量，无法消除这条路径的主要中间分配。
- **让结果键共享 `Arc<str>`**：可以减少键字符串副本，但会改变返回结构及所有候选调用方，并给每行增加共享计数管理成本。
- **为每个读音预留独立结果向量后再合并**：会把多个临时容器保留到合并阶段，峰值内存和分配次数都高于直接写入最终向量。

## Consequences

多读音单位置查询不再为每个读音建立临时行向量，结果顺序、上限、排序、键所有权和错误传播保持不变。查询分支与精确单键查询各自维护相同的 SQL 语义；若未来修改精确查询排序或字段，需要同步检查这条直接读取路径。
