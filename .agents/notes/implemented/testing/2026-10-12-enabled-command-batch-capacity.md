# Agent Note: 启用命令表按批次增长容量

Status: implemented

## Problem

`enabled_commands` 首次加载有效命令包时为输出行和触发词去重集合固定预留 `MAX_COMMANDS`。两条命令也承担 256 条的缓冲成本，而每批命令数量在包加载后已经确定。

## Decision

按当前包的行数与剩余输出限额估计本批最多新增的行数。输出空间不足时按当前容量的两倍与本批所需总行数取大值，并钳制到 `MAX_COMMANDS`；去重集合按本批最多新增数预留。仍逐行处理整包，不能按容量估计截断输入：前面重复的触发词不应消耗输出限额。

此决定部分接替[空启用列表延后缓冲](2026-10-11-enabled-command-table-lazy-buffer.md) 的有效表容量策略，空结果零容量继续成立。引擎宿主表的短表去重与延后缓冲使用不同入口；短语表没有触发词去重，不能直接复用其按批次 `take` 的逻辑。

## Alternatives considered

- 保持固定上限：满表只需一次预留，但短表保留了大量未使用容量。
- 每批精确预留所需行数：短表紧凑，但多包合并时可能反复移动旧行；倍增增长控制这种成本。
- 先扫描去重后精确计数：重复密集输入可以少预留，但增加去重查询或中间状态；本片保留既有逐行插入规则。

## Verification

两行容量回归在旧实现上因实际容量 256、期望 2 失败；修复后单包、多包、全重复包、重复行前置的满表、缺失/无效包和空列表通过。插件套件 55 项通过；Clippy、Rustfmt、差异、笔记和本地 quick 门禁覆盖本片。

## Consequences

短表的输出与去重集合不再固定预留全部上限。跨包可能增加扩容次数；重复密集批次的预留是上界而非唯一行的精确值。分配器和哈希表可以提供比请求更多的容量，不承诺系统 RSS 或端到端输入延迟改善。
