# Agent Note: 多读音查询复用范围和 GLOB 缓冲

Status: implemented

## Problem

`LanguageDictionary::lookup_readings` 的多位置多读音路径每遍历一个首读音，都重新创建查询范围的 `lower`、`upper` 和完整 `GLOB` 字符串。九键注音的候选列表和组词重算会反复经过此入口，即使全部未命中也会为这些查询参数反复分配。合成 SQLite 用例中，八个同长度首读音的预热未命中查询产生 26 次 Rust 分配。

## Decision

三个字符串在首读音循环外从空缓冲开始。每轮清空内容，保留存储，按原范围长度和 `GLOB` 容量提示使用 `reserve_exact` 补足，再以借用字符串绑定查询。每轮的 SQLite 行迭代在重写缓冲前结束，命中行仍把自己的键和文字复制到公开结果。

## Alternatives considered

- **按 `limit` 预留结果向量**：多读音查询需要先收集所有命中行再排序，`limit` 不代表中间行数；这样会给稀疏查询增加内存，且不能处理 `usize::MAX` 的完整候选列表。
- **一次按最长首读音预留三个字符串**：增加预扫描，并让尚未执行任何查询的路径提前申请存储；逐轮按需补足更贴近实际查询。
- **把所有范围和 `GLOB` 都缓存下来**：会保留每个首读音的独立字符串，增加会话状态、缓存失效条件和内存；当前循环只需要三个工作缓冲。

## Verification

测试先在旧实现上失败，实际分配为 26 次；修复后通过最多 8 次分配的门槛，空结果保持零容量。另一个合成词典用例交替使用短读音、长读音、Unicode 和 `GLOB` 元字符，验证字面匹配、重复读音、粗筛淘汰、权重及文字/键排序、零和有限上限、`usize::MAX`，并在释放输入与词典后检查结果仍独立拥有键和文字。语言词典模块 18 项测试通过。

## Consequences

同长度或更短的后续首读音复用已有查询参数存储；需要更多容量时仍正常扩容。SQL 文本、查询范围、转义、字段转换、精确匹配、排序、截断和错误传播均保持原有行为。本次分配计量仅覆盖 Rust 分配，不涵盖 SQLite 内部内存，也不宣称端到端时延改善。
