# Agent Note: 九键拼写匹配索引复用缓冲

Status: implemented

## Problem

九键刷新已经复用最终的 `spellings` 字符串缓冲，但 `SpellingTable::spellings_for_into` 每次仍把匹配音节借用成新的 `Vec<&(String, String)>`。匹配项排序结束后这个临时向量立即丢弃，热刷新会为同一批音节反复申请索引槽位。

## Decision

`NineKeySession` 持有 `spelling_match_indices: Vec<usize>`，九键刷新把它传给 `spellings_for_into`。方法清空并复用索引缓冲，按音节表索引收集匹配项，排序时仍访问原表中的音节和编码，最后按排序后的索引复制文本到既有 `destination`。独立测试入口 `spellings_for` 使用局部索引缓冲；快照、撤销记录和拼写表都不拥有这份会话工作区。

排序覆盖位数、编码长度、频度、字典序，匹配条件、分割边界和输出文本均保持原语义不变。空输入同时清空索引缓冲，避免把上一轮结果带入下一轮。

## Existing decisions

本片建立在[九键读音列表复用刷新缓冲](2026-10-17-nine-key-spelling-buffer.md)之上：那篇只复用最终的 `Vec<String>`，本片复用其上游的匹配索引工作区。两者都只声明容器容量复用，不把局部分配下降推导成词库查询、RSS 或端到端设备延迟收益。

## Alternatives considered

- **继续收集借用元组**：改动最小，但每次刷新都放弃临时匹配向量的容量，无法消除该分配热点。
- **把匹配项复制成拥有型音节再排序**：可以让排序代码保持原形，但会额外复制文本，增加分配和内存带宽，收益方向相反。
- **把可变匹配缓冲放进 `SpellingTable`**：可以隐藏调用参数，但键盘表是进程级共享只读状态，把会话临时状态放进去会扩大生命周期和借用边界，也无法支持多个会话并发刷新。

## Verification

新增 `spelling_match_indices_reuse_storage`：先预热输出和索引缓冲，再用九键表的合成 `64` 输入刷新，分配数不超过每个输出字符串复制本身的数量加一，防止重新申请索引工作区；既有拼写排序测试继续覆盖输出顺序和筛选边界。

九键支配行投影的冻结分配对照同步计入这一次额外减少的匹配索引申请，原断言差值从 `1042` 更新为 `1043`；候选字段、顺序和容量对照保持不变。

## Consequences

九键会话在热刷新中保留匹配索引槽位，减少临时 `Vec` 的扩容和释放；每个会话增加一个可回收的 `Vec<usize>` 字段，冷启动第一次匹配仍可能扩容。排序闭包多一次按索引访问音节表，但不改变排序键和输出所有权。
