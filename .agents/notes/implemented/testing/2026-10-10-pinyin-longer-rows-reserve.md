# Agent Note: 拼音长词续接按页大小预留聚合行

Status: implemented

## Problem

`PinyinDatabase::query_longer_phrases` 在首个非空页出现时按 `extra_syllables * limit` 为聚合 `Vec<DictRow>` 预留。长词续接的每张表实际最多返回 `limit` 行，但稀疏词库常只有少数行；一条首页结果会为后续未命中或短页申请整个位数上限，保留了上一片从空页延后预留时明确记录的“非空时大提示风险”。

## Decision

每张页查询完成后再根据页大小决定聚合容量：满页继续按剩余页数乘 `limit` 预留，保持密集命中一次分配；短页只为实际页行数预留，后续短页按缺口增长，后续满页再按剩余上限扩容。第一张页为空不申请存储，延续现有边界。只改变聚合向量容量，不改变底层 `rows`、SQL、表遍历、词面去重、权重排序、截断、字段与返回所有权。

## 既有笔记审计

[聚合空页延后预留](../../implemented/testing/2026-10-10-pinyin-empty-aggregate-storage.md)已明确保留非空页的乘积容量风险，本篇处理该独立后续，互链并保留原空页收益与冷测量。底层空页、按键分组哈希表和精确分段聚合属于不同容器，暂不扩大范围。检索 `query_longer_phrases`、`extra_syllables * limit`、`rows.reserve_exact` 未发现同一按页大小决定。

## Alternatives considered

- 保留乘积预留：密集结果最快且不扩容，但稀疏第一页仍申请远超实际结果的存储。
- 所有页自然增长：稀疏页最省，但密集页会多次扩容，破坏当前命中分配预算。
- 首页按 `page.len() * extra_syllables`：比乘积更适合稀疏页，但一个短页后接满页仍可能低估或高估，按剩余页是否满页分支更直接。
- 先执行计数查询再精确预留：需要重复 SQLite 查询并引入数据库变化边界，取消一次查询的收益。

## Verification

冻结当前 `query_longer_phrases` 完整正文并逐字段对照。红测试在一行页、`extra=3`、`limit=1000` 时证明旧容量为 3000 而新目标接近实际；密集页保留旧容量和分配次数。覆盖首空后命中、短页、多页满页、未命中、重复词面、负/大权重、limit 0 与非法输入。结果顺序、去重、容量、分配次数、请求峰值与底层 SQL 行为用合成 SQLite fixture 对照。

红测试在旧实现的一行页、`extra=3`、`limit=1000` 场景中观察到容量 `3000`；当前实现同一场景返回容量 `1`。冻结旧正文与当前实现逐项比较，字段、顺序、去重和返回结果相等；密集页容量与分配边界保持，稀疏页允许按最多 `extra` 次增量扩容。当前 arm64 debug 的稀疏直接测量为旧容量 `3000`、新容量 `1`，堆剩余 `168024 -> 80` 字节，峰值 `224161 -> 56161` 字节，最低值两侧均为 `0`。拼音模块 `59` 项通过，完整引擎 `1538` 项通过、`13` 项忽略，golden `31` 项通过，Clippy `--all-targets -- -D warnings`、格式、差异和 `365` 篇笔记校验通过；quick 门禁通过：Windows 本机 102 项通过（2 项主机差异排除、59 项需 Windows 构建、1 项非测试），Linux 原生宿主 73/73，Android host Java、macOS 配置/编译、Apple bridge 和契约检查通过；wasm、Harmony 真打包及 Windows 交叉编译按环境跳过。

## Consequences

短页后续突然满页会增加一次扩容与复制；这是用较低稀疏峰值换取的明确代价，需用密集计量限制。`Vec::reserve_exact` 只保证至少容量，不承诺物理字节精确等于请求；请求字节不等于 RSS 或 SQLite C 堆。只改长词续接聚合，不顺手改变精确分段、简拼、缓存和底层行容器。
