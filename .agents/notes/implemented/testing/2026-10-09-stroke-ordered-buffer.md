# Agent Note: 笔画候选按最终顺序覆写缓冲

Status: implemented

## Problem

笔画复用入口按精确、补全顺序覆写候选，再稳定移动非正权重行。移动整行也移动字符串容量；精确区末尾的零权重行使补全区槽位偏移，长短键交替时下次相同查询重新扩容。合成回归中精确路径分配 55 次，通配路径分配 56 次。已有密集测试的补全键长度相同，没有覆盖这个形状。

## Decision

先在 `EXACT_LIMIT + COMPLETION_LIMIT` 大小的栈上引用表中按原查询顺序去重，保留文字首次出现的键、权重。再依次遍历正权重与非正权重引用，直接按最终稳定顺序覆写已有候选。查询 SQL、限额和公开拥有型入口的字符串移动路径保持原契约。

## 既有笔记审计

[中间候选缓冲](../../implemented/testing/2026-10-09-stroke-candidate-buffer.md) 部分重叠：保留查询行复用和拥有型移动决定，本篇替代热入口写完再排序的决定，两篇互链。[目标容量预留](../../implemented/testing/2026-10-10-stroke-destination-reserve.md) 负责最终 `WordItem` 增长，继续有效。其余笔画命中涉及移动键盘、单字筛选、提交借用和位置守卫，均无关；glide beam 的缓冲不参与笔画查询。

## Alternatives considered

- 保留稳定排序并加长所有键的容量：改动较小，但为短键常驻长键峰值空间，也没有消除排序临时分配。
- 先按频率分区再去重：无需引用表，但首次零或负权重精确行会被同文字高权重补全替代，改变去重契约。
- 拥有型入口也使用引用表复制字符串：便于完全共用逻辑，但冷查询重新复制字典字符串，破坏已有分配预算。

## Verification

300 行合成候选、补全键长度交替为 8 与 56 字节时，旧实现预热后的精确及开头通配符查询分别分配 55 与 56 次。按最终顺序覆写后连续三次分别为 3 与 4 次，预算为至多 16 次；完整字段、顺序和最终向量地址保持一致，并与公开拥有型查询逐行对照。

引擎 1434 项测试、golden 31 项测试、Clippy、Rustfmt、差异和笔记检查通过；独立设计及代码审查无遗留问题。完整 quick 门禁退出为 0 并报告 `quick check passed`，Linux 原生宿主 73 项 ctest、macOS 原生宿主和共享 Apple bridge 构建通过。

## Consequences

候选字符串容量留在最终顺序的槽位中，不再因同一查询的稳定频率分区而移到长短不同的键上；热入口也不再申请稳定排序的临时空间。引用表在常见 64 位平台约占 7 KiB 栈，每次调用做一次首次去重和两遍分区扫描，保持已有有界二次去重复杂度。

表容量依赖两个查询限额，填表前检查总行数；不能在去重后补读。去重必须早于分区；栈表仅持有查询缓冲的借用，不保留到查询之外。不同查询形状或截断后增长仍可能分配，不承诺所有查询零分配。公开拥有型入口继续移动字典字符串。若改变限额或加入递归调用，须重新评估栈预算。
