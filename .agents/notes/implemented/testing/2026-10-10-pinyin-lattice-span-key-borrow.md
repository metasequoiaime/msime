# Agent Note: 词网格跨度缓存借用查询键

Status: implemented

## Problem

词网格的切分之间反复查询相同跨度。`cached_lattice_span` 即使命中已缓存的空结果，仍先把上限转成字符串，再逐音节拼接键。冻结 `d8e319f2f3923b41bf92f01bfc6b4ba0f93dc3cd` 的完整 helper 后，三音节空结果命中实测仍分配 3 次；这些分配只用于临时查找键。

## Decision

跨度缓存使用 `DefaultHasher` 对上限和借用的原样音节切片计算索引，命中后核对上限及完整键。哈希只用于定位；碰撞或键不符时重新查库，并替换同索引槽。冷查询保存一个连接字符串，每个音节前保留一个撇号，沿用原键的分隔结构，空跨度和包含一个空音节的跨度具有不同编码。热查询按分隔符逐段借用比对，不创建键字符串；返回行仍克隆，调用方继续拥有完整结果。

该模式沿用 `fuzzy_cache` 的索引与完整键校验方式，遵循 [Rust `Hash`](https://doc.rust-lang.org/std/hash/trait.Hash.html) 对切片和字符串的实现。测试不固定哈希值，也不假设不同请求一定有不同哈希。音节来自已切分输入，每项不含撇号，私有 helper 依赖这一前提保证分隔符编码无歧义；若未来接受内部含撇号的任意字符串，必须改用能区分音节边界的编码。SQL、排序、限额、4096 条容量和字典版本失效入口保持原有职责。

历史检索中，[模糊整词候选与替补整句排序](../bug-fix/2026-10-08-fuzzy-whole-input-before-stand-in-sentence.md) 只提及未来模糊词网格需要把规则加入跨度键；该决定属于候选覆盖与排序，与当前原样跨度的存储优化无关。

## Alternatives considered

- 保留字符串键并一次预留完整容量：实现最小，能减少拼接时的扩容，但每次热命中仍需要拥有临时键和上限字符串。
- 哈希索引后缓存 `Vec<String>` 原样音节：可以直接比较切片，但冷查询要逐音节复制，多音节跨度增加堆分配。一个连接字符串保留原键编码，同时避免每音节拥有一个副本。
- 复用可变字符串缓冲作为查找键：能保留单次字符串索引，但需要引入跨调用的额外可变状态及借用协调；已有模糊缓存的哈希与完整键校验模式无需增加查询状态。

## Verification

## Consequences

空结果的热命中不分配，非空结果只保留行克隆所需分配；冷查询的键构造只拥有一个字符串。缓存节点增加上限元数据，两个冷样本的峰值增加 16 字节，因此不承诺总堆占用下降。哈希碰撞会让不同请求竞争一个槽，减少有效缓存容量，替换也保留该槽原有 FIFO 年龄；完整键校验防止返回错误行。

该证据只衡量 Rust 分配次数与逻辑请求字节，不涵盖 SQLite C 堆、进程 RSS 或发布构建的真实按键延迟。若碰撞竞争或哈希及校验成本在实际输入中成为热点，需要重新评估复合键索引；当前测试不推断端到端计时收益。
