# Agent Note: 双拼直接辅助码匹配借用字符缓冲

Status: implemented

## Problem

双拼直接辅助码路径会对每个候选词先执行 `word.chars().collect()`，再为每个需要校验的字符构造临时 `String`，随后只读一次。这些字符容器和临时文本位于候选过滤热路径上，匹配结束后立即释放。

## Decision

`direct_helpcode_matches` 改用 `word.chars()` 迭代器按路径位置读取需要校验的字符，并以固定四字节栈数组调用 `encode_utf8` 后查询 `HelpcodeKeymap`。路径中没有首码的项仍保留原索引跳过行为，短词仍按原规则拒绝；辅助码首字母、第二位、字符顺序和匹配结果保持不变。没有新增公开接口、缓存或依赖。

## Historical audit

已检索双拼直接辅助码路径、`direct_helpcode_matches`、帮助码键表和辅助码过滤缓冲笔记。现有[双拼单字辅助码匹配分类复用栈缓冲](2026-10-15-shuangpin-helpcode-match-buffer.md)只处理单字辅助码的分类向量，不覆盖直接辅助码的字符读取；帮助码重排和结果缓冲笔记也不持有这里的字符所有权。没有发现重复实现或待吸收的决定。

## Alternatives considered

- **继续收集 `Vec<char>` 并复用它**：可以保留索引访问，但每个候选仍需拥有字符向量；直接迭代更小且不改变路径位置语义。
- **给 `HelpcodeKeymap` 增加字符专用接口**：可把编码缓冲隐藏在键表内，但会扩展帮助码公共类型的接口；局部栈数组已足够消除分配，因此不引入额外 API。
- **用 `word.chars().nth(index)`**：可避免向量，但每个位置都从头遍历，候选和路径变长时会重复扫描；单次迭代保持线性成本。

## Consequences

直接辅助码候选匹配不再为字符向量或字符临时字符串申请堆内存；字符编码仍使用最多四字节的局部缓冲。匹配函数继续按路径索引读取带首码的字符，跳过无首码项，返回值、短词边界、Unicode 字符和辅助码比较顺序保持原样。

## Verification

TDD 先在旧实现上运行新增分配回归，得到 `2` 次申请并按 `0` 次目标失败；改用迭代器和栈编码缓冲后同一测试为 `0` 次申请并通过。后续验证包括双拼引擎定向测试、全引擎单测、golden、Clippy、Rustfmt、差异检查、笔记校验和 quick 门禁。
