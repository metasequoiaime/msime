# Agent Note: 打字流模拟评测（typing_sim）

Status: implemented

## Problem

维护者要九键在真实打字里达到九成准确率。仓库里所有的数都是冷启动：`convert_eval` 关学习、每条用例前清空上文，一串键只问一次金标准排第几，九键词级首选 0.563（一串数字对应几个同样成立的金标准，上限只有 0.721），全键盘 0.756（上限 0.880）。真实打字有学习、有上文、有部分选择和拼写列，有人只打到声母就去看候选，这些冷启动都量不到，所以「九成」既没有定义，也没有办法知道离它多远。

一份设计稿和两份审查摆在面前：设计稿要新写一个按顺序打一整段文字流的模拟器，主集用 LCCC 对话；第一份审查说它不够逼真（没有校准、没有联想、主配置不简拼、学习在多人语料上量不出来）；第二份审查说它站不住（LCCC 只许科研用、模型就是在 LCCC 和 C4 上训的、首选率能靠把词拆开刷上去、读音标错不报、几处筛选按引擎输出筛掉了难例、区间偏窄、没有留出集）。

## Decision

新写 example `crates/input-runtime/examples/typing_sim/`，让一个模拟用户用手机出厂配置把一整段文字流从头打到尾。生产代码只多一个 `host::Session::set_clock`，委托给引擎会话已有的 `Session::set_clock`，只给评测和测试用。

- **配置**（`profile.rs`）：每个值从 `Preferences::default()` 读，照 host-api `apply_pending`、`apply_local_mode_resource_gates` 和 `ffi::session` 的映射换成 `EngineOptions` 和 runtime 设置：学习开、调频 promote 1/1、混输英文和行内日期时间开、每页 6 个、`first_page_rows` 6、`phrase_preedit` 开、不挂模型。`--model keyboard` 只挂上 runtime 逐键的键盘重排器，引擎内的键盘模型层（`neural_keyboard`）固定关，和 #10197 之后 host-api 按 `keyboard_reranker_enabled` 挂重排器、不再把这个偏好交给引擎一样；README 表里「挂模型」两列是 #10197 之前两层同开时量的。不挂 settled 重排（移动端没有那个模型）。报告的 `config.engine` 原样列出这些值。
- **打字流**（`main.rs`）：一个 Runtime 从头打到尾；每行是一条消息，发出后失焦再聚焦；标点和非汉字写进上文不计分；学习开着时先打预热。会话时钟换成虚拟时钟，按键 350 ms、选择 700 ms、块间 1 s、消息间 20 s，行内日期时间钉在 2026-01-05 10:00。
- **切块和简拼**（`corpus.rs`）：块长 1 加几何分布（平均 3.5 字、最长 8 字、词不拆开），三成的块末音节只打声母。两者都只由种子、行号和块的位置决定，不用随机数生成器的状态，所以换文档顺序也切出同样的块，0.3 的简拼块一定也在 0.6 里。
- **选词**（`user.rs`）：候选栏前 6 个里挑盖住最多剩余金标准的那个，一样长取靠前的；没有就开面板（每页 24 个，最多两页），再没有就锁拼写列的下一个音节；简拼的块只看候选栏，没有就补完声母那个音节。选完核对剩下的键是否等于剩余金标准的键，对不上就走失败路径，剩下的字留在分母里。
- **口径**（`metrics.rs`）：逐字首选率 `cfa`（严口径，纠正之后点的第一位不算，见下文「严口径」）和宽口径 `cfa_lenient`、整块首选率 `cca`、每次上屏首选率 `cpr`（和设备上打字统计 `ranks[0]` 同口径）、零修正块率 `zcr`、每字按键 `kspc`、`key_saving`、`chars_per_commit`，按文档 cluster bootstrap 的 95% 区间，按块长、简拼、首次出现、预热里见过、键串对应多个金标准、常见块分桶，每 2000 字一桶的学习曲线。
- **评测集**：`typing-tatoeba-v1.tsv`（Tatoeba 普通话句子，CC BY 2.0 FR，随机抽样）和 `typing-chat-v1.tsv`（为本仓库手写的单人聊天，GPL-3.0），Tatoeba 那份每行带 Tatoeba 作者的用户名（`author` 列，CC BY 署名），由 `scripts/build-typing-set.py` 用 jieba 切词、pypinyin 按整句标读音生成，读音和引擎不一致的 423 个词逐条读过，改正 39 处（`typing-readings-reviewed.tsv`）。按文档分 warmup、dev、test；`--dump` 和 `sample_failures` 不写 test 的文字。
- **门禁**：`verify-local.sh` 加一段默认不跑的 `typing simulation eval`（`MSIME_TYPING_EVAL=1` 加 `MSIME_EVAL_RESOURCES`），手写聊天集上九键主配置对照 `baseline-typing-chat-nine-key.json`。整组运行用 `scripts/typing-eval-matrix.sh`，不进门禁。

主配置事先定下：九键、手机出厂配置、学习开、不挂模型、抽样切块 3.5 字、三成末音节简拼、候选栏 6 个、`dict-v2.0.39`。「九成」指它在 test 上的 `cfa`，同时看 `cca`。

### 严口径（2026-10-29 修订）

第一版的 `cfa` 只看点选时座位是不是 0。独立复核发现，用户在候选栏和面板里都找不到时会先补完停在声母上的音节、或者在拼写列里锁定音节，再回来点第一位，这些字也记成了首选，九键主配置上约占十个点。这和「打完直接点第一个就对」不是一回事，所以主指标改成严口径：每次点选记下这一块里在它之前有没有做过纠正（`Selection::after_correction`），`cfa` 只数座位为 0 且之前没有纠正的字；原来的数改名 `cfa_lenient` 留作对照。

纠正只算改变了引擎手里输入的两件事：补完简拼、锁拼写。点第一位之外的候选、开面板、翻页不算：它们不改输入，那次点选本身已经记为不是首选，之后剩下的键上排第一的仍是引擎对同一串输入的判断；把它们也算进去，会让一次面板点选连带惩罚后面本来就排对的字，量的就成了「整块一次对」，那是 `cca` 已经在量的东西。`--slip` 点错后整块重打也不算，重打的是同一串键，引擎没有多拿到信息。`cpr` 仍按设备打字统计的口径只看座位，好和现场数据对照。按定义 `cca` ≤ `cfa` ≤ `cfa_lenient`。

在 develop 50bab97f3a（已含 #10110、#10111）上重跑了全部 61 臂，九键主配置 test 上严口径 Tatoeba 0.499、聊天 0.515，宽口径 0.601 / 0.608；一词一块不简拼时九键 0.787 / 0.824、全键盘 0.898 / 0.926，两种口径差 0.5 个点以内。门禁基线按严口径重写。全表见 README「现在的数」。

### 两份审查里接受和不接受的

接受的：

- 不用 LCCC（CDial-GPT 写明「仅限科研用途」），也不把语料发给外部 API；顺手改了 README 里「LCCC 是 MIT」的说法。
- 评测集不来自模型的训练语料：两份都对 `chinese-ime-lm/data/c4.txt` 和 `lccc.txt` 做了 8 字窗口检查，5.5% 和 4.4% 的行碰上，碰上的都是常用说法；和仓库已有整句集零重合。
- 用户挑最长的匹配，加上整块首选率 `cca`，拆词刷不上去。
- 读音用第二个工具交叉核对、人工改正，冻结进文件。
- 不按引擎输出筛任何一行，打不出来的字留在分母里，评审只看是不是正确的中文、能不能进公开仓库。
- 「第一次出现」只做描述性分桶；学习的贡献用同一条流上学习开关的两臂比，引擎的改动看学习关的那一臂。
- 用 `--order-seed` 换文档顺序看结果动多少；dev/test 分开。
- `--slip` 点错臂和「键串对应多个金标准」分桶，看激进的学习有没有代价。
- 默认简拼三成而不是零，另跑零和六成，以及每个音节都打声母（`--abbreviate-mode all`）。
- 抽样切块代替固定的 2 到 4 字切法，另跑一词一块、整句一块、平均 2.5 和 5 字、换一个切块种子。
- 报告里给出和设备统计同口径的 `cpr`、`chars_per_commit`、`key_saving`，以后拿现场数据校准简拼比例和块长。
- 常见块分桶、时间参数的敏感性运行、预热算作「同领域预热」而不是个人学习。

不接受的：

- **上屏后联想**：`next_word_prediction` 只在 Android 上、要用户自己打开，默认关（`preferences.rs`、host-api `apply_pending`），出厂配置里根本没有联想行，建模它量的是一个非默认配置。
- **先拿现场统计校准再定主配置**：设备上的位次和效率不分输入来源，云端汇总要维护者决定能不能用，这一轮拿不到。主配置照样事先定下，报告给出同口径的数，等拿到现场数据再对。
- **配置和 host-api 输出逐项相等的测试**：映射在 `HostSession::apply_pending` 里，是私有的；要测它就得把映射拆成公开函数，是生产代码的重构，不在这次范围内。改成从 `Preferences::default()` 读值、在报告头列出全部选项。
- **混入的英文走九键英文路径单独测**：两份集合里含字母或数字的行很少，这一轮只写进上文，算在已知局限里。
- **等价写法组、打错格子再退格**：要逐词标注，这一轮没做。
- **200k 字长期臂、用户本人的聊天导出**：没有同一个人写的、许可清楚的这么多文字；导出用户聊天涉及隐私，要维护者决定。
- **C4 中文校验集当副集**：随机抽出的前 7 篇里有 4 篇是 SEO、博彩和团购导航页，清理成能打的文字等于按评审者的口味选材。

## 第一轮测量

`dict-v2.0.39`，develop 5d1f841971，test 部分，宽口径（当时的 `cfa`，现在的 `cfa_lenient`）。严口径的现行数字见上文和 `resources/eval/README.md`「现在的数」：

- 九键主配置 `cfa` Tatoeba 0.605（0.584–0.625）、聊天 0.603（0.558–0.650），`cca` 0.46 左右；同一个模拟用户在全键盘上 0.76–0.82。这个口径下的九成不是调排序能到的，缺口最大的几块是同码同长的别的词排第一、整句解码出错、简拼。
- 简拼 0 / 0.3 / 0.6 和块长（一词一块 0.720 到整句一块 0.456）各自能让数字动五到二十个点，主配置的这两个假设没有现场数据校准，是这一轮最大的不确定。
- 学习在单人聊天上加 3.5 个点，在多作者的 Tatoeba 上几乎为零，全键盘上为负；「最近选过的放第一位」让同码不同字的块从 0.548 掉到 0.459。
- #10110 加 #10111 在九键和 14 键 32 臂上 `cfa` 变化都在 ±1.2 个点以内，全键盘逐字节不变。
- 同一臂两次运行逐字节相同（develop 上手写聊天的九键主配置重跑一次 `cmp` 相同；全键盘 Tatoeba 两臂在不同负载下各重跑一次相同；PR 头和 develop 的全键盘臂相同；`verify-local.sh` 的那条命令用新编的二进制跑出来与基线相同）。

## Alternatives considered

- **扩展 `convert_eval`**：它的前提是每条用例独立、关学习、清上文，与打字流正好相反；加一个模式会让两种互斥的语义挤在一个入口里。
- **经 C ABI 驱动真正的 host-api 会话**（像 `keystroke_latency` 那样）：配置和打字统计都是真的，最逼真；但会话时钟没法从外面换，学习的 3 s / 8 s / 10 s 窗口随机器快慢变，跨消息也会凑出词对，结果不可复现。要换时钟就得给 C ABI 加评测专用的入口，比加一个 Rust 方法重得多。
- **用真实时钟不换**：机器快时所有窗口永远满足，负载两三百时停顿又会越过 3 s，同一个二进制跑两次结果不同。
- **LCCC 当主集**：是唯一现成的大规模真实对话，但许可只许科研用，而且就是模型的训练语料。

## Consequences

- 收益：第一次有了「真实打字」的数，以及学习、简拼、块长、模型、首屏个数各自动多少。两次运行的报告逐字节相同，可以当基线用。
- 代价：慢。九键主配置在 Tatoeba 上一臂约 1.4 万字、二十多分钟（编译机负载七百时更久），挂模型的臂翻倍；整组 40 臂在负载高的 Studio 上要两个多小时，所以不进默认门禁。
- 局限：用户总是上屏金标准，学习只被正确的词喂；Tatoeba 作者很多，学习量到的是同领域的话；手写聊天是合成文字，常用说法偏多；块长和简拼比例没有现场数据校准；消息之间按失焦处理，没有核对聊天应用发出消息时宿主实际发给引擎的是哪个动作；挂模型时首屏之外的重排不跑 settled 模型。
- 与[评测资源完整性](2026-10-19-eval-resource-integrity.md)共用 `eval_resources::verify`，资源必须和锁一一对应；与[换锁笔记](../bug-fix/2026-10-27-dictionary-lock-latest.md)一样以 `dict-v2.0.39` 为准。
