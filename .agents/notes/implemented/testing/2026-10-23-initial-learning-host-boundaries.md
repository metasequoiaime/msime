# Agent Note: 单码学习沿宿主候选身份与持久化边界诊断

Status: implemented

## Problem

#9384 报告小鹤单码反复选择后，换一个上文又退回原首选。报告者确认使用默认的学习开启、`promote` 和触发次数 1。直接调用引擎 `Session::select` 的小型合成词库没有复现，关闭全局调频时的上下文提升不能解释报告者已确认的配置。

## Decision

诊断保留引擎层对照，另沿 macOS 使用的 Host API 验证：保留默认辅助码与整句候选，声明 macOS 的快捷短语候选及组字能力，通过视图中的真实候选代次和绝对索引选择。资源、工作词库、用户日志和缓存使用不同目录；逐轮检查上屏、固定诊断、工作词库权重与用户日志，并检查换上文及重建会话后的候选顺序。必须覆盖「显示已首位、全局词频仍低于原首选」的中间状态，确认继续选择仍有全局学习。macOS 原生诊断使用既有 `ShortcutTest.mm` 的真实 `MSIMEClientSession` 与 `handleEvent`，分别通过数字键和方向键加空格选择；不替换选择器或调频实现。

Host API 夹具采用 `resources/components/chinese-main.lock.json` 锁定的公开词库读音与权重，只将字面替换成合成值。来源提交为 `128a332cabc5fa42b1cf5f827033ad5697ff528b`，原始文件大小 73723904 字节、SHA-256 为 `7c672458e6068c22c07b33b146c5a07f4e734959abc3bddd2784fe18a7582a76`，本机读取前已经校验。测试不读取个人词库、配置或输入历史。

## Historical audit

[双拼模糊覆盖与学习](../bug-fix/2026-10-20-shuangpin-fuzzy-coverage-learning.md)部分重叠：它证明持久化成功仍可能被查询排序掩盖，本次继续分开检查写入和呈现；它修复的是模糊读音覆盖，不据此认定单码原因。检索单码学习、首字母调频、一次置前及 issue 编号：九键首字母、九键缓存、数字符号候选、大写拼音入口与格网评分行索引的命中均不持有本次 macOS 单码选择契约，没有可直接更新的既有归属。

## Alternatives considered

- 只保留引擎 `Session::select` 对照：用例短、能隔离调频算法；但跳过宿主的候选索引映射，也没有复现产品的目录分离，因此增加 Host API 诊断。
- 用关闭调频的现象解释报告：能稳定得到相似的上下文变化；但与报告者确认的 `promote` 配置不符，不能据此关闭 issue。
- 复制真实用户词库与完整配置：最接近报告环境；会引入私人资料且不能形成公开回归，采用锁定公开资源与合成字面。

## Verification

两项引擎诊断已通过，覆盖双读音及七条候选中原第七位的选择。Host API 新用例实际通过，1 项通过、0 失败（`issue-9384-host-identity-reproduction.log`）：换上文和重建会话仍为首位，工作词库 `le` 条目的权重高于原首选，用户日志权重与它一致，随包资源不变。完整锁定词库的独立实验也通过：仅将单字 l/w 表的字面替换成合成值，保留全部行、读音、权重与重复关系。选择前显示排名依次为 4、3、0、0、0，选择后工作权重依次为 3709480、5546144、11083167、14837507、14837507，逐轮用户日志与工作词库一致；原首选权重为 14837007。第三次显示已首位但基础权重仍低于原首选，选择仍写入提升，换上文与重建均保留首位。实验包装器退出 0，日志为 `issue-9384-full-dictionary-round-weights.log`；依赖外部词库的临时集成程序移到仓库外研究目录，不能混入普通测试。Host API 逐轮增强断言通过，1 项通过、0 失败（`issue-9384-host-per-round.log`）。macOS 原生数字键与向下键加空格两条诊断已随完整 `shortcut` 套件通过（`issue-9384-native-keys-down.log`，ctest 1 项通过、0 失败）：每次上屏一次，逐轮词频与日志一致，中间状态继续提升，换上文和重开仍首位，随包资源不变。首轮原生测试用右键移动候选，在目标高亮准备断言失败；代码确认双拼右键用于音节编辑后改用向下键，未将该准备失败称为调频缺陷。两项引擎诊断本轮重新执行通过（`issue-9384-engine-current.log`）。以上空白状态实验没有得到失败复现或生产修复，不能把这些诊断称为问题已修复；也没有 macOS 已安装输入法的实际验收。报告公开视频已逐帧核对：目标在开始时位于第二格，连续选择超过五次后换上文仍回退；当前完整锁定词库的初始目标在第五格，因此不能用「选择次数不足」解释视频。报告固定提交的资源锁与本次锁相同，但视频的实际候选顺序不同，后续需要继续核对产品实际资源选择、工作词库及额外排序能力，不能把同一源码锁等同于同一运行时资源。视频与截图仅存于仓库外研究目录，不进入测试、提交或公开日志。随后把锁定且逐文件核验的全部基础资源（英文、其它词典、二元/三元模型、日文及句子模型）加入同一合成实验，复用已构建的诊断程序，1 项通过、0 失败（`issue-9384-complete-resources-probe.log`）；逐轮排名与权重不变，换上文与重开仍首位，单纯缺少这些随包基础资源未解释差异。实际安装代次、已有用户状态及按需能力仍未被该空白状态实验覆盖。

## 已有上下文的失败对照

首次引擎启动前加入合成的 `personal_bigram(丙,甲,10)`，保留真实二元/三元表结构，在相同默认配置下执行五轮学习后换上文，Host API tracked 回归稳定失败：显示首位为甲，期望为乙；此前每轮已核对工作词库和用户日志一致。仓库外计数 0 的对照通过，10 和 1000 均失败，定位到个人上下文重排覆盖已持久化的全局词频。初版实验写错三元表列名，模型没有加载，该次通过不作为证据；修正为 `earlier/previous/word/count` 后才得到上述失败。新行为决定见[全局调频首选与个人上下文](../bug-fix/2026-10-24-global-learning-before-personal-context.md)。修复后的当前源码两条 Host API 回归均通过，包含重建后再换上文；全套引擎 2545 项通过、0 失败、56 项忽略，31 项 golden 通过。这是合成状态下的真实缺陷，不证明报告者的实际历史内容；当前源码重建 Host API 静态库和标准 `target/macos-isolated` 的 `shortcut-test` 后，完整 `shortcut` 套件通过，耗时 93.14 秒；数字键与向下键加空格分别覆盖空白和预置个人上下文，共四条新增路径。原生会话重建仅检查无上文首位，重建后再次换上文由 Host API 回归覆盖。原生链接有部分 C 对象按 macOS 27 构建、最低目标为 13 的警告；这不是最低 macOS 13 或已安装系统输入源的验收。

## Android 设备边界

Android API 35 的当前引擎测试程序精确执行匹配日志首选保护和两条小鹤单码学习诊断，三项均通过；标准客户端四 crate 设备测试另有 2068 项通过、0 失败。两类程序均由 adb shell 运行，不是应用 UID 或安装 APK 验收。

## Consequences

增加一条从宿主候选身份到持久化状态的诊断路径，防止把当前上下文提升误认成全局学习。小型词库仍不能覆盖完整资源中的所有候选来源、模型或实际磁盘权限；用例通过仅排除它明确覆盖的假设，#9384 保持开放。
