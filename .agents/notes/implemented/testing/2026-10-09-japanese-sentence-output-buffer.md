# Agent Note: 日文 provider 复用句子结果容器

Status: implemented

## Problem

日文 provider 已复用转换与最终候选行，但矩阵每次创建 `Vec<JapaneseConversion>`，消费后立即释放。即使没有句子结果，固定 12 条限额也会申请一次结果容器。真实红测试中，单假名、完整预测与待定 `kak` 热查询分别为 11、14、19 次分配。

## Decision

矩阵将原搜索正文抽成接收 `Output` 的私有核心。原拥有型 `search_converted` 在生产已无调用，收为仅测试的冷查询入口，继续按原限额创建新向量；crate 内部的 `search_converted_into` 清空旧结果、按限额补足容量，再将原向量交给同一核心，取回结果。搜索正文的查询、剪枝、EOS、排序、去重、待定补全插入与限额不改变。

provider 持有初始为空的句子向量。有词库查询写入该向量，按原顺序 `drain` 到最终候选行；每条句子仍在写入后释放，消费结束只留下向量容量。无词库、非法方案与裸 `-` 的短路不申请句子存储。文本所有权继续归矩阵结果和最终候选，不保留上一轮句子文本或跨查询候选内容。

沿用现有 `Rows` 的存储转移与各输入方案的输出容量复用模式，没有新依赖、unsafe、公开 API 或第二套搜索规则。[Rust Vec 的 clear](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.clear) 释放元素并保留容量；[mem::take](https://doc.rust-lang.org/std/mem/fn.take.html) 将已有向量转入搜索核心后再归还。

## Alternatives considered

- **矩阵直接回调到最终候选**：可进一步省去中间容器与部分词条文本复制，但矩阵和 provider 的去重、限额及所有权边界不同，直接共用会改变结果计数或需要新的独立去重存储；本篇复用现有拥有型结果。
- **复用每条句子字符串**：可减少词条复制，但末行文本已有拥有转移，覆盖旧行需要另一套借用与拥有写入策略，并长期保留上一轮文本；本篇仅保留空容器，避免改变文本释放时机。
- **继续逐次创建结果向量**：代码最少且没有常驻容量，代价是有词库的每个热查询都重复申请固定结果容器。

## Verification

先收紧三条 provider 热分配预算，旧实现以 11、14、19 次真实失败。复用后分别为 10、13、18 次；完整行字段与已有对照一致。冻结 `f37203c77` 的 provider 查询正文保持，拼接键、词条视图与句子容器的差值分别统计；除裸 `-` 外，该合成有词库夹具的每轮预热查询恰好另少一次分配。

矩阵复用入口与冷拥有型入口逐项对照文本和成本，覆盖 70 条同读音词条、负成本、平局、重复词面、连接成本、空输入、未命中、只有待定字母、完整与待定读音、长 UTF-8 和未知 Unicode 回退。限额在 0、1、2、12、24、64、128 之间往返，旧结果文本和脏成本不得残留；容量足够时指针与容量不变，非零限额恰好比冷查询少一次分配，零限额两侧都不分配结果容器。独立容量增长测试覆盖初始空向量与再次使用增长后的存储。现有批量剪枝和冻结矩阵对照继续检验完整算法。

搜索核心从零限额判断到最终返回与本切片基线 `ca42c7f25` 逐字一致，只拆出 `Output` 构造。98 项日文测试、完整 engine 1485 项单测与 31 项 golden 通过，5 项本地计时默认忽略；Clippy、Rustfmt、差异与 354 篇笔记检查通过。自审无遗留问题。完整 quick 门禁退出 0 并报告 `quick check passed`：共享 Rust、Android 目标与 Java、Linux 桌面外壳、Linux 原生宿主 73 项测试与五笔版构建及安装检查、macOS 原生宿主和 Apple bridge 通过。Windows 本机 102 项测试通过；Wasm、Windows 交叉构建和 HarmonyOS 真 ArkTS 编译因缺少工具链或前置输入由脚本跳过，未做设备或系统输入法界面验收。

## Consequences

有词库且容量已预热的 provider 查询省一次句子结果向量分配，包括矩阵返回空结果的查询。当前 provider 限额为 12，容量只需容纳这一固定限额，与输入长度无关；Vec 的实际容量仍遵循标准库增长规则。每个 provider 多出一个 Vec 字段并在有词库查询后保留小块元素存储，句子文本在本轮消费后释放。若未来 provider 限额改变，应重新核对保留容量和预算。

矩阵行、节点文本、词库排名和最终候选仍会分配，仅测试的冷拥有型矩阵入口保持原分配路径；日文模块本就不对 crate 外公开，没有外部 API 变化。本篇只证明结果容器分配减少，没有整段搜索或真实按键延迟改善的计时结论。

[精确词条流式消费](2026-10-09-japanese-exact-lemma-stream.md) 进一步取消 matrix 命中的精确视图向量；本篇每个热查询独立省一次外层结果容器的决定和历史 10/13/18 预算保留，精确流式后完整预测预算为 11；[滚动字节边界](2026-10-10-japanese-rolling-boundaries.md)再省一次，当前为 10。两侧冷/复用查询仍共用搜索核心，分配差仍只隔离一份结果容器。
