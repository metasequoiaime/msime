# Agent Note: 启用短语按批次增长容量

Status: implemented

## Problem

`enabled_phrases` 的首次有效行触发 8,192 行固定预留。仅启用少量短语的宿主也承担最大输出缓冲成本。每个包的行数在载入后已经确定，不需要扫描两次文件才能估算本批次所需空间。

## Decision

函数按当前短语包可接收的行数计算目标容量；空间不足时取当前容量的两倍与本批次所需容量的较大者，并钳制到 `MAX_ENABLED_PHRASES`，随后按目标容量执行 `reserve_exact`。空结果不分配，跨包合并保留已有顺序与总量上限。

本决定部分接替[空启用列表延后缓冲](2026-10-11-enabled-phrase-table-lazy-buffer.md) 的有效表容量策略；空结果零容量的边界继续保留。辅助码预览与引擎快速短语过滤使用不同容器和入口，不由本决定覆盖。

## Verification

容量回归测试在固定预留实现上先失败，修复后覆盖单包两行、多个包、无效包、空启用列表和 8,192 行截断。client-core 插件测试、Clippy、Rustfmt、差异检查和 quick 门禁覆盖提交。

## Alternatives considered

- 保持一次预留全部上限：满表无需扩容，但少量启用行会占用几乎全部未使用缓冲。
- 每个包都只精确预留当前总行数：短表最紧凑，但大量小包可能反复移动已有行；采用倍增增长控制这种成本。
- 完全依赖 `Vec` 的自然增长：代码最少且摊销成本低，但增长策略没有上限保证，接近 8,192 行时可能申请超出限制的容量。

## Consequences

少量短语表只申请当前批次所需空间，多个批次按倍增方式减少重复搬移；满表仍最多保留 `MAX_ENABLED_PHRASES` 个结果。多包合并可能比固定预留增加扩容次数，分配器也可能返回比请求更大的区域；若短语上限或批次规模改变，应重新评估增长因子。
