# Agent Note: 在线提供方结果槽测试等待发布屏障

Status: implemented

## Problem

`a_busy_provider_keeps_only_the_newest_completed_result` 阻塞第一条请求，提交三个替换请求后释放工作线程，随后轮询一次结果便断言最终值。轮询可能恰好发生在第一条已发布、最后一条尚未完成时，读到 `ni` 并误报。结果槽的契约只保留最新已完成结果，不保证尚未完成的请求已覆盖旧结果。

## Decision

测试由 provider 回报每个请求开始，确认最终请求已经开始后再提交无结果的屏障请求。单个工作线程必须先发布上一请求的结果才会开始下一请求，因此收到屏障开始信号后读取槽，可检查最终结果和随后槽为空。请求队列覆盖、结果槽覆盖及对外 API 的生产行为保持。

## Existing decisions

检索活跃笔记中的 `OnlineProviderWorker`、结果槽、最新完成、bounded 与 debounce，未发现同一测试同步决定。在线候选过滤、去重和缓冲分配笔记约束的是数据处理，不承担工作线程发布时序。

## Alternatives considered

- 加长轮询间隔：改动小，低负载下更容易让最终请求完成，但不能建立发布的先后关系。
- 轮询并丢掉中间结果直到最终值：可验证最终结果到达，但不能证明未消费的结果槽确实只保留最后一条。
- 在生产 API 增加等待完成入口：直接表达同步，但为单测扩展公开接口和线程状态没有必要；已有 provider 回调足以构建屏障。

## Verification

原测试在完整引擎/runtime 套件中实际失败：期望 `nihao`、得到 `ni`。改后使用 channel 的有限等待，不依赖 sleep 或请求耗时；独立进程连续 200 次通过，完整 runtime 286 项通过。

## Consequences

测试检查的是最终结果已发布后的槽内容，仍同时覆盖忙碌时请求替换和未消费结果替换。多一次合成的无结果请求，仅用于测试同步，不改变生产路径。
