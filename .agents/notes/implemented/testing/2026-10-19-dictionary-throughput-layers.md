# Agent Note: 分离引擎与个人队列的导入吞吐测量

Status: implemented

## Problem

#8643 要求约三万词完整写入达到每秒万行。有界同步已减少集合重复解析，但同机模拟器仍需约 47–54 秒。新的 release 合成测量为 33555 词、21266 毫秒、144 次有界调用；8 秒采样窗口中，活动线程约四分之一的样本落在 outbox 序列化和原子写盘，另有大量样本落在集合重新读取。单看这个热点不足以证明仅修改 outbox 就能达到目标，个人请求队列与引擎事务也有独立的持久化成本。

## Decision

Host API 增加显式运行、默认忽略的分层吞吐测量。在相同的空合成主库、精确 `(key,value)` 索引、合成词与 128 项批次条件下，分别通过引擎批量编辑和个人队列加 Host API 同步写入全部词。每层使用全新目录，计时包含该层排队与同步，夹具和词条构造不计入；结束后直接检查 SQLite 完整行数，个人队列路径还检查无剩余项和失败项。

测量记录总耗时、批次数和最长批次，不以墙钟阈值作为回归门禁。已有完整集合测量继续包含导入解析、集合落盘和有界同步，三层数值用于确定下一步需要改变的持久化边界；不把跳过上层工作的结果当作产品吞吐。

## Historical audit

- [集合有界同步](../bug-fix/2026-10-19-collection-scoped-synchronization.md)：部分重叠，保留已有完整产品路径和实际预算模型，新增的是用于判断吞吐下界的分层证据。
- [个人词库有界事务](../bug-fix/2026-10-18-personal-dictionary-batches.md)：部分重叠，沿用 128 项事务及持久化语义，本改动不放宽上限、不改变文件格式或同步级别。

## Alternatives considered

- 直接采用小进度文件替换整个 outbox 重写：能减少已确认的序列化和写入字节；但会引入迁移与崩溃恢复契约，且个人请求队列的固定落盘成本可能仍超过目标，先测清下界再选择生产方案。
- 只看一次采样的函数比例：不需要新增测量；但比例只属于采样窗口，不能区分引擎事务与个人队列的独立耗时，也不能证明省掉某个热点后达到目标。

## Verification

最终源码显式 release 测量如下，每层结束均断言 SQLite 完整行数，个人路径无剩余项和失败项：

| 词数 | 128 项批次数 | 引擎直接写入 | 个人队列及同步 | 引擎 / 个人最长批次 |
| --- | --- | --- | --- | --- |
| 33555 | 263 | 3288 ms | 7180 ms | 31 / 42 ms |
| 50000 | 391 | 3572 ms | 12540 ms | 31 / 89 ms |

五万词夹具已跳过 Unicode 代理区，构造有效标量且保留 33555 词规模的既有值。一次补跑曾复用修改前的旧二进制而在代理区崩溃，不计通过；上述两轮来自明确重编后的源码。严格 Clippy 与本机格式、差异、笔记门禁通过。远端 quick `20261020-001716` 通过，覆盖 Rust workspace、Android 与 WebAssembly 检查、Android host Java、Linux 设置壳与原生 92 项测试、macOS 原生编译及 Apple bridge；缺少 MinGW、Windows pipe、HarmonyOS staged 资源和 pnpm 的阶段按脚本跳过。

随后加入集合直达 Engine 的专用 2048 项入口后，33555 词完整 scoped 测量为 9 轮、4155 ms（导入 414 ms、同步 3741 ms、最长同步 2025 ms），约 8074 词/秒。它仍在同一未隔离宿主负载下运行，尚未达到每秒万行；直达实现的恢复边界与版本迁移仍需提案中的后续工作。

## Consequences

分层测试只使用合成值，不读取报告附件或用户词库。空主库、固定编码与索引、宿主负载均影响结果，不能外推为正式词库或真机承诺。忽略的测量必须显式运行并记录结果；代码本身不是性能目标已经达到的证据。

下一步交付边界的恢复约束见[稳定集合意图提案](../../proposed/bug-fix/2026-10-19-durable-collection-delivery.md)；该篇仍为提案，不改变这里已实现的产品契约。
