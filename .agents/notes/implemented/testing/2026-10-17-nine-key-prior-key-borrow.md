# Agent Note: 九键音节频度索引借用拼写表键

Status: implemented

## Problem

`SyllablePrior::from_weights` 为每个完整音节复制一份 `String`，又为每个前缀调用 `to_string()` 作为两个频度 `HashMap` 的键。`SpellingTable` 的音节字符串在九键会话中来自静态表，频度索引只在查询路径排序期间读取这些键，不需要拥有它们。固定静态九键表的合成回归在旧实现中产生 1789 次分配，其中绝大多数是短音节和前缀键。

## Decision

`SyllablePrior<'a>` 的两个索引改为保存 `&'a str`。完整音节和前缀都直接借用传入 `SpellingTable` 的字符串，频度值、前缀覆盖规则、同分更新顺序和查找接口保持不变。九键会话的 `prior` 借用静态拼写表，因此不延长词典或会话之外的生命周期；测试用的临时拼写表仍可按调用者生命周期构造。前缀索引按所有音节长度的上界一次预留哈希容量，避免借用键路径因哈希表增长产生额外分配。

## Historical audit

已检索九键路径排序、`SyllablePrior`、拼写表容量和频度索引相关笔记。九键路径排序笔记只约束频度值和排序顺序；路径链、种子尾段、排名键缓存以及读音列表缓冲分别管理路径和候选存储，不拥有本索引的键。没有发现相同的借用生命周期决定或需要吸收的提案。

## Alternatives considered

- **继续复制拥有型键**：实现最简单，但静态表的每个音节和前缀都要申请短字符串，首次九键查询会产生大量无必要的堆分配。
- **只为前缀增加独立缓存**：可以复用已构造的键，但仍要复制完整音节键并维护缓存失效；直接借用同一张表的字符串更小，也没有额外生命周期状态。
- **把频度预计算进静态表**：可消除运行时索引构造，但频度来自用户词库，词库变化后必须重建静态数据；本次只借用键，不改变频度来源和缓存边界。

## Verification

旧实现上的新增分配回归测得 1789 次分配并失败；借用键并预留索引后为 2 次分配并通过。九键模块定向测试、完整引擎测试、Golden、Clippy、格式检查、笔记校验、差异检查和本地 quick 门禁在提交前复跑。

## Consequences

首次构造九键频度索引不再为完整音节和前缀键复制字符串，静态表场景从 1789 次分配降至 2 次；两个哈希表仍各保留自己的桶存储。频度数据仍按当前词库查询，`SyllablePrior` 不跨词典生命周期缓存，候选顺序与切分路径排序保持一致。`from_dictionary` 为 SQLite 参数准备的临时查询键仍属于数据库接口边界，本片不改变那部分存储。
