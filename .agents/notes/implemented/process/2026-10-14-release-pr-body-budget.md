# Agent Note: 发布 PR 正文使用有界提交摘要

Status: implemented

## Problem

`release-pr.sh` 将所有 first-parent 提交主题写入正文。0.53.0 发布分支已成功推送，但正文超过 GitHub 的 65536 字符限制，创建 PR 失败，重新执行又会因远端已有同名分支而另建日期分支。

## Decision

保留版本表、来源提交和合并说明。正文按 UTF-8 字节设置 60000 的保守预算，提交摘要最多展示最近 100 项，并提供固定提交之间的完整对比链接。摘要只省略完整条目，不截断字符或 Markdown 结构。正文生成与校验放在推送之前，让正文超限不能留下新远端分支。

已推送但尚未创建 PR 的当前发布分支由本次操作按固定 head 补建 PR，不扩大脚本的自动复用分支规则。

## Alternatives considered

直接截取前 65536 个字符最容易修补，也能保留最多文本；但会截断提交条目、折叠块或版本信息，并依赖服务端的字符计数定义，因此使用完整条目和保守字节预算。

把完整日志另存为附件可以保留每一条主题，但会增加文件上传、清理和访问权限管理；固定提交的 GitHub 对比页面已经提供完整改动，无需增加附件状态。

## Testing

7 项回归测试覆盖大量提交、中文和 emoji 长主题、单条超长主题、小列表、空列表、固定内容超限，以及 CLI 在合成 Git 历史上的顺序、固定提交链接和原地写入失败保护。真实发布范围的 dry run 正文为 7218 字节；现有 `release/0.53.0` 分支补建为 #7720，固定 head 未变，正文为 7245 字节。

## Consequences

正文只展示近期提交，审查完整内容需要打开对比链接。预算按 UTF-8 字节计算比字符限制更保守，因此中文主题可能更早被省略。补建发布 PR 本身不授权合并或触发发布工作流。

历史笔记检索没有发现持有 `release-pr.sh` 正文生成决定的既有笔记；Linux legacy 包发布、macOS CI 工具链笔记只涉及平台构建，与正文预算无关。
