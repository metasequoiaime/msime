# Agent Note: 合并纪律与代码健康的约定

Status: implemented

## Problem

本仓库的改动和社区 PR 几乎全部由编码代理提交、由自动流程合并。2026-11-02 对 2026-10-26 以来合进 develop 的约 925 个提交做了一次审计（恶意代码、维护性、验证严谨度三条线），没有发现恶意代码，但发现三类反复出现、现有约定拦不住的问题：

- 合并不等检查。develop 的保护规则（ruleset「main and develop protection」）把管理员设为 `bypass_mode: always`，自动合并以管理员身份运行，必过检查形同虚设。2026-10-31 合并的 68 个 PR 中，9 个合并时必过检查未出结果，33 个合并时 `android-device-pr` 未跑完、其中 20 个事后失败；#10394 引入的设备断言在任何设备上都失败（ci-red #10442），引出一串修复 PR。
- PR 自己写下的合并条件被跳过。#10521 正文要求保持 draft 等报告者确认，被转 ready 17 秒后合并，推测的根因是错的（#10548 重修）；#10417 验证段列着未完成的本地门禁就合并，导致 #10427。另有为了让新改动过关而关掉旧回归测试前置条件（#10419 → #10425）、合并后才推的提交静默丢失（#10206、#9106 → #10320、#10322）、以及不经授权翻转出厂默认值（#10386）。
- 维护性在快速变差：鸿蒙 `tests/run.sh` 一周从 63 行涨到 951 行源码 grep，Android `check-host.sh` 涨了 826 行；几个宿主主文件一周各涨一千到两千多行。安全线还发现语法模型目录从 develop 运行时读取、下载地址只校验 `https://` 前缀，一次合并即可改变所有客户端的下载来源（已另行修复）。

## Decision

把这些教训写进 AGENTS.md，新增「合并」和「代码健康」两节，并就地补充已有条目：

- 合并：必过检查和 `android-device-pr` 终态成功后才合，不用管理员身份绕过；验证段写「交给 CI」之前确认 CI 真的执行那条测试（`special_checks` 里由 `verify-local.sh` 负责的只在本地跑，#10480 因此留下一条只在本地红的 Windows 测试）；PR 正文自己写的合并条件和验证段里未完成的本地门禁有约束力，推测未复现的根因不进 develop；不为让新改动通过去改旧回归测试的前置条件；准备合并后不再推，合并前核对 head 提交。
- 代码健康：新断言写成行为测试，不再往 `run.sh` 和 `check-host.sh` 加源码 grep；不再往巨型文件加功能；运行时从本仓库分支拉取的文件不能当信任根。
- 「对齐不等于改默认值」一条推广到所有改出厂值或改缺字段读法的 PR。
- 修正 Android 模拟器一条里「PR 上不跑」的过时说法：自 2026-10-28 起改键盘或设置界面的 PR 会在 API 35 上跑 `android-device-pr`。

每条都附真实 PR 编号，让后来的代理能看到具体后果而不是抽象原则。

## Alternatives considered

- 直接收紧保护规则，取消管理员绕过：机器强制最可靠，也是本笔记最推荐的后续动作；但它会改变维护者自动合并流水线的运行方式，属于需要维护者决定的仓库设置，不由一次审计 PR 改动。文字约定先落地，规则收紧另行决定。
- 为源码 grep 守卫和巨型文件加 CI 门禁（行数不许再涨）：能机器强制，但需要先定阈值和豁免机制，误报会挡住正常修复；先用约定冻结增长，观察一轮后再决定是否上门禁。
- 一次性删除现存的源码 grep 守卫、拆分巨型文件：收益大但风险高，会和大量并行中的 PR 冲突；约定只要求「改到哪条换哪条」「新代码进新文件」，逐步偿还。

## Consequences

代理有了明确的合并前检查清单，合并节奏会变慢：要等设备 job 跑完（API 35 一次约一小时）。源码 grep 守卫和巨型文件停止增长，但现存的不会自动减少，需要后续审计按批迁移。只要保护规则仍允许管理员绕过，这些约定就依赖代理自觉遵守，下一轮审计会重新统计合并时检查未完成的 PR 数量来核对效果。
