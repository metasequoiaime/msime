# Agent Note: 推送前确认 PR 还开着，连着合并时逐个跟上 develop

Status: implemented

## Problem

2026-10-30 这一轮把十几个 PR 依次合进 develop，期间出了两类事故，都不是代码本身的错，而是推送和合并的顺序没人把关。

**合并后才推上去的提交悄悄丢了。** `AGENTS.md` 的 Worktree 一节已经写了「PR 合并后不要在原分支上继续提交或推送」，理由只是远端分支会被重新建出来。实际上更严重的后果是提交本身进不了 develop：PR 已经合并，后推的提交没有任何 PR 带它们进去，GitHub 的合并后自动删分支又把痕迹抹掉了。逐个核对已合并 PR 的 head（`gh pr list --state merged` 的 `headRefOid` 与分支当前的提交比较）才找到这些：

- #9106 在 2026-10-21 开出 21 秒就合并了，之后推到 `fix/ios-voice-session-page` 上的 4 个 iOS 提交（语音与 AI 服务页样式、长按空格说话开关、两个弹窗贴合内容的修复）一直不在 develop 上，由 #10322 和 #10324 补回。弹窗那两个修复丢了之后，「底部弹窗高度不对」被当成新问题又报了一次。
- #10206 合并后推上去的 `3ce6a537b7`（verify-local 的 Windows 子工程运行时）由 #10320 补回。
- 服务端仓库 msime-cloud 的 #1589 同样有一个合并后推上去的提交（单手模式侧边数字键盘的同步字段），由 #1591 补回。

**两个各自全绿的 PR 合在一起编不过。** #10322 删掉了 iOS 的 `voiceShortcutKey`，04:11 合并；#10318（iPhone 横屏和鸿蒙平板的分离式键盘）的检查是在 #10322 合并之前跑的，它的测试还在引用这个符号，04:16 合并后 develop 的 iOS 测试编译失败，04:39 由 #10332 修好。同一轮里 #10318 还把两个没格式化的文件带进 develop，之后在 develop 上提交的格式检查跟着失败，由 #10334 补上。

## Decision

`AGENTS.md` 增加两条约定：

- Worktree 一节「PR 合并后不要在原分支上继续提交或推送」补上后果和检查办法：每次推送前先 `gh pr list --head <branch> --state all --json number,state`，PR 已经 MERGED 就从 `origin/develop` 新切分支，把提交 cherry-pick 过去另开 PR。
- 改动范围一节新增：连着合几个 PR 时，后合的 PR 如果和刚合进去的那个改了同一个平台或共享代码（`crates/`、`shared/`、`packages/`），先 `gh pr update-branch <n>`，再 `gh pr checks <n> --required --watch`，在新的 develop 上转绿再合。互不相干的平台可以直接合。

两条都是给代理和维护者的操作约定，不改仓库设置，也不加新的 workflow。

## Alternatives considered

- **在仓库规则集里打开「合并前分支必须与 develop 同步」**：由 GitHub 强制，人和代理都绕不过去，第二类事故从根上消失。没有采用：develop 一天合几十个 PR，打开后每合一个，其余所有开着的 PR 都要重新同步、重跑几十分钟的 macOS / iOS 检查，外部贡献者的 PR 也一样。绝大多数 PR 之间并不冲突，这个代价是为少数情况让所有人付。规则集归维护者管，要改另行决定。
- **GitHub merge queue**：按顺序在「develop + 队列前面的 PR」上重跑检查，正是第二类事故要的东西，而且不用每个 PR 自己同步。没有采用：需要改规则集并让 CI workflow 响应 `merge_group` 事件，macOS、iOS 的检查要在队列里再跑一遍，排队时间按最慢的 macOS 15 x86_64（二十多分钟）叠加。值得单独评估，不在这次的范围里。
- **推送前的 git hook 自动查 PR 状态**：不靠人记得。没有采用：`pre-push` 里调 `gh` 依赖网络和登录状态，离线或 token 过期时要么误拦要么得放行；而且本地钩子要每台机器各自装，管不到没装的贡献者和代理。
- **只靠事后核对已合并 PR 的 head**：这一轮正是这样找回的，脚本一跑就知道哪些分支在合并后还有新提交。没有采用为唯一手段：发现得太晚，#9106 的提交丢了九天，期间同一个问题被重新报告、重新排查。可以作为定期的兜底，不替代推送前的检查。

## Consequences

- **收益**：推送前多一条命令，挡住「推到已合并的分支上」这一整类丢提交；连着合并时，同平台的 PR 一定在最新的 develop 上验证过。
- **代价**：同平台的 PR 连着合时要串行等 CI，一次 iOS 检查二十分钟上下，几个 iOS PR 依次合要多花一两个小时。互不相干的平台不受影响。
- **判断「同一个平台」靠人**：两个 PR 改的目录不重叠也可能互相影响（例如一个改了 Rust 的公共接口，另一个在平台代码里调用它），所以共享目录被列了进去；仍然拿不准时按要同步处理。
- **不管已经丢的**：这两条只防以后。已合并 PR 之后还有新提交的分支，要靠上面说的事后核对去找。
