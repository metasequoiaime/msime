# Agent Note: 一个 issue 一个 PR

Status: implemented

## Problem

处理 GitHub issue 时，代理会把同一次处理的多个 issue 合进一个 PR。#7045 就是这样：7 个互不相关的 issue（#6888 AI 候选占位、#6847 Linux 设置窗口闪烁、#6829 DeepL 官方 API、#6789 五笔查码、#6781 Android 复制图片发送、#6807 Caps Lock 切换中英文、#6792 物理键盘候选栏跟随光标）落在同一个 PR 里，改动横跨引擎、共享设置和六个平台宿主。结果是：

- 审查没法按 issue 分开看，一个 issue 的问题要在其他 6 个的 diff 里找。
- 合并只能全有或全无。#6789 的 iOS 查码面板、#6888 的 Android 设备验证还没补完，却跟着其余的一起进了 develop，只能事后各开跟进 PR。
- 回滚粒度也是整包，某一项出问题无法单独撤回。
- `Fixes #N` 写在一个 PR 里，其中一项（#6807）在合并前没来得及写进正文，issue 没被自动关闭。

## Decision

每个 GitHub issue 单独一条分支、一个 PR，正文写 `Fixes #N`；只实现了 issue 的一部分时写 `Refs #N`，不自动关闭。几个 issue 即使同一次处理，也各开各的 PR。

没有对应 issue、在做某件事时顺带发现的小问题（漏改的调用点、相邻的小 bug），并进那件事的 PR，不为每个小问题另开分支。规则写在 AGENTS.md 的「改动范围」一节。

## Alternatives considered

- 同一次处理的 issue 合进一个 PR：最强的理由是省 CI 和门禁——这个仓库的 pre-push 门禁要编译整个工作区，多个 PR 就要多跑几遍，几个 issue 碰同一批文件时还要互相解冲突。但 #7045 说明，省下的这些时间远不如审查、合并、回滚能按 issue 分开重要；冲突可以靠先合一个、后面的合入 develop 再解决。
- 按平台或模块打包（例如所有 Android issue 一个 PR）：比全部合在一起好，但同一平台上的 issue 依然互不相关，合并和回滚的问题照旧。
- 不定规则，由代理自行判断：#7045 正是代理自行判断的结果，而且代理的全局配置里原本就有「同一次对话的问题合进一个 PR」的倾向，不写进仓库规则就会继续这样做。

## Consequences

issue 多的时候 PR 数量变多，CI 和本地门禁的总耗时随之增加；几个 issue 改到同一批文件时，后合的 PR 需要再合一次 develop。这是有意接受的代价。issue 回复可以直接指向各自的 PR，合并即关闭对应 issue。

检索活跃笔记未发现 PR 粒度或 issue 处理流程的已有归属，本篇为首篇。
