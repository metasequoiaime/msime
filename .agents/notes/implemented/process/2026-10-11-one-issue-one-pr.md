# Agent Note: 一个 issue 一个 PR

Status: implemented

## Problem

处理 GitHub issue 时，代理会把同一次处理的多个 issue 合进一个 PR。#7045 就是这样：7 个互不相关的 issue（#6888 AI 候选占位、#6847 Linux 设置窗口闪烁、#6829 DeepL 官方 API、#6789 五笔查码、#6781 Android 复制图片发送、#6807 Caps Lock 切换中英文、#6792 物理键盘候选栏跟随光标）落在同一个 PR 里，改动横跨引擎、共享设置和六个平台宿主。结果是：

- 审查没法按 issue 分开看，一个 issue 的问题要在其他 6 个的 diff 里找。
- 合并只能全有或全无。#6789 的 iOS 查码面板、#6888 的 Android 设备验证还没补完，却跟着其余的一起进了 develop，只能事后各开跟进 PR。
- 回滚粒度也是整包，某一项出问题无法单独撤回。
- `Fixes #N` 写在一个 PR 里，其中一项（#6807）在合并前没来得及写进正文，issue 没被自动关闭。

## Decision

每个 GitHub issue 单独一条分支、一个 PR，正文写 `Fixes #N`；只有 issue 要求的行为或平台还有一部分没实现时才写 `Refs #N`，不自动关闭，并在正文列出还差什么。几个 issue 即使同一次处理，也各开各的 PR。

没有对应 issue、在做某件事时顺带发现的小问题（漏改的调用点、相邻的小 bug），并进那件事的 PR，不为每个小问题另开分支。规则写在 AGENTS.md 的「改动范围」一节。

## `Refs` 的判据

`Refs` 只看实现范围：issue 要的某个行为没做、要的某个平台没接、或者只加了诊断还没修，才算只做了一部分。验收缺口不算：没在真机、报告者的环境、真实 TIP/IMK/Fcitx 编辑器里跑过，写进 PR 的验证段，照样写 `Fixes`；需要报告者复验的，合并后在 issue 里请对方用下一个版本确认，复现了再重开。

2026-10-25 清点时，最近合并的 300 个 PR 里 57 个只写了 `Refs`，挂着 28 个仍打开的 issue；逐个核对后，其中 11 个的代码早已完整覆盖 issue，只是 PR 因「尚未设备验收」「未覆盖报告者桌面」写了 `Refs` 并保持草稿，合并时没人改关键字，issue 一直没关，只能人工补评论关闭。另有十几个同样只差报告者复验。

## Alternatives considered

- 同一次处理的 issue 合进一个 PR：最强的理由是省 CI 和门禁——这个仓库的 pre-push 门禁要编译整个工作区，多个 PR 就要多跑几遍，几个 issue 碰同一批文件时还要互相解冲突。但 #7045 说明，省下的这些时间远不如审查、合并、回滚能按 issue 分开重要；冲突可以靠先合一个、后面的合入 develop 再解决。
- 按平台或模块打包（例如所有 Android issue 一个 PR）：比全部合在一起好，但同一平台上的 issue 依然互不相关，合并和回滚的问题照旧。
- 不定规则，由代理自行判断：#7045 正是代理自行判断的结果，而且代理的全局配置里原本就有「同一次对话的问题合进一个 PR」的倾向，不写进仓库规则就会继续这样做。
- 验收没做完也写 `Refs`，等报告者确认再关：最强的理由是关早了会让报告者以为问题已经解决，而代码只在合成环境里证明过。但 issue 关闭后可以随时重开，报告者复测失败时重开的成本很低；反过来，`Refs` 合并后没有任何机制会再回来关 issue，2026-10-25 的清点就是结果。验收缺口留在 PR 验证段里，比留一个打开的 issue 更容易被下一个改这段代码的人看到。

## Consequences

issue 多的时候 PR 数量变多，CI 和本地门禁的总耗时随之增加；几个 issue 改到同一批文件时，后合的 PR 需要再合一次 develop。这是有意接受的代价。issue 回复可以直接指向各自的 PR，合并即关闭对应 issue。按实现范围而不是验收状态选 `Fixes` / `Refs`，代价是一部分 issue 会在报告者复验前关闭，偶尔需要重开；换来的是打开的 issue 只剩真正没做完的工作。

检索活跃笔记未发现 PR 粒度或 issue 处理流程的已有归属，本篇为首篇。
