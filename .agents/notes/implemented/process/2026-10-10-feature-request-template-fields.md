# Agent Note: 功能建议模板按场景拆问，平台不进模板

Status: implemented

## Problem

功能建议模板原先只有「遇到了什么不便」「希望怎样改进」「其他信息」三栏。官网需求表单（msime-web 的 `/feedback/`）不自带字段，而是读取本仓库 `.github/ISSUE_TEMPLATE` 现场渲染，所以模板问得多粗，官网建出来的 Issue 就有多粗。#6648 就是典型：提交者只写了一两句，维护者看不出使用场景、现在的替代做法和期望的具体操作，也没有版本可以核对新版本里是否已经有了这个功能。

## Decision

`feature_request.yml` 拆成六栏：必填的「在什么情况下用到」（`scenario`）、「现在是怎么做的，哪里不方便」（`problem`）、「希望怎样改进」（`proposal`），可选的「其他输入法的做法」（`reference`）、「输入法版本」（`version`）、「其他信息」（`additional`）。`problem`、`proposal`、`additional` 沿用原 id，其他是新字段。每栏都给出面向普通用户的说明和示例，示例统一围绕同一个候选字号的场景，示范「具体到软件、操作和效果」的写法。

模板不加平台字段。平台由官网表单的归属选择决定：msime-web 把它写成 Issue 正文的首节，并打上本仓库已有的 `platform/*` 标签（msime-web#365）。直接在 GitHub 提交的大多是贡献者，可以在正文里说明，也可以由维护者补标签。

## Alternatives considered

- 模板加一个「平台」下拉框：直接在 GitHub 上提交的 Issue 也能带上平台，这是它最强的理由。但官网用户已经在表单顶部选过平台，模板字段会让他们再选一次，两处可能不一致，还要让官网特判这个 id 去隐藏或预填，等于在两个仓库之间新增一条隐式契约。
- 官网对必填文本框设最少字数：能挡住一句话的提交，但 GitHub 原生表单做不到同样的限制，两个入口的规则会分叉；而且字数门槛容易逼出凑字的内容，不如把问题本身问具体。
- 保持三栏，只改说明文字：改动最小，但「哪里不方便」一栏同时承担了场景和现状两件事，用户往往只答其中一件，拆开才能让两者都被问到。

## Consequences

必填栏从两栏变成三栏，提交门槛略有提高。官网表单的模板版本随本次提交变化，正在填写旧版本模板的用户提交时会收到「仓库模板已更新」的提示并按新模板核对，这是官网已有的处理路径。Bug 反馈模板已有复现步骤、期望结果和版本栏，本次不动。

检索活跃笔记未发现 Issue 模板或官网需求表单的已有归属，本篇为首篇。
