# Agent Note: 混输首屏限制表情候选占位

Status: implemented

## Problem

Linux 的拼音候选把 emoji 和颜文字接在其描绘的汉字后面。同一页有多个锚定词时，表情行会和汉字一起占满首屏，常用同音字被推到下一页。#11323 要求聚合表情或让一页只出现一个表情；共享引擎的九键和 26 键混排路径还共用同一套锚定逻辑，改动需要保留九键现有排序契约。

## Decision

26 键混排在收集锚定表情时使用宿主传入的 `first_page_rows` 计算插入位置；只有普通候选已经填满一页时，首屏才最多选择一行 emoji 或颜文字。超过上限的锚定行不丢弃，沿用每组末尾的有界候选队列，排在列表后面。短列表没有被表情挤走普通候选时保留原顺序。`first_page_rows` 为 0 的内部测试辅助路径和九键 `insert_expressive_rows` 不启用这条首屏策略，因此九键的既有候选分页与排序保持不变。

这个限制按 emoji 与颜文字合计计算，而不是每类各留一行：用户看到的是同一种“表达候选”占位，分开计数仍可能让两行表情连续挤走汉字。

## Alternatives considered

- **只限制同一个锚定词后的表情**：这是已有 #11334 修复采用的范围，能处理单个汉字后连续表情，但多个汉字各带一行表情时首屏仍可能被占满，不能覆盖 #11323 的场景。
- **把多行表情聚合成一行**：候选行没有“选择其中一个并插入”的协议，聚合后会改变上屏文本，不能安全实现。
- **删除超出首屏上限的表情**：会丢掉用户仍可能需要的候选；把它们移到列表末尾既保留候选，又不改变普通候选的顺序。

## Consequences

首屏在普通候选足够填满一页时最多出现一行表达候选，后续汉字保留在同一页；其余表达候选仍可翻页选择。短列表不会为了制造空白页而丢掉表达候选。该规则只作用于 26 键混输，九键继续使用原有每组上限和锚定顺序。候选排列对依赖表达候选位置的评测需要以 `first_page_rows` 一起复现，且报告者的 Linux 桌面和真实编辑器验收仍待完成。

验证覆盖 `queries.rs` 的合成回归，确认 emoji 与颜文字合计只占首屏一行、其余行保留在列表尾部；远端 `rbuild bash scripts/verify-local.sh --quick` 通过。
