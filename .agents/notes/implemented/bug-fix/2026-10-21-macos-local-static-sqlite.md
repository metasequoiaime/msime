# Agent Note: 本机签名输入法使用静态 SQLite

Status: implemented

## Problem

本机 SDK 的 SQLite 暴露了系统运行库不存在的符号。改链 Homebrew 动态 SQLite 能通过未签名测试，但安装脚本启用 hardened runtime 后，开发证书与 Homebrew 库的 Team ID 不同，dyld 在启动时拒绝加载。编译通过不能证明签名安装可用。

## Decision

本机上手指南的 SQLite 兼容路径使用现有 Homebrew 静态库，并清空此前设置的动态库搜索参数。`text-client-test` 复用 `apple-client` 公开传递的 SQLite 依赖，不额外声明 `-lsqlite3`，避免链接器先绑定系统动态库。

## Alternatives considered

- 动态链接 Homebrew SQLite：无需改动依赖且未签名测试通过，但签名后的库验证拒绝加载，因此不用。
- 关闭库验证：可以加载不同签名来源的动态库，但没有必要为可静态链接的依赖放宽输入法的运行时保护。

## Consequences

静态库进入最终二进制，不需要重新签名或修改 Homebrew 全局安装。代价是二进制增大，SQLite 更新需要重新构建。官方设置应用的启动刷新仍可能覆盖本地输入法；开发测试必须避免同时运行官方设置应用。相同标识的构建目录进程也不能充当已安装副本的验收证据。

相关历史检索命中九键测试和词库自动更新笔记，二者不持有本机签名链接决策，不需要迁移。

## Verification

静态链接构建的 6 项关键 CTest 通过，Apple Development 签名后的只读注册探针可以启动。注销重新登录后，用户确认核心可用。配套设置应用以相同版本构建，嵌入已经验收的签名核心，打包后用 `ditto` 恢复 Sparkle 链接，再签外层应用，深度签名检查通过；用户确认 0.53.0 设置页面和输入正常。

替换设置应用时，旧官方设置进程仍可能刷新磁盘上的核心，因此验收不能只看仍运行的旧进程。退出设置应用、重新安装本地核心后，再启动本地设置应用，核对内嵌核心和安装副本 UUID 一致，才能证明不再被官方副本覆盖。首次依赖缺失需要获得用户允许后才下载。
