# Agent Note: 粤语双拼展开按两键定音节

Status: implemented

## Problem

#10085 报告粤语双拼的几处候选错误。[粤语双拼键位规则](../../implemented/feature/2026-10-26-cantonese-shuangpin.md)把每两键解成粤拼音节，再把结果当普通粤拼输入交给原有查找，这一步丢掉了双拼本身的约束：

- 展开读音直接把音节拼在一起（`danz` → `daanei`），普通粤拼的最长匹配重新切分成 `daan ei`，候选变成「蛋」「但」，「打」不见了，候选覆盖的键数也跟着算错。
- 普通粤拼对末音节做前缀补全。`voda` 展开成 `ngodaa` 后，`daa` 被当成 `daap`、`daai` 的开头，补出「我答」「我帶」；而 `daap` 在双拼里是 `dc`，`da` 只能是 `daa`。
- 一个双拼码对应多个读音时，各读音的候选按读音字节序首尾相接（`sx` 先列 `soek` 的「削」，再列 `soeng` 的「上」）。
- 独立「粤语双拼」入口下末尾只按了一个键时，展开整体失败，退回普通粤拼，把双拼码当粤拼字母去读。

## Decision

- 展开读音在每个音节之间都写 `'`，临时粤拼输入的分段就是双拼的两键一音节，不再由最长匹配重切。末尾刚敲下的 `'` 不再让整段退回普通粤拼。
- 双拼展开的查找不对末音节做前缀补全（`candidates_into_jyutping` 的 `complete_trailing` 为假），普通粤拼路径不变。
- 所有展开读音的候选合在一起，先按覆盖的音节数从多到少、再按权重从高到低稳定排序，然后按文字和覆盖音节数去重。
- 独立双拼入口下最后一段以单个键结尾时，前面的完整码照常展开，末键只定下声母：`shuangpin::initial_prefixes` 从库存里取出首键为该键的音节在粤拼里的开头拼写（`v` → `ng`，零声母 `o` 按首字母分组，`m`、`ng` 整个音节作前缀），这些前缀会补出别的键上的音节（单按 `o` 时 `m` 前缀会补出上千条 `maa` 一类的行，「唔」之外的 `m` 行全被挤掉；单按 `n` 时一半是 `ng` 开头的行），所以查询前先用 `shuangpin::key_spans` 按库存把每个前缀收窄成只落在该键上的段：`g` 拆成 `ga`、`ge`、`go`……绕开 `gw`，`n` 绕开 `ng`，零声母键的 `m`、`ng` 只剩整音节本身做精确查询；前缀下没有别的键的音节时（`d`、`s` 等大多数键）仍是原来的一次区间查询。同一个前缀的各段结果合起来按权重留最重的 `SPAN_LIMIT` 行，补出的末音节再用 `shuangpin::encode` 核对一次，筛掉库存里 `encode` 不认识的口语音（`deu`、`gep` 一类二十几个）；这些音节不在任何键上，收窄时也不为它们拆段，否则 `d`、`c`、`z` 会被拆成十几段，查询反而比原来多。这些候选覆盖整段输入，`shuangpin_code_end` 把末尾单键按一个字节计。
- 「粤语」入口的自动识别遇到奇数长度仍交给普通粤拼。自动识别靠前两键不是合法粤拼音节来判断，而 `gw`、`kw`、`ba`、`cy` 这些开头既能解成双拼码、又是粤拼音节的前两个字母，第三键可能是用户还在拼同一个粤拼音节（`gwo`），这时把它当下一个声母会改变纯粤拼用户的结果。

## Alternatives considered

- **按报告者的 Rime 方案逐条复刻 xform 顺序**：报告者的要点是复韵母必须先于单韵母处理，否则会被覆盖。这里的 `encode` 拿整个韵母做精确匹配，不存在顺序覆盖，`yun`/`yut`/`uk` → `r`、`aap` → `c` 等映射已经与报告一致；参考仓库没有许可证，不能拷贝其 schema。
- **末尾单键总是逐个枚举以该键开头的音节、各做一次精确查找**：结果最精确，但一个声母常有三四十个音节，乘上前面码的多个读音，每次按键要多出上百次查询。按库存收窄的段只在前缀与别的键共用开头时才拆，段数是声母后第二个字母的种类数（`g` 约五六段），而不是音节数。
- **只靠放大区间查询的上限**：最初的实现用 `SPAN_LIMIT` 而不是 `COMPLETION_LIMIT` 作上限，想靠多取一些行抵消筛掉的部分。按实际词库核对，单按 `o` 时 `m` 前缀约有一千四百多行，最重的两百行里只剩「唔」，「呣」「嘸」都被挤掉；`ng` 前缀约六十行只留下三十来行；单按 `n` 时两百行里只有一百零七行真是 `n` 声母。任何固定上限都挡不住共用开头的前缀。
- **区间查询取满上限又筛掉了行时，退到逐音节精确查询**：这一版曾经这样做，结果正确，但单按 `g`、`k`、`n`、`o` 这类键时几乎每次都会触发：实际词库的 `g` 区间有两千八百多条单音节行，最重的两百行里就有 `gw` 行，于是要再扫一遍库存、对四十九个 `g` 音节各做一次精确查询，最多分配约两千八百行再排序截断，低端手机上每次按键的延迟会明显变大。按段查询同样取回本键最重的行（只有 `encode` 不认识的口语音可能占掉区间末尾的几行），实际词库里只有 `g`、`k`、`m`、`n`、`v` 键要拆成四到六段，零声母键的 `m`、`ng` 各做一次精确查询，查询次数和取回的行数都少得多。
- **在 SQL 里按音节数或声母过滤**：要给共用的 `LanguageDictionary` 加一个只给粤语双拼用的查询，而 `g`/`gw`、`n`/`ng` 的区分属于双拼键位规则，不该进通用字典层。
- **自动识别入口也接受末尾单键**：双拼用户在「粤语」入口里也能边打边看到候选，但会把正在拼的粤拼音节误读成下一个声母，破坏 [iOS 独立入口](../../implemented/feature/2026-10-27-ios-cantonese-shuangpin-selection.md) 中保留普通入口自动识别行为的约定。

## Consequences

- 双拼候选只来自按键确定的音节，`voda` 不再出现「我答」「我帶」；词库里没有「我打」「上傳」这类整词时，仍只能逐字选出。整句组词和补词不在这次范围内。
- 同一双拼码的多个读音按权重混排，首选是最常用的读音，而不是字节序最小的读音。
- 独立双拼入口下末尾单键会多出若干次区间查询（零声母 `o` 最多七个前缀，与别的键共用开头的前缀再按第二个字母拆成几段），展开组合仍受 64 个上限约束。
- 报告中 iOS 点「上」却上屏 `SX` 的现象在引擎和 runtime 层没有复现：同一条 `Action::Select` 路线上屏「上」，剩下的 `cr` 继续给出「傳」。宿主层（行内预编辑、文档回声判断）还需要在真机上复查。
- 所以这次只是 #10085 的一部分，PR 用 `Refs #10085` 而不关闭 issue。仍未完成的是 iOS 宿主上屏编码的问题，以及报告要的整词识别：`sxcr` 出「上傳」、`vodanz` 出「我打你」需要粤语双拼的整句组词，实际词库里也没有「上傳」「我打」「我打你」「打你」这些词（`soeng cyun` 只有「相傳」）。

## Verification

- `cargo test -p msime-engine --lib cantonese::`：新增 `voda` 不补全、`vodanz` 选「我」后 `danz` 读作 `daa nei`、`sx`/`sxcr` 按覆盖和权重合并、独立入口末尾单键（`vod`、`von`、`voo`、`d`）及自动入口奇数长度不变的回归；单按 `n`、`o` 时两百多条 `ngo`、`maa` 重行不挤掉「你」「唔」「誒」。`cargo test -p msime-engine --lib cantonese::shuangpin`：`key_spans` 把 `g`、`n`、零声母的 `m`/`ng` 拆成只落在本键上的段，不与别的键共用开头的前缀不拆。
- `cargo test -p msime-input-runtime --lib cantonese`：`cantonese_shuangpin_tap_commits_the_word_and_keeps_the_rest_composing` 在两个入口下经 `Action::Select` 点选「上」再点「傳」。
- iOS、Android、HarmonyOS 真机与模拟器上的实际打字均未验证。
