# Agent Note: 导入同步在有界作用域内复用集合状态

Status: implemented

## Problem

#8643 的 33555 条合成 Rime 词在当前 release 宿主测量中完整写入耗时 11861/11526 ms，分别花 7926/7537 ms 在集合刷新、3836/3896 ms 在引擎同步。每 128 条后重新解析全部集合及余下 outbox；采样同时命中 CollectionFile/OutboxFile 反序列化和原子写盘。负载为空主库加精确索引、全部共用同一编码，不能代表正式主库或手机。

## Decision

集合服务提供持有原有集合锁与已完整校验状态的刷新作用域，同一作用域多次刷新仍在每次发送后原子保存 outbox 与原有回执。Host API 给命名词库增加 `synchronize` 操作，按 `budget_millis`（1–2000，默认 2000）毫秒软预算运行，在每轮调用既有个人同步（至多 128 条、批后释放维护租约）后刷新该作用域。忙碌时未发送集合条目，直接保留待处理；批次中失败与无进展按原规则结束。Android 导入等待改用此操作，仍在工作线程调用，提示与两秒预算不变。键盘空闲续写共用该入口，预算为 100 毫秒，批间继续释放维护租约；返回主线程重新确认代次和没有输入会话后再继续。空闲任务的代次改为 `volatile`，排队工作在执行前也确认代次，键盘启动仍只执行原有单批同步。

不保存跨调用缓存，不改变磁盘格式、文件权限、fsync 或原子替换规则；下一次调用重新读盘，其他进程在作用域结束后可取得集合锁。`synchronize` 返回个人队列与 outbox 的总 `pending_count`、个人 `failed_count` 和最后一轮 `sent`，不让空活动队列被误认为全量导入完成。

## Alternatives considered

- 跨调用缓存已解析文件：能够进一步减少解析，但要引入内存预算与跨进程失效规则；本方案只在原集合锁内复用状态，结束即释放。
- 改成 SQLite 或分块 outbox：可以降低重写剩余队列的成本，但改变落盘格式、迁移与降级边界；先减少已确认的重复解析并量化收益，再决定是否需要迁移。
- 延迟所有 outbox 确认直到作用域结束：落盘次数更少；但数据库成功后进程崩溃可能重排新请求并把自身词条误认成用户原有词，继续每批落盘。

## Verification

- 宿主词库服务 100 项回归与 Host API 批次 16 项回归通过，两包全部 targets 的严格 Clippy 通过。覆盖超过 128 条的完整写入重载、繁忙时两份持久队列不变、首次校验拒绝损坏、预算到期保留 132 条、单项失败后继续同步、未知字段与非法预算拒绝、每批 outbox 落盘和检查点写失败后重试不重复发送。
- 同一 release 二进制交替测量旧/新/旧/新，每轮断言 SQLite 中完整的 33555 条，不以耗时设单测门槛。
- 正式只读拼音资源按仓库锁 SHA-256 校验后复制到合成目录，实际候选会话中的 `a/mei/ke` 常用字位置在导入低权重原字及权重 7622 的合成新字后保持，停用集合后仍保持；此专项不使用报告附件或用户工作库，也不能代表全部三万词的整体排序。
- 最终完整 quick 通过，实际覆盖 Linux 设置壳编译、Linux 原生 92 项测试和 macOS 原生编译；缺少工具链的阶段按脚本报告跳过。Android 宿主检查通过 248 项 JVM 冒烟及 191 份设备套件源码编译，新原生 APK 和设备测试 APK 构建通过。
- Android API 28、35 的四包测试各通过 1855 项（client-core 425、client-base 36、client-providers 224、client-services 1170），各有 14 项忽略、7 项硬链接用例被设备 runner 按平台过滤。
- API 35 原生导入专项通过 74 词立即应用、九键第六项、繁忙重试、排序与 33555 条完整写入重载；显式容量测量为 47139 毫秒、216 轮，100 毫秒空闲软预算下最长调用 372 毫秒。
- API 28 核心 smoke 完整通过，覆盖原生输入、七套数字键盘方案、词库导入及剪贴板保存生命周期。API 28 显式容量测量通过同样的完整性断言，33555 条耗时 53798 毫秒、232 轮，最长空闲同步调用 632 毫秒。API 35 默认完整 smoke 全部通过且没有跳过已知失败套件，覆盖完整候选、各输入方案、实时偏好及剪贴板保存生命周期；未启用额外的设置、统计或手写套件。

## Consequences

集合锁最多跨多个批次持有，2000/100 毫秒均为批次结束后检查的软预算；正在编辑集合的其他进程可能等待。任何集合损坏仍须在第一个同步批次前报告，不得借复用状态跳过首次完整校验。

最终源码的实际预算模型为首次 2000 毫秒、后续 100 毫秒，同一二进制交替执行旧/新/旧/新：

| 路径 | 第一轮 | 第二轮 | 同步调用次数 |
| --- | --- | --- | --- |
| 原单批同步加刷新 | 19418 ms | 20271 ms | 263 / 263 |
| 有界作用域，后续 100 毫秒 | 17020 ms | 15753 ms | 116 / 112 |

新路径最长调用为 2026/2043 ms，包含首次两秒窗口内的多个独立 128 项事务，不能拿它与旧路径单批最长调用比较。测量运行在同一专用副盘临时目录，系统其他负载未隔离，不将结果当成手机吞吐或固定提速比例，尚未达到每秒万行。早期全部调用都用 2000 毫秒的模型为旧 14043/19663 ms、新 9835/12086 ms，只说明减少重复解析的潜力，不代表产品空闲续写的实际收益。

原生容量显式测量通过产品的 `synchronizeIdle` Java 入口继续排空，每次使用真实空闲任务的 100 毫秒预算；循环只替代等待真实键盘空闲事件，不将它记作系统输入法生命周期验收。两套设备均为 arm64 专用模拟器，测量时未隔离宿主上的其他负载，不将耗时当作真机吞吐承诺。源代码提交 `43758ad509` 的全部 PR CI 检查通过；最终跟进只更新本篇验证记录。

进一步选择持久化方案前，使用[分层吞吐测量](../testing/2026-10-19-dictionary-throughput-layers.md)分别检查引擎批次和个人队列的成本；分层结果不替代完整导入或设备测量。
