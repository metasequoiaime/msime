# Agent Note: 拼音候选保留大写字面片段

Status: implemented

## Problem

#8773 的当前图把整串大写双拼解成中文；报告同时要求首字母大写英文继续补全，以及大写 `F` 保留、后续小写双拼转换成中文。只调高英文候选排名无法同时满足这三种输入。

现有 `QuanpinScheme`、`ShuangpinScheme` 保留带大小写原文，但词库和句子查询统一使用小写键，因此大写也参加中文解码。`CandidateQueries::mixed` 只允许不能完整切成拼音的精确英文领头；原文正好也是合法拼音或双拼时，中文仍占首位。

官方文档只能作为已有能力的边界依据：[Apple 双拼帮助](https://support.apple.com/zh-hans/guide/chinese-input-method/cim9ecd77923/mac)支持在中文候选里选择英文；[微软拼音帮助](https://support.microsoft.com/zh-cn/windows/hardware/input-devices/microsoft-simplified-chinese-ime)保留双拼下的 `Shift+U/V` 特殊模式。它们没有定义水杉应怎样处理所有大小写混合，本篇分段规则依据本 issue 的期望图及仓库已有约束作出，不将它冒充其他产品的完整行为。

## Decision

普通全拼、双拼组字中，大写字母属于字面片段，不作为中文音节或简拼查询。原文不拆开上屏：纯大写组字提供原文及英文补全，混合组字允许小写片段转换中文、保留大写片段。整词英文匹配继续作为英文候选；不能把所有首字母大写输入强制切换成专用英文模式，否则 `F` 加小写双拼的中文混输消失。

共享 `InputSession` 从原文中取开头的大写片段和首个小写片段，仅将小写片段交给现有全拼或双拼 provider。候选可覆盖这个小写片段的一部分；覆盖完整片段时带上随后连续的大写字母，下一个小写片段在选词后继续查询。未转换的完整原文始终有一行；大写起头而小写片段不是完整音节时，原文优先，避免 `Python` 的 `P` 被拼成简拼。完全匹配的英文可领先，其他英文补全可选。

合成行使用既有 `Generated` / `Fallback` 来源，`pinyin` 存实际覆盖的带大小写原文，`canonical_pinyin` 留空。提交入口先识别这类行，按原文字节范围推进并切断学习链，不将合成行送入调频、整句学习、个人上下文或手动词条管理。不新增宿主来源枚举或 wire 字段。内部光标只查询光标前的原文，不给会整段结束组字的英文补全；混合原文停用云与 AI 拼音查询，代次校验继续拒绝旧回包。

末尾辅助码只在它前面没有字面大写时优先，避免将 `NIHC` 误当作 `ni` 加双辅助码。音节内辅助码沿用已有双拼解析器，只有音节编码本身均为小写、且大写位于双辅助码第二位的路径才拥有大写。关闭辅助码后同一字符按字面内容处理。

解码结果需保留原始输入范围与来源：选中含字面片段的候选不能把字面字母算作拼音音节，也不能把合成字符串按原词条写入词频或造词日志。退格、光标中间编辑、选词续输、结束组字和异步候选必须共用相同的片段边界。大写显示恢复由 #8776 独立负责，内部英文词条仍保留规范化查询键和词库原始身份。

已启用快捷入口与活动辅助码保持明确的优先级；#8774 独立处理未启用入口和空 Unicode 遇到拒绝大写的衔接。本篇不更改 `local_modes.shift_letter_entry` 默认值。它既涉及桌面习惯，也被触屏菜单复用，不能用翻转一个默认布尔值绕过解码问题。

## Alternatives considered

- **只让英文候选领头**：改动小，常见完整英文词能避免空格误选中文；但缩写或未收录的词仍无保障，大写仍参与错误中文组合，无法满足报告中的字面 `F` 混输。
- **所有首字母大写都只出英文**：词形和空格上屏容易统一；但关闭了报告明确期望的小写片段中文转换。
- **默认禁用快捷入口**：连续英文更容易输入；但已有用户和触屏菜单同时受影响，且无法解决普通字母已经进入拼音后的中文误解码。
- **快照里改中文候选文字并拼上大写**：能迅速改变显示；但候选来源和音节消费仍指向原词，选词续输、调频和学习会产生错误身份。片段边界必须在解码和消费层成立。
- **在词网格中引入字面边并一次解码所有片段**：能产出跨多个大小写边界的整句候选，并与中文句子统一排序；但需要改变句子评分、读音与学习的完整契约。当前按首个小写片段复用 provider 和既有逐段选词入口，先修正字面边界及实际消费，不把英文字母当音节参与句子模型。

## Verification

合成回归覆盖全大写 `NIHAO` 不出「你好」、`Python` 不按 `p` 简拼替换、`Fnihao` 能选 `F你好`、全小写仍出原中文、活动辅助码仍筛选；全拼与双拼、光标前缀选词与删除、空格和标点上屏、原文提交、异步回包及学习日志分别验证。共享 runtime 回归经真实引擎检查全拼、双拼的大写与中文混输及高亮候选选择。

远程独立镜像的最终完整回归：引擎 2359 项通过、49 项忽略，runtime 324 项通过，golden 31 项通过（300 个场景）。两 crate 的全部 targets 严格 Clippy 与格式检查通过。首轮 quick 的平台编译通过，但工具契约误用系统 Python 3.9 失败；显式改用已安装的 Python 3.14 后重跑 quick，最终通过：Rust 工作区、Android 与 WebAssembly 目标、Java 宿主、Linux 设置壳和原生 90 项、macOS 原生宿主、共享 Apple bridge 均通过。Windows 本机可运行 169 项通过，2 项因宿主差异排除，61 项需要 Windows；MinGW/pipe 与 HarmonyOS 真打包因环境缺失跳过，不计通过。不能把该首轮记为门禁通过。

iOS 的辅助码关闭回归现在核对 `shiY` 的大写字面片段：只把 `shi` 转换成原首选，再保留 `Y`；不再要求与全小写 `shiy` 的候选相同。开启辅助码时的 `Y` 仍按部首筛出「识」。原生 arm64 测试包在远端构建后，因远端系统盘耗尽而无法安装；复用同一编译产物，在本机同版本 iOS 27 模拟器执行 `HelpcodeSettingsTests`，5 项全部通过，不计作真实系统键盘验收。补测后的 quick（`20261019-204348`）通过，Linux 设置壳和原生 90 项均实际执行通过；笔记在本机单独校验通过。

## Reproduction

最初在未修改生产代码的独立远程 macOS 镜像运行 `cargo test -p msime-engine --lib capital_`：全拼 `NIHAO` 的首候选实际为「你好」；`Fnihao` 的候选实际为空，两项均失败。每项在全拼断言处即失败，该红阶段不代表双拼也已实测。修复后的回归执行完整的全拼和双拼分支。

## Consequences

`Ni` 不再把首字母当简拼「你」；全大写和未知英文都有可直接选中的原文，大小写边界不会被句子联想吞掉。候选的消费范围与来源先成立，快照不再承担修补中文候选字符串的职责。代价是含字面大写的片段不参与个人中文学习、云候选和 AI 拼音候选，多段小写按既有逐段选择路径推进，整段结束时依次使用各段首选。没有在宿主另存组合状态，也没有把合成词库回归当作系统输入法 UI 验收；尚未完成真实 macOS 编辑器验收。
