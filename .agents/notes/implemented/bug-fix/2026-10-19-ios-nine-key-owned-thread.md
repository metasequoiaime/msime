# Agent Note: iOS 九键与 26 键拼音查询交给固定会话线程

Status: implemented

## Problem

真机九键连续输入时，主线程同步等待引擎查询。减少UIKit重复更新后仍有约35–36 ms的整键加布局P95；[个人评分上界试验](../../rejected/bug-fix/2026-10-19-lattice-personal-score-bound.md)没有带来足够整体收益。主线程等待期间不能及时处理触摸与绘制。C ABI会话绑定创建它的操作系统线程，普通串行DispatchQueue不能保证每次使用同一线程。

## Decision

用一个持久Foundation线程拥有进程内的全部输入会话，创建、焦点、查询、设置、维护和销毁都通过它执行。保留原有同步API作为控制命令的顺序屏障；普通全拼九键数字、26 键全拼字母和 26 键双拼字母走异步入口，主线程只投递按键，按顺序接收拥有型快照后绘制。原始C指针和借用字节不跨异步边界。

异步按键完成前，控制器视为正在组字，空格、退格、回车、Tab、Shift、符号和焦点边界先排空此前按键并画出最新一帧。回调按文档身份和显示代次核对；离页、方案改变或输入框改变不能使旧结果在新文档重现。候选选择必须使用画面快照携带的候选身份，不能用异步引擎的最新页重新解释旧按钮下标。每次上屏完整保留，不能通过丢弃旧快照丢掉提交。旧画面候选身份被拒绝时重新读取当前视图并携带诊断返回，不能构造空预编辑把仍在引擎里的组字视觉清掉。候选释义、云结果和设置等同步session调用同样先排空此前的异步按键（九键数字和 26 键字母），避免较新的结果画完后又恢复较旧的按键快照。主线程的UIKit和文本代理访问仍只在主线程。

## Historical audit

已检索iOS异步、线程绑定、持久线程及焦点代次。[主线程绘制预算](../../implemented/bug-fix/2026-10-18-ios-keystroke-render-budget.md)仍持有UIKit重复更新决定，本篇接管引擎等待；[词库维护锁释放](../../implemented/bug-fix/2026-10-14-ios-snapshot-worker-lock-release.md)仍持有休眠及重建语义，线程迁移必须保留。页面请求代次工具管理SwiftUI页面，不用于输入命令顺序。没有完全吸收或过时提案。

## 26 键全拼与双拼（#10031）

iPhone 用户多数用 26 键全拼，0.52 之后这条路径每个字母仍在主线程同步等待引擎，与九键改造前的等待是同一种。异步入口因此覆盖三类按键：普通全拼九键的数字 2–9，26 键全拼的小写字母，26 键双拼（小鹤、自然码、微软、首道）的小写字母和微软双拼的 `;`。其余按键一律同步：五笔、粤拼、日语、韩语、越南语、藏文、注音、笔画，14／18 键与九键双拼网格，本地模式，Shift 之后的辅助码大写，分词符 `'`。桥接的 `enqueueCharacter` 只按引擎网格和字节把关（九键网格收数字、不带按下点；不用网格时收小写字母和 `;`），方案由键盘判断，两层不重复同一张方案表。

双拼带按下点的字母（#10018）连同 `TouchPoint` 按值进入异步任务，在拥有线程上调用 `msime_client_touch_character`，与同步触点入口逐字相同。布局变了要重新注册几何时，`registeredKeyGeometryID` 在投递这一键之前同步调用 `setKeyGeometry`，它先排空此前已投递的字母，所以几何代次与按键在拥有线程上的先后不变。

回调记下投递时的方案，交付时方案已经变了（九键、全拼、双拼之间切换）、切到英文、输入框换了或经过焦点边界就不画。Shift 的判断依赖画面上是否已有组字：组字中的 Shift 是辅助码，空闲时 Shift 切到英文。字母还没画出来时按 Shift 会被误判为空闲，于是切英文并把字母原样上屏。所以 Shift、符号和 Tab 与空格、删除一样先排空。候选点选沿用画面快照的候选身份，旧画面的身份被拒绝时保留组字并显示诊断。

本轮在模拟器验证了以下用例：全拼、双拼连打时投递立即返回、按序画出整段拼写；首字母还在会话线程上时按空格、删除、收起、宿主编辑和切换中英，组字都已结束，旧回调没有把它画回来；字母还没画出来就按 Shift，双拼进入辅助码，全拼插入分词，组字仍在；iPad 上字母还没画出来就按 Tab，打开候选面板而不是写入制表符；字母还没画出来就按逗号，上屏后旧回调没有把组字画回来；微软双拼的 `;` 经会话线程查询，结果与同步入口一致；五笔、日语的字母仍当场同步画出；双拼带按下点的异步结果与同步触点入口相同；桥接只收规定的网格与字节。本轮没有在真机上做前后对照。0.52 用户报告的 26 键卡顿是否改善、改善多少，要等真机测量。

## Alternatives considered

- 串行DispatchQueue：API简单、便于排序，但会话按操作系统线程绑定，串行不代表固定线程，不采用。
- 只继续同步微优化：改动较小，但多轮真机试验已显示局部收益不足；仍保留已验证的UI复用，不把它当成解除主线程等待的方案。
- 26 键继续同步，只做九键：九键的真机数据不能直接搬到 26 键，同步路径也已经稳定。可是 26 键字母与九键数字走同一个引擎查询和同一套快照绘制，等待的来源相同，而 26 键是更多人用的布局，不采用。
- 把连打的字母攒成一批再交给引擎，跳过中间查询：引擎工作更少，但 C ABI 没有批量字母入口，要新加契约；某个字母的快照还可能带上屏，中间结果不能随意跳过，不采用。
- 丢弃所有较旧结果：能减少绘制，却可能丢失提交；本实现先保留有序交付及控制屏障，不用丢提交换速度。

## Verification

本地`bash scripts/verify-local.sh --quick`、`pnpm run verify-notes`与`git diff --check`通过。

模拟器相关124项（1项跳过）通过，另有51项边界回归通过，覆盖拼写光标、宿主自身编辑回声、成对标点和真实词库会话重建。新增桥接回归阻塞拥有线程后连续投递64426，检查投递立即返回、快照按序交付、紧随删除/提交正确；检查主线程回调、回调内取消的重入，以及旧代次的选词、拼音、以词定字和四种候选管理动作拒绝后保留当前组字。控制器补充回归检查首键后立即空格、删除、收起、宿主编辑回调和切换语言，随后主队列旧回调不能恢复组字。

最终正常Release再次编译、签名校验并安装启动；扩展二进制检查不含临时探针符号，源文件不含探针或临时保亮改动。专用模拟器已关闭并删除。

正常Release真机的系统键盘三轮共12句、117个数字通过，交替空格和首选候选提交，只留下汉字、无残留组字。普通XCTest点按等待空闲，只证明功能链路。

## Consequences

同步屏障不能从会话线程等待自己；完成回调不得持锁调用UIKit，防止重入死锁。不能在未处理首键时误判空闲并维护词库或直接插入空格。后台查询仍消耗CPU，也引入交付调度成本。实测主线程占用明显降低，帧间隔改善，候选完成时间尾部仍有约40–45 ms，不能保证所有按键达到16 ms预算。控制命令仍同步等待此前查询，快速连续按空格或删除时仍可能等待；后续应继续减少引擎及UIKit实际工作量。上面的真机数字只来自九键；26 键全拼和双拼改成异步之后，主线程不再等字母查询，但 Shift、符号和 Tab 现在也要先等此前的字母查完。26 键的实际收益和尾部延迟还没有真机数据。连打时不带上屏的中间快照只画最新一帧，被合并掉的那一帧携带的诊断（`diagnosticText`）不会显示；同步路径会显示它，直到下一键清掉。诊断本来只维持到下一键或几秒，连打中下一键很快就到，影响小，九键改成异步时已经如此，现在 26 键全拼和双拼也一样。

按压动画的后续处理及尚未完成的真机手感验证见[九键反馈直接跟随触摸状态](2026-10-19-ios-nine-key-immediate-press-feedback.md)，不改变本篇的会话线程与有序交付决定。
