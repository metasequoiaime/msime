# Agent Note: 九宫格切分路径按音节频度截断，整句跨路径扣掉词组奖励；九键 1 键组字时分词、右列重输；无拼音读法时给英文词

Status: implemented

## Problem

内测用户录屏反馈 Android 九键「多打几个字就鬼畜，老以为自己打错了」。录屏里的几处都能在引擎里稳定复现：

- `943426943426`（一点一点）首选「洗点一点」，「一点一点删除」整个候选列表里都没有；`7264685487`（然后就s）首选「盘后」，「然后」从列表里消失，用户点了首选，上屏的是「盘后」。
- `9436364782662`（这能算吗）首选「洗噩梦算吗」，`943636478`（这能去）首选「西鄂能去」。
- 打 `77` 想要 QQ，九键一行候选都没有，只能切到全键盘。
- 想清空整串拼音时习惯按右列中间那格，那里是「拆分」，按下去得到的是一个音节分界；清空在长按 ⌫ 上，用户不知道。

前两条是 `crates/engine/src/nine_key.rs` 的两个缺陷叠在一起：

1. `SpellingTable::split_paths` 每个位置只留 48 条切分路径，按「音节少、末音节完整」之后用字典序截断。9 键是 wxyz、7 键是 pqrs，长串里 xi、p 开头的路径把 yi、zhe、r 开头的全部挤掉，正确读法根本没被查询。
2. 每条路径各自交给整句解码，解出的整句行按 `weight` 跨路径比较。整句分是 `log_prob * 1000`，词组边每覆盖一个音节加 `PHRASE_LENGTH_BONUS`（20）。这份奖励在同一串音节里是常数，跨路径比较时就变成「切得越碎、越能凑成词组的读法分越高」。

用仓库的评测集量过九键整句：`sentences-neutral-v1` 九键 top-1 只有 0.050，正确答案出现在列表里的比例（found）只有 0.094；手写的 60 条常用句 top-1 0.300、found 0.350。

## Decision

- **切分路径按音节频度截断。** `SyllablePrior` 在九键第一次查词前用 `QuanpinDictionary::best_weights` 取每个完整音节最常用单字的权重，记成 `ln(weight / 各音节权重之和)`，前缀取以它开头的音节里最高的那个。`split_paths` 的排序变成：音节少、末音节完整、频度之和高，最后才是字典序（只为确定性）。频度只决定留哪 48 条路径，候选本身的先后仍由词库和整句解码决定。
- **整句跨路径比较前每个音节扣一份奖励。** `rank_key` 对 `Generated` 行用 `comparable_weight`：`weight - PHRASE_LENGTH_BONUS * 1000 * 音节数`。同一条路径内所有整句扣的一样多，先后不变；路径之间多切出来的音节得靠词本身的分量取胜。`PHRASE_LENGTH_BONUS` 从 `LatticeOptions::default` 的字面量提成 `lattice::decode` 的公开常量，两处共用。
- **没有任何拼音读法时给英文词。** 拼音候选为空且没有锁定拼音时，`english_candidates` 不再看中英混输开关和最短前缀，`77` 直接给出 QQ。拼音有读法时混输开关照旧说了算。
- **Android 九键：组字时 1 键是「分词」，右列中间是「重输」。** 不组字时 1 键仍是 `@#`、打开符号面板；组字时键面换成「分词」，点按向引擎送 `'`（原「拆分」的功能）。右列中间那格改回「重输」，组字时丢掉整串（`discardComposition`），和搜狗、讯飞九键的位置一致；长按 ⌫ 清空保留。1 键的键面在 `ImeLayoutRows.updateNineKeySymbolKey` 里随 render 更新。

## Alternatives considered

- **路径直接按音节对数概率排序，不再以「音节少」为第一键。** 理由最强的一条是它更像一个真正的音节语言模型，少音节优先是硬规则。实测 60 条整句 top-1 0.217 → 0.200、found 不变，没有收益，还会让部分输入的路径集合大幅变化，所以保留「音节少」为第一键。
- **只扣整句里词组实际拿到的奖励（按 `sentence_words` 里多字词的字数）。** 这是对奖励最「精确」的还原。但单字边的 `ln(w / 1e6)` 和词组边的 `ln(w)` 本来就不在一个量纲上，扣完后词组仍被系统性高估，整句集 top-1 反而从 0.233 掉到 0.150（未挂重排模型时），放弃。
- **每条路径只留前 1～2 个整句，让更多路径挤进 128 行上限。** 怀疑 found 低是候选上限造成的；实测 found 一点没动，说明瓶颈不在上限，放弃。
- **每音节扣 35 而不是 20。** 在 1105 条中立集上与 20 完全相同，60 条手写集多对 1 条（统计分辨率 ±13pp 以内）。20 等于奖励本身，不引入一个调出来的常数，选 20。
- **把右列改回「重输」，拆分只留在长按里。** 拆分在九键上是常用操作（`94'26` 西安），藏进长按会重演「功能存在但没人知道」的问题；放到组字时的 1 键与主流九键一致。

## Verification

锁定资源（`desktop-dictionary.lock.json` 的 dict-v2.0.14 加 `sentence-model.safetensors`）上用 `convert_eval --nine-key` 测，原逻辑跑出的 words 结果与提交前的 `baseline-nine-key.json` 逐字节一致，确认测评环境就是基线的环境：

| 九键集 | 原逻辑 | 现在 |
|---|---|---|
| `quanpin-words-v1` 3000 条 top-1 / top-5 / found | 0.553 / 0.831 / 0.948 | 0.573 / 0.850 / 0.967 |
| 其中 4 音节 top-1 | 0.775 | 0.871 |
| `sentences-v1` 60 条 top-1 / found | 0.300 / 0.350 | 0.367 / 0.417 |
| `sentences-neutral-v1` 1105 条 top-1 / found | 0.050 / 0.094 | 0.112 / 0.203 |

words 集没有任何音节档回退，`baseline-nine-key.json` 随本次更新。单测覆盖：频度截断把字典序截断挤掉的「一点一点」留下来、前缀取最高音节的频度、多一个音节的整句不再靠奖励胜出、`77` 在混输关闭时给出 QQ；Android `NineKeyLayoutSmoke` 钉住 1 键在组字与否、拼音与数字键面下的键面和行为。

## Consequences

- 九键长句的首选明显变正常，正确答案进入列表的比例翻倍。九键第一次查词多一次约 410 个音节的批量查询，之后缓存在会话里。
- 整句九键仍远不如全键盘：found 只有两成到四成。剩下的问题不在九键，而在整句解码本身——同一串拼音 wo'jin'tian'qu'shang'ban 交给解码器得到的是「我今天趣上班」（我今 + 天趣），全键盘上同样会出；正确路径已经排在 48 条之首。要再往上走得改词网格打分，不是九键截断。
- 用户关掉了中英混输，九键打出拼不成音节的数字时仍会看到英文词；这只在列表本来为空时发生。
- Android 九键右列的「拆分」没有了，习惯了它的用户要改用组字时的 1 键「分词」。iOS、HarmonyOS 九键这次没改。
