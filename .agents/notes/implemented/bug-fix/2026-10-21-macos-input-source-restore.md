# Agent Note: macOS 恢复输入源时避免重复选择模式

Status: implemented

## Problem

#8993 的输入源通知与 IMK 日志表明，从强制 ASCII 的应用返回后，系统正在恢复水杉输入源时，`activateServer:` 同步调用 `selectInputMode:`，随后输入源又变成 U.S.。控制器的模式记录在离开输入法时已清空，因此「尚未收到模式报告」被当作「系统没有选中目标模式」，即使目标正由系统恢复，也会重复请求。

只取消全部系统模式同步会让 Shift、菜单、悬浮工具栏以及应用中英文记忆失去原有行为。需要区分系统正在交接焦点和用户主动要求切模式。

## Decision

激活时把系统模式同步延后一轮主队列，并在执行时确认仍是同一活动客户端、同一焦点控制器和同一次激活。实际选中的输入源由 TIS 重新读取；仍是外部 ASCII 输入源或无法识别时，不发送自动选择请求。已经恢复到本 bundle 模式时先以它校准模式记录，再按当前应用的真实状态同步；目标已经选中时不调用 `selectInputMode:`。

显式中英文切换、方案选择和系统模式报告继续走现有同步路径，并使尚未执行的激活校准失效；不能用滞后的 TIS 状态覆盖刚发出的选择。不用定时重试和固定延迟。菜单栏状态项仍反映控制器的真实状态，不等待输入源切换。测试替换读取系统输入源的入口，不读取或修改开发者的真实输入源。

## Historical audit

- [macOS 菜单栏模式状态项](../../implemented/feature/2026-10-12-macos-input-mode-status-item.md)：部分重叠，保留状态项显示真实状态与不可用模式回退的决定；只改变激活时自动同步的时序。
- 首次选择按需模式、输入源登记与安装相关笔记管理的是可用模式集合，未处理系统恢复中的重复选择，不由本项取代。

## Alternatives considered

- 彻底删除 `selectInputMode:`：改动最少，也消除了激活期间的重复请求；但现有的显式中英文和方案切换无法再同步系统菜单栏，不采用。
- 只在激活时同步读取 TIS：可发现已经选中的目标，从而跳过相同请求；但报告里 `Activate Server` 先于输入源通知，TIS 此时仍可能显示 U.S.，同步读取不能证明交接已完成。
- 只把同步放进下一轮主队列：避开 IMK 激活调用栈，状态改动小；但排队期间可能已经换客户端或离开水杉，需要在执行时复核焦点和实际输入源，不能无条件执行。

## Testing

`InputModeIdentifiersTest.mm` 用合成可用模式覆盖实际模式校准、相同目标无重复请求、外部或未知模式拒绝、显式切换仍可用，以及正在选择时不覆盖记录。`ShortcutTest.mm` 的 `--input-source-restore` 使用受控输入源与主队列屏障，覆盖延后读取、客户端和焦点变化、激活代次合并、最新目标与显式同步优先；测试不切换开发者的真实输入源。主队列等待复用已有 `DrainMainQueue`，先结算前序用例遗留的窗口布局，再等待队列屏障，避免把 AppKit 布局耗时误算成输入源调度超时。

两份测试的严格 Clang 语法检查、原生 `--input-source-restore`、`input-mode-identifiers`、完整 `shortcut` 与 `shortcut-translations` 均通过；完整 macOS 宿主编译及 `scripts/verify-local.sh --quick` 通过，笔记校验与 diff 检查通过。远端复用已有构建目录，迁移后的 Tauri Android 权限缓存与 Apple 桥接 CMake 缓存清理后重建；未新建完整构建树。测试目前直接进入调度方法，不代表真实系统调用 `activateServer:` 或 Kindle 窗口切换验收。

## Consequences

系统自动恢复到目标模式时无需再次选择，避免在 IMK 激活调用栈中干扰恢复过程；应用记忆与显式中英文切换继续使用原有规则。状态项立即显示真实目标，系统模式校准需等一轮主队列。排队执行前有新的显式同步时，旧校准失效，避免滞后的 TIS 状态造成重复请求。

TIS 在不同系统版本上可能晚于一轮主队列才反映恢复状态，此时保守地跳过自动选择，后续显式操作和偏好刷新继续沿用现有路径。异步回调重新读取当前目标，不把上一个应用的目标带给下一个应用。真实 Kindle 场景仍需装机与窗口切换验收，合成记录只能证明请求时序，不能单独证明操作系统不再退回 ASCII。
