# Agent Note: 安卓账号译文与候选同一帧出现

Status: implemented

## Problem

开着「水杉账号」候选翻译时，候选下面的译文行每换一代都晚一步，停顿重排时还会先消失再出现：

- 共享层每次重解都清掉候选的译文，新的一代要由宿主重新交一遍（[候选释义和读音与候选同一帧出现](2026-11-22-android-candidate-glosses-same-frame.md) 之后，离线释义已经当场交回）。
- 账号译文的缓存本来按词存着，但每一代都先核对账号绑定才肯用：`verifyCandidateTranslationBinding` 在 worker 上跨进程读一次 `SyncSignals.binding`，再排回主线程、在主线程上又跨进程读一次，两次一致才把缓存交给共享层并重画。候选先画成没有译文的样子，过一跳才补上；延后模型的手机上每次停顿重排都把它们清掉再补回来。
- 目标语言不是英语、又没装这种语言的离线词典时，译文行先显示英文离线释义（退回画英文），再换成目标语言的在线译文，停顿重排时又换回英文。
- 每张新列表都在主线程上做一次跨进程读取。

用户自己的翻译服务没有账号绑定，缓存一直是当场交回的，但做法是在 `render` 里再嵌套一次 `render`，整套候选区画两遍。

## Decision

账号绑定是账号级的事实，登录、退出、换号时才变，不随候选的代次变；改成后台核对，核对过的缓存与候选同一帧画出。

- **`CandidateTranslationBinding` 持有「缓存现在能不能用」。** 读绑定只在 worker 上做（跨进程调用），其余状态只在主线程上：
  - 键盘显示、换输入框、会话重建、进程刚起来时还没核对过（`reset`）：这时不画缓存里的账号译文，也不发请求；核对完成后重画一次，这一代的缓存译文和请求接上。代价是每次显示键盘后第一张列表的账号译文晚一跳。
  - 核对过之后，每张新列表照常用缓存；距上次核对超过 10 秒就在后台再核对一次，期间仍用缓存。
  - 核对发现账号变了：store 换绑定（同时清空），画面上的账号译文随之去掉；provider 不可达时证明不了缓存属于谁，解绑、不用缓存，下一张列表再核对。
  - worker 可能悄悄丢掉排着的核对（`DiscardOldestPolicy`），核对一秒没回音就重发。
- **整页请求自己核对绑定。** `CandidateTranslationStore.fence`：请求在 worker 上发出前、回答到达后各读一次绑定，与缓存绑定的那个比对；对不上就不发、不收，放开签名，并在主线程上让绑定马上重新核对。所以换号前后不会替旧账号发请求，路上换号时回答也不进旧账号的缓存，与原来「发请求前和回答到达时各读一次」相同，只是挪到 worker 上。
- **缓存的译文在画候选条之前当场交给共享层。** `render` 在画候选条之前调 `scheduleCandidateTranslations` 和 `scheduleUserCandidateTranslations`：缓存可用时在这里合并离线释义和在线译文、交给共享层、换上视图，不再嵌套 `render`。只有没见过的词等网络。新译文到达时 store 的回调照旧换上视图并重画一次。
- 卡片（`ImeGlossCard`）读账号缓存的核对不变，它只读 `boundTo`，绑定的建立和改写归整页。

## Alternatives considered

- **每一代照旧核对，只是把主线程上那次读取去掉。** 最接近原来的保证，但核对本身就是那一跳：译文行仍晚一步，停顿重排仍会让它们消失再出现。
- **完全不核对，只靠请求时的核对。** 最简单，Windows 和 iOS 键盘扩展也只在 store 一层隔离；但别的进程里换号之后，键盘里还开着的缓存会一直画上一个账号查过的词，直到下一次请求失败。保留后台核对，把这个窗口限在 10 秒加一跳，键盘每次显示都从头核对。
- **主进程在绑定变化时通知键盘进程（provider `notifyChange` 加 `ContentObserver`）。** 能把窗口缩到一跳以内，但要改账号那一侧的代码，另行处理。
- **核对放到单独的线程上。** 不会被整页请求挤掉，但多一个常驻线程；核对现在很少发生，超时重发已经够用。

## Consequences

- 账号译文和候选同一帧出现；停顿重排不再让它们消失再出现；没装目标语言离线词典时不再先显示英文再换成目标语言。用户服务的译文同样当场交回，不再整套重画两遍。
- 每张新列表的主线程上少一次跨进程读取。
- 安全窗口：别的进程里换号之后、键盘还开着时，上一个账号缓存里的译文最多再显示 10 秒加一跳（原来是一张列表）。泄露的只是「上一个账号最近查过这个词」：译文本身是正在显示的候选的释义，缓存只在内存里、最多 256 条。请求和回答仍然按当前账号核对，不会替旧账号发请求，也不会把新账号的回答记进旧账号的缓存。
- 每次显示键盘后的第一张列表，账号译文晚一跳出现（核对完成之前不画）。
- 验证：`CandidateTranslationBindingSmoke`（首次核对、有效期内不再读、过期后台再核对、换号清空并通知、reset 作废路上的核对、provider 不可达、核对被丢掉后重发、worker 拒收后重试、`holds` 只认当前账号）；`CandidateTranslationStoreSmoke` 新增请求前绑定对不上不发、回答到达时对不上不收、两次都对得上才进缓存。模拟器上没有账号，用本地探针伪造一个已绑定的 store 和合成的译文，看译文是否与候选同一帧出现；真实账号和网络都没有跑到。
