# Agent Note: 九键每次刷新只查前 24 条切分

Status: implemented

## Problem

iPhone XR（A12）上九键打字卡：真机打点显示每个数字的引擎耗时中位数约 39 ms，词库连接打开内存映射后约 31 ms。`NineKeySession::refresh` 每次把切分搜索留下的路径（至多 `PATH_LIMIT` 条）全部拿去查词库：每条都要查一遍候选、按备选切分组句、解码整句，一次刷新的耗时大致随条数增长。在 Studio 上采样，九键刷新约 69% 的时间花在逐条路径的 `query_filtered_rows` 里。

## Decision

新增 `QUERY_PATH_LIMIT`（24），`refresh` 调 `split_paths_with_scratch` 时以它为输出上限。切分搜索本身每个位置仍留 `PATH_LIMIT`（48）条，只截最后物化、拿去查询的路径；种子路径仍在这之后补进来。14 键与九键双拼走同一段刷新，一并生效。

对照实验（同一份词库与评测集）：

| 查询条数 | `ninekey_latency` 指令数 | 九键常用词 首选 / 前五 / 前九 | 九键长句 首选 / 前五 / 前九 |
| --- | --- | --- | --- |
| 48 | 579 亿 | 0.575 / 0.852 / 0.907 | 0.617 / 0.654 / 0.716 |
| 32 | 499 亿 | 0.572 / 0.848 / 0.903 | 0.617 / 0.642 / 0.704 |
| 24 | 400 亿 | 0.571 / 0.847 / 0.902 | 0.617 / 0.642 / 0.704 |
| 16 | 333 亿 | 0.566 / 0.843 / 0.895 | 0.593 / 0.630 / 0.691 |

指令数含启动时加载词库与模型的固定开销，按数字计的降幅更大。把搜索宽度也一起降到 24 时，各组评测数字和指令数与只截查询完全相同，所以只改查询这一步，搜索宽度不动。

`convert_eval` 基线随之更新：九键常用词首选 57.5% → 57.1%、前五 85.2% → 84.7%；九键长句首选不变、前五 65.4% → 64.2%；14 键常用词首选 66.0% → 65.8%；14 键长句总体指标不变。评测不覆盖先锁定音节的输入，另用真实词库对 1500 个多音节词各试一遍「打完数字、在左列锁定首音节」：正确词进前九的从 1448 个变为 1446 个，不锁定时从 1388 个变为 1379 个。

## Alternatives considered

- **32 条**：工作量只少约 14%，常用词与长句的损失和 24 条几乎相同，提速只有一半。
- **16 条**：工作量少约 42%，但长句首选开始掉（0.617 → 0.593，81 条里少 2 条）。
- **保持 48 条，只做不改变结果的优化**：词库映射和整句解码缓存已经做了，剩下的耗时分散在候选整页复制、解码和 SQLite 上，没有一项能单独把 XR 拉回一帧以内。
- **九键数字层统一词网格**（[提案](../../proposed/feature/2026-10-09-nine-key-digit-lattice.md)）：把所有切分放进一张以数字为位置的词网格一次解码，质量和耗时都能从结构上解决，是长期方向；改动面大，不是这次的范围。本篇把查询条数降下来不妨碍它。
- **由宿主按设备快慢决定条数**：只在慢机上降，快机保持 48。要新增跨平台的设置或能力字段，各宿主还得判断设备快慢，同一份输入在不同设备上候选不同，测试与评测都要分档；质量损失本来就很小，不值得这层复杂度。

## Consequences

收益：九键、14 键每次刷新查询的路径减半，整轮工作量少约三成，慢设备获益最大。

代价：候选质量有可见但很小的下降，数字见上；九键双拼没有评测集，没有量化。有种子的长串原本按 `SEEDED_PATH_LIMIT`（24）截频度切分，与本上限相等，那一步不再多截，见 [整句种子](../feature/2026-10-10-nine-key-sentence-seeds.md)。

测试：`dominated_projection_tests` 与 `filter_projection_tests` 的冻结刷新改用同一个查询上限，它们只对照各自的投影优化；按 48 条对照时，测试词库的音节频度几乎为零，路径排序退化为字典序，锁定 `ni` 后 `6342` 的 `men'hao` 排在 24 条之外，「你们好」不再出现，真实词库上没有这个现象（上面的锁定实验）。

`host-api` 的九键双拼换表用例也受精简夹具影响：原夹具只有词组行，米旮旯 2 的 `6442` 对应的 `ni'hao` 在无单字频度时按字典序落在 24 条之外。单变量对照中，恢复 48 条查询时原断言通过；保持 24 条、只为夹具补上合成的 `ni`、`hao` 单字频度时也通过。该用例在首次按键前为两份夹具词库补齐频度，作用范围限于这条换表测试，并检查更新成功且立即应用、同一个词的候选及读音。查询预算沿用 24 条。

错表对照临时强制重建会话继续使用原表，候选断言得到合成单字「甲」而非预期词组，按预期失败；撤回对照改动后，`host-api` 全集 934 项通过、5 项忽略。夹具中的合成单字只为切分提供频度，词组候选断言仍能检出换表错误。
