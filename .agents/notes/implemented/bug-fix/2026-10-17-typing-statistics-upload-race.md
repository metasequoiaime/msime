# Agent Note: 关闭上传时串行化云端操作

Status: implemented

## Problem

桌面设置应用的自动上传和关闭开关分别在独立的 `spawn_blocking` 任务里运行。自动上传先读本地状态再发送 `PUT /v1/users/me/typing-statistics`，关闭开关先写本地关闭状态再发送 `DELETE`。本地文件锁只覆盖各自的读写，网络请求之间没有顺序约束；如果 `DELETE` 先完成、已经开始的 `PUT` 后完成，用户关闭开关后云端副本会被重新写回。

## Decision

`TypingStatisticsStore` 为每个共享该 store 的克隆持有一把进程内上传操作锁。桌面设置应用在自动上传和开关变更命令中，从读取本地上传状态开始一直持有这把锁，直到 `PUT` 或 `DELETE` 和后续本地状态写回完成。统计记数与普通统计页读写不取得这把锁，仍由原来的文件锁保护，因此网络请求不会阻塞输入法记数。

## Alternatives considered

- **发送完成后再补一次删除。** 可以覆盖一部分交错顺序，但补删请求本身仍可能早于原来的 `DELETE` 完成，无法建立严格的最后写入顺序。
- **只在状态文件里增加版本号。** 能避免过期的上传时间写回，却不能阻止已经发出的 `PUT` 在删除之后改写云端数据。
- **把网络请求放进统计文件锁。** 能串行化，但会让输入法在网络故障或慢请求期间无法记数和读统计，违反统计本地路径的响应性边界。

## Consequences

- 同一桌面进程内的上传和删除按调用开始顺序完成，关闭开关后不会被并发上传重新写回。
- 上传请求持续期间，另一个上传或删除命令会等待；统计记录和统计页读取不等待这把锁。
- 这把锁是进程内契约；不同进程不共享 Tauri 命令状态，而每个设置应用进程只允许自己的命令发送账号云端请求。跨进程的本地统计文件仍使用既有文件锁。
- 回归测试验证同一 store 的克隆不能同时进入两个云端操作边界。
