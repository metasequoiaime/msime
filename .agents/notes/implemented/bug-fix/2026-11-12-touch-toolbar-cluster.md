# Agent Note: Android 与鸿蒙空闲工具栏图标聚拢到右侧

Status: implemented

## Problem

iOS 的空闲工具栏已经改成品牌 Logo 在左、其余图标聚拢靠右（[iOS 工具栏图标聚拢到右侧](2026-11-07-ios-toolbar-cluster.md)）。Android 仍把中间的工具各带一份权重等分滚动区，鸿蒙把标志、工具和收起一共几格等分整行：可见工具少的时候图标被拉得很散，两个工具时相邻图标隔着半行，和 iOS 并排看是两种工具栏。维护者对着三端截图要求 Android 也按 iOS 的排法。

已检索 proposed、implemented、rejected 里的工具栏、`shortcutBar`、`toolbarRow` 和等分。[Android 空闲工具栏独立尺寸](../feature/2026-10-26-android-toolbar-size.md) 和 [Android 独立工具栏尺寸切换抖动](2026-11-08-android-toolbar-size-jitter.md) 持有行高、按钮缩放和最小点击区，本篇不改它们，只在缩放时多算一个收起键前的间距；[Android 工具栏排序](../feature/2026-10-15-android-toolbar-order.md) 持有顺序和长按入口，本篇只把工具在滚动区里的起始下标从 1 改成 2；[鸿蒙手机工具栏可选工具](../feature/2026-10-17-harmony-toolbar-tools.md) 里「关掉的工具不占格，剩下的格子等宽排开」这一句由本篇取代，其余照旧。

## Decision

三端用同一组数值：工具的格子宽 40，相邻两格间隔 8，行两侧内边距 2。出处是 iOS 的 `KeyboardToolbarButton.padSide = 40`（`KeyboardToolbarButton.swift:8`）、`shortcutBar.spacing = 8`（`KeyboardViewController.swift:2900`）和工具栏左右各 2 的约束（`KeyboardViewController.swift:2948`–`2949`）。Android 和鸿蒙原来的格宽、内边距就是 40 和 2，这次新增的只有 8 的间距和「靠行尾」。间距不随可见工具的数量变化，也不随工具栏尺寸缩放。

### Android

`ImeToolbar.installShortcutBar` 里滚动区的子视图依次是：算式结果胶囊、一块权重为 1 的可伸缩空白、按用户顺序排的工具。工具不再带权重，宽度固定为一格，每个工具的起始边留一个间距（`ToolbarClusterPolicy.CELL_DP`、`GAP_DP`）。

靠行尾和溢出滚动靠同一块空白衔接，不需要切换状态的代码：`HorizontalScrollView` 开着 `fillViewport`，内容比视口窄时被拉到视口宽，多出来的宽度全部落在空白上，工具贴着行尾；内容比视口宽时空白宽度是 0，内容从行首排起，滚动位置 0 就是结果胶囊和用户排在最前面的工具。所以放不下时初始位置露出的是最前面的工具，不是最后面的。

结果胶囊仍是滚动区的第一个子视图，紧挨品牌键；工具靠行尾时它和工具之间隔着那块空白。长空格样式的「符」仍在品牌键右边、滚动区之外。两端的品牌键、「符」和收起键保持 44 dp 的点击区。收起键比工具的格子宽 4 dp，图标各自居中，所以它前面的间距是 `ToolbarClusterPolicy.edgeGap`：8 减去多出来的一半，100% 时是 6 dp，最后一个工具到收起键的图标中心距仍是 48 dp；工具栏尺寸放大时在 `applyShortcutSize` 里跟着重算（150% 时 5 dp）。

`ToolbarClusterPolicy` 里另有 `leadingSpace`、`scrollRange`、`toolOffset` 三个函数，把上面这套排法写成算式。键盘本身不调用它们，布局由 `LinearLayout` 完成；它们是设备套件核对真实布局用的规格，同时由 JVM 冒烟钉住规则本身。

### 鸿蒙

`KeyboardView.toolbarRow` 分成三段：标志（长空格样式时加「符」）一组在行首，`Blank` 把后面推到行尾，工具和收起一组在行尾，组内 `space` 是间距，每格宽度固定。

这一行不能滚动。手机上五个工具全开再加长空格样式的「符」是 8 格，需要 376 vp，360 vp 宽的手机放不下，浮动键盘更窄。`TouchToolbarPolicy.cluster` 按这一行的实际宽度给出格宽和间距：放得下用 40 和 8；放不下先把间距均匀收窄到 0，还放不下再把格子均匀收窄，也就是退回原来等分整行的样子，收起键不会被挤出去。宽度还没量出来时按设计尺寸。

## Alternatives considered

- **格子做成 48、不留间距。** 图标中心距同样是 48，而且没有点了没反应的 8 dp 空隙，点击区比 40 的格子大，这是它最强的理由。放弃是因为 40 是三端共用的格宽：激活底块、`ToolbarSizePolicy.buttonWidthDp(40, …)` 的缩放和最小点击宽度都以它为准，iOS 也是 40 的格子加 8 的间距；改成 48 等于 Android 单独换一套基准，窄屏上每个工具多占 8 dp 还会更早开始滚动。
- **放不下时也保持靠右，初始滚动到末尾。** 这样两种状态看起来都是「贴着收起键」，视觉上最连贯。放弃是因为被滚出视口的正是用户特意排在最前面的工具，自定义顺序就失去了意义；RTL 下还要自己换算初始偏移。
- **算式结果胶囊跟着工具一起靠右。** 滚动区就不需要中间的空白，内容整体右对齐即可。放弃是因为胶囊出现在品牌键右边是既有行为，结果出现时不应该把工具再往左推一截，也不应该换位置。
- **按视口宽度自己算空白的宽度再设进去。** 位置完全由纯函数决定，JVM 就能测到真实行为。放弃是因为要在布局之后再改布局，多一轮测量，视口宽度变化时会先画一帧旧位置；带权重的空白在同一轮测量里就得到同样的结果。
- **收起键前也留整 8 dp。** 写法最简单。放弃是因为收起键是 44 dp，照搬 8 dp 时最后一个图标到收起箭头是 50 dp，比其他图标之间宽 2 dp，一排图标里只有最后一格不齐。
- **鸿蒙给工具套一个横向 `Scroll`。** 和 Android 完全一致，放不下时也不用收窄。放弃是因为鸿蒙最多 8 格，只差二十来 vp，为它加滚动容器会让这一行多一个手势竞争对象（长按进设置、按压缩放都在这些按钮上），收窄间距后肉眼几乎看不出差别。
- **继续等分。** 不改代码，工具少时每格的可点范围也更大。这正是被指出的问题，放弃。

## Consequences

- 三端空闲工具栏是同一种排法：Logo 在左，其余图标以 48 的中心距贴着右边，增减工具只改变这一串的长度。
- Android 工具的点击区从「不小于 40 dp、随等分变宽」变成固定 40 dp，工具之间有 8 dp 不响应点按的空隙，与 iOS 相同；最小点击区没有变小。可见工具超过视口时比原来早一点开始滚动（每格多占 6 dp）。
- Android 滚动区多了一个不可见、不进无障碍树的子视图，工具的子视图下标从 1 起变成从 2 起（`ToolbarClusterPolicy.LEADING_CHILDREN`）；读屏顺序、排序、显示隐藏、尺寸缩放都不变。
- 鸿蒙放不下时间距小于 8，极窄时格子小于 40，这两种情况下与另外两端不完全一致。
- 皮肤面板瓷砖里的缩略工具栏（`KeyboardSkinPreview`，七列等分）没有改，它是设计稿 MiniKb 的示意图，不随用户的工具开关变化。

## Verification

- `ToolbarClusterPolicySmoke`（JVM）：格宽和间距的数值、放得下时贴行尾且中心距与数量无关、正好放下与差 1 的分界、放不下时第一个工具在滚动位置 0 可见且能滚到最后一个、结果胶囊在前、收起键前的间距在 100% 和 150% 下保持中心距。
- `ToolbarEdgesDeviceSmoke`（设备）：在 240、320、600 dp 宽、有无结果胶囊的八种组合下，逐个核对真实布局里每个工具的位置等于 `ToolbarClusterPolicy.toolOffset`，格宽恰好一格，放得下时最后一个工具贴滚动区行尾，放不下时第一个工具在滚动起点可见；只剩一个工具时它是一格宽、贴行尾；排序后工具从第 2 个子视图起。原来钉着等分的三处断言（工具不窄于 40 dp、工具从第 1 个子视图起、单个工具占满滚动区）改成了上面这些。
- 在 API 35 模拟器上用 0.7.4 发布包的原生库和资源加这次的 Java 打包，`ToolbarEdgesDeviceSmoke` 和 `ToolbarScrollDeviceSmoke` 通过；改前改后各截了默认四个工具和十个工具溢出两种状态。
- `kb-view.test.ts`：`TouchToolbarPolicy.cluster` 在 2 到 7 格时都是 40 和 8、8 格放不下时只收间距且正好铺满、更窄时格子等分、宽度未量出时用设计尺寸。
- 鸿蒙的 `KeyboardView.ets` 改动没有经过 `hvigorw assembleHap` 编译，也没有上设备看过，合并前需要补。
