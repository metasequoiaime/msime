# Agent Note: Linux 在线缓存使用进程内凭据指纹

Status: implemented

## Problem

Linux 在线 provider 的自定义翻译缓存用 API 密钥的普通 SHA-256 摘要区分凭据，触发发布 PR #8835 的 `py/weak-sensitive-data-hashing` 检查。小牛、腾讯翻译和 AI 候选缓存也使用相同的无密钥摘要方式；同一凭据在不同进程中的标识固定。

## Decision

模块加载时生成一个 32 字节随机挑战，四种凭据缓存标识统一用 API 凭据作为 HMAC-SHA-256 密钥，对该挑战签名。缓存本来只存于进程内，签名只需在同一进程内稳定，不需要持久化挑战、跨进程比较或迁移旧缓存。凭据规范化仍发生在计算标识之前，凭据轮换仍隔离缓存。

提示词、上下文摘要以及远端服务签名协议不变。正缓存、八分钟负缓存和 4096 项容量也保持原有语义。

密钥包含四字节凭据长度前缀，避免 HMAC 的短密钥补零把空串与一个 NUL 等不同凭据映射为同一签名；长密钥仍由标准库处理。

## Alternatives considered

- **保留普通 SHA-256**：实现简单，API 密钥通常也具有较高熵；但固定指纹允许跨进程关联，不需要为了内存缓存保留这种性质，也未解决扫描警报。
- **使用密码 KDF**：对低熵密码验证器能增加离线猜测成本；这里不存储密码验证器，把高成本计算放入候选查询热路径没有必要。
- **忽略告警**：可以解释缓存用途而不增加算法状态；但进程随机挑战能以小幅改动收窄指纹作用域，因此直接改进缓存标识。
- **随机密钥对凭据消息做 HMAC**：同样有进程隔离和低计算成本，但 CodeQL 仍把消息视为需要昂贵散列的密码。API 凭据本身承担密钥职责，因此使用凭据对进程随机挑战签名，明确区分 HMAC 密钥与要散列的消息，不修改扫描配置。

## Verification

缓存回归覆盖规范化后复用、凭据轮换隔离、同一模块生命周期内稳定以及独立模块生命周期之间隔离。新增翻译回归在旧实现下因缓存键等于普通摘要而失败。既有小牛、腾讯和 AI 用例继续检查请求与缓存行为。

同文件的请求长度回归仍把 `online` 归入 16 KiB，已与现有 128 KiB 上限不符；未修改的基线也能复现失败。测试分别覆盖在线请求 128 KiB、AI 测试 32 KiB及其他请求 16 KiB 的边界，不调整实现。

Linux Python 3.12 容器内的八个相关测试文件、72 项用例通过，包含真实 socket/HTTP 的配置规范化与凭据轮换测试。macOS 直接运行该 socket 用例不具备 Linux `SO_PEERCRED`，因此以 Linux 容器结果为准。

## Consequences

缓存键不包含明文凭据，也不再使用可跨进程关联的普通摘要；每次进程启动增加一次随机挑战生成。这不是低熵密码验证器，也不保护已经泄露的整个进程内存，发送请求所需的凭据仍在当前请求配置中。
