# Agent Note: 自动候选保留玻璃实例而非反馈父窗口外观

Status: implemented

## Problem

macOS 亮色系统、暗色应用中的候选玻璃可以在显示后自动变暗。逐键重建 `MSIMECandidateChromeView` 同时销毁玻璃及其自适应状态，下一次显示又从系统外观开始。把最近观察到的玻璃明暗写回父窗口后，用户实测每次按键亮暗交替；该方案改变了系统判断材质时的输入，不能当作稳定的外观记忆。

## Decision

自动系统主题、同一客户端、原生玻璃仍启用时，普通候选与展开网格复用原卡片、玻璃及内容容器，只移除旧候选控件并创建新控件。窗口已经持有该卡片时不再重新设置 `contentView`。普通收起保留系统主题没有退场动画的原卡片，再显示时继续使用它。

父窗口的 `appearance` 只接受显式主题或客户端已有颜色；值未变化时不重复赋值，不把玻璃内容的外观写回父窗口。内容外观回调仅刷新候选配色，系统仍能根据背后的窗口调整玻璃。旧候选按钮必须离开当前内容容器，原有点击身份与代次校验保持不变。

手动主题、皮肤包、canvas、关闭玻璃或切换客户端仍走原有重建路径，不把上一客户端的玻璃带到另一个客户端。不存在新的偏好、落盘缓存、应用名称猜测或文档读取。

## Historical audit

- [系统候选液态玻璃](../feature/2026-10-19-macos-candidate-liquid-glass.md)：部分取代其中把玻璃外观写回父窗口的尝试；原生材质启用条件、输入区颜色推断与文字对比度保留。
- [玻璃内容归属](2026-10-19-macos-glass-content-containment.md)：部分重叠，仍将实际控件放在玻璃的 `contentView` 内。
- [候选显隐动效](../feature/2026-10-16-macos-candidate-declared-motion.md)：部分重叠，皮肤退场与动画路径不变；复用只限未覆盖皮肤的自动系统主题。

## Alternatives considered

- **缓存玻璃明暗并写回窗口**：下一帧可以直接按上次观察值初始化，改动也少；但父窗口外观本身参与系统材质判断，用户已观察到逐键亮暗交替，因此移除反馈路径。
- **只缓存文字配色，仍逐键新建玻璃**：不会改变父窗口，但新玻璃依然丢失已适应背景的状态，不能消除材质每次重新调整的闪烁。

## Verification

回归用例覆盖自动系统主题下普通候选、展开网格、收起后再次显示、连续四次完整重建：外层窗口保持浅色，玻璃和内容容器身份稳定，旧候选按钮移除，文字继续跟随模拟的系统内容外观；另覆盖手动主题与客户端切换不复用旧卡片。审查时运行本地 quick 门禁、候选 item/row 布局两项及完整原生快捷键套件并通过；真实玻璃材质的视觉效果仍需在系统输入场景中手动验收。

颜色刷新期间，玻璃布局可能同步重入内容外观回调。控制器将重入请求标记为待刷新，在当前一轮结束后重新读取内容区外观，避免外层旧的浅色配色覆盖内层新的深色配色。原生快捷键套件的系统主题明暗循环在修复前稳定复现选中底色错误，修复后继续作为回归入口。

## Consequences

保留系统自己维护的材质状态，避免在按键路径反复创建玻璃，也取消自适应明暗的父子反馈。自动系统主题不再以卡片对象身份区分页面，因此旧按钮拒绝依赖按钮脱离当前内容容器，不能只检查外层卡片身份。首次进入全新客户端仍需要系统判断一次背景，构建成功不能代替真实输入验收。
