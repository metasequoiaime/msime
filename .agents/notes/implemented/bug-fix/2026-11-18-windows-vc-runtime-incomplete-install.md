# Agent Note: Windows 安装器诊断不完整的 VC++ 运行库

Status: implemented

## Problem

Issue [#11561](https://github.com/metasequoiaime/msime/issues/11561) 中，Windows 11 用户安装 Visual C++ v14.52.37029 后仍被水杉安装器拒绝。pve9 的 Windows 复验显示，VC++ 注册表项在 64 位和 WOW6432Node 中都登记为 `14.52.37029.00`，但 `vcruntime140_1.dll` 缺失。水杉发布的 Server、Watchdog、准备程序和 `fmt.dll` 都实际导入 `VCRUNTIME140_1.dll`，所以这个系统组件确实没有修好；只看注册表或允许跳过检查会把安装时错误变成宿主进程启动崩溃。

已有的[安装前拒绝过旧 VC 运行库决定](2026-11-09-windows-vc-runtime-preflight.md)规定安装器读取原生 `System32` 文件，并在三个 DLL 任一缺失或过旧时阻止安装。本次缺口是提示只说“缺少或过旧”，没有告诉用户是哪一个文件坏了，也没有把修复动作直接指向微软安装包。

## Decision

安装器继续以 `msvcp140.dll`、`vcruntime140.dll` 和 `vcruntime140_1.dll` 三个原生文件的实际版本作为唯一放行条件，不增加“忽略依赖”选项。诊断函数逐个返回缺失、无法读取版本、实际版本或低于 `14.51.36244.0` 的状态；日志和交互提示使用同一组文件结果，因此注册表中的“已安装”登记不会掩盖文件组不完整。

VC++ 缺失或不完整时，交互提示同时给出“已安装的应用 → Visual C++ → 修改 → 修复”的操作，以及微软官方 x64 安装包直链。安装器仍不代替用户静默安装共享系统组件；完成修复后需要重新运行安装包。WebView2 的可选继续策略保持不变。

## Verification

- `scripts/test-installer-prerequisites.py` 通过，确认原生文件检查、三个 DLL 名称、逐文件诊断和直接修复链接仍在安装前路径中。
- 现有 `platforms/windows/installer/tests/vc-runtime-native.ps1` 的探针覆盖缺失文件、无版本文件、版本边界和 Inno 6/7 的原生目录选择；本次未改变其版本判定逻辑。
- pve9 的 Windows 复验记录了注册表版本与三个文件测试不一致的现场；官方 `vc_redist.x64.exe` 包含 `vcruntime140_1.dll`，修复指引因此指向该安装包而不是放宽检查。

## Alternatives considered

- **只信注册表并继续安装**：最符合报告者对“已安装”的直觉，但 pve9 已证明登记可以和文件组不一致，会重新引入 #11126 的宿主崩溃风险，因此不采用。
- **允许跳过 VC 检查**：能让安装器继续，但发布程序仍会导入缺失 DLL，用户得到的是安装成功后无法启动的坏安装，因此不采用。
- **把 VC++ 安装包内置到水杉安装包并自动修复**：可以减少手工步骤，但会扩大签名、载荷和共享组件更新责任；本次先用官方直链和明确修复路径解决诊断缺口，保留系统级依赖边界。

## Consequences

用户能直接看到具体损坏的 DLL，并按 Windows 的修复入口处理；安装器不会把注册表假象当成可用运行库。缺点是修复共享组件后仍需重新启动水杉安装包，且没有网络或权限时仍需管理员处理。严格文件检查和 `vcruntime140_1.dll` 依赖保持不变，避免用“能安装”换来运行时崩溃。
