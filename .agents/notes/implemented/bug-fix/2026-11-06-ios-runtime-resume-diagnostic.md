# Agent Note: iOS 键盘恢复失败保留运行时诊断

Status: implemented

## Problem

键盘控制器从收起状态重新出现时，`MetasequoiaInputSessionBridge` 会先准备选项，再在 `resumeDictionarySession()` 中创建带词库租约的会话。创建失败时句柄保持为 `0`，但恢复方法没有把失败原因写入 `initializationDiagnostic`。后续按键经过 `dispatch` 时只能看到空句柄，于是把真实的词库锁、资源或会话错误显示成「输入运行时尚未准备完成」。这让用户每次都只能看到泛化提示，也遮住了设备上能帮助定位的原因。

现有的会话生命周期约束见 [iOS 键盘只在显示期间持有会话](./2026-11-02-ios-keyboard-session-only-while-shown.md)，本次修复只补齐该生命周期下的失败诊断，不改变收起时释放词库锁的决定。

## Decision

`resumeDictionarySession()` 在创建会话失败时保存「输入运行时创建或激活失败：<底层原因>」到 `initializationDiagnostic`，再把原错误抛给控制器。之后句柄为空的按键路径会复用这条诊断，因此不会退回泛化的「尚未准备完成」。恢复成功后清掉旧诊断；选项为空的不可用路径也保留已有初始化诊断，只有没有诊断时才填入默认文本。

新增测试先占住词库访问锁，再验证恢复抛错后的下一次按键仍返回创建失败原因。这样测试覆盖的是恢复失败到按键诊断之间的状态契约，不依赖某个具体设备上的资源错误文本。

## Alternatives considered

- 只在 `KeyboardViewController.viewWillAppear` 的 `catch` 中显示一次底层错误：这能覆盖当前出现过程，但诊断是临时的，用户下一次按键仍会从句柄为空的桥得到泛化提示，且控制器之外的调用方没有一致行为。
- 在恢复失败后自动改走只读会话：这可能静默绕过用户已授权的词库写入能力，改变学习和个人词库语义；当前证据只证明诊断被遮蔽，不能据此改变会话访问模式。
- 让 `dispatch` 根据 `suspended` 判断并固定显示恢复错误：挂起本身是正常状态，键盘尚未出现时设置网格等调用必须继续记录状态，因此不能把所有挂起状态都视为失败；失败原因应由恢复路径明确写入。

## Consequences

恢复失败后的错误会在后续按键中继续可见，设备日志和用户反馈可以直接带上底层原因，定位词库锁或资源问题时不再丢失信息。恢复成功会清掉旧诊断，正常重新出现不会残留错误。

本次改动不增加重试、不改变只读回退，也不改变会话持锁的生命周期。新增测试依赖测试进程能够占住同一组词库锁；它只验证错误传播，不替换真机上的资源和权限验收。由于当前开发机磁盘空间不足以安全启动完整 iOS 构建，本地设备验收仍需在有足够空间的环境补跑。
