# Agent Note: Android 长符号条目按文字宽度跨列

Status: implemented

## Problem

#7795 的网络符号格把邮箱后缀和单个符号一样放在五列等宽格里，缩小字号后仍省略域名末尾，用户无法区分同一服务的不同后缀。

## Decision

固定符号与常用分类保留五列基础网格，超过四个码位的条目至少跨两列，并按实际字形宽度与可用列宽增加跨度。整行放不下时换行，不拆分或缩写上屏值；布局宽度变化后重排这些固定条目。目录分页仍使用既有等宽网格，颜文字仍为两列。

## Historical audit

[邮箱后缀](../feature/2026-10-09-android-email-suffixes.md)部分重叠：复用后缀表、字号与上屏规则，替代固定单格省略的宽度策略。符号目录分页的缓存与分代规则不变。

## Alternatives considered

- 网络分类全部改成两列，长后缀宽度够用，实现简单；但网址片段与单个符号都占大格，增加不必要的滚动，常用分类也无法复用这条规则。
- 继续缩小字号，保留五列紧凑布局；字面已为 11sp，继续缩小降低辨认能力，仍不能保证不同域名的末尾可见。

## Consequences

网络和常用分类的邮箱后缀有足够宽度显示完整域名，单个符号仍保持基础列宽。跨列增加行数，但保持项目顺序；目录分页的每格子视图和行起始索引保持不变。极端字号或窄到整行也放不下的窗口仍以单行省略兜底。

## Verification

- JVM 模型检查覆盖未测量布局、小屏增大跨度、整行跨度上限、常用后缀以及目录保持一列。Android 主机检查通过：230 个 JVM smoke、93 个设备源文件编译。
- 修复前 APK 在 API 35 的专项检查因 `@proton.me` 仍使用窄格而失败；修复后 API 28 和 API 35 检查四种后缀的真实字符绘制坐标，确认每个字符有位置且未超出键边界，点击提交完整的 `@protonmail.com`，重新打开常用分类仍完整显示。用例保存恢复偏好和常用记录，数据均为合成值。
- API 35 的 320dp 窄屏专项同样通过完整绘制和上屏检查，验收结束恢复设备原分辨率。
- arm64 完整版 release APK 构建与签名校验通过；API 28 的 `smoke.sh --core` 通过短语上屏和删除；API 35 同时通过繁体显示和上屏、密码框直输。
- API 35 既有 `PairedPunctuationDeviceSmoke` 通过，中文成对符号的插入和跨过后半个保持正常。
- `scripts/verify-local.sh --quick` 通过。未在报告者的 vivo API 30 真机验收。
