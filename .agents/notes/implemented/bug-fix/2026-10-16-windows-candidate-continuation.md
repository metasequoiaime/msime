# Agent Note: Windows 外部候选选择由 TIP 自己的会话继续组字

Status: implemented

## Problem

`ReplyComposer::select_candidate` 已经改变 Server 会话，却把没有 `commit` 的成功选择编码成 `ui_rejected_selection`。网址开头、顶级域名补全留在组字中，TIP 收到拒绝后保持旧状态，双方从此不同步。只改候选窗显示不能修复 TIP 的按键分类和上屏。

## Decision

新增可选协商能力 `CandidateContinuation`。Server 为没有上屏的成功选择发送前置组字状态、候选文本和预期后置状态；TIP 在创建线程的 TSF 编辑会话里核对前置状态，在自己的当前候选列表中按文本唯一匹配，使用本地 generation/index 执行选择，再核对无上屏和后置状态。组字算法仍由 Engine 决定，不能通过重放补全字符串模拟模式。

状态只包含原文、预编辑、读音、光标、方案、本地模式、英文模式、整句改字及词组前缀，排除两进程各自的 session/generation 和异步候选排序。两份列表的序号可以不同。

worker 只维护局部分帧器，并校验管道注册代次；完成载荷保留第一帧的 focus/epoch，投递前及持有队列锁时再次核对。无效或中断的载荷使链路 dirty，后续帧不能拼到另一个 owner。分帧器在失败时保留首帧归属，孤儿尾帧没有归属、不能重置新组字。故障通知使用独立的单槽成员状态，UI 消费时再核对 owner；窗口队列满导致 `PostMessage` 失败时，由 UI 线程既有的偏好定时器在队列恢复后消费同一槽。应用拒绝编辑会话、类别分配失败、引擎拒绝或 TSF 重画失败都使仍属同一 owner 的 transport dirty。

请求为版本化的 ASCII JSON（Unicode 使用 JSON 转义），在既有固定大小 worker 包上按事务编号、帧序号和总帧数分帧。总载荷有上限，禁止截断；缺帧、重帧、乱序、焦点变化、组字 epoch 变化不能交付部分请求。最后一帧只投递有焦点与组字 epoch 约束的成员所有消息，不在 worker 线程调用宿主会话。无法应用时使 transport 失效，不能上屏候选文本作为降级。

协商结果随 Main endpoint 的不可变注册身份保留。只有双方声明能力才发新帧；旧组合保持既有回复，不宣称旧 DLL 已获得补全点选修复。完整上屏、部分汉字选词和释义页保留原有回复。

## Alternatives considered

- **发送补全文本并替换旧键击缓冲** — 可复用 `NeedToCreateWord`，改动集中。但宿主会话拥有模式和原文，修改旧缓冲不能更新它；重新输入文本也无法恢复删掉触发前缀后仍存在的网址模式。
- **发送 Server 的 generation/index** — 载荷最小，也使用引擎选择。但两个进程的会话身份不同，云候选和 AI 候选会改变排序，必须解析到 TIP 自己的候选身份。
- **把旧原文和候选装进单个回复** — 复用现有收包路径，但载荷上限是 199 个 UTF-16 单元，长网址会超限。分帧保留完整状态，并显式限定总量。
- **让新能力成为握手必需项** — 能要求两端同时升级，但让旧 DLL 所在的所有应用都失去输入服务。选择可选能力，仅在支持它的新版组合中使用新语义。

## Testing

- 真实 Server 和独立 TIP 引擎会话选择网址开头及 TLD 后，模式、原文、后续数字和路径保持一致。
- 长载荷跨帧完整交付；过期状态、候选不存在/重复、无效帧和生命周期变化不能执行选择。
- `candidate_continuation_pipe` 验证固定 ABI、上限、缺帧、重复、乱序、事务和 owner 变化以及每一帧写失败都会停止发送并关闭链路。
- 新旧组合只在双向交集中协商能力，`PipeTicket` 将该交集纳入传输身份。

## Consequences

未在真实 Windows 编辑器中验收前，只能声称引擎、协议和编译层已验证。传输完成仍不是 TIP 应用动作的回执，沿用当前选择交付模型；应用拒绝后以 transport reset 收敛，不能重放不确定选择。
