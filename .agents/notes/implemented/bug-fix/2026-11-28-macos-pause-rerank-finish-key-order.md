# Agent Note: macOS 上屏前做完停顿重解时不碰客户端

Status: implemented

## Problem

#11517 报告快速打字时偶尔「先打 a 再打 b，结果是 ba」。[把整句联想模型挪出按键](2026-11-16-macos-keystroke-reranker-at-pause.md)之后，空格和组字中的标点上屏前要先调 `finishPauseRerankBeforeCommit` 把停顿重解做完。它原来把做完的回复整个交给 `apply:`：写一次标记文字（`setMarkedText:`），再 `renderCandidates` 为候选窗读一次光标（`attributesForCharacterIndex:lineHeightRectangle:`），然后空格才照新画出的高亮项选词、标点才 `typeASCII:`。

这两步都是对客户端的同步调用。IMK 会在同步调用里处理下一个已经排着的键（`_applySequence` 的注释、[上屏重入保留较新组字](2026-10-23-macos-reentrant-text-client-commit.md)和释义到达只重画候选卡都基于这一点）。所以打完 `nihao` 紧接着按空格和 `w`：`w` 在空格交给会话之前就进了组字，会话里成了 `nihaow`，空格上屏的是它的首选；标点同理，`w` 跑到逗号前面。打得越快、重解剩得越多（停顿不够长、机器忙），越容易有键排在后面，与报告的「卡一下就错位」一致。

## Decision

- `finishPauseRerankBeforeCommit` 返回 `BOOL`：重解做了事、回复带 `view` 时只把它记进 `_view`，返回 YES；不写标记文字、不重画候选窗。从它返回到这个键交给会话之间，不对客户端做任何调用。
- 候选窗开着的空格：做完了就发 `MSIME_COMMIT_CANDIDATE`，上屏会话里新的高亮项，与候选窗没画出来时的空格一致。候选窗上画的还是旧代次的身份，照它选会被会话当成过期吞掉；为它重画又要读光标。随后的 `apply:` 把文档和候选窗一起更新；会话没接下时补画一次候选窗。
- 选了释义列（`_armedGlossColumn > 0`）的空格不先重解：上屏的是用户看着的那一项的释义，重解会换掉高亮项，新代次也还没有释义。
- 候选窗没画出来的空格和组字中的标点：会话本来就按自己的高亮项上屏，只是不再先写客户端；会话没接下这个键时补画一次候选窗，免得 `_view` 和画面的代次对不上。
- 数字键和点选照旧不重解。

## Alternatives considered

- **在嵌套的 `handleEvent:` 里把键排队，外层处理完再放出来。** 能保住所有路径的顺序，但 `handleEvent:` 要当场答复处不处理；排队的键放出来时如果应当交还应用（上屏后的回车、退格、方向键、数字），已经没法交回去，用 `CGEventPost` 重投又会排到后面已经到达的键之后，换一种方式乱序。
- **保留 `apply:`，事后看 `_spacingInputSequence` 发现有嵌套的键就补救。** 那个键已经进了组字，没有能撤回的办法，只能检测不能修正。
- **只更新 `_view` 和候选窗、不写标记文字。** 重画仍要读光标，同样是同步调用；重解只改顺序、不改组字，标记文字本来就不必在上屏前重写。

## Verification

`ShortcutTest` 的 `--nested-commit` 新增 `TestPauseRerankFinishKeepsKeyOrder`：假客户端在被调用的第一个同步方法（读选区、读文字、读光标、上屏、写标记）里送进下一个键 `w`，假会话的 `finishPauseRerankWithError:` 第一次回一个新代次的视图。候选窗开着的空格、没画出来的空格、组字中的逗号三种情形，都断言会话先收到重解、再收到这个键的上屏，最后才收到 `w`。

## Consequences

- 收益：上屏前的重解不再给后面的键开出越过当前键的窗口，空格和标点也少了一次写标记、一次读光标。
- 代价：做完重解后到上屏之间候选窗不再重画一次；这一帧本来也只存在几毫秒，用户看到的是上屏后的结果。候选窗开着的空格在做完重解时改按会话的高亮项上屏，不再核对画面上的身份：这时画面上的身份已经过期，这条核对原本就过不去，所以以前要先重画。
- 选了释义列的空格不再先重解。
- 仍在的同类窗口：上屏后联想（默认关）出现时，第一个键先读一次选区再收联想（`dismissPredictionForKey:client:`），释义列上屏先 `insertText:` 再取消组字；后一个键在这些调用里会先到会话。这次没有改，#11517 继续跟踪。
- 没有在报告者的机器和应用里验证；IMK 在同步调用里处理下一键的时机靠代码里已有的结论和合成客户端模拟，没有真实 IMK 的复现。
