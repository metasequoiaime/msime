# Agent Note: 全拼模糊候选参与同覆盖词频排序

Status: implemented

## Problem

#11321 复现了全拼开启 `z-zh` 后选择「之前」的词频记录已经写入，但重新输入 `ziqian` 时仍排在所有字面 `zi'qian` 候选之后。模糊行和字面行的实际按键覆盖相同，原合并只按覆盖长度稳定排序，因此词库来源不同的两组行没有共享调频顺序。

## Decision

全拼模糊合并先按实际按键覆盖长度分组。只有某个覆盖组里出现了与用户日志权重完全匹配的模糊词库行，才在该组内只重排词库来源的行，按持久化权重降序稳定排序；生成整句、在线候选和其他非词库行保留原有位置。没有学习记录时继续保持精确行优先的默认顺序，精确行和模糊行在权重相同时保持合并到达顺序，词库键、调频触发计数和落盘格式不变。

排序发生在去重之后，避免同一词面的精确行和模糊行互相复活。排序在会话候选投影阶段读取现有用户日志，不改变词库查询缓存；未开启模糊音的查询没有模糊行，不会触发该排序，因此默认候选顺序保持不变。

## Alternatives considered

- 只把用户选择记在用户输入 `zi'qian` 上：能让字面查询复用记录，但模糊候选在不同输入或重建会话中仍无法按它的标准读音参与排序，且会产生重复学习键。
- 把所有候选按权重全局排序：实现更短，但整句概率、在线候选和词库词频不在同一量纲，会破坏覆盖长度和整句站位约定，因此只移动同覆盖组内的词库行。
- 只把模糊行整体移到字面行前：能改善首屏但忽略用户词频，低权重模糊词会遮住高权重字面词，无法满足调频语义。
- 把所有同覆盖词库行按权重排序：能直接解决排序，但会让从未学习的高权重模糊行越过精确首选，推翻既有的精确优先约定，因此只在用户日志确认模糊行已经学习后启用。

## Verification

共享引擎合成词库回归开启 `z-zh`，连续选择模糊候选「之前」并销毁重建会话；修复后持久化权重让它进入首位，且没有诊断错误。既有全拼回归仍保证未学习时精确「宗国」排在模糊「中国」前面，现有双拼模糊学习回归保持通过。

## Consequences

开启模糊音并学习过某个模糊候选后，精确和模糊候选在相同覆盖范围内会共同响应词频学习；未学习的模糊行仍遵循精确优先，生成整句和在线行的排序边界不变。每个覆盖组只在日志命中学习模糊行时创建临时排序容器。真实 macOS 输入法和报告者 Host API 环境仍需在 PR 中复验。
