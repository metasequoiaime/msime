# Agent Note: 微软双拼分号键参与 Emoji 与颜文字混输

Status: implemented

## Problem

普通组字把微软双拼的 `;` 当作 `ing` 韵母键，`j;gk` 能拼出「警告」。`local::emoji::query_mixed` 在归一化前只收字母和 `'`，因此同一组字的 Emoji 和颜文字混输查询直接返回空表，根本到不了 `jinggao` 的资源编码。符号混输的同类入口由 [符号候选笔记](../feature/2026-10-13-symbol-candidates.md) 归属，这里只修 Emoji 和颜文字共用的查询。

## Decision

`query_mixed` 只在方案为双拼、且当前双拼键表实际使用分号键时接受 `;`。原始编码仍先作为一个查询前缀，`QueryPrefixes` 再用已有的 `normalize_input` 查全拼编码；`j;gk` 因而能命中 `jinggao`。全拼和不使用分号键的双拼方案仍拒绝它。E、M 本地模式的查询不改：它们的输入状态机只接收字母和 `'`，不会把 `;` 交到该查询。

## Alternatives considered

- **让所有方案都接受分号。** 校验更短，也不必查看键表；但全拼和其他双拼方案并不把分号当拼写，放行会让无效输入进入资源查询。
- **只在 `QueryPrefixes` 里处理分号。** 归一化已经在那里完成，看起来可以集中处理；但调用在进入它之前就被拒绝，仍需调整入口校验，单改这一层不能修复故障。

## Consequences

使用分号韵母的微软双拼组字现在可以得到对应 Emoji 和颜文字混排行；其他方案的输入边界保持原样。命中时会多做一次原始编码的资源查询，随后复用已有的全拼查询路径。合成资源的回归测试先在修复前得到空表，修复后同时命中两类行；平台宿主中的实际候选显示由 PR CI 的引擎与宿主构建继续覆盖。
