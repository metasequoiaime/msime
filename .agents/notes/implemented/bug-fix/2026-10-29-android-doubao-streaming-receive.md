# Agent Note: Android 豆包流式边录边读回包，失败按原因提示

Status: implemented

## Problem

#9886：同样的语音配置下短句能识别，说久了就报「网络断开」。#9939 只把整句上传那条路的报错分类改对了，豆包流式这条路的长录音中断原因没有处理。

`DoubaoRecognizer` 原来在一个循环里发完一块音频，再用 `while (in.available() > 0 || last)` 读回包。socket 是 `SSLSocketFactory.createSocket(plain, host, port, true)` 包出来的 Conscrypt `SSLSocket`，它的 `available()` 只报已经解密、留在本机缓冲里的字节，不会去网络上取；缓冲里的明文只会由一次 `read()` 带进来，而这个循环在发出最后一帧之前从不调用 `read()`。于是说话期间一帧回包也读不到：

- 双向流式（`bigmodel_async`，出厂预设）说话期间持续回中间结果，客户端不读，回包堆在接收窗口里，窗口满了服务端写不出去，就会断开连接。说得越久堆得越多，越容易断。
- 中间文字从不显示，键盘的停顿自动结束（`armSilenceStop`）也从不触发，只能等用户点「说完了」或录满上限。

同时还有三处问题：

- `recognize()` 遇到任何 `IOException`、关闭帧或错误帧都返回 null，两个调用方一律提示「语音识别服务未响应，请稍后重试」，分不出断网、超时、服务中止和没说话。错误帧带的豆包错误码和关闭帧的状态码都没读。
- 回包的 `result` 只按对象读。整句流式的文档把它写成分句列表，iOS 和 Windows 两种形状都读；按列表回时 Android 读出来是空的。
- 豆包流式和整句上传一样录到 60 秒就悄悄停下，用户不知道后半段没录进去。
- 整句上传的本机超时（`HttpAsrRecognizer.Failure.TIMEOUT`）在诊断里记成 `voice_failure_network`，和提示的「请求超时」对不上；系统识别的错误码 1（`ERROR_NETWORK_TIMEOUT`）也一样。

## Decision

### 收发分开

收发过程移到不依赖 Android、org.json 和 JNI 的 `DoubaoStreamSession`。采集线程只管读麦克风、发音频帧；会话开始时另起一条守护线程 `msime-doubao-reader`，一直阻塞在 `InputStream.read()` 上，到一帧处理一帧：中间结果当场回调监听者，ping 当场回 pong，关闭帧、错误帧、读不懂的回包和断线各自记下原因。会话里不再出现 `available()`。

- 两条线程共用一条连接写帧（音频与 pong），`DoubaoRecognizer.sendFrame` 在输出流上同步，一帧整帧写出，不会交错。
- 握手之后把读超时设为 0：整句流式（`bigmodel_nostream`）说话期间可能很久不回包，读超时会把正常的会话打断。等最终结果的时限由会话自己计：发出最后一帧后最多等 30 秒，到时记为超时并关掉连接让读线程退出。
- 读线程先结束（服务端报错、断开或提前给了最终结果）时，采集线程在下一块音频前停下；读线程失败时还会关掉连接，让可能阻塞在写上的采集线程立即返回。写失败后先等读线程 1 秒，看它能不能读出关闭帧或错误帧，读不到才记为网络中断。
- 帧边界、分片重组、1 MiB 单帧和 8 MiB 单条消息的上限、控制帧处理与原来一致。帧仍由共享层构造和解码，`DoubaoRecognizer` 把麦克风、`NativeClient` 的编解码和底层 socket 注入会话。

### 失败分类

豆包流式的失败与整句上传归到同一个 `HttpAsrRecognizer.Failure`，`recognize()` 没有文字时抛 `HttpAsrRecognizer.Refused`：

| 情形 | 原因 |
| --- | --- |
| 连接或握手读超时（`SocketTimeoutException`） | `TIMEOUT` |
| 连接失败、TLS 失败、读写中途断开、没有关闭帧就断线 | `NETWORK` |
| 握手被拒 | 按状态码：413 为 `LIMIT`，408/504 为 `SERVICE_TIMEOUT`，其余为 `SERVICE`；读不出状态码为 `NETWORK`，101 却对不上校验值为 `SERVICE` |
| 最终结果之前收到关闭帧：没带状态码、1000 或 1001 | `ENDED`：服务端没报错就结束了会话，多半是它那一侧的会话时长或空闲限制 |
| 关闭帧 1009 | `LIMIT` |
| 关闭帧 1011–1014 | `BUSY`：服务端故障或重启，稍后重试 |
| 其余关闭帧（协议错误、策略拒绝等） | `SERVICE` |
| 错误帧 550xxxxx（服务内部错误，55000031 是过载） | `BUSY` |
| 错误帧 45000081（服务端等音频包超时） | `SERVICE_TIMEOUT` |
| 错误帧 45000002（空音频） | `EMPTY` |
| 其余错误帧（参数无效、音频格式不对）、读不出错误码、读不懂的回包、帧超出上限 | `SERVICE` |
| 读线程上解码（共享层 JNI）或回调抛出 `RuntimeException`/`LinkageError` | 会话立即结束，异常在调用线程上重新抛出，由调用方原有的兜底提示「语音识别服务无法启动」 |
| 发出最后一帧后 30 秒没有最终结果 | `TIMEOUT` |
| 最终结果没有任何文字 | `EMPTY` |
| 打不开麦克风 | `PERMISSION` 或 `UNAVAILABLE`，与整句上传的采集一致 |
| 地址或起始帧在本机就构造不出来 | `SERVICE` |

错误码表取自《大模型流式语音识别 API》（45000001 参数无效、45000002 空音频、45000081 等包超时、45000151 音频格式不正确、550xxxxx 服务内部错误、55000031 服务过载），共享层 `credential/doubao.rs` 的「测试连接」也按同一张表区分 550xxxxx。`BUSY` 提示「语音服务暂时不可用，请稍后重试」，`ENDED` 提示「语音服务提前结束了识别，可能已到服务时长限制」；两者都只由豆包流式给出，诊断记 `voice_failure_response`。以前这几种一律落到 `SERVICE`，提示「语音服务拒绝请求，请检查服务配置」，服务限时或过载时让用户去查配置是错的指引。

提示文字和诊断类别集中在 `VoiceFailurePolicy`，键盘（`ImeVoiceEntry`）和识别窗口（`VoiceRecognitionActivity`）的整句上传与豆包流式四处共用，文字沿用 #9939。已经识别出文字之后才失败的，文字照常上屏或保存，另外提示一句中断原因（例如「网络中断，已保留识别到的文字」），诊断照记失败类别。输入位置变了、文字存进语音结果而没有上屏时，这句说明并进同一条提示（「……，已存入语音结果」）：提示只显示最后一句，分两次说会把它盖掉，用户就不知道保留的这段不完整。键盘里豆包流式遇到 `PERMISSION` 与整句上传一样转交识别窗口去申请权限，用户已经结束采集的除外。

### 豆包不按停顿自动结束

键盘里点语音键开始的聆听，本机模型在出字后停顿 1.5 秒自动结束（`armSilenceStop`），VAD 判定还在说话时推迟。豆包流式的中间结果现在读得到了，但不接这个计时：豆包不报是否在说话，`VoiceHoldPolicy.silenceElapsed(held=false, speaking=false)` 到点就结束；整句流式（`bigmodel_nostream`）说话期间要到音频超过 15 秒才回第一段结果，按出字后停顿计时，口述 20 秒的用户会在 16.5 秒左右、话还没说完时被掐断，正是 #9886 的长录音场景。豆包仍由用户点「说完了」、松开空格或录满上限结束，和改动前一样（改动前中间结果读不到，计时从不启动）；iOS 的豆包也不按停顿结束。中间文字照常显示在聆听面板上。`check-host.sh` 钉住系统识别和豆包两处 `heard(..., false)`。

### 单次录音上限

- 豆包流式的上限放宽到 5 分钟（`DoubaoRecognizer.MAX_MILLIS`）。流式协议边说边识别，不受请求体大小限制，上限只防忘了关麦克风。
- 整句上传保持 60 秒（`HttpAsrRecognizer.MAX_MILLIS`）：整段音频一次上传，还受服务端请求体大小和读超时限制。读超时按请求体放宽，见 [整句上传的读超时](2026-10-31-android-upload-asr-read-timeout.md)。
- 录音到了上限、由识别器自己停下时，识别出的文字照常交出，再提示「单次语音最长 60 秒，已识别前 60 秒」（豆包是「5 分钟」）。
- 语音贡献只收 60 秒以内的整段音频，豆包流式录音超过 60 秒时这次不留音频，不上传截掉后半段的音频配整段文字。

### 诊断类别

新增 `voice_failure_timeout`，追加在 `DiagnosticEventKind` 末尾（识别窗口跨进程只传序号），共享层 `client-services::diagnostics::EVENT_KINDS` 同步加上，诊断包导出时才不会丢掉它。本机这一侧等服务超时（`TIMEOUT`）和系统识别的错误码 1 记这个类别；服务端自己回的 408/504（`SERVICE_TIMEOUT`）是服务的回应，仍记 `voice_failure_response`。

## Alternatives considered

- **录音期间把读超时设得很短（例如 20 ms），每发一块音频就试读一次，捕获 `SocketTimeoutException` 后继续发。** 改动最小，不用第二条线程。不用它，是因为它依赖 TLS socket 在读超时之后状态仍然完好：Conscrypt 有基于文件描述符和基于 `SSLEngine` 的两套 socket 实现，不同 Android 版本默认用的不一样，这一点在两套上都要设备验证；而且每 100 ms 抛一次异常、读不完时回包仍会滞后一块音频。独立读线程不依赖这个语义。
- **到 60 秒自动开新的一段继续录，结果拼起来上屏。** 用户感受不到上限。不用它，是因为分段处的字会被切断或重复，拼接要处理标点和重叠，豆包流式本来就支持长时间会话，用不着分段；整句上传分段则要多次上传、多倍等待。维护者选了放宽豆包流式上限、整句上传到点提示。
- **豆包流式也保持 60 秒，到点提示。** 最一致，但流式协议没有整句上传那样的请求体限制，60 秒只会无谓地截断长段口述。
- **只对双向流式按停顿自动结束，按地址里的 `bigmodel_nostream` 区分。** 双向流式说话期间持续出字，停顿计时大体可用。不用它，是因为地址可以自定义，按字符串猜模式不可靠；双向流式「只在结果变化时回包」也没在真机上确认过；而改动前豆包本来就不按停顿结束，保持原样没有回退。
- **正常关闭也归到 `LIMIT`（「音频超过服务限制，请缩短录音」）。** 不新增原因。不用它，是因为没报错的正常关闭不一定是录音太长（也可能是空闲限制或服务端重启），说成「超过限制」是替服务端下结论；`ENDED` 的提示用「可能」措辞，只说服务结束了识别。

## Consequences

- **收益**：说话期间就能读到回包，双向流式不再因为回包堆积被服务端断开；键盘里豆包的中间文字实时显示。失败提示分得清断网、超时、服务结束会话、服务故障、拒绝请求和没说话；到上限不再悄悄截断。共享 JNI 在读线程上的意外失败不会让输入法进程退出。
- **代价**：每次豆包会话多一条守护线程。录音期间网络静默断开时，采集线程可能阻塞在写上，直到 TCP 放弃或用户点「取消」；这一点和改动前相同。
- **已知上限**：Conscrypt `available()` 的语义和「回包堆积导致服务端断开」这一推断没有在真机上用真实豆包账号对比验证过；若真机上 55 秒长录音仍然断开，要重查服务端断开的原因，而不是这条收发路径。豆包实际用哪个关闭状态码结束超时的会话、整句流式的 `result` 实际是对象还是列表，也都没有用真实回包确认；分类按协议和文档的约定写，真实回包对不上时改 `VoiceFailurePolicy.closed`/`doubaoError` 这两张表。因为这些都没验证，PR 只写 `Refs #9886`，issue 等真机确认后再关。本机模型（`LocalAsrPolicy.MAX_MILLIS`）的 60 秒上限和系统识别服务自身的时长限制不在本次范围内。

## Verification

- `platforms/android/tests/voice/DoubaoStreamSessionSmoke.java`：回包流的 `available()` 永远是 0，模拟 Conscrypt；断言中间结果在录音结束前送到监听者，以及按状态码归类的关闭帧、按错误码归类的错误帧、断线、写失败、最终结果超时、空结果、上限、取消、ping、分片和提前给出最终结果各自的结局；解码抛出意外异常时会话立即结束、异常回到调用线程、不走未捕获异常处理。
- `platforms/android/tests/voice/VoiceFailurePolicySmoke.java`：提示、诊断类别、中断提示、上限提示、握手状态码、豆包错误码和关闭状态码的归类；没有文字时断网、超时、服务结束会话、服务故障、拒绝请求和空回复的提示各不相同。
- `platforms/android/tests/voice/WebSocketFramesSmoke.java`：握手状态码和关闭帧状态码的解析。
- `scripts/test-android-voice-project-config.py`：会话与识别器里没有 `.available()`，读线程存在，`result` 的分句列表和错误码都有人读。
- `platforms/android/check-host.sh`：系统识别和豆包的中间结果都以 `heard(..., false)` 接线，不按停顿结束。
- `crates/client-services/src/diagnostics/tests.rs`：`voice_failure_timeout` 能导出进诊断包。
