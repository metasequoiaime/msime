# Agent Note: 鸿蒙手写区接收触摸并直接识别笔画

Status: implemented

## Problem

手机上的手写面板能够打开，但在参考线覆盖的书写区划动没有笔迹。将触摸交给书写区外层后，笔迹出现，停笔又报「无法读取手写画布」。离屏白底黑字图能够进入通用文字识别，但真机对合成「工」「十」返回空文字，不能以 API 调用成功证明手写可用。

## Decision

书写区的外层 Stack 统一接收触摸，内部 Canvas 只绘制笔迹。触点取事件的 changedTouches，取消事件不依赖仍有活动触点。保留用户设置的笔迹颜色、粗细、停笔时间与既有修订号和串行请求队列。

鸿蒙启用仓库现有的 Rust 单字笔画识别器，经有界的 C ABI 与 NAPI 工作线程接收已完成的笔画，返回最多 12 个候选；不截图、不联网，不保存笔画或识别内容。Android 仍使用 ML Kit，桌面已有入口不变。宿主只接入识别，不复制输入算法。

打包脚本获取资源锁固定的 Tegaki zh_CN 模型，校验大小和 SHA-256，携带模型与 Zinnia 许可证，模型与引擎词库分目录暂存，复用既有资源分代安装。约增加 26.8 MB 模型；模型首次加载与分类放在原生工作线程，避免阻塞书写。

## Related notes

检索鸿蒙、手写与 Core Vision 相关记录后，旧的[手写板设置预览](../../implemented/feature/2026-10-12-harmony-handwriting-pad-preview.md)只规定设置动画，属于部分重叠，本次不改变其示例笔画和默认值。其他命中的计时器、翻译和语言入口记录不涉及本次识别决定。

## Alternatives considered

- 组件截图交给系统 OCR 可以复用现有 API 且不附带模型，但真机截图链路失败；改成离屏图后仍无法识别合成手写字，不能作为可用的单字手写识别器。
- 离屏白底黑字图消除了皮肤和组件挂载的影响，是保留 OCR 的最强理由；真机确认图像有正确笔迹而识别结果为空，因此移除整条 OCR 路径，直接复用已有笔画模型，不增加第二条识别路径。

## Verification

- 鸿蒙逻辑测试、ArkTS HAP 构建、原生 `aarch64-unknown-linux-ohos` 交叉构建和签名包校验通过。
- C ABI 合成「中」笔画测试返回包含「中」的候选；边界请求测试通过。
- 手写区扩大后，设备坐标按实际画布尺寸记录，再映射到固定 420×420 识别坐标。
- 签名包已覆盖安装；真机端到端候选、上屏、删除和重写验收因设备锁屏未完成。

## Consequences

收益是鸿蒙和桌面复用同一套 Engine 笔画识别器，放大书写区不会改变识别比例，识别不依赖截图或网络。代价是 HAP 增加约 26.8 MB 中文模型，且真机完整交互验收仍需在设备保持解锁后补跑。
