# Agent Note: 编辑器重新聚焦时恢复鸿蒙悬浮工具栏

Status: implemented

## Problem

用户反馈 HarmonyOS 2in1 切换窗口后悬浮工具栏消失。此前宿主只在自己记录的全屏状态变化时才调用 `show()` 或 `hide()`；系统若自行收起状态面板，宿主的缓存仍是「未隐藏」，下次切到非全屏编辑器时就不会请求显示。源代码存在这条可能路径，但没有读取设备日志，不能断言它是用户现象的唯一原因。

## Decision

每次编辑器绑定都用 `InputClient.getCallingWindowInfo()` 查询调用窗口：`WindowStatusType.FULL_SCREEN` 时请求 `hide()`，否则请求 `show()`，不再按缓存跳过。全屏隐藏沿用对齐 Windows `OnWinEvent` 的原有策略，本决定不改变它。

`ToolbarFocus` 串行执行同一面板的显示和隐藏，并用焦点代次丢弃旧窗口的迟到查询和排队请求；编辑器解绑或工具栏被关闭时废止旧代次。窗口状态查询失败时记录错误并尝试显示，避免一次失败让工具栏无法恢复。面板创建期间到达的编辑器在挂载后执行同样的焦点处理。

`openToolbar` 把面板交给 `ToolbarFocus.beginSetup()`，直到调整尺寸、刷新内容、移到右下角并显示之后才 `endSetup()`；这段时间里到达的焦点不显示也不隐藏这个面板，由 `openToolbar` 自己的 `show()` 负责首帧，避免面板先出现在系统默认位置再跳到右下角。

## Alternatives considered

- 保留可见状态缓存以减少重复调用。系统可以独立收起状态面板，缓存不能证明真实可见，所以不再据此跳过请求。
- 每个窗口直接异步调用 `show()` / `hide()`，不经队列。代码更短，但旧窗口的慢请求可能在新窗口之后完成并覆盖结果，因此保留串行化与过期检查。
- 全屏编辑器也显示工具栏。有用户反馈全屏时需要工具栏，但这会改变所有 2in1 用户的现有行为，并与 Windows、Linux 宿主的全屏规则分开，需要维护者另行决定，不在本次修复内。

## Consequences

- 非全屏编辑器每次绑定都会请求一次 `show()`，即使面板已可见；代价是多一次系统调用，换来系统自行收起面板后能恢复。
- 编辑框保持焦点期间才进入或退出全屏的窗口，仍要到下一次聚焦才生效，这是 HarmonyOS 只在查询时提供窗口状态的限制。
- 若系统的显示或隐藏调用始终不返回，串行队列会一直等待，之后的焦点请求也无法生效。
- `openToolbar` 期间被丢弃的全屏焦点不会隐藏首次打开的工具栏，要到下一次聚焦才按全屏隐藏。

## Verification

- `platforms/harmony/tests/toolbar-focus.test.ts` 用模拟面板覆盖：重复聚焦、全屏隐藏、旧查询迟到、解绑后的迟到查询、旧面板、查询失败后尝试显示、慢隐藏与后续显示的顺序、显示失败后重试，以及面板准备期间焦点不显示、准备完成后照常显示。
- `KeyboardExtensionAbility.ets` 里的接线（`inputStart` 与建面板期间的编辑器都走 `followCallingWindow`，解绑和关闭工具栏使代次失效，`openToolbar` 包住 `beginSetup` / `endSetup`）在 node 下编不了，也按仓库约定不再加源码 grep 守卫，目前没有自动测试钉住，靠 HAP 构建和设备验收覆盖。
- 本笔记描述的实现（d1412dc4a3：保留全屏隐藏，并加入 `beginSetup` / `endSetup`）尚未编译 ArkTS HAP，也没有在鸿蒙电脑与真实窗口中验证，不能据合成测试确认设备上的具体故障原因。PR 正文里的 HAP 编译和自签测试包 6000 的部分实机检查都基于更早的 f18cf67，那一版全屏时也显示工具栏、没有准备期间的焦点门控，结果不覆盖本实现；自签组合构建 5004、5005 的使用者反馈同样来自不同实现。
