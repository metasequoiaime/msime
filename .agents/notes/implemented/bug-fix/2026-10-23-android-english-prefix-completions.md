# Agent Note: Android 英文候选恢复前缀补全

Status: implemented

## Problem

#9275 要求英文键盘输入三个字母时出现相关完整单词。Android 的普通英文候选当时只请求 `correction: true`，因此词库虽有前缀补全入口，候选栏却只显示原文和可选的唯一纠错。`eng` 与 `English` 不是一次编辑距离内的纠错，增加词库不能接回缺失的展示路径。

## Decision

Android 的候选工作线程请求共享引擎的合并展示（`correction: true, completions: true`，`limit` 为 12，见[移动端英文纠错](../../implemented/feature/2026-10-16-mobile-english-correction.md)的合并展示一节）：有纠错时只有原文与纠错，原文已是完整的词时只有原文，否则原文后接至多十一个前缀补全。Java 侧不再合并两次查询，只解码列表与 `corrected`，沿用现有代次与编辑器当前词校验。

空格与标点仍单独调用纠错查询，判据仍是两行且第一行为原文，不从展示列表读取第二项，因此 `eng` 不会因为出现 `English` 就在空格时自动扩写。只有用户明确点击补全才替换当前词，与点纠错走同一条替换路径。点原文时，只有展示了纠错（`corrected` 为真）或答案尚未返回才记为拒绝纠错；只有补全时点原文仅收起候选。密码、网址、邮箱和禁止建议框仍由现有门禁排除。

## Related notes audit

[移动端英文纠错](../../implemented/feature/2026-10-16-mobile-english-correction.md)部分重叠：它持有合并展示的协议和三端接线，本篇只记 #9275 在 Android 上的问题、验证与取舍。英文前缀借用、空页存储和中英混输的笔记约束不同路径，不改变其查询与排序规则。没有发现需要吸收或废弃的提案。

## Alternatives considered

- Android 侧分别查询纠错与补全再合并（本篇最初的实现）：不需要改共享协议，但有纠错时也追加补全、原文已是完整的词时仍列补全，与维护者在 #8119 定下的候选规则不符；规则还要在三端各写一份。引擎提供带 `corrected` 的合并展示后改用它，合并规则只有 Rust 一份。
- 把补全直接放进原有纠错响应：只需一次调用，但现有三个手机宿主都把第二项解释为可自动提交的唯一纠错，会把不完整单词扩写。现在的合并展示是另一种请求，原有纠错响应形状不变，边界查询不受影响。
- 扩充英文词库：能改善真实缺词，但无法让当前没有调用补全的候选栏展示这些词。先用锁定词库验证已收录单词的召回。

## Verification

最初的 Java 合并实现：JVM 合并回归在仅返回纠错的对照实现下先失败，恢复实现后通过。Android Java/JNI 检查、256 项 JVM 冒烟和 215 个设备源文件编译通过。锁定资源的英文词库按引擎的前缀排序查询，`eng` 的首项为 `English`，后续为 `engineering`、`engine`；该词库中 `eng` 不是精确词，合并展示仍会列出补全。API 35 安装修复前的 APK 后，同一设备专项在 `three-letter English completion` 阶段失败，只能观察到原文 `eng`。修复后的原生 full APK 在 API 28、35 通过真实软键补全专项，输入 `eng` 显示 `English`；不点候选时空格得到 `eng `，点击补全只替换当前词并保留前后文。

改用合并展示后，`EnglishSuggestionModelSmoke` 改为覆盖 `corrected` 的解码：纠错答案、只有补全的答案、旧请求没有标记，以及标为纠错却不是两行的答案被拒绝。`check-host.sh` 的 288 项 JVM 冒烟与 248 个设备源文件编译通过。改用后的 APK 没有在模拟器或真机上重跑设备专项。

## Consequences

补全由共享引擎在同一次查询中给出，每次展示只有一次有界词库查询；有纠错时不再展示补全，原文已是完整的词时只展示原文。词库缺失时仍不能给出补全。前缀补全不是上下文预测，不将本修复声称为完整英文联想模型升级。空格仍可采用已有纠错，但不会因为补全展示在第二项而扩写完整单词。设备日志只记录点击与轮询后的候选可观察等待时间，不把它当作逐键查询延迟基准；未在报告人的真机上验收。
