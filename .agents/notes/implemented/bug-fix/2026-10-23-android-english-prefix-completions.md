# Agent Note: Android 英文候选恢复前缀补全

Status: implemented

## Problem

#9275 要求英文键盘输入三个字母时出现相关完整单词。Android 的普通英文候选目前只请求 `correction: true`，因此词库虽有前缀补全入口，候选栏却只显示原文和可选的唯一纠错。`eng` 与 `English` 不是一次编辑距离内的纠错，增加词库不能接回缺失的展示路径。

## Decision

Android 的候选工作线程继续查询原文和唯一纠错，再通过已有的只读英文补全接口读取最多十二项词典结果。展示合并保留原文和纠错顺序，新补全忽略大小写去重，合并结果最多三十二项，沿用现有代次与编辑器当前词校验。补全失败时仍展示纠错；含撇号的输入只走纠错入口。

空格与标点仍单独调用纠错查询，不从展示列表读取第二项，因此 `eng` 不会因为出现 `English` 就在空格时自动扩写。只有用户明确点击补全才替换当前词。密码、网址、邮箱和禁止建议框仍由现有门禁排除。

## Related notes audit

[移动端英文纠错](../../implemented/feature/2026-10-16-mobile-english-correction.md)部分重叠：保留其唯一自动纠错和原文优先的决定，本篇只补 Android 的手动补全展示。英文前缀借用、空页存储和中英混输的笔记约束不同路径，不改变其查询与排序规则。没有发现需要吸收或废弃的提案。

## Alternatives considered

- 把补全也放进共享纠错响应：只需一次调用，但现有三个手机宿主都把第二项解释为可自动提交的唯一纠错，会把不完整单词扩写；新增协议字段与三端迁移超过本 Android issue 的需要。
- 扩充英文词库：能改善真实缺词，但无法让当前没有调用补全的候选栏展示这些词。先用锁定词库验证已收录单词的召回。

## Verification

JVM 合并回归在仅返回纠错的对照实现下先失败，恢复实现后通过，覆盖三字母前缀、原文与纠错顺序、大小写去重、不同前缀和数量上限。Android Java/JNI 检查、256 项 JVM 冒烟和 215 个设备源文件编译通过。

锁定资源的英文词库按引擎的前缀排序查询，`eng` 的首项为 `English`，后续为 `engineering`、`engine`，无需修改词库。API 35 安装修复前的 APK 后，同一设备专项在 `three-letter English completion` 阶段失败，只能观察到原文 `eng`。修复后的原生 full APK 在 API 28、35 通过真实软键补全专项，输入 `eng` 显示 `English`；不点候选时空格得到 `eng `，点击补全只替换当前词并保留前后文。两平台的完整英文纠错入口也通过，包含分词、拼写纠错、拒绝纠错、标点和受限输入框门禁。

本地 `pnpm run verify-notes`、`git diff --check` 通过。远端使用 Python 3.14 重跑的 `bash scripts/verify-local.sh --quick` 通过（运行 `20261023-023203`），覆盖契约检查、Rust workspace、Android 目标和宿主 Java、共享 Apple 桥接编译；其他平台按改动范围跳过。首次运行误用远端系统 Python 3.9，未通过，不作为通过证据。

## Consequences

每次展示多一次有界词库查询，词库缺失时仍不能给出补全。前缀补全不是上下文预测，不将本修复声称为完整英文联想模型升级。空格仍可采用已有纠错，但不会因为补全展示在第二项而扩写完整单词。设备日志只记录点击与轮询后的候选可观察等待时间，不把它当作逐键查询延迟基准；未在报告人的真机上验收。
