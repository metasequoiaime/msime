# Agent Note: 安卓候选释义和读音与候选同一帧出现

Status: implemented

## Problem

打开候选释义（「离线英文释义」，或选了别的目标语言）后，打字时候选条一闪一闪。原因有三：

- **释义总比候选晚一步。** `scheduleCandidateGlosses` 每一代候选都在工作线程上查一次释义，查完再排回主线程应用。查本身只要一两毫秒，但来回排队要十几到几十毫秒，这段时间里候选先画成没有释义的样子。
- **停顿重排把释义清掉。** 共享层每次重解（`Runtime::refresh`）都清空释义。停顿重排即使候选没变也推进代次，发布的那一代没有释义，宿主又要重新查。在延后模型的手机上，停顿 40 ms 起跑（[安卓候选按住时不换代，停顿计时从输入算起](../../implemented/bug-fix/2026-11-22-android-candidate-update-timing.md)），于是每个键都是「有→无→有」再闪一次。
- **读音（「显示读音」）走同一条工作线程。** 新词的读音同样晚一步出现。

此外，目标语言不是英语、且目标语言的离线词典装着时，宿主仍然先查一遍英文释义：合并时只取目标语言，这一遍查了也画不出来。

模拟器（API 35，模型强制延后到停顿）上量到：释义在每一代出现后 13–40 ms 才到，停顿重排的那一代又从有变成无。

## Decision

整页释义和读音都在主线程上、画这一代候选之前当场查，并按候选记住查过的回答。改动只在安卓宿主，不依赖共享层。

- **在 `renderViews` 开头当场查。** `scheduleCandidateGlosses` 改为在主线程上调 `CandidateGlossLookup.lookUp`，应用后不再另画一次，接下来画的就是带释义的这一代。`scheduleCandidatePronunciations` 紧接着调 `CandidateReadingLookup.readings`，目标语言释义的读音和释义在同一帧出现。原来的 `candidateGlossWorker` 不再有用处，删掉。
- **只在主线程上查。** 共享层把打开过的释义词库留在查询线程上（`engine/src/host/glosses.rs` 的 `thread_local!`，见 [共享 Rust 层在没有变化时不再整份读写和 fsync](../../implemented/bug-fix/2026-10-27-shared-rust-idle-io-hot-path.md)）。只在主线程上查，词库也只在主线程上留一份。鸿蒙本来就在 UI 线程上查。`onTrimMemory` 里的 `releaseProcessCache` 也运行在主线程，于是放掉的正是这一份。
- **按候选记住回答（`CandidateLookupMemo`）。** 释义属于候选本身，不属于哪一代。按语言、来源和文字（读音按 `CandidatePronunciationPolicy.key`）记住回答，没有释义的也记。新的一代只查没见过的候选，全都见过时不查。每种语言最多记 512 条，最久没用的先丢，只在内存里。
  - 下列时候清空：释义设置、词典或资源变了（`invalidateCandidateGlosses`）；读音设置变了，或读音资源包路径变了；键盘显示时（设置页可能改了自定义译文）；内存吃紧时。
  - 隐私模式或不许学习的输入框（`learningSuppressed()`）不记。
- **只查画得出来的语言。** 安卓只有一个目标语言，候选下面只画它。英文释义只在两种情况下才查：目标语言是英语，或目标语言的离线词典没装（这时退回画英文）。
- **空闲时预热。** 键盘显示后、会话建好后的第一个空闲时刻，在主线程上打开要用的释义词库，打字时的第一次查询就不用等打开。读音不预热：共享层每次都重新打开读音词库。
- **抽出两个查询类和一个记忆类。** `CandidateGlossLookup`、`CandidateReadingLookup` 通过 `Native` 端口调原生查询，请求的拼装和回答的解码留在宿主；`CandidateLookupMemo` 是两者共用的记忆。三者都由 JVM 冒烟驱动。

## Alternatives considered

- **工作线程上查，主线程等它几毫秒再画。** 主线程不碰 SQLite，词库也只留一份；但主线程照样要等，还要多一套跨线程交接和超时。耗时一样，代码更多。
- **只记住回答，仍在工作线程上查没见过的。** 记住的可以当场应用，停顿重排不再闪；但新词的释义仍晚一步，打字时还是一闪。若以后慢手机上当场查没见过的词太贵，退回这种做法。
- **只查当前看得见的一批候选，滚动时再查追加的。** 能再省下一部分请求（现在一代最多问 128 个候选，画出来的只有六个左右）。精确拼写和辅助码筛选会换代，换代后照样重新查，所以不会漏。这次先不做，等量到需要再做。
- **在共享层让重解保留仍在列表里的候选的释义。** 根上更省，安卓就不必每代再应用一次；但这会影响所有平台，留给共享层的讨论（#11819）。

## Consequences

- **释义和读音与候选同一帧出现，停顿重排不再把释义清掉又补上。**
- **主线程上的开销。** 在一台手机上（Android 16，arm64，目标语言日语，开着「显示读音」）量到：
  - 停顿重排的那一代都从记忆里取，释义一步不超过 1–2 ms。
  - 打没见过的输入时，要查词典的那几代：释义 p50 1 ms、p95 5 ms、最多 6 ms；读音最多 2 ms。
  - 所有代合起来：释义 p95 3 ms，读音 p95 1 ms。
  - 改动之前，同一台手机上主线程一代要查两种语言，p50 3 ms、p95 7 ms，而且当时仍有闪动。
- **内存。** 记忆每种语言最多 512 条，几百字节一条；释义词库由工作线程上的一份换成主线程上的一份。长按释义卡片仍在自己的线程上查，用到时另有一份。
- **少查一种语言。** 目标语言不是英语、离线词典装着时，不再查英文释义。
- **在线译文（账号、自己的服务）仍是异步的。** 账号路径每一代都要在工作线程上核对绑定。只改了离线部分。
- **验证：**
  - JVM 冒烟：`CandidateGlossLookupSmoke`、`CandidateReadingLookupSmoke`，覆盖只查没见过的、换代不重查、按来源区分、每种语言各记各的、只查画得出来的语言、失败不记、清空、无痕不记、容量淘汰、预热。
  - 模拟器（API 35）和手机上的计时用本地探针测，探针不随改动提交。
