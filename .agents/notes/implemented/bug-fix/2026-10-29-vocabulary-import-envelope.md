# Agent Note: 词表原文与 JSON 请求分别限制大小

Status: implemented

## Problem

背单词导入允许最多 8 MiB 原始词表，但 C ABI、Android Java/JNI 和鸿蒙设置桥把整个 JSON 请求也限制为 8 MiB。双引号、反斜线和换行序列化时需要转义，合法文件可能在抵达共享解析器之前就被拒绝。合成回归用 12,000 行带引号释义的 CSV：约 4.7 MiB 原文可直接经共享会话导入，序列化为约 9.3 MiB 的请求后却被旧 C 入口拒绝。

## Decision

原始文本继续由 `session::MAX_IMPORT_BYTES` 限制为 8 MiB；C ABI、Android Java/JNI 和鸿蒙设置桥的外层传输预算为 17 MiB，给宿主常规 JSON 序列化最多约两倍的转义与目录等元数据留空间。鸿蒙 NAPI 的通用字符串预算原本就是 17 MiB，继续沿用。JNI 在复制数组前检查请求长度，C 入口在构造切片和解析前检查长度。

文件读取上限、词条规则、行数和落盘词书的大小限制保持原有值。传输预算不承诺接受所有等价 JSON 表示：调用方刻意把每个字符编码成 `\uXXXX` 时，仍可能先触及传输上限。

## 旧笔记审计

检索词表、JSON、大小与 CSV 引号相关活跃笔记。[插件编辑器](../../implemented/feature/2026-10-26-in-app-plugin-editor.md)同样为词表的 JSON 转义单独预留预算，但约束另一接口，属于部分重叠、继续有效；[跨行引号记录](2026-10-13-wordbook-multiline-quote.md)约束 CSV 的记录边界，部分相关、继续有效。语音端点、模型清单、重排文本归一化的检索命中与本次导入传输预算无关。本篇不取代已有决定。

## Alternatives considered

- 继续把原文与请求都限制为 8 MiB：内存预算最小，但会因合法词表的字符内容不同而缩小实际可导入范围，宿主与共享会话行为也不一致。
- 取消请求大小检查：所有可解析表示都能到达共享层，但超大请求会先被复制和反序列化，失去入口的内存边界。
- 按六倍转义预留 49 MiB：能容纳全部字符写成 `\uXXXX` 的表示，但现有宿主不需要这种编码，并且会显著扩大复制与反序列化的内存预算。

## Verification

回归先在旧实现上复现 C 入口拒绝、共享会话成功的差异。修复后的边界测试核对导入数量与释义，另验证超过 8 MiB 原文由共享解析器拒绝、超过 17 MiB 的有效 JSON 由入口拒绝，两种拒绝都不创建词书或进度文件。Android 既有契约检查继续约束 JNI 在复制前拒绝超限数组。

## Consequences

合法词表不会再仅因宿主常规 JSON 转义而被误拒，原文解析与落盘限制仍独立生效。代价是外层请求可比以前更大；多语言宿主中的传输常量仍需同步维护。自动化验证覆盖共享会话、C ABI 与宿主契约，未在 Android、iOS 或鸿蒙真实界面中导入这份合成大文件。
