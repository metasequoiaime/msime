# Agent Note: Android 表情包兼容未声明图片类型的输入框

Status: implemented

## Problem

Android 水杉娘表情包原先只有在输入框通过 `EditorInfo.contentMimeTypes` 声明收 `image/png` 时才调用 `commitContent`。部分聊天输入框没有声明这个字段，但实际仍实现了 `InputConnection.commitContent`，导致点击表情后输入法直接退回剪贴板，用户需要离开键盘再长按粘贴，和同类表情包的点击发送行为不一致。

这份改动的第一版把判定放宽成「有输入连接就先试 `commitContent`，返回 false 再回退」。Pixel 3 XL 真机验收查出它带来两个问题：

- **静默丢图**：Flutter 应用 `app.glean.glean` 的搜索框（`contentMimeTypes=[]`、`extras=null`）里点贴纸，输入框没有图、键盘没有提示。归因来自代码路径加旁证，没有抓到返回值的日志：该应用的 dex 里有 `TextInputAction.commitContent`，说明 Flutter 嵌入层实现了这个接口并转给框架，而文本框没配可收类型时框架侧不处理。`commitContent` 返回 true 后 `sent=true`，剪贴板回退和提示都被跳过。改动前这些输入框稳定得到「已复制…长按输入框粘贴发送」。
- **微信通道被排到后面**：微信聊天输入框不声明图片类型，原本直接走私有表情命令；第一版先调 `commitContent`，只有它返回 false 才轮到私有命令。真实微信的 `commitContent` 返回什么没有验证过，返回 true 的话已上线的直发就失效。

## Decision

`StickerPackModel.route` 按输入框的声明选一条路，已知能用的通道优先，三条路互不先试对方：

- **`DECLARED`**（声明收 PNG）：只调 `commitContent`，返回 false 才复制到剪贴板并提示。与放宽前相同。
- **`EXPRESSION`**（`extras` 里 `SUPPORT_SOGOU_EXPRESSION = 1`、又没声明 PNG）：只发微信的私有表情命令，不调 `commitContent`；命令没被收下才复制并提示。与放宽前相同，微信路径一步未变。
- **`UNDECLARED`**（其余）：先把 FileProvider URI 放进系统剪贴板，再试一次 `commitContent`，不论返回什么都提示。返回 true 时提示「已发送水杉娘「X」，没有出现时长按输入框粘贴」，返回 false 时仍是原来的「已复制水杉娘「X」，长按输入框粘贴发送」。剪贴板没放成时分别是「已尝试发送水杉娘「X」」和「无法复制这张表情」。

理由：输入法从 `commitContent` 的返回值分不出「收下了」和「读完就丢」，而未声明的输入框在放宽前本来就每次都写剪贴板，所以保留副本不比原来多占用户的剪贴板；多出来的只是一次直发尝试和一句措辞不同的提示。提示在返回 true 时不说「已复制…粘贴发送」，否则图片已经进了输入框的用户照做会发两张。

先放剪贴板再调 `commitContent`：后者是主线程上的同步跨进程调用，对方主线程忙时要等到答复或框架超时。副本先放好，等待期间和超时之后用户都有东西可粘贴。微信式输入框不再有这次调用。

设备夹具新增独立的 `StickerEditorActivity`（状态行在最上面，三个输入框都不声明图片类型）：真的读图的、返回 true 却丢内容的、带私有表情通道且 `commitContent` 会吞内容的。`EmojiPickerDeviceSmoke` 在三者里各发一张，分别核对收到的 PNG、提示加剪贴板里的贴纸 URI、以及状态行是 `expression:` 而不是 `discarded-before-expression`。纯逻辑（选路和四种提示）在 `StickerPackModelSmoke` 里覆盖。

第一版加在 `EditorActivity` 里的那个输入框撤掉了：它把后面的输入框、复制按钮和状态行各往下挤一行，Pixel 3 XL 原生分辨率（1440x2960，density 560，高约 846 dp）下键盘弹起后状态行不在可见区，而 `await` 只认看得见的节点，新阶段在图片已收到的情况下超时。新阶段改读自己那个始终在最上面的状态行，并用不要求可见的 `awaitAny`；也不再断言「每行 5 个」。

## Alternatives considered

- **继续严格依赖 `contentMimeTypes`**：符合 Android 编辑器声明的保守解释，也不增加对不规范输入框的尝试，但无法覆盖反馈中的聊天应用；现有回退只能复制，不能满足点击直接发送，因此不采用。
- **只按目标应用包名白名单绕过声明**：可以把直发限定在确认过的应用，不会在别处多一句提示。但报告者没有给出稳定的包名，现在列不出名单，其他同类聊天输入框仍会失败，也会把应用兼容性写死在输入法里，因此不采用。拿到包名并在真机上确认后，可以把这些应用改成返回 true 时不提示。
- **未声明的也只看 `commitContent` 返回值（第一版）**：收下图的应用里最干净，没有多余提示。但返回 true 却丢内容的输入框里毫无反应，真机上一个 Flutter 应用就是这样，其他 Flutter 文本框走同一个嵌入层，预计相同但只测了这一个，因此不采用。
- **返回 true 后观察对方有没有来读 FileProvider，再决定提不提示**：能分出「收下」和「丢掉」。但 provider 在主进程、键盘在 `:ime` 进程，要跨进程回报，还要定一个等多久算没读的时限；对方读了也不等于显示了（按对 Flutter 引擎的记忆它是读完才丢的，未对照源码确认），信号本身不可靠，因此不采用。
- **把 `commitContent` 挪到工作线程以免阻塞键盘**：能消掉那次等待，但 `InputConnection` 的调用顺序要和主线程上的上屏、组字保持一致，换线程会让贴纸和随后的按键乱序，因此不采用。

## Consequences

任何输入框里点贴纸都有可见结果：图片进了输入框（声明的、微信式的），或者键盘上有一句提示。

未声明但真的收图的输入框里，每发一张都会出现一句「已发送…没有出现时长按输入框粘贴」，剪贴板也会被这张贴纸覆盖。前者是新增的打扰，后者和放宽前一样。

未声明的输入框每次点贴纸多一次同步的 `commitContent`，对方卡顿时键盘主线程会等它；已声明的输入框和「最近复制」图片的发送一直有同样的等待，这次没有消除它。

微信路径回到放宽前的样子，真实微信上仍未验证（验收机上没有装）。报告者的应用也仍未在真机上确认。

`StickerPackModel.commitsContent` 继续保留给最近复制图片等严格按声明判断的路径，避免把未声明的普通图片发送策略一并放宽；本次只改变内置表情包的发送顺序。

iOS 和 HarmonyOS 没有同样的问题，这次不改：iOS 的直插只在宿主声明 `supportsAdaptiveImageGlyph` 时才做，其余照旧写剪贴板并提示；HarmonyOS 只有剪贴板一条路。
