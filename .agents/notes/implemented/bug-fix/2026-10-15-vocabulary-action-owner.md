# Agent Note: 背单词的文件读取和确认绑定客户端代次

Status: implemented

## Problem

`VocabularyReviewPage` 用 `requestRef` 隔离已发出的旧请求，但导入文件的读取、清空进度和删除词书的确认都发生在进入该请求槽位之前。等待期间替换客户端后，旧回调仍能发起旧客户端的修改，旧读取错误及导入成功提示也能污染新页面。客户端 A 切到 B 再切回同一个 A 对象时，仅比较对象身份无法识别原操作已经过期。

释义展开状态也属于当前已接受的队列。只在提交回答时收起释义，无法覆盖切换词书、替换客户端，以及回答等待期间再次展开旧卡片的情况；下一张卡会直接显示答案。

已经接受的状态也需要归属：客户端替换时只清请求槽位并设置忙碌，旧词书、队列和导入提示仍留在页面。新客户端加载失败后忙碌解除，用户能把旧卡片的作答或旧词书的操作交给新客户端，而且页面没有初次加载失败时的重试入口。

## Decision

复用 `useAsyncGeneration(client)`，在文件读取与确认之前捕获代次，`update` 在调用宿主前检查捕获代次，结果写入继续同时检查代次和请求槽位。读取错误与导入提示也检查相同代次。已经发出的宿主操作完成底层调用，但不再更新失效页面。

`update` 成功通过挂载、代次和请求身份守卫后，与 `setStatus(next)` 一起清除 `revealed`。每次接受的新队列从隐藏释义开始，即使新旧首卡的词头与内容完全相同；失败或过期回包不清除当前卡片的展开状态。

客户端替换时同时清除已接受的 `status`、释义展开和导入提示。新客户端加载期间只显示读取状态，失败后只提供重试，成功后再开放该客户端自己的词书与卡片。相同客户端内的操作失败继续保留当前卡片和展开状态。

## Alternatives considered

- 比较客户端对象可直接识别 A 到 B 的替换，代码也少；但 A 到 B 再回 A 后旧确认会重新生效，因此使用单调代次。
- 只保护请求返回值可保持现有串行机制；但删除、清空和导入的副作用已经发生，守卫必须放在调用之前。
- 按首卡词头或内容派生展开键，能避免跨卡复用布尔值；但不同词书或重置后的新队列可能返回完全相同的卡片，必须以接受队列为边界。
- 用 effect 监听卡片字段，能集中清除；但相同内容不触发，且多一次提交时机，因此在统一接受点更新。
- 保留上一客户端的状态能在慢加载期间继续展示内容；但这份内容没有新客户端的有效归属，失败后会开放错误的操作。客户端替换时清除状态，同一客户端的失败仍沿用保留现卡的行为。
