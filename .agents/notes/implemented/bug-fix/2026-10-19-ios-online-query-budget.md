# Agent Note: iOS 连续输入的在线查询与候选控件预算

Status: implemented

## Problem

即使 iOS 的云候选和候选栏 AI 都关闭，连续输入的每次 `render` 仍会调用 `online_query`，序列化一份永远不会使用的在线查询。候选栏还会在每次按键时重建相同的本地输入菜单，并把没有变化的候选词块重新写入 `UIButton.Configuration`，触发不必要的文本测量和布局。

## Decision

在键盘生命周期同步云候选和候选栏 AI 的开关。两者都关闭时跳过 `online_query`，并取消可能残留的请求；开关在键盘重新出现或共享偏好重载后变化时重新启用。候选栏只在本地输入菜单内容变化时重建菜单，并按候选词块的显示输入和样式代次缓存控件更新；候选宽度约束只有实际宽度变化时才重新激活。带释义的词块把构造释义行时算好的内容宽度直接传给约束更新；没有释义行时不做只供释义使用的文本测量。避免同一词块两次从 Swift 富文本转成 `NSAttributedString`、重复测量首行及从多行文本截取首行。

## Alternatives considered

- **让 `OnlineCandidateProvider` 自己继续每键查询再判断**：仍然为离线用户支付查询和 JSON 序列化成本，不能解决连续输入的主线程预算。
- **每次都重画候选栏以避免缓存失效**：候选内容、皮肤、字体或释义变化时确实需要重画，但相同的词块配置和菜单不应重复触发布局，因此按显示输入和样式代次失效。
- **把候选栏整体移到后台线程**：UIKit 视图和配置必须在主线程更新，后台绘制会引入代次和竞态；本次只跳过可证明无变化的主线程工作。

- **设置约束时重新从完成的多行富文本量首行**：能让约束函数自行推导全部输入，但标题构造时已有完全相同的首行宽度，重复的富文本桥接、子串申请和排版测量不增加正确性；直接传递算好的内容宽度。

## Consequences

默认离线输入不再为每个字符构造在线查询，也不再重复构造没有变化的候选菜单和词块。用户开启任一在线候选后仍按原来的停顿去抖、代次和取消规则工作；候选内容或皮肤、字体变化会使缓存失效并完整刷新。
