# Agent Note: 个人词库导入按有界批次共用事务

Status: implemented

## Problem

#8643 报告 Android 导入约三万词后写入极慢。现有集合队列最多送 128 个请求，但个人词库同步每轮只取 4 个，且每个请求都重新准备日志与英文表、打开主词库和附加数据库、单独提交事务。Android 又在每轮后重读集合并补充队列；把原有两秒等待改长不会消除这些重复工作。

[导入后立即应用](../../implemented/bug-fix/2026-10-17-android-import-apply-before-success.md) 为短维护窗口保留每批 4 项；该决定在逐词事务前提下合理。本篇保留独占维护租约、请求回执和每项失败隔离，把事务边界与已有 128 项队列对齐。Rime 权重与水杉词频的比较是 #8643 的另一部分；本篇覆盖已有字不被改权重的合成端到端回归，不自动关闭整个 issue。

## Decision

引擎提供有界批量编辑：至多 128 项，一次准备连接、一个外层事务，每项用保存点隔离。校验失败或条目级 SQL 失败只拒绝该项；打开数据库、外层回滚或最终提交失败让整批保持待处理。数据库提交成功后，个人词库队列才记录应用状态。保留逐项请求 id 和现有回执格式，数据库成功但队列写盘失败后重试仍幂等。集合新增先核对同一请求 id 的完整 payload 回执，再按日志表主键 `dictionary/key/value` 精确判断用户原有词，避免将本批已提交词误记为原有词。真正 `AlreadyPresent` 不写入表示 `Written` 的旧回执格式。

原有通用逐项同步仍保留四项语义；新增批量回调仅供拥有批量数据库编辑能力的宿主入口使用。集合新增在 `preserve_existing` 路径同时检查当前代次实际词库表：已发布词条不改权重、不写成 `user_inserted`，返回 `AlreadyPresent`，由集合层记录并在停用时保留；只有工作库中不存在该词时才新增个人覆盖。所有平台通过同一 C ABI 同步入口受益，不增加 JNI 或网络接口。

集合待发 JSON 序列化直接借用尚未发送的操作，不为每批深拷贝全部编码和正文；集合内去重校验使用借用的编码/正文元组，保持相同身份判定。读写、完整文件校验、原子替换与 fsync 边界不变，不通过缓存跳过磁盘上的损坏或变更。

## Alternatives considered

- 只把四项改成 128 项：代码最少，减少队列与集合刷新次数；但仍为每个词重新准备连接并同步提交，维护锁占用会随逐词落盘成本增长。
- 只延长 Android 两秒预算：能在成功提示前多写一些词；不能提高吞吐，并会让设置页更久等待。
- 大词库一次无限事务：提交次数最少，但持有维护锁太久、无法在批间让输入会话取得共享租约。批次沿用已有队列的 128 项上限。
- 缓存完整集合与待发快照：可消除重复解析，但跨进程写入、损坏检测和内存上限需要额外失效契约；本轮先去掉采样已确认的深拷贝及临时身份分配，不引入缓存或新落盘格式。
- 只查个人日志判断已有词：实现最简单，但日志没有用户行的已发布词会被集合导入改权重并取得用户所有权；因此同时查实际工作词库表。

## Verification

确定性红绿回归：旧实现一次 128 项后剩 124 项，新实现剩 0 项。第一版批量实现仍全量扫描用户词，在「数据库提交、队列尚未确认」的重试回归中错误地产生 `AlreadyPresent`；改为回执优先后通过。

host-api 的词库筛选 149 项通过，另有 1 项显式吞吐测量被默认忽略；导入筛选 9 项通过。services 的词库筛选 110 项通过、1 项忽略；engine 的个人词库相关筛选 49 项通过。新增测试覆盖逐项 `RAISE(ABORT)`、整批 `RAISE(ROLLBACK)`、读事务阻塞最终 commit、回执 payload 冲突、数据库已提交后队列重试与超限批次；提交失败时主库和回执均只保留 seed，重试后均有全部 4 项。另有合成回归证明集合新增遇到已发布拼音词时保留原权重、返回 `AlreadyPresent` 且不写用户行。三包全部 targets 的严格 Clippy 通过。

新增 Rime 端到端回归使用 `a/mei/ke` 三组小主库，每组已有字的权重为 1000、500，导入文件故意给它们 0、7622，并增加权重 400 的新字；通过真实输入会话核对导入前、导入后与停用集合后的候选顺序，停用后原字权重仍为 1000、500，新字删除。宿主与 API 28、35 的原生 release APK 均通过；这证明不覆盖已有词的契约，没有覆盖正式主库与全部导入词的整体排序。

借用序列化的回归核对含空洞队列、中文、引号与 Add/Remove 顺序的字节结果等同旧格式且可重新加载。宿主 services 词库筛选 98 项通过、1 项忽略，host-api 批次筛选 9 项通过、1 项显式测量忽略；两包全部 targets 的严格 Clippy 通过。最终两 API 的四包单测分别为 36、425、224、1167 项通过，services 9 项忽略、4 项硬链接过滤，借用序列化测试实际执行。

合并最新 `develop` 前，33555 词的宿主 release 成对测量采用相同副盘临时目录、空主库与 `(key,value)` 索引，优化前后各运行两轮。优化前为 18139/23056 ms、峰值 RSS 169050112/169869312 字节；优化后为 20047/20343 ms、峰值 RSS 163495936/158679040 字节，均为 263 轮、实际全部写入。临时分配与峰值内存减少，但耗时没有稳定下降，不宣称端到端提速或每秒万行；单轮初测的 10664 ms 也不能代替这组成对结果。

同一 macOS 调试构建、同一合成 512 词 Rime 文件：修前 128 轮、4394 ms、最慢同步 40 ms；修后 4 轮、625 ms、最慢同步 118 ms。这是一组本机测量，不能外推为手机吞吐，也没有达到每秒万行。

API 28、35 专用 AVD 均运行 client-base/core/providers/services 整套 Rust 单测，四包分别为 36、399、222、1067 项通过；硬链接等设备不支持的用例按既有 runner 规则跳过。另在两 API 上执行 host-api 新增的 7 项批次/故障/重试用例，均通过。512 个合成词的设备调试构建首轮测量分别为 280/275 ms，最慢同步 95/114 ms；并发构建期间重测分别为 737/682 ms、最慢同步 331/251 ms。夹具使用空主库加索引，不能代表真实手机和已使用词库。API 35 的 20000 词测量为 157 轮、57480 ms、最慢同步 283 ms，离每秒万行仍很远。

测量三万行时命中既有单集合 20000 词上限：服务接受两万词，三万词的最终断言失败。显式测量入口现在提前限定集合容量，并核对实际导入数量，防止把截断后的词数当作完整吞吐。本篇不改变该容量限制；[三万行集合容量](2026-10-19-dictionary-collection-capacity.md)独立补齐报告规模的截断缺口。HarmonyOS 的文本契约原来硬编码 `.take(4)`，现在检查宿主使用批量回调、集合活动队列上限与通用有界取数；实际队列行为仍由 Rust 回归验证。

容量分支补入当时 `develop` 后的 quick（`20261019-215350`）通过：Rust 工作区、Android 与 WebAssembly 目标、Android 宿主 Java、Linux 设置壳及原生 92 项、macOS 原生宿主、Apple bridge 与 170 项可在本机运行的 Windows 测试。MinGW/Windows 原生交叉构建和 pipe 因工具链缺失跳过，HarmonyOS 原生打包因暂存环境缺失跳过，不计通过。笔记校验、格式与差异检查通过。

API 35 原生 APK 的独立导入套件通过：74 个合成词全部应用，第六项进入九键候选，活跃会话的请求保留 pending，关闭会话后重试成功。API 28 的整套核心验收发现[剪贴板取消选择器的旧用例重复返回](../feature/2026-10-16-android-clipboard-export.md)：诊断确认后台旧选择器导致多按一次返回，修正后独立两阶段通过；API 28 的 `--core` 整套原生 smoke 通过。API 35 原生 smoke 分段执行：修正合成重启编辑器的系统栏边距后，前缀通过；剪贴板最终两阶段独立通过；后续十万辅助码、74 词真实导入和剪贴板分词拖选通过。数字键盘套件在笔画键面失败，后面的套件未运行，不计整套通过。设备词库文件存在，但运行配置缺少 `language_dictionaries`；配置丢失路径留待独立回归与修复，当前证据不归因为批量事务。

## Consequences

每批连接准备与提交次数下降，维护窗口扩为最多 128 项，仍在批间释放租约供输入会话取得共享访问。Android 的两秒预算在当前批结束后判断，不是硬截止。

保存点释放不是落盘；只有外层事务提交后才能改变请求队列状态，依据 [SQLite 保存点语义](https://www.sqlite.org/lang_savepoint.html)。不改变 SQLite 同步级别、日志模式或持久化保证。实际词库的整体排序与进一步吞吐仍需验证；重复解析、完整校验和原子写盘仍随批次重复，去除临时分配不能消除这些成本。若继续优化，需重新评估集合状态的持久化与跨进程失效契约，PR 使用 `Refs #8643`。

后续[有界作用域同步](2026-10-19-collection-scoped-synchronization.md)在同一次调用持有的原集合锁内复用已校验状态，仍每批落盘并释放维护租约；不引入跨调用缓存或新磁盘格式。
