# Agent Note: Android 保留宿主契约后裁剪未用依赖代码

Status: implemented

## Problem

#11115 的 full/pinyin 瘦包再次越过 132,000,000 字节预警线。实际 nightly APK 中 DEX 约 18.9 MB，发布构建关闭 R8，未使用的依赖代码一起进入包。原生库与词库已经做过瘦身，单独缩短资源路径仍无法把下载到的拼音包压回预警线。

## Decision

发布构建只启用 R8 的未引用代码裁剪，不改类名、不内联或改写方法、不裁剪资源。第一步完整保留 `app.msime.android` 的类、接口及全部成员，覆盖 BuildConfig 反射、JNI 回调、Fragment 和按名字创建的宿主实现；反射调用的 AndroidX FileProvider 同样显式保留。第三方依赖沿用随 AAR/JAR 发布的 consumer keep 规则。额外保留 `FragmentTransaction.attach/detach`：设备生命周期回归通过反射重建视图，宿主没有静态引用这两个 AndroidX 方法，R8 无法从产品调用图看见这条验收路径；不改变原测试的前置条件。

这承接[RELR 与无损图标瘦身](2026-11-05-android-slim-apk-relr-webp.md) 当时推迟的依赖裁剪，不改变其原生重定位格式、资源内容和体积阈值。保留整个宿主包比精细 keep 牺牲一部分节省量，但动态入口集中在宿主，先保证既有运行时契约，避免把首次启用 R8 同全面混淆绑在一起。

## Alternatives considered

- 只启用 AAPT2 资源稀疏编码和路径缩短：不改运行时功能，验证面较小；实际旧拼音包从 132,187,757 降到 132,049,355 字节，签名前仍超过预警线，不能独立解决且余量不足。
- 完整 R8 优化与混淆：省得更多，但首次接入同时改变成员名、代码布局和动态创建路径，增加诊断与回归范围；这次只裁剪未用代码。
- 压缩 DEX 或原生库：能明显减小下载，却增加安装解压占用，已有笔记明确避免；继续保持可直接映射。

## 已取得证据

首轮同一源码、锁定资源、ABI 和开发签名的 full/pinyin 瘦包均为 `132200045 → 122316002` 字节，减少 `9884043` 字节，继续低于原来的 `132000000` 预警线。DEX 未压缩大小分别为 `18918304 → 9036092` 和 `18918240 → 9036028` 字节。补上 Fragment 保留规则后的完整夹具 full 包为 `255441590 → 245557547` 字节，DEX 为 `18918304 → 9036408` 字节；当前实现提交 `5e7ea96f26` 的最终 full/pinyin 瘦包均为 `132281965 → 122381538` 字节，减少 `9900427` 字节；对应 DEX 分别为 `18920104 → 9038228`、`18920040 → 9038164` 字节。同源最终对照保留 `1408` 个动态入口源码类和 `20381` 个成员，`1360` 个资源/原生库条目逐字节一致。

比较两份 APK 的 DEX access flags：排除 `ACC_SYNTHETIC` 编译器生成物后，宿主及 FileProvider 的 `1408` 个源码声明类、`20379` 个声明成员完整保留。D8 与 R8 会生成不同的 lambda 和桥接类，这些编译器实现不作为按名字反射的稳定入口。首轮 `1360` 个资源与原生库条目逐字节比较，只有基于新 DEX 重建的 `assets/dexopt/baseline.prof` 和 `baseline.profm` 允许变化，其余无差异。修复版完整夹具包另用同一份原生库重新打未裁剪对照，`1372` 个资源与原生库条目均无差异；不能将提交身份变化重编的原生库当作同源字节对照。

API 35 使用最终 full 瘦包执行崩溃、系统退出与 ANR 专项，整套通过。输入、设置和手写套件使用同代码的 R8 full 构建补齐锁定语言词库与词书，正在 API 28、35 专用 AVD 验收，不把缺资源的瘦包回退当裁剪结果。API 28 另用 `msime-client-test-api28-11115@emulator-5582`，避免占用其他会话的 `5566`。

## Consequences

同源、同资源、同签名的 full/pinyin 包都低于预警线；数据资源和原生库逐字节不变，宿主类与成员完整保留。设备运行仍需覆盖 API 28 与 API 35 的原生入口、输入、设置、反射创建、剪贴板及手写；体积和静态契约不能替代这些行为证据。

## Verification

依赖内的反射不能只靠静态调用图证明，必须核对第三方 consumer keep 及设备行为。包体积下降不代表功能验证通过。首轮 quick（`20261113-171138`）及正常推送门禁通过，保留规则修复后的 quick（`20261113-182912`）及合入新 develop 后的 quick（`20261113-183858`）通过。API 28 首轮完整核心套件只有剪贴板生命周期失败，DEX 对照确认原包的 `FragmentTransaction.attach/detach` 被裁剪。修复包在 API 35 的 Fragment detach/attach、Activity 重建、保存失败后重试三条原有生命周期回归均通过；API 28 标准 `--core` 正在重新执行。单独安装后直接启动生命周期脚本曾在“编辑器就绪”阶段失败，同源未裁剪包也出现相同失败，不将这条结果记为 R8 引入的问题或通过结果。

API 35 首轮完整套件还出现组字重启、剪贴板分词、提示位置、工具栏长按、触控板与九键数字层失败；前三项在未裁剪包通过，修复版针对前四项的原有回归均通过。触控板专项在修复版仍失败于放大镜与实体候选订阅共存，触控板与九键数字层的同源未裁剪包在同一阶段也失败，不能归因于 R8。首轮英文纠错失败，未裁剪包和修复包的独立英文纠错专项均通过。完整套件后续又出现删除撤销、长按预览和硬件翻译失败；未裁剪包的原有专项也出现对应失败，修复版硬件翻译专项通过。删除撤销的两包对照均在同一恢复阶段失败；长按预览两包都未观察到悬浮预览，不据此排除设备或前序状态影响。完整设备验收与失败原因对照完成前保持 draft，暂不发布。
