# Agent Note: 安卓候选按住时不换代，停顿计时从输入算起

Status: implemented

## Problem

安卓的停顿重解（[鸿蒙与安卓的停顿重解](../../implemented/feature/2026-11-04-harmony-pause-rerank.md)）在最后一次 `render()` 之后 300 ms 起跑，每一片都推进候选代次，候选没变也推进。用户正好在这时伸手点候选，三件事撞在一起：

- **点了没反应。** #8578 让按住候选时不重画候选条，视图却照样换了。松手时按钮上还是按下时那一代的身份，`selectStripCandidate` 见代次过期，静默返回。模拟器（API 35，把延后阈值改成 0，与「增强」延后到停顿的手机走同一条路）上按停顿发布的时刻扫按压：与发布重叠的 7/7 次被丢，不重叠的 9/9 次正常，重叠的那几次多数 `moved` 为假。
- **换序的时刻不固定。** 每次 `render()` 都重新计时、丢掉正在跑的片：释义、读音、在线行到达，甚至诊断提示消失，都会把停顿往后推，用户看到的是「打完字半秒左右候选还会换」。账号翻译的整页请求同样在每次重绘时作废、重发。
- **点读音来回换。** 读音行选拼音是一次派发，`Runtime::dispatch` 先摘下延后的模型，选完的列表按不带模型的顺序画出来，下一次停顿再换回模型的顺序：首选和次选换过去又换回来。

云候选、AI 候选到达也推进代次，按住候选时同样会让点击落空。

## Decision

只改安卓宿主，不依赖共享内核的改动。

- **按住候选时不换代。** `PauseRerankController` 多一个端口 `candidateHeld`：为真时不起新的一片、不收集后台评分，16 ms 后再看；归还取消的评分照常进行。在线结果交回主线程时经 `CandidateHoldGate.runWhenFree`，按住时排队，松手后按先后应用；工作线程原有的 2 s 等待超时后放弃，等着的结果就不再应用。「按住」取正在显示的候选条或竖排候选、展开面板和九键面板里是否有未结束的触摸（`candidatePressed`），`render()` 跳过重画也只用这一个判断：两者都是为了让按下时画出来的候选点得中，分成两份就可能一处加了候选区、另一处漏掉。按压标记在松手后两次主线程排队才摘掉，排队中的点击也在保护之内。
- **计时从用户的输入算起。** `apply()` 收到一次派发的结果时调 `schedule` 重新计时；`render()` 只调 `keep`，组字不再适用时取消，否则让已经排着的停顿照原来的时刻进行。账号翻译的 `CandidateTranslationStore.refresh` 遇到同一页（同样的目标语言、代次和词）已经排着或正在请求时什么都不做；请求失败时放开签名，下一次重绘照旧重试。
- **延后的模型 40 ms 起跑。** 原生回复带 `deferred` 时，这个会话之后的停顿 40 ms 起跑，与 macOS 相同（[macOS 把整句联想模型挪出按键](../../implemented/bug-fix/2026-11-16-macos-keystroke-reranker-at-pause.md)）：分数备忘在同一段组字里保留，每次只算新的前缀，换序紧跟在按键之后。后台的落定模型仍等 300 ms。会话第一次停顿之前还不知道走哪条路，仍按 300 ms。
- **点读音在同一帧里重解。** `ImeLayoutRows.chooseNineKeySpelling` 派发之后调 `settleNow`：会话挂着延后的模型时当场最多跑 3 片，只发布最后一片的视图。同一次主线程回调里画出结果，不带模型的那一帧不上屏；3 片没解完的照常接着做。
- **没在窗口里解完的重解照样晚到。** 慢手机上一次停顿的片数多，换序仍可能晚于 40 ms 加一片，但按住候选时不会发生。

## Alternatives considered

- **只改延迟，不管按住。** 40 ms 起跑让换序多数落在打字的空隙里，用户伸手时列表已经稳定；但慢手机、长句和云候选到达仍会在按压中途换代，点击照样落空。所以两样都做。
- **按住时照常换代，松手时按文字在新一代里找回同一个词。** 这能覆盖所有来源（包括尾部展开），但要给候选条、竖排、展开面板、九键面板和读音行各改一套绑定，是更大的改动；按住时不换代能先消掉多数情况，按文字找回留给统一绑定的后续改动。Windows 遇到同类问题时也是暂停重排，而不是重放旧选择（[Windows 待确认回复期间暂停候选重排](../../implemented/bug-fix/2026-11-16-windows-candidate-rerank-selection.md)）。
- **在共享内核里让没变的重解不推进代次、让选读音保留模型。** 根上更干净，但会改所有平台的候选身份规则：鸿蒙、安卓和 Rust 的测试都断言每片推进，macOS 依赖它。需要各平台确认，另行讨论；安卓这边不等它。
- **空格上屏前做完重解（macOS 的做法）。** 首选更准，但空格上屏的就不一定是画出来的那个词。这次保持安卓原来的行为：上屏画出来的首选。
- **按住时把在线结果丢掉。** 实现最简单，但手指按得久一点云候选就没了；排队到松手只多等一会儿。

## Consequences

- 按住候选时，停顿重解和在线结果都推迟到松手，按下时画出来的候选点得中。代价是：按住不放（包括长按出菜单）期间，换序和云候选都不出现。
- 停顿换序在延后模型的手机上提前到按键后约 40 ms 加一片，并且不再被无关的重绘推后；打字的空隙里会多跑几片模型，按键最多等一片（Pixel 3 XL 上一片 p50 17.5 ms）。
- 读音行点选在手指抬起的那一帧多等最多 3 片，换来不再先显示不带模型的顺序。
- 还没覆盖的：滑动或惯性滚动候选条时的换代（候选条会跳回开头）、竖排和实体键盘候选条按槽位选词、读音行按槽位选拼音、尾部展开时按钮短暂过期。这些留给统一候选绑定和滚动位置的后续改动。
- 验证：`PauseRerankControllerSmoke`（24 项，新增按住、片间按下、按住时仍归还、40 ms 起跑与会话隔离、重绘不重新计时、`settleNow` 的片数上限与前提）、`CandidateHoldGateSmoke`、`CandidateTranslationStoreSmoke`（新增同一页不重发、失败后重试）。在线结果的排队只有 JVM 覆盖：模拟器上没有账号，取不到云候选。
