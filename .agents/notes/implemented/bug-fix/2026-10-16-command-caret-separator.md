# Agent Note: 翻译命令在光标处插入分词撇号

Status: implemented

## Problem

`/fy`、`/fanyi` 和 `/translate` 在末尾接受分词撇号，光标编辑却只接受小写字母。宿主判断撇号用途的 `takes_local_separator` 还依据整段末尾，因此光标在触发词内部时误报可分词，在原文以撇号结尾、光标在单词内部时又误报不可分词。

## Decision

翻译命令的分词判断接收与 `local_preedit` 同坐标的光标位置，仅把 `/` 之后、光标之前的前缀交给现有 `takes_word_separator`。末尾输入、光标插入和宿主标点路由共享此判断。保留通用相邻撇号检查、生成模式长度上限和 Mention 字符集。

## Alternatives considered

- **在所有命令和提及中收撇号。** 实现最短且允许任意多词参数，但扩大了普通命令与 Mention 的语法；只复用翻译模式既有的分词规则。
- **只补光标插入分支。** 可以直接解决字符入口的拒绝，但标点入口仍依据整段末尾决定是否提前上屏；必须同步宿主查询的光标语义。

## Verification

两项核心 Session 回归在旧实现中分别因按键被拒绝、触发词内误报可分词失败，修复后通过。真实 Session 回归覆盖三种翻译触发词、单字母后插入、整段末尾已有撇号时从字符与标点入口插入、预编辑与光标、翻译源文本与候选、退格恢复；触发词内部与刚过触发词的位置不接受分词，连续撇号和长度上限不扩大。完整引擎 2211 项单测与 31 项 golden 通过，35 项按既有配置忽略；Clippy、格式、笔记与差异检查通过。独立审查复核了 Runtime 两条标点路由及上述边界，无剩余问题。首次本地完整 quick 门禁通过，覆盖 Rust 工作区、Android/wasm、Android Java、macOS 原生宿主和 Apple bridge；Linux 缺 Docker、Windows 缺 MinGW、HarmonyOS 缺完整构建环境的阶段按规则跳过，尚未构建的 Tauri 设置应用未参与工作区编译。

推送门禁复跑暴露了 Windows `host_online_candidates` 的过时断言：首次 quick 的 Windows 阶段在共享宿主库生成前跳过了它，库建好后才执行，旧断言仍要求空 AI 回答把占位行改成「—」。按当前 API 及其既有 Rust 回归，AI 不再预留占位，空回答与兼容 resolve 返回未应用且完整视图不变。该 C++ 测试单独编译运行时先稳定失败，同步断言后通过；产品行为未改动。独立审查后补充查询必须为对象的前置断言，单独运行与完整 quick 复跑均通过；后者实际执行 165 项 Windows 宿主测试，2 项因宿主差异排除。

## Consequences

光标编辑与末尾输入复用同一条翻译分词语法，普通命令与 Mention 仍只收小写字母。光标包含入口 `/`，不额外减一；相邻撇号由既有插入检查吞掉，末尾连续撇号的退出行为维持既有测试。宿主查询只检查光标前缀，避免因尾部字符而提前提交组合；原有长度门禁仍由输入路径执行。未进行系统输入框或翻译服务联网验收。

## 历史笔记检索

检索活跃笔记的 `/fy`、翻译命令、分隔与光标。[插件命令行](../../implemented/architecture/2026-10-13-script-plugin-command-rows.md)约束插件参数只收小写字母，与本修复部分相关，继续保留其边界；[表达式光标单位输入](../../implemented/bug-fix/2026-10-16-expression-caret-unit-letter.md)覆盖相邻模式，其决定不变。翻译服务、候选释义筛选、缓存与命令表分配笔记均不持有本次光标分词规则。
