# Agent Note: Windows TSF 配置按管道代次补发

Status: implemented

## Problem

Windows Server 原来只在偏好修订变化时把 TSF 本地配置发给全部已注册管道。新宿主进程、同一进程里的新 TSF 会话和重连管道不会改变这个全局修订号，因此可能一直保留 DLL 编译时的智能标点默认值。用户切换设置后暂时恢复，重启输入法服务或换到另一个宿主又失效，正好符合这种时序。

## Decision

Server 维护已收到当前配置的 `PipeTicket` 集合。配置修订变化，或任一管道的注册代次、能力或客户端集合变化时，向当前所有 TSF 管道重发完整配置；只有发送成功且配置修订没有被更新的快照才记为已发送。管道代次变化覆盖同一 TSF 线程的重连，客户端集合变化覆盖新宿主进程。发送条件不依赖 `mode_view()`：开始菜单、搜索框等宿主可能在焦点会话尚未建立时完成注册，若等待焦点，TIP 会继续使用编译时默认的智能标点开关。

## Alternatives considered

- **继续只按全局偏好修订发送**：实现最简单，但新注册管道没有触发条件，无法保证每个 TSF 客户端收到本地开关。
- **每个按键重发完整配置**：能掩盖遗漏，但把多帧配置写入输入热路径，增加管道占用和时序风险。
- **让 TSF 自己从磁盘读取偏好**：会跨越 Server 与 TSF 的进程边界，并重复配置解析；TSF 应只消费已校验的 IPC 帧。
- **等 `mode_view()` 非空后再发送**：不能采用。注册完成和焦点会话建立不是同一时刻，开始菜单等宿主的首个按键可能落在两者之间；配置推送应以管道快照为准。

## Consequences

- 新宿主、TSF 重连和 Server 启动后晚注册的管道都能在首次按键前拿到智能标点及其他 TSF 本地设置。
- 配置仍按批次发送；没有新管道且修订未变时不会重复发送。发送失败或配置在发送期间再次变化时会保留待发送状态，下一轮重试。
- 追踪器只记录注册身份，不改变焦点授权；`send_tsf_config` 仍由 Server 的现有管道快照和写入检查负责。
