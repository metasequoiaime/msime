# Agent Note: 九键读音行的未覆盖尾段显示为拼音

Status: implemented

## Problem

#10603：安卓九键关掉整句联想后输入「今天你要」（`546842664926`），读音行和写进输入框的组字是 `jin'tian'ni'926`。读音行 `nine_key_reading` 由 `NineKeySession::write_reading` 生成：首行候选覆盖的那段写拼音，没覆盖的那段原样写键码。整句开着时首行几乎总是覆盖全部数字的整句，尾段很少出现；整句关掉后首行只是词库里最长的前缀词（`今天你`），剩下的 `926` 就以数字出现在读音行上，安卓和鸿蒙还把这段读音写进输入框。

## Decision

`write_reading` 写尾段时先调用 `write_tail_spelling`：对首行没覆盖的那段数字跑一次拼写表的 `split_paths_limited`（输出上限 1），取排第一的切分写成拼音。排序沿用九宫格切分路径的规则：音节少的在前，末音节完整的在前，再按内嵌音节频度（`SyllablePrior`）。用户打的切分换算成尾段内的位置一并传入，切分照样守住。尾段切不成音节（`77`、切分处断不开）或会话还没建出频度表时返回 `false`，退回原来的原样键码写法。

尾段不查词库，只是音节层面的猜测；它和左列拼写选项、切分路径截断用的是同一份频度，所以与左列里排第一的音节一致。九键双拼、14/18 键共用这段代码，同样受益。首行没有读音（英文词、模糊音、emoji）时读音行仍为空，宿主照旧退回 `preedit`。

## Alternatives considered

- **维持原状，说明这是「无候选覆盖的尾段只能显示数字」。** 最强的理由是尾段的读法确实有歧义（`926` 可以是 yao、wan、yan、zao），原样显示数字不会显示错的拼音。不采用：安卓和鸿蒙把读音行写进输入框，用户看到的是一串数字，体验上明显是缺陷；而歧义在别处已经用同一份音节频度消解（左列首位、切分截断），再显示数字并没有更诚实。
- **按首行之后的剩余数字再查一次词库，用那里首行的读音。** 读音会更贴近选完首行后实际出现的候选，但每次刷新多一次词库查询，九键长串本来就紧贴 16 ms 帧预算（见 `resources/eval/README.md`），读音行不值这一次查询。
- **从刷新时已有的整串切分 `alternatives` 里挑一条在首行覆盖处有音节边界的路径。** 不用额外计算，但这些路径按整串排序、可能已被截断或被种子路径替换，找不到对齐路径时还要回退，规则比单独切尾段更难说清。

## Consequences

整句关掉时读音行和输入框里的组字不再出现数字，例如 `jin'tian'ni'yao`；尾段猜的音节可能与用户想打的不同（同码音节按频度取最常见的），选完首行后左列和候选会按实际剩余数字重新给出。读音行与按键的对齐不变：安卓 `CompositionCaretPolicy` 按九键键位比对字母和数字，点读音行移光标照常工作。只有存在未覆盖尾段时才多一次小规模切分计算，热刷新覆盖全部数字的常见路径不受影响。
