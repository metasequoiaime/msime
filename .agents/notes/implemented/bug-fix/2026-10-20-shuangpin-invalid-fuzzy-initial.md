# Agent Note: 双拼非法声母组合保留已启用的模糊读法

Status: implemented

## Problem

#8947 开启 `s-sh` 后，小鹤 `slrf` 不能出现「双人」，`ulrf` 可以。双拼先验证两键是否对应标准音节；`sl` 的字面 `suang` 不合法，被拆成单键，模糊查询随后再也看不到 `shuang` 的可能性。实际词库 C ABI 已复现。

## Decision

原查询保持不变，只在已启用声母模糊规则且原两键不能组成标准音节时，补充同方案下声母伙伴对应的合法两键编码。替代路径复用正常查询、辅助码与模糊尾查询，每个请求最多 32 条；关闭模糊、合法两键及手动分隔符仍按原边界处理。新行标记模糊命中，匹配码恢复为原输入，标准读音保留用于学习。

替代路径合并后沿用[双拼模糊候选排序](2026-10-20-shuangpin-fuzzy-coverage-learning.md)的覆盖与词库权重规则，不让声母伙伴枚举顺序遮住高频词。原编码非法时可能识别不到末尾辅助码，因此从合法替代读法取得同一末码，在权重合并之后重新施加单辅助码的匹配优先级；整句分数继续不参与词频比较。

## Alternatives considered

让通用双拼解码接受 `suang` 等非标准音节，能从最早入口保留用户输入，但这会改变普通切分、预编辑、规范化与学习契约，也会让未启用模糊音的用户取得非法读音。只补充受规则约束的合法编码，避免放宽标准音节表。

各替代路径内部排好序后直接拼接，可以完整保留每条路径的辅助码顺序，但多个合法声母伙伴之间的权重无法比较。统一合并权重后重新施加单辅助码顺序，同时守住两项约束。

## Verification

基线只加入新回归时，`slrf` 候选仍只有「双」而没有「双人」，补丁后通过。远端运行 `20261020-185132` 的 2372 项引擎单测、31 项 golden 与全目标 clippy 通过，49 项仍按原约定忽略。会话回归检查整段、保留尾部和光标前缀选择，原始匹配码消费与标准读音调频均通过。追加回归在 `20261020-185709` 验证五种内置双拼方案及末尾辅助码。

实际随包词库经 macOS C ABI 检查，开启 `s-sh` 后 `slrf` 的首选为「双人」，按 `slrf` 选择上屏且清空预编辑；标准 `ulrf` 同样通过。这是共享引擎与会话验收，尚未作 Fcitx5 桌面输入界面验收。

提交前 quick `20261020-185817` 通过，覆盖 Rust workspace、Android 目标／Java、WebAssembly、HarmonyOS 设置页、Linux 设置壳和 93 项原生测试、macOS 宿主及 Apple bridge 构建。Windows 原生／MinGW、pipe 与 HarmonyOS HAP 因工具链或暂存前置缺失明确跳过。

与最新 `develop` 组合时，合成词库 C ABI 复现 `lf` 同时启用 `n-l`、`r-l` 后，权重 100 的「嫩」排在权重 10000 的「人」之前。新增定向回归检查跨路径词频、`lfa` 与 `lfc` 的辅助码优先级，以及冷、热查询的原始匹配码。

组合复验 `20261020-224926` 通过 2379 项引擎单测、31 项 golden 与全目标 clippy，49 项按原约定忽略。跨路径回归同时检查两个词均消费完整编码时，首字辅助码匹配仍优先于尾字匹配。新宿主库 C ABI 确认合成 `lf` 的首选变为高频「人」，实际随包词库的 `slrf` 与 `ulrf` 首选仍为「双人」；三次选择均正确上屏并清空预编辑。

最终 quick `20261020-230053` 通过：Windows 便携测试 171 项、Linux 原生 94 项及 Rust workspace、Android 目标／Java、WASM、Linux 设置壳、macOS 宿主与 Apple bridge 通过。Windows 原生／MinGW、pipe 和 HarmonyOS HAP 因工具链或暂存依赖缺失跳过。前一轮 quick 在 Windows 便携测试的 12 个链接目标失败；单目标单独链接成功，改用数据盘上的短 `TMPDIR` 后整套通过，未调整测试排除规则。

## Consequences

非法两键的查询会增加最多 32 条替代路径，合法两键不产生额外编码查询。共享查询直接受益，不增加平台分支。合法双拼的模糊单字排序属于 #8944；本次只保证新引入的非法两键替代路径遵守已经落地的同覆盖排序规则。
