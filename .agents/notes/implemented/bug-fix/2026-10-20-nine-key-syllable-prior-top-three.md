# Agent Note: 九键音节频度取前三个字的权重之和

Status: implemented

## Problem

iPhone 真机验收时，九键打 `966365468426786254`（我们今天去哪里）首选是「我们今天去马力」，「哪里」不在前五个候选里。同一份代码配随包的 dict-v2.0.24 是对的；手机已经自动更新到 dict-v2.0.32，而 dict-v2.0.30 起词库仓库按万象词频调了单字权重：na 最常用的「那」从 9929703 降到 5580163，ma 最常用的「吗」从 9028487 降到 5664547，两个音节的先后翻了过来。

九键在 12 个数字以上只按音节频度留 24 条切分，种子 `wo'men'jin'tian'qu'na` 往后接尾段时只取频度最高的 `SEED_TAIL_LIMIT`（3）条。6254 的四种读法 ma'ji、na'ji、ma'li、na'li 里，na'li 因为 na 比 ma 低 1.5% 排到第四被丢掉，后面的整句解码根本见不到它。九键整句集（81 条，不挂模型）的首选准确率从 dict-v2.0.24 的 0.519 掉到 dict-v2.0.32 的 0.432。

根子在 `SyllablePrior` 只看每个音节最常用的那一个字（[九宫格切分路径按音节频度截断](2026-10-08-nine-key-path-ranking.md)）：两个音节的先后取决于各自头一个字的权重差几个百分点，词库任何一次单字权重调整都能把它翻过来。

## Decision

- `SyllablePrior::from_dictionary` 改用 `QuanpinDictionary::top_weight_sums`：每个完整音节取权重最高的 `PRIOR_CHAR_LIMIT`（3）个字的权重之和，再照旧取对数；前缀仍取以它开头的音节里最高的那个。na 有「那、哪、拿」三个常用字，比只有一个常用字「吗」的 ma 稳，dict-v2.0.32 上 na'li 回到前三条尾段里。
- 截断条数、种子尾段条数、整句解码都不变，只换音节频度的口径。`top_weight_sums` 走的是已有的 `query_exact_keys_per_key`，与原来的 `best_weights` 同一次批量查询，每个键多取两行。
- `resources/eval` 里四份网格基线（九键、九键长句、14 键、14 键长句）随本次重新生成。

## Alternatives considered

- **在词库侧回退或调整单字权重。** 最直接，也是一开始的建议：用户通过词库自动更新一天内就能拿到，不用等客户端发版。但它只修这一对音节，引擎对单字权重的过度敏感还在，下一次词库调频照样会在别的音节上翻车；而且已经装了 dict-v2.0.30 以后版本的用户，词库没回退之前一直是坏的。
- **多留尾段（`SEED_TAIL_LIMIT` 4 或 5）。** dict-v2.0.32 上准确率比本方案还高一些（5 条时 81 条不挂模型 top-1 0.481），但按键耗时 p50 从约 4.6 ms 升到 5.0–5.6 ms，涨 7%–20%。九键长串本来就超出 16 ms 帧预算（见 `resources/eval/README.md`），不再往上加。
- **放宽切分预算（`SEEDED_PATH_LIMIT` 32）。** dict-v2.0.32 上「我们今天去哪里」仍然是「马力」，没修好。#6681 量过放宽切分上限会让每键耗时翻倍，这条路本来就被否过。
- **取更多个字（前 8 个之和）。** 随包的 dict-v2.0.24 上 81 条不挂模型 top-1 从 0.519 掉到 0.494，dict-v2.0.32 上也只有 0.420，两个词库上都比前三个字差。

## Verification

- 单测 `seed_tails_keep_a_reading_whose_best_character_barely_loses` 用 dict-v2.0.32 的真实权重构造 na、ma、li、ji：只看最常用的字时种子尾段里没有 na'li，取前三个字之和时有。`cargo test -p msime-engine`（2369 项）和 clippy 在 Mac Studio 上通过。
- 锁定资源（dict-v2.0.24 加 `sentence-model.safetensors`，即 `verify-local.sh` 的评测口径），新旧基线对比：

| 集合 | top-1 | top-5 | found |
|---|---|---|---|
| 九键词级 2791 条 | 0.574 → 0.575 | 0.851 → 0.852 | 0.968 → 0.969 |
| 九键长句 81 条 | 0.617 → 0.617 | 0.654 → 0.654 | 0.753 → 0.741 |
| 14 键词级 2791 条 | 0.660 → 0.660 | 0.906 → 0.906 | 0.975 → 0.975 |
| 14 键长句 81 条 | 不变 | 不变 | 不变 |

- 九键长句逐条有得有失：「晚饭想吃什么」「这件衣服很好看」等变对，「请大家准时参加会议」「周末我们去看电影吧」「你们先吃我马上就过来」掉出首选。
- dict-v2.0.32 上 81 条不挂模型 top-1 0.432 → 0.457、top-5 0.543 → 0.568；挂模型 top-1 持平 0.519、top-5 0.568 → 0.593。60 条手写整句不挂模型 top-1 在 dict-v2.0.24 上 0.367 → 0.383，dict-v2.0.32 上持平 0.383；1105 条中立集不挂模型 top-1 在 dict-v2.0.24 上 0.164 → 0.169，dict-v2.0.32 上 0.141 → 0.139。
- `rerank_latency --nine-key`（dict-v2.0.24）与基线交替各跑五轮，只算引擎的 p50 基线 4.57–5.71 ms、本方案 4.51–4.81 ms，没有可见差别。
- iPhone 17（iOS 27.0.1，手机上是 dict-v2.0.32）装上新包后，九键连按 `966365468426786254` 首选是「我们今天去哪里」，读音 `wo'men'jin'tian'qu'na'li`。

## Consequences

- 收益：九键切分的去留不再取决于两个音节头一个字的微小权重差，词库调单字权重时九键长句不会因此丢掉正确切分。dict-v2.0.32 上丢掉的准确率收回了一部分，按键耗时不变。
- 代价：随包的 dict-v2.0.24 上九键长句 found 少了 1 条（0.753 → 0.741），request 类首选少了 2 条，换来 question、statement 类各多对 1 条，总的 top-1 持平。
- 遗留：dict-v2.0.32 上九键长句仍比 dict-v2.0.24 低（挂模型 top-1 都是 0.519 对 0.617），剩下的差距来自词库本身的调频，不在九键截断上。词库自动更新会直接装上 msime 没评测过的新版本，这个流程缺口这次没有处理。
