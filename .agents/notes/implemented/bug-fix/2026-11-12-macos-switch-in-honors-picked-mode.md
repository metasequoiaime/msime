# Agent Note: macOS 从别的输入源直接选「水杉全拼」时照它改方案

Status: implemented

## Problem

用户反馈（macOS，刚更新完）：误加了「水杉双拼」之后想换回全拼。在水杉设置里把方案改成全拼，方案自己又变回双拼；在系统设置里添加「水杉全拼」再选它，每次都被弹回双拼；偶尔停在「水杉全拼」上，按一下 Shift 又回到双拼。

三个现象是同一件事的两半，都在 `platforms/macos/src/input/` 的切回处理里。

第一半：只加了「水杉双拼」一个入口时，设置里选的全拼留不住。菜单栏选不上没启用的「中」，停在「双」；之后每次从别的输入源切回来，系统报告「双」，`MSIMESchemeForReportedInputMode` 对「中」以外的入口直接返回它的方案，偏好被改回双拼。

第二半：
[macOS 从别的输入源切回时报告「中」不改双拼](2026-10-29-macos-keep-shuangpin-on-return.md) 让切进水杉后、按键之前报告的「中」一律保留当前方案，再由 `syncSystemInputModeForClient:` 把菜单栏选回方案自己的入口。它假设这份报告是系统自己落在「中」上，但从 ABC 等输入源在输入菜单或切换条上直接选「水杉全拼」，到达控制器的是同一份报告：方案停在双拼，菜单栏被选回「水杉双拼」。在系统设置里添加输入法的整个过程都不会在水杉里按键，所以怎么选都弹回去。选回「双」的请求没有生效时（客户端不响应 `selectInputMode:`），菜单栏停在「水杉全拼」而方案仍是双拼，下一次同步——按 Shift 切中英就会触发——再把它选回「双」，这就是 Shift 那个现象；这一条是按代码推出来的，没有在设备上复现。那篇笔记把这一点记成了代价（「需要切回后在水杉里再选一次」），而它保护的场景——离开时在「双」、系统回来时自己落在「中」——没有设备证据，报告者也没有确认过。

## Decision

共享记录 `MSIMESystemInputModeState` 多一个字段 `left`：离开水杉时 `MSIMEResetSystemInputModeState` 把当时显示的入口（`current`）记进去；`current` 已经是空的就保留上一次的值，进程启动后还没离开过时是 nil。

`MSIMEReportReturnsToLeftInputMode(state, switchedIn, reported)` 判断切进后的一份报告是不是系统把用户送回了原来的入口：`switchedIn` 为真，并且报告的就是 `left`，或者 `left` 未知。控制器把它的结果（而不是原始的 `switchedIn`）交给 `MSIMESchemeForReportedInputMode`。于是：

- 离开时在「中」（方案是双拼，但当时「双」选不上或没来得及选），回来还是「中」：方案不动，菜单栏选回「双」，和之前一样。
- 进程刚启动、不知道离开时在哪个入口：按送回处理，和之前一样。
- 离开时在「双」，回来报告「中」：这是用户挑的入口，改用本版本的默认方案（full 是全拼），菜单栏留在「中」。

`MSIMEReportRepeatsLeftInputMode` 是更严的一条：`switchedIn` 为真、`left` 已知并且报告的就是它。这时不论是哪个入口，控制器都不改方案。只有「双」一个入口、设置里选了全拼的人，切回来报告的「双」因此不再把方案改回双拼；菜单栏仍停在「双」，状态项显示真实方案。`left` 未知时报告的 双、五、日 等照旧选各自的方案，在水杉里按过键之后报告的也照旧。

中英状态仍按原始的 `switchedIn` 走，[macOS 切进水杉时的模式报告不把默认英文改回中文](2026-11-10-macos-switch-in-keeps-starting-english.md) 的起点规则不变；英文切回中文的回执标记（[macOS 英文按 Shift 回中文时保留双拼](2026-11-10-macos-shift-keeps-shuangpin.md)）也不变。

激活校准先到时的顺序是：校准记下「中」，同步按双拼选回「双」，随后到达的「中」报告与记录不同、被采纳，按 `left` 判为用户的选择，方案改成全拼，同步再把菜单栏选回「中」。结果和报告先到时相同，菜单栏中间会经过一次「双」。

诊断日志同时补了两行，用来对照一份报告是控制器自己请求的回执还是用户选的：`input_mode_select mode=…` 记控制器每一次请求系统换入口，`input_mode_report … action=ignored reason=own_select|repeat` 记没有被采纳的报告；被采纳的那一行多了 `left=`。模式名不是输入内容。

- [macOS 切进水杉时的模式报告不把默认英文改回中文](2026-11-10-macos-switch-in-keeps-starting-english.md)：部分重叠，不改。中英状态继续看原始的 `switchedIn`。

## Alternatives considered

- 整条撤回 10-29 的规则，切进后的「中」一律按用户选择处理：实现最小，入口名和方案完全对应。不选它，是因为离开时就在「中」的情况（在设置窗口里把方案改成双拼时没有客户端可以选「双」，随后切走）回来报告「中」确实不是选择，撤回会把这些用户的方案改成全拼并写进偏好。
- 保持现状，只在设置页提示「要换全拼请到方案菜单里改」：不改行为。不选它，是因为菜单里那一项就叫「水杉全拼」，选了它却得到双拼，提示解释不了这个结果。
- 把 `left` 存进 NSUserDefaults，进程重启后也知道离开时的入口：能覆盖「更新后进程刚拉起、还没离开过」这一段。没有做，是因为共享记录现在是纯内存结构，持久化要在离开回调和启动两处加读写；未知时按送回处理与现状一致，用户切走一次（去 ABC 搜输入法就是）之后就有记录了。

## Consequences

收益：从别的输入源直接选「水杉全拼」会得到全拼，不再弹回双拼；五笔、粤拼、注音、笔画同理。设置里选的方案不再被切回时的报告改掉。新增的诊断行让之后的方案误改报告能直接从日志里看出每一份模式报告的来历。

代价：同时加了「全拼」「双拼」两个入口的双拼用户，离开时在「双」、回来时落在「全拼」入口上（用切换条依次切过去、或系统按文稿恢复了它），方案会改成全拼并保存，要再选一次「水杉双拼」或删掉「水杉全拼」入口。这正是 10-29 那篇想避免的情况；那里的前提「系统会自己落在中」没有设备证据。

只有一个入口而方案与它不符时，系统输入菜单显示的入口名（水杉双拼）和实际方案（全拼）不一致，直到用户添加对应入口或在水杉里再选一次这个入口。

没有设备验证：三个现象都只按代码和单元测试确认，Shift 那一条没有复现；新加的诊断行就是为了下一份日志能直接判断。

## Testing

`platforms/macos/tests/input/InputModeIdentifiersTest.mm`：离开时记下入口、连着离开两次不冲掉、新记录为 nil；离开时在「双」后切进报告「中」改用全拼（报告先到和校准先到两种顺序）；离开时在「中」回来还是「中」方案不动；`MSIMEReportRepeatsLeftInputMode` 只在入口已知且相同时为真。把判断换回旧规则时新断言失败。

`platforms/macos/tests/input/ShortcutTest.mm` 的 `TestSwitchBackKeepsShuangpin` 在真实控制器上跑同样三种情况，以及「离开时在双、方案是全拼、回来报告双」保持全拼、按过键后再报告双改成双拼；原有几段显式写明 `left` 未知。
