# Agent Note: macOS 横排候选窗在一次输入里只变宽不变窄

Status: implemented

## Problem

有用户因为「打字的时候候选框长度一直变化」卸载了输入法。横排候选卡片的宽度是 `candidatePageGeometry:` 按这一页候选的自然宽度算出来的，每按一个键候选都换一批，卡片就跟着伸缩。在 0.54.1 上打开诊断日志打一段字，`candidate-frame show` 记下的宽度在一次输入里是 642、716、558、566、557、574、719、753、623、642、773、792pt，不到一秒里来回跳两百多点；同一个键之后候选再补一轮（相隔约 10ms 的第二次排版）还会再变一次，例如 642 → 716。卡片右边缘一直在动，眼睛会被拉过去。

竖排早有同类保护：`MSIMETallestCandidateHeight` 记住这次显示以来最高的竖排高度，只用来决定放在光标上方还是下方，不让列表在光标两侧来回跳。横排的宽度没有对应的东西。

## Decision

`platforms/macos/src/candidate/CandidatePlacement.h` 新增 `MSIMEWidestCandidateWidth`，`InputController` 用 `_widestHorizontalCandidateWidth` 记住横排卡片这次显示以来最宽的一次：

- 候选窗一直开着（`_panel.isVisible`）的这段时间里，记下的宽度作为最小宽度交给 `candidatePageGeometry:`，卡片只变宽不变窄。
- 候选窗隐藏过（上屏、取消、清空、失焦，所有隐藏路径都会 `orderOut`）就从这一次的宽度重新记，和竖排高度的记忆同一个判据。
- 外观设置变了（`appearanceChanged:`：字号、整体大小、皮肤、内边距、圆角等）或明暗切换换了皮肤包（`refreshCandidateSkin` 整页重排的那一支）也清零：记下的宽度是按旧排版算的，不清的话调小整体大小后卡片还停在原来的宽度。`ShortcutTest` 里「调到 150% 再调回 100%，窗口回到原尺寸」的断言守着这一条。
- 竖排不记：竖排的宽度取最宽的一行，本来就不随每个键大幅变化，这次没有改它。
- 记下的宽度经 `minimumWidth` 进入排版，而不是在排版之后硬改窗口宽度：`geometry.lineWidth`、首行的翻页和展开键都按同一个宽度对齐。横排候选按自然宽度从左排（`SingleLineColumns` 放得下时保留自然宽度），多出来的空白都在右边，候选之间的间距不变。
- 记下的宽度含首行右端紧凑展开键那一格（`compactExpand` 时的 `arrowWidth`），交给排版前先扣掉，避免展开键出现、消失时宽度被重复累加。
- 展开的候选网格（`renderExpandedCandidates`）不受影响。

## Alternatives considered

- **固定宽度：卡片始终按屏幕宽度的一个比例或皮肤给的宽度画。** 最强的理由是完全不动，连「只变宽」的那几次跳动也没有。没有采用：候选少、字短时卡片会空出一大片，皮肤的装饰图和背景按卡片尺寸铺，固定宽度会改变所有皮肤的观感；而一次输入里只变宽，绝大多数情况下前两三个键之后宽度就稳定了。
- **按字数分档，宽度只取几个固定档位。** 能减少跳动次数，但档位交界处照样来回跳，候选长短正好在交界附近时比现在更明显。
- **在排版之后直接把窗口宽度改成记下的值。** 改动最小，但候选行、首行的翻页和展开键都是按排版算出的宽度摆的，硬改窗口会让右端的控件和卡片边缘对不上。

## Consequences

- 一次输入里候选窗右边缘只会向右移动，不再左右来回跳；输入短词时如果前面出现过很长的候选，卡片右侧会留出空白，直到这次输入结束。
- 新开一次输入时宽度从头算，不会把上一次的长候选带到下一次。
- 宽度仍受屏幕宽度和原有上限约束（`CandidateCardMinimumWidth` 不放大皮肤给的部分，记下的宽度来自之前合法的排版）。
- 验证：`candidate-placement-test` 覆盖记忆的增长、隐藏后重置和竖排不记；macOS CMake 构建和候选相关 ctest 在 Studio 上运行。改完之后在本机重新打字，用诊断日志核对同一次输入里的宽度序列只增不减，这一步见 PR 说明。Windows 和 Linux 的横排候选窗有没有同样的问题没有核对。
