# Agent Note: 安装前同时检查 x86 依赖所需的 VC++ 运行库

Status: implemented

## Problem

完整包在空白 Windows 11 的实际安装中通过了原先只检查 x64 VC++ 运行库的预检，却在注册 x86 TIP 时以 `regsvr32` 退出码 `0x3` 失败并回滚。验收机的 System32 有 VC++ 运行库，SysWOW64 下的 `msvcp140.dll`、`vcruntime140.dll` 和 `vcruntime140_1.dll` 均不存在，两个注册表视图也都没有 x86 运行库登记。TSF 自身使用静态 CRT 不代表旁边的动态依赖也使用静态 CRT，原注释据此前者免检 x86 不成立。

## Decision

安装器复用同一个带版本下限的注册表检查函数，分别检查 x86 与 x64 的运行库键，并对每个架构显式读取两个视图。现代安装包要求两者都存在；`Windows7X86` 仅要求 x86，不要求无法在该系统安装的 x64 运行库。提示提供对应下载链接，静默安装延续原来只写日志、继续执行的既有策略。

完整包验收与此预检修复分别保留构建身份：原产品二进制为 `ffc17be201`，已签名的 WER 注册项修复包为 `231529bbac`；不能把该包上的安装结果称为本次后续预检改动的安装结果。

## Alternatives considered

- 将所有 x86 动态依赖改成静态 CRT：可以减少用户预装组件，但需要切换依赖构建和分发策略，不能用 TSF 本身的编译设置替代对整条动态依赖链的验证。这次保留现有构建，准确提示它实际需要的运行库。

## Consequences

只装了 x64 运行库的用户现在可以在注册失败之前看到缺少 x86 的提示。检查仍通过注册表完成，不依赖会被 WOW64 重定向的文件查询；日志和测试只使用空白验收机及合成数据。缺少运行库时静默安装仍可能按既有策略失败。

源码契约检查通过。另将实际 Pascal 检查函数原样提取，只把 I/O 根替换为合成 HKCU 键，再由实际 ISCC 编译并执行现代与 `Windows7X86` 两种夹具：缺少两个运行库、只有 x64、x86 版本过旧、`Installed=0`、旧主版本、最低版本、新主版本与现代包缺少 x64 均得到预期结果；Win7 x86 分支在没有 x64 时通过。相同夹具替换为 `231529bbac` 的原检查函数后，在只有 x64 的场景实际失败，失败原因为旧实现错误接受缺少 x86。这验证真实 Pascal 逻辑及预处理分支，不宣称在 Win7 系统安装过本次改动。

同一冻结源码的远端完整 `scripts/verify-local.sh --quick`、两条专项和笔记校验均退出 0，覆盖输入前后哈希一致。验证后恢复远端原 `e746981d18` 源码与 107 项原生缓存设置，工作树干净，三份正式 Rust 产物 SHA-256 不变；正式 ABI 继续在创建目录前拒绝测试字段。

验收机经 Microsoft 官方签名和完整文件哈希核对后补齐 x86 运行库；同一 `231529bbac` 安装包的原安装脚本随后完成 x64/x86 TIP 注册、原地升级、数据目录迁移和卸载。这证明原失败与缺失运行库相关，不将旧包的安装通过当作新预检补丁的安装通过。首个下载在传输完成前被签名门禁拒绝，未安装；后一轮运行库安装成功后，夹具错误要求 x86 提供 `vcruntime140_1.dll` 而误报失败，实际 x86 必需文件为 `msvcp140.dll` 与 `vcruntime140.dll`。两轮失败原件保留。
