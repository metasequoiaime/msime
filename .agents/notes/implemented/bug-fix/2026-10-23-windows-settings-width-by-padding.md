# Agent Note: 设置正文的宽度上限靠内边距实现，不是 MaxWidth；上限改为 1800

Status: implemented

## Problem

[正文列限宽 900 并居中](2026-10-21-windows-settings-content-max-width.md)那次改动**从未生效**，而且没人发现：它同时写了 `page.MaxWidth(900)` 和 `page.HorizontalAlignment(HorizontalAlignment::Center)`，而 WinUI 里水平居中会让元素按**自身内容的自然宽度**排版、不再拉伸到可用宽度——于是 `MaxWidth` 永远碰不到，正文宽度实际是卡片内容撑出来的那个值（约 870 DIP）。把 `MaxWidth` 从 900 改成 1400 截图毫无变化，才暴露出来。

那篇笔记的验证写着「1700 × 900 下正文收在 900 并居中」——900 和 870 肉眼难分，截图看上去符合预期，所以错误的结论被当成验证通过。

后果是 2560 的屏幕上最大化后，正文缩成窄窄一条浮在中间，两侧各空出 700 多 DIP。

## Decision

正文面板保持拉伸（**never** 用 `HorizontalAlignment::Center` 配 `MaxWidth`，那会关掉拉伸），把超出上限的部分摊进左右内边距，正文因此居中：

```cpp
const double overflow = width > content_maximum_width ? (width - content_maximum_width) / 2 : 0;
return Thickness{side + overflow, 24, side + overflow, 44};
```

边距本来就按可用宽度算（`content_padding`，窄于 640 时收到 32），只是多了这一项，不新增布局层次，也不依赖对齐方式的副作用。

上限取 **1800 DIP**。2560 的屏幕上正文占七成，两侧各留约 270；900 太窄（占三分之一），再宽则一行里的标签贴最左、控件贴最右，中间拉开上千 DIP，读起来要来回扫。

## Alternatives considered

- **留在 1400** — 比 900 好得多，实测两侧各留 483 DIP。否决：维护者看过实际画面后仍觉得留白太多。
- **完全不限宽，铺满窗口** — 留白最少。否决：这正是 2026-10-21 那次要解决的问题——超宽时一行里标签与控件分踞两端，中间上千 DIP 空白。
- **给行内「标签↔控件」设最大间距，让正文可以铺满** — 真正的根治：行自身紧凑之后，正文列宽不宽就不重要了。没有在本次做：它要改 `add_row` 的两列 Grid，影响每一个设置页的每一行，值得单独一轮并逐页看过。本次先把宽度上限调到可用。
- **按窗口宽度取百分比** — 比固定值更「自适应」。否决：可读宽度有绝对的上界，百分比在超宽屏上会一路放大到同样难读。

## Consequences

- **收益**：最大化后正文占满七成宽度，留白对称且不喧宾夺主；默认 1000 × 780 下版面不变（可用宽度远小于上限，`overflow` 为 0）。
- **代价**：1800 这个上限下，一行里标签与控件之间仍有近千 DIP 空白——行布局本身没改。
- **重访信号**：如果行布局改成控件不贴右边缘，这个上限就可以放宽甚至取消。
- **教训**：`MaxWidth` 与 `HorizontalAlignment::Center` 在 WinUI 里互相抵消。代码里已写明不要改回去。

## Verification

Windows 11、Windows App SDK 1.7.260224002，2576 × 1408 最大化实测：正文列约 1700 DIP（卡片铺到两侧各留约 270），对照 1400 时的 1300、900 版本的约 870。默认尺寸下版面与改动前一致。

构建期间有两次链接失败被误判为成功：运行中的设置窗口锁着 `msime-client-settings.exe`，`LNK1104` 写不进去，而构建输出被 `grep` 过滤掉了这一行。构建脚本现在先 `taskkill` 再编译。
