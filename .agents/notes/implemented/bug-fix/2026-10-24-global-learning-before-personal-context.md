# Agent Note: 全局调频首选优先于个人上下文重排

Status: implemented

## Problem

#9384 在默认学习开启、`promote`、触发次数 1 时，反复选择单码候选后换上文仍回到原首选。空白用户状态不能复现；首次启动引擎前加入合成的 `personal_bigram(丙,甲,10)` 后，Host API 五轮 `l` 选择乙、`wj` 选择丙、再输入 `l`，甲重新占据首位。乙的工作权重和日志均为 14837507，已经超过甲的 14837007；问题发生在正确写回之后的个人上下文重排。计数 0 对照通过，计数 10 和 1000 均失败。实验不读取个人输入或用户词库，也不能证明报告者实际拥有同样的历史。

## Decision

个人上下文重排即将挤掉字典首选时，继续尊重手动置顶；调频开启时，也保护与当前用户覆盖权重日志精确匹配的解码拼音字典首选。匹配条件是 `dictionary=pinyin`、候选的真实词库读音、字面、`operation=upsert` 与当前权重全部一致。其它候选仍按上下文排序，未调频的词库首选仍可被上下文替换。查询复用现有日志和连接缓存，仅在首选即将失位时执行，不新增落盘格式或每键全表读取。

这条契约把已经写进全局词库、当前解码顺序中的字典首选作为优先选择。日志也包含用户编辑、插入和权重重平衡，因此它代表当前词库的用户修改状态，不声称每条 upsert 都由明确选择产生。其它读音、删除、过期权重和非拼音词典的日志不提供保护；频率模式关闭时仍允许上下文排序，手动置顶照常生效。重平衡修改的邻居以后在更窄输入下成为首选时也受保护；手工写回出厂权重仍有 upsert，当前格式没有“恢复自动上下文”的来源标记，因此也受保护。

## Alternatives considered

- 继续让个人上下文覆盖所有普通调频结果：保留最大的上下文适应性，并且与参考实现一致；但与默认全局调频及报告者明确期望冲突，已经写回的首选仍会被旧历史挤掉。
- 自动学习时写手动 `pinned_candidates`：可以准确记录当前编码的显式首选，也最直接复用保护逻辑；但会把普通词频学习变成手动置顶，干扰调频关闭和用户手动操作的独立语义。
- 增加专门的已学习首选持久表：能排除词库编辑或权重重平衡形成的日志；需要格式、迁移、删除、词库换代和同步契约。现有精确匹配能表达当前用户修改后的全局词库首选，先复用它并明确适用边界。
- 整组跳过个人上下文重排：实现最短；会让其余候选失去上下文适应性，保留首选后继续排列其它行。

## Consequences

已经被用户修改或权重重平衡的全局首选会减少上下文替换首位的机会；这是明确的优先级选择。错误或不可读的日志按无匹配处理，不能伪造学习成功。此修改位于共享引擎，宿主实际输入体验与 Android 设备读写要求必须单独报告，不能将 Rust 单测称为全部设备验证。
