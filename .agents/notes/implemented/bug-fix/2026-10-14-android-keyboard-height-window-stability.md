# Agent Note: Android 键盘高度验收等待输入法窗口稳定

Status: implemented

## Problem

API 35 发版验收的 `KeyboardHeightDeviceSmoke` 偶发报告底部留白把键位抬高 777 px，而 40 dp 在该模拟器上应为 105 px。键盘实现只给键区增加 40 dp 的底部内边距；同一套件在本机 API 35 重跑时实际测得 105 px。问题出在测试重启输入法并重新打开编辑器后，UiAutomation 的无障碍树会短暂同时经历旧输入法窗口和新输入法窗口。原测试只要求 `n` 键连续两次读到相同边界，没有把输入法窗口边界纳入稳定条件，可能在窗口切换期间取到两个不同窗口的绝对屏幕坐标。

## Decision

`KeyboardHeightDeviceSmoke` 的底部留白测量同时读取 `TYPE_INPUT_METHOD` 窗口和 `n` 键的屏幕边界，只有键位与所属输入法窗口边界连续四次相同才认为重启后的键盘已经稳定。测量仍比较绝对屏幕坐标，因此真实的 40 dp 位移和键高变化仍会被断言；新增等待只排除输入法窗口切换动画与旧窗口残留造成的跨窗口坐标差。

2026-10-15：[作用域锁释放](2026-10-15-scoped-file-lock-release.md)的完整 API 35 验收在十四键等高测量中得到 `-71 px`，而二十六键为 `602 px`。该分支仍调用只比较节点的通用等待，没有使用本篇的窗口稳定条件。复用同一等待并传入十四键选择器，同时拒绝空矩形及输入法窗口外的过渡坐标；不修改产品键盘高度或放宽高度断言。

## Alternatives considered

- 继续调用通用的 `awaitStableBounds`：实现最小，但它只比较目标节点，无法区分旧窗口和新窗口，正是这次 API 35 发版失败的触发条件。
- 只把等待次数或固定 sleep 调大：可以降低竞态概率，但没有验证窗口本身是否稳定；设备负载变化时仍可能误测，且会无谓拖慢每次测量。
- 修改 `ImeBottomBar` 的 40 dp 实现：本机窗口日志显示未加留白与加留白的键盘窗口顶部正好相差 105 px，产品位移符合策略，修改实现会掩盖测试竞态。

## Consequences

底部留白与十四键等高验收在窗口动画期间会多等待最多约一秒，但跨 API 28/35 的测量契约保持不变。若输入法窗口始终无法连续稳定四次，测试会明确报告窗口未稳定，而不会给出一个看似真实的错误位移。该等待逻辑只用于本套件的重启测量，其他设备套件仍使用通用无障碍等待。
