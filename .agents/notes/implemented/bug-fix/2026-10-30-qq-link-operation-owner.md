# Agent Note: QQ 绑定回执保持操作归属

Status: implemented

## Problem

共享 React 的 `QqLinkCard` 在 `client` 或 `userId` 变化时重置表单，`useAccountAction` 也会作废旧操作。然而绑定的成功、专属错误和解绑成功只检查组件是否挂载，没有检查操作属于哪个账号。旧绑定回执可以清空新账号正在输入的绑定码、关闭新表单或覆盖提示。旧操作还会继续调用 `reload()`；它在调用时重新取当前代次，使旧客户端的列表得到新代次，可能覆盖新客户端的绑定列表。

## Decision

每次绑定和解绑捕获现有 `clientGeneration`，在请求返回和列表刷新返回后检查挂载状态与同一代次。列表刷新接收该操作捕获的代次，不在异步链中重新认领当前账号；失效后不发起后续读取、不修改表单或反馈。首次读取和手动重试仍默认捕获调用时的代次。

## Existing notes audit

检索 `QQ 群助手`、`QQ 绑定`、`useAccountAction` 与账号代次。现有[账号模型](../../implemented/simplification/2026-10-16-account-model.md)持有客户端类型，[账号设置同步卡片](../../implemented/simplification/2026-10-23-account-settings-sync-card.md)持有另一张卡片的异步状态，[账号资料页面](../../implemented/simplification/2026-10-24-account-profile-pages.md)持有资料页边界，均部分相关并保留；Android、iOS 与 Windows 原生账号笔记持有不同宿主，不归并。本篇只处理 QQ 卡片的绑定、解绑和后续读取归属。

## Alternatives considered

- **给卡片按账号加 React `key`，切换时整张重建**：可以隔离新旧组件状态，但旧操作仍可能继续发起列表请求，也不能单靠账号 `key` 覆盖客户端替换。复用已有操作代次可同时守住状态和后续请求，无须改变父级挂载契约。
- **扩大 `useAccountAction.perform` 接口，向所有账号动作传入 `isCurrent`**：可统一检查方式，但本次只缺 QQ 卡片内的代次传递，其他账号动作已有显式守卫；局部修复避免扩大无关接口与调用范围。

## Verification

- 新增七项受控 Promise 回归，覆盖客户端替换、同客户端切换账号、旧绑定成功与失败、绑定或解绑后正在读取列表时切换账号。旧实现七项均失败：新草稿被清空、表单被关闭、旧提示出现或旧客户端被继续读取；修复后 QQ 卡片全部十二项测试通过。
- 新账号的绑定还在等待时，旧失败不能解锁按钮或覆盖反馈；新绑定随后仍能正常完成。既有回归继续覆盖普通绑定、解绑、当前失败提示与重试。
- 账号及通用异步生命周期相关的 47 个测试文件、325 项测试通过；独立审查复跑 QQ 卡片十二项通过，建议隔离客户端与账号两个变化维度，采纳后十二项再次通过。
- 桌面与鸿蒙共享设置生产构建、改动文件 lint 和格式检查、`pnpm run verify-notes`、`git diff --check` 与本地 quick 门禁通过。quick 首轮与单独启动的鸿蒙构建争用同一输出目录，报产物不存在；停止并行构建后整套门禁通过，未修改产品代码规避。
- quick 覆盖仓库契约、Rust 工作区、Android 目标与共享 Apple 桥。Linux 桌面检查因无 Docker、Windows 原生宿主因未配置交叉工具链、鸿蒙 ArkTS 真打包因缺少暂存输入而跳过，其余原生阶段按范围跳过；本次没有设备或真实账号验收。

## Consequences

新账号的草稿、列表、反馈和忙碌状态不再受旧 QQ 操作影响。代码增加局部归属检查，复用已有代次与账号操作层，不改变客户端接口、绑定流程或存储格式。

已经发给宿主的绑定或解绑请求不能撤回，本次只阻止过期回执和后续读取影响当前页面。测试使用合成绑定码和客户端，不调用真实账号或 QQ 群助手，也不代表原生设备验收。
