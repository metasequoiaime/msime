# Agent Note: 个人上下文重排保持匹配编码和读音边界

Status: implemented

## Problem

#10323 报告全拼上屏一个字后输入 `gei`，较短读音的「个」排到完整读音的「给」前。干净状态的当前锁定词库，经完整 runtime 和模型测试，无上文或以「我」为外部上文时首选均为「给」，不能据此声称已经重现报告者的个人状态。

共享引擎中有一条能复现同类现象的确定路径：`personal_rerank::leading_group_len` 只检查字典来源和字数，把完整读音与较短读音的单字候选并入同组。存在较强的个人二元关系时，上屏后触发的个人上下文重排会把短读音提到第一位。合成会话用 `hao` 的「子」、`gei` 的「甲」和 `ge` 的「乙」，只在隔离日志中注入「子→乙」32 次，旧实现从正确首选「甲」变成「乙」。不需要神经模型、模糊音或纠错。

## Decision

个人上下文只重排首个连续的同字数、匹配编码消耗相同字母数（不计音节分隔符）的字典组。全拼下组首的匹配编码已经等于其完整真实读音时，候选还必须与组首具有相同真实读音，或者自身也是这串字母的另一种完整切分；例如 `fangan` 的 `fan'gan`（反感）与 `fang'an`（方案）同组重排，`gei` 下匹配 `ge` 的短读音因少消耗一个字母不进组。候选的 `pinyin` 决定提交时消耗的编码，`canonical_pinyin` 标识词典读音。简拼和双拼的匹配编码本来就可以指向多个完整读音，不能额外收紧成某一个读音；例如小鹤单码 `l` 下的 `lai` 和 `le` 继续允许上下文重排。双拼的匹配编码是按键序列而不是拼写出的读音，零声母单键 `a`、`e`、`o` 与 `a`、`e` 等读音字面相同只是巧合，因此读音保护只在全拼方案下生效。遇到边界便停止，不跨过其它组搜索后续同音候选。

既有最多 16 项的栈上排序、同音词的上下文适应、手动固定与匹配调频日志的首选保护继续沿用。不删除较短读音候选，不改用户词库或出厂默认值，也不把所有神经重排规则一并改变。

## Alternatives considered

- **关闭个人上下文。** 能避免此路径且代码最少，但会同时取消正常同音候选的个性化排序；保留功能，只收紧错分的候选组。
- **无条件比较真实读音。** 能直接隔离短读音，但首次全量测试发现它破坏小鹤单声母 `l` 的既有跨读音学习；这类输入的读音本来未确定。只在组首已经由匹配编码完整拼出时额外保护真实读音。

## Verification

合成会话回归在旧实现精确运行 1 项、失败 1 项，失败发生在上屏上下文后的首选断言；相同会话无上下文时的完整读音首选及短读音仍可见的断言已通过。另新增低层边界回归，分别覆盖匹配编码不同、真实读音不同及两者都不同。最终收窄实现的 `cargo test -p msime-engine` 通过：库测试 2896 项通过、57 项按既有规则忽略，golden 31 项、数据集 3 项与线程 3 项通过。`cargo clippy -p msime-engine --all-targets -- -D warnings` 通过，小鹤单声母跨读音学习的既有回归也通过。远端 macOS 的 `bash scripts/verify-local.sh --quick` 通过，覆盖工作区、Android／wasm 交叉检查、Android Java、macOS 原生宿主及 Apple 桥；缺少 node／pnpm、Docker、MinGW 与完整 Harmony 工程的阶段按脚本跳过，笔记校验在本机另外通过。`cargo fmt --all -- --check`、`pnpm run verify-notes` 与 `git diff --check` 通过。

评审后改为按消耗字母数分组并只在全拼下保护读音：`fan'gan`／`fang'an` 低层与会话回归、双拼零声母单键 `a` 回归均已加入，两项完整切分回归在改前的匹配编码分组下失败、改后通过；`cargo test -p msime-engine`（库测试 2899 项通过、57 项忽略，golden 31 项、数据集 3 项与线程 3 项通过）和 `cargo clippy -p msime-engine --all-targets -- -D warnings` 通过。

## Consequences

以前跨读音的个人关系不再用于当前首组排序，但学习记录保留，输入对应读音时仍可生效。此修复证明并阻止共享引擎中的确定路径，报告者的 macOS 个人数据未读取、未修改，仍需在合并后复验其原环境。
