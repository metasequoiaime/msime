# Agent Note: Windows 原生设置窗口复用现有实例

Status: implemented

## Problem

Windows 0.3.0 的用户截图显示多个设置窗口重叠。现代 WinUI 与 Win7 原生设置入口都在每次进程启动时创建窗口，没有进程实例守卫；托盘、首次准备、开始菜单和页面路由重复启动设置程序时都能继续增加窗口。Server 的生产实例锁只约束 Server，不能约束独立的设置宿主。截图本身不能确定每一次重复启动来自自动触发还是用户点击。

## Decision

两个原生设置入口共用 `SettingsInstance`，在初始化 UI 之前获取按系统登录会话、用户 SID 和产品版本隔离的命名互斥体，持有至进程退出。原实例初始化期间的后续启动等待它发布激活窗口，超时或通信失败返回失败，不绕过互斥体新建窗口。原实例退出或异常终止后，新启动可获取锁。

后续启动通过隐藏的原生顶层窗口转发最多 64 字节的 `settings` 路由。接收端验证消息标识、字节数、终止符和路由词汇，并在已有 UI 线程执行导航；裸 `settings` 保留当前页面，带页面的请求切换页面与原有别名标签，然后恢复最小化窗口并请求前台。入口不接收文件路径、环境变量或任意执行命令。面板进程和游戏兼容配置辅助入口保持原有生命周期。

## Alternatives considered

- **只在 Server 的启动函数里去重。** 改动集中，也能覆盖托盘，但开始菜单和直接运行设置程序不经过 Server，首次打开还存在初始化竞态，因此实例约束放在设置宿主入口。
- **发现已有互斥体就退出。** 能阻止叠窗，但会吞掉「关于」「语音」「帮助」等页面请求，也无法恢复最小化的窗口，因此仍将路由交给现有实例。
- **采用 Windows App SDK 的实例重定向。** 现代 WinUI 可以复用 SDK，但 Win7 宿主不依赖该运行时；两个宿主共用 Win32 互斥体和有限消息契约，避免维护两套不同的启动语义。

## Consequences

重复启动只留下一个设置窗口，页面路由继续有效，异常退出不留下磁盘锁文件。代价是后续进程在首个 UI 初始化期间最多等待十秒，向已存在的 UI 发送消息最多等待两秒；窗口无响应或系统拒绝消息时不再打开替代窗口。互斥体按产品版本隔离，不会阻止不同版本各自打开设置。

## Verification

`windows-settings-instance` 使用真实 Win32 窗口和子进程，覆盖初始化期间的八次启动、页面请求、最小化恢复、非法路由、不同版本隔离、关闭后重新启动、初始化超时和废弃互斥体接管。在 Windows 交互会话中以 MSVC `/W4 /WX` 构建并运行通过，MinGW `-Wall -Wextra -Werror -fsyntax-only` 也通过。SSH 非交互桌面无法证明窗口可见和恢复，窗口断言以交互会话的结果为准。

现代 WinUI 与 Win7 设置均以同一提交的 `msime-host-api` 完成 MSVC 构建。在 Windows 验证机的各自实际宿主中（Win7 兼容宿主运行于当前 Windows 系统，未在 Windows 7 系统验收），合成状态目录下连续启动八次，后续进程均成功退出、原窗口句柄保持不变、最小化恢复并显示「关于」页，关闭后重开通过。现代页由 UI Automation 的 `settings-page-about` 确认，Win7 由原生页面选择控件确认。`ctest` 中 `windows-settings-instance` 和 `windows7-routes` 均通过。没有执行安装包安装或发版。
