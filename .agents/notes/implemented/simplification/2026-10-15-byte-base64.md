# Agent Note: 共享 UI 的字节 Base64 编码

Status: implemented

## Problem

词库导入的 `bytesToBase64` 与皮肤预览的 `skinImageUrl` 各自把字节拼成二进制字符串再交给 `btoa`。词库按三个字节的倍数分块编码，图片按 32768 个参数分块后拼成整段字符串再编码；两处在不同业务模块维护相同编码职责。

## Decision

内部叶子模块 `core/base64.ts` 持有分块编码，接受 `Uint8Array` 或只读数字数组，按 `3 * 8192` 字节构造短二进制串再逐块 `btoa`，仅最后一块可能产生填充。按索引读取输入，避免为了复用而复制整份图片数组。`dictionary-file.ts` 保留原 `bytesToBase64` 导出并供 `readScelFile` 使用；`skinImageUrl` 在原有类型与字节校验之后调用公共编码器。

编码器不接管 MIME、字节上限、图片读取或 hook 生命周期；空图片仍按既有规则生成空 Base64 数据 URL。触屏图片压缩已有 Base64，不需要在此解码再编码。

## Historical audit

检索 `base64`、`bytesToBase64`、`skinImageUrl` 和图片字节：已有[细胞词库导入](../feature/2026-10-13-scel-import.md)持有分块编码要求，部分重叠并互链；Windows 社区 Host API 的 Base64 是 Rust 与 C++ 传输格式，与前端实现独立；百炼语音及 Android 图片发送属于其他编解码链路，无关。未发现同等公共编码器。

## Alternatives considered

- **皮肤直接导入词库模块的编码器。** 完全复用已验证实现、改动最少，但让图片预览依赖整份词库解析模块，公共叶子模块能保留原方向。
- **统一转 `Uint8Array` 后调用原函数。** 原算法可以不改，但每次皮肤编码都额外复制最多 8 MiB 数据；索引读取两类输入只需修改分块遍历。
- **改用原生 `Uint8Array.toBase64`。** 可以避免二进制字符串，但会扩大原生 WebView 的 API 兼容要求，本片沿用两处已有的 `btoa`。

## Consequences

词库和图片共用字节编码，标准字母表、填充、空输入和图片校验保持原语义；图片也按块编码，不再先构造整段二进制串。代价是新增内部模块；编码器要求输入为字节，MIME 和大小检查仍由业务调用者负责。分块长度必须是三的倍数，避免中间块出现填充。

纯函数测试用固定向量和整段一次 `btoa` 的参照结果核对数字数组、类型数组、全部字节值、分块边界、3 MiB 输入和带偏移视图；皮肤回归核对空图片、跨块数据 URL 和原有非法输入拒绝。既有词库大文件编码与导入测试继续覆盖原导出路径。

浏览器 API 契约参见 [HTML btoa 规范](https://html.spec.whatwg.org/multipage/webappapis.html#dom-btoa-dev)和 [MDN 文档](https://developer.mozilla.org/en-US/docs/Web/API/Window/btoa)。
