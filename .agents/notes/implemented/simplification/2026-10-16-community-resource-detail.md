# Agent Note: 社区资源详情与动作独立复用

Status: implemented

## Problem

词库与回复模板的详情是整页图库里的私有函数，持有加载、收藏、导入、评分、举报、下架和编辑后刷新。其他共享入口无法单独展示详情，动作生命周期的验证必须经过列表导航。

## Decision

`use-community-resource-detail.ts` 持有原有状态与动作，客户端只要求详情动作；`community-resource-detail.tsx` 持有界面、能力显示条件和编辑器接线，客户端另外要求发布能力。页面通过新组件展示详情，公共包入口导出组件与 props。保留各操作顺序、逐步 owner 与 mounted 检查、同步防重、错误格式、提示和发布刷新闭包，不引入额外取消语义。

初始详情和发布后的后台刷新额外共享 `refreshGeneration`。每次后台刷新推进序号，用户操作被同步防重守卫接受时也推进序号，使操作之前已经发出的后台读取立即失效；同一客户端的收藏、评分和新版本结果不会再被旧详情或旧错误覆盖。后台回包同时校验客户端、资源 ID 的 owner 代次、挂载状态和刷新序号。过期发布刷新失败被消费，当前刷新失败继续向编辑器调用方传播。操作仍使用独立的公共 runner，不把刷新编号当作操作取消条件。

详情的本机导入入口复用 `canInstallCommunityDictionary`，与安装操作和图库采用同一能力判断：只提供 `installCollection` 或只提供 `import` 都显示按钮，两者均无时隐藏。宿主只支持命名词库时也能执行已有安装操作，按钮仍按详情展示版本安装并保留原有提示。

## Alternatives considered

- 只移出完整详情组件：可以直接复用界面且接线较少，但无界面调用和生命周期测试仍依赖整份 JSX，因此同时分离状态 hook。
- 直接共用 `addCommunityReply` 执行详情里的收藏与添加：已存在且可以删掉连续步骤，但详情在每一步等待后检查 owner，避免切换后继续下一步；通用添加操作没有这个职责，保留详情原有步骤和逐步守卫。
- 详情回包只检查客户端与资源 ID：状态较少且可处理切换页面，但同一 owner 的首次请求与操作后读取仍可乱序完成，旧收藏、评分和版本会覆盖新结果，因此另加后台刷新序号。
- 初始详情加载完成前禁用操作：可以阻断首次加载与修改的交错，但会让本来可直接使用列表副本的页面等待网络，且不能解决发布后刷新与后续操作的交错，因此保留可操作的详情副本并校验回包顺序。
- 在详情里单独扩写两种安装能力的条件：改动直接，但安装工具已经持有相同规则，继续手写会让入口与实际安装能力再次分叉，因此直接复用公共判断。

本机安装入口回归覆盖未提供宿主、空能力对象、仅命名词库和仅逐条导入：仅命名词库场景在修复前因找不到按钮失败，修复后能点击安装并显示对应提示，且不会调用云端导入。详情组件、状态与资源操作 3 文件 48 项通过，桌面生产构建、HarmonyOS 类型检查、lint、格式和 notes 检查通过。

## Consequences

详情和状态可脱离图库使用，页面仅控制选择与返回历史；界面与 hook 多一层动作接线，需要原页面测试和机械比对确认。状态初始化与客户端、资源 ID owner 规则原样保留，不扩展重新初始化策略。后台刷新多维护一个请求序号与共享判断；操作开始后不再接受此前详情和错误，列表副本保持到操作后的重读完成。详情每一步等待后的守卫继续存在，旧请求仍只丢弃过期界面结果，不新增取消宿主操作的语义。

本片不改变宿主读写、权限、Android 资源或协议，不把共享前端验证称为设备验收。
