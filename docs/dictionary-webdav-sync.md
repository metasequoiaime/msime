# 「我的词条」经 WebDAV 网盘同步

用户可以把「我的词条」存在自己的 WebDAV 网盘上（坚果云、Nextcloud 等），在几台设备之间同步。网盘上只有密文，网盘本身没有能运行的逻辑：每台设备读写网盘上的一份只追加的事件日志，按日志算出同一个结果。设计取舍见 [决策笔记](../.agents/notes/implemented/feature/2026-10-27-dictionary-self-hosted-sync.md)，对应 #9880。

这份文档的「存储布局」「记录」「合并」三节是契约：任何实现（各平台的客户端、以后的工具）都按它读写网盘上的文件。

## 同步什么

- **同步**：用户在「我的词条」里看到的那些词条——Engine 日志里 `user_inserted` 的词条，包括用户自己加的、导入的、MCP 加的，也包括打字时 Engine 自动造的词（Engine 不区分这两种，列表里也不区分）——以及它们的删除。一个词条的身份是（词库类别、编码、词），词库类别是 `pinyin`、`wubi`、`wubi98`、`quick`、`english` 之一。改编码就是删掉旧词条、加上新词条。
- **不同步**：打字学到的权重、候选顺序、固定位置和选择次数；主词库和对主词库词条的删除或改权重；用户命名的词条集合（集合里的词照样作为词条同步，集合本身的名字、开关和来源不同步）；模型、皮肤、剪贴板、输入记录和凭据。
- 收到的新词以默认权重写进本机词库，本机已经有的词保留本机的权重。

## 客户端怎么配置

偏好文档里的 `dictionary_sync_webdav`：

```json
{"dictionary_sync_webdav": {"url": "https://dav.jianguoyun.com/dav/", "username": "<网盘账号>", "password": "<应用密码>"}}
```

- 三项要么都空（不同步），要么都合规；没配置时这个键不写进文档。规则与 [云剪贴板的网盘](cloud-clipboard-webdav.md) 相同：`https://`（`http://` 只接受本机回环），不带查询串、片段和用户信息，不跟随重定向；账号 1 到 256 字节、不含冒号和控制字符，应用密码 1 到 256 字节。与 `cloud_clipboard_webdav` 各配各的，可以是同一个网盘账号。
- 应用密码列在凭据清单里，账号在诊断快照里也换成 `<redacted>`；整组不随设置文件导出（`LOCAL_SECTIONS`）、不进账号设置同步，MCP 的偏好白名单也不包括它。
- 保存之前先「测试连接」（`probe`，见下文），不通过不保存。
- 设备身份绑定基地址和账号：换了地址或账号就是一台新设备、要重新批准；换应用密码不换。

## 宿主怎么接入

C 入口是 `msime_client_dictionary_sync`，一个按 `operation` 分发的 JSON 请求，格式和错误码见 `crates/host-api/include/msime_client.h`。宿主要做的只有这几件：

- **给一个目录**：放本机同步状态、词库密钥串和锁文件的绝对路径目录，同一台设备上的输入法、设置应用和面板要给同一个（否则会登记成几台设备）。里面有词条明文，放在应用私有、不备份的地方：桌面端可以是账号目录旁的 `dictionary-sync/`，Android 是 `noBackupFilesDir/dictionary-sync`，iOS 是 App 和键盘扩展共用的 App Group 容器里的 `dictionary-sync/`，HarmonyOS 是应用私有目录。
- **按时调用 `run`**：用户改词之后马上以 `local_change` 调一次（记录本机改动，通常不联网，例外见下文「触发」）；打开设置应用或词库页时以 `opened` 调；之后按上一次结果里的 `next_check_ms` 以 `periodic` 再调；「立即同步」按钮是 `manual`。要不要联网、额度够不够都由 Rust 决定，宿主不用自己算防抖和退避。都在工作线程上调用。
- **设置界面**：网盘地址、账号和应用密码（遮罩、留空沿用、测试连接通过才保存），本机的核对码和等待批准的设备（`devices`、`approve`、`reject`、`remove`，与云剪贴板的设备管理同一种形状，可以复用那套界面），状态（`status`：上次同步时间、待发送和待写入的数量、错误），被挡下的大批删除的两个选择，以及很少用到的「重置密钥」和「以本机为准重新开始」。

写本机词库时 Rust 每批取一次 Engine 的独占维护权；Linux、macOS、Windows 在 `manual`、`opened` 和设备操作时会请输入法让出词库（50 毫秒间隔、2500 毫秒预算、租约 30 秒；macOS 设置应用在租约挂上时还经分布式通知立刻叫醒 IMK，与设置页改词时相同，`request_json_announcing`），自动同步和移动端不打扰输入会话，词库忙就留到下一次。所以在桌面端，别处的改动通常在打开设置或者没有输入会话占着词库的时候写进来。

| 宿主 | 状态 |
| --- | --- |
| Windows（含 Win7） | 已接入。目录是本用户的 `%LOCALAPPDATA%\<本版本的用户目录>\dictionary-sync`（`platforms/windows/common/DictionarySyncDirectory.h`），Server 和设置窗口共用。Server 在候选窗口删词后以 `local_change` 记一次，按 `next_check_ms` 以 `periodic` 再调（`src/system/DictionarySyncWorker.cpp`，只在受管理的 Server 里）；WinUI 设置在词库页「云端词库」标签、Win7 在词库同步面板（`--route=dictionary-sync`，从设置窗口词库页打开）里配置网盘、看状态和设备，进入时 `opened`、「立即同步」`manual`，经设置改了词之后 `local_change`。密钥串身份冲突（`clipboard_keystore_conflict`）时宿主重试 |
| macOS、Linux | 共享 React 设置页「词库」→「管理词库」里的「词库同步」与「词库同步设备」两组；Tauri 设置应用的 `dictionary_sync` 命令在阻塞线程上调 `msime_host_api::dictionary_webdav::request_json`（C 入口的同一个实现），HostOptions 取词库命令用的那份，目录是账号目录下的 `dictionary-sync/`：macOS 是输入法与设置应用共用的 `~/Library/Application Support/<设置应用 bundle id>/dictionary-sync`，Linux 是 IBus、Fcitx5 和设置应用共用的状态目录（通常 `~/.config/msime-client`）下的 `dictionary-sync`。输入法进程（IMK、IBus、Fcitx5）不调用，见下文「触发」 |
| HarmonyOS | 同一个共享设置页（手机在「词库」页直列，2in1 在「管理词库」标签），经 `startRequest` 的 `dictionary_sync` → `HarmonyAccountCloudBridge.dictionarySync` → NAPI `dictionarySync`（工作线程）；目录是设置应用沙箱的 `files/state/dictionary-sync`；除 `status` 外都要隐私政策的授权。键盘扩展不调用，见下文「触发」 |
| iOS | 设置 App「词库 → 词库同步」：网盘填写页（测试连接通过才保存）、状态与「立即同步」、核对码和设备批准、被挡下的大批删除、重置密钥、以本机为准重新开始和停止同步。App 回到前台时 `opened`，在前台时按 `next_check_ms` 以 `periodic` 再调，进后台就停；键盘扩展在应用了 App 排队的编辑或候选栏删除词条之后以 `local_change` 记录，只在有完全访问、App 已经用这个网盘同步过（目录里已有同步状态和密钥串）、状态文件不超过 2 MiB 时才调，否则留给 App。目录是 App Group 容器里的 `dictionary-sync/`（0700、首次解锁后的文件保护、不进备份），密钥串是 Rust 在里面写的文件，App 和键盘共用同一份和同一把锁 |
| Android | 设置 App「我的 → 词库同步」（词库页也有入口）和 `:ime` 键盘进程的触发已接入，见下文 |

Android 的接法（`platforms/android`）：

- JNI 是 `NativeClient.dictionarySync`（`msime_client_dictionary_sync`，请求上限 2 MiB），Java 这一层是 `DictionaryWebDavSync`；两个进程给的目录都是 `noBackupFilesDir/dictionary-sync`，HostOptions 是 `runtime-options.json` 那一份。
- 设置页（`home/DictionarySyncPage`）：网盘地址、账号和应用密码在对话框里填，应用密码不回显、留空沿用已存的；「测试连接」只测不存，「保存」先测、通过了才写进偏好，没通过时对话框和草稿都留着。打开这一页时以 `opened` 同步并读设备，「立即同步」是 `manual`，都在工作线程上。状态、被挡下的大批删除（「同步删除」「从网盘恢复」）、本机核对码、等待允许的设备（允许 / 拒绝）、已允许的设备（移除）、「重置密钥」和「以本机为准重新开始」都在这一页，移除、重置和重新开始先确认。
- 键盘进程（`core/ImeDictionarySync`）：候选栏删除之后、设置页排进队列的改词被键盘写进词库之后以 `local_change` 调；之后按 `next_check_ms` 以 `periodic` 定时，键盘收起（输入会话刚结束）时如果还有没写进本机的远端改动就马上再来一次。调用在它自己的一条工作线程上，不在输入线程上，也不排在建会话用的线程后面；定时用主线程的 Handler（与键盘已有的个人词库维护相同，没有拿 WorkManager 排任务），进程被回收时定时跟着没了，下一次键盘起来再接上。输入会话开着时 Rust 拿不到词库维护权，这一轮不写，等会话结束。
- 设备身份：一个安装只有一份词库密钥串，在共用目录里由 Rust 在锁里「读不到才生成」。键盘进程还多守一条：本机还没有设备编号时不跑，第一次登记只由设置页（打开或保存之后的 `opened`）做。这份密钥串由 Rust 存成只有本应用能读的文件，不像云剪贴板的中继密钥串那样由 Java 用 AndroidKeyStore 加密，因为这个入口没有让宿主保管密钥串的接口；noBackupFilesDir 不进云备份和设备间迁移。

目录不能直接用账号目录或 `files/state` 本身：云剪贴板的中继在那里放着 `cloud-clipboard-relay-keystore` 和 `cloud-clipboard-webdav-state`，词库的密钥串和它的网盘缓存用的是同样的文件名，放在一起会互相覆盖，所以一律是下面的 `dictionary-sync/` 子目录。

### 触发

共享设置页（`packages/ui/src/settings/use-dictionary-sync.ts`）替用到它的宿主排触发，宿主只提供 `dictionarySync.request(action)`：

- 设置打开、并且已保存的偏好里配置了网盘时以 `opened` 调一次；保存了新的网盘配置（测试连接通过之后）也再调一次。
- 之后按每次结果里的 `next_check_ms`（限在 1 秒到 30 分钟之间）以 `periodic` 再调，直到设置关掉。
- 经设置改了词（单条编辑和删除、导入、个人词库文件导入、失败重试、命名词库的增删改与启停、装社区词库、清除学习数据）成功之后以 `local_change` 调；连续几次只排一次。
- 「立即同步」和被挡下的删除的两个选择是 `manual`。
- 所有请求排成一队依次发出，Rust 那边整次同步本来就持有一把文件锁。

`local_change` 并不总是不联网。它把这次改词记成「最后一次改词」，所以一分钟的防抖在这一次总是还没到；但本机改动从第一处没发出去的算起已满十分钟（一直在改时防抖的上限）、并且离上一次发送已满五分钟时，发送已经到期，Rust 在这一次就联网拉取并发送（仍受退避和自动额度限制，`client-core` 的 `a_local_change_sends_at_once_once_unsent_edits_are_ten_minutes_old` 覆盖）。所以它要和其他触发一样放在工作线程上，鸿蒙也把它算作要授权的请求。

macOS、Linux 与 HarmonyOS 的输入法进程不触发同步。macOS 的 IMK、Linux 的 IBus 和 Fcitx5 里没有现成的同步类后台工作可以挂（它们只有遥测的定时上传），打字时 Engine 自动造的词、候选栏里删掉的词和输入法自带词库窗口里改的词，由下一次设置应用的 `opened`、`periodic` 或任何一次同步开头的核对记下来，不会丢，只是要等设置应用打开时才发出去；别的设备的改动同样在设置应用打开时才写进本机词库。鸿蒙的键盘扩展在 API 12 起的独立沙箱里，读写的是它自己那份个人词库（`user/` 不经共享沙箱交换，见 `platforms/harmony/README.md`「输入法扩展的独立沙箱」），而这个入口没有云剪贴板那样「只用已有设备身份」的开关，键盘一调就会登记成同一台手机的第二台设备，所以键盘不调；鸿蒙同步的是设置应用那一份「我的词条」，网盘来的词要等两份个人词库接上之后才进键盘。`scripts/test-harmony-dictionary-sync.py` 守着这一点。

## 存储布局

用户选一个文件夹作基地址（通常就是网盘根目录，例如坚果云的 `https://dav.jianguoyun.com/dav/`），客户端只在它下面的 `msime-dictionary/` 里读写，与云剪贴板的 `msime-clipboard/` 互不相干：

```text
<基地址>/msime-dictionary/v1/format.json
<基地址>/msime-dictionary/v1/tmp/<Unix 秒>-<32 位十六进制>.json
<基地址>/msime-dictionary/v1/epoch-NNNNNN/checkpoint.json
<基地址>/msime-dictionary/v1/epoch-NNNNNN/e-NNNNNNNNNNNN.json
<基地址>/msime-dictionary/keyring/                 （词库自己的密钥串，见「密钥与设备批准」）
<基地址>/msime-dictionary/probe-<16 位十六进制>/    （只在「测试连接」时短暂存在）
```

- `format.json` 是 `{"format":"msime-dictionary","version":1}`。不认识的格式或版本，客户端报 `dictionary_sync_unsupported`，不读也不写。
- epoch 编号 6 位、事件序号 12 位，都是左补零的十进制；序号跨 epoch 连续递增。文件名里只有编号，不出现设备、词或编码。
- 客户端从不删除 `msime-dictionary/`、`v1/`、`tmp/` 和 `keyring/` 本身（坚果云不许删除根目录下的文件夹），会被删除的只有旧的 epoch 目录、临时文件和探测目录。

### 写入：抢下一个序号

一个事件就是一个不可变文件。写入的设备在它读到的最后一个序号 `n` 上，把事件独占创建为 `e-<n+1>.json`；谁先创建出来谁的写入算数，没抢到的设备重读日志后再试（最多 6 次）。独占创建与云剪贴板相同：先 `PUT` 到 `tmp/` 下一个唯一的临时名，再 `MOVE` 到目标并带 `Overwrite: F`，201 或 204 是抢到了，409 或 412 是没抢到。不用 `PUT If-None-Match: *`：坚果云不理会这个头。见 [云剪贴板的 WebDAV 后端](cloud-clipboard-webdav.md)。

### 读取

客户端在本机记着读到的 epoch、序号、链头（最后一个事件文件字节的 SHA-256）和由此算出的共享状态。一次读取是对当前 epoch 目录的一个 `PROPFIND`（Depth 1），然后按序号 `GET` 新事件、依次接上：

- 下一个事件的 `prev` 必须等于本机记得的链头，否则是 `dictionary_sync_rollback`。
- 列出来的序号中间有缺口（列表还没跟上）时读到缺口为止；但本机读过的最后一个事件从列表里消失了、或者列出了更大的序号而下一个序号直接 `GET` 也不存在，就是历史被删过，同样是 `dictionary_sync_rollback`——更大的序号只能在下一个序号写好之后才写得出来。
- 读到封口事件就进入下一个 epoch；当前 epoch 目录已经不存在（被压缩删掉了）时从网盘上最新的检查点重新开始。

## 记录

### 事件文件

事件文件是 JSON，头部是明文：

| 字段 | 含义 |
| --- | --- |
| `format`、`version` | `"msime-dictionary"`、`1`。版本不认识的事件跳过 |
| `seq` | 序号，必须与文件名相同 |
| `prev` | 上一个事件文件字节的 SHA-256（小写十六进制）；第一个 epoch 的第一个事件是 64 个 `0` |
| `at` | 写入设备的 Unix 秒数 |
| `type` | `ops` 或 `seal` |

`ops` 事件另有 `key_id`（这个 epoch 的密钥编号，32 位小写十六进制）和 `box`。`box` 是 `"v1." ‖ base64url(nonce ‖ XChaCha20-Poly1305(子密钥, nonce, 明文, aad))`，nonce 24 字节随机，aad 是 ASCII 字节：

```text
"msime-dictionary-v1-event" ‖ 0x00 ‖ seq ‖ 0x00 ‖ prev ‖ 0x00 ‖ at ‖ 0x00 ‖ key_id
```

（数字写成十进制。）改动头部的任何字段都会让解密失败。明文是 JSON：

| 字段 | 含义 |
| --- | --- |
| `device` | 写入设备在词库密钥串里的编号（32 位小写十六进制） |
| `ack` | 这台设备的本机词库已经持久地写到了哪个序号（不能超过 `seq - 1`，超过时按 `seq - 1` 算） |
| `ops` | 操作，每条是 `[类别, 编码, 词, 时间戳, 是否存在]`，最多 1000 条，明文最多 256 KiB |
| `retire` | 可选，用户移除了的设备编号 |

一条操作的编码必须已经是规范写法（见下文），时间戳在 2^10 到 2^53 - 1 之间，否则只跳过这一条。

`seal` 事件另有 `next_epoch`（当前 epoch 加一），不加密，不需要密钥就能写；可选的 `upgrade` 是迁移到的新格式版本，这一版读到它就停下（`dictionary_sync_unsupported`），这是正在运行的客户端得知格式升级的方式。

### 跳过的规则

解析不了、序号与文件名不符、版本不认识、`key_id` 不是这个 epoch 的、解不开、明文不对、操作超过 1000 条的事件，照样占用这个序号、接上哈希链，但不改变状态。所有持有密钥的设备都这样跳过它，一个坏文件不会卡住日志。没有这个 epoch 密钥的设备停在这里等（等待批准或换钥）。

### 检查点

`checkpoint.json` 是一个 epoch 开始时的完整共享状态：

```json
{"format":"msime-dictionary","version":1,"epoch":3,"seq":130,"head":"…","generation":1,"lineage":"…","key_id":"…","box":"v1.…"}
```

- `seq`、`head` 是它接着的那个封口事件的序号和哈希；第一个 epoch 是 `0` 和 64 个 `0`。
- `generation` 是密钥换过、日志重建过几次，只增不减；`lineage` 是这份共享词库的编号（16 字节随机数的十六进制），第一台设备建日志时生成，换钥和压缩都不变，只有「以本机为准重新开始」时换。
- `box` 的子密钥是检查点那一把，aad 是 `"msime-dictionary-v1-checkpoint" ‖ 0x00 ‖ epoch ‖ 0x00 ‖ seq ‖ 0x00 ‖ head ‖ 0x00 ‖ generation ‖ 0x00 ‖ lineage ‖ 0x00 ‖ key_id`。明文是 `{"writers":[设备编号…],"devices":[[设备编号, 确认位置, 最后出现的时间, 是否已移除]…],"entries":[[类别, 编码, 词, 时间戳, 写入者在 writers 里的下标, 序号, 是否存在]…]}`，各表按设备编号或（类别、编码、词）排序，同一个状态写出的明文相同。
- 读检查点时逐项核对：规范的词条、合法的时间戳、不超过 `seq` 的序号和确认位置、不重复的键、最多 30 万个词条、最多 64 台设备。不合规的整份不认（`dictionary_sync_corrupt`）。

### 词条的规范写法

与 Engine 写入个人词库时相同：编码转成小写 ASCII；拼音的空格换成 `'`，是用 `'` 隔开的非空小写字母音节；五笔（两版）1 到 4 个字母；快捷短语 1 到 32 个字母或数字；英文最多 64 个字母、`-` 或 `'`；编码最多 512 字节。词不能为空、最多 4096 字节，不含控制字符（快捷短语可以有换行和制表符）。词本身不做 Unicode 规范化：码位不同就是不同的词条。拼音音节是否存在、个数是否与字数相同由 Engine 写入时判断，Engine 不收的词条本机不再重试，直到它的共享值变了。

## 合并

每个词条是一个「最后写入者胜」的寄存器，删除也是一次写入（墓碑）。两次写入按（时间戳、设备编号、是否存在）比较，大的胜；时间戳相同时设备编号大的胜，同一台设备的同一时间戳「存在」胜过「删除」。比较只看操作自己带的值，与它们到达网盘的先后无关：同一组操作按任何顺序、重复任意次合并，结果都一样。

时间戳是混合逻辑时钟：高位是 Unix 毫秒、低 10 位是计数，整个值不超过 2^53 - 1（JavaScript 能精确表示）。本机的下一个时间戳比它发出或收到过的都大、并且不早于本机时间；见过的最大值随同步状态原子写盘，所以重启、系统时间往回调都不会发出更小的时间戳。收到的时间戳比本机时间快一天以上时只在状态里提示时钟不准，合并照常。重装的设备是一个新的设备编号，第一次加入时先读完日志、推进时钟再记录本机的词。

合成示例（都由 `cloud::dictionary_sync` 的模拟测试验证）：

| 情形 | 结果 |
| --- | --- |
| B 10:00 把「水杉」的编码从 `shui'shan` 改成 `ss`，A 10:05 删除 `shui'shan` 的「水杉」；两台都离线，谁先上传都一样 | `shui'shan` 删除，`ss` 保留：A 删的是旧词条，改编码得到的是另一个词条 |
| B 删除「水杉」又在 10:10 加回来，A 10:20 删除它 | 删除（A 的更晚） |
| A 10:10 删除，B 10:20 加回来 | 保留（B 的更晚） |
| A、B 同时把 `shui'shan` 改成不同的编码 | 两个新编码都保留，旧的删除 |

### 第一次加入

一台设备第一次加入（或者共享词库被另一台设备重建过之后重新加入）时：本机已有的词都保留；共享词库里没有的（包括那边删过的）作为新词发出去；共享词库里有、本机没有的写进本机。第一次加入从不删除本机的词。

### 墓碑回收与压缩

一个 epoch 里攒到 64 个事件或 8 MiB 时，写入的设备封口：一个 `seal` 事件抢下一个序号，然后建下一个 epoch 的目录、独占创建它的 `checkpoint.json`。封口时回收墓碑：参与确认的是没被移除、而且在日志里最晚一次写入之前 90 天内写过事件的设备；它们确认位置的最小值以内的墓碑删掉。被移除的设备、以及 180 天没出现的设备从设备表里去掉；墓碑超过 10 万个时去掉时间戳最早的。输入全部来自日志（「最晚一次写入」看的是事件的 `at`，不看本机时间），所有设备在同一个位置做出同样的决定。

封口的设备中断时，下一台读到封口的设备补写检查点。读过整个 epoch 的设备会核对检查点就是它自己算出的那一份，不一致是 `dictionary_sync_corrupt`。新检查点写好 10 分钟后，旧 epoch 目录被删掉。

确认位置（`ack`）只在本机词库真的写好之后推进：收到不等于写进了词库，Engine 忙着时不确认，墓碑就一直为这台设备留着。本机落后又一天没写过事件时，设备写一个只带确认的事件；加入之后马上写一个，在设备表里登记。

### 长期离线的设备

本机所在的 epoch 已经被删掉的设备从最新的检查点重新开始：共享状态换成检查点里的，与本机记得的「词库里有哪些词」比较，检查点里没有的就是别处删掉了，从本机词库删去；本机还没发出的改动照样发出。超过 90 天没出现的设备，它没写进本机词库的那些删除对应的墓碑可能已经回收；它回来后仍按上面的比较删掉这些词，但它离线期间对同一个词条做的、实际早于那次删除的修改会让这个词条重新出现。这是首版明确接受的限制。

## 崩溃与重试

本机的同步状态是一个原子替换的文件，里面有：日志位置和共享状态、认为本机词库里有哪些词（`applied`）、还没发出去的操作（`outbox`，每个词条只留最新一条）、时钟、确认位置和缓存的子密钥。一次同步按固定顺序做，每一步之后写盘：

1. 记录本机改动：本机词库相对 `applied` 的变化记成带时间戳的操作放进 `outbox`。已经和有效值一致的（上一次写进本机词库之后、写盘之前崩溃留下的）只修正 `applied`，不发操作。
2. 拉取新事件，与位置、时钟一起写盘。自己写的、已经在日志里的操作从 `outbox` 去掉（发出之后、写盘之前崩溃时靠这一步认出来，不发第二遍）；被共享值盖过的待发操作也去掉。
3. 把远端改动分批（每批最多 128 项，与 Engine 批量编辑上限相同）写进本机词库，写好的才算进 `applied`。每项带一个请求编号（`dsync-` 加 32 位十六进制，由词条、加入还是删除和决定它的那条操作唯一决定），Engine 按它记回执；崩溃时没写盘的那几批会再写一次，同一个编号重试不改变结果，加入已有的词、删除已经不在的词也不改变结果。Engine 删不掉的词照实留在 `applied` 里、不再重试，免得下一次核对把它当成本机新加的词发出去。
4. 发送：每个事件抢到序号后就当作读到了自己的事件接上日志。
5. 该封口时封口；删掉过了宽限期的旧 epoch。

写本机词库从不跨网络请求持有词库维护权：每次只写一批，网络请求都在批与批之间之外。Engine 忙（输入会话占着词库、维护在预算内拿不到）时这一轮先不写，5 秒、30 秒、2 分钟、10 分钟后再试（之后一直是 10 分钟），不联网；拉取和发送照常。

### 大批删除

一次核对里本机少了 50 个以上、并且至少是原有词条一半的词时，先不把删除发出去，状态里标出被挡下的数量：多半是本机词库被重置或者损坏了，不该把其他设备上的词也删掉。用户选「同步删除」就照常发出；选「从网盘恢复」就把这些词从共享词库写回本机。

## 密钥与设备批准

网盘只见到密文。词库的密钥 `K` 来自词库自己的密钥串：它是 [云剪贴板端到端加密](cloud-clipboard-e2e.md) 那一套协议的另一个实例——同样的设备密钥对、核对码、封装和批准流程，同样由第一台设备生成密钥、新设备必须由已有设备点「允许」——放在 `msime-dictionary/keyring/` 下，按 [云剪贴板 WebDAV 布局 v1](cloud-clipboard-webdav.md) 存放（格式名仍是 `msime-clipboard`）。本机的密钥串与云剪贴板的分开存放，所以同一台设备在两个功能里是两个设备身份、要分别批准一次。

密钥串只交出 `M = HKDF-SHA256(K, info="msime-dictionary-v1-key", 32)`，不交出 `K` 本身；两把子密钥再由 HKDF-SHA256 从 `M` 派生：事件用 `info="msime-dictionary-v1-event"`，检查点用 `info="msime-dictionary-v1-checkpoint"`，都是 32 字节，没有 salt。`key_id` 就是密钥串给 `K` 的编号。本机同步状态里只存子密钥。

### 设备身份

设备编号是本机词库密钥串里的设备编号（公钥 SHA-256 的前 16 字节）。一个安装只有一份密钥串，它的所有进程（输入法、设置应用、面板）用同一个目录、在同一把锁下「读不到才生成」，所以设备身份在进程之间和重启之后都不变；登记按设备编号进行，重复登记只更新名称，批准的一方看到的每台设备只有一条。日志里的设备表同样按编号记，一台设备写多少次事件都只有一条。设备编号只在重装（密钥串没了）时变，那是一台新设备。

### 移除设备与换钥

在一台已获准的设备上移除另一台：密钥串换钥（新密钥只封装给本机，其他设备要重新点一次「允许」），同时在日志里宣布移除（`retire`），被移除的设备不再拖住墓碑回收。持有新旧两把密钥的设备随即封口当前 epoch，把共享状态用新密钥写成下一个 epoch 的检查点（`generation` 加一）；之后的事件都用新密钥。被移除的设备手里只有旧密钥，读到封口为止；其他设备在重新获准之前同样停在封口，它们的改动留在本机，获准后发出。持有当前密钥的设备只往「epoch 的密钥就是密钥串现在的密钥」的 epoch 里写。

### 以本机为准重新开始

持有旧密钥的设备都不在了、本机只拿到了重置后的新密钥时，用户可以选择以本机为准重新开始：不解密地走到日志末尾，封口，用新密钥写一份只有本机词条的检查点，换一个新的 `lineage`，`generation` 加一。其他设备拿到新密钥后认出 `lineage` 变了，按「第一次加入」把它们的词合并进来，不会因此删词。

## 防回退

能写网盘的人（包括已经被移除、但还知道应用密码的设备）可以删改文件，例如删掉一次删除让词复活。客户端记着读到的位置：

- 新事件必须接在本机记得的链头后面；本机读过的最后一个事件不能消失，列出的序号不能跳过一个不存在的序号；
- 从检查点重新开始时，epoch、序号和 `generation` 都不许比本机记得的小，序号相同时链头也要相同；`lineage` 变了时 `generation` 必须变大；
- 本机读到过日志，而网盘上的 `msime-dictionary/v1/` 不见了时，不会从头再建一份。

不满足时报 `dictionary_sync_rollback`。如果是用户自己清理了网盘上的文件夹，在设置里选择「确认网盘现状并恢复同步」，确认后以 `probe` 的 `trust_remote:true` 恢复。本机会忘掉同步位置和待发改动，按「第一次加入」从网盘现状重新开始；本机词条保留，但未上传删除可能重新合并回来。普通测试连接和保存前预检始终不改同步状态或防回退记录。这只防「改写本机已经读过的历史」：知道应用密码又持有密钥的人仍可以往后追加事件。移除一台设备之后要在网盘上换一个应用密码。

## 上限

| 项 | 上限 |
| --- | --- |
| 一个事件的操作数 | 1000 条 |
| 一个事件的明文 | 256 KiB（一个事件至少装得下 50 条最长的词条） |
| 一个事件文件 | 512 KiB |
| 一个检查点文件 | 32 MiB；最多 30 万个词条（含墓碑）、64 台设备 |
| 一次列目录的响应 | 2 MiB（压缩让一个 epoch 目录通常不超过 66 项） |
| `format.json` | 4 KiB |
| 共享词库里的词条 | 10 万个以内才收新词（删除照常） |
| 墓碑 | 10 万个，超过时回收最早的 |
| 待发送的操作 | 2 万个词条；超过时本机的改动先留在词库里，等发出去一批再记，不会丢 |
| 一次写进本机词库 | 128 项 |
| 一个词条 | 编码 512 字节，词 4096 字节 |
| 本机同步状态文件 | 64 MiB，序列化后写入前检查，与读取上限一致 |

响应或本机状态超过字节上限时是 `dictionary_sync_too_large`。本机状态超限时不替换上一次可读文件，新增词仍保留在本机词库；删减本次新增内容后可重试。成功 HTTP 响应的正文必须完整读完：无 `Content-Length` 或 chunked 正文超限也返回上述错误；传输中断返回 `dictionary_sync_unavailable`，不会把空正文当成成功并推进日志位置。非成功 HTTP 状态仍按鉴权、限流等既有规则处理。

## 请求量

坚果云免费账号每 30 分钟 600 个请求，与这个账号授权的所有第三方应用（包括水杉的云剪贴板）共用。词库同步给每台设备定的额度是每 30 分钟自动同步最多 40 个请求，加上用户手动「立即同步」最多 60 个；三台设备同时用满也只占三成。额度按滚动窗口在本机计数，独占创建算两个请求（`PUT` 和 `MOVE`）。

- **拉取**：一个 `PROPFIND`，加上每个新事件一个 `GET`。打开设置应用时拉一次（距上次不到一分钟就不拉），宿主活着时每 30 分钟拉一次。
- **发送**：最后一次改词之后等一分钟（一直在改时最多等十分钟），两次自动发送至少隔五分钟；一次发送是每个事件一个 `PUT` 加一个 `MOVE`，抢不到序号时多一个 `PROPFIND`。改一个词马上就记下来（通常不联网，到了十分钟的上限时这一次就发送），所以时间戳接近改动发生的时刻。
- **压缩**：约 7 个请求，每 64 个事件一次。
- **出错**：连不上时 1、2、5、10、30、60 分钟后再自动试；限流或额度用完等 30 分钟；凭据不对、日志被回退、格式不认识、日志损坏之后自动同步停一小时，手动同步照常。
- 「立即同步」不受防抖和间隔限制，额度用完时报 `dictionary_sync_rate_limited`。

## 网盘能看到什么

词、编码、设备之间的确认和移除都在本机加密，网盘看不到。网盘能看到：事件的数量、大小和写入时间（`at`），检查点的大小、epoch、换钥次数和共享词库编号，以及密钥串里的设备名称、公钥和登记时间（与云剪贴板相同，见 [端到端加密](cloud-clipboard-e2e.md) 的威胁模型）。删掉的词在压缩后从网盘上删掉，但网盘的回收站和历史版本可能还留着旧的密文。

## 实现在哪里

- `crates/client-core/src/cloud/dictionary_sync.rs` 及其子模块：不碰网络、不碰 Engine 的协议核心——时钟（`clock`）、词条身份（`entry`）、合并与墓碑回收（`replica`）、加密（`crypto`）、文件格式和日志位置（`log`）、一次同步的步骤与本机状态（`sync`）、调度与额度（`schedule`）。网盘、本机词库、时钟和写盘都经接口注入；`simulation_tests.rs` 用内存里的网盘和合成设备跑上面的全部规则。
- `crates/client-services/src/dictionary_webdav.rs`：WebDAV 传输（核心的 `RemoteStore`，独占创建、限流退避和响应上限用云剪贴板的 `clipboard_webdav::Dav`）、词库密钥串（云剪贴板的 `RelayClipboard` 加一个给每个请求路径加 `msime-dictionary/keyring/` 前缀的传输，全部用法收在 `KeyRingAccess` 一处）、本机状态的写盘和锁、测试连接。
- `crates/client-core/src/preferences.rs`：偏好 `dictionary_sync_webdav`。
- `crates/host-api/src/dictionary_webdav.rs`：Engine 一侧的本机词库（一致的读、批量写、维护权和请求输入法让出词库的策略）和 `msime_client_dictionary_sync` 的动作分派。
- 测试：`client-core` 的模拟测试；`crates/clipboard-relay/tests/dictionary_webdav_flow.rs` 对着真实的 WebDAV 服务端（`dav-server`）跑配对、互传、错误的应用密码、超大响应、同时抢序号、截尾和服务端暂时不可用；`host-api` 的单元测试对着真实的 Engine 词库跑读写、输入会话占着词库时的「忙」和 Engine 不收的词。

### 检查点超过上限时

生成和读取都遵守 32 MiB 上限。合法长短语可能在达到 10 万词之前就超过它：普通压缩会保留当前日志继续同步，用户删减词条并让设备确认后再压缩。换钥不能继续使用旧钥，检查点超限时返回 `dictionary_sync_too_large`，不封口；应先在仍使用旧钥的设备上删减并同步，或以较小的本机词库重新开始。重新开始在封口前也执行同样的大小检查，失败不会挡住其他设备继续写旧日志。尚未压缩时目录中的事件会继续增长，仍受目录列表的读取上限限制。
