# 输入习惯同步协议（v1）

输入习惯同步把一台设备上学到的候选顺序（内置词的调频和阶梯降权、删除记录、置顶、固定位置）带到同一账号的其他设备上。内容在设备上压缩、补齐、加密后才上传，每台设备在服务端有自己的一份密文，服务端只保存不透明的字节，读不到内容。这份文档是服务端（msime-cloud）、Rust 驱动（client-core、engine、client-services、host-api）和各平台客户端共同的契约。设计取舍、分期和被否掉的方案见 [决策笔记](../.agents/notes/proposed/feature/2026-10-27-learning-sync-e2e.md)。

服务端部分由 msime-cloud 实现，实现中定下的细节（设备与会话同寿命、按设备上限定的限流、传输名额）已写进下文。其余部分按决策笔记里的分期落地，落地时改动这份文档，不另起一份。

## 与其他同步的关系

- 账号的「词库」同步（Android 的「云同步」）上传的是记为用户词的词条，明文，服务端可读。输入习惯同步不碰这些行：用户词归词库同步管，下文合并规则里写明远端行从不覆盖本机的用户词。
- 输入习惯同步是 [云剪贴板端到端加密协议](cloud-clipboard-e2e.md) 的又一个实例，叫 learning 域。设备身份、账号密钥、本机密钥串、服务端表都和剪贴板分开，同一台设备在两个功能里是两个设备身份，要分别批准。
- 各域的账号密钥和设备身份 never 合并或互相派生：关掉云剪贴板或删除剪贴板数据时，服务端会删掉剪贴板的设备登记和密钥，learning 域不能因此失效；反过来也一样。
- learning 域在封装和核对上比剪贴板 v1 多两步（带认证的封装、反向核对码），见下文。剪贴板仍按它自己的协议，不受影响。

## 威胁模型

**防的：**

- 数据库泄露、服务端运维人员读库。
- 服务端或拿到会话令牌的人登记一台假设备，借此取得账号密钥。新设备必须由用户在已有设备上核对后点「允许」。设备核对码是公钥哈希截成的 16 位十进制，强度约 2⁵³：服务端要在 D 登记之后、用户点「允许」之前，现场搜出一个号码与 D 相同、并且自己知道私钥的假设备公钥，`P_D` 事先不知道，没法预先算好。在通常几分钟的批准窗口里这需要大规模算力，拿到会话令牌的人和一般的服务端入侵做不到；服务端可以拖着不列出待批准的设备来拉长窗口，所以对掌握大规模算力的对手，这一条只是抬高了成本，见「不防的」。强度与云剪贴板的设备核对码相同。
- 服务端给一台还没被批准的新设备塞一把它自己生成的密钥（剪贴板 v1 不防的那一条）。新设备只有在用户核对反向核对码一致后才启用密钥，见「反向核对」。
- 服务端把 A 设备的密文冒充成 B 设备的。设备编号在密文头里，并且是 AEAD 的附加数据；读取方解密后核对头里的设备编号就是它请求的那台，见「防回滚」。
- 服务端把某台设备的数据回滚到旧版本。代次在密文头里、受 AEAD 保护，读取方记住每台设备见过的最大代次，见「防回滚」。
- 泄露的会话令牌伪造或覆盖别的设备的密文。`PUT /blobs` 和 `DELETE /blobs` 只允许当前会话绑定的那台设备写、删自己那一份。

**不防的：**

- 本机被攻破。桌面端和 HarmonyOS 的密钥串只是当前用户私有的文件，没有进系统密钥库；能读这个文件的程序就能解开全部输入习惯。所以能还原句子的整句联想数据（n-gram）要等这些平台的密钥串进了系统密钥库才同步。
- 服务端看得到的元数据，见「服务端看得到的元数据」，PRIVACY.md 会写明。
- 设备时钟偏差很大时，并发修改的胜负可能和真实先后相反（见「时间戳」）。
- 任何有效会话清空整个 learning 域。`POST /rekey`（`previous_key_id` 在 `GET` 里就能看到）、`DELETE /devices/{device_id}` 和账号的删除数据接口都能删掉别的设备的密文和封装；`rekey` 不能要求调用方持有旧密钥的封装，因为所有设备都丢了时的「重置」就是从一台没有封装的新设备发起的。后果只是拒绝服务：本机才是正本，删掉的只是副本。被清空后每台真设备都会收到 `learning_key_rotated`，要重新被允许；发起 `rekey` 的如果是攻击者登记的设备，它就是新密钥的唯一持有者，可以去批准真设备；真设备上弹出反向核对时，用户在自己的设备上看不到对应的号码，只要不点「一致」，真设备就不会用它的密钥上传。界面要写明：只有在另一台自己的设备上看到同一串号码时才点「一致」。
- 掌握大规模算力、又控制服务端的对手：它可以在批准窗口里做约 2⁵³ 次运算，凑出一台核对码与真设备相同的假设备，骗用户在已有设备上点「允许」。要堵上得让核对码在批准之后才揭示的随机数上做承诺，这一版不做，和云剪贴板一起留到以后。

## 编码约定

与云剪贴板协议相同：

- `b64`：RFC 4648 §5 的 base64url，不带填充。
- `hex`：小写十六进制。
- `HKDF`：HKDF-SHA256；`AEAD`：XChaCha20-Poly1305（24 字节 nonce，16 字节 tag）；`DH`：X25519。全零的 DH 结果视为失败。
- `info`、`aad` 中的字符串都是 ASCII 字节，`‖` 表示拼接，`0x00` 是一个零字节。整数一律大端。

## 域分隔标签

learning 域只用下面这些标签，不沿用 `msime-clipboard-v1-*`。它们不全是 HKDF 的 `info`，每个标签怎么用以「用法」一栏为准：

| 标签 | 用途 | 用法 |
| --- | --- | --- |
| `msime-learning-v1-key-id` | 由账号密钥算 `key_id` | HKDF 的 `info` |
| `msime-learning-v1-blob` | 由账号密钥算密文加密密钥 | HKDF 的 `info` |
| `msime-learning-v1-wrap` | 封装密钥的派生，以及封装的附加数据前缀 | HKDF 的 `info`，同时是封装 `aad` 的前缀 |
| `msime-learning-v1-code` | 设备核对码 | 不经过 HKDF：拼在公钥前面作 SHA-256 的输入，见「设备身份」 |
| `msime-learning-v1-sas` | 反向核对码 | HKDF 的 `info` |

## 设备身份

- 每台设备第一次打开输入习惯同步时随机生成 32 字节的 X25519 私钥，只保存在本机的 learning 密钥串里。
- `public_key` = `b64(公钥 32 字节)`；`device_id` = `hex(SHA-256(公钥)[0..16])`，32 个字符；`device_id_raw` 是同样的 16 字节原值，用在密文头里。
- 设备核对码 `code`：`SHA-256("msime-learning-v1-code" ‖ 公钥)` 的前 8 字节读成无符号整数，对 10¹⁶ 取余，左补零到 16 位，每 4 位一组。批准时已有设备显示它，新设备也显示自己的，用户核对一致才点「允许」。

## 账号密钥

- 账号同一时刻只有一把 `K_learn`（32 字节随机数），由第一台打开输入习惯同步的设备在本机生成，只封装给它自己。服务端谎称「你是第一台」没有收益：密钥是本机生成的，服务端读不到。
- `key_id` = `hex(HKDF(ikm=K_learn, salt=空, info="msime-learning-v1-key-id", 16))`；`key_id_raw` 是这 16 字节原值。
- `blob_key` = `HKDF(ikm=K_learn, salt=空, info="msime-learning-v1-blob", 32)`。
- 换钥只在移除设备和「重置输入习惯同步」时发生：生成新的 `K_learn`，只封装给本机；服务端在同一事务里删掉全部密文和全部旧封装。其余设备都要重新批准，之后用新密钥重新上传。被移除的设备再也拿不到能解的密文，服务端不保留旧密钥下的任何密文。
- 没有恢复码，也没有口令派生。每台设备本地都有完整的学习数据，云端只是副本；所有设备都丢了时，在新设备上重置，旧密文直接删除。

## 带认证的封装

批准者 A（静态私钥 `s_A`，公钥 `P_A`，编号 `ID_A`）把 `K_learn` 交给设备 D（公钥 `P_D`，编号 `ID_D`）：

1. 生成临时私钥 `e`，公钥 `E`。`dh1 = DH(e, P_D)`，`dh2 = DH(s_A, P_D)`，任一全零即失败。
2. `wrap_key = HKDF(ikm=dh1 ‖ dh2, salt=E ‖ P_A ‖ P_D, info="msime-learning-v1-wrap", 32)`
3. `aad = "msime-learning-v1-wrap" ‖ 0x00 ‖ key_id ‖ 0x00 ‖ ID_A ‖ 0x00 ‖ ID_D`（`key_id`、`ID_A`、`ID_D` 用 hex 字符串）
4. `wrap = "v1." ‖ b64(E ‖ nonce ‖ AEAD(wrap_key, nonce, K_learn, aad))`，固定 142 个字符。

服务端随封装保存 `approver_device_id`。D 解封时用 `GET` 里给出的批准者公钥，以 `DH(s_D, E)` 和 `DH(s_D, P_A)` 得到同样的 `dh1`、`dh2`；批准者公钥不对时 AEAD 校验失败。解开后重新计算 `key_id`，与服务端给的不同就当作没有拿到密钥。第一台设备封装给自己时 A 就是 D。

带认证的封装保证「封装出自持有 `s_A` 的设备」，但服务端可以自己登记一台假的批准者，用它的私钥封装一把假密钥。挡住这一步的是下面的反向核对。

## 反向核对

- A 点「允许」并上传封装后，显示反向核对码 `sas`：`HKDF(ikm=K_learn, salt=P_A ‖ P_D, info="msime-learning-v1-sas", 8)` 读成无符号整数，对 10¹⁶ 取余，左补零到 16 位，每 4 位一组。
- D 解封后用自己解出的密钥和封装记录的批准者公钥算同一个值并显示，用户在 D 上点「一致」之后，`K_learn` 才生效（写进密钥串的「已确认」状态）。确认之前 D 不上传、不下载、不解密任何密文。
- 用户点「不一致」时，D 丢掉这把密钥和封装，保留自己的设备身份，报 `learning_sas_mismatch`，提示用户检查设备列表、移除不认识的设备。
- 核对码里带上 `K_learn`，是为了不给服务端留下用算力换胜算的路。只用两台设备公钥算的话，攻击和设备核对码一样是一次第二原像搜索：`P_D` 是 D 登记时才随机生成的，服务端只能在 D 登记之后、用户核对之前，搜一个让号码相同、并且自己知道私钥的假批准者公钥，16 位十进制约 2⁵³ 次运算，没法事先算好，强度与设备核对码相同（见「威胁模型」）。带上只有真设备持有的 `K_learn` 之后，服务端造的假批准者给 D 的是另一把密钥，两边显示的号码相互独立，不管用多少算力，碰上的概率都只有 10⁻¹⁶。

## 密文信封 MSL1

每台设备在服务端只有一份密文，内容是这台设备导出的全部输入习惯。

明文头，68 字节，不加密：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | ASCII `MSL1` |
| 4 | 16 | `key_id_raw` |
| 20 | 16 | 上传设备的 `device_id_raw` |
| 36 | 8 | `generation`，u64 大端 |
| 44 | 24 | `nonce`，随机 |

之后是 `AEAD(blob_key, nonce, padded, aad=整个 68 字节明文头)`，长度是 `padded` 加 16 字节 tag。AEAD 只证明这个头是某台持有 `K_learn` 的设备写的，不证明它就是请求的那一份；解密后对头部字段的核对见「防回滚」。

- `gz`：明文流（见下一节）按 RFC 1952 压缩成单个 gzip 成员，头部 `MTIME` 为 0、不带文件名和注释，免得压缩头泄露时间。
- `padded` = `u32 大端(len(gz)) ‖ gz ‖ 零字节`，总长 `padme(4 + len(gz))`。解密方校验长度字段不越界、补齐的字节全为零，否则按解不开处理。
- `padme(L)`：`L < 2` 时为 `L`；否则 `E = ⌊log₂ L⌋`，`S = ⌊log₂ E⌋ + 1`，`m = 2^(E−S) − 1`，结果是 `(L + m) & ~m`。额外开销不超过 12%。不按 2 的幂分桶：那样 4.1 MiB 会补到 8 MiB，正好顶到上限。
- `generation` 就是这次上传的 `?revision=N`，见服务端接口。
- 整个信封（明文头加密文）不超过 8 MiB（8,388,608 字节）。超过时客户端按「上限与额度」末尾的规则截断明文流再上传，提示 `learning_too_large`，不让整份同步失败；其他设备的照常下载合并。

## 明文流 `msime-learning-sync` v1

UTF-8 的 NDJSON，一行一条记录，顺序固定，同样的学习数据总是写出同样的字节（上传前用它的 SHA-256 判断有没有变化）：

```json
{"type":"header","format":"msime-learning-sync","version":1,"content_id":"<本机词库内容标识>"}
{"type":"weight","dictionary":"pinyin","key":"ni'hao","value":"你好","weight":12345,"display":"","updated_at":1793000000}
{"type":"delete","dictionary":"pinyin","key":"ni'hao","value":"拟好","updated_at":1793000001}
{"type":"pin","context":"…","value":"…","updated_at":1793000002}
{"type":"position","context":"…","key":"…","value":"…","position":2,"updated_at":1793000003}
{"type":"footer","records":4}
```

- `weight`：日志里 `operation='upsert'` 且 `user_inserted=0` 的行，即内置词学到的权重，包括阶梯降权写下的那些行。`user_inserted=1` 的行不导出，它们归词库同步。
- `delete`：日志里全部 `operation='delete'` 的行（删除记录）。
- `pin`：`pinned_candidates` 的行。
- `position`：固定位置的完整候选状态，每个 `(context, key, value)` 一条，带 `position` 和必填 `updated_at`。第一期先迁移现有 `fixed_candidate_positions`：旧行的时间戳设为 `1`；新增或移动时按下节更新。候选表只按身份唯一，不能有 `(context, position)` 唯一约束；显示用的 `fixed_candidate_positions` 仍是槽位唯一的投影。被槽位冲突暂时隐藏的候选也导出、计入记录数和上限，摘要与重启恢复不能只读显示投影。备份恢复仍用自己的格式和合并语义；它替换或合并固定位置时必须同步候选状态，不能只改显示表后让旧候选在重算时回来。
- 排序：`weight` 与 `delete` 按 `(dictionary, key, value)` 混排，然后 `pin` 按 `context`，然后 `position` 按 `(context, key, value)`；字符串按 UTF-8 字节比较。
- `updated_at` 是这一行在日志里的逻辑修改时间，以 Unix 秒为起点并按下节单调推进，可能超前于实际时钟，不是导出时间。
- `content_id` 是导出设备当前词库代次的内容标识。与本机不同时照样合并，设置页提示「这台设备的词库版本与其他设备不同，部分候选顺序可能不一致」：学到的权重是相对导出设备词库邻居的绝对值，词库版本不同时重放后名次可能不同。
- `dictionary` 只取 Engine 认识的种类（`pinyin`、`wubi`、`wubi98`、`quick`、`english`），其余的行不导出；读到不认识的种类时跳过这一条。
- 不认识的 `type` 跳过并计数，不让整份失败：第二期在同一版本里加整句联想的记录，旧客户端照样合并它认识的部分。只有不兼容的改动才升 `version`，读到更高的 `version` 时整份跳过，提示升级。
- 记录数和 `footer.records` 不符、`footer` 之后还有内容、字段缺失或类型不对、数值超出「上限与额度」里的范围（包括 `updated_at`），按解不开处理。

## 时间戳

Engine 里每一条在冲突分支里改写 `user_dictionary_operations`、`pinned_candidates` 或固定位置候选状态的语句，都把 `updated_at` 写成 `min(max(unixepoch(), 旧值 + 1, reset_floor + 1), 2⁴⁰)`；第一次插入没有旧值，取 `min(max(unixepoch(), reset_floor + 1), 2⁴⁰)`。`reset_floor` 是当前账号在本机的重置屏障，没有时为 0，定义见「本机重置屏障」。同一行的时间戳因此单调递增：收到一条带「未来时间」的远端行之后，本机下一次修改这一行仍然比它大，重置后新写的行也高于屏障。合并写入远端行时原样保留它的 `updated_at`。上限 2⁴⁰ 与「上限与额度」一致，保证不会溢出 SQLite 的 64 位整数，也不会写出别的设备拒收的值；碰到之后这一行再改也停在 2⁴⁰，按平局规则比较，不能再保证新修改胜出。屏障已到这个上限时，也不能再保证重置后的新行能通过屏障。

未达到上限时，这保证之后的修改能胜出，不保证「真实时间更晚的先胜」：两台设备在各自时钟下几乎同时改同一行时，时钟快的一方胜。

一次调频在同一个事务里写下的一组行（被选中的那一行，加上阶梯降权改写的各行，见 `ranking.rs` 的 `adjust_candidate_ranking`）必须用同一个时间戳：事务先算 `g = max(unixepoch(), 这次要写的各行里已有的最大 updated_at + 1, reset_floor + 1)`，再把 `g` 写进这一组的每一行，`g` 同样封顶 2⁴⁰。逐行各算各的 `max` 不行：一行刚在这一秒里改过、或者刚合并进一条时钟偏快的远端行，它会得到「旧值 + 1」，同组其他行得到「现在」，一组行的时间戳参差不齐，逐行比较时这组就会被拆开，一部分用本机的、一部分用远端的。现在 `adjust_candidate_ranking` 对每一行各调一次 `update_ranked_weight`，Engine 实现 Lamport 时间戳时要把 `g` 传进去。

## 合并规则

合并分两步：先在纯函数 `combine` 里把所有远端设备的记录按下表折叠成一份（可交换、可结合、幂等，与设备顺序和重复次数无关），再在一个事务里和本机日志比较、写入胜出的远端行。固定位置保留完整候选状态，本机与远端共同参与相同规则；只有应用到显示表时才按槽位投影，不能在中间折叠、保存或导出时丢掉槽位冲突的输家。

| 数据 | 第一期 | 规则 |
| --- | --- | --- |
| `weight` 与 `delete` | 同步 | 按 `(dictionary, key, value)` 比较：`updated_at` 大的胜；相同时 `delete` 胜；都是 `weight` 时 `weight` 大的胜；再相同时 `display` 按字节大的胜。本机这一行 `user_inserted=1` 时从不被远端行覆盖。远端行写进本机时记为 `user_inserted=0`，写法与 `merge_dictionary_state` 相同（先改工作词库，再记日志）。一次调频写下的一组行（含阶梯降权）共用同一个时间戳 `g`（见「时间戳」），所以在两组都写过的行上，`g` 大的那一组整组胜出；两组的 `g` 恰好相等时按上面的平局规则逐行比较，组可能被拆开，这只在两台设备同一秒调同一组时发生，接受 |
| `delete` 胜出时的副作用 | 同步 | 与本机删词相同：删掉这个词的置顶，删掉包含它的整句联想记录（`removal.rs` 的删词事务）。删除记录必须同步：连续选词造词前会查删除记录，不同步的话对端会把删掉的词又造回来 |
| `pin` | 同步 | 按 `context` 比较 `updated_at`，大的胜，相同时 `value` 按字节大的胜。26 键取消置顶只发生在删词时，由 `delete` 的副作用带过去。九宫格的置顶和固定到第 1 位也写一条 `pin`（上下文 `nine-key:<数字>:<锁定>`），用户取消那个词的固定或把它挪到别的槽位时删掉本机这一条，和 `position` 的取消固定一样不留删除记录，远端副本以后仍可能把它带回来 |
| `position` | 同步，无删除记录 | 同一 `(context, key, value)` 取 `updated_at` 较大的那条，时间相同取较小的 `position`；本机与远端一视同仁，不用 `INSERT OR IGNORE` 保留本机。将完整候选状态合并并持久化之后，对每个 `(context, position)` 取时间较大的候选，时间相同取 `(key, value)` 字节序较小者，生成显示投影；输家保留在候选表中。合并、投影和重新导出不更新时间戳。取消固定只删除本机对应候选并重算投影，不留删除记录，远端副本以后仍可能把它带回来，第一期不承诺传播取消 |
| 快捷短语槽位（`quick_phrase_slots`） | 第二期 | 不在任何导出流里，第二期给它加时间戳和删除记录 |
| 整句联想（`personal_bigram`、`personal_trigram`） | 第二期 | 按设备分槽：每台设备上传自己计数最高的 5 万条；接收方按来源设备另存，读取时本机计数加上远端计数之和；远端合计截到 20 万行；移除设备时删掉它的贡献 |
| 拼写纠错计数、自动纠错抑制 | 不同步 | 纠错类别取决于键位相邻，触屏和实体键盘之间不能混用 |
| 连续选词对、选词计数、回执 | 永不同步 | 都是用完就丢的进度计数，产出的词已经随词库同步 |

其他约定：

- 首次打开时不问「合并还是用云端」：先上传本机这份，再合并其他设备的。本机原有的行保留原来的 `updated_at`，久未使用的设备加入时不会盖掉别人更新的调整。
- 「重置学习」只清本机，界面上写明。它把本机日志、固定位置候选状态和显示投影一起清空，不写删除记录，所以其他设备上的数据不受影响；本机按下一节的重置屏障过滤后续合并。它不承诺抹掉所有离线设备上尚未被本机观察到的旧修改。
- 保留槽位冲突输家是同步合并的要求。本机显式固定到已有主人的槽位时，按现有语义移除目标槽位的旧候选，再写入新候选；取消也同步移除对应候选，不只删显示行。开关未启用时，`A@1 → B@1 → 取消 B` 之后该槽位仍为空，不能因引入候选表让 A 复活。同步开启时，被本机移除但没有删除记录的远端副本仍可能在后续回来，这是第一期取消不传播的限制。
- 固定位置不能在 `combine` 中提前丢掉槽位冲突输家。例如同一上下文内 `a < b`，`A={b@2}`、`B={a@2}`、`C={a@1}`，时间戳相同；若每轮先取同一身份的较小位置、再丢槽位输家，两种括号分组分别剩 `{a@1}` 和 `{a@1,b@2}`。保留候选状态时两种分组都保存 `a@1,b@2`，最终显示一致。实现必须测试所有排列和括号分组，以及保存、重启、再导出后的结果。
- 合并在 Engine 的独占维护锁下执行。待合并的结果先写成本机的待合并文件，由持有词库的进程在没有输入会话时认领、合并，失败重试三次后放弃，做法与本地备份恢复的待合并文件相同。

## 本机重置屏障

- `cloud-sync/learning.json` 按账号持久保存两个只增不减的逻辑时间：`observed_max` 和 `reset_floor`，初值都是 0，不挂在 `key_id` 或来源设备下。换钥、重新批准、退出登录都不删。
- `observed_max` 至少覆盖本机现存学习记录、本机已经发布过的同步导出，以及本机已经通过解密、头部和完整流格式校验的远端记录的最大 `updated_at`，包括待合并、因本机用户词或槽位冲突未显示的行。发布本机导出之前先持久化本次扫描到的上限；接纳远端结果时先持久化其上限，再发布待合并文件。持久化失败就不发布或接纳这一批。已经观察的时间上限不能因本机后来删行、应用失败、清空待合并文件或换代而丢失。
- 重置与远端结果接纳、本机学习写入、导出及合并在同一独占维护边界内串行。先取 `F = max(旧 reset_floor, unixepoch(), observed_max, 本机所有学习记录的最大 updated_at)`，持久化 `reset_floor = F`，成功后才清空本机学习状态并报告重置成功；持久化失败不清空。中途退出后允许重试清空，屏障不回退。
- 后续合并跳过所有 `updated_at <= reset_floor` 的远端行，包含 `position` 和未显示的槽位冲突候选；在重置之前接纳的待合并文件也要在真正应用时重新检查屏障。新写本机行按「时间戳」取至少 `reset_floor + 1`，不能在清空旧行后退回仅用 `unixepoch()`。
- 例如实际 Unix 秒为 100，本机在同一秒多次修改到逻辑时间 103，并已传给另一台设备。重置必须得到 `F >= 103`，对端重传这条旧行仍被过滤；本机重置后新写的行至少为 104。换钥重传也保留这个区别。
- 这是对本机已观察逻辑时间的屏障，不是全账号的真实时间分界。离线设备有本机未见过、`updated_at > F` 的旧行时，它仍可在以后合并进来；对端在重置后新写、但 `updated_at <= F` 的行也会被过滤，直到该行在对端的逻辑时间超过屏障。仅凭逐行时间戳无法区分这两种情况，不能承诺「所有重置前的都不回来、所有重置后的都能合并」。界面说明本机重置的这一限制；跨设备协调重置需要另行设计，不在 v1 内。

## 防回滚

- 读取方按（账号，`key_id`，来源设备）分别记两项：已验证的最大代次 `verified`、已应用的代次 `applied`，都只增不减，永不清零。存在本机的 `cloud-sync/learning.json`，与 `state.json` 分开（旧版本改写 `state.json` 时会丢掉它不认识的字段），退出登录不删。
- 读取方不信服务端给的路径和元数据，只信解密后验证过的明文头。下载 `GET /blobs/{device_id}` 拿到的信封，AEAD 校验通过之后还必须逐项核对：头里的 `device_id_raw` 等于这次请求的 `device_id`，并且这台设备在 `GET /` 返回的设备列表里；`key_id_raw` 等于本机当前的 `key_id`；`generation` 不小于元数据里这台设备的 `revision`（取元数据和下载之间那台设备可能又上传过一次，所以不要求相等）。任何一项不符都按 `learning_undecryptable` 跳过，不推进任何进度。下面按来源设备记的进度，一律以验证过的头里的 `device_id_raw` 为准，从不用 URL 或元数据里的设备编号：否则服务端把 A 的旧密文放进 B 的位置，就能绕过 A 的 `verified` 下限。
- 只下载、只接受 `key_id` 等于本机当前密钥的密文。`generation < verified` 的一律拒收；`generation == applied` 的跳过；其余的解密成功后先推进 `verified`，合并成功后再推进 `applied`。合并失败只是 `applied` 不动，下一轮重新下载同一个代次再合并。
- 本机拿到新的 `key_id`（换钥后被重新批准）时，旧 `key_id` 下的 `verified`、`applied` 可以删掉：旧密钥下的密文不会再被接受。按账号记的 `observed_max` 和 `reset_floor`（见「本机重置屏障」）不在其中，不删：换钥之后每台设备都会用新密钥把整份状态重新上传，屏障仍要按同样的逻辑时间过滤。
- 上传方记自己上次上传的代次 `uploaded` 和明文流的 SHA-256。下一次上传用 `N = max(服务端当前代次, uploaded) + 1`：服务端丢了或回滚了这台设备的密文时，新的代次仍然比其他设备记着的大。
- 算出的 `N` 超过 2⁵³−1 时，说明服务端这一份不是本机正常上传的（拿到这台设备会话的人可以写一份格式正确、代次极大的垃圾信封）。这时上传方先 `DELETE /blobs/{本机}`，再用 `N = uploaded + 1` 上传。其他设备只在解密成功后才推进 `verified`，垃圾信封解不开，它们的下限仍不超过 `uploaded`，所以这一份照样被接受。

## 服务端接口

都在 `https://api.msime.app/v1/users/me/learning` 下，需要登录。错误一律是 `{"error":{"code":"...","message":"..."}}`。只有匿名身份的账号（有 anonymous 身份、没有任何非匿名身份）一律返回 403 `learning_requires_account`。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /?device_id=<id>` | 返回 `{"key_id", "wrap": {"wrap", "approver_device_id"}\|null, "devices": [{"device_id", "public_key", "name", "created_at", "last_seen", "approved"}], "blobs": [{"device_id", "key_id", "revision", "bytes", "updated_at"}]}`。`wrap` 是给请求里那台设备的封装 |
| `PUT /devices/{device_id}` | 请求体 `{"public_key", "name"}`，登记设备并绑定当前会话；已由同一会话登记时只更新名称，已绑定在别的有效会话上返回 403 `learning_device_mismatch`。一个会话只绑定一台设备：同一会话登记另一个编号时，原来那台连同封装和密文一起被替换。会话被吊销或过期时设备行级联删除，见下文「设备与会话同寿命」。每个账号最多 20 台设备 |
| `DELETE /devices/{device_id}` | 删除设备、它的封装和密文。用于拒绝待批准的设备和本机关闭功能；移除一台已批准的设备要走 `rekey`。删掉最后一台设备时一并删除 `key_id` |
| `POST /key` | 请求体 `{"key_id", "wrap"}`，只在账号还没有密钥时可建，封装给的必须是调用会话绑定的设备 |
| `PUT /wraps/{device_id}` | 请求体 `{"key_id", "wrap", "approver_device_id"}`，批准一台设备。`approver_device_id` 必须是调用会话绑定、并且持有当前密钥封装的设备 |
| `POST /rekey` | 请求体 `{"previous_key_id", "key_id", "wrap", "revoke": []}`，同一事务里确认当前密钥、删除 `revoke` 里的设备、删除全部密文和全部旧封装、写入新密钥和给调用设备的封装 |
| `GET /blobs/{device_id}` | 返回这台设备的信封原样字节（`application/octet-stream`） |
| `PUT /blobs/{device_id}?revision=N` | 请求体是信封原样字节。只允许调用会话绑定的那台设备写自己的那份 |
| `DELETE /blobs/{device_id}` | 只允许调用会话绑定的那台设备删自己的那份 |

服务端对密文只做格式检查，不尝试理解内容：

- 以 `MSL1` 开头，长度在 68 + 16 字节到 8 MiB 之间，`padded` 的长度（总长减 84）是 `padme` 的不动点。
- 头里的 `device_id_raw` 与路径一致，`generation` 等于 `N`、不超过 2⁵³−1（否则 400 `invalid_learning_blob`）。头里的 `key_id_raw` 不是账号当前的 `key_id`、或上传的设备不持有当前密钥的封装时返回 409 `learning_key_conflict`，而不是 400：换钥之后还在用旧密钥上传的设备据此知道要重新被批准，不会当成自己的信封写坏了。`N` 必须大于这台设备已存的代次（没有时为 0，删掉之后也是 0），否则 409 `revision_conflict`。这些检查在写入事务里做（比较并交换）。
- 不以 `MSL1` 开头、而以 `{` 或 gzip 魔数 `1f 8b` 开头的请求体，返回 400 `learning_e2e_required`，防止旧客户端或写错的客户端上传明文。
- 请求体用 `MaxBytesReader` 限在 8 MiB，指整个信封（明文头加密文），与「上限与额度」一致；超出返回 413 `learning_too_large`。路由超时 60 秒。
- 上传和下载密文时，每个服务端副本同时最多传输 8 份（每份整份放在内存里），在路由超时内等不到名额返回 503 `server_busy` 并带 `Retry-After`，不读请求体、不写入；客户端按 `Retry-After` 稍后重试。

设备与会话同寿命：

- 设备行绑定登记它的会话。会话被吊销（退出登录、在「我的设备」里撤销、封禁、刷新令牌重放）时立即删除设备；会话过期后由服务端每小时的清理删除，设备、封装和密文随之删除。账号因此没有设备时一并删除 `key_id`。刷新令牌不换会话，不影响设备。
- 会话最长 30 天，刷新不延长，所以一台设备最长 30 天就要重新登录、重新被批准，与「本机的密钥串」里退出登录即删除密钥串、重新登录要重新批准一致。服务端不允许新会话接管旧会话的设备：会话绑定是挡「泄露的会话令牌覆盖别的设备的密文」的那一道。
- 过期会话在清理之前，登记设备时服务端先删掉这个账号绑定在已过期会话上的设备，结果与清理相同，所以同一个设备编号在重新登录后也能登记，登记成未批准的设备。
- 「180 天没有请求的设备」那条清理按现在的会话时长不会先触发，它是独立于会话时长的规则，会话时长以后放宽时仍然生效。

## 上限与额度

| 项 | 上限 |
| --- | --- |
| 一台设备的信封 | 8 MiB，超出返回 413 `learning_too_large` |
| 一个账号全部密文合计 | 64 MiB，超出返回 413 `learning_quota` |
| 一个账号的设备 | 20 台，满了返回 409 `learning_device_limit` |
| 明文流记录数 | 500,000 条（不含 header 与 footer） |
| `key` / `value` / `display` / `context` | 512 / 2048 / 2048 / 1024 字节 |
| `weight` | 1 到 100,000,000 |
| `position` | 1 到 5 |
| `generation`（即 `revision`） | 1 到 2⁵³−1，JSON 里的数字和服务端的 `bigint` 都能精确表示；服务端拒收超出的，返回 400 `invalid_learning_blob` |
| `updated_at` | 1 到 2⁴⁰（约公元 36812 年），超出的按格式不对处理，见「明文流」 |
| 上传频率 | 客户端自动上传每小时最多一次，明文流的 SHA-256 没变时不上传；手动「立即同步」不限 |
| 服务端限流 | 每个用户写入（登记和删除设备、建钥、批准、换钥、上传和删除密文）每小时 120 次，读取（元数据和下载密文）每小时 960 次，超出返回 429 `rate_limit_exceeded`。按 20 台设备的用量定：一次换钥后重新批准要 1 次换钥、19 次批准和 20 次上传，20 台设备每小时自动上传又是 20 次写入；每台设备每轮自动同步读一次元数据、下载其余 19 台的密文，合计每小时 400 次读取。最初定的 `PUT` 30 次、`GET` 240 次在设备接近上限时不够 |
| 不在线的设备 | 180 天没有请求的设备，服务端删掉它的设备行、封装和密文；设备也随它的会话过期删除，会话最长 30 天 |
| 第二期整句联想 | 每台设备上传 5 万条，接收方远端合计 20 万行 |

明文流超过记录上限、或补齐加密后的信封超过 8 MiB 时，客户端截断后照常上传，并提示 `learning_too_large`，不让整份同步失败：

- 只丢 `weight` 行，按 `(updated_at, dictionary, key, value)` 从小到大丢，也就是先丢最久没动过的调权。`delete`、`pin`、`position` 行从不丢：丢了删除记录，对端会把删掉的词又造回来。
- 先按记录上限丢到不超过 500,000 条，再看信封大小，超过时继续按同样的顺序丢，直到放得下。截断只由学习数据本身决定，同样的学习数据总是截出同样的明文流，上传前比较的 SHA-256 是截断之后那份的。
- 只剩 `delete`、`pin`、`position` 仍放不下时这一轮不上传，仍提示 `learning_too_large`，其他设备的照常下载合并。
- 服务端返回 413 `learning_quota`（账号合计超额）时，本机暂停上传，其他设备的照常下载合并，不靠截断解决。

## 错误码

服务端返回：

| 状态 | `code` | 含义 |
| --- | --- | --- |
| 400 | `invalid_device_id` | `device_id` 缺失或格式不对 |
| 400 | `invalid_learning_device` | 公钥与编号不符、名称超长或含控制字符 |
| 400 | `invalid_learning_key` | `key_id` 或封装格式不对、封装对象没登记 |
| 400 | `invalid_learning_blob` | 信封格式不对（长度、补齐、头部与路径或 `revision` 不一致） |
| 400 | `learning_e2e_required` | 请求体看起来是明文 |
| 403 | `learning_requires_account` | 只有匿名身份的账号 |
| 403 | `learning_device_mismatch` | 写、删、批准所用的设备不是当前会话绑定的那台 |
| 404 | `not_found` | 设备或密文不存在 |
| 409 | `learning_key_conflict` | 已有密钥时建钥；请求或信封头里的 `key_id` 不是当前密钥；批准者或上传的设备不持有当前密钥的封装 |
| 409 | `revision_conflict` | `revision` 不大于已存的代次 |
| 409 | `learning_device_limit` | 设备已满 |
| 413 | `learning_too_large` | 单个信封超过 8 MiB |
| 413 | `learning_quota` | 账号合计超过 64 MiB |
| 429 | `rate_limit_exceeded` | 超出限流，带 `Retry-After` |
| 503 | `server_busy` | 服务端副本同时传输的密文已满，带 `Retry-After`，稍后重试 |

客户端驱动给宿主的（`status` 为 0，宿主只负责翻译成界面文案）：

| `code` | 含义 |
| --- | --- |
| `learning_disabled_locally` | 本机关掉了学习（`input.learning`、`platform.ios.dictionary_learning`、`platform.macos.candidate_learning`），没有可同步的东西 |
| `learning_waiting_approval` | 本机在等另一台设备允许，同时给出本机核对码 |
| `learning_sas_mismatch` | 用户在反向核对时点了「不一致」，密钥已丢弃 |
| `learning_key_rotated` | 账号换了密钥，本机要在其他设备上重新被允许 |
| `learning_too_large` | 本机的输入习惯超过上限，已丢掉最久没动过的调权后上传；连删除记录、置顶和固定位置都放不下时这一轮没有上传 |
| `learning_undecryptable` | 某台设备的密文解不开或格式不对，已跳过，带来源设备名 |
| `learning_rollback` | 某台设备的密文代次比见过的小，已拒收 |
| `learning_dictionary_mismatch` | 有设备的 `content_id` 与本机不同，照常合并，只做提示 |
| `learning_merge_pending` | 已下载，等持有词库的进程空闲时合并 |

## 服务端看得到的元数据

- 每台设备的名称、公钥、登记时间、最后在线时间、绑定的是哪个会话。
- 谁批准了谁（封装上的 `approver_device_id`）。
- 账号当前的 `key_id`，设备数量。
- 每台设备密文补齐后的大小、代次和上传时间。因为只在内容变了时上传，上传时间能看出这台设备大约在哪个小时里学到了新东西。
- 请求本身带的 IP 地址和时间，与其他账号接口相同。

## 本机的密钥串

learning 域的密钥串与云剪贴板的分开存放，名字是 `learning-keystore`，放在与 `cloud-clipboard-keystore` 相同的位置（各平台的位置见 [云剪贴板协议的密钥串存放位置](cloud-clipboard-e2e.md#密钥串的存放位置)），里面另外记着 `K_learn` 是否已经过反向核对。同一台设备的输入法、设置应用和面板共用一份；读、比、写在同一把跨进程锁里做完，不替换另一个设备身份，规则与剪贴板相同。退出登录时与会话一起删除，重新登录要重新批准。HarmonyOS 的键盘不生成身份，用设置应用经共享沙箱镜像过来的那份。
