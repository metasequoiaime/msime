# Windows packaging layout

The installer consumes a staging directory, not source-tree paths. `Prepare-PackageFiles.ps1` writes these inputs for `msime_setup.iss`:

| Staging path | Contents |
| --- | --- |
| `tsf_dll/32` and `tsf_dll/64` | `MetasequoiaImeTsf.dll` and matching symbols, the host DLL, and the runtime DLLs beside the 32-bit TIP (the x64 ones by the same names); the installer also puts the `tsf_dll/64` host and runtime DLLs into the Server folder, so `server_exe` does not carry them |
| `server_exe` | Windows Server, native WinUI 3 `msime-client-settings.exe`, the shared `MSIME.exe` panel shell, the `msime-mcp.exe` MCP server for AI assistants, and native resources |
| `app_data` | default configuration and runtime resources |

Native CMake targets come from the configured Windows build directory (`target/windows-full/<arch>` for full and `target/windows-<id>/<arch>` for another edition, as produced by `../Build-Client.ps1 -Edition <id>`). `Prepare-PackageFiles.ps1 -Edition <id>` takes that edition's host DLL name, resource lock and language dictionaries from `shared/contracts/editions.json` and writes `server_exe/edition.json` for an edition other than full; `Compile-Installer.ps1 -Edition <id>` passes `/DEdition=<id>` to ISCC, and `editions.iss` (generated by `../scripts/edition_windows.py gen`) supplies that edition's AppId, install directory, registry key, watchdog task and installer name. Without `/DEdition` the script compiles full exactly as before. The TSF DLL remains an in-process component and the Server remains out of process; packaging them together does not change that boundary.

For a release package, run `Sign-PackageBinaries-SimplySign.ps1` after staging. It selects the connected Certum code-signing certificate, signs every EXE/DLL under `server_exe` and `tsf_dll` in one signtool invocation, then verifies the certificate and trusted timestamp on every file. The local test-certificate script (`Sign-PackageBinaries-Local.ps1`) is separate and must not be used for public releases. After Inno Setup creates the outer installer, run `Sign-Installer-SimplySign.ps1` to apply and verify the same release signature and timestamp to the installer itself.

For the complete release sequence, use `Package-SimplySign.ps1`. It builds both architectures, stages the package, signs payloads, compiles Inno Setup with `Compile-Installer.ps1`, signs the outer installer, and writes `msime-windows-<edition>-<version>-symbols.zip` for the same build beside it in `Output` with `Collect-Symbols.ps1`; it never installs or modifies CI state. The release `release-windows.yml` publishes carries CI's unsigned installer and CI's symbols, which do not match the locally built binaries, so the maintainer replaces both the installer (with its `.sha256`) and the symbols archive on that release with the ones this script wrote. The installer is built on Windows, not in CI: the Windows CI job and `release-windows.yml` both stop at the MinGW cross build.

`msime_setup.iss` requires Inno Setup 6.6 or newer. It installs the 32-bit TSF DLL under `{commonpf32}\<install_dir>\msime_v<version>\` and the 64-bit (on Windows on Arm, Arm64X) TSF DLL, with the host and runtime DLLs it loads from its own directory, under `{sys}\IME\<install_dir>\msime_v<version>\` (`MySystemTipDir`), each with the `regserver` flag so the TIP is registered; Counter-Strike 2's Trusted Mode refuses foreign DLLs outside the Windows system directory, so a 64-bit TIP under Program Files never loads there. The System32 copies carry `uninsrestartdelete`, and because a Setup compiled with Inno Setup 7 is a 32-bit process whose `[Code]` file functions and `Exec` are redirected to SysWOW64 (Inno Setup 6 bypasses redirection there in 64-bit install mode), the script probes and cleans that directory only through `cmd.exe` and a 64-bit PowerShell launched with `ExecNativeSys`, which is `ExecWithNativeSysDir` under 7 and `Exec` under 6; stopping the Server by path goes through the same macro. It puts the Server package under `{commonpf64}\<install_dir>\server`, writes `VersionDir`, `ServerPath` and `DataDir` under `HKLM\<registry_key>` (both from the edition's `platforms.windows` section; full uses `metasequoiaime-full` and `Software\Metasequoia\MetasequoiaIME-Full`, while `metasequoiaime` and `Software\Metasequoia\MetasequoiaIME` belong to msime-windows), and copies `config.toml` only when it does not already exist so an upgrade never overwrites user configuration. `THIRD_PARTY_NOTICES.txt` and `LICENSE.txt` ship with the package, as GPLv3 sections 4 and 6 require. `ISCC /DLightPackage=1` produces the light package, which omits the bundled dictionaries. PDB and `.ilk` files stay in the staging folders but are not installed; `Collect-Symbols.ps1` packs the staged PDBs, plus the host DLL's from each architecture's build output, into `msime-windows-<edition>-<version>-symbols.zip`, which `release-windows.yml` and `Package-SimplySign.ps1` both write beside the installer, and an upgrade deletes the PDBs older packages left in the Server folder.

Build the native WinUI 3 settings project and the shared Tauri panel shell before staging. `Prepare-PackageFiles.ps1` accepts the native settings executable through `-DesktopExecutable` (defaulting to `target/windows-full/x64/bin/msime-client-settings.exe`) and an optional `-DesktopPreviewExecutable`; the consolidated build discovers both beside the Server automatically. Both full and light packages include the two binaries under the names resolved by the native shell launcher. A missing settings binary is rejected before resetting the existing staging directories. The shared panel shell still needs WebView2; the WinUI 3 settings window does not.
