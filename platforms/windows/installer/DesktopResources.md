# Shared desktop resources in Windows packages

Full `Prepare-PackageFiles.ps1` runs require the exact resource set in `resources/desktop-dictionary.lock.json`. Download that pinned release's files into `target/desktop-resources`, or pass `-DesktopResourcesDirectory` with an absolute path or a path relative to `RepoRoot`.

Every listed file must match its pinned byte length and SHA-256 before staging directories are reset. Only manifest-listed files are copied, retaining their original names, including the licence texts that must travel with the data: `msime-mozc_dictionary_oss_README.txt` and `msime-mozc_LICENSE.txt` for `msime-japanese.dat`, `msime-scowl_Copyright.txt` for `msime-english.db`. 现代 full 和拼音包不把日文词典组、`msime-wubi.db` 写进 `server_exe/resources`；用户在设置应用里选用这些方案时，设置应用把它们下载到通过校验的 `resource-packs` 目录。五笔版保留 `msime-wubi.db`，日文版保留日文词典组，因为它们分别是默认方案。Windows 7 没有资源包入口，继续保留完整词库。暂存后还会由 `Get-VerifiedDesktopResources.ps1` 再验一次。结果位于 `server_exe/resources`，Inno 的 Server 递归规则把它装进 Program Files 的原生程序目录；脚本不会下载或跟随任何资源地址。

Light packages neither require nor carry this bundle. A stale `resources` directory copied from native build output is removed from light staging, not from the installed application. Full packages likewise replace native-output resources with only verified files.

`app_data` is the second staging destination and carries no dictionary: it holds the helpcode tables, the audio cues, the built-in sound packs from `resources/sound-packs` (as `sound-packs`) and the factory `config.default.toml`. The application icon comes from `installer/assets`. `HelpCodeDirectory` defaults to `resources/helpcodes`; only its `*.txt` tables are staged, and its notices reach the package through `THIRD_PARTY_NOTICES.txt`. The offline handwriting model and the desktop settled-rerank model are not staged: the settings app downloads them on demand into the data directory's `resource-packs`, verified against `resources/handwriting-model.lock.json` and `resources/settled-model.lock.json`, and the handwriting model arrives with its `HandwritingModel-LICENSE.txt`. Neither `server_exe/handwriting` nor `server_exe/settled-model` exists in the package, even when an earlier build left `target/handwriting-model` or `target/settled-model` behind.

Offline glosses for non-English translation targets are optional and sit beside the verified directory rather than in it, as `server_exe/offline-glosses`: one `zh-<lang>.db` per language built by `scripts/build_offline_glosses.py`, staged from `target/offline-glosses` together with `offline-glosses-NOTICE.txt`, and only when that notice is present. `resources/offline-glosses.lock.json` records their source and license; see `docs/third-party.md`. Without them, candidate glosses stay English only. Light packages never carry them.

The two keystroke rerank models that 整句联想「增强」 runs on (chinese-ime-lm `rerank-v2`, 8x448 and 6x256, in ONNX Runtime's ORT format) are staged beside the verified directory as `server_exe/rerank-model` and `server_exe/rerank-model-small`, each holding `lm_step.ort`, `model.json` and `vocab.json`. `scripts/fetch_rerank_model.py` downloads them into `target/rerank-model` against `resources/rerank-model.lock.json`; staging checks every file's length and SHA-256 against that lock before touching the previous staging and copies only the files it names. The Server names its own directory to its sessions as `rerank_models` (`src/system/RerankModelRoot.h`), and the x64 host DLL it loads is built with the ONNX Runtime backend (`../Build-Client.md`); without the models it falls back to the sentence model in `resources`. Only editions whose edition table entry has `features.neural_keyboard` carry them (full and pinyin); light packages and Windows 7 packages never do, the latter because the Windows 7 host does not link ONNX Runtime. Release builds set `MSIME_REQUIRE_RERANK_MODELS=1`, which refuses a package that should carry them and does not. The models add about 39 MB uncompressed under Program Files.

The official plugin packs (the uuid script plugin and the latex-symbols phrase table that `plugins/official-packs.json` lists) are staged from `target/plugin-packs`, which `scripts/build-official-plugins.sh` builds and checks against the locked content hash, into `server_exe/plugin-packs/<kind>/<id>/`. Inno installs them with the Server under Program Files, where only administrators can write, and `[InstallDelete]` removes the previous set first, so a pack a newer version drops does not stay listed as built in. They never go to `app_data`: the data directory is writable by the user, and a pack there could be swapped for anything. The Server names the directory to its sessions as `plugin_packs` (`src/system/PluginPackRoot.h`) and both settings shells look for it beside their own executable. A package built without them installs without official packs; release builds set `MSIME_REQUIRE_OFFICIAL_PLUGINS=1`, which refuses that.

Third-party notice collection is separate from resource staging: packaging still requires `THIRD_PARTY_NOTICES.txt` through `NoticesDirectory`. Do not bypass that requirement or treat these resource checks as a distribution license audit.

`msime-client-prepare.exe` consumes the installed resource directory to create fresh per-user HostOptions. The production Server runs the same preparation flow automatically when its user state directory is absent; an existing state directory is never rebuilt on its own. See `../PrepareHost.md`.

The package fixture (`tests/package-files.ps1`) uses a synthetic manifest and synthetic files, verifies the output hashes, checks both size and same-size hash corruption, excludes unlisted files, preserves previous staging on preflight failure, and checks that light packages omit resources. Synthetic bytes are what make the corruption cases possible; the real release bytes are checked by the pinned length and SHA-256 gate above.
