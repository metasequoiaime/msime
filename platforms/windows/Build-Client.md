# Client Windows build entry

Run `Build-Client.ps1` in a Windows MSVC environment with CMake, Cargo, pnpm, the x86_64-pc-windows-msvc, i686-pc-windows-msvc and aarch64-pc-windows-msvc Rust targets, the Visual Studio ARM64 and ARM64EC build tools (`Microsoft.VisualStudio.Component.VC.Tools.ARM64` and `...ARM64EC`), and clang on PATH: ring, which the host links, assembles its ARM64 code with clang only. Visual Studio's own clang (`Microsoft.VisualStudio.Component.VC.Llvm.Clang`, `VC\Tools\Llvm\x64\bin`) will do. Supply separate absolute native dependency prefixes with the packages listed in `vcpkg.json`:

```powershell
.\platforms\windows\Build-Client.ps1 -X64Dependencies C:\deps\x64 -X86Dependencies C:\deps\x86
```

The Rust half of the client (the x64, x86 and ARM64 host DLLs, the MCP server and the Tauri panel shell) does not depend on the edition, so it is built by `Build-RustOutputs.ps1 -Architecture x64|x86|arm64 -OutputDirectory <dir>`, which collects each architecture's outputs under fixed names in `<dir>/<arch>`. `Build-Client.ps1 -RustOutputs <dir>` takes them from there and runs no cargo or pnpm command; this is how `release-windows.yml` builds the Rust half once, one job per architecture in parallel, for all six editions. Without `-RustOutputs`, `Build-Client.ps1` runs `Build-RustOutputs.ps1` itself for all three architectures into `target/windows-rust`, so a local build needs the Rust toolchain, pnpm and clang listed above.

The default CMake generator is Visual Studio 2022. Each prefix must contain libraries built for its architecture and a compatible MSVC runtime; this script does not download or build dependencies, alter Rust toolchains, sign binaries, register TSF, invoke CI, or install the input method.

The x64 build includes Server, Watchdog, preparation tool, native WinUI 3 settings and TSF. The x86 build contains the in-process TSF and matching Host DLL, not another Server. The arm64 build contains the TSF DLL for Windows on Arm, which is [Arm64X](https://learn.microsoft.com/windows/arm/arm64x-build): native ARM64 processes (Explorer, Edge, Notepad) and emulated x64 processes load it through the same registration, so it carries ARM64 code for the first and ARM64EC code for the second. `tsf/CMakeLists.txt` links it in two passes (`MSIME_TSF_ARM64X=ARM64`, then `ARM64EC`, sharing the linker response file the first one writes). The ARM64 half imports an ARM64 host DLL built here with a static C runtime and named after the edition's host DLL with `_arm64` appended (`msime_host_api_arm64.dll`); the ARM64EC half imports the x64 host DLL, which runs emulated. Everything else stays x64 and runs emulated on Windows on Arm. Native outputs go to `target/windows-full/<arch>/bin`. Rust release artifacts remain under the explicit target triple, with debug information enabled; native CMake uses RelWithDebInfo. The WinUI 3 project is built self-contained and staged as `msime-client-settings.exe`; the shared Tauri panel shell is built without bundling, typechecked, and staged as `MSIME.exe`. Both PDBs are retained beside their executable. Missing settings output, or missing or ambiguous Tauri symbol output, fails the build. Packaging prefers the staged WinUI settings binary when no `DesktopExecutable` override is supplied, falling back to the old Cargo path only when it is absent. An explicit override never silently falls back and never inherits unrelated symbols.

The x64 build also stages the on-device speech runtime beside the Server: `python scripts/fetch_voice_runtime.py --platform windows-x64` downloads the sherpa-onnx release pinned in `resources/voice-runtime.lock.json` into `target/voice-runtime/windows-x64`, discards it unless its SHA-256 and size match, and reuses a verified copy on later runs; `sherpa-onnx-c-api.dll`, `onnxruntime.dll` and `onnxruntime_providers_shared.dll` are then copied into the x64 bin directory and pass the same x64 PE gate. The Server loads them with LoadLibrary from its own directory at the first local dictation, so they must stay beside it. They are upstream MSVC `/MD` builds and need the VC runtime the installer already requires. The build therefore needs Python and network access to GitHub on its first run. It does not fetch the offline handwriting model or the settled-rerank model: the installer does not carry them, and the settings app downloads them on demand.

Every native command exit status is checked immediately. The caller's directory and dependency prefix, and in `Build-RustOutputs.ps1` the Cargo target directory, release-debug setting, ARM64 Rust flags and `MSIME_VERSION`, are restored on success or failure. `tests/tools/build_client.ps1` tests the orchestration using command probes, including failure at every stage; it drives probes rather than a compiler, so it covers the ordering and the error handling, not the native build itself or its runtime dependency closure.

Before reporting completion, the build reads PE headers from all six x64 EXE outputs (`MetasequoiaImeServer.exe`, `MetasequoiaImeWatchdog.exe`, `msime-client-prepare.exe`, `msime-mcp.exe`, `msime-client-settings.exe`, `MSIME.exe`), the three x64 voice runtime DLLs, the TSF/Host DLL pair for x64 and x86, and the Arm64X TSF DLL with its ARM64 host DLL; for the Arm64X DLL it also requires the hybrid metadata that only an Arm64X image carries, so a plain ARM64 build cannot pass. It rejects missing or truncated headers, wrong machine or optional-header type, and EXE/DLL flag mismatches. `Test-PortableExecutable.ps1` can also inspect individual outputs without loading them. Header fields follow Microsoft's [PE format specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format). This is an architecture/type gate, not full image validation, signature checking, import resolution or Windows runtime verification. Parser fixtures intentionally contain only synthetic headers; they are not executable images.

The build also collects top-level release `bin/*.dll` from each explicitly provided dependency prefix. Every candidate passes the PE architecture/DLL gate before copying; same-named different output content causes failure rather than overwrite. Identical files are reused. Static prefixes may have no bin directory. Debug subdirectories and non-DLL files are not copied. Each TSF staging directory carries these ordinary dependencies without COM registration; the Server package already copies its output directory recursively.

This collects all release DLLs from the supplied prefixes, not only imported ones. It is not recursive import analysis: Windows components, VC runtime redistribution and dynamically loaded modules outside those prefixes still need explicit provisioning and verification. Distribution must retain the licenses for supplied dependency packages; prefix collection is not a license audit.

`installer/test.ps1` and `test-light.ps1` call this entry through the shared local install workflow. They require both dependency prefixes and an explicit notice directory, then stage, self-sign, compile and launch the installer. Use this build-only entry when those local-machine side effects are not intended. See `installer/LocalInstall.md` for scope and verification limits, and `installer/README.md` for the signed release sequence.
