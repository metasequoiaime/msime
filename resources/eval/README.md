# 整句转换评测集

在此之前仓库没有任何衡量拼音→中文转换质量的手段。词图、回退解码器、以及将来任何重排，做完都无法说明变好还是变坏——这个目录提供那个数字。

跑法：

```sh
cargo run --release -p msime-input-runtime --example convert_eval -- \
  --resources <已校验的词库目录> \
  --set resources/eval/sentences-v1.tsv \
  --baseline resources/eval/baseline-sentences.json
```

`--update-baseline` 接受当前结果。`--limit N` 取等距子集（不是前 N 条，否则全是短词）。

`--keyboard-neural` 额外启用引擎内的键盘神经联想，用随资源提供的键盘模型混合评分词网格路径，验证全拼、双拼、九键与十四键共用的混合评分。默认关闭，保持现有质量基线的测量方式；runtime 挂载的重排器仍按资源里有没有模型决定。这两层排序不同，修引擎内的模型评分时必须显式加这个开关。

**基线是带重排的数字。** `sentence-model.safetensors` 已经在 `desktop-dictionary.lock.json` 里，所以按锁文件取到的资源目录一定带它，而 `convert_eval` 见到模型就会挂上重排器。想量引擎单独的表现，把模型从资源目录里拿掉再跑——它会打印 `no model at ...`，那一行是判断当前测的是哪个臂的唯一依据。

## 延迟基准

同一批输入还用来量重排的代价。`convert_eval` 回答「排得对不对」，`rerank_latency` 回答「一次按键为此多花多少毫秒」：

```sh
cargo run --release -p msime-input-runtime --example rerank_latency -- \
  --resources <已校验的词库目录> \
  --set resources/eval/sentences-v1.tsv
```

需要资源目录里有 `sentence-model.safetensors`——它量的就是重排的开销，没有模型就没有可量的东西。`--budget-ms` 默认 16（一帧），p95 超出即以非零码退出；`--warmup N` 丢弃前 N 条用例的样本（默认 5）。`--grid nine` 在九宫格上打（字母换成键上的数字，同 `convert_eval --grid nine`，`--nine-key` 是它的旧写法），量九键长串每次按键的开销；`--grid fourteen` 在全拼 14 键上打。

同进程里开两个 runtime，一个挂重排一个不挂，逐条交替先后顺序，按键**配对**相减。配对是必须的：真正要问的不是一次按键多久，而是**因为重排**多了多久，两次独立运行的差值里混着散热状态和页缓存。

**要看超预算的按键占比，不要只看均值。** 多数按键根本不走重排（三音节以下词图不跑，只有一条读法时也无从选择），均值把少数按键的代价摊到了全部按键上。6.8M int8 在整句集上均值只多 7.9ms，看着在预算内，实际是 25.2% 的按键超过一帧。

## 两个集，测的不是一回事

### `quanpin-words-v1.tsv` — 25,119 条词级

由 `build_eval_set` 从 microsoft/Windows-classic-samples 的 `SampleIMESimplifiedQuanPin.txt` 固化而来，MIT 授权，本仓库不收录该文件，没有任何构建脚本读它，也不进入 `msime-pinyin.db`，所以一次性固化进仓库；重新生成需要自备那份源文件。

生成时丢弃 27,561 条单字、1,955 条截断条目，无解析失败。截断过滤用 Engine 自己的 `normalize_full_pinyin` 判断「key 能否恰好切成 gold 字数个音节」，而不是长度阈值——该格式在 12 字符处截断，但 `chulufengma`、`shumenshul` 这类更短的 key 同样被砍，长度阈值漏得掉。

**它测的是词典命中与排序，不是整句能力。** 实测 `gold_source` 几乎全是 `database`，词图一次都没有贡献过正确答案。

**不要用 `msime-pinyin.db` 自身出题。** 它就是解码器查的那张表，等于让系统考自己；而 1–2 音节的排序实现就是 `ORDER BY weight DESC`，拿 weight 当金标准是在考 SQLite。

#### `--nine-key`：同一个词级集在九键上打

`convert_eval --nine-key` 打开 Runtime 的九键模式，把每条用例的字母换成键盘上印在旁边的数字（a–c 是 2，w–z 是 9）再逐键输入，金标准不变。全键盘上 xi'an 和 yi'an 是两个输入，九键上是同一串 9426，所以权重口径不一致的词在这里才暴露出来（一按 压过 西安）；全拼的数字测不到这一层。

`verify-local.sh` 以 `--limit 3000 --nine-key` 跑它，对照 `baseline-nine-key.json`。完整 25,119 条上，2026-10-06 在当时锁定的 dict-v2.0.13 上量到九键 top-1 0.552、top-5 0.826，全拼是 0.753 / 0.941（同一份词库，挂着重排模型）：九键比全键盘少对两成，这个差距就是九键排序要追的东西。换到 dict-v2.0.39 后全拼是 0.756 / 0.945，完整九键因构建机过载没有重跑，所以新词库上的两者差距还没有量过。

### `sentences-nine-key-v1.tsv` — 81 条九键长句

手写的合成短句，4 到 12 个字每档 9 条，`verify-local.sh` 以 `--nine-key` 跑它，对照 `baseline-nine-key-sentences.json`。这份集合建于九键一次最多 32 个数字的时候，每条都在 32 个字母以内，12 个字的句子也能整串打完；当时 `sentences-v1.tsv` 11 个音节以上的 7 条里有 6 条超过 32 个字母，`sentences-neutral-v1.tsv` 1105 条里也有 279 条超过，在九键上金标准打不出来。上限现在是 48 个数字（`crates/engine/src/nine_key.rs` 的 `DIGIT_LIMIT`，#9392），到上限时先选首选再接着打；按 48 算，超过的只剩 `sentences-v1.tsv` 的 1 条和 `sentences-neutral-v1.tsv` 的 30 条。金标准的取舍与 `sentences-v1.tsv` 相同，另外不收 ta 开头或句中带 他/她 的句子（#6059）。

同一份集合在全键盘上打（不带 `--nine-key`）是九键要追的参照：按切分路径各自解码时（#6377），九键 top-1 0.457、found 0.556；按键之间沿用前几次的好切分、跨切分比较时每个词组多扣一份奖励之后（#6059），0.506 / 0.617；全键盘 0.691 / 0.716。九键按键延迟用 `rerank_latency --nine-key` 在这份集合上量，见上文的「延迟基准」。

### `sentences-particles-v1.tsv` — 103 条常用词接句末语气词

常用的两字词后面接一个句末语气词（债券吗、标注呀、相关吧），全键盘、九键、14 键各打一遍，`verify-local.sh` 以 `particles`、`particles-nine-key`、`particles-fourteen-key` 跑它，对照同名基线。词级集的金标准几乎都是词库里的词，整句集是书面长句，都量不到这种口语短句；而词网格的 n-gram 表只有句首记号、没有句尾，又是从维基百科统计的，句尾的吗、呀、吧只能按单字词频和同音或同码的那、亚、把比。用例从锁定词库按权重靠前的两字词里抽出，取舍写在文件头。

句末语气词加分（`SENTENCE_FINAL_PARTICLE_BONUS`）和叠字叹词不拿词组奖励之前与之后，top-1：全键盘 0.524 → 0.680，九键 0.146 → 0.194，14 键 0.282 → 0.311；top-5 九键 0.641 → 0.728、14 键 0.650 → 0.854。九键剩下的失败大多是整串数字被解成完全不同的读法（一词全码、此案蛀牙），这是词组边按 `ln(权重)`、单字边按 `ln(权重 / 10⁶)` 计分的口径差，见[句末语气词笔记](../../.agents/notes/implemented/bug-fix/2026-10-23-sentence-final-particles.md)。

### `--grid fourteen`：同两份集合在全拼 14 键上打

`convert_eval --grid fourteen` 打开 Runtime 的 14 键网格，把每个字母换成它所在键的组码（QW 键是 q，BN 键是 b，即每组的首字母），用宿主触屏键面用的 `GridKey` 逐键送进去，金标准不变。14 键与九键是同一套解码（`KeyGrid`），只换码表：421 个全拼音节在九键上是 218 种码，在 14 键上是 314 种，重码少了，所以同一份集合上 14 键应当不低于九键。`verify-local.sh` 以 `fourteen-key`（`quanpin-words-v1.tsv --limit 3000`）和 `fourteen-key-sentences`（`sentences-nine-key-v1.tsv`）跑它们，对照 `baseline-fourteen-key.json` 和 `baseline-fourteen-key-sentences.json`。

同一次 release 构建、同一份代码，挂 `sentence-model.safetensors`，分别在换锁前的 dict-v2.0.24 和现在锁定的 dict-v2.0.39 上跑（[换锁笔记](../../.agents/notes/implemented/bug-fix/2026-10-27-dictionary-lock-latest.md)）：

| 集合 | 词库 | 九键 top-1 | 九键 top-5 | 14 键 top-1 | 14 键 top-5 |
|---|---|---|---|---|---|
| `quanpin-words-v1` 3000 条（实取 2791） | dict-v2.0.24 | 0.571 | 0.847 | 0.658 | 0.903 |
| | dict-v2.0.39 | 0.518 | 0.815 | 0.619 | 0.888 |
| `sentences-nine-key-v1` 81 条 | dict-v2.0.24 | 0.642 | 0.667 | 0.667 | 0.691 |
| | dict-v2.0.39 | 0.519 | 0.605 | 0.580 | 0.654 |

两行用的是同一个二进制，差别全部来自词库数据：dict-v2.0.30 起词库仓库把与万象共有的单字和词语的权重改成按万象词频换算的值（[msime-dictionary#84](https://github.com/metasequoiaime/msime-dictionary/pull/84)），单字和多字词的权重都大幅变动（摆脱 199375→80850、拜托 53420→171736；散步 101880→64915、跑步 66055→335220，两者在九键上同码），同码、同音词的先后因此被改写，九键和 14 键的重码最多，掉得也最多。共享词网格扣除每词插入代价那次改动的前后对照在 dict-v2.0.24 上量，见文末的评分决策笔记。

`rerank_latency` 在同一锁定资源上交替测量修复前后三轮，挂着重排模型的 p95 中位数九键 21.65→21.22 ms、14 键 20.57→19.37 ms；全拼 8.12→7.56 ms。九键、14 键前后都超出 16 ms 的帧预算，现有长串延迟缺口仍在；本次未观察到新增退化。详细对照条件见文末的评分决策笔记。

14 键的重码集中在少数几组上：bi/bu/ni/nu、xi/xu/zi/zu 这样的四重码，shi/shu，以及 sha 对 a'ga 这类跨音节的歧义。同一串组码下谁排第一只看词库权重，harness 又关掉了学习，所以这里量到的是新用户的第一次输入。BN UI GH AS OP（`bugao`）在锁定词库（dict-v2.0.39）里首选是「不好」（权重 1294182），「你好」（705916）第二；九键上两者是 28426 和 64426，不相遇。三端的手工验收以「你好」出现在候选里、点读音行的 ni 后成为首选为准。

### `sentences-v2.tsv` — 310 条收割，带上文

从 C4 中文部分（ODC-BY，保留标点的原文，不是 `corpus/fetch.py` 剥过标点的训练语料）收割：把句子用 Engine 的拼音表转成拼音再打回去，首选与原句不同的收下来，上文取同一篇的前一句。`harvest_eval_set` 做这件事，`scripts/review-harvested-cases.py` 用 Jev 过一道评审（选中原文且无强歧义否决），再按拼音+原文去重。500 条收割 → 345 条通过 → 310 条。

**它不是准确率基准，用错了会得出荒谬结论。** 用例是按「产品当前打错」筛出来的，所以 `top1` 天生偏低（收割时是 0.308，锁定的 dict-v2.0.39 上是 0.494），拿它和 v1 相减没有任何意义。它回答的是另一个问题：**已经打错的那些里，有多少是排序够得着的**——收割时 `top5` 是 0.776，dict-v2.0.39 上是 0.772，即近八成的正确答案就在前五名，剩下两成多要解码器出力。收割时要求金标准必须出现在候选列表里（`hanzi_to_pinyin` 对多音字不总是对，键错了原句永远解不出来，那种用例是废的），所以对着 C++ Engine 加 Google 整句解码器收割时 `found` 是 1.000；Google 解码器删掉后，只有它给得出的答案没了，`found` 在锁定的 dict-v2.0.39 上是 0.885（v2）和 0.878（neutral），dict-v2.0.24 上是 0.939 和 0.928。

想要有代表性的准确率集，得不筛成败地随机抽样，那是 `harvest_eval_set` 换一个判断条件的事，不是换一份语料。

**已知杂质**：网页文本按标点切句，少数用例是切出来的半句（「是一次意气风发」）。金标准仍是原文、拼音仍解得出来，所以测的东西没变，只是读起来不像完整句子。

**它和 v1 互补，不替代 v1。** v1 是手写的、干净的、无上文的，量的是「常见句子排得对不对」；v2 是收割的、带上文的、全是硬骨头，量的是「排错的还有多少救得回来」。两个都在 `verify-local.sh` 里。

**但 v2 不能用来比较多个重排器。** 它收割时挂着产品在用的那个模型，于是用例的定义就是「这个模型会错的句子」——同一个模型在上面必然接近零分，而没参与收割的模型不受这个约束。实测：挂 4.25M 收割的一批上，4.25M 是 0.000，24.9M 是 0.699，两个数字放进一张表毫无意义。要跨模型比较用下面那份。

### `sentences-v1.tsv` — 60 条整句，手写

整句语料在仓库里不存在，磁盘上也没有任何 bigram 计数，所以这部分只能手写。金标准是「母语者在该拼音串下唯一自然的写法」；拼音本身就有两种同样自然写法的句子一律不收——评测集不能既诚实又有歧义。

**n=60 的统计分辨率：单臂比例的 95% 置信半宽约 ±13 个百分点。** 聚合数字的小幅变动不构成证据。两次运行要逐条比对每个 gold 的 rank，而不是对着汇总值做减法。基线 JSON 因此保留了分标签、分音节数和失败样例。

标签分布：`function-word` 10、`seg-ambiguity` 12、`homophone` 12、`number-measure` 6、`name-place` 6、`long-sentence` 8、`short-phrase` 6。人名一律是常见姓 + 通用名，不含真实个人信息。

### `sentences-neutral-v1.tsv` — 1105 条整句，中立收割

和 v2 同一套流程，差别只有一处、但决定了它的用途：**收割时不挂任何模型**，让引擎单独产出候选。于是用例的定义是「引擎会错的句子」而不是「某个模型会错的句子」，集合对所有重排器一视同仁。名字里的 neutral 就是这个意思。

**它是用来比较重排器的。** 手写的 60 条上，4.25M 与 24.9M 只在 3 条上判定不同，McNemar p=0.25——扔三次硬币全同向就是这个数；这 1105 条上两者分歧 272 条，p=4.9e-38：

| 打分器 | 命中 /1104 | |
|---|---|---|
| 引擎原序 | 9 | 0.008，按构造 |
| 4.25M | 687 | 0.622 |
| 24.9M | 889 | 0.805 |

它对引擎不中立——按构造引擎原序在上面几乎全错，那一行只用来确认集合确实由引擎的失败组成。

**分辨力是它存在的理由。** 手写的 60 条上，4.25M 与 24.9M 只在 3 条上判定不同，McNemar p=0.25——扔三次硬币全同向就是这个数；在这 1105 条上，两者分歧数以百计。

**收割时没有挂任何模型。** 挂着某个模型收割，等于把用例定义成「它会错的句子」，再拿它评测同一个模型只会得到 0.000（实测：挂 4.25M 收割的集合上，4.25M 是 0.000，没参与收割的 24.9M 是 0.699）。这份对重排器中立，但对引擎不中立——按构造，引擎原序在上面几乎全错。

**已冻结。** 改一条或加一批都发 v2，这样今天量的数字和一年后量的仍然可比。

语料署名（C4 为 ODC-BY）写在文件头里，随文本传播。

## 双拼与触屏误触

`--scheme shuangpin` 把同样的全拼用例编成 26 键双拼的按键再打，`--touch-mode` 在参考键位几何上合成误触和落点，量双拼纠错（纠错整句）能把按错的键纠回多少、会不会碰坏打对的输入。触点模式像触屏宿主那样先注册几何（`Runtime::set_key_geometry`），每键带上按下点（`Runtime::set_key_touch`，即 `msime_client_touch_character` 走的那条路）再派发，量的是按落点计价的纠错；加 `--no-touch-points` 只送按到的键、不送落点，量的是引擎收不到触点时按方案键位生成邻键和对调变体的「平面表」。评测的设计见[评测笔记](../../.agents/notes/implemented/testing/2026-10-27-shuangpin-touch-eval.md)，触点计价和调参见[触点纠错笔记](../../.agents/notes/implemented/feature/2026-10-27-shuangpin-touch-correction.md)。

```sh
cargo run --release -p msime-input-runtime --example convert_eval -- \
  --resources <已校验的词库目录> \
  --set resources/eval/sentences-v1.tsv --set resources/eval/sentences-neutral-v1.tsv \
  --set resources/eval/sentences-v2.tsv --set resources/eval/sentences-particles-v1.tsv \
  --scheme shuangpin --shuangpin-profile xiaohe,ziranma,shoudao,microsoft,smart_abc --autocorrect \
  --key-geometry resources/eval/key-geometry/android-portrait.json \
  --key-geometry resources/eval/key-geometry/android-portrait-microsoft.json \
  --touch-mode none,clean,noisy,realistic --touch-sigma 0,0.15,0.25,0.35 --touch-bias-y 0,0.1 \
  --seed 20261027 --jobs 5 --assert-top1-unchanged \
  --baseline resources/eval/baseline-shuangpin-touch-sentences.json
```

词级那一份把四个 `--set` 换成 `--set resources/eval/quanpin-words-v1.tsv --max-syllables 2 --limit 3000`，对照 `baseline-shuangpin-touch-words.json`。两份基线各跑一次完整的组合（5 个方案 × 4 种模式 × 4 个 σ × 2 个偏置，none 模式不分 σ 和偏置），送落点、用引擎默认的计价参数。送落点时每条用例的触点各不相同，记忆表帮不上忙，所以加 `--jobs 5` 让五个方案各开一个线程同时跑（输出与一个一个跑逐字节相同），再加 `--assert-top1-unchanged`。在同时跑着 CI 的 Mac Studio 上整句那份要几个小时（看负载）、词级那份十分钟上下，没有放进 `verify-local.sh`。引擎收到触点之前的平面表数字用同样的命令加 `--no-touch-points` 复现。

`--assert-top1-unchanged` 逐条比较 clean 与原样输入的实际首选文本，候选表从空到非空也算变化。报告里的 `top1_changed` 保留平面表基线的定义，只计原本排第一的金标准降位；它为 0 不代表所有实际首选都相同。

**基线只用 `desktop-dictionary.lock.json` 那一组文件加 `sentence-model.safetensors` 生成，资源目录里不放 settled 模型 `sentence-model-desktop.safetensors`。** 那个文件由另一份锁 `settled-model.lock.json` 发布，`convert_eval` 见到它就挂上 settled 重排，排序会变，两份双拼基线就对不上了，并不是产品改了。跑的时候 stderr 必须打出 `no settled model at ...`；打出 `settling with ...` 时先把那个文件挪出资源目录。

**编码。** 用例的输入是不带分隔的全拼，先按 TSV 里的音节数切成音节，只认只有一种切法的（`fangan` 两个音节可以是 fang'an 也可以是 fan'gan，金标准是哪一个说不清，不打）。切音节按与方案无关的音节表（`host::is_shuangpin_syllable`），不按某个方案编不编得出来，所以有没有歧义在五个方案上判断得一样。再用引擎自己的表（`host::encode_shuangpin`）逐音节编成两键码。切不开、有歧义或有音节在这个方案里编不出来的用例丢掉，每个方案编出来的条数写在报告的 `encoding` 里。纠错整句不接受手打的 `'`，所以按键里不带它。

**几何。** `key-geometry/` 下是宿主下发给引擎的同一种 JSON：`id` 是非零代次，`keys` 是 a 到 z 的 `[cx, cy, w, h]`，`semicolon` 是微软双拼显示的 `;` 键（没有为 `null`），`duplicates` 是分离键盘里重复的字母键 `["g", cx, cy, w, h]`。坐标是各平台自己的单位（dp、pt、vp），y 向下。宿主只在微软双拼下显示 `;`，第二行因此多一个键、键宽也不同，所以每个平台有一份不带 `;` 的和一份 `-microsoft`：给多份 `--key-geometry` 时，用 `;` 键的方案（按引擎的判据，内置方案里只有微软双拼）取带 `;` 的那份，其余方案取不带的。带 `;` 和不带 `;` 的各最多给一份，同一种给了两份会报错，不管这次跑的方案用不用得上它、也不管是不是只跑 `none`；报告的 `geometry` 只列实际用上的几何。这几份是按常量构造的参考布局，不是真机导出的：Android 按 `KeyboardGeometry` 的 `DESIGN_*` 常量（411 dp 宽、左右各留 6、键距 5、键高 46、行距 8）、第二行铺满宽度（`ImeLetterRows`）、末行大小写和删除各 1.4 个键宽（`KeyboardActionRow.DESIGN_LETTER_EDGE_WEIGHT`）；iPhone 按 390 pt 宽、键距 6、键高 42、行距 7，不显示 `;` 时第二行和第一行同宽同距、两端各缩进按键区宽度的 5%（`KeyboardLayoutPreference` 的 `letterInsetRatio`，恰好半个键距）；HarmonyOS 按 360 vp 宽、`KeyboardMetrics` 的键距 6、键高 44（`ROW_HEIGHT_VP`，默认高度调整为 0）和行距 7、不显示 `;` 时第二行两端各缩进半个键；`ipad-split` 是 iPad 横屏两个 360 pt 的半边、右半边内侧重复 G 和 V，没有微软双拼的版本。宿主接入触点的那一期会换成真机导出的几何，基线随之重跑。

**落点。** 落点服从 N(键心 + (0, b), σ²)，σ 和 b 以键为单位（σ 不小于 0；b 为正表示落点普遍偏下，可以为负）：横向按键宽的中位数、纵向按键高的中位数归一。落在键的矩形里就是按到了它，落在键距或字母区外归最近的键，模拟宿主把键距让给相邻键。大小写、删除、候选栏这些功能键不建模，落在那里的点也归最近的字母键，所以按错率偏低。用户想按的键换成按到的键送进去，落点（积分方格的格心，σ/8 一格）作为按下点一起送。抽一键只用一个均匀随机数，先定按到哪个键、再在这个键的格里定落点，所以同一个种子按到的键与 `--no-touch-points` 逐个相同，`--no-touch-points` 的报告与引擎收到触点之前的平面表基线逐字节相同。

四种模式：

- `none`：按想按的键原样打，不带触点，即桌面和实体键盘的基线；不分 σ 和偏置，每个方案只有一组。
- `clean`：每键都按在本键上（手抖了但打对了），是触点纠错的精度闸：送进去的键和 `none` 相同，只多了落点。落点在按对的那部分格里抽。`--assert-top1-unchanged` 在 clean 集里只要有一条用例的首选和 `none` 不同就以非零退出。加 `--no-touch-points` 时它和 `none` 完全相同。
- `noisy`：至少一键按到了别的键，量召回。按「至少一键按错」的条件分布精确抽样，不反复重抽；σ 为 0 时没有一键会按错，这些用例记在 `skipped` 里。
- `realistic`：不加条件的落点分布，看净收益。

**报告。** 每组配置一项，按音节档（1、2、3–5、6+）和错键数档（0、1、2、3+）分桶。`top1`、`top3`、`top9`（第一页）、`found`、`mrr` 是金标准在整张候选表里的名次；`top1_changed` 和 `gold_demoted` 是计数，拿同一条用例按想按的键原样打出的名次作对照：前者是对照首选是金标准、这次不是，后者是这次名次更靠后或找不到了。种子固定时同一份二进制两次运行的输出逐字节相同：每条用例的随机数流只由种子、方案、模式、σ、偏置和用例序号决定。同一条用例的同一串按键、带同样（量化后）的触点只打一次。

**调参。** `--touch-tuning base=12,scale=8,...` 覆盖引擎的触点计价参数（`base`、`scale`、`sigma_x`、`sigma_y`、`bias_y`、`min`、`max`、`cut`、`show`，意思见 `msime_engine::touch::TouchTuning`），只覆盖给出的几项，报告头里多一行 `touch_tuning`。它经 `host::Session::set_touch_tuning` 设进引擎，只有 Rust 示例能设，宿主经 FFI 设不了。

`rerank_latency` 接受同样的 `--scheme shuangpin --shuangpin-profile <方案> --autocorrect`，再给 `--key-geometry` 和 `--touch-sigma` 时按 `realistic`（或 `--touch-mode` 指定的模式）合成误触和落点，像宿主一样每键带上按下点，量带着按错的键时每次按键的开销；`--no-touch-points` 只送按到的键。`--touch-arms` 把两臂换成都挂模型、一臂送落点一臂不送，配对量出触点计价本身每键多花多少；再加 `--no-touch-points` 两臂都不送（A/A），量的是同一台机器上配对增量本身的噪声。配对增量的 p95 在 A/A 下也不是 0（两次相同的按键各自抖动），所以触点的代价看「with touches 与 flat table 两臂 p95 之差」，并且同一条命令重复至少 5 轮、取中位数并报出各轮的范围，单轮的数字不作数。几何的挑法和 σ、偏置的校验与 `convert_eval` 相同。在这个方案里编不出来的用例不计时，noisy 下没有一键可能按错的用例也不计时（不退回想按的键），两者的条数都打在 stderr；一条不剩时以非零退出。

## 往整句集里加用例

手写不是唯一来源。真实行文自己就是金标准：把句子用 Engine 自己的拼音表转成拼音，再把拼音打回去，首选不是原句的就是一个带已知正确答案、并且带着真实上文的失败用例。三步，最后一步是人。

上文那一列是第 6 列，`sentences-v1.tsv` 的手写行没有它，读作空串，两个既有基线因此逐字节不变。它存在的理由和 `sentences-v1.tsv` 那节说的是同一件事：把 会议 排在 回忆 前面是关于前文的判断，一个没有前文的集合问不出这个问题。**上文是 seed 进已提交历史的，不是当按键重放的**——重放会让每条用例的成绩取决于上一句转得好不好，而那正是逐例测量要排除的混淆。每条用例开始前 `convert_eval` 先清空已提交历史再 seed（`Runtime::clear_context`），因为取消输入不清历史、seed 是追加：此前没有这一步，每条用例都是对着前面所有用例上文的尾部 1024 字节排序的，v2 的 `top1` 因此从 0.308 被压到 0.263、`top5` 从 0.776 压到 0.763，`found` 不受影响。v2 本身也是在同样的累积上文下收割的，所以其中有一部分用例在干净上文下本来就不会错，`top1` 的回升里有这份选择偏差，不全是排序能力。`harvest_eval_set` 已同样修正，以后的收割不再有这个问题。

### 一、收割

```sh
cargo run --release -p msime-input-runtime --example harvest_eval_set -- \
  --resources <已校验的词库目录> \
  --corpus <一行一篇的纯文本> \
  --out target/harvest.tsv \
  --attribution "语料来源与授权"
```

`--limit N` 限收录条数，`--min-chars` / `--max-chars` 限句长。署名写进输出文件头：C4 中文部分是 ODC-BY，LCCC 是 MIT，两者都要求署名跟着文本走，而一份收割出来的句子就是那些文本。

**想要上文列，语料就必须一行一篇、保留标点、句序不变。** 上文取自前一句，所以标点被剥掉或句子被打乱的语料只能永远产出空上文。`chinese-ime-lm` 的 `corpus/fetch.py` 输出就是这样：它的 `segment()` 只保留汉字串并按固定宽度切断，那对训练字模型是对的，对上文列是错的。不要上文的话它照样能用——每行当作一句，上文留空，用例本身仍然成立，`sentences-v1.tsv` 的手写行也没有上文。解压与 JSON 拆包在这个 example 之外做，它只读纯文本，这是它不依赖任何语料格式的原因。

**挂不挂模型，取决于挖来干什么。** 挂上产品在用的权重，挖到的是「产品真正会错的句子」，适合拿去指导训练或改进：第一批不挂模型挖到的 108 条里，重排自己就修好了 80.6%，几乎整批都是产品不需要做的工；挂上之后同一份语料的失败率从 8.5% 降到 3.9%。

**但要建评测集，就不能挂。** 挂着某个模型收割，等于给它出了一张必然考零分的卷子——用例的定义就是「它会错的句子」。实测：挂 4.25M 收割的 1200 条，4.25M 自己在上面 top-1 是 0.000，而没参与收割的 24.9M 是 0.699。两个数字放在一张表里没有任何意义。让引擎单独产出候选，集合才对所有重排器中立。

输出 8 列，比评测集多「当前首选」和「金标准排名」供评审时看。它**不是评测集**：它只证明「解码器没还原出原文」，没有判断过原文是不是该拼音串唯一自然的写法。

### 二、机器初筛

评审要看真实候选，所以先让 `convert_eval` 把收割文件跑一遍并导出。它读第 6 列作上文，多出来的两列忽略：

```sh
cargo run --release -p msime-input-runtime --example convert_eval -- \
  --resources <已校验的词库目录> \
  --set target/harvest.tsv \
  --dump target/harvest.jsonl

TYPESAFE_API_KEY=... scripts/review-harvested-cases.py target/harvest.jsonl target/harvest
```

脚本对每条问四个互不依赖的问题：在解码器实际产出的那些写法之间**做选择**，选中的那条**是不是正确的中文**（无错字、无病句），**是不是一句人会打出来的中文**（而非网页标题或关键词串），以及这串拼音**是不是有不止一种同样自然的写法**。前三项都过才写进 `target/harvest-accepted.tsv`，列与 `sentences-v1.tsv` 一致、可直接粘；其余连同四个分数写进 `target/harvest-flagged.tsv`。3600 条一轮约 294 万 input token，$0.12。

**选择是主判据，成句是否决，歧义只记录不否决。** 歧义这个信号被试过两次，两次都失效：第一版在 >0.40 就否决，砍掉 150 条里的 70 条，而这 70 条的选择全都落在原文上；改成 >0.65 之后，在 C4 语料的 1200 条上仍然挡掉 436 条，**同样是选择全部落在原文**，分数铺在 0.65 到 0.87 之间，与用例是否真的两可没有可见关系——`吃得白白胖胖` 判 0.72，而「吃的白白胖胖」根本不成句。分数仍然写进 flagged 文件，供以后寻找它真正有意义的区间，但不再据此否决。

那 436 条真正缺的是另外两问。C4 是网页文本，收割活下来的有相当一部分是标题和关键词串——`黄页三门峡分站`、`南岗洗车店`、`资江天气`。它们不是有歧义，是**不成句**，拿它们做重排评测，量的是模型给导航栏排序的本事。加上成句这一问后，网页碎片被准确挑出（成句分 0.13 到 0.29），而 `人间正道虽然艰险`、`让我们懂得要用知识改变人生` 这类留下，3600 条里拦下 1039 条。

**第四问「是不是正确的中文」是人工抽样逼出来的。** 加上成句判据之后读了 30 条 accept，仍有三条带着语料自己的错——`人多为患`（应是 人满为患）、`济南是自然风景优美`、`如何考出钢琴`。这类比随机噪声更糟：`人多为患` 惩罚的恰恰是好到能提出 `人满为患` 的那个打分器，**模型越强扣分越多**。

**这一问的阈值也踩了一次坑，处理方式同上：先看分布再定。** 起手定在 0.50，拦下 384 条，抽查发现 0.40–0.49 区间几乎都是正常句子（`整个行业又该何去何从` 0.48、`我为你的成功而鼓掌` 0.41），而真正的病句集中在 0.35 以下（`他负责洗碗和打扰卫生` 0.20、`圆形剧场工作人员是一个快乐的心情` 0.30）。落在 0.35，捞回 357 条。分数在 flagged 文件里，调阈值不需要重跑 API。

**它只提议，不决定，也不是门禁。**

### 三、人工确认，这一步才产生评测集

逐行读 `harvest-accepted.tsv`，问三件事：这串拼音是不是只有原文这一种自然写法？这句话适不适合躺在一个公开仓库里？它是不是以代词开头？

**后两条是机器筛不掉的。** C4 是网页抓取，成人内容、政治敏感内容和营销号文案都在里面，机器判据只问语法和成句，不问该不该进仓库——1105 条的那一轮里手工剔掉了 4 条。以 `ta` 开头的一律剔除（那轮 55 条）：他/她/它 在拼音上不可分辨，没有上文时信息论上就没有正确答案，谁答对都只是语料先验碰巧对上。

拿不准就丢。少一条没关系，多一条两可的句子会让之后每一次比较都测不准。

`flagged` 里 `disagrees-with-original` 那一档通常直接丢：语料自带错别字——LCCC 里有 我说连累我**阿**（该是 啊）、没什么**拉**（该是 啦），这时「金标准」本身就是错的，150 条里有 23 条属于这一档。C4 上这一档占到 1200 条的 447 条，比例高得多，因为网页文本里的错字和残句比对话还密。`not-a-sentence` 那一档同样丢，理由见上。

**收割用哪套配置，就给哪个模型出了一张必然考零分的卷子。** 挂着产品在用的模型收割，挖到的定义就是「这个模型会错的句子」——拿它回过头评测同一个模型，得到的是 0.000，不是模型的能力。这不是假设：1200 条挂 4.25M 收割出来的用例，4.25M 自己在上面 top-1 恰好是 0.000，而没参与收割的 24.9M 是 0.699。**要比较多个模型，收割时不要挂任何模型**，让引擎单独产出候选，这样集合对所有重排器都中立。代价是会挖到一批模型本来就能修好的用例，但对评测而言那正是能区分模型的部分。

并入后重跑 `convert_eval` 并 `--update-baseline`，基线 JSON 才对得上新的集合。新收割的用例不要并进 `sentences-v1.tsv`——两者分布不同，混在一起两边的数字都失去意义；发成独立的 `sentences-harvested-v*.tsv`。

**对话语料的「上文」不是这个意义上的上文。** LCCC 是对话轮次，前一句是对方说的话，而模型把上文当作「我刚提交的内容」。150 条带上文重跑，top-1 从 0.687 掉到 0.667——3 条，噪声内，方向还不对。这说明机制通了，不说明有收益；要上文真正起作用，语料得是保留标点的连续行文。

## 为什么报告要分 source

候选带 `source`，对应 `msime_engine::CandidateSource`。3 音节以上时 Engine 加入词图路径（`sentence_alternatives` 打开时是多条）。Google 回退已删除，source 9 不再占据位置 1。runtime 的 `demote_runner_up_readings` 对 3 字及以上的读法保留三条词图整句，紧跟在第一条之后，其余移到列表末尾；2 字读法只保留一条。

所以位置 1 到底是谁，随输入而变——词图的改动能不能反映到 top-1 也随之而变。`top1_source` 和 `gold_source` 每次运行都记录实际情况，而不是假定其中一种。
